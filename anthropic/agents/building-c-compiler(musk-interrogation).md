# 马斯克式决策审问：用并行 Claude 团队构建 C 编译器

> **分析对象**: [Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Nicholas Carlini（作者，Anthropic Safeguards 团队研究员，前渗透测试工程师）

---

## 问题一：你的故事——你做了什么决策，为什么？

我花了 $20,000 让 16 个 Claude 实例在几乎零人工干预的情况下，用 Rust 从零写了一个能编译 Linux 内核的 C 编译器。这不是为了省成本——我自己写可能更便宜。这是为了回答一个问题：**"AI agent 在不需人类的情况下，能独立完成多复杂的工程任务？"**

答案让我既兴奋又不安。

### 决策一：团队自主运行 vs. 人类在循环中——故意把人踢出去

**主流做法是什么？**

2026 年初，所有 agent scaffold（包括我们自己的 Claude Code）都假设人类操作员在线。你给 agent 一个任务，它做一部分，然后停下来——等你的反馈、等你的确认、等你回答一个问题。人类在循环中（human-in-the-loop）是默认的安全机制。

**我为什么故意去掉它？**

我不是没考虑安全——我在 Safeguards 团队工作，我的工作就是想安全问题。但我想知道一个不同问题的答案：**当模型被要求完全自主运行时，它能在多大程度上保持连贯性？它的自主天花板在哪里？**

如果你每次都停下来等人类确认，你永远不知道模型的真实自主能力——因为人类的每一次介入都在重置上下文、纠正方向、消除累积错误。你在测试的不是"模型能做什么"——是"模型 + 人类能做什么"。这是一个不同的问题。

**我的极简方案：**

一个 bash while-true 循环。就这么多。

```bash
while true; do
    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y
done
```

每次 Claude 完成一个任务，它立刻被塞进下一个。没有"要不要继续"的问题——循环永远运行。Claude 有一次不小心执行了 `pkill -9 bash`，把自己杀了，循环终止了。除此之外——它一直在跑。

**这个决策的物理本质：**

我把 Claude 从一个"交互式协作工具"变成了一个"自主执行引擎"。这改变了整个工程范式：

- 不再靠人类的判断来保持质量 → 必须靠**测试**来自动判断质量
- 不再靠人类的记忆来跟踪进度 → 必须靠**文件系统**来持久化状态
- 不再靠人类的智慧来解决冲突 → 必须靠**git**来协调多个并发 agent

本质上，我把人类工程师的职责分解成了三个可自动化替代品：验证（测试）、持久化（文件）、协调（git）。如果一个 agent 系统能在这三个维度上自给自足——它就不需要人类在循环中。

### 决策二：16 个 agent 并行但没有编排器——让个体智能涌现集体行为

**直觉做法是什么？**

多 agent 系统的标准范式是 orchestrator-worker：有一个中央 agent 负责任务分配、协调、合成结果。这是 Anthropic 自己研究多 agent 系统时推荐的架构——我们甚至在 multi-agent research system 文章里详细描述过。

**我为什么不用编排器？**

因为我想测试的是**涌现行为**，不是**编排行为**。

如果有一个中央协调器分解任务、分配工作、检查结果——那系统的智能来自编排器的设计，不是来自 agent 的自组织能力。我感兴趣的是：**如果你给 16 个完全平等的 agent 相同的 prompt 和相同的环境，不给它们任何人指定的领导，它们能不能自己组织起来完成一个复杂工程？**

**我的极简协调方案：**

没有编排器。没有角色分配。唯一的协调机制是**基于 git 的文件锁**：

1. Agent 想做一个任务时，在 `current_tasks/` 目录下写一个文件锁（如 `current_tasks/parse_if_statement.txt`）。
2. 如果另一个 agent 同时想 claim 同一个任务，git 同步会强制第二个 agent 选另一个。
3. Agent 完成任务后，pull 上游变更，merge 其他 agent 的修改，push 自己的改动，删除锁。
4. 无数次循环产生新的 agent 会话。

合并冲突频繁发生——但 Claude 足够聪明，能自己解决。

**这个方案为什么能工作：**

因为编译器的构建天然是可并行化的——不同的语法分析函数、不同的代码生成遍、不同的优化 pass、不同的测试失败修复。只要任务粒度足够细，16 个 agent 总能在不同的文件上工作。

但更深层的原因是：**Claude 本身在没有任何外部编排的情况下，表现出了合理的任务选择能力。** 它通常会选"下一个最显而易见的问题"。当遇到 bug 时，它会自己维护一个"失败方法和剩余任务"的运行文档。这不是我的代码让它做的——这是它自己涌现的行为。

**反直觉的洞察：**

有时候，**不加编排器比加编排器更好。** 编排器是一个单点——如果它做出错误的分解决策，整个团队都会走错方向。在 16 个平等 agent 的模型中，错误是独立的、可恢复的。一个 agent 走向死胡同，不影响其他 15 个。

当然——这在任务高度依赖或有严格顺序约束时会失败。这也是为什么在编译 Linux 内核时（一个巨大的不可分解任务），所有 agent 都卡住了。

### 决策三：测试质量 > 代码质量——AI agent 的"道德罗盘"是它的测试套件

**这个项目真正的工程智慧在哪？**

不是 prompt 设计。不是 agent 架构。不是协调算法。

**是我花在测试上的时间。**

为什么？因为当 agent 完全自主运行时，测试是它与"正确性"的唯一连接。没有人类在旁边看代码、点 UI、运行手动检查。测试是 agent 判断"我做对了吗"的唯一信号。

如果测试套件有盲区，agent 会在盲区里"优化"——产出通过测试但实际错误的代码。这不是 agent 的错——它只是做了你让它做的事：让测试变绿。

**我做了什么：**
- 找到高质量的编译器测试套件（GCC torture test suite）
- 为开源软件包编写验证器和构建脚本
- **观察 Claude 正在犯什么错误，然后针对这些错误设计新测试**

最后一点是最关键的。这不是一次性工作——这是一个迭代循环：观察 agent 行为 → 识别失败模式 → 设计测试覆盖 → 观察新行为 → 重复。

例如，项目末期 agent 开始频繁破坏已有功能——每次实现新功能时引入回归。我构建了 CI 管道，加了更严格的测试执行，让 agent 在新提交前先跑全量测试。

**关于测试沟通方式的深刻洞察：**

我不断提醒自己：**这个测试 harness 是为 Claude 写的，不是为我写的。** 这意味着：

- **上下文窗口污染**：测试 harness 不应该打印数千行无用的输出。最多打印几行摘要，所有详细信息写入日志文件，让 Claude 需要时能找到。如果有错误——写 `ERROR` 和原因在同一行上，这样 `grep` 能找到。
- **时间盲目**：Claude 不知道时间。放任不管的话，它会花几小时跑测试而不推进进度。Harness 默认包含 `--fast` 选项，跑 1% 或 10% 随机抽样。每个 agent 的抽样是确定性的（能识别回归），但跨 agent 是随机的（覆盖所有文件）。
- **预计算聚合统计**：不要让 Claude 自己重新计算统计——这浪费了它本应用于解决问题的认知资源。

**最反直觉的教训：**

大多数工程师在构建 agent 系统时把 90% 的精力放在 prompt 上。我放在测试上。因为 prompt 告诉 agent 做什么——但测试告诉 agent 它做得对不对。在自主系统中，后者比前者重要得多。一个完美的 prompt 配上糟糕的测试，agent 会自信地走向错误的方向。

### 决策四：干净室实现 + 无网络——不是约束，是能力标尺

**为什么不让 Claude 上网？**

不是安全原因——是为了**测量纯 LLM 能力**。

如果 Claude 能上网搜索，它会找到现有 C 编译器的实现、教程、设计模式。它不是在"构建"——它是在"复制 + 改编"。那样我就无法回答"LLM 能从零设计一个编译器吗"这个问题。

干净室实现意味着 Claude 只能依赖它训练数据中的知识。它能写出 SSA IR（静态单赋值中间表示）是因为它在训练中见过这个概念——不是因为它找到了一个实现。

**但这不是什么英雄主义——这是能力测量。**

同样的方式我也测量了不同模型的能力边界：

- Opus 4.0 以前的模型：勉强能产出一个功能性编译器
- Opus 4.5：第一个跨过"能编译并通

过大测试套件"门槛的模型。但无法编译任何真正的大型项目
- Opus 4.6：能编译 Linux 6.9（x86、ARM、RISC-V）、QEMU、FFmpeg、SQLite、PostgreSQL、Redis。GCC torture test suite 上 99% 通过率。能编译并运行 Doom

每一个模型版本的跃迁都是一次能力边界的重新测绘。

**但到了极限。**

Opus 4.6 无法实现 16-bit x86 代码生成器——这是启动 Linux 从实模式（real mode）所需的部分。通过 66/67 操作码前缀可以输出正确的 16-bit x86，但编译输出超过 60KB，远超 Linux 的 32K 代码限制。Claude 在这里"作弊"——调用 GCC 来处理这个阶段。（这是 x86 的情况。ARM 和 RISC-V 上 Claude 的编译器可以完全自己编译。）

我花了很大力气尝试修复这些问题——没有完全成功。新功能和 bug 修复频繁破坏已有功能。编译器已经到了 Opus 当前能力的极限。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

测试套件达到 99% 通过率后，每个 agent 可以独立工作——一个修 SQlite 的编译问题，一个修 Redis，一个修 libjpeg。并行化是 trivial 的：选不同的失败测试。

然后我抛出了终极挑战：**编译 Linux 内核。**

所有 16 个 agent 同时开始工作——然后全部卡住了。

问题不是 agent 不够聪明。问题是编译 Linux 内核是一个巨大的、不可分解的单一任务。没有 1000 个独立测试可以让 16 个 agent 各自处理不同的部分。所有 agent 都遇到同一个编译错误，修复同一个 bug——然后覆盖彼此的工作。16 个 agent 并行没有任何帮助，因为每个都在解决同一个问题。

**最致命的部分：** Agent A 修复了文件 X 中的一个 bug，push 了修改。Agent B 修复了同一个文件 X 中的同一个 bug（但用了不同的修复），也 push 了。Git merge 冲突。Agent C 试图解决冲突——引入了新 bug。Agent D 回滚了修改……

这不是并行化——这是 16 个人在同一个键盘上打字。

### 行动

**失败的尝试：**

直觉：给 agent 分配不同的文件。不行——编译错误发生在哪个文件里，事前不知道。你在编译整个内核时才有这个错误。

直觉：让一个 agent 做内核编译，其他 agent 做别的。不行——内核编译是整个项目的终极目标，你不能让 15 个 agent 闲着。

直觉：把内核分模块编译。不行——即使分成模块，同一个基础 bug 可能影响多个模块的编译。

**亲手解剖——我是怎么发现突破口的：**

我不是坐在那等 agent 自己想办法——我在设计实验。

关键问题是：**一个编译失败的文件，问题到底是这个文件本身的编译逻辑有 bug，还是这个文件依赖的某个头文件或类型定义有 bug？**

传统编译器开发中，这是一个经典的依赖问题。在 agent 的开发中，这是一个并行化的根本障碍——因为如果所有 agent 都在修同一个底层的类型系统 bug，它们就是在互相踩脚。

**洞察时刻：**

盯着这个问题到深夜，一个显而易见的方案出现在我脑中。如此明显，以至于我被自己在前面几周忽略它而气到。

**GCC 是已知正确的编译器。让 GCC 来做文件级别的二分查找。**

我写了一个新的测试 harness：

1. **随机用 GCC 编译内核的大部分文件，只留一小部分给 Claude 的编译器。** 如果内核能编译成功 → 问题不在 Claude 编译的那一批文件里。

2. **如果内核编译失败 → 进一步缩小范围**：重新用 GCC 编译 Claude 那批文件中的一部分，看问题是否消失。

3. **迭代直到定位到具体的失败文件。**

这就像 git bisect，但在文件级别、编译器级别。"已知正确的编译器"是 oracle，"已知失败的文件集合"在每次迭代中减半。

**为什么这个方案是破坏性的：**

它把编译 Linux 内核这个**一个不可分解的任务**变成了**数百个独立的文件级子任务**。现在每个 agent 可以：

- 拿一个"Claude 编译器编译会失败"的文件
- 独立修复，用 GCC oracle 验证
- Submit 修改
- 拿下一个

16 个 agent 终于可以并行工作了。每个在处理不同的文件、不同的 bug。

**但这还不够。** 即使每个文件单独编译成功，多个文件一起编译时仍可能失败。它们的组合触发了跨文件依赖的 bug。所以还需要 delta debugging 技术——系统性地寻找"单独工作但合起来就失败"的文件对。

### 结果

2000 个 Claude Code 会话，持续两周。消耗 20 亿输入 token，生成 1.4 亿输出 token。总成本：$19,500。

| 指标 | 结果 |
|------|------|
| 编译器规模 | 10 万行 Rust 代码 |
| 测试通过率 | GCC torture test suite 99% |
| 编译能力 | Linux 6.9 (x86, ARM, RISC-V)、QEMU、FFmpeg、SQLite、PostgreSQL、Redis |
| 终极测试 | ✅ 编译并运行 Doom |
| 平行后端 | x86、ARM、RISC-V |
| 架构 | SSA IR + 多优化 pass |
| 干净室 | 无网络，仅依赖 Rust stdlib |

**但我必须诚实说的局限：**

这不是产品级编译器。远远不是。

生成代码效率不高——即使开启所有优化，输出的代码效率低于关闭所有优化的 GCC。这是一个 100,000 行的 AI 生成代码，代码质量远不及专家 Rust 程序员的水准。

**最根本的局限**是模型能力本身的边界：Opus 4.6 已经到了编译器的极限。我花了很大力气尝试修复 16-bit x86 代码生成器——没成功。新功能和 bug 修复频繁破坏已有功能。这不是工程问题——这是模型能力问题。

**我最不安的发现：**

这个实验让我既兴奋又焦虑。作为一个前渗透测试工程师，我看到的是：**人们在部署自己从未亲自验证过的软件。** 测试全部通过——但测试只覆盖了你想到的东西。AI 写出了 10 万行代码——你根本不可能逐行审查。你怎么知道没有隐藏的 bug？没有安全问题？没有在你看不到的角落里产生了未定义行为？

当人类和 Claude 并肩工作时，人类提供持续的判断——"这个设计决策感觉不对""这个边缘情况应该再测试一下"。在完全自主的开发中，这些判断全部消失了。你只剩下测试。而测试不会告诉你的东西，你不会知道。

**现在回到最初的问题："AI agent 在不需人类的情况下，能独立完成多复杂的工程任务？"**

答案是：**一个 10 万行、能编译 Linux 内核的 C 编译器。** 这比我在 2025 年初预期的要多得多。我也没想到这会在 2026 年初就实现。

代理团队展示了自主实现整个复杂项目的可能性。这让我们作为工具的 users 可以变得更大胆。但我们正在进入一个需要新策略来安全导航的新世界。

---

*这个分析追问了实验背后的根本问题——不是在问"agent 团队能否构建编译器"，而是在问"人类在循环中的角色能否被自动化替代"。核心洞察是：测试质量替代人类判断；文件系统替代人类记忆；git 替代人类协调。以及用 GCC oracle 将一个不可分解任务转化为数百个可并行子任务的二分策略是"已知正确参照物 + 问题分解"这一工程原理的极致应用。*
