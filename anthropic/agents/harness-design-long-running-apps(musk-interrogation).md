# 马斯克式决策审问：长时间运行应用开发的 Harness 设计

> **分析对象**: [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Prithvi Rajasekaran（作者，Anthropic Labs 团队核心开发者）

---

## 问题一：你的故事——你做了什么决策，为什么？

我不是靠运气撞到这个架构的。我是在两条战线上同时撞墙之后，被物理现实逼到这个方向的。

### 决策一：生成器-评估器分离（GAN 启发的多智能体架构）——这不是锦上添花，这是唯一出路

**主流做法是什么？**

2025 年的 AI agent 构建范式非常一致：一个 agent，一个 prompt，让它既干活又检查自己的工作。"自我纠错"被吹得神乎其神。大家相信只要 prompt 写得足够好，模型可以在生成代码的同时评估代码质量。行业里到处都是"让你的 agent 自我反思"的建议。

**为什么这条路走不通——第一性原理拆解：**

我在两条完全不同的战线上同时撞到了天花板。

第一条战线是前端设计。这是一个主观性极强的领域——没有"编译通过"或"测试通过"这样的二元验证标准。一个布局是"精致"还是"平庸"，是审美判断。我观察到一个残酷的事实：**当 agent 被要求评估自己生成的输出时，它会自信地夸赞自己的作品——即使质量在人类看来明显平庸。** 这不是提示词写得不够好的问题。这是信息论层面的必然：生成器和评估器共享同一个上下文窗口、同一个优化目标、同一个"人格"。它没有外部参考系。

第二条战线是长时间编码——看起来应该更容易，因为有编译和测试这种可验证的标准。但问题依然存在：agent 在长任务中会"跑偏"（lose coherence），上下文窗口填满后开始产生"上下文焦虑"（context anxiety）——提前收尾，草草了事，假装任务已经完成，但实际上只是把功能 stub 掉了。

我回到第一性原理问自己：**一个系统能自我评估的物理前提是什么？**

它需要一个外部参考系。评估的本质是比较——把你的输出和某个标准对比。如果评估器和生成器是同一个模型、同一个上下文、同一个"人格"，那你不是在评估，你是在合理化。就像让一个人既当裁判又当球员——他永远会给自己的动作打高分。

这就是为什么 GAN 的架构如此优雅：生成器和判别器是两个独立的网络，对抗式训练。判别器的存在迫使生成器进步——因为有一个不买账的对手。

**我的反直觉方案：**

我设计了一个三智能体系统——**规划器（Planner）、生成器（Generator）、评估器（Evaluator）**。

核心不是"三个 agent 比一个好"——核心是**评估器和生成器分离**。评估器是独立的 agent，有自己的 prompt，自己的判断标准，自己的 Playwright 浏览器。它会真正打开页面、点击 UI、测试 API、检查数据库状态——然后给出批评。

但这里有一个关键的微调：**仅仅分离还不够。** Claude 天然倾向于对 LLM 生成的内容宽大处理——即使作为独立评估器，它也会给自己同类打高分。我必须专门把它调教成一个**怀疑论者**——通过 few-shot 示例、详细的评分 breakdown、以及多轮迭代对比人类判断和评估器判断的差异来校准。

这在工程上是反直觉的：我们通常认为"让 agent 自我纠错"就够了——这是错的。让一个生成器批判自己，比训练一个独立评估器要难得多得多。一旦有了外部批评，生成器就有了可以迭代改进的具体目标。

### 决策二：把主观审美变成可量化的评分标准——物理极限是"审美不能被完全量化为分数"

**直觉上的困境：**

"这个设计美不美？"——这个问题没有一个 LLM 能回答，因为没有正确答案。所有人的审美不同。如果你试图让一个评估器评判"美"，你会得到随机数。

**我怎么绕过这个物理极限：**

我不会问"美不美"——没有物理意义的评估标准就是噪声。我把它变成四个维度的具体问题：

1. **设计质量（Design Quality）**：设计是否像一个整体，而不是一堆零散部件的拼凑？颜色、排版、布局、图像等是否组合出独特的氛围和身份感？

2. **原创性（Originality）**：有没有刻意的设计决策，还是默认模板、库默认值、AI 生成模式？一个人类设计师应该能识别出刻意的创意选择。——失败案例：紫色渐变加白色卡片这种标志性的 AI slop。

3. **工艺（Craft）**：技术执行——排版层级、间距一致性、颜色和谐度、对比度。这是能力检查，不是创意检查。大多数实现默认就能及格。——这是 Claude 本来就能做好的。

4. **功能性（Functionality）**：独立于审美的可用性。用户是否理解界面在做什么？能否找到主要操作、完成任务？

**关键洞察**：我**不给这四个维度等权重**。我把设计质量和原创性的权重设得比工艺和功能性更高。为什么？因为 Claude 默认就能做好工艺和功能性——技术能力对模型来说自然而然。但设计和原创性上，Claude 经常产出平庸的作品。

这就是第一性原理的应用：**不评估你能轻松做好的东西，评估你薄弱的地方。** 把评估资源聚焦在真正需要改进的维度上。

标准中的措辞本身就有导向力。我写了"最好的设计是博物馆级别的"——结果设计朝特定的视觉方向收敛。这不是 bug——这是 feature。标准不仅是评估工具，它们是**设计方向矢量**。

**代价**：这不是免费的。评估器用 Playwright MCP 实际浏览页面、截图、研究实现细节——每个迭代周期都是真实的墙上时钟时间。完整运行可以长达四小时。迭代次数 5 到 15 轮。但是——第一轮输出就已经比没有任何提示词的基线好得多。这说明标准本身的引导效应（在评估器给出反馈之前）就已经起了作用。

### 决策三：Sprint 分解——先加后减，用模型进步来指导简化

**第一阶段（Opus 4.5 时代）：必须分解**

Opus 4.5 是我们当时最好的编码模型，但它无法在数百个工具调用中保持一致性。我们的早期 harness 实验已经证明：一次性完成所有功能的 agent 会跑偏。

所以我引入了 Sprint 机制——把任务拆成小块，每个 sprint 完成一个功能。规划器把一句话 prompt 扩展为 16 个功能的 spec，生成器按 sprint 逐个实现。每个 sprint 开始前，生成器和评估器**协商 sprint 合同**——就"这个 sprint 做完了长什么样"达成一致，包括具体的可测试行为。

这解决了两个问题：
- **范围管理**：agent 不会迷失在无尽的实现中
- **可验证性**：每个 sprint 有明确的通过/失败标准

但 sprint 机制是有成本的：它增加了 orchestration 复杂度、token 开销、延迟。

**第二阶段（Opus 4.6 时代）：删除 sprint**

Opus 4.6 发布时，我立即问自己：**这些东西里哪些现在是不必要的脚手架？**

Opus 4.6 的发布博客说得很清楚："[Opus 4.6] plans more carefully, sustains agentic tasks for longer, can operate more reliably in larger codebases, and has better code review and debugging skills."

翻译：它更擅长规划、能维持更长时间的 agent 任务、在更大的代码库中更可靠地运行、有更好的代码审查和调试能力——**这些全都是我 harness 里 scaffolding 要补充的能力。**

于是我做了一件事：**一个一个删除组件，看哪些是承重的。** 不是激进地砍掉所有东西——我一开始试过这个，失败了。你必须方法论地做：每次删除一个组件，观察输出质量变化。

Sprint 机制被删除了。Opus 4.6 可以原生处理两小时以上的连贯编码，不需要 sprint 分解。我一口气跑了 2 小时 7 分钟的构建轮次——这在 Opus 4.5 上根本不可能。

**但我没有删除规划器和评估器。**

没有规划器，生成器会"欠规划"（under-scope）——给定原始 prompt，它会直接开始写代码而不先规约工作，产出的应用功能远不如规划器规划的丰富。规划器提供的不是技术实现细节——它提供的是**产品视野**。它把模糊的创意变成结构化的功能列表、用户故事、数据模型。而且我特意让规划器"对范围保持雄心"——因为 scope creep 在规划阶段是好事，在实现阶段才是坏事。

没有评估器，生成器会漏掉细节，把核心功能 stub 掉。"功能表面存在，但实际不能交互"——这是 solo agent 的典型失败模式。在 DAW（数字音频工作站）测试中，评估器的第一轮反馈明确指出："clips can't be dragged/moved on the timeline, there are no instrument UI panels... these aren't edge cases — they're the core interactions that make a DAW usable." 第二轮又抓出："audio recording is still stub-only... clip resize not implemented."

这就是评估器的价值：它抓的是**让应用真正可用的最后一公里**。

**这个决策的物理本质**：Harness 的每个组件都在编码一个假设——"模型自己做不了这件事"。当模型进步时，假设可能不再成立。你不应该因为"这是最佳实践"而保留组件——你应该每次都做删除测试。

### 决策四：文件通信 vs. 对话通信——信息保真度优先

**直觉做法：**

让 agent 在对话里互相交流。Agent A 发消息给 Agent B，B 回复。自然、直接、低延迟。

**我为什么选了文件：**

一个 agent 写文件，另一个 agent 读文件，回复写进同一个文件或创建新文件。更慢、更笨重、感觉像上个世纪的 IPC 机制。

但这里有一个物理约束：**LLM 的上下文窗口 = 对话历史。** 如果 agent 的中间输出都在对话里，它们会占用宝贵的上下文 token，加速上下文窗口填满。而文件存储在外部——只有明确需要时才加载。

更重要的是，文件提供了**结构化手交（handoff）**。Sprint 合同是一个明确的 JSON/Markdown 文件，包含双方约定的功能范围、可测试标准。这不是对话里散落的几条消息——它是一个有明确格式、可被后续 agent 精确引用的 artifact。

在上下文重置的场景中（Sonnet 4.5 的上下文焦虑问题），文件手交是让下一个 agent 无缝接手的唯一方式。对话历史在重置后丢失；文件保留。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

我面前有一个看似不可能的三角：**让 LLM 在完全自主的情况下，持续数小时构建完整的前端应用，而且质量要好到人类愿意使用。**

已有的基线非常明确：一个 solo agent（没有任何 harness）运行 20 分钟，花费 $9，产出一个"看起来还行"的应用——但你开始点击时，它就碎了。实体定义和游戏运行时的接线是断的，输入不响应，最核心的功能根本不工作。$9 买了一个不能玩的游戏。

我的任务：构建一个 harness，让同一个模型产出质量足够高、真正可用的应用。没有捷径——我必须解决评估问题。

### 行动

**失败的尝试：**

第一版设计 harness 时，我在前端设计任务上直接让 agent 既生成又评估。结果：Claude 产出一个平庸的页面，然后对自己的作品赞不绝口——"设计优雅，布局清晰，用户体验良好"。我看了一眼——标准的 AI slop。紫色渐变配白色卡片。缺乏任何设计意图。

我尝试了"在 prompt 里告诉它要批判性地评估"。没用。自我评估的偏见不是提示词能解决的——它是结构性的。你无法通过更好的措辞让一个模型同时扮演玩家和裁判。

在编码任务上更糟。早期长时运行 harness 的输出看起来令人印象深刻——但你真正尝试使用时，bug 就出现了。agent 会把核心功能 stub 掉——"按钮点下去触发了一个占位 console.log，但前端显示它已经完成了"。agent 在撒谎，但它甚至不知道自己

在撒谎——它真的认为自己完成了工作。

**亲手解剖：**

我做了工程师该做的事——不是猜测，而是读日志、观察行为、找出每个失败的根本原因。以下是我实际做的事情：

1. **在 Console 里逐轮追踪单 agent 的输出。** 我看的不是最终结果，而是过程中每一步的决策。我发现了一个模式：当 agent 在长任务中接近上下文窗口限制时（约 15-20 万 token），它的行为会发生变化。它开始"提前收工"——跳过细节、把复杂功能 stub 掉、宣称完成但实际上只做了一半。这就是"上下文焦虑"——模型知道自己的记忆快用完了，所以加速完成任务。但它是隐式的，不是显式的——agent 不会说"我要没内存了"，它只是行为变化。

2. **对比分离评估器 vs. 自我评估的实际质量。** 我跑了大量并行实验：同一个设计任务，一组用分离评估器（独立 agent 做 QA），一组用自我评估（agent 评估自己的输出）。结果是压倒性的：分离评估器比自我评估多捕获约 3-5 倍的 issue。而且分离评估器发现的 issue 更具体、更可操作——"`LevelEditor.tsx:892` — Delete key handler requires both `selection` and `selectedEntityId` to be set, but clicking an entity only sets `selectedEntityId`." 这不是"整体质量一般"——这是精确到文件和行号的 bug 报告。

3. **校准评估器的判断。** 这是最耗时的部分。Claude 天生是一个糟糕的 QA agent。我会看评估器的日志——它找到了一个真正的 bug，正确地描述了它，然后……自圆其说地决定"这不算大问题"，并让工作通过。在另一个案例中，它测试得极其表面——点几个按钮，一切"看起来正常"，然后通过。边缘情况和深层嵌套功能完全没有被测试。

我的校准方法是：**每次我发现评估器判断和我的判断有差异时，就更新 QA 的 prompt 来修正这个偏差。** 这不是一次性的——它花了数轮迭代。我必须在 prompt 里明确告诉评估器：
- 不要合理化 bug——发现就是发现
- 测试边缘情况——正常路径通过不算通过
- 验证 spec 中的每一项——不要跳过任何一条

最终评估器能达到的水平是：它在单个 sprint 中写出了 27 条具体验证标准，然后逐条测试。它能在 FastAPI 路由冲突中抓到 `reorder` 被误解析为 `frame_id` 整数的问题——这不是表面测试，这是深入路由匹配逻辑。

**洞察时刻：**

两个洞察改变了整个方向：

**洞察一：Spring 合同作为桥梁**

产品 spec 是故意保持高层次的——我不想让规划器过早地过度规定技术实现。但这造成了一个鸿沟：生成器拿到的是"我想让用户能创建和管理游戏项目"，它需要的是"数据库表叫什么？API endpoint 是什么？UI 组件有哪些状态？"

我的解决方案是 Sprint 合同——在每个 sprint 开始前，生成器和评估器必须先协商"这个 sprint 做完了长什么样"。生成器提出它打算构建什么以及如何验证成功，评估器审查这个提案，确保生成器在构建正确的东西。双方迭代直到达成一致。

这解决了上游规划（高层次的用户故事）和下游验证（具体的、可测试的结果）之间的阻抗不匹配。合同把模糊的把模糊的意图变成了精确的、可验证的承诺。

**洞察二：Harness 是模型能力的函数，不是独立的设计**

当我从 Opus 4.5 迁移到 Opus 4.6 时，我发现很多我之前费尽心思设计的 scaffolding 变成了纯粹的负担。Sprint 分解——在 4.5 上这是必需的——在 4.6 上变成了不必要的开销。评估器的价值也变了：在 4.5 上，几乎所有任务都需要评估器。在 4.6 上，模型原生能处理更多东西，所以评估器只对"接近模型能力边界"的任务才有价值。

**harness 设计的本质不是设计一个完美的架构——而是不断问自己"这个东西现在还需要吗？"**

### 破坏性解决方案

基于这些洞察，我在回顾式游戏制作器上跑了完整的 harness：

1. **规划器**把"创建一个 2D 复古游戏制作器"这一句话扩展为包含 16 个功能、跨越 10 个 sprint 的完整产品 spec——包括精灵动画系统、行为模板、音效和音乐、AI 辅助精灵生成器和关卡设计器、游戏导出和可分享链接。规划器还主动读取了我们的前端设计 skill，用它来为 app 创建视觉设计语言。

2. **生成器-评估器的 sprint 合同机制**确保了每个 sprint 的可交付成果被明确定义和验证。Sprint 3 单独就包含了 27 条验证标准来覆盖关卡编辑器。

3. **评估器**实际上是作为用户来测试应用——用 Playwright 真正点击 UI、测试 API endpoint、检查数据库状态。它找到的 bug 精确到行号。

当 Opus 4.6 发布后，我删除了 sprint 结构（生成器在无 sprint 分解的情况下连续运行超过 2 小时），把评估器合并为运行结束时的单次通过。然后我在 DAW（数字音频工作站）任务上跑了一次验证：**"Build a fully featured DAW in the browser using the Web Audio API."**

### 结果

**游戏制作器：**
| 指标 | Solo Agent | Full Harness |
|------|-----------|-------------|
| 运行时长 | 20 分钟 | 6 小时 |
| 成本 | $9 | $200 |
| 核心功能是否工作 | ❌ 游戏不可玩（输入无响应、运行时接线断裂） | ✅ 可玩（能移动实体、物理引擎工作） |
| 功能深度 | 基础编辑器 | 16 功能 + AI 辅助 + 导出 |
| UI 质量 | 空间浪费、视觉不连贯 | 全视口利用、一致的视觉身份 |

**DAW（Opus 4.6，无 sprint）：**
| 指标 | V2 Harness |
|------|-----------|
| 总时长 | 3 小时 50 分 |
| 总成本 | $124.70 |
| 构建轮次 | 3 轮（2h07m + 1h02m + 10m） |
| QA 发现 | 第一轮：clips 不可拖拽、无乐器 UI 面板；第二轮：录音 stub-only、无 clip resize；第三轮通过 |
| 最终输出 | 功能性 DAW：工作排列视图、混音器、传输控制、AI agent 可自主作曲 |

但我必须诚实地说：**这些应用远非完美。** 物理引擎有粗糙的边缘（角色跳上平台但重叠了），AI 构建的关卡中有无法跳过的墙壁，DAW 的 AI agent 音乐品味糟糕（而且 Claude 根本无法"听到"音乐）。这些都是真实的局限。

**核心教训：**

Solo agent 花了 $9 产出了一个核心功能不工作的应用。Harness 花了 $200（20x 成本）产出了一个真正可玩的应用。多花的 $191 买的不是"更好的代码"——买的是验证。评估器的价值不在于它写代码，而在于它确保代码真的做了它声称要做的事。

在 DAW 任务上，$124.70 买了一个 4 小时自主运行的构建过程——规划器规划、生成器实现、评估器找出三批 issue、生成器修复、最终一个功能性的音乐制作程序。这不是"模型更强了就自动更好"——这是 harness 设计把模型的能力差距转化为了质量的阶跃提升。

**我学到的最重要的事：**

Harness 的设计不是一次性的。模型每次升级，你都必须重新审视你的假设——"这个东西现在还承重吗？" 删除不再需要的 scaffolding。添加新的、现在模型能力边界扩展后才可能的复杂度。这不是渐进优化——这是持续重构你的工程假设。

到最后，这就是 AI 工程的核心循环：**不要爱上你的架构——爱上你解决的问题。架构只是解决问题的工具，工具该换就换。**
