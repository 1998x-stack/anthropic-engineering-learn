# 马斯克式决策审问：扩展 Managed Agents——将大脑与双手解耦

> **分析对象**: [Scaling Managed Agents: Decoupling the brain from the hands](https://www.anthropic.com/engineering/managed-agents)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Lance Martin, Gabe Cemaj, Michael Cohen（作者，Managed Agents 架构师）

---

## 问题一：你的故事——你做了什么决策，为什么？

我们在构建一个 agent 基础设施时，遇到了一个几十年前的操作系统设计已经解决的问题。我们当时不知道——我们在忙着给"宠物"做人工呼吸。

一台出故障的容器。里面有一个正在运行的 agent 会话。唯一能看到它内部的窗口是 WebSocket 事件流——但它不能告诉你故障发生在哪里。Harness 的 bug？事件流的丢包？容器离线？三个完全不同的根因，从外部看起来一模一样。

要弄清楚发生了什么，工程师必须打开容器内部的 shell。但容器里存着用户数据——这意味着我们实际上丧失了调试能力。

这就是为什么我重新发明了操作系统——在 agent 的层面。

### 决策一：虚拟化 Agent 组件——从程序到操作系统的心智模型迁移

**直觉做法是什么？**

把所有东西塞进一个容器。Session 数据、agent harness、沙箱——全在一起。文件编辑是直接 syscall，没有服务边界需要设计。简单、快速、符合直觉。

**为什么这是"养宠物"的灾难：**

一个容器 = 一个不可替代的实体。如果它挂了——它的 session 就丢了。如果它不响应——你必须"护理"它恢复健康。这不是基础设施——这是养了一只仓鼠。

在 Pets vs. Cattle 的类比中：宠物是有名字的、手工照料的个体，你不能承受失去它。牛是可替换的——一头病了，换一头。**我们把 agent 容器养成了宠物。**

更深层的问题：耦合意味着**任何一部分的故障都拖累整个系统**。Harness 里的 bug → 容器挂掉 → Session 丢失。事件流丢包 → 用户看到超时 → 无法区分根因。一个假设（"Claude 操作的东西和 harness 在同一个容器里"）变成了客户连接 VPC 时的架构障碍。

**我的反直觉方案——操作系统类比：**

几十年前，操作系统设计者面对的是同一个问题：如何设计一个系统，能运行"尚未被发明的程序"？

他们的答案：**虚拟化硬件为抽象。** Process、file——这些接口足够通用，能容纳不存在的程序。`read()` 命令不知道也不关心它是在读 1970 年代的磁盘还是现代 SSD。接口保持稳定，实现随意替换。

我把同样的模式应用到 agent 系统。

Managed Agents 虚拟化了 agent 的三个组件：

1. **Session（会话）：** 一切发生过的 append-only 日志。不是 Claude 的上下文窗口——是上下文的**持久化存储**。接口：`getEvents()`——大脑可以按位置切片查询事件流。

2. **Harness（线束）：** 调用 Claude 并将 Claude 的工具调用路由到相关基础设施的循环。接口：`wake(sessionId)` + `emitEvent(id, event)`——无状态的、可崩溃的、可重启的。

3. **Sandbox（沙箱）：** Claude 可以运行代码和编辑文件的执行环境。接口：`execute(name, input) → string`——一个名字和输入进去，一个字符串返回。Harness 不关心沙箱是容器、手机、还是宝可梦模拟器。

**这些接口的物理本质：**

它们是我对"agent 系统在 5 年、10 年后仍然需要什么"的赌注。我对接口的形状有强烈意见——但对接口背后的实现没有意见。Session 必须是持久的、可查询的。Harness 必须是无状态的、可恢复的。Sandbox 必须是可替换的、不可信的。但 Session 的存储引擎可以是今天的 PostgreSQL、明天的 FoundationDB。Harness 的编排引擎可以是今天的 Kubernetes deployment、明天的自定义调度器。

### 决策二：大脑从容器中移出——TTFT 下降 60%（p50）和 90%+（p95）

**耦合架构下的物理现实：**

当大脑（harness）和双手（sandbox）在同一个容器里时——每次启动一个 agent 会话，你都必须先配置容器、克隆仓库、启动进程、从服务器拉取待处理事件。**每个会话支付全部容器设置成本——即使这个会话根本不需要沙箱。**

这个死时间表现为 Time-to-First-Token（TTFT）——用户在提交任务后多久看到第一个响应 token。这是用户最**感觉**到的延迟。

进一步——当你需要多个大脑时，你需要多个容器。一个大脑 = 一个容器 = 一份完整的设置成本。Scaling 变成了复制宠物。

**解耦后的物理现实：**

大脑是一个无状态 harness，运行在容器之外。双手是按需配置的沙箱，通过 `execute(name, input) → string` 调用。

结果：
- 不需要容器的会话 → 不需要等待容器。推理从编排层拉取 session log 的待处理事件开始。
- 需要容器的会话 → 通过工具调用按需配置。
- 容器死了 → harness 把失败作为工具调用错误捕获，传给 Claude。Claude 决定重试 → 用标准配方 `provision({resources})` 重新初始化一个新容器。不需要护理。

**量化影响：**

p50 TTFT 下降了约 60%。p95 下降了超过 90%。

这是延迟曲线尾部的巨大改善——那些最慢的 5% 的请求，用户在最长等待的场景，被消除了。

**物理本质：**

我们不是在优化代码——我们是在消除等待。TTFT 的瓶颈不是推理速度（那是模型层面的）。瓶颈是**基础设施准备时间**——配置容器、克隆仓库、启动进程。把大脑从容器中移出意味着推理可以在基础设施准备好之前就开始——或者根本不需要基础设施就能开始。

### 决策三：Session = 上下文窗口外的持久化上下文对象——对抗"上下文经济的不可逆性"

**主流做法的问题：**

长时任务超过上下文窗口限制时，标准答案都是做不可逆的决策——压缩（保留摘要，丢弃细节）、上下文修剪（删除旧的工具结果和 thinking block）。

问题是：**你不知道未来的推理回合需要哪些 token。** 一旦你在第 3 步压缩时丢弃了"看起来不重要的细节"——第 15 步发现自己需要那个细节时，它永远消失了。压缩是对未来的赌注——而且你经常赌错。

**我的替代方案——Session 作为查询接口而不是存储方案：**

Session 不是 Claude 的上下文窗口——Session 是**窗口外的持久化事件日志**。

接口 `getEvents()` 让大脑按位置切片查询事件流。大脑可以：
- 从上次停止阅读的地方继续
- 回退到某个特定时刻之前的几个事件看前因
- 重新读取某个特定动作之前的上下文

任何获取的事件都可以在 harness 中被转换后再传入 Claude 的上下文窗口——包括为实现高 prompt cache 命中率而做的上下文组织。

**这个设计的物理本质：**

我把"上下文存储"和"上下文管理"两个关注点分离了。Session 只保证一件事：**上下文是持久的、可查询的。** 它不管你怎么用。Harness 负责具体的上下文工程——压缩策略、缓存优化、修剪规则——这些会随着模型变化而改变。

这就像数据库的存储引擎和查询优化器分离：存储引擎保证数据持久性和可检索性。查询优化器决定哪些数据在什么时候以什么形式出现在查询结果中。互不干扰，各自进化。

### 决策四：安全边界——token 永远不可从沙箱触及

**耦合架构下的安全漏洞：**

当 sandbox 和 harness 在同一个容器里——容器里有 credentials。一个 prompt injection 只需要说服 Claude 去读自己的环境变量——攻击者就拿到了 token。一旦有了 token，攻击者可以生成新的、不受限制的会话，把工作委派给它们。

窄范围授权是明显的缓解——但这是在编码一个假设："Claude 用有限的 token 做不了什么。" Claude 正在变得越来越聪明。这不是一个安全的赌注。

**结构性修复——两种模式：**

1. **Auth 与资源捆绑。** 对于 Git：用仓库的 access token 在 sandbox 初始化时克隆仓库，将其嵌入本地 git remote。`git push` 和 `git pull` 在 sandbox 内工作——但 agent 从未处理过 token 本身。

2. **Vault + 代理。** 对于自定义工具（通过 MCP）：OAuth token 存储在安全 vault 中。Claude 通过一个专门代理调用 MCP 工具。代理接收一个与 session 关联的 token，从 vault 中获取对应的 credentials，然后调用外部服务。**Harness 从未感知到任何 credentials。**

**这个设计的物理本质：**

不是"让 Claude 更难以拿到 token"——是**让 token 在物理上不可达。** 这是一个空气间隙（air gap）：代码执行发生在 token 不存在的环境中。无论 Claude 有多聪明——它不能读取不存在的东西。

这是防呆设计的终极应用：不是通过策略阻止错误——是通过物理架构使错误不可能。

### 决策五：`execute(name, input) → string`——一个统一所有"手"的接口

**耦合架构下的限制：**

一个 harness = 一个容器 = 一套资源。每个大脑只能伸向一套手。当一个容器失败——大脑伸向的所有手的状态都丢失了。

**解耦后的可能性：**

`execute(name, input) → string`——这行签名兼容任何自定义工具、任何 MCP 服务器、我们的内置工具。Harness 不知道沙箱是容器、手机、还是宝可梦模拟器。

进一步——因为没有任何手与任何大脑耦合——**大脑之间可以传递手。** Agent A 创建了一个沙箱，做了一些工作，然后把沙箱的名字传给 Agent B——Agent B 可以在同样的环境中继续工作。

这对多 agent 协作的影响是深远的：不是"agent 之间通过消息协调"——是"agent 之间通过共享工作环境协调"。状态不是传递的——状态是驻留的。

结合"许多大脑"的扩展性——Scaling 意味着启动许多无状态的 harness，只在需要时才连接到手。**每个大脑是轻量级的、可替换的、无状态的进程。** 双手是重量级的、可重用的执行环境。大脑和手的数量可以独立扩展——因为它们是独立的资源池。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

我们的第一个架构把所有 agent 组件塞进一个容器。好处：文件编辑是直接 syscall，没有服务边界需要设计。坏处：我们养了一只宠物。

容器失败 → session 丢失。容器无响应 → 工程师必须手动护理。调试的唯一窗口是 WebSocket 事件流——但它不能告诉你故障发生在 harness、网络、还是容器。要诊断，你必须打开容器里的 shell——但容器里有用户数据，这意味着我们实际上丧失了调试能力。

更深的问题：耦合意味着**系统中的每个假设都被埋进了一个单体内。** Harness 假设 Claude 操作的东西和自己在同一个容器里 → 当客户想把 Claude 连接到自己的 VPC 时，他们要么与我们的网络对等，要么在自己的环境中运行我们的 harness。一个埋进 harness 的假设变成了连接不同基础设施时的架构障碍。

### 行动

**失败方案一——更好的容器管理：**

直觉：让容器更可靠。更好的健康检查。更快的故障转移。更智能的重启。

但这解决的是症状：容器不可靠。它没有解决根因：**容器不应该是不可替代的。** 护理一个生病的容器——无论你护理得多好——它还是一个需要手工照料的东西。更好的解决方案是让容器不需要护理。让它变成可替换的。变成牛，不是宠物。

**失败方案二——更精细的监控：**

直觉：更多指标、更细粒度的遥测、更好的告警。这样至少我们能区分故障模式。

但这不能解决真正的问题：我们在做一个**反应性的**操作。用户报故障 → 我们调试 → 我们修复。Agent 系统应该是自我修复的。如果一个工具调用失败了——Claude 应该收到这个失败，并决定下一步做什么。不是我们作为人类操作员收到告警然后手动干预。

**亲手解剖——我是怎么找到突破口的：**

我回到第一性原理问自己：**agent 系统的物理组件是什么？**

1. **状态（State）**：session 的记录——所有发生了的事情。这是历史。历史是不可替代的——如果丢了，就永远丢了。

2. **计算（Computation）**：harness 的运行逻辑——调用 Claude、路由工具调用、管理循环。这是过程。过程是可重现的——给定相同的 session，重放一遍。

3. **执行（Execution）**：sandbox——Claude 运行代码、编辑文件的地方。这是环境。环境应该可以从干净状态重建。

在耦合架构中，这三样东西被塞进了同一个容器——一个单体内。一个单体的故障导致状态丢失（历史没了）、计算中断（harness 挂了）、执行环境不可用（sandbox 死了）。

**洞察——这三个组件在物理上是不等价的：**

状态（session）是不可替代的。计算（harness）是可替代的——它是逻辑，可以重新运行。执行（sandbox）是半可替代的——可以从干净状态重建，但可能包含中间产物。

不可替代的东西应该被**持久化**。可替代的东西应该被**无状态化**。半可替代的东西应该被**可替换化**。

**破坏性解决方案——三个组件的物理分离：**

**Session → 持久化，独立于 harness。**
接口：`getEvents()`。Session 是一个 append-only 事件日志，**永远**存在于 harness 之外。一个 harness 崩溃了？新的 harness 可以 `wake(sessionId)` → `getSession(id)` 取回事件日志 → 从最后一个事件恢复。Session 是真相的源头——不与任何 harness 的生命周期耦合。

**Harness → 无状态化，可重启。**
接口：`wake(sessionId)` + `emitEvent(id, event)`。Harness 不再需要"存活"——它可以在任何时候崩溃，重启后继续。像一个进程——进程可以被杀掉，重新启动后从保存的上下文继续。

**Sandbox → 可替换化，按需配置。**
接口：`execute(name, input) → string`。Sandbox 是 exec 目标——名字和输入进去，字符串返回。如果 sandbox 死了——harness 捕获失败，传给 Claude。Claude 决定下一步——可能是重试，这时候用标准配方 `provision({resources})` 创建新 sandbox。不再护理。

**把安全边界变成物理隔绝：**

Token 永远不进入 sandbox。Git token 在 sandbox 初始化时嵌入 local remote——Claude 用 `git push` 和 `git pull` 而不碰 token。OAuth token 存储在安全 vault 中，通过代理访问——harness 从未感知 credentials。

这是一个空气间隙：无论 Claude 变得多聪明——它不能读取在它执行环境中物理上不存在的东西。

### 结果

**性能改善：**

| 指标 | 改善 |
|------|------|
| p50 TTFT | 下降约 60% |
| p95 TTFT | 下降超过 90% |
| Session 可靠性 | 崩溃可恢复，不再丢失 |
| 扩展性 | 大脑和手独立扩展 |

p95 的改善是最重要的——那些最慢的 5% 的用户请求（最长等待的场景）被消除了。这不是渐进优化——这是架构重构消除了整个延迟来源。

**架构改善：**

- **调试能力**：故障模式现在可以被区分——harness 故障、容器故障、网络问题不再"看起来一样"。因为组件是分离的，它们的故障边界也是分离的。
- **安全性**：Token 物理上与沙箱隔离。Prompt injection 无法窃取不存在的东西。
- **可扩展性**：大脑可以传递给手。不同的大脑可以在同一只手上工作。这为多 agent 协作打开了物理可能性。
- **未来适应性**：接口不依赖于今天的具体实现。明天的沙箱可能是完全不同的技术栈——只要它实现了 `execute(name, input) → string`。

**这个设计的深层哲学：**

Managed Agents 是一个**元 harness**——它不是关于"今天最好的 agent harness 是什么"，是关于"明天、后天的 harness 如何能存在并演变"。就像操作系统不是关于"今天运行什么程序"——是关于"提供一个能让任何程序运行的基础"。

我们对 Claude 周围接口的形状有强烈意见：Claude 需要操纵状态（session）和执行计算（sandbox）。Claude 需要扩展到许多大脑和许多手。但我们不对大脑的数量、位置或手的类型做任何假设。

这就是"为尚未存在的程序设计系统"的 agent 版本。

---

*这个分析用第一性原理拆解了 Managed Agents 的架构决策——核心洞察来自操作系统的设计哲学：虚拟化硬件为抽象接口（process、file），接口稳定而实现可替换。Managed Agents 把同样的模式应用到 agent 组件（session、harness、sandbox）。关键物理分离：状态（session）= 不可替代 → 持久化。计算（harness）= 可替代 → 无状态化。执行（sandbox）= 半可替代 → 可替换化。TTFT 的 90%+ 改善来自于消除了基础设施准备等待时间——推理可以在沙箱配置完成之前就开始。*
