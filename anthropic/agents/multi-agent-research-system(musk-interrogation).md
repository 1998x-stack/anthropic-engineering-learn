# 马斯克式决策审问：Anthropic 多智能体研究系统

> **分析对象**: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: 该系统的核心决策者（工程负责人视角）

---

## 问题一：你的故事——你做了什么决策，为什么？

让我从头讲起。

### 决策一：多智能体 vs. 单智能体 vs. RAG——这是物理极限问题，不是偏好问题

**主流做法是什么？**

2025年初，所有人都在用 RAG。给一个查询，从向量数据库里捞几个最相似的 chunk，塞进提示词，让模型生成答案。这就是检索增强生成——静态的、线性的、一次性的。OpenAI 的 BrowseComp 基准测试上，大家都在用单智能体浏览器慢慢爬。

**我怎么拆解到第一性原理？**

研究不是检索。研究的本质是将浩瀚语料压缩为洞察——信息论层面的压缩。我盯着这个问题的物理极限：

- 单个上下文窗口的 token 容量是硬约束（约 20 万 token）
- 人类做研究时从来不是"先搜完再看"——他们在探索中不断修正方向，发现新线索后立刻转向
- 一个不可预测的过程，你根本无法预先硬编码步骤

那么根本问题变成了：**如何在给定的 token 预算下，最大化有用信息的吞吐量？**

这不是"多智能体好还是单智能体好"的品味之争。这是一个**并行计算 vs. 串行计算**的架构问题。单个 agent 是单核 CPU，多 agent 是多核并行。当你面对的是广度优先的搜索任务——同时探索十个独立方向——串行架构在物理上就不可行。

**我做了什么反常识的决定？**

我在所有人都喊着"一个足够强的大模型就够了"的时候，坚持用 orchestrator-worker 多智能体架构。主流观点认为模型能力提升会消除多智能体需求——错了。一旦智能达到某个阈值，扩展集体智能比提升个体智能更有效。人类历史上，过去十万年个体智力几乎没有变化，但人类社会的集体能力却呈指数级增长。token 使用量解释了 BrowseComp 上 80% 的性能方差——这才是物理本质。

**数据证明我对了**：多智能体系统（Claude Opus 4 lead + Sonnet 4 subagents）在内部研究评估上比单智能体 Claude Opus 4 高出 **90.2%**。这不是微调提升，这是架构范式级别的差距。

**代价是什么？** 多智能体系统的 token 消耗是对话的 15 倍。我知道这意味着经济可行性必须建立在任务价值足够高的前提下——不适合所有场景。我是对的。研究、商业分析、学术调研——这些任务的价值远超 token 成本。

### 决策二：同步执行 vs. 异步执行——故意选择"次优"方案

**直觉上怎么做？**

任何分布式系统工程师的第一反应都是：异步！让所有 subagent 并行跑，lead agent 实时调控，别傻等着。这样吞吐量最高，没有瓶颈。

**我为什么选了同步？**

我把问题拆到原子层面。异步带来的不是"一点额外复杂度"——它带来的是完全不同的故障模式：

1. **结果协调**：10 个异步 subagent 同时返回部分结果，lead agent 如何在信息不完整的情况下做决策？这要求 lead agent 本身是一个实时调度器——目前的模型做不到。
2. **状态一致性**：subagent A 开始搜索"2025年半导体供应链"，subagent B 完成了相同任务并返回结果——lead agent 如何在 A 还在跑的时候告诉它"别搜了，B 已经完成了"？需要跨 agent 通信协议。
3. **错误传播**：一个 subagent 卡死了。在同步模式下，我们知道它在哪一步卡住的——我们甚至可以让模型自己适应工具失败。在异步模式下，整个系统的状态图变成指数级复杂。

**同步是故意的技术债务。** 我知道它会产生瓶颈——lead agent 必须等最慢的 subagent 完成才能继续；subagent 之间无法协调；一个 subagent 卡住，整个系统阻塞。

但 synchronous → asynchronous 的迁移路径是可预测的。反过来，如果你一开始就在异步的泥潭里挣扎，你永远不知道你的系统为什么不工作。先让它跑起来，用同步拿到 90% 的性能增益，然后当模型能力足够处理更复杂的协调任务时，逐步引入异步。**删除、简化、优化、加速——按这个顺序来。**

### 决策三：启发式提示词 vs. 硬规则——用框架代替手铐

**标准做法是什么？**

给你 50 页的指令文档。每个场景都有一条规则。"如果查询类型是 X，启动 3 个 subagent。如果来源质量低于 0.7，丢弃。如果 token 超过 10 万，压缩。"

这种做法的结果是：agent 变成了一台没有判断力的机器。它会在找到足够信息后继续搜索，会为简单查询启动 50 个 subagent，会在不存在的信息上无限搜索。

**为什么我选了启发式？**

我观察了人类研究员如何工作。他们不会背一个决策树。他们心里有一组经验法则：

- 先把大问题拆成小问题
- 判断来源质量（学术 PDF > SEO 内容农场）
- 根据新发现调整搜索方向
- 知道什么时候深入（深度），什么时候扫面（广度）

我把这些编码进提示词——不是作为"如果你遇到情况 37，执行步骤 42"，而是作为**判断框架**。agent 需要学会判断，不是学会服从。

更重要的是，我直接在提示词里嵌入了**努力量级规则**：

- 简单事实查找：1 个 agent，3-10 次工具调用
- 直接比较：2-4 个 subagent，每个 10-15 次调用
- 复杂研究：10+ 个 subagent，明确分工

这解决了"agent 不知道何时停止"这个最让用户愤怒的失败模式。早期的 agent 会为一个"巴黎人口多少"的问题搜遍整个互联网。

### 决策四：单一 LLM 评委 vs. 多评委面板——相信信息熵的最小值

**评估研究输出有多难？**

研究的答案是自由文本，没有"唯一正确答案"。你怎么用程序判断"这个关于半导体供应链的报告好不好"？

主流思路是：用多个 LLM 评委分别评估不同维度——事实准确性一个评委，引用准确性一个评委，完整性一个评委，来源质量一个评委。取平均分。

**我做了相反的事。**

我们实验了多评委方案。结果：不一致。评委 A 给了 0.9，评委 B 给了 0.4。这两个分数的平均值没有任何物理意义——它们是不同评估框架下的不同信号。

**我的洞察**：评估的一致性来自于**统一的评分标准和单一判断上下文**。一个 LLM 调用，一个提示词，输出 0.0-1.0 的分数加上 pass/fail 判定。这个方法与人类判断高度一致，而且可以规模化评估数百个输出。

这个决定的物理本质是：你在评估一个信息压缩过程（agent 把大量搜索结果压缩为答案）——评估者本身也需要保持信息一致性。多个并行评估者产生的噪声本身就是信息损失。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

2025年初，我们的多智能体研究系统从原型走向生产。原型在开发者机器上跑得很好，30% 到 80% 的成功率提升让我们兴奋不已。然后我们把它放在真实用户面前。

噩梦开始了。

用户报告："Claude 找不到明显的信息。" 但我们不知道原因。是 agent 用了烂搜索词？选了垃圾来源？工具调用失败了？每个 agent 做的是动态决策，即使完全相同的输入，两次运行的路径也完全不同。这不是传统的"输入 X → 路径 Y → 输出 Z"的调试模式。一个 prompt 的小改动会导致 subagent 行为发生不可预测的连锁反应——涌现行为，没有任何人编程实现，却真实存在。

我的责任：把这团乱麻变成可运行的、可调试的、可部署的生产系统。同时保证用户隐私——不能看单个对话内容。

### 行动

**失败的尝试：**

直觉告诉你，agent 不工作，就去改 prompt。我们试了。改了 20 次。有时改进了一个场景，退化了两个。有时 Prompt A 在周一比 Prompt B 好 15%，周三反过来。没有系统性理解的情况下改 prompt，就是掷骰子。

我们又试了"更多测试用例"。从 20 个扩展到 200 个。问题依旧是：你看得到结果（输出不行），但你看不到过程（为什么不行）。

**亲手解剖——我做了哪些极端实验？**

我让团队做了三件事：

1. **追踪一切，但只追踪高层模式。** 完全的 production tracing——不是看对话内容（隐私红线），而是看 agent 的决策模式：用了什么工具？启动了多少 subagent？搜索了多久？在哪些节点卡住了？这让我们从"用户说找不到信息"变成了"47% 的失败案例中，subagent 选择了低质量来源，且没有切换到更好的来源"。这是可操作的信息。

2. **在 Console 里用真实 prompt 和工具做模拟。** 不是对着 prompt 文本推理它的行为。我要求工程师实际跑 agent，一步一步看它做了什么。这立刻暴露了失败模式：agent 在结果已经足够时继续搜索；使用过于冗长的搜索查询（搜索"2025 年全球半导体行业供应链中断的详细分析报告"而不是"半导体短缺 2025"）；选错工具。**建立对 agent 行为的准确心智模型，是做好 prompt engineering 的前提。** 靠猜是猜不出来的。

3. **人类测试员而不是自动化测试。** LLM 评委能发现很多问题，但人类注意到了一件自动化评估完全漏掉的事：早期的 agent 一致性地选择了 SEO 优化的内容农场而不是学术 PDF 或个人博客——因为搜索引擎排名机制偏向前者。这不是"理解错误"，这是"来源选择的系统性偏见"。没有人类测试员，这个 bug 会一直在生产环境里存在。

**洞察时刻：**

深夜，盯着一堆 token 消耗数据，我突然意识到一件事：

**token 使用量解释了 80% 的性能方差。**

这不是在说"更多 token = 更好"——这是说"如何组织 token 的使用才是关键"。单 agent 模式的问题不是 token 不够，而是 token 使用效率低下：串行搜索意味着大量 token 浪费在不相关的路径上，因为 agent 没有并行探索多个方向的能力。

多智能体架构不是"让多个 agent 一起工作"——它是**让 token 预算在独立的上下文窗口中并行燃烧**。每个 subagent 有自己的上下文窗口，不受其他 agent 搜索路径的干扰。这是 token 使用的分工经济学。

但这带来了一个新问题：token 消耗是对话的 15 倍。你不能无节制地并行。需要**按查询复杂度动态分配 token 预算**——这就是我们为什么把"努力量级规则"直接嵌入 prompt。

**破坏性解决方案：**

基于这些洞察，我推动了三件事：

1. **给 orchestrator 教它如何委派。** 不是"研究半导体短缺"——太模糊，三个 agent 会做一样的事。而是"研究 2025 年全球半导体供应链现状，重点关注台积电的产能、英特尔的代工战略、以及汽车行业的 chip 需求。输出格式：每家公司的结构化摘要。搜索范围：Bloomberg, Reuters, 行业报告。" **详细的委派描述 = 避免重复劳动和遗漏。**

2. **状态化错误恢复而不是重启。** 传统软件出错了重启就好。Agent 运行 15 分钟后在工具调用 87 次时出错——重启意味着扔掉 87 次调用的所有上下文，token 成本爆炸，用户等得更久。我们构建了从出错点恢复的机制，并且让模型在工具失败时自主适应——告诉 agent "工具 X 失败了，你可以尝试用 Y"，它经常能找到替代方案。结合确定性的重试逻辑和定期 checkpoint。

3. **彩虹部署 (rainbow deployment)。** Agent 系统是高度状态化的——它们连续运行几十分钟甚至几小时。你想推一个新版本？你不能"同时更新所有 agent"——因为部署那一刻，有几千个 agent 正跑到中途。你杀掉它们，用户的工作就丢了。我们用彩虹部署：新旧版本同时运行，流量逐步切换。运行中的 agent 继续用旧版本直到完成，新 agent 用新版本。

### 结果

- 内部评估：多智能体系统比单智能体高 **90.2%**
- 用户反馈：从"找不到明显信息"到"帮我发现了没想到的商业机会、搞定了复杂医疗选项、节省了数天工作量"
- 用户增长：Claude Research 最常用的场景是专业领域软件开发（10%）、专业内容优化（8%）、商业增长策略（8%）、学术研究辅助（7%）

**但我必须承认我们还没解决的问题：**

同步执行是一个故意的短视决策。随着模型能处理更长、更复杂的研究任务，异步执行的性能收益将超过复杂度成本。我们还没做这个迁移——它在路线图上。

多智能体系统今天不适合所有场景。需要大量共享上下文的编码任务、agent 间强依赖的任务——单 agent 可能更好。我从不说什么架构是万能的。**理解物理极限，在约束内优化——这才是工程。**

## 附录：这个系统教给我的几条原则

1. **Token 不是你花的钱——是你投入的计算力。** 关键是组织结构让它并行燃烧，不是线性地烧。

2. **不要想象你的 agent 会做什么——观察它。** 在 Console 里用真实 prompt 跑模拟。你猜的行为和实际行为之间的差距，就是你的 bugs 所在。

3. **启发式 > 硬规则。** Agent 需要判断框架，不是决策树。人类研究员不会背规则手册——他们有心智模型。

4. **评估从第一天开始，20 个用例够用。** 效果大的时候（30% → 80%），你不需要统计显著性。别等"完美评估系统"——那是拖延的借口。

5. **同步是好的第一步。** 先让系统可控地工作，再引入异步的复杂度。删除、简化、优化、加速——顺序不能乱。

6. **人类测试员不能被替代。** LLM 评委能规模化评估，但 SEO 偏见这种东西——只有人才能发现你的 agent 在选择垃圾来源而不是权威来源。

7. **生产环境中，"最后一公里"占了 90% 的路程。** 原型到生产之间的差距，远比你以为的大。agent 系统的一个小错误会像滚雪球一样放大——因为每一步的决策都依赖于前一步的结果。错误会复合。
