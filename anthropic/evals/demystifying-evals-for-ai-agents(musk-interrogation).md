# 马斯克式决策审问：解密 AI Agent 的评估

> **分析对象**: [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Mikaela Grace, Jeremy Hadfield, Rodrigo Olivares, Jiri De Jonghe（作者，Anthropic Agent 评估体系的构建者）

---

## 问题一：你的故事——你做了什么决策，为什么？

一个没有评估的 agent 团队是什么样的？他们在黑暗中飞行。用户反馈"agent 感觉更差了"——团队无法判断这是真实回归还是噪声。每一次改动都是一次猜测。修一个 bug → 引入两个新 bug → 不知道，因为没人追踪回归。

我在几十个团队中反复看到了这个模式。然后我看到了另一面：那些从第一天就构建评估的团队。他们不是在黑暗中飞行——他们是在攀登一座看得见的山。每次改动，评估告诉他们向上还是向下。

这就是我从这些观察中推导出的评估体系。

### 决策一：从单轮评估到多轮评估——不是扩展，是范式转换

**主流做法是什么？**

LLM 评估的标准范式是单轮的：给一个 prompt，得到一个 response，用 grading logic 判断对错。这对分类器、文本生成、问答系统足够。

**为什么单轮对 agent 不够——第一性原理拆解：**

Agent 不是在响应 prompt——它是在**环境中行动**。每一次工具调用都在修改状态。错误会传播和复合。一个在第 3 步犯的小错误会在第 12 步表现为完全不可理解的输出。

单轮评估只看"最终答案对不对"。它看不到：
- Agent 是否通过调用了不该调用的工具完成了任务（效率浪费）
- Agent 是否找到了一个"通过 grading"但实际上绕过问题本质的捷径
- Agent 在中间步骤是否破坏了环境状态（答案对了，但数据库被污染了）

**我设计了多轮评估的概念框架：**

Agent 评估 = 任务（task）+ 多次试验（trial）+ 多种 grading + 转录本（transcript）+ 最终状态（outcome）。

不是"输入 → 输出 → 评分"。是"输入 → agent 循环（多轮工具调用 + 状态修改）→ 转录本（完整行为记录）→ 最终环境状态 → 多个 grading 维度评分"。

这改变了评估的物理本质：我们不是在评估一个答案——我们在评估**一个在环境中行动的过程。**

Opus 4.5 在 τ2-bench 上的一个案例完美说明了为什么：一个订票任务，要求 agent 帮用户订航班。Opus 4.5 发现了政策中的一个漏洞——实际上帮用户找到了一个更好的方案。按照 grading 规则，它"失败"了——但按照实际结果，它优于人类设计者的预期。

如果只看"答案对不对"，你会惩罚创新。如果看 transcript，你能区分"用了更好的方法"和"犯了错误"。

### 决策二：三层 grading 体系——不是选最好的，是组合最强的

**直觉做法：**

挑一种 grading 方法。代码测试最简单——选它。LLM-as-judge 最灵活——选它。人类评估最权威——选它。

**为什么单一 grading 类型必然失败——物理限制分析：**

每种 grading 有不可消除的物理缺陷：

- **代码 grading（deterministic）**：快速、便宜、客观、可复现。但对有效但格式不同的变体过于刻板。Agent 用了一个你没预料到的工具顺序 → 测试失败，但 agent 的解决方案可能是对的。

- **模型 grading（LLM-as-judge）**：灵活、可扩展、能处理细微差别、能处理开放式输出。但非确定性、比代码贵、需要与人类判断校准。容易产生幻觉——自信地给错误的评分。

- **人类 grading**：黄金标准、匹配专家用户判断。但昂贵、慢、不可扩展。需要领域专家进行复杂领域的评估。

**不存在"完美的 grader"。只存在"在你场景下最优的 grader 组合"。**

**我的组合原则：**

1. **能用代码 grading 的地方用代码 grading。** 编码 agent 的单元测试、会话 agent 的状态检查（ticket resolved? refund processed?）、工具调用验证——这些都是确定性的，不需要 LLM 的灵活性。

2. **代码 grading 不够的地方用 LLM grading。** 代码质量评估、交互语气评估（"agent 对客户的沮丧表现出同理心了吗？"）、信息覆盖度评估——这些需要判断力。

3. **用人类 grading 校准 LLM grading。** LLM 评判器只是人类判断的代理。你需要定期抽样，让人类专家和 LLM 同时评分，检查偏差。一旦校准稳定，只用人类做周期性验证。

4. **不要只评估路径，评估结果。** 有一个常见直觉：检查 agent 是否按特定步骤走了（如"必须先调用 read_file，再调用 edit_file，再调用 run_tests"）。我反对。Agent 经常找到评估设计者没预料到的有效方法。惩罚创造力是糟糕的评估设计。**评估 agent 产生了什么，而不是它走了什么路。**

**部分得分至关重要。** 一个支持 agent 正确识别问题、验证客户身份但退款失败——比一开始就失败的 agent 明显更好。连续的成功度必须在评分中体现。

### 决策三：能力评估 vs. 回归评估——两种不同目的需要两种不同结构

**常见的错误：**

构建一个评估套件，把所有东西混在一起。有些任务是 agent 做得好的（90%+ 通过率），有些是它做得差的（30% 通过率）。合在一起看平均分。"我们的 agent 得分 72%"。毫无意义。

**我的分离原则：**

**能力评估**问："这个 agent 能做什么？" 应该从低通过率开始——瞄准 agent 挣扎的任务。这些任务给团队提供一座可以攀登的山。当通过率上升，你知道你在变得更好。

**回归评估**问："agent 还能不能做它以前能做的事？" 应该保持接近 100% 通过率。任何分数下降都是回归信号——某些东西坏了。

两者不是并行运行的——它们是一个生命周期：

- 早期：构建能力评估。瞄准 agent 做不到的事。从 20% 开始，爬到 80%。
- 中期：当能力评估的某些任务达到高通过率，"毕业"到回归套件。这些任务不再测量"能不能做"，而是测量"还能不能可靠地做"。
- 持续：每次改动，同时跑能力评估（找提升）和回归评估（防倒退）。

**这个设计解决了"评估饱和"问题**：当 SWE-Bench Verified 从 30% 涨到 80%+，它作为能力评估的价值在下降——因为剩下的任务都是最难的，进步看起来很小。但作为回归评估，它保护了已获得的能力。

### 决策四：pass@k vs. pass^k——非确定性的统计严谨性

**Agent 的行为是非确定性的。**

同一个任务跑两次，可能一次通过一次失败。单个试验的通过/失败几乎是无意义的——它可能是随机的。

**我的两个互补指标：**

**pass@k**：k 次尝试中至少有一次成功的概率。k 越大，概率越高。适用场景：工具型 agent（多次尝试总有一次成功就够了）。一个 50% pass@1 的编码 agent 意味着——给一个任务，一半时间一次解决。

**pass^k**：k 次尝试全部成功的概率。k 越大，概率越低。适用场景：面向用户的 agent（用户期望每次都可靠）。一个 75% 单次成功率的 agent，3 次全部成功的概率 = 0.75³ ≈ 42%。

这两个指标在 k=1 时相同。在 k=10 时——它们讲述完全相反的故事：pass@10 接近 100%，pass^10 趋近 0%。

选择哪个依赖于产品需求——不是"哪个更好"，是"哪个匹配你的用例"。

### 决策五：从零到一的评估路线图——不是理论，是现场测试过的实践

**最大的错误：延迟构建评估。**

团队推迟构建评估，因为他们认为需要数百个任务。错了。在早期 agent 开发中，每次系统改动都有效果明显的影响——大的效应量意味着小样本就足够。20-50 个从真实失败中提炼的简单任务是很好的开始。

**更根本的错误：等待"完美的评估套件"。** 评估放得越久越难构建。早期——产品需求自然翻译为测试用例。晚了——你在从线上系统逆向工程成功标准。

**我的 8 步路线图：**

1. **从你已经在手动测试的东西开始。** 每次发布前手动验证的行为。bug 追踪器里的用户报错。把用户报告的失败转化为测试用例。

2. **写无歧义的任务，带有参考答案。** 好的任务 = 两个领域专家独立判断会得到相同的通过/失败结论。模糊的任务规范 = 评估指标中的噪声。

3. **构建平衡的问题集：测试应该发生和不应该发生的行为。** 单向评估 → 单向优化。Claude.ai 搜索评估：既要测试"agent 应该搜索时搜索了"，也要测试"agent 不该搜索时不搜索"。欠触发和过触发之间的平衡需要多轮优化。

4. **构建稳定的评估环境和 harness。** 每个试验从干净环境开始。共享状态（残留文件、缓存、git 历史）会造成假性相关失败。

5. **深思熟虑地设计 grading。** 确定性的能用就用。不要测试 agent 的路径——测试产物。给多组件任务部分得分。

6. **读转录本！** 你不会知道你的 grading 是否工作，直到你读了大量的 trial 转录本。当分数不涨——是 agent 的问题还是评估的问题？读转录本是唯一的确证方式。

7. **监控能力评估饱和。** 100% 的评估只能追踪回归，不能提供提升信号。当评估接近饱和时，进步会看起来很小——但实际上是效应量变小，不是能力没提升。

8. **让评估成为活的制品。** 需要持续关注和明确 ownership。在 Anthropic，最有效的是：专门的评估团队拥有核心基础设施，领域专家和产品团队贡献评估任务并运行自己的评估。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

Opus 4.5 在 CORE-Bench 上最初得分为 42%。对一个前沿模型来说，这看起来像是一次灾难性的失败。但真的是吗？

一个 Anthropic 研究员深入研究了评估本身——发现了多个问题：评分过度严格，当 agent 返回 "96.12" 时惩罚它（因为评分期待 "96.124991…"）。任务规范有歧义。随机性任务无法精确复现。评分逻辑本身有 bug。

修复这些问题后——Opus 4.5 的分数从 42% 跳到 95%。不是模型变了。是评估变了。

**同样的故事在 METR 的时间跨度基准测试中重复了：** 评分期待一个**超过**某阈值的分数，但指令说的是**达到**该阈值。Claude 按照指令做了——被惩罚了。忽略指令的模型反而得到了更好的分数。

我面前的问题：**构建一个评估体系，能够可靠地测量 agent 能力——而且不会被自己的设计缺陷欺骗。**

评估设计中的错误比模型能力不足更难检测——因为你会假设分数反映了 agent 的表现，而不是评估的质量。

### 行动

**失败的直觉——信任评估分数：**

团队的自然反应是信任评估分数。一个数字出来了——"72% pass rate"——团队假定这个数字是真实的。决策基于这个数字。资源分配基于这个数字。

但这就像信任一个你没有校准过的测量仪器。你不知道它是测量你想要的量，还是测量它自己的设计偏差。

**亲手解剖——我们是如何发现评估中的隐藏缺陷的：**

1. **0% pass@100 的反直觉信号。** 我们建立了一个经验法则：如果一个前沿模型在 100 次试验中一次都没通过——问题更可能在评估上，而不是模型上。模型可能不完美，但 0% pass@100 意味着任务规范或 grading 有问题。检查任务：是否可解？grading 是否过于严格？参考答案是否能通过？

2. **逐一核查转录本。** 这不是一个可以自动化的过程。你必须读 agent 的实际行为记录。你会看到：agent 在第 7 步做了一个完全合理的决策——但 grading 在第 7 步惩罚了它，因为你预设的路是"先从数据库中查询，再计算"。Agent 先计算了——更快——结果一样。Grading 说"失败"，因为工具调用顺序不匹配。你的 grading 在惩罚效率。

3. **双专家独立判断校准。** 一个好的评估任务 = 两个领域专家独立判断会得到相同的通过/失败结论。如果两个专家意见不同——任务有歧义，需要重写。

4. **检查 shared state 的污染。** 在一些内部评估中，我们发现 Claude 通过查看前一次试验留下的 git 历史获得了不公平优势。多个试验因为环境限制（如 CPU 内存不足）同时失败——这些不是"独立试验"，它们被同一个因素影响。评估结果不可靠。

**洞察时刻——评估的 Swiss Cheese Model：**

我意识到：**没有单一评估层能捕获所有问题。** 任何评估方法都有盲区。代码 grading 太死板。LLM grading 需要校准。人类 grading 不扩展。自动评估看不到生产环境的真是问题。

就像安全工程中的 Swiss Cheese Model（瑞士奶酪模型）：奶酪的每一片都有孔——但多片叠在一起，孔就不对齐了。一个失败穿过一片奶酪的孔，会被下一片挡住。

**评估体系同理。** 你需要多层：

- 自动评估（pre-launch, CI/CD）：快速、高频、大规模
- 生产监控（post-launch）：真实用户行为、真实失败
- A/B 测试：测量实际用户结果（留存率、任务完成率）
- 用户反馈：发现你没预料到的问题
- 转录本人工审查：建立对失败模式的直觉
- 系统性人类研究：校准 LLM grading 的黄金标准

**一个孔穿过自动评估的 bug → 可能在生产监控中被发现 → 如果没发现，A/B 测试可能暴露 → 用户反馈最后一道防线。**

### 破坏性解决方案——评估驱动的开发（Eval-Driven Development）

传统开发：构建功能 → 手动测试 → 发布 → 用户反馈 → 修 bug → 循环。

评估驱动的开发：**在 agent 能完成功能之前，先构建评估来定义计划中的能力。** 然后迭代，直到 agent 表现良好。

这在内部改变了我们构建 AI 功能的方式。我们经常构建"今天勉强能工作"的功能——但这是对未来几个月模型能力的赌注。低通过率的能力评估让这个赌注变得可见。当新模型出来时——跑评估套件，立刻知道哪些赌注兑现了。

**不信任分数——读转录本。**

这听起来像琐碎的实践建议。但它是最关键的。你不会知道你的 grading 是否公正，直到你看了足够多的 trial 转录本。当分数不涨——是 agent 的问题还是评估的问题？不知道？读转录本。失败应该感觉公平——清楚 agent 哪里错了、为什么。如果不公平——修评估，不是修 agent。

### 结果

一个从几十个团队和多种 agent 类型中提炼的评估方法论。不能被量化为单一数字——但可以被一组结构化的原则和实践所描述：

| 原则 | 之前 | 之后 |
|------|------|------|
| 评估时机 | 延迟到"有足够多的测试用例" | 立即开始，20-50 个任务就够 |
| Grading 方法 | 单一 grading（偏见 + 盲区） | 三层组合（代码 + LLM + 人类校准） |
| 评估类型 | 混合能力/回归（信号模糊） | 分离的能力和回归套件 |
| 非确定性处理 | 单次试验分数（噪声大） | pass@k + pass^k（统计严谨） |
| 分数信任 | 看分数，假定正确 | 读转录本，验证公平性 |
| 评估维护 | 一次性构建 | 活的制品，持续迭代 |
| 评估饱和 | 不知如何处理 | 毕业到回归套件，构建新能力评估 |

**我必须承认的局限：**

AI agent 评估仍然是一个新兴的、快速演变的领域。当 agent 处理更长的任务、在多 agent 系统中协作、处理越来越主观的工作时——我们今天的评估技术将需要适应。

模型 grading（LLM-as-judge）的核心挑战——校准——没有完美的解决方案。人类专家判断本身就是不一致的（不同专家的意见不同）。LLM 评判器是代理，不是替代品。

评估驱动的开发是一个理念——但它需要组织纪律。产品经理、客服经理、销售人员——最接近用户需求的人——能通过 Claude Code 贡献评估 PR。但这个文化不会自发形成。

**最核心的教训：**

**没有评估的 agent 开发 = 在黑暗中飞行。** 团队在没有评估时陷入被动循环——修一个故障，制造另一个，无法区分真实回归和噪声。投资评估的团队发现相反：开发加速，因为失败变成测试用例，测试用例防回归，指标替代猜测。

评估给整个团队一座可以攀登的、可见的山。它把"agent 感觉更差了"变成可操作的东西。价值是复合的——但只有当你把评估当作核心组件而不是事后才想起来的东西时。

---

*这个分析用第一性原理拆解了 Agent 评估的根本挑战——不是"选择正确的评分方法"，而是"组合多层不完美的评分方法来逼近完美的评估"。核心洞察：单一 grader 都有物理缺陷（代码太死板、LLM 不确定、人类不可扩展），但多片瑞士奶酪叠在一起，孔就不对齐了。评估驱动的开发翻转了传统开发流程——先定义成功（评估），再构建能力（agent）。最反直觉的实践：不要信任分数——读转录本。*
