# 马斯克式决策审问：设计 AI 抗性的技术评估

> **分析对象**: [Designing AI resistant technical evaluations](https://www.anthropic.com/engineering/AI-resistant-technical-evaluations)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Tristan Hume（作者，Anthropic 性能优化团队负责人，该 take-home 测试的设计与反复重构者）

---

## 问题一：你的故事——你做了什么决策，为什么？

我在和自己公司造的模型打一场军备竞赛。输了的代价不是我一个人的——是整个招聘管道。

2023 年 11 月，我设计了一个 take-home 测试来筛选性能工程师。它帮我们招到了数十个工程师，包括那些带起了 Trainium 集群、交付了 Claude 3 Opus 之后每一代模型的人。这个测试是成功的。

然后 Claude Opus 4 打败了它。我重新设计了。Opus 4.5 又打败了重设计的版本。我再次重新设计。这一次——我放弃了一切关于"贴近实际工作"的幻想，转向了一个只有 Zachtronics 游戏玩家才会觉得熟悉的怪异领域。

这不是我在炫耀迭代能力。这是一个越来越绝望的工程师在记录 AI 进步是如何一个一个地抹去人类相对于模型的优势。

### 决策一：允许 AI 辅助而不是禁止它——在模型会用的地方测试人类+AI 的能力

**主流做法是什么？**

每次 AI 能力进步，招聘团队的第一反应都是：禁止 AI。候选人不能在 take-home 中使用 AI 工具。回归"纯人类"评估。

**我为什么坚决反对：**

禁止 AI 辅助是一个懒惰的方案。它解决了评估问题，但逃避了一个更根本的问题：**如果候选人在实际工作中会使用 AI，你在测试什么？**

Anthropic 的正式候选人指南明确说"除非另有说明，take-home 应不使用 AI 完成"。对大多数岗位，这是合理的。但对性能工程——我明确写了"另有说明"。

我的推理链：

1. **实际工作中，性能工程师每天都在用 AI。** Claude Code 是我们工作流程的组成部分——调试、优化、写工具。禁止 AI 的测试测量的是候选人在一个他们永远不会遇到的环境中表现如何。

2. **长时间问题天然对 AI 更难。** 给 Claude 一个 50 分钟解决的单文件算法题——秒杀。给 Claude 一个需要 2-4 小时理解系统、构建工具、渐进优化的开放式性能工程问题——它在时间约束下仍然吃力。AI 辅助的 take-home 不是"让人和 AI 比"——是"看在 AI 辅助下，人能不能比纯 AI 表现更好"。

3. **人类在 AI 辅助下的优势应该被测量，而不是被消除。** 如果一个人能利用 Claude Code 产出比 Claude Code 独自运行更好的结果——那这个人值得被雇佣。这就是工作场景。

**我拒绝屈服于的想法**：人类只在超过几小时的超长任务上才有优势。如果这是真的，那么我们在 2 小时时间窗口内就没有办法评估候选人——但我不相信这是真的。我要找到一个方式，在 2 小时 + AI 辅助的场景下，让优秀的人类工程师依然能区分自己。

**但这里有一个真实问题**：Claude 跑得太快了。人类通常花前半小时来读代码、理解问题。Claude 在前 30 秒就读完了整个代码库。当人类还在理解问题的时候，Claude 已经实现了第一个优化。人类试图"驾驭"Claude 来参与竞争，结果是一直在被 Claude 拖着走，理解 Claude 做了什么只是事后。

这暗示着一个更深的问题：如果最佳策略是"坐着看 Claude 跑"，那么这个测试就不是在测试候选人——是在测试 Claude。我必须确保测试的结构让人类判断和创造力在某个点上成为瓶颈。

### 决策二：用模型找模型的弱点——不是猜测，是测量

**直觉做法：**

我觉得哪部分 Claude 应该做不好——然后在那部分加大难度。

**为什么这行不通：**

直觉在 AI 能力面前是糟糕的指南。我对"Claude 做不到什么"的直觉，在 Opus 4 上和 Opus 4.5 上完全不同。而且直觉经常错——我会低估模型在某个领域的能力，也会高估。

**我的方法论：**

**让模型自己告诉我它哪里弱。**

当 Opus 4 打败了原版测试，我不是坐在那里想"什么会让 Claude 更困难"。我让 Claude Opus 4 实际跑测试，观测它在哪个具体点上开始挣扎。**那个点——就是新版测试的起点。**

我把 Claude 已经解决的部分删掉（multicore——Claude 完美解决了，而且它只拖慢开发循环而不增加信号）。我在 Claude 开始费力的地方增加深度。写了更干净的起始代码。缩短了时间限制（从 4 小时到 2 小时——四小时时间窗口在时间安排上造成了数周的延迟，两小时更容易塞进周末）。

**为什么这个方法论是正确的：**

因为你的目标不是"构建一个 Claude 永远解决不了的问题"——这是不可能的。模型在持续进步。你的目标是**构建一个 Claude 需要比人类更多时间才能解决的问题**。只要能测量出这个差距，测试就还有信号。

用模型识别自己的弱点——然后在那

里加深问题——是利用了模型的"相对弱点"，而不是依赖你对模型能力的主观判断。

这就像拳击——你不是试图找到一个对手永远打不到你的角度（不存在），你是找到他需要多一步才能打到的角度，然后利用那一步的时间差。

### 决策三：放弃"贴近实际工作"——从 Version 2 到 Version 3 的范式转换

**Version 1 到 Version 2 的演变逻辑：**

V1（原版）：模拟加速器上的并行树遍历。手动 scratchpad 内存、VLIW、SIMD、多核。候选人的任务是从串行实现逐步利用并行性。包含一个 bug 需要先调试（测试构建工具的能力）。

当 Opus 4 打败它 → V2：增加更多机器特性以增加深度，删除 multicore（Claude 已完美解决，对人类无额外信号），在新起点上给候选人更多优化空间。强调巧妙的优化洞察而不是调试和代码量。

**V2 到 V3：被迫的范式转换**

Opus 4.5 打败了 V2。在两小时内。它先解决了初始瓶颈，实现了所有常见的微优化，然后停下来——确信遇到了不可逾越的内存带宽瓶颈。大多数人类也得出同样的结论。

但当我告诉 Claude 可以达到的周期数后——它想了想，找到了绕过瓶颈的技巧。然后调试、微调、实现进一步优化。2 小时结束时，它的得分超过了同等时间限制下的最强人类——那个人类还大量使用了 Claude 4 并做了方向引导。

**我尝试了一个"更贴近实际工作"的替代方案——失败了：**

我选了一个我做过的最棘手的 kernel 优化问题：在 2D TPU 寄存器上高效转置数据，同时避免 bank conflict。把它蒸馏成模拟机器上的简化问题。让 Claude 在一天内实现了改变。

Claude Opus 4.5 找到了一个我没想到的优雅优化。它通过仔细分析发现——与其想办法转置数据，不如转置整个计算。它重写了整个程序。

在我的真实案例中，这个方案行不通（有硬约束）。所以我修补了问题，堵上了这个捷径。然后 Claude 继续推进——但还是找不到最有效的解决方案。看起来我有了新问题……

然后我用 Claude Code 的 "ultrathink" 功能和更长的思考预算双重检查——它解决了。它甚至知道修复 bank conflict 的技巧。

**深刻的失败洞察**：我选错了问题。跨平台工程师都在和数据转置和 bank conflict 做斗争——所以 Claude 在训练数据中有大量相关经验可以借鉴。我是从第一性原理推导出我的解决方案的——但 Claude 可以从整个行业积累的经验工具箱中抽取。我的第一性原理 vs. 整个互联网的集体智慧——我输了。

**被迫的转向——走向怪异：**

我需要一个问题，人类推理能赢过 Claude 更大的经验基础。一个足够"分布外"的问题——不在模型训练数据的舒适区内。

但这与我的目标相矛盾：贴近实际工作。实际工作用的就是标准的优化技术——正是训练数据最丰富的领域。

我最终放弃了"贴近实际工作"。V3 的新测试灵感来自 Zachtronics 编程解谜游戏（Shenzhen I/O 等）。这些游戏使用极其不寻常、高度受限的指令集，强制你用非传统方式编程。程序被拆到多个通信芯片上，每个芯片只能容纳约 10 条指令和一两个状态寄存器。巧妙的优化往往涉及把状态编码到指令指针或分支标志里。

我设计了一组使用微型、高度受限指令集的解谜题，优化目标是最小化指令数。无可视化工具、无调试器——通过插入精准的 print 语句或让 coding 模型在几分钟内生成交互式调试器来构建自己的工具。判断如何投资工具建设本身就是被测试的信号。

**测试 Claude Opus 4.5 在这个新问题上——它失败了。**

**我对这个决策的真实感受：**

我很遗憾放弃了原版测试的真实性和可变深度。原版有效是因为它像真实工作。替代版有效是因为它模拟**新颖**工作——一个 Claude 在训练数据中没见过的工作。

"贴近实际工作"可能已经是一种奢侈——在模型能解决所有标准优化问题的世界里，你必须去人类有比较优势的领域：第一次面对一个全新的、奇怪的、从没见过的问题，从零推导解决方案。这正是 Zachtronics 式解谜所测试的——不是知识，是第一性原理推理。

### 决策四：开源原版测试作为公开挑战——把劣势变成招聘信号

Opus 4.5 在两小时内追平了最强人类。但在无限时间下——人类仍然有优势。最快的人类提交方案显著超过了 Claude 在使用大量 test-time compute 后的最佳成绩。

我把原版测试开源了。这不是为了炫耀——这是把"AI 已经能打败 2 小时内的人类"变成"但你能用更多时间证明你比 AI 更强吗？"

公开的排行榜：

| 分数 (cycles) | 谁做到的 | 
|---|---|
| 2164 | Claude Opus 4（test-time compute harness 多小时后）|
| 1790 | Claude Opus 4.5（普通 Claude Code 会话，约等于 2 小时最佳人类）|
| 1579 | Claude Opus 4.5（2 小时 harness）|
| 1548 | Claude Sonnet 4.5（远超 2 小时 harness）|
| 1487 | Claude Opus 4.5（11.5 小时 harness）|
| 1363 | Claude Opus 4.5（改进 harness，多小时后）|

如果你能低于 1487 周期——你就打败了 Claude 发布时的最佳成绩。如果低于 1363——你就是人类中的顶尖。

这变成了一个筛选信号：能打败 Claude 无限时间成绩的人几乎一定是非常强的工程师。不需要 2 小时限制——给他们足够时间，看他们能推到多深。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

2025 年 5 月，我测试了 Claude Opus 4 的预发布版本在我们用来招聘性能工程师的 take-home 上的表现。它给出了比 4 小时内的几乎所有人类都好得多的优化方案。

这不是"AI 能不能写代码"的抽象讨论——这是一个具体的、紧迫的工程问题：**我们正在使用的、已经帮我们招到数十个优秀工程师的测试，即将失去信号。** 如果我什么都不做，当 Opus 4 正式发布后，每个候选人的最佳策略都是"让 Claude Code 替你跑测试"——而我们无法区分谁是我们想招的人。

然后 Opus 4.5 来了。在 2 小时限制内，它的分数追平了最强人类——那个人类还是用了 Claude 4 做辅助的。如果我什么都不做，我们的测试将不再是"你能用 AI 辅助做什么"——而是"Claude 能做什么"。

我的任务：设计一个测试，让人类在 2 小时 + AI 辅助的时间限制下，依然能展示出超过纯模型的能力。不是临时的——是一个能活过当前模型的测试。同时保持与真实工作相关、有趣、信号强。

### 行动

**失败尝试一：一个"更难的实际优化问题"——被模型的训练数据碾压**

我选了我做过的一个真实 kernel 优化：在 2D TPU 寄存器上高效转置数据，同时避免 bank conflict。这是一个我花了很长时间从第一性原理推导出解决方案的问题——典型的"理解系统 → 找到约束 → 推导最优方案"流程。

我把问题蒸馏成模拟机器上的简化版本。让 Claude 在一天内实现了骨架代码。然后测试。

Claude Opus 4.5 找到了一个我没想到的优化——而且非常优雅。它没有像人类那样试图找到巧妙的转置模式——它转置了整个计算。重写了程序结构，从根本上回避了数据转置的问题。

在我的真实案例中这个方案行不通——有硬约束。所以我修补了模拟器，堵上了这个捷径。然后 Claude 继续推进——但在找不到最有效的方案时卡住了。看起来我有新问题了。

然后我用 "ultrathink" 功能复查——它解决了。在更长的思考预算下，它找到了正确的方法，甚至知道修复 bank conflict 的特定技巧。

**我意识到自己犯了一个根本性的错误：** 我选了一个**人人都遇到过的问题**。数据转置和 bank conflict 是 GPU/TPU/NPU 编程中的经典挑战——有数十年的大量文献。Claude 的训练数据中有无数工程师讨论这些问题、写教程、分享解决方案的文本。它不是在"推理"——它在从比任何单个人类都大得多的经验基础中"检索"。

用训练数据丰富的问题对抗 LLM——必败。

**失败尝试二：常识方案——被速度差碾压**

另一个方案是"把门槛提高到 Claude Code 单独无法达到的水平"。然后让候选人用 Claude 辅助来完成。

问题是速度。Claude 在前 30 秒读完了整个代码库。人类在前 30 分钟还在理解问题。当人类还在画图理解数据流的时候，Claude 已经提交了第三轮优化。

如果人类试图"驾驭"Claude 参与竞争——他们永远在追赶。他们会花大部分时间去理解 Claude 刚刚做了什么，而不是主动地推动优化。在 2 小时的时间限制下，主导策略是"坐在那儿看着 Claude 跑"——你能干预的地方微乎其微。

这印证了一个痛苦的真相：对于已经有大量训练数据、Claude 在速度上占绝对优势的标准优化问题——在有限时间内，人类没有比较优势。

**亲手解剖——我是怎么找到突破口的：**

我退了一步。不是问"什么优化问题 Claude 做不好"——而是问"**什么样的问题，无论 Claude 有多聪明，它都缺乏回答所需的经验基础？** "

答案是：**一个在自然界中不存在的问题。**

Zachtronics 游戏（Shenzhen I/O、TIS-100、EXAPUNKS）的独特之处在于它们是专门为挑战人类编程思维而设计的。它们的约束是高度人工的——几片芯片，每片 10 条指令，一两个寄存器——在最极限的条件下进行优化。这些约束在真实世界中不存在，所以在互联网上、在教科书里、在开源代码中——几乎找不到相关讨论和解决方案。

这就是突破口：不是找一个更难的实际问题——是创造一个**在 Claude 训练数据中从未出现过的问题**。

**破坏性解决方案——Zachtronics 式微型指令集解谜：**

我设计了一个新的 take-home，使用一个极其微小、高度受限的指令集。目标不是优化实际性能——是在这个受限指令集上最小化指令数。

关键设计决策：

1. **指令集不自然：** 每个芯片只能容纳约 10 行代码和一两个状态寄存器。优化需要把状态编码到指令指针或分支标志中——没有任何真实架构是这样的。没有训练数据可以参考。

2. **无调试工具：** 不提供可视化或调试器。入门代码只检查解决方案是否有效。候选人必须自己判断——是插入精准的 print 语句，还是让 coding 模型在几分钟内生成一个交互式调试器。判断如何投资工具建设是被测试的信号的一部分。

3. **多个独立子问题：** 不像原版的一个深度问题，新测试由多个较小的独立解谜组成。降低了方差（一个卡住不至于全盘崩溃），也让评分分布更宽。

测试 Claude Opus 4.5——它失败了。人类同事（不熟悉问题的人）能显著超过 Claude。我的最强同事的得分高于所有候选人。

**洞察时刻——为什么这个方案能工作：**

Claude 做真实的性能优化比你快——因为它见过无数类似的优化。Claude 做你创造的奇怪解谜比你慢——因为它没见过任何类似的东西。

回到第一性原理：**评估工具的有效性 = f（被评估者在问题空间中的经验 vs. 评估工具的经验）。**

原版测试中：Claude 的经验 ≈ 整个互联网，人类候选人的经验 ≈ 个人职业经历。Claude 有绝对优势。

新版测试中：Claude 的经验 ≈ 零，人类候选人的经验 ≈ 零。两者都从第一性原理开始。但人类在第一性原理推理上有比较优势——这是进化赋予我们的能力。

**我真实的遗憾：**

我放弃了"贴近实际工作"。原版测试有效是因为它直接模拟了 Anthropic 性能工程师的日常工作。替代版有效是因为它创造了完全人工的问题空间。

"现实主义"可能是我们承担不起的奢侈——至少在当前模型的能力水平上是如此。当模型能解决所有标准优化问题时，你必须去人类仍有优势的领域：首次面对一个全新的、奇怪的问题，从零推导解决方案。

### 结果

- 原版 take-home 已被公开为挑战赛。人类在无限时间下的最快成绩显著超过 Claude 在大量 test-time compute 后的最佳成绩。最强人类：**低于 Claude 最佳成绩（1363 cycles）**。
- V3（Zachtronics 式）测试正在使用。早期结果：分数与候选人过去工作的水平相关性良好。
- 招聘管道持续产生结果——从 1000+ 候选人中招到了数十个工程师，包括直接从本科毕业但测试中展示出足够技能的工程师。
- 但没有人知道 V3 能活多久。Opus 4.6 或下一个 Opus——可能再来一次迭代。

**我必须承认的局限：**

新测试方差可能比原版更低（更多独立子问题意味着一个区域的优秀不能完全弥补另一个区域）。但方差低本身也可能是好事——更稳定的评分。

我不确定这个方向能走多远。能否持续设计出模型训练数据中不存在的问题？随着模型能力的提升——它们会不会自己学会处理"任何奇怪的东西"？

V3 的成功没有证明我解决了问题——只证明了在当前模型能力水平下，这个特定的计策还能工作。但计策的寿命在缩短。V1 活了近两年。V2 活了几个月。V3 能活多久？

**最根本的困境：**

当我用 Zachtronics 式解谜取代一个贴近实际工作的测试时——我在做出一个隐含的声明：**当前模型的能力边界已经越过了"人类在标准工作中的比较优势"。** 这是个令人不安的声明，来自一个在 Anthropic 内部看着这些模型进步的人。

公开挑战赛的数据说明了一个更微妙的现实：人类在无限时间下仍然有优势。但招聘测试不能用无限时间——它必须在有限时间内产生信号。在这个约束下，我们必须不断重新发明评估方式。

这不是 AI 安全的抽象讨论——这是每天在招聘管道中上演的军备竞赛。到目前为止，我每个回合都赢了。但下一回合什么时候来——我不知道。

---

*这个分析用第一性原理拆解了 "AI 抗性评估设计" 的根本困境——不是"设计 AI 解决不了的问题"（做不到），是"设计 AI 需要比人类更多时间才能解决的问题"（利用时间窗口的差距）。当模型训练数据覆盖了所有标准优化技术时，"贴近实际工作"从优势变成了劣势——你必须去训练数据之外寻找人类有比较优势的领域。核心洞察：评估工具有效性 = f（被评估者在问题空间的经验 vs. 评估工具的经验），当两者都为零时，人类的第一性原理推理能力胜出。*
