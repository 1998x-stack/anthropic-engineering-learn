# 马斯克式决策审问：构建有效的 AI Agent

> **分析对象**: [Building Effective AI Agents](https://www.anthropic.com/engineering/building-effective-agents)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Erik S. 和 Barry Zhang（作者，Anthropic Agent 架构核心理念的奠基人）

---

## 问题一：你的故事——你做了什么决策，为什么？

我在 2025 年初做了一个在当时的 AI 行业看来近乎异端的决定：**公开发文告诉所有人，你们过度工程化了。最成功的 agent 实现用的不是复杂框架，而是简单、可组合的模式。**

这不是谦虚。这是我亲自看了几十个团队的实际生产系统后得出的结论。数据不会说谎。

### 决策一：Workflow vs. Agent 的明确分界——不是所有 AI 系统都是 "agent"

**当时的混乱是什么？**

2024 年底到 2025 年初，"agent" 这个词已经彻底失去了意义。有些人把完全自主运行数天的系统叫 agent。有些人把按固定步骤调用 LLM 的脚本也叫 agent。客户问"我需要一个 agent 吗？"——所有人都说"是的！" 但没人说清楚"什么是 agent"。

这种定义的混乱导致了一个工程灾难：团队在只需要一个简单 workflow 的地方构建了复杂的 agent 系统。花了数月时间、耗费巨额 token 成本——最后发现，一个 prompt chain 就能解决同样的问题，而且更可靠、更快、更便宜。

**我的第一性原理拆解：**

我回到最根本的问题：**"agent" 和 "workflow" 的物理区别是什么？**

- **Workflow**：系统的控制流是由**预定义代码路径**决定的。LLM 是聪明齿轮——它在每个步骤作出推理，但步与步之间的决策是由代码控制的。

- **Agent**：LLM **动态地指导自己的过程和工具使用**，自主维护对任务完成方式的控制。没有预定义的路径——模型在每一步基于环境反馈决定下一步做什么。

这个区分的物理本质是**控制权的归属**。Workflow 中，控制权在代码。Agent 中，控制权在模型。这不是程度差异——这是架构范式的不同。

**为什么这个区分至关重要：**

因为控制权归属决定了系统的故障模式、调试方式、成本和延迟特征。

- Workflow 是可预测的——它总是走相同的步骤。调试一个 workflow 就是调试常规代码。成本是固定的——你知道会调用多少次 LLM。

- Agent 是不可预测的——同一个任务两次运行可能走完全不同的路径。调试一个 agent 需要追踪它的决策过程。成本是可变的——你不知道它会跑多少次循环。

当团队在只需要 workflow 的场景中部署 agent 时，他们在为不需要的灵活性付费——更高的成本、更长的延迟、更复杂的调试。这是工程上的资源错配。

**我的根本原则：**

"找到最简单的解决方案，只在必要时增加复杂度。" 这可能意味着根本不构建 agentic 系统。优化带检索和上下文示例的单次 LLM 调用，对很多应用来说就够了。

这不是"不要用 agent"——这是"在你需要 agent 之前，不要用 agent"。Agentic 系统是用延迟和成本换取更好的任务性能。你需要判断这个权衡是否合理。

### 决策二：五种可组合模式而不是一个万能框架——用乐高替代黑箱

**主流做法是什么？**

行业里充斥着 agent 框架——LangChain、AutoGPT、CrewAI……它们提供了开箱即用的 agent 实现。导入库，配置几个参数，agent 就跑起来了。

问题是什么？这些框架在你和 LLM 之间加了抽象层。你不再能看到底层的 prompt 和响应。调试变得困难——你不知道模型实际收到了什么指令，也不知道它为什么做出某个决策。框架还让你倾向于增加复杂度——"既然框架有这个功能，那我就用吧"。

**我做了什么不同的事？**

我公开说：**从直接调用 LLM API 开始。** 很多模式只需要几行代码。如果你一定要用框架，确保你理解底层代码。对底层机制的误解是客户出错的最常见原因。

然后我把我们在生产环境中看到的最成功的模式提炼为**五种可组合的构建块**：

1. **Prompt Chaining（提示链）**：把任务拆成固定步骤，每一步的输出是下一步的输入。每一步可以有程序化的检查门。物理适用性：任务可以被干净地分解为固定子任务。你在用延迟换精度。

2. **Routing（路由）**：分类输入，导向不同的专门化处理流程。物理适用性：不同类别的输入如果用同一个 prompt 处理会互相伤害——优化 A 类会劣化 B 类。分离关注点。

3. **Parallelization（并行化）**：两种变体——分片（把任务拆成独立子任务并行运行）和投票（同一任务跑多次获取多样输出后聚合）。物理适用性：子任务独立且可并行，或需要多视角提升置信度。

4. **Orchestrator-Workers（编排器-执行器）**：中央 LLM 动态分解任务、委派给执行 LLM、合成结果。物理适用性：子任务无法预先定义——取决于具体输入。与并行化的关键区别：灵活性——子任务不是预定义的，由编排器动态决定。

5. **Evaluator-Optimizer（评估器-优化器）**：一个 LLM 生成，另一个 LLM 评估并反馈，循环迭代。物理适用性：有明确的评估标准，迭代改进提供可衡量的价值。类比人类写作的修改过程。

**这五个模式的物理本质：**

它们不是"五个最好的 agent 设计"——它们是**复杂度递增的五个 control flow 拓扑结构**。从完全确定性的 prompt chain 到完全自主的 agent loop。

把控制权 100% 交给代码的 workflow，到控制权 100% 交给模型的 agent——这五个模式是连续的谱系，不是离散的类别。你可以组合它们——在一个 agent 内部的某个步骤使用 routing，在 orchestrator-worker 的评估阶段使用 evaluator-optimizer。

这就是为什么我反对框架：框架给你的是一个固定的抽象。我给你的是一套可以任意组合的拓扑原语。前者限制你，后者解放你。

### 决策三：工具设计的投入 > Prompt 设计的投入——Agent 的瓶颈不是指令，是接口

**直觉是什么？**

所有人都在优化 prompt。prompt engineering 是 2024 年 AI 工程的核心议题。你让 prompt 更清晰、更结构化、更多 few-shot 示例。

**为什么这是资源错配：**

在我们为 SWE-bench 构建编码 agent 的过程中，我们发现：**我们在工具优化上花的时间比整体 prompt 更多。** 这不是偶然——这是 agent 系统的物理特性决定的。

Agent 不是在真空里推理——它在与**环境**交互。工具是 agent 与环境的接口。如果工具定义模糊、参数名令人困惑、返回格式不一致——agent 就会犯错。这与 prompt 写得多好无关。一个完美的 prompt 配上糟糕的工具，结果还是糟糕的。

**我的 ACI（Agent-Computer Interface）原则：**

我提出把 HCI（人机交互）的设计原则应用到 ACI（agent-计算机交互）上。你花多少精力设计给人用的界面，就该花多少精力设计给 agent 用的工具。

具体规则：

1. **给模型足够的时间"思考"再行动。** 工具调用不应该让模型陷入死胡同——格式设计要允许它逐步构建输出，而不是要求它预先知道最终结果的所有细节。比如：让模型重写整个文件而不是生成 diff——因为写 diff 需要在新代码写出之前就知道变更了多少行。这是信息论上的反顺序。

2. **保持格式接近模型在训练数据中自然见过的东西。** 模型在互联网文本中见过大量 markdown，但很少见过被正确转义的 JSON 内嵌代码。所以工具输出用 markdown 而不是 JSON 包裹代码——消除不必要的转义开销。

3. **消除格式负担。** 不要让模型做"准确计数数千行代码"或"字符串转义所有它写的代码"这样的事——这分散了它本该用于解决问题的认知资源。

4. **站在模型的视角。** 基于工具描述和参数名，使用这个工具是否显而易见？还是需要仔细思考？如果是后者——对模型也一样。好的工具定义包含：使用示例、边缘情况、输入格式要求、与其它工具的明确边界。

5. **防呆设计（Poka-yoke）。** 改变参数让犯错更难。我们发现模型在移动出根目录后会混淆相对路径——改成始终要求绝对路径，模型就完美使用了。

**反直觉结论：**

提示词工程关注的是"告诉模型做什么"。工具工程关注的是"让模型能做它被告诉要做的事"。在 agent 系统中，后者的杠杆效应往往大于前者。

### 决策四：Agent 定义——不是"多聪明"，是"多自主"

**主流误读：**

行业里很多人把 agent 等同于"更强的模型"。用 Opus 就是 agent，用 Haiku 就不是。错。

**我的精确定义：**

Agent 是"LLM 基于环境反馈在循环中自主使用工具"。三个要素缺一不可：

1. **自主使用工具** —— 模型决定何时调用哪个工具
2. **环境反馈** —— 每次工具调用返回的结果是下一步决策的依据
3. **循环** —— 不是一次调用，是多轮交互

Agent 开始于人类的指令或交互式讨论。一旦任务明确，agent 独立规划和运行，可能在关键检查点暂停等待人类反馈。任务通常在完成时终止——但也常见设置停止条件（如最大迭代次数）以维持控制。

**这个定义的重要性：**

Agent 的自主性意味着更高的成本和复合错误的可能性。我明确建议在沙箱环境中做大量测试，设置适当的护栏。Agent 不是魔法的——它们是可预测地不可预测的系统。你知道它们能做什么，但不知道它们怎么做到。

**适合 agent 的场景：**
- 无法预测所需步骤数量的开放性问题
- 无法硬编码固定路径的任务
- 你对模型的决策有一定程度的信任
- 需要在受信任环境中扩展任务处理能力

**不适合 agent 的场景：**
- 明确、固定步骤的任务 → workflow 即可
- 成本和延迟敏感的场景 → 优化单次 LLM 调用
- 需要精确控制每一步的场景 → 程序化编排

## 问题二：你解决过最难的问题是什么？

### 情境与任务

2024 年，我与几十个团队合作构建 LLM agent。我反复看到一个模式：团队花了几个月实现复杂的 agent 系统——多 agent 架构、复杂的框架集成、精巧的编排逻辑——结果系统不可靠、难调试、成本爆表。

但在另一边，我看到一些团队用极其简单的实现取得了惊人成果。不是因为他们更聪明——是因为他们问对了问题。

我的任务：不是去教人"如何构建更复杂的 agent"——而是**说服整个行业停止过度工程化，回到第一性原理思考。**

这比构建任何技术系统都难。因为过度工程化的驱动力不是技术需求——是人性。复杂的系统让人感觉很高级。简单的系统让人感觉"不够 AI"。工程师想用最酷的工具。管理者想展示最前沿的架构。

### 行动

**我看到的失败模式——数据驱动的观察，不是理论推演：**

我不是坐在办公室里想"agent 应该怎么设计"——我看了几十个实际生产系统，总结出规律：

1. **框架陷阱。** 团队引入 LangChain 或类似框架，配置好，跑起来。前几周一切顺利。然后问题来了——agent 做出了一个奇怪的决策，没人知道为什么。框架掩盖了底层 prompt 和工具调用的细节。调试变成了猜谜。工程师开始怀疑"是 prompt 的问题还是框架的问题还是模型的问题？"

2. **过早优化。** 一个客服系统只需要将用户查询分类到 5 个类别，每个类别有不同的处理流程。这是 routing workflow 的完美用例。但团队构建了一个完整的自主 agent，让模型在每次对话中决定做什么。结果：agent 偶尔走了一条意想不到的路径，给出错误的回答。客户不满。团队加护栏。系统越来越复杂。最终——他们回归到了一个简单的 routing workflow。白费了三个月的开发时间。

3. **工具定义粪坑。** 一个团队花了两周优化 prompt，但 agent 还是不稳定。我去看了他们的工具定义——参数名含糊、缺少使用示例、多个工具功能重叠导致 agent 不知道选哪个。我让他们花两天重新设计工具接口。问题解决了 80%。

4. **控制权的错配。** 一个金融分析系统需要精确的多步骤计算——先在数据库中查询数据，再计算风险指标，再生成报告。这是 linear workflow。但团队让 agent 自主决定步骤——结果 agent 偶尔跳过"查询数据"这一步，直接基于过时缓存生成报告。客户的合规团队发现后勃然大怒。

**洞察时刻——从几十个案例中提炼的根本规律：**

深夜，看着所有这些案例的笔记，一个模式浮现了：

**过度工程化的驱动因素不是技术——是控制权的困惑。** 团队不知道什么应该由代码控制，什么应该由模型控制。在没有清晰控制权边界的情况下，他们倾向于把一切都交给模型——"让 agent 自己决定"。这看起来更高级。但结果是系统的不确定性超出了它所处理任务的可接受范围。

**控制权分配不是技术选择——它是基于任务特性的物理必然。** 如果任务步骤是固定且可预测的，代码应该控制。如果步骤不可预测且需要动态决策，模型应该控制。控制权应该放在最能做出正确决策的地方——不是放在最酷的地方。

**破坏性解决方案——五模式框架 + "从简单开始"原则：**

我选择不发布另一个框架。我发布了一个**反框架宣言**。

核心信息：不是"用我们的方法构建 agent"——而是"在你需要 agent 之前，不要构建 agent。如果你需要它，从最简单的可组合模式开始。"

五个 workflow 模式不是"你要学习的五种 agent 类型"——它们是复杂度递增的五个控制拓扑。你应该从最左边开始（最简单的 prompt chain），然后问自己"这个模式能解决我的问题吗？" 只有在不能的时候，才向右移动一个模式。移动到 agent 是最后的选择——不是默认的。

这是对行业惯性的直接挑战。当时的整个行业叙事是"一切都要变成 agent"。我说："不。大多数东西只需要一个更好的提示词。"

### 结果

这不是一个可以用单一数字衡量的结果——这是行业思维方式的转变。

但这篇文章的引用和影响是可见的：

- 成为 Anthropic 工程博客中被引用最多的文章
- 五个 workflow 模式被广泛采纳为 agent 体系结构的标准分类法
- "从简单开始，只在必要时增加复杂度"成为 Claude 生态系统的核心设计原则
- 直接影响了后续 Anthropic agent 产品（Claude Code、Claude Research）的架构决策
- 我们的客户开始用"这是我需要的 control flow 模式"而不是"我需要一个 agent"来讨论问题

在 SWE-bench 上的编码 agent 实现中——我们花了更多时间优化工具而不是整体 prompt——这个实现本身成为了工具优先设计的标杆案例。一个简单改动：工具始终要求绝对文件路径而不是相对路径。模型在这之后完美使用了该方法。一个看似微小的工具接口改变，消除了整个错误类别。

**我必须承认的局限：**

这些模式是描述性的，不是规定性的——它们基于我们在 2024 年看到的生产系统。随着模型能力提升，一些模式可能变得不那么必要（更强的模型可能不需要 evaluator-optimizer 循环来改进输出）。其他模式可能变得更加重要（orchestrator-workers 随着模型协调能力提升而扩展）。

"最简单的东西"在今天和明天可能完全不同。2025 年的"简单" prompt chain 可能在 2026 年被一个直接更强大的单次 LLM 调用所取代。这个原则本身不会过时——但它的具体实现是持续变动的。

框架的价值也不应被完全否定。对于快速原型，框架确实能让团队在几小时内而不是几天内启动。关键不是"不用框架"——是"理解框架下面发生了什么"。

**最核心的教训：**

**Agent 工程的首要原则是：不要过度工程化。** 这听起来像一个不性感的教训。大家都想构建"多 agent 协作系统"，都想用"最先进的编排框架"。但物理现实是：复杂度本身有成本——调试成本、维护成本、token 成本、失败成本。每次你增加一个抽象层、一个额外的 agent、一个多余的决策点——你都在付出这些成本。只有当收益明确超过成本时，才应该增加复杂度。

成功的 LLM 系统不是关于构建最精密的系统。它是关于构建**适合你需求的系统**。从简单提示词开始，用全面的评估优化它，只在简单方案不够的时候添加多步 agentic 系统。

这不是我在降低期望。这是我在把 AI 工程从"构建最酷的东西"拉回"解决真正的问题"。
