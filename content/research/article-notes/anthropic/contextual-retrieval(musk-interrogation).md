# 马斯克式决策审问：AI 系统中的上下文检索

> **分析对象**: [Contextual Retrieval in AI Systems](https://www.anthropic.com/engineering/contextual-retrieval)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Daniel Ford（作者，Contextual Retrieval 方法的发明者）

---

## 问题一：你的故事——你做了什么决策，为什么？

RAG（检索增强生成）是 AI 应用的基础设施。你把知识库切成小块 → 转成向量 → 存进向量数据库 → 用户提问时检索最相似的 chunk → 塞进 prompt → 模型生成答案。

问题是：**传统 RAG 在编码信息时系统地摧毁了上下文。** 一个 chunk 说"公司收入增长了 3%"。哪个公司？哪个季度？chunk 本身不知道——它被从完整文档中切出来时丢失了这些信息。

我的方案不是改进 embedding 模型、不是改进检索算法、不是改进 reranker——是**在预处理阶段，用 Claude 为每个 chunk 生成一段 50-100 token 的上下文说明，然后把它贴在 chunk 前面。** 就这么简单。检索失败率降低 49%。加上 reranking——降低 67%。

这不是一个算法的突破。这是一个对问题本质的重新认识。

### 决策一：问题不在检索——在数据准备

**主流做法是什么？**

整个 RAG 社区都在优化同一件事。更好的 embedding 模型。更智能的 chunk 策略。更复杂的检索算法。HyDE（假设文档嵌入）。Summary-based indexing。Multi-vector retrieval。

所有这些都是**在检索阶段修补信息丢失的问题。**

**我回到第一性原理问自己：**

为什么检索会失败？不是因为 embedding 模型不够好——Gemini Text 004 的语义理解已经很强了。不是因为 chunk 策略不够智能——不同的 chunk 大小、重叠策略已经被广泛研究。

**检索失败是因为 chunk 本身就不包含检索它所需的信息。**

"公司收入增长了 3%"。用户搜索"ACME Corp 2023 Q2 收入增长"。这个 chunk 是完美的答案——但它不包含"ACME Corp"或"2023 Q2"这些关键词。Embedding 模型不知道这个 chunk 在说 ACME Corp——它只知道"公司收入增长了 3%"在语义上接近"企业财务表现"。但它不如另一个明确提到"ACME"但不如直接相关的 chunk 更接近。

这是信息论层面的问题：**chunk 被从文档中切出来时，丢失了 chunk 的身份信息。** 就像一个证人只说"他拿走了钱"——没有告诉你谁、什么时候、在哪。不管你的检索算法多聪明——你无法检索一个不包含检索条件的信息。

**我的反直觉方案——在预处理阶段修复信息，而不是在检索阶段：**

不碰 embedding。不碰检索算法。用 Claude 为每个 chunk 生成上下文——在 embedding 之前。

原始 chunk：`"公司收入增长了 3%。"`

加上上下文：`"这段内容来自 ACME Corp 2023 年 Q2 的 SEC 文件；上一季度收入为 3.14 亿美元。公司收入增长了 3%。"`

现在这个 chunk 包含了"ACME Corp"、"SEC 文件"、"Q2 2023"、"3.14 亿美元"——所有用户可能搜索的词都在里面了。Embedding 模型可以正确地捕捉它的语义。BM25 可以精确地匹配关键词。

**这个方法的物理本质：**

它把"chunk 的上下文"从"完整文档中隐含的信息"变成了"chunk 文本中的显式信息"。传统的 RAG pipeline 中，上下文在文档级别，但检索在 chunk 级别。Contextual Retrieval 把上下文拉到了 chunk 级别——检索可以直接访问它。

这不是一个算法的改进——是一个**数据准备范式的转变。** 不是在检索时变聪明——是在准备数据时让数据本身变聪明。

### 决策二：用 Claude 做上下文生成——LLM 是这个任务的最佳工具

**直觉的替代方案：**

- 人工标注：写一个简短说明描述每个 chunk 的上下文。准确但有规模限制——你不可能手工标注百万级别的 chunk。
- 规则引擎：用模板生成上下文——"这段内容来自 {文档名}，在 {段落位置}"。快速但粗糙——你需要的是语义内容，不是文件名。
- 文档级摘要：为每个文档做一个总结，附加到所有 chunk 上。快速但效果有限——"这是一篇关于金融的文档"对检索的帮助微乎其微。

**我为什么用 Claude（具体来说，Claude 3 Haiku）：**

因为上下文生成是一个**自然语言理解 + 自然语言生成**任务。规则引擎不懂语义。

我的 prompt 极其简单——把完整文档和当前 chunk 一起给 Claude，让它生成一段简短的上下文说明：

```
<document>{{完整文档}}</document>
<chunk>{{当前 chunk}}</chunk>
生成一段简短精炼的上下文，将这个 chunk 置于整个文档的语境中，
用于改进搜索检索。只输出上下文，不要其他内容。
```

Claude 读了整个文档（知道 ACME Corp、Q2 2023、SEC 文件），看了当前 chunk（"公司收入增长了 3%"），生成了 50-100 token 的上下文——精准、简洁、包含了检索所需的所有关键信息。

**为什么是 Haiku 而不是 Opus：**

上下文生成不是需要深度推理的任务——它需要的是**读文档 + 提取关键身份信息 + 简洁输出。** Haiku 足够好且足够便宜。

**结合 prompt caching 的经济学：**

把整个文档加载到 cache 一次。然后对每个 chunk 只发送 chunk 内容 + 缓存的文档引用。不用每次为每个 chunk 重新发送完整文档。

成本计算：800 token chunk、8k token 文档、50 token 上下文指令、100 token 上下文输出——**一次性生成全部上下文化 chunk 的成本是每百万文档 token $1.02。**

这意味着一个 100 万 token 的知识库，上下文化的总成本大约是 1 美元。对比人力标注——这是根本性的成本下降。

### 决策三：Contextual Embeddings + Contextual BM25——语义 + 关键词的双重攻击

**单独改进 embedding 能走多远：**

Contextual Embeddings 单独：检索失败率从 5.7% 降到 3.7%。35% 的降低。显著但不够。

为什么？因为 embedding 模型本质上是**语义相似度**驱动。对于"错误代码 TS-999"，embedding 可能找到关于"错误代码"的一般内容——但可能漏掉精确的"TS-999"。这是 embedding 的固有弱点——它对精确的技术标识符、代码、特定名称的敏感性不如语义概念。

**加上 Contextual BM25：**

BM25（Best Matching 25）是基于 TF-IDF 的词频-逆文档频率排名函数。它做的是精确的词和短语匹配。查询"TS-999" → BM25 精确匹配到包含"TS-999"的文档。

Contextual BM25 = BM25 索引建立在上

下文化的 chunk 上（而不只是原始 chunk）。因为上下文化的 chunk 包含了"ACME Corp"、"Q2 2023"等关键词——BM25 现在可以匹配这些词。

**组合效果：**

Contextual Embeddings + Contextual BM25：检索失败率从 5.7% 降到 2.9%。49% 的降低。

这不是 embedding 和 BM25 的简单叠加——这是**互补。** Embedding 捕获语义：BM25 捕获精确关键词。Embedding 在概念层面找相关——BM25 在字符串层面找精确匹配。在传统 RAG 中两者本来就组合——但它们在**原始的、缺乏上下文的 chunk**上工作。Contextual Retrieval 让两者都在**信息完整的 chunk**上工作——各自发挥优势。

### 决策四：加上 Reranking——67% 的终极改善

**为什么还要 reranking：**

用了 Contextual Embeddings + Contextual BM25 检索出 top-150 个候选 chunk。但在 150 个中——top-20 应该是最相关的 20 个，而不是"碰巧出现在前 150"的 20 个。

Reranking 做了初始检索做不到的事情：**对候选 chunk 进行精细排序。** 初始检索（embedding + BM25）是粗筛——快速但不够精准。Reranker 把 top-150 个候选逐一打分，选出真正的 top-20。

**Cohere reranker 的结果：**

Reranked Contextual Embedding + Contextual BM25：检索失败率从 5.7% 降到 1.9%。67% 的降低。

但这是一个用延迟换精度的权衡。Reranking 增加了额外的运行时步骤——即使 reranker 并行评分所有 chunk，还是有不可避免的额外延迟。

**所有的改进都可以叠加：**

- Embeddings + BM25 比单独 embeddings 好
- Voyage 和 Gemini 的 embedding 在我们测试中最好
- Top-20 chunk 比 top-5 或 top-10 更有效
- 加上上下文显著提升检索准确度
- Reranking 比没有 reranking 好
- **所有这些好处叠加：** 最佳配置 = Contextual Embeddings (Voyage/Gemini) + Contextual BM25 + Reranking + Top-20

这是工程中最罕见的情况：不是改进 A 和 B 互斥——而是它们互补叠加。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

RAG 是 AI 应用的标配。但有一个系统性的失败模式：chunk 在被从文档中切分后丢失了上下文——"公司收入增长 3%"，检索系统无法回答"ACME Corp Q2 2023 收入增长了多少"，因为 chunk 本身不包含"ACME Corp"。

整个行业都在从检索端解决这个问题——更好的 embedding、更智能的 chunk、HyDE、summary-based indexing。但这些方法都在**修补症状**——它们试图在检索时重建 chunk 被切分时丢失的信息。

我的任务：**在信息丢失发生的阶段修复它——在预处理阶段，不是在检索阶段。**

### 行动

**我测试过的失败方法：**

1. **文档级摘要附加到所有 chunk** —— 为每个文档生成一个概要，附加到该文档的所有 chunk 上。"这是一篇关于 ACME Corp 2023 年 Q2 财务表现的 SEC 文件。" 实验证明收益非常有限。太泛了——对区分同一文档内的不同 chunk 没有帮助。所有 chunk 拿到相同的摘要，检索系统无法用摘要区分它们。

2. **假设文档嵌入（HyDE）** —— 在检索时让 LLM 生成一个"假设的完美答案"，然后用这个假设答案做 embedding 来检索。概念上精巧但性能低。假设答案可能与实际 chunk 的措辞有语义偏差——embedding 匹配错位。

3. **Summary-based indexing（LlamaIndex 的文档摘要索引）** —— 在文档级别做摘要，用摘要做检索。同样——粒度太粗，在 chunk 级别丢失区分度。

**亲手解剖——我是怎么找到突破口的：**

这些方法的共同失败模式是什么？它们都在**文档级别**或**检索时**处理上下文。而不是在**chunk 级别、预处理时**处理。

我回到最根本的问题：**检索失败时，chunk 到底缺了什么？**

读了几十个失败的检索案例，答案很明显——chunk 缺了它的**身份信息**：它来自哪个文档？在讨论什么实体？在什么时间背景下？前面说了什么？

这导致了一个简单的实验：**如果我在 chunk 前面手动加上一段说明——"这段内容来自 ACME Corp 的 SEC 文件，讨论的是 2023 Q2 收入"——检索会不会改善？**

我在一个小数据集上手工标注了 50 个 chunk，每个加了人工写的上下文。检索改善显著。

**洞察——这不是"更聪明的检索"，是"更聪明的数据"：**

传统 RAG 假设"chunk 的语义信息完全包含在 chunk 的文本中"。这个假设是错的。chunk 是完整文档的一部分——它的含义依赖于文档中其他部分提供的信息。切分操作把隐含的上下文切掉了。

修复不是在检索端——是在数据准备端。**把隐含的上下文变成显式的文本。** 这样 embedding 模型和 BM25 都可以自然地利用它——不需要任何算法改动。

**破坏性解决方案——用 LLM 自动化上下文生成 + Prompt Caching 控制成本：**

人工标注不可扩展——百万级别的 chunk 不可能手工处理。

但上下文生成恰好是 LLM 擅长的任务：读一个完整文档 → 理解一个 chunk 在文档中的位置 → 生成一个简洁的上下文说明。理解文档级别的上下文是 LLM 的核心能力。

用 Claude 3 Haiku（最便宜的模型）加上 prompt caching（文档缓存一次，每个 chunk 只消耗生成上下文的 token）。成本：**每百万文档 token $1.02。**

$1.02 换来 49% 的检索失败率降低。加上 reranking 的成本——67% 的降低。这不是"有点用"——这是把 RAG 从"经常失败"变成"基本可靠"。

### 结果

跨多种知识领域（代码库、小说、arXiv 论文、科学论文）、多种 embedding 模型、多种检索策略的验证实验：

| 配置 | 检索失败率 (1 - recall@20) |
|------|---------------------------|
| 传统 RAG (Embeddings + BM25) | 5.7% |
| + Contextual Embeddings | 3.7% (↓ 35%) |
| + Contextual Embeddings + Contextual BM25 | 2.9% (↓ 49%) |
| + Reranked | 1.9% (↓ 67%) |

上下文化在所有 embedding 模型和所有知识领域上都改善了性能。

**我特别自豪的两个设计决策：**

1. **"如果知识库小于 20 万 token，直接塞进 prompt。"** 这是文章的第二段——在所有 RAG 讨论之前。最简单的方案就是最好的方案。Contextual Retrieval 是为**超出上下文窗口**的知识库设计的。这体现了"从简单开始，只在必要时增加复杂度"的原则。

2. **每百万文档 token $1.02。** 上下文生成的全部成本。不需要专门的嵌入服务，不需要专门的人力标注团队。就是 Claude 3 Haiku 跑一次预处理。

**我必须承认的局限：**

- Chunk 边界的选择（大小、边界位置、重叠量）仍然影响性能——上下文不能弥补糟糕的切分策略。
- 不同 embedding 模型受益程度不同——Voyage 和 Gemini 表现最好，但其他模型也有改善。
- 通用上下文生成 prompt 工作良好——但针对特定领域的定制 prompt（如包含跨文档术语表）可能更好。
- Reranking 增加了运行时延迟。更多 chunk → 更好的检索 → 更多延迟。需要在成本和精度之间找平衡。

**最核心的教训：**

**有时候最好的解决方案不是更聪明的算法——是更好的数据。** 整个 RAG 社区都在优化检索算法、改进 embedding 模型、设计更智能的 chunk 策略。但这些都在修补一个可以在预处理阶段系统性地修复的问题：chunk 丢失了身份信息。

Contextual Retrieval 的本质不是技术上的复杂——它是概念上的清晰。问的不是"怎么让检索更聪明"——是"chunk 缺了什么信息，我怎么在检索之前把它补上？"

50-100 token 的 LLM 生成的上下文。每百万文档 token 一刀。67% 的检索失敗率降低。最简单的方案通常是最好的——但前提是你要问对问题。

---

*这个分析用第一性原理拆解了 Contextual Retrieval 的根本创新——不是在检索阶段修复信息丢失，而是在数据准备阶段防止信息丢失。核心洞察：传统 RAG 的失败不是因为检索算法不够聪明——是因为 chunk 在被切分时系统地丢失了身份信息。解决方案是把隐含的上下文变成显式的文本——用 Claude 为每个 chunk 生成 50-100 token 的上下文说明，在 embedding 和 BM25 索引之前附加到 chunk 上。这不是算法优化——是数据准备范式的转变。*
