# 马斯克式决策审问：AI Agent 的有效上下文工程

> **分析对象**: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Anthropic Applied AI 团队核心成员（Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield）

---

## 问题一：你的故事——你做了什么决策，为什么？

全世界都在沉迷 prompt engineering 的时候，我在推动一个更根本的范式转移——从"写好 prompt"转向"管好 context"。这不是语义游戏。这是认知模型的根本改变。

### 决策一：从 Prompt Engineering 到 Context Engineering——不是词语游戏，是认知模型的重构

**主流做法是什么？**

2024-2025 年，整个 AI 工程社区都在优化同一件事：prompt。系统提示词怎么写？few-shot 示例怎么选？Chain-of-Thought 怎么引导？"找最对的词"是所有人的执念。

这在一开始是对的——当你的用例是"给一段文本做情感分类"或者"总结这篇文章"，模型的输入只有你的 prompt 和目标文本。Prompt 就是一切。

**为什么这个范式不够——第一性原理拆解：**

Agent 不是分类器。Agent 在一个循环里运行——它读入信息、调用工具、获取新信息、再做决策、再调用工具……每次推理都产生新的数据，这些数据可能对下一次推理相关。Context 不是静态的输入——它是一个**不断膨胀的信息宇宙**，而上下文窗口是一个**固定大小的容器**。

问题的物理本质变成了：**在这个信息宇宙中，哪些 token 值得放入那个有限的窗口？**

这不是"prompt 怎么写"的问题——这是"信息如何被筛选、组织、压缩、存留"的问题。Prompt 只是 context 的一个组成部分，还有工具定义、MCP 服务器返回的数据、消息历史、外部检索结果、文件内容……

我打一个类比：prompt engineering 像是在写一封完美的信。context engineering 像是在管理一个新闻编辑部——每一秒都有新的信息涌进来，你必须不断决定什么上头条、什么进简报、什么直接扔掉。

**我的反直觉立场：**

我公开说 prompt 的精确格式（XML tagging vs Markdown headers）正在变得不那么重要。这在 prompt engineering 社区听来是异端——多少人靠"prompt 格式优化"吃饭？但物理现实是：模型越来越强，它能理解不完美格式的 prompt。真正限制 agent 性能的瓶颈已经不是措辞——是**信息过载**。

上下文窗口的有限性是物理约束——不是工程选择。Transformer 架构的自注意力机制产生 n² 的成对关系，每个新 token 增加了对所有已有 token 的关系计算。模型的"注意力预算"是有限资源，每引入一个新 token 就消耗一部分预算。在长上下文中不是硬断崖，而是逐渐退化——模型仍然"有能力"，但对信息的检索精度和长程推理能力下降了。

这是物理极限，不是 prompt 能解决的。

**为什么我确信这是对的？**

因为我们观察到"上下文腐烂"（context rot）是一个跨模型的普适现象——所有 LLM 都在上下文增长时出现信息回忆精度下降。如果我们不主动管理 context，agent 会在自身产生的信息海洋中淹死。

### 决策二：Just-in-Time 上下文 vs. 预加载——检索时机决定了效率边界

**主流做法是什么？**

AI 原生应用的标准范式是：用 embedding 做离线索引，查询时检索最相似的 chunk，塞进上下文——RAG 的标准流程。所有"可能相关"的上下文在推理开始前就被加载进来。

**为什么这不是最优的——物理极限分析：**

预加载有一个根本问题：**你不知道什么是真正相关的，直到你开始推理。** 所以你倾向于"宁可多加载"——把所有可能相关的东西都塞进上下文。"以防万一"。

结果呢？上下文里 70% 的 token 最终没有被使用。但这些 token 仍然消耗注意力预算——它们在 n² 矩阵里占用了注意力的份额，分散了模型对真正关键信息的关注。

**我的方案：Just-in-Time**

Agent 在上下文中保持的是**轻量级引用**——文件路径、存储查询、网页链接——而不是加载完整数据。当推理过程中确定某个数据是需要的，再用工具动态加载进来。

这模仿的是人类认知：我们不把整本书背下来——我们记住"这本书在图书馆三楼左边第二个书架上"，需要时再去拿。

Claude Code 用这个策略做大规模数据

库的复杂分析：模型写定向查询 → 存储结果 → 用 `head` 和 `tail` 命令分析海量数据，而从不把完整数据对象加载进上下文。

**这个决策的物理本质：**

信息检索有两种成本——**空间的**（上下文窗口占用）和**时间的**（检索延迟）。预加载优化了时间成本（不需要运行时检索），代价是空间成本爆表（不相关的数据浪费了注意力预算）。Just-in-Time 优化了空间成本（只加载真正需要的），代价是时间成本更高（运行时每次检索都有延迟）。

关键洞察是：**对于 agent 任务，空间成本比时间成本更致命。** 注意力预算耗尽导致的错误决策（选错工具、忽略关键信息、提前终止）比额外的检索延迟代价大得多。一个慢但正确的 agent ＞ 一个快但跑偏的 agent。

**混合策略的必然性：**

不是非此即彼。法律和金融领域的内容相对静态——预加载一些基础上下文是合理的。但研究、编码、探索性任务是高度动态的——Just-in-Time 是必需的。

Claude Code 用的就是混合模型：`CLAUDE.md` 文件在启动时直接加载（预加载），但 `glob` 和 `grep` 等原语让它在运行时动态导航环境（Just-in-Time）。这样就绕过了陈旧索引和复杂语法树的问题。

### 决策三："正确的海拔"——在死板和模糊之间找到最优信号密度

**两个极端：**

极端一：工程师在 prompt 里硬编码复杂的 if-else 逻辑。"如果用户提到 X，执行步骤 1-7。如果遇到错误类型 A，走分支 B……" 这不是 prompt——这是在 prompt 里手写一个决策树。维护成本爆炸。Agent 变成了没有判断力的规则引擎。

极端二："请你专业地完成任务"——只有高层指导，没有任何具体信号。Agent 被迫猜测你的意图，错误地假设共享上下文，产出你不想要的结果。

**我的"Goldilocks 区域"：**

不硬编码规则 + 不模糊 = **给出强启发式**。

"用好的判断来选择工具"→ 太模糊。

"如果用户要求创建文件，必须先确认目录存在，然后使用 create_file 工具，最后调用 verify_file 工具验证"→ 太死板。

"创建文件前先确认目录结构。选择最适合的工具完成任务。完成后验证结果"→ 正确的海拔。

关键在于：**prompt 提供的是行为框架，不是操作手册。** 模型需要足够具体的信号来引导行为，但也需要足够的灵活性来根据实际情境做出判断。

**另一个反直觉的立场：few-shot 示例的质量 > 数量**

团队的直觉是：把所有边缘情况都写成示例塞进 prompt。这是错的。一堆杂乱的边缘示例产生噪声——模型在太多有时冲突的信号中迷失。

我坚持：**精选一组多样化的、典范性的示例。** 对于 LLM，好的示例是"一张图胜过千言万语"。5 个高质量、有代表性的示例比 50 个覆盖所有边缘情况的示例更有效——因为模型从模式中学习，而不是从规则中学习。

### 决策四：三种长时任务策略的物理分工——不是"选最好的"，是"匹配任务特性"

长时任务（数十分钟到数小时）超出单个上下文窗口容量时，有三个策略。它们的物理特性决定了各自的适用场景：

**1. 压缩（Compaction）**

把即将溢出上下文窗口的对话总结压缩，然后用摘要启动新窗口。这是第一杠杆——对大多数场景足够。

物理属性：保持对话流，适合需要大量来回交流的任务。但有信息损失——过于激进的压缩会丢掉"现在看起来不重要但后面会变得关键"的微妙信息。

最佳实践：先最大化召回（确保压缩捕获所有相关信息），再优化精度（消除冗余内容）。最安全的轻度压缩是清除深层历史中的工具调用结果——一旦工具调用在深层历史中，agent 为什么还需要看原始结果？

**2. 结构化笔记（Structured Note-taking / Agentic Memory）**

Agent 定期写笔记到上下文窗口外的持久化存储，后续再拉回。Claude Code 的待办事项列表、自定义 agent 的 NOTES.md 文件。

物理属性：提供跨上下文的持久记忆，开销极小。适合有明确里程碑的迭代开发。Claude 玩宝可梦是最佳例子——它在数千步游戏中维护精确计数："过去 1234 步我在 Route 1 训练宝可梦，皮卡丘从 2 级升到 10 级，目标达成。"

**3. 子 Agent 架构（Sub-agent Architectures）**

每个子 agent 有干净的上下文窗口做专项工作，主 agent 只接收精简摘要。

物理属性：适合复杂研究和分析任务，并行探索有红利。这不是"三个里面的一个选项"——这是**分离关注点**。子 agent 消耗数万 token 做深度搜索，但只返回 1000-2000 token 的蒸馏摘要。详细的搜索上下文被隔离在子 agent 内部，主 agent 关注的是合成和分析。

**我的分工原则：**

不是选最好的——是匹配任务特性：

- 需要大量来回交流 → **压缩**
- 有明确里程碑的迭代开发 → **笔记**
- 复杂研究和并行探索 → **子 agent**

这三个不是竞争关系——是互补关系。大多数生产级 agent 系统会同时使用多个策略。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

Transformer 架构有一个物理现实：自注意力机制产生 n² 的成对关系。10 万 token 的上下文 = 100 亿个注意力关系。而且模型训练数据中短序列远比长序列常见——模型对上下文范围内的长距离依赖经验更少、专用参数更少。

结果是：随着上下文增长，每个新 token 都在消耗有限的"注意力预算"。模型仍然有能力的错觉——但它对特定信息的检索精度在下降，长程推理能力在退化。这不是硬断崖，而是渐进退化。

我面前的问题：**在给定有限的注意力预算下，如何找到最小的、信号最强的那组 token，最大化期望行为的概率？**

这听起来像一个工程优化问题。但它比那复杂得多——因为"什么信息是相关的"本身就是一个依赖于推理过程的问题，而且推理过程本身又消耗注意力预算。

### 行动

**失败的尝试：**

最早，我们试过"把一切都塞进去"的策略。更大上下文窗口？好，那就把更多信息塞进去。预加载所有可能相关的文档。保留所有工具调用结果。永不清理历史。

结果：Agent 在信息洪流中溺水。它开始忽略关键指令——不是因为指令不在上下文里，而是因为在 15 万 token 的噪音中，那些指令的注意力权重被稀释了。Agent 开始做出它"不应该做"的决策——不是因为它想违反指令，是因为它在物理上无法有效地注意到那些指令。

然后我们试了另一个极端：激进清理。压缩得太多，丢掉了"当时看起来不重要"的信息——然后 agent 在后续步骤中发现缺少关键上下文，做出错误判断。

**亲手解剖：**

我们做的不是理论推演——是直接观察 agent 在实际长任务中的行为模式：

1. **追踪"上下文腐烂"的实际影响。** 我们设计了针在干草堆（needle-in-a-haystack）风格的测试——在越来越大的上下文中藏一条关键信息，看模型能否准确回忆。结果很明确：所有模型都有退化趋势，只是程度不同。这不是某一个模型的 bug——这是 Transformer 架构的特性。

2. **拆解 Claude Code 的上下文组件。** 当 agent 在一次长会话中使用数万 token 时，真正有多少是"信号"？多少是"噪声"？我们发现一个惊人的比例：**大部分 token 来自工具调用的原始输出——那些 agent 已经处理过、不再需要重新看的数据。**

   这就是为什么"清除工具调用结果"成了最安全、效果最好的第一步优化：一旦工具调用在深层历史中，agent 不需要再看原始结果。它在调用时已经读取并决策过了。把这些清除掉，释放数千 token 的注意力预算——几乎没有信息损失。

3. **对比不同长时策略的实际效果。** 同一个任务：压缩 vs. 笔记 vs. 子 agent。我们不在真空里讨论理论优势——我们实际跑任务，对比结果质量。

   结论很清楚：
   - 压缩在保持对话流上最优——agent 有"连续记忆"的感觉。但过度压缩导致失去微妙的关键上下文。
   - 笔记在跨会话连贯性上最优——agent 通过自己的笔记自引导。但笔记的内容完全依赖 agent 的判断力（它可能写错了、漏了关键信息）。
   - 子 agent 在任务分解和并行化上最优——但代价是更高的 token 开销和编排复杂度。

**洞察时刻：**

盯着这些实验结果，一个根本的洞察击中了我：

**上下文工程不是在优化一个"东西"——它是在管理一个"注意力经济"。**

每个 token 有成本（消耗注意力预算）和收益（提供决策信号）。最优上下文不是"信息最多的上下文"——是**边际信号最高的那组 token**。

这完全翻转了传统的思维方式。传统思维问："什么信息可能相关？全塞进去。" 上下文工程问："这个 token 带来的额外信号，值不值得它消耗的注意力预算？"

这解释了为什么少即是多。它也解释了我们之前看到的所有反直觉现象：

- 为什么 sometimes 删除信息能提高性能？→ 释放的注意力预算让模型更关注剩余的高信号 token。
- 为什么"5 个好的 few-shot 示例"比"50 个覆盖所有边缘情况的示例"更好？→ 50 个示例中很多是冗余的——它们消耗了注意力但没有增加新信号。
- 为什么 Just-in-Time 检索比预加载更好？→ 预加载的"以防万一"信息大部分最终没被使用，但全程消耗了注意力预算。

**破坏性解决方案：**

基于"注意力经济"的洞察，我推动了三个层面的工程实践：

**1. 工具设计的代币效率原则**

工具不应该返回"尽可能多的信息"——它们应该返回"刚好够让 agent 做出下一个决策的信息"。工具的返回格式应该紧凑、结构化、消除冗余。工具之间不应该有功能重叠——如果人类工程师无法确定某个场景该用哪个工具，agent 也不可能做得更好。

这就像良好的代码库设计：函数应自包含、对错误健壮、用途极其明确。最小可行的工具集不仅简化了 agent 的决策——也减少了上下文污染。

**2. 渐进式信息揭示（Progressive Disclosure）**

不是一次性把信息地图全部展开——而是让 agent 逐步发现相关上下文。每次交互产生指导下一个决策的上下文：文件大小暗示复杂度；命名约定暗示用途；时间戳可以作为相关性的代理。

Agent 层层构建理解，只在工作记忆中保留必需的内容，用笔记策略做额外持久化。这保持了 agent 对相关子集的关注，而不是被可能相关但实际无关的全量信息淹没。

文件系统的元数据本身就是信息载体——不需要显式加载文件内容就能提供信号。`test_utils.py` 在 `tests/` 目录下跟在 `src/core_logic/` 下意味完全不同。

**3. "先召回再精度"的压缩调优方法论**

压缩的工程难题是选择保留什么、丢弃什么。调优的方法论是：
- 第一阶段：最大化召回——确保压缩捕获 trace 中的每一条相关信息。哪怕包含一些冗余。
- 第二阶段：优化精度——在保证不丢关键信息的前提下，消除多余内容。

先保证不丢东西，再优化不塞垃圾。顺序不能反——因为丢掉的微妙上下文可能再也找不回来。

### 结果

这些实践的效果不能用一个单一数字概括——它们体现在多个维度：

| 维度 | 之前 | 之后 |
|------|------|------|
| 工具调用结果污染 | 深层历史中堆积大量原始输出，消耗注意力 | 清除旧工具结果，释放数千 token 预算 |
| 长任务连贯性 | Agent 在超过上下文限制后行为退化 | 压缩 + 笔记 + 子 agent 的多策略维持连贯 |
| 信息检索效率 | 预加载大量 "以防万一" 的文档 | Just-in-Time 动态检索，只加载真正需要的 |
| Prompt 可维护性 | 硬编码规则树，脆弱且难维护 | 强启发式框架，灵活且可扩展 |
| 子 agent 效率 | 子 agent 返回数万 token 原始结果 | 子 agent 返回 1000-2000 token 蒸馏摘要 |

Claude 玩宝可梦是最直观的证明——agent 在没有人为提示的情况下自主发展出地图、进度追踪、战斗策略笔记。在上下文重置后读取自己的笔记，继续数小时的训练序列或地牢探索。这不是我们的代码让它做的——这是上下文工程让它能自己做到的。

**我必须承认的局限：**

运行时探索比预计算数据检索慢。这是时间-空间的经典权衡——我们优化了空间，付出了时间代价。

Just-in-Time 方法需要可观测性和精心设计的工具来确保 agent 不会在信息导航中迷路——用错工具、追逐死胡同、未能识别关键信息。

模型越强，需要的工程越少——但注意力预算的物理限制不会消失。更大的上下文窗口只能缓解问题，不能解决它——因为更大的窗口意味着更多可能的噪音，依然需要主动管理。

上下文工程本身在快速演变——今天的"最佳实践"可能在下一代模型发布后就过时。这要求工程师持续重新审视自己的假设。

**最核心的教训：**

**注意力是 LLM 最稀缺的资源，不是 token 长度。** 给模型再多上下文窗口，如果不能有效管理其中的信息密度，模型照样会被噪音淹没。上下文工程的本质是：在每一个推理时刻，找到那组边际信号最高的 token——不多也不少。

这就是从 prompt engineering 到 context engineering 的根本转变：从"我该说什么"到"我该让模型看到什么"。

*这个分析用第一性原理拆解了上下文工程的物理基础——Transformer 的 n² 注意力机制决定了注意力是稀缺资源，工程的本质是管理这个注意力经济：每个 token 有成本和收益，最优上下文是边际信号最高的那组 token，不是信息最多的那组。不是"选最好的策略"——是"匹配任务特性的物理分工"。*
