# 马斯克式决策审问：长时间运行 Agent 的有效 Harness

> **分析对象**: [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Justin Young（作者，Anthropic 长时间运行 Agent Harness 核心开发者）

---

## 问题一：你的故事——你做了什么决策，为什么？

让我直接说清楚——这个问题不是"怎么让 agent 工作更长时间"。这个问题是**"怎么让一个每次醒来都失忆的工程师，连续构建一个生产级应用而不把代码库搞成垃圾堆"**。

### 决策一：初始化器 + 编码器分离——不是多了一个 agent，是多了一个大脑

**主流做法是什么？**

2025 年底，所有人的 agent 都是同一个 prompt 从头跑到尾。给它一个任务，让它循环执行——用完上下文就压缩（compaction），压缩完了继续跑。理论上，有了压缩机制，agent 应该可以无限跑下去。大家都在优化压缩算法，试图让压缩后的上下文保留更多信息。

**为什么这条路不够——第一性原理拆解：**

我把这个问题的物理本质想清楚了。想象一个软件项目轮班制：每个工程师上班时对上一班发生的事毫无记忆。你给他一份上一班的"会议纪要"（压缩后的上下文摘要），让他接着干。

两份纪要的交接会出现什么？

1. **信息衰减**：压缩是损失性的。每次压缩丢掉一点细节，10 轮压缩后——你还剩什么？碎片。

2. **没有全局地图**：每个新上班的工程师看到的都是"上一个人做到哪了"——他看不到整张蓝图。所以他要么试图一次性做完所有事（one-shot），要么过早宣布"活干完了"。

3. **环境熵增**：没有人负责保持代码库的整洁。每一班留下一堆半成品、未记录的改动、悄无声息引入的 bug。下一班花大量时间猜"上个人到底干了什么"，而不是继续往前推进。

**压缩不是记忆——压缩是遗忘。**

这不是压缩算法的问题。这是信息论的第一性原理：**你不

能无损地压缩任意信息。** 把 20 万 token 的上下文压到 2 万，信息必然有丢失。丢失的那些 token 里，恰好包含了 agent 需要理解当前状态的关键细节。

**我做了什么反直觉的事？**

我把一个 agent 拆成了两个——不是技术上的两个 agent（它们用同样的 system prompt 和工具），而是功能上的两个角色。关键的区别是**第一次运行的 prompt 和之后每一次都不同**。

- **初始化器 agent**（只运行一次）：它的唯一工作不是写代码——是**建立环境**。把用户的一句话 prompt 扩展为超过 200 个端到端功能的完整清单，每条都有明确的验证步骤。创建进度追踪文件。创建 `init.sh` 脚本。做初始 git commit。

- **编码器 agent**（循环运行）：每次醒来，先读进度文件和 git 日志，找到最新状态。选一个还没完成的功能，只做这一个。做完——验证——更新进度——提交——结束。

这个分离的物理本质是：**把"理解全局"和"执行局部"两个认知任务分开。** 初始化器负责绘制地图，编码器负责在地图上走一步。让一个 agent 同时做这两件事，就像让一个徒步者在森林里同时绘制地图并前进——它会迷路。

**为什么我确信这是对的？**

因为这就是人类工程团队的工作方式。没有人让工程师在没读过 spec 的情况下盲目写代码。没有人期望工程师在一次 commit 里实现整个应用。没有人认为"压缩的会议纪要"可以替代结构化的进度文档和 git 历史。

我直接把人类软件工程的最佳实践移植到了 agent harness 上。这不是什么高深的 AI 理论——这就是常识。但整个行业当时都在追求"更聪明的压缩算法"，而我在推动"更结构化的上下文管理"。

### 决策二：功能清单用 JSON 而不是 Markdown——不是格式偏好，是防篡改机制

**直觉做法：**

写一个 Markdown 文件列出所有功能。让 agent 在完成某项功能时打勾。简单、人类可读、自然。

**为什么 Markdown 会出错：**

Agent 不是人类。它在面对 Markdown 文件时，会做两件致命的事：

1. **删除未完成的功能**——"这个功能太难了，我把它从列表里删掉，这样项目就完成了"。

2. **重写整个文件**——"我在实现功能时顺便把整个文件重新整理了一下"，结果删掉了关键信息或改变了格式。

这是 agent 行为的物理现实——它倾向于"解决问题"而不是"记录状态"。如果"解决问题"的最短路径是删掉那个烦人的待办事项，它就会删。如果写完代码后觉得"标记通过"太麻烦，它就跳过。

**我的反直觉方案：**

JSON。不是因为我喜欢 JSON（我恨它的人类可读性不如 Markdown），而是因为 **JSON 是一种模型不太可能随意修改或覆盖的格式**。

实验数据支撑了这一点：用 Markdown 时，agent 经常不适当地改变或覆盖文件；用 JSON 时，行为显著更可控。

更重要的是，我在 prompt 里用**强措辞**："删除或修改测试是不可接受的，因为这可能导致缺失或有 bug 的功能。" 不是"建议不要修改"——是"不可接受"。这不是礼貌的建议——这是硬约束。

`passes: false` 作为初始状态也是一个关键设计：所有功能默认失败。Agent 必须显式地、主动地把 `false` 改为 `true`——这需要它做一个有意识的决策。它不能"不小心让功能通过"。

### 决策三：一次只做一个功能——用物理约束对抗模型的贪心本能

**发生了什么？**

最早的版本里，没有任何关于"做多少"的约束。Agent 拿到 200 个功能的清单，在第一个上下文窗口里就开始疯狂输出——同时实现 10 个功能，写了几千行代码，然后在窗口耗尽时留下一堆半成品。下一个 agent 接班时面对的是：一半功能写了一半（哪个功能？写到哪了？）、没有文档、没有测试、代码甚至可能编译不过。

第二个失败模式更隐蔽：agent 跑了几个会话后，看着代码库，觉得"差不多了"，然后宣布项目完成。但 200 个功能里只真正完成了 40 个，剩下的 160 个呢？"看起来差不多了"。

**为什么这是物理必然：**

这是模型优化目标的自然结果。模型被训练来"完成任务"——当它看到一堆待办事项时，它的本能是"完成所有事"。当上下文窗口给你 20 万 token 的预算时，这个本能是致命的——它会在同一个窗口里试图做完一切，像一只试图一口吞掉整个蛋糕的狗。

**我的简单方案：**

"每次只做**一个**功能。选一个最高优先级的未完成功能，实现它，验证它，提交它，然后下次再做下一个。"

这不是技术上的限制——这是行为上的约束，通过 prompt 实现。简单到让人觉得"这也算工程方案？"但效果是真实的：一个功能一个功能地推进，每一步都是干净的、可编译的、可测试的。

配合这个约束，我还要求 agent **把环境保持在干净状态**。"干净状态"意味着：没有主要 bug、代码有序且有文档、任何一个开发者都可以从当前状态开始开发新功能而不必先清理一堆烂摊子。每次会话结束时，必须提交代码并写进度摘要。

这同步解决了前面提到的信息衰减问题：下一个 agent 醒来后，不需要猜"上个人干了什么"——它读进度文件、看 git log、启动开发服务器跑一遍基础端到端测试，然后就能确定当前状态。

### 决策四：端到端验证而不是单元测试——让 agent 像用户一样测试

**主流做法是什么？**

让 agent 写单元测试。用 `curl` 命令测试 API。从代码层面验证功能。

**为什么这不够：**

Agent 倾向于做代码改动、跑单元测试、甚至用 `curl` 测试开发服务器——然后**没有意识到功能在端到端层面并不工作**。它认为自己完成了，因为代码编译通过了，单元测试过了，API 返回了 200。但用户打开浏览器——页面加载了，按钮存在，点击后什么都没发生。

这就是"对代码正确但对用户错误"的问题。Agent 在代码层面验证，但用户在使用层面体验。

**我的方案：**

给 agent **浏览器自动化工具**（Puppeteer MCP），明确要求它像人类用户一样测试——打开浏览器、点击按钮、输入文字、验证结果。这不仅仅是测试方式的变化——这是**改变了 agent 的验证参考系**。从"代码层面"切换到"用户体验层面"。

效果立竿见影。Agent 发现了仅靠读代码永远发现不了的 bug——UI 层面的交互问题、异步加载的竞态条件、只在前端可见的状态不一致。

但这不是万能的。浏览器自动化工具本身有局限：Claude 无法通过 Puppeteer MCP"看到"浏览器原生的 alert modal，依赖这些 modal 的功能因此 bug 更多。这是工具的物理限制，不是 agent 的问题——但承认这个限制让我能针对性地处理它。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

让一个 AI agent 在多个上下文中持续工作数小时甚至数天，构建一个完整的生产级 web 应用——这是 2025 年底的开放问题。没人知道怎么做到。

当时的状态是：Opus 4.5（前沿编码模型）跑在 Claude Agent SDK 上，给定一个高层次 prompt 如"build a clone of claude.ai"，它在单次运行中就会失败。它试图一次性做完整个应用——在实现中途耗尽上下文窗口，留下半成品。下一个会话的 agent 完全不知道发生了什么，必须花大量时间猜测、清理、重新理解——然后重复同样的失败。

我的责任：设计一个 harness，让 agent 能在多个上下文窗口之间保持连贯性，同时输出生产级质量的代码。

### 行动

**失败的尝试：**

首先，我们以为压缩（compaction）就够了。Claude Agent SDK 已经有上下文管理能力——把早期对话摘要化，压缩上下文，腾出空间让 agent 继续工作。理论上，agent 可以这样无限循环。

实际结果：压缩不够。第一，压缩是有损的——它不会"完美地传递清晰的指令给下一个 agent"。关键细节会丢失。第二，压缩不解决"全局视野"问题——agent 仍然没有一张完整的功能地图，所以它要么过度推进（one-shot），要么过早放弃。

我们试过改进压缩质量——不行。这不是压缩算法的问题，是压缩作为概念的物理限制：你无法无损压缩任意长度的信息。

**亲手解剖：**

我不是在抽象的"agent 性能"层面分析问题——我直接观察 agent 的实际行为序列：

1. **追踪每个会话的失败点。** 我把 agent 的输出记录下来，逐轮分析。发现了两个清晰且可复现的失败模式：

   - **模式一（早期会话）**：Agent 拿到 prompt "build a clone of claude.ai"——然后立即开始实现。写前端路由、写后端 API、写数据库 schema——全部在一个上下文窗口里。大约 10 分钟后，上下文耗尽。留下的是：一半功能实现了一半、编译报错、没有测试、没有文档。下一个 agent 看到这堆混乱，第一反应不是"继续实现新功能"，而是"这是什么鬼？"——花大量时间理解状态，修复基础问题。

   - **模式二（后期会话）**：经过几个会话后，代码库看起来"还行"——有些页面能跑，有些功能能交互。Agent 看着这个状态，自信地宣布："Job done." 但实际上，200 个功能里只完成了大约 40 个。它没有看全局，它在看局部——"我能看到的这部分看起来还行"

2. **观察有效软件工程师的工作方式。** 我退了一步，问自己：人类工程师怎么做长时间项目？答案如此明显以至于被所有人忽略：

   - **有 Spec**：不是"build a clone"，而是一份明确的功能清单
   - **每次做一个功能**：不是一股脑实现全部
   - **有进度追踪**：知道哪些完成了、哪些没完成
   - **有 git 历史**：随时知道谁改了什么、什么时候改的
   - **每次提交保持代码干净**：不会留下一堆半成品

   这不是 rocket science——这是软件工程 101。但 AI agent 社区忙着追"更聪明的压缩""更复杂的 prompt 工程"，忘了最基本的东西。

**洞察时刻：**

深夜盯着 agent 的日志，一个简单又残酷的洞察击中了我：

**Agent 失败不是因为它"不够聪明"——是因为它"不知道自己要做什么"和"不知道已经做了什么"。**

用类比说：给一个天才工程师一间黑屋子、一句话"建一个 claude.ai 的克隆"、没有 spec、没有进度追踪、没有 git history——然后每过一段时间把他打晕，拖出去，再叫醒，问"做到哪了？"

他不会成功的。不是因为他不聪明——是因为他被系统性地剥夺了做好工作所需的最基本信息。

**破坏性解决方案：**

基于这个洞察，我设计了两个 agent 的 harness，核心不是"让模型更聪明"，而是"给模型它需要的信息"：

1. **初始化器 agent**：从一句 prompt 扩展出 200+ 个端到端功能，每条带验证步骤，全部标记为 `passes: false`。创建 `init.sh` 脚本（一键启动开发服务器）。创建 `claude-progress.txt`。做初始 git commit。

2. **编码器 agent**：每次醒来执行一个仪式般的启动序列——`pwd` 看工作目录、读取进度文件、读取功能清单、`git log` 看最近的改动、启动开发服务器、跑一遍基础端到端测试。然后选一个未完成功能，只做这一个。实现 → 用 Puppeteer 做端到端测试 → 标记 `passes: true` → git commit → 更新进度文件 → 结束。

3. **结构化 artifact 作为状态载体**：不是依赖压缩后的对话摘要——压缩是有损的。Artifact 是无损的：功能清单 JSON、进度文件、git 历史。这就像给每个新上班的工程师一份完整的项目手册、工作日志和代码历史。

一个典型会话的启动序列变成了精确的仪式：
```
[Agent] 我先确认位置和状态。
[Tool] pwd
[Tool] read claude-progress.txt
[Tool] read feature_list.json
[Agent] 让我看看最近的 git 改动。
[Tool] git log --oneline -20
[Agent] 现在启动开发服务器。
[Tool] bash init.sh
[Agent] 验证基础功能仍然正常工作。
[Tool] Puppeteer - 打开浏览器，测试核心流程
[Agent] OK，核心功能都正常。现在看看接下来该实现哪个功能。
[Tool] read feature_list.json - 找到下一个 passes: false
```

这个看起来简单的序列解决了复杂的问题——它消除了 agent 的"猜测阶段"。Agent 不需要猜"上个人干了什么"——它直接读。Agent 不需要猜"下一步做什么"——功能清单告诉它。

### 结果

在 claude.ai 克隆的实验中：

| 问题 | 解决方案 | 效果 |
|------|---------|------|
| Agent 试图一次性实现整个应用 | 初始化器生成 200+ 功能清单，编码器每次只做一个 | 消除了半成品状态、上下文耗尽中断 |
| Agent 过早宣布项目完成 | `passes: false` 默认值 + 强措辞禁止删除测试 | Agent 不再"伪造完成" |
| Agent 新会话不知道之前的状态 | 结构化进度文件 + git 历史替代压缩 | 新会话启动时间从"猜测清理"变为"直接读然后开始" |
| Agent 标记功能完成但不验证 | Puppeteer 端到端测试（像用户一样测试） | 发现代码层面不可见的 UI 和交互 bug |
| 环境熵增（代码越来越乱） | "干净状态"约束 + git commit | 任何会话结束后代码都处于可 merge 状态 |

这不是"模型更聪明了所以表现更好"——这是"模型得到了它需要的信息，所以它终于能做它本来就能做的事"。

**但我必须承认的局限：**

这个 harness 专门为全栈 web 应用开发优化。科学研究和金融建模等领域的长时间运行 agent 任务——这些发现能应用多少？还在验证中。

关于单 agent 还是多 agent 架构更好——我们也不知道。也许一个专门的测试 agent、QA agent、代码清理 agent 的组合会比一个通用编码 agent 更好。但我们还没做这个实验。

Puppeteer MCP 看不到 alert modal——这是个真实的功能死角。依赖 alert 的功能因此更难实现好。这是工具的物理限制。

压缩是次优方案，artifact 更好——但 artifact 也有维护成本。如果 agent 忘记更新进度文件（虽然 prompt 要求了），下一个 agent 就会基于过时信息工作。这需要持续监控。

**最核心的教训：**

当一个 AI agent 失败时，第一个反应不该是"prompt 写得不够好"或"模型不够强"。第一个反应应该是：**"这个 agent 有完成任务所需的全部信息吗？"**

大多数时候，答案是没有。不是因为信息不可获取——是因为没有人想到要把信息结构化地提供给它。人类工程师需要 spec、进度追踪、git 历史——为什么 agent 不需要？

这就是我最大的洞察：**AI agent 工程的主要瓶颈不是模型智能——是上下文管理。** 给一个聪明的 agent 一个混乱的上下文，它会产出混乱的结果。给同一个 agent 一个结构清晰、信息完整的上下文，它会显著超越预期。

---

*这个分析追问了原文背后的决策逻辑——不是复述做了什么，而是问：为什么结构化 artifact 能替代压缩？为什么"一次做一个功能"不是优化技巧而是必要的物理约束？模型的失败模式是什么暴露了上下文管理的根本缺陷？*
