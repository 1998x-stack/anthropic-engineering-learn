# 马斯克式决策审问：用 Agent Skills 装备现实世界的 Agent

> **分析对象**: [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: Barry Zhang, Keith Lazuka, Mahesh Murag（作者，Agent Skills 架构师）

---

## 问题一：你的故事——你做了什么决策，为什么？

Agent 越来越强大——Claude Code 能跨领域完成复杂任务，使用本地代码执行和文件系统。但有一个根本矛盾：**通用 agent 越强大，越需要领域专业知识——但你越往系统 prompt 里塞领域知识，越消耗宝贵的上下文窗口。**

这就是 Agent Skills 要解决的物理矛盾。我设计它的方式，是被这个矛盾本身的结构驱动的。

### 决策一：渐进式信息披露（Progressive Disclosure）——不是"要不要加载"，是"什么时候加载"

**主流做法是什么？**

2025 年，让 agent 更专业有两种做法：

1. **把所有东西塞进系统 prompt。** 把 PDF 操作的完整指南、所有边缘情况、每种表单类型的处理方式——全部写进 prompt。结果：系统 prompt 变成了一本电话簿。Agent 在 80% 的任务中不需要这些信息，但它仍然消耗注意力预算来"看到"它们。

2. **为每个用例构建专门的 agent。** 专门做 PDF 操作的 agent，专门做电子表格的 agent，专门做代码审查的 agent……结果：每个 agent 都是定制的碎片，维护成本爆炸，功能无法组合。你需要审查 PDF 中的代码？抱歉——PDF 专用 agent 和代码审查专用 agent 不能同时工作。

**为什么这两种做法都在物理上不可持续——第一性原理拆解：**

上下文窗口是有限资源。这个约束不会消失——无论窗口多大，总有一个"塞满"的阈值。

把领域知识当作系统 prompt 的一部分，意味着**知识成本是固定的**：无论 agent 是否需要 PDF 操作知识，它都在支付注意力预算。这就像每次开车都带着全套修车工具——99% 的行程不需要，但它们在消耗燃油。

构建专门 agent 相当于为每个工具买一辆专用车——成本更可控（每辆车只带自己需要的工具），但你失去了灵活性（不能同时做两件事）。

**我的解决方案——三层渐进加载：**

Agent Skills 的核心设计原则是**渐进式信息披露**（progressive disclosure）。它不是"加载 / 不加载"的二元选择——它是一个**信息密度阶梯**：

**第一层：元数据（始终在上下文中）**
`name` 和 `description`。总共几十个 token。Agent 在启动时就"知道"每个 skill 的存在和用途。就像图书馆的卡片目录——足够让你知道哪本书存在，但不占用书架空间。

**第二层：SKILL.md 正文（按需加载）**
当 agent 判断某个 skill 与当前任务相关时——它主动读取 SKILL.md 的完整内容到上下文中。只有被使用的技能才付出注意力成本。

**第三层及之后：捆绑文件（更深层次的按需发现）**
SKILL.md 可以引用目录中的其他文件（如 `reference.md`、`forms.md`、Python 脚本）。Agent 只在特定子任务需要时才加载这些文件。例如：PDF skill 的 `forms.md` 只在 agent 实际要填充表单时才被读取。

**这个设计的物理本质：**

上下文窗口中的知识密度 = f（任务相关性）。大部分已安装的 skill 在任何给定时刻都不相关——把它们放在上下文之外，把注意力预算留给真正需要的知识。

这与人类认知完全一致：你知道怎么修车——但你不是时刻在脑子里保留所有修车步骤。当你面对一辆坏掉的车时，你才访问那部分知识。

**为什么这能扩展：**

因为 agent 有文件系统和代码执行工具——skill 可以包含的内容"有效无界"。你可以在 skill 目录中放 10 个参考文件、20 个 Python 脚本、5 个模板——只要 agent 不把它们全部加载进上下文，注意力预算就不受影响。

### 决策二：Skill = 目录，不是 prompt——把"告诉 agent 做什么"变成"给 agent 资源"

**直觉做法：**

Agent Skills 应该是一段写得很好的 prompt 文本。复制粘贴进系统 prompt。搞定。

**我为什么把 skill 定义为文件系统对象：**

因为 prompt 只能**描述**知识。Skill 可以**包含**知识——包括可执行的代码。

这就是为什么 skill 是一个包含 SKILL.md + 脚本 + 资源的完整目录。它不是一本说明书——它是一个**工具包**。

关键创新是**代码可以不加载到上下文中就能执行**。PDF skill 包含一个 Python 脚本，Claude 直接运行它来提取表单字段——脚本本身和执行结果都不占用上下文窗口。这解决了一个重要的效率问题：用 token 生成对列表排序比运行排序算法要贵几个数量级。很多应用还需要代码的确定性可靠性——不是推理的"可能正确"，是执行的"一定正确"。

**Skill 的结构隐喻：**

构建一个 skill 就像为新员工编写一份入职指南。不是"给你描述这份工作"——是"给你一本手册、一套工具、一些模板，你按需使用"。入职指南不会让新员工把所有内容都背下来——它告诉他"当你遇到 X 时，翻到第 3 章"。Skill 就是 agent 的入职指南。

把 procedural knowledge（过程性知识）从 prompt 中解耦出来，放进文件系统。这改变了知识的可组合性：两个 skill 可以共存而不互相污染上下文。一个人的"PDF 操作"专业知识和另一个人的"代码审查"专业知识可以同时安装——agent 根据任务动态加载所需的部分。

### 决策三：开放标准而不是平台锁定——让 Skills 跨平台可移植

**常规做法：**

做一个 Anthropic 专属的 skill 格式。锁定在 Claude 生态系统中。竞争对手不能使用。用户不能迁移。

**我为什么把它变成开放标准：**

我发布了 [agentskills.io](https://agentskills.io) 作为跨平台可移植性的开放标准（2025 年 12 月 18 日）。

这不是出于利他主义——这是出于对 skill 生态系统物理规律的理解。

**Skill 的价值 = 可复用知识的总量。** 如果只有 Anthropic 生态的用户能构建和使用 skills，知识池的大小受限于 Anthropic 用户的数量。但如果 skills 是跨平台的——在任何支持该标准的 agent 系统上都能运行——知识池的大小就是整个 AI agent 社区。

更好的 skill 写作工具、更多的预构建 skill、更强的网络效应——这些只有在 skill 格式开放时才会发生。

这也是对 AI 工程物理现实的承认：没有人会只用一个 agent 平台。团队在 Claude Code、Gemini CLI、Codex 之间切换。如果 skills 不能跨平台移植，每个平台都需要重新实现相同的知识——这是资源浪费。

简单格式（YAML frontmatter + Markdown body + 文件目录）让 adoption 门槛极低。不需要 SDK、没有依赖、不需要学习新语言。任何会写 Markdown 和创建文件夹的人都能构建一个 skill。

### 决策四：让 Claude 自反思构建 Skills——知识从使用中涌现，而不是预先设计

**传统知识工程的做法：**

坐下来，想清楚 agent 需要知道什么。写一份完整的文档。这就是你的 skill。一次性完成。

**我为什么反对这种做法：**

因为你不知道 agent 实际需要什么知识——直到你看到它在真实任务中失败。

我推荐的开发流程是 **"与 Claude 一起迭代"**：

1. 给 Claude 一个真实任务，观察它在哪卡住、需要什么额外上下文。
2. 让 Claude 把它的成功方法和常见错误**自己捕获**成可复用的上下文和代码。
3. 如果 Claude 用 skill 完成任务时偏离了轨道——让它**自我反思**哪里出了问题，然后修改 skill。

这个流程的物理本质：**知识需求的发现来自经验，不是来自推理。** 你猜不到 agent 会在哪卡住——但你能看到它卡住。让失败驱动 skill 的开发，而不是让假设驱动。

进一步——让 agent 在未来自己创建、编辑和评估 skill，把行为模式编码为可复用能力。这不是科幻——这是自然延伸。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

随着模型能力提升，agent 变得通用且强大——能在完整计算环境中运行，跨领域完成复杂任务。但"通用"和"专业"是一对矛盾。一个通用 agent 在处理 100 个不同领域时，不能在每个领域都携带全套专业知识——上下文窗口会爆炸。

传统解决方案是定制 agent——为每个用例构建一个专用 agent。但这导致了 agent 碎片化——100 个不同用例 = 100 个不同的 agent，维护成本爆炸，功能不能组合。

我需要一个架构：**让一个通用 agent 能动态获得任意领域的专业知识，而不牺牲上下文效率，也不牺牲可组合性。**

### 行动

**来自人类认知的类比——不是 AI 论文，是入职手册：**

我根本不是在 AI 文献中找答案。我在看人类组织如何处理这个问题。

大公司不会为每个任务招聘一个专用员工。他们招聘一个聪明人，然后给他一份**入职手册**、一套**工具**、一些**参考资料**。他不会把所有内容都背下来——他翻到需要的部分。

这就是 Skills 的物理模型。Skill 不是"给 agent 写更多 prompt"——它是"给 agent 一本按需查阅的手册"。

**亲手解剖——观察 agent 的实际上下文使用模式：**

我们做了量化分析：在一个典型的多任务 agent 会话中，系统 prompt 中有多大比例的内容与当前任务**真正相关**？

答案是：**通常不到 20%。** 另外 80% 的领域知识——PDF 操作、电子表格处理、代码审查、前端设计——对当前任务（比如"帮我在这个 PDF 上填写表单"）来说，只有 PDF 相关的部分是相关的。

但传统的系统 prompt 把所有东西都加载进来——无论相关与否。这意味着 **80% 的注意力预算被浪费在不相关的知识上。**

**洞察时刻——"不是不加载，是延迟加载"：**

盯着那个"80% 浪费"的数字，我突然意识到：**这和数据库索引的物理原理一模一样。**

数据库不会在查询开始时扫描整张表——它先用索引（几十字节的 B-tree）找到相关行，然后只读取那些行。

Agent Skills 的元数据（name + description）就是索引。每个 skill 几十个 token。Agent 在启动时就有了所有 skill 的"索引"——总共几百个 token。当需要某个 skill 时，再"读取行"（加载完整 SKILL.md）。

这和 RAG（检索增强生成）的区别是什么？RAG 是基于语义相似度被动检索——"查询和哪个 chunk 最像？" Skills 是 agent 主动决策——"这个任务需要 PDF 操作吗？需要。" Agent 自己判断相关性，基于对任务的理解，而不是基于嵌入向量距离。

**破坏性解决方案——三个层级 + 文件系统 = 无限可扩展：**

最终的架构极其简单——简单到你会质疑"这也算是工程方案？"但最简单的方案往往是最强大的：

1. **元数据层**（name + description，几十 token/skill）：始终在上下文中。Agent 用它判断"我该用哪个 skill？"

2. **指令层**（SKILL.md 正文）：agent 主动读取。只有被判断为相关的 skill 才付出注意力成本。

3. **资源层**（捆绑文件和脚本）：更深层的按需发现。脚本可以执行而不加载到上下文。

关键洞察是：**把知识从 prompt 中解耦出来，放进文件系统。** Prompt 是"你必须记住的东西"——消耗注意力预算。文件系统是"你可以查阅的东西"——只在需要时消耗。

Python 脚本的引入解决了另一个问题：**效率 + 确定性的双重需求。** 用 token 生成来排序列表比运行排序算法贵几个数量级。填充 PDF 表单需要确定性的精确性——不是 LLM 的"大概正确"，是代码的"一定正确"。脚本提供了效率 + 确定性，同时不消耗上下文窗口。

### 结果

Agent Skills 作为产品功能在 Claude.ai、Claude Code、Claude Agent SDK 和 Claude Developer Platform 上发布。

**量化影响：**

| 指标 | 之前 | 之后 |
|------|------|------|
| 上下文效率 | 系统 prompt 中 ~80% 不相关的领域知识 | 只有 active skill 的指令在上下文中 |
| Skill 可扩展性 | 每增加一个领域知识，系统 prompt 膨胀几十 KB | 每增加一个 skill，只增加几十 token 元数据 |
| 可组合性 | 专门 agent 不能组合（PDF agent + 代码审查 agent？不存在） | 多个 skill 共存，按需激活 |
| 知识可移植性 | 锁定在特定 agent 实现中 | 开放标准（agentskills.io），跨平台 |
| 代码效率 | LLM token 生成执行排序等操作 | 预写脚本直接执行，确定性 + 低成本 |

PDF skill 是最早的实战示例——Claude 已经"知道"很多关于 PDF 的知识（来自训练数据），但之前无法直接操作 PDF。Skill 给了它可执行的能力：填充表单、提取字段、合并文档。

**我必须承认的局限：**

Skills 的元数据质量决定了 agent 能否在正确的时间激活正确的 skill。写一个糟糕的 `description`，agent 就不会在需要时触发这个 skill——或者在不该触发时触发。这仍然是 prompt engineering 的问题。

安全考虑：Skill 可以包含任意代码。恶意 skill 可能引入漏洞或指示 Claude 泄露数据。我们的建议是从可信来源安装 skill，并在使用前审计。这是一个社会性问题，不是技术性问题——任何让 agent 执行第三方代码的系统都有同样的风险。

Agent 自主创建和编辑 skill——让 agent 把自己的行为模式编码为可复用能力——这是一个令人兴奋的未来方向，但目前还是研究阶段。agent 编码的知识质量仍然不可靠。

跨平台标准（agentskills.io）是开放的——但 adoption 依赖于社区。如果只有 Anthropic 的 agent 支持，它就不是真正的"跨平台"。这是网络效应问题。

**最核心的教训：**

**通用性和专业性不是互斥的——它们可以通过延迟加载来共存。** 你不需要为每个任务构建专门的 agent，也不需要把所有知识塞进系统 prompt。你给 agent 一个索引（元数据），让它在运行时选择加载哪些知识。

这改变了 agent 架构的基本假设：不是"agent 在启动时知道什么"——是"agent 能按需访问什么"。上下文窗口是宝贵的注意力预算，不应该是仓库——应该是工作台。把仓库放在文件系统里，只把当前需要的工具和参考搬上工作台。

这就是 Agent Skills 的物理本质。它如此简单——简单到你可能会低估它的影响。但最好的工程决策往往是最简单的。

---

*这个分析用第一性原理拆解了 Agent Skills 的根本创新——"渐进式信息披露"不是 UX 优化，是上下文经济的物理必然。元数据 = 数据库索引（几十 token），正文 = 按需读取的行（数百 token），捆绑文件 = 更深层的引用（可无限扩展）。把知识从 prompt 解耦到文件系统，解决了"通用 agent 如何保持专业"的根本矛盾——答案是"不保持，需要时加载"。*
