# Agent 的上下文工程：用正确的信息喂养智能体

**作者:** LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/context-engineering-for-agents)  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 上下文工程 (Context Engineering) 是在 Agent 执行的每一步，为上下文窗口填入恰到好处的信息的技术与艺术。四大策略 —— 写入、选择、压缩、隔离 —— 构成了上下文工程的完整方法论。

---

## 核心要点

1. **上下文窗口就是 Agent 的工作记忆** —— 正如 Andrej Karpathy 所说，LLM 是新型操作系统，上下文窗口就是它的 RAM
2. **坏上下文比没上下文更危险** —— 上下文中毒 (Context Poisoning)、上下文干扰 (Context Distraction)、上下文冲突 (Context Clash) 会直接导致 Agent 失控
3. **上下文工程是 Agent 工程师的第一要务** —— Cognition（Devin 的创造者）明确指出：这是构建 AI Agent 工程师最重要的工作
4. **四大策略缺一不可** —— 写入 (Write)、选择 (Select)、压缩 (Compress)、隔离 (Isolate) 各解决不同层面的问题

---

## 一、什么是上下文工程？

Andrej Karpathy 将 LLM 比作一种新型操作系统：

| 操作系统概念 | LLM 类比 | 含义 |
|------------|---------|------|
| CPU | LLM 模型本身 | 执行推理和计算 |
| RAM | 上下文窗口 (Context Window) | 模型当前"看到"的全部信息 |
| 磁盘 | 外部存储（文件、数据库） | 持久化但不直接参与推理 |
| 操作系统 | 线束 (Harness) | 管理资源调度和信息流 |

> **类比理解**  
> 想象你是一位厨师，厨房操作台就是你的"上下文窗口"。操作台面积有限，你不可能把整个仓库的食材全摆上去。上下文工程就是：在做每道菜的每一步时，确保操作台上摆着**恰好需要的食材和工具** —— 多了碍事，少了做不了，错了翻车。

上下文工程需要管理三类信息：

```
┌─────────────────────────────────────────────────────┐
│              上下文窗口中的三类信息                      │
│                                                     │
│  ┌───────────────┐  ┌──────────────┐  ┌───────────┐ │
│  │  指令          │  │  知识         │  │  工具反馈  │ │
│  │ (Instructions) │  │ (Knowledge)  │  │  (Tools)  │ │
│  │               │  │              │  │           │ │
│  │ · 系统提示     │  │ · 事实数据    │  │ · 工具调用 │ │
│  │ · 记忆文件     │  │ · 检索文档    │  │   返回值   │ │
│  │ · Few-shot    │  │ · 代码上下文  │  │ · 错误信息 │ │
│  │   示例        │  │ · 用户记忆    │  │ · 执行日志 │ │
│  │ · 工具描述     │  │              │  │           │ │
│  └───────────────┘  └──────────────┘  └───────────┘ │
│                                                     │
│          每一步都需要精确控制这三类信息的配比             │
└─────────────────────────────────────────────────────┘
```

## 二、为什么 Agent 对上下文工程需求更高？

普通的单轮对话只需处理一次上下文。但 Agent 执行长时任务时，上下文会**持续累积** —— 工具反馈不断涌入，上下文窗口逐渐被填满。这会引发四种致命问题：

| 问题 | 英文术语 | 表现 | 后果 |
|------|---------|------|------|
| 上下文中毒 | Context Poisoning | 幻觉生成的错误信息进入上下文 | Agent 基于错误前提继续推理，错上加错 |
| 上下文干扰 | Context Distraction | 大量上下文淹没了模型的训练知识 | 模型忘记自己本来知道的东西 |
| 上下文混淆 | Context Confusion | 多余的信息影响模型判断 | 模型被无关信息误导 |
| 上下文冲突 | Context Clash | 上下文中不同部分相互矛盾 | 模型行为不可预测 |

> **类比理解**  
> 回到厨师的比喻：**中毒**是有人往你的食材里掺了假料（你不知道盐罐里装的其实是糖）；**干扰**是操作台堆满了杂物，你连菜板都找不到了；**混淆**是一道菜的食谱旁边放着另一道菜的食谱，你搞混了步骤；**冲突**是两张食谱写着相反的调味量。

> **为什么重要**  
> Cognition（Devin 背后的公司）直接说："上下文工程实际上是构建 AI Agent 工程师的**第一要务**。" 这不是锦上添花的优化 —— 这是 Agent 能不能干活的根本问题。

## 三、策略一：写入上下文 (Write)

**核心思想：** 把信息保存到上下文窗口**之外**，防止在压缩或截断中丢失。

### 3.1 草稿板 (Scratchpad)

就像人类做笔记一样，Agent 可以将思考过程和中间结果写入外部存储。

```
Agent 执行过程
┌──────────┐     ┌──────────┐     ┌──────────┐
│  步骤 1   │────→│  步骤 2   │────→│  步骤 3   │
│ 分析需求  │     │ 调研方案  │     │ 编写代码  │
└────┬─────┘     └────┬─────┘     └────┬─────┘
     │                │                │
     ▼                ▼                ▼
┌──────────────────────────────────────────┐
│        草稿板 (Scratchpad / Memory)       │
│                                          │
│  · 步骤 1 的分析结论                       │
│  · 步骤 2 的方案对比                       │
│  · 关键决策和理由                           │
│                                          │
│  即使上下文窗口被压缩，这些内容依然存在        │
└──────────────────────────────────────────┘
```

**实践案例：** Anthropic 的多 Agent 研究员 (Multi-agent Researcher) 会将计划写入 Memory 工具，这样即使后续上下文被截断，核心计划依然可以被重新读取。

### 3.2 跨会话记忆 (Memories)

从"一次对话内的笔记"升级为"跨越多次会话的学习"。

学术界的 Reflexion 框架最早引入了"自我生成记忆"的概念 —— Agent 在任务结束后反思自己的表现，将经验教训写入记忆，下次执行类似任务时参考。

如今的产品已经广泛采用这个思路：

| 产品 | 记忆实现方式 |
|------|------------|
| ChatGPT | 自动提取用户偏好，跨对话持久化 |
| Cursor | 项目级规则文件，Agent 启动时自动加载 |
| Windsurf | 自动生成的长期记忆，用于个性化响应 |
| Claude Code | CLAUDE.md 文件，由 Agent 和用户共同维护 |

## 四、策略二：选择上下文 (Select)

**核心思想：** 精准地将**需要的**信息拉入上下文窗口。写入是"存"，选择是"取"。

### 4.1 草稿板选择

两种方式将草稿板内容带回上下文：

- **工具调用读取：** Agent 主动调用工具来读取之前保存的笔记
- **状态注入：** 线束在每一步自动将草稿板内容注入上下文

关键在于**细粒度控制** —— 不是把所有笔记一股脑塞进去，而是让模型只看到当前需要的部分。

### 4.2 记忆选择

挑战在于**相关性判断** —— 从大量历史记忆中找到当前任务真正需要的那些。

```
记忆选择的两种模式

模式 A：窄域始终加载                模式 B：按需检索
┌─────────────────┐              ┌─────────────────┐
│  CLAUDE.md      │              │  记忆数据库       │
│  rules files    │              │  (大量历史记忆)   │
│  agents.md      │              │                 │
│                 │              │    嵌入向量       │
│  每次启动都加载  │              │    知识图谱       │
│  内容少，精度高  │              │    语义搜索       │
│  适合项目级规则  │              │                 │
└─────────────────┘              │  按需检索        │
                                 │  内容多，需判断   │
                                 │  适合海量记忆     │
                                 └─────────────────┘
```

> **值得注意的风险**  
> Simon Willison 曾指出：记忆检索可能带回**意想不到的内容**。如果攻击者在你的记忆库中注入了恶意指令，按需检索可能把它当成"相关记忆"拉进上下文 —— 这是提示注入 (Prompt Injection) 在记忆层面的延伸。

### 4.3 工具选择

工具太多会让模型困惑。研究表明，对工具描述做 RAG（检索增强生成），按需呈现相关工具，可以将工具选择准确率**提升 3 倍**。

```
错误做法：一次加载全部工具
┌─────────────────────────────────┐
│ 上下文窗口                       │
│                                 │
│ 工具 1 描述 ← 本次不需要          │
│ 工具 2 描述 ← 本次不需要          │
│ 工具 3 描述 ← 需要               │
│ ...                             │
│ 工具 50 描述 ← 本次不需要         │
│                                 │
│ 模型：这么多工具... 选哪个？       │
└─────────────────────────────────┘

正确做法：按需检索呈现
┌─────────────────────────────────┐
│ 上下文窗口                       │
│                                 │
│ 工具 3 描述 ← 高相关              │
│ 工具 17 描述 ← 中等相关           │
│                                 │
│ 模型：清晰明确，直接调用工具 3     │
└─────────────────────────────────┘
```

### 4.4 知识选择（代码场景的 RAG）

Windsurf 创始人 Varun 的核心洞察：

> *"索引代码 ≠ 检索上下文"*（Indexing code ≠ Context retrieval）

代码检索不像普通文档检索那么简单。高质量的代码上下文需要多种技术协同：

| 技术 | 解决的问题 |
|------|-----------|
| AST 解析 (Abstract Syntax Tree) | 理解代码结构，而非仅仅文本匹配 |
| 语义分块 (Semantic Chunking) | 按逻辑单元而非固定长度切分代码 |
| Grep / 正则搜索 | 精确定位已知的标识符和模式 |
| 知识图谱 (Knowledge Graph) | 追踪函数调用链、依赖关系 |
| 重排序 (Re-ranking) | 对候选结果按相关性排序 |

## 五、策略三：压缩上下文 (Compress)

**核心思想：** 保留关键 token，丢弃冗余 token。当上下文窗口快满的时候，压缩是唯一的出路。

### 5.1 上下文摘要 (Context Summarization)

用模型自己来总结和压缩上下文。

```
压缩触发流程

上下文使用率:  ████████████████████░░░░  95%
                                      ↓ 触发自动压缩
                                      
原始上下文 (100k tokens)
┌─────────────────────────────┐
│ 消息 1: 用户请求             │
│ 消息 2-50: 工具调用和反馈     │ ──→ 压缩为摘要
│ 消息 51-80: 中间推理过程      │ ──→ 压缩为摘要
│ 消息 81-100: 最近的工作       │ ──→ 保留原文
└─────────────────────────────┘
                ↓
压缩后 (30k tokens)
┌─────────────────────────────┐
│ 消息 1: 用户请求             │
│ 摘要: 前 80 条消息的核心内容   │
│ 消息 81-100: 最近的工作       │
└─────────────────────────────┘
```

**实践案例：**
- **Claude Code** 在上下文使用率达到 95% 时自动触发压缩 (auto-compact)
- **Cognition (Devin)** 使用专门微调的模型来做摘要，尤其在 Agent 与 Agent 之间传递上下文时

### 5.2 上下文修剪 (Context Trimming)

比摘要更"粗暴"但更高效 —— 直接按规则删除内容。

| 方式 | 说明 |
|------|------|
| 硬编码启发式 | 删除最早的 N 条消息、截断过长的工具输出 |
| 训练剪枝器 | 如 Provence 模型，经过训练来判断哪些 token 可以安全删除 |

> **类比理解**  
> 摘要就像你在书上划重点然后写读书笔记 —— 信息被浓缩但保留了语义。修剪则像你直接撕掉前面的章节 —— 简单粗暴，但有可能丢失重要线索。实际工程中两者通常配合使用。

## 六、策略四：隔离上下文 (Isolate)

**核心思想：** 把上下文拆分到不同的 Agent 或环境中，让每个执行单元只看到自己需要的信息。

### 6.1 多 Agent 隔离

每个子 Agent (Sub-agent) 拥有独立的上下文窗口，专注于窄范围的子任务。

```
主 Agent
┌────────────────────────────────────────────────┐
│  上下文: 高层计划 + 任务分解                       │
│                                                │
│    分发任务          分发任务         分发任务      │
│       │                │               │        │
│       ▼                ▼               ▼        │
│  ┌─────────┐     ┌─────────┐     ┌─────────┐   │
│  │ 子Agent A│     │ 子Agent B│     │ 子Agent C│   │
│  │         │     │         │     │         │   │
│  │ 独立上下文│     │ 独立上下文│     │ 独立上下文│   │
│  │ 只看到   │     │ 只看到   │     │ 只看到   │   │
│  │ 子任务 A │     │ 子任务 B │     │ 子任务 C │   │
│  └─────────┘     └─────────┘     └─────────┘   │
│       │                │               │        │
│       ▼                ▼               ▼        │
│             汇总结果到主 Agent                    │
└────────────────────────────────────────────────┘
```

Anthropic 的描述：子 Agent "在各自独立的上下文窗口中并行运行"。

> **权衡取舍**  
> 多 Agent 隔离可以有效避免上下文污染，但代价是 token 用量可能增加到 **15 倍** —— 因为每个子 Agent 都需要加载基础指令和工具描述。这是一个经典的"空间换质量"的权衡。

### 6.2 环境隔离 (Environment Isolation)

HuggingFace 的 CodeAgent 提供了另一种思路：Agent 输出代码，代码在沙箱中执行，**变量持久化在运行环境中**，而非存储在 LLM 的上下文窗口里。

```
LLM 上下文                    Python 运行环境 (沙箱)
┌───────────────┐            ┌───────────────────┐
│ 只保留代码逻辑  │ ──生成──→  │ df = pd.read(...)  │
│ 和高层推理      │            │ result = df.sum()  │
│               │            │                   │
│ 不存储数据内容  │  ←─返回──  │ 变量持久化在这里    │
│ 不存储中间变量  │   摘要     │ 数据持久化在这里    │
└───────────────┘            └───────────────────┘
```

> **为什么重要**  
> 这种设计让 LLM 上下文保持"干净" —— 只包含推理逻辑，把数据和中间状态卸载到执行环境中。对于数据密集型任务（数据分析、ETL 等），这是避免上下文爆炸的关键模式。

### 6.3 状态隔离 (State Isolation)

线束可以维护一个运行时状态对象 (Runtime State)，将不同类型的信息存储在不同的字段中。只有消息历史暴露给 LLM，其他元数据、中间结果存在状态对象的其他字段中。

```
运行时状态对象 (Runtime State)
┌──────────────────────────────────────────┐
│                                          │
│  messages: [...]  ← 暴露给 LLM           │
│                                          │
│  metadata: {...}  ← 对 LLM 不可见        │
│  tool_cache: {...}  ← 对 LLM 不可见      │
│  intermediate_results: {...} ← 对 LLM 不可见│
│                                          │
│  线束决定哪些字段在什么时候暴露给模型         │
└──────────────────────────────────────────┘
```

## 延伸思考

1. **压缩的信息损失：** 上下文压缩不可避免地会丢失信息。有没有办法量化"压缩后 Agent 性能下降了多少"？怎样的压缩策略能在 token 节省和性能保持之间找到最优平衡点？

2. **隔离的成本问题：** 多 Agent 隔离最高带来 15 倍的 token 开销。随着 Agent 任务越来越复杂，如何设计"最小隔离"策略 —— 在避免上下文污染的同时，尽量减少冗余 token？

3. **上下文中毒的防御：** 如果 Agent 自己产生的幻觉被写入记忆并在未来被检索回来，这种"自我中毒"循环如何打破？是否需要记忆的"可信度评分"机制？

4. **从手工到自动：** 当前的上下文工程大量依赖人工设计的启发式规则。未来是否会出现"元 Agent" —— 一个专门负责为其他 Agent 做上下文工程的 Agent？
