# 用线束工程提升深度 Agent：从排行榜第 30 名到第 5 名

**作者:** LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)  
**日期:** 2026 年 5 月  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 不换模型，只改线束 (Harness)，编程 Agent 在 Terminal Bench 2.0 上从 52.8% 提升到 66.5%，排名从第 30 名跃升到第 5 名。线束工程不是锦上添花，而是决定性的胜负手。

---

## 核心要点

1. **线束工程的 ROI 惊人** —— 同一个模型 (gpt-5.2-codex)，仅调整线束就带来 13.7 个百分点的提升
2. **"自我验证"是最大的杠杆** —— Agent 最常见的失败模式是"写完代码、看一眼觉得没问题、就停了"，强制验证是最有效的干预
3. **中间件 (Middleware) 是线束的核心武器** —— 通过钩子拦截 Agent 的关键行为（退出、循环、超时），注入确定性逻辑
4. **推理计算也需要"编排"** —— 不是推理越多越好，"推理三明治" (Reasoning Sandwich) 策略比全程最高推理多 12.6 个百分点

---

## 一、什么是线束工程 (Harness Engineering)？

线束工程的目标很明确：**在不换模型的前提下，通过优化模型周围的工具和逻辑，提升任务完成率、降低 Token 消耗、减少延迟。**

> **类比理解**  
> 模型是赛车引擎，线束是底盘、悬挂、空气动力学套件。两台车装同一款引擎，但底盘调校不同，圈速可以差出几秒。线束工程就是 Agent 领域的"底盘调校"。

### 核心方法论：用 Trace 驱动改进

线束工程不是凭直觉改参数，而是用**执行轨迹 (Trace)** 大规模分析故障模式，找到最高频的失败原因，然后针对性修复。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  运行基准测试  │────→│ 收集执行轨迹  │────→│ 分析故障模式  │
│  (Benchmark)  │     │  (Traces)    │     │  (Patterns)  │
└──────────────┘     └──────────────┘     └──────┬───────┘
                                                  │
       ┌──────────────────────────────────────────┘
       │
       ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ 修改线束配置   │────→│ 重新跑基准    │────→│ 对比改进幅度  │
│ (Harness)    │     │  (Re-run)    │     │  (Delta)     │
└──────────────┘     └──────────────┘     └──────────────┘
       │                                          │
       └──────────── 循环迭代 ─────────────────────┘
```

这个循环类似于机器学习中的 Boosting —— 每一轮聚焦上一轮犯的错误，逐步消除最高频的失败模式。

## 二、实验设置

### Terminal Bench 2.0

| 维度 | 说明 |
|------|------|
| **任务数** | 89 个任务 |
| **领域覆盖** | 机器学习、调试、生物信息学 |
| **执行环境** | Harbor 编排 + Daytona 沙箱 |
| **可观测性** | 每个动作记录到 LangSmith |
| **固定模型** | gpt-5.2-codex |

### 三个可调"旋钮"

线束工程的改进集中在三个维度：

| 旋钮 | 说明 | 类比 |
|------|------|------|
| **系统提示 (System Prompt)** | 给 Agent 的行为指南 | 赛前战术手册 |
| **工具 (Tools)** | Agent 可用的外部能力 | 车载工具箱 |
| **中间件 (Middleware)** | 包裹在模型和工具调用前后的钩子逻辑 | 安全气囊 + 限速器 |

**基线成绩：** 默认提示 + 标准工具 + 无中间件 = **52.8%**

### Trace 分析器：让 Agent 诊断 Agent

LangChain 构建了一个专门的 Trace 分析技能 (Trace Analyzer Skill)：

1. 从 LangSmith 拉取一批实验的执行轨迹
2. 并行生成多个错误分析子 Agent，各自分析不同的失败案例
3. 主 Agent 综合所有子 Agent 的发现，提炼出可操作的改进建议
4. 根据建议修改线束，进入下一轮迭代

> **为什么重要**  
> 手动翻看 89 个任务的执行轨迹不现实。用 Agent 分析 Agent 的失败轨迹，是实现大规模线束迭代的关键。

## 三、哪些改动带来了提升？

### 3.1 构建-验证循环 (Build & Self-Verify)

**问题：** 最常见的失败模式 —— Agent 写完代码后，重新阅读自己的代码，觉得"看起来没问题"，就直接退出了。**从不运行测试。**

> **类比理解**  
> 这就像一个程序员写完代码后只做了 Code Review，从不编译运行。看着没问题 ≠ 跑起来没问题。

**解法：** 在系统提示中强制要求四步工作流：

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  1. 规划发现   │───→│  2. 构建实现   │───→│  3. 验证测试   │───→│  4. 修复缺陷   │
│  Planning &   │    │  Build       │    │  Verify      │    │  Fix         │
│  Discovery    │    │              │    │              │    │              │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

**关键中间件：PreCompletionChecklistMiddleware**

这个中间件在 Agent 试图退出时触发拦截，提醒它对照任务规格说明 (Task Spec) 逐项检查是否真正完成。

> 这与 Ralph Wiggum Loop 的设计思想一致 —— 通过钩子 (Hook) 在 Agent 退出前强制它继续执行验证步骤。

### 3.2 给 Agent 提供环境上下文

Agent 经常在不了解自身运行环境的情况下开始工作，导致大量时间浪费在探索目录结构上。

**三个具体改进：**

| 中间件/策略 | 作用 | 效果 |
|------------|------|------|
| **LocalContextMiddleware** | Agent 启动时自动注入当前工作目录和目录结构 | 减少"摸索环境"的浪费 |
| **明确测试方式** | 告知 Agent 其代码将被程序化测试 | 引导 Agent 写可测试的代码 |
| **时间预算注入** | 注入剩余时间提醒，引导 Agent 从实现切换到验证 | 避免"实现到最后一秒，没时间验证" |

> **为什么重要**  
> 上下文工程 (Context Engineering) 不只是优化 Prompt。它是"替 Agent 做好入职引导"—— 就像新员工第一天，你会告诉他办公室在哪、项目用什么技术栈、代码规范是什么。不说这些，他也能慢慢摸索出来，但会浪费大量时间。

### 3.3 帮 Agent 跳出死循环 (Doom Loop)

**问题：** Agent 反复编辑同一个文件，每次微调一点，但从不后退一步重新思考方法。

> **类比理解**  
> 这就像你在迷宫里一直撞同一面墙，每次换个角度撞，但从不考虑走另一条路。

**解法：LoopDetectionMiddleware**

这个中间件跟踪每个文件的编辑次数。当同一个文件被编辑超过 N 次时，注入一条提示："考虑重新审视你的方法。"

虽然只是一条简单的提示，但足以让模型"抬头看路"，从局部优化切换到全局重新规划。

### 3.4 编排推理计算 (Reasoning Compute)

gpt-5.2-codex 有四种推理模式：`low`、`medium`、`high`、`xhigh`。

**直觉假设：** 推理越强越好 → 全程 `xhigh`。

**实际结果：**

| 策略 | 得分 | 问题 |
|------|------|------|
| 全程 `xhigh` | 53.9% | 频繁超时，慢推理吃掉了执行时间 |
| 全程 `high` | 63.6% | 快但关键步骤推理不够深 |
| **推理三明治** `xhigh → high → xhigh` | **66.5%** | 兼顾深度思考与执行效率 |

### 推理三明治 (Reasoning Sandwich)

```
┌─────────────────────────────────────────────────────────────────────┐
│                        任务执行时间线                                 │
│                                                                     │
│  ██████████████     ░░░░░░░░░░░░░░░░░░░░░░     ██████████████       │
│  ◀── xhigh ──▶     ◀────── high ──────▶     ◀── xhigh ──▶       │
│                                                                     │
│  深度规划 & 理解      快速实现 & 迭代           深度验证 & 修复        │
│  "想清楚做什么"       "快速做出来"              "确认做对了"           │
└─────────────────────────────────────────────────────────────────────┘
```

> **为什么重要**  
> 推理计算不是"越多越好"，而是"在对的时候用对的量"。开头用深度推理理解问题、制定计划；中间用快速推理高效实现；结尾用深度推理严格验证。这就像考试策略——先花 10 分钟审题想思路，中间快速作答，最后留时间检查。

## 五、实践启示

### 1. 替 Agent 做好上下文工程

不要指望 Agent 自己摸索环境。主动注入：

- 目录结构和关键文件位置
- 可用工具和最佳实践
- 代码将如何被测试

### 2. 激进地推动自我验证

Agent 天然倾向于"写完就停"。必须通过中间件**强制**验证：

- 退出前运行测试
- 对照任务规格逐项检查
- 区分"看起来对"和"跑起来对"

### 3. 用 Trace 作为反馈信号

不要凭直觉调参。**分析执行轨迹**，让数据告诉你：

- 哪些任务失败了？
- 失败的模式是什么？
- 工具和推理哪个环节出了问题？

### 4. 检测并修复坏模式

用确定性逻辑拦截已知的失败模式：

- 死循环 → LoopDetectionMiddleware
- 跳过验证 → PreCompletionChecklistMiddleware
- 时间分配不合理 → 时间预算注入

### 5. 线束要适配模型

不同模型需要不同的线束设计。Claude 和 Codex 的最优提示策略、工具配置、推理编排都不同。**没有通用的最优线束**——线束必须针对具体模型调校。

## 延伸思考

1. **线束工程的天花板在哪里？** 13.7 个百分点的提升令人印象深刻，但继续迭代还能带来多少增益？是否存在收益递减点？如果存在，那个点之后应该把精力转向哪里？
2. **中间件的副作用：** 每个中间件都在消耗上下文窗口空间和执行时间。随着中间件越加越多，是否会出现"中间件膨胀"问题？如何衡量一个中间件的 ROI？
3. **推理三明治的通用性：** xhigh-high-xhigh 的策略是否适用于所有任务类型？对于纯调试任务、纯创意任务、纯数据处理任务，最优的推理编排是否不同？
4. **从 Boosting 到 Agent 改进：** Trace 分析器的工作方式类似 Boosting——聚焦前一轮的错误。这个类比能走多远？是否可以借鉴更多集成学习的思想来系统化线束迭代？
