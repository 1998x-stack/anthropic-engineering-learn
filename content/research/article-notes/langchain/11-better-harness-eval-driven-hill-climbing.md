# Better-Harness：用评估驱动的爬山法持续优化 Agent 线束

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/better-harness-eval-driven-hill-climbing)  
**日期:** 2026 年 4 月 8 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 评估 (Eval) 之于 Agent，正如训练数据之于经典 ML 模型。Better-Harness 是一套系统化的"爬山法 (Hill-Climbing)"流程——用评估信号驱动线束的每一次迭代，让 Agent 从"能用"走向"好用"。

---

## 核心要点

1. **评估就是 Agent 的训练数据** —— 每条评估提供一个信号："Agent 做对了吗？"这个信号引导下一次线束编辑的方向
2. **爬山法必须防过拟合** —— 将评估集拆分为"优化集"和"保留集 (Holdout)"，确保改进是真正的泛化而非局部拟合
3. **一次只改一件事** —— 每轮实验只做一个定向修改，避免混杂因素，确保因果可归因
4. **评估需要像训练数据一样维护** —— 随模型迭代，评估也需要"大扫除"：移除已饱和的、更新不再适用的
5. **终局是飞轮** —— 生产轨迹 → 自动发现错误 → 生成评估 → 优化线束 → 更好的 Agent → 更多轨迹

---

## 一、评估 = Agent 的训练数据

### 为什么这个类比精确

在经典机器学习中，每一条训练样本贡献一个梯度 (Gradient)，引导模型参数向正确方向更新。Agent 评估的角色完全对等：

| 经典 ML | Agent 工程 |
|---------|-----------|
| 训练样本 | 评估用例 (Eval Case) |
| 梯度信号 | "Agent 是否执行了正确的动作？" |
| 模型参数更新 | 线束编辑 (Prompt / 工具 / 逻辑) |
| 训练数据质量 | 评估设计的严谨程度 |

> **类比理解**  
> 想象你在教一个新员工做客服。你不会告诉他"好好干"然后就走了——你会准备一套**标准案例**："遇到退款请求这样处理、遇到投诉这样处理。"这些案例就是评估。每次新员工处理完一个案例，你检查结果、给反馈、调整他的操作手册。这就是 Better-Harness 在做的事情。

### 为什么重要

> 很多团队把评估当作"测试"——上线前跑一次就完了。Better-Harness 的核心洞察是：评估不是一次性的考试，而是**持续驱动改进的训练信号**。对评估的设计应该投入与 ML 训练数据质量管理同等的严谨程度。

---

## 二、如何获取好的评估

好的评估是整套方法论的燃料。来源有三类：

| 来源 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| **手工构造 (Hand-curated)** | 精准反映期望行为 | 耗时，难以规模化 | 核心场景、边界情况 |
| **外部数据集 (External Datasets)** | 数量大，覆盖广 | 需要人工筛选以对齐实际需求 | 补充覆盖率 |
| **生产轨迹挖掘 (Trace Mining)** | 来自真实用户行为 | 需要标注和清洗 | 发现未预料的失败模式 |

### 关键实践：给每条评估打标签

为评估打上**行为类别标签** (Behavioral Category Tag)，例如"工具选择"、"多步推理"、"默认参数使用"等。

标签带来两个关键能力：

1. **有意义的拆分** —— 可以按类别构建保留集，确保每个行为维度都被验证
2. **定向实验** —— 当某类评估失败率高时，可以针对性地优化

> **类比理解**  
> 就像体检不能只量体重——你需要分项检查（血压、血糖、心率）。给评估打标签就是给 Agent 做"分项体检"，而不是只看一个总分。

## 三、Better-Harness 流程：六步爬山法

### 全景图

```
┌──────────────────────────────────────────────────────────────┐
│                  Better-Harness 爬山循环                       │
│                                                              │
│   ① 收集 & 标记评估                                           │
│       │                                                      │
│       ▼                                                      │
│   ② 按类别拆分 ──→ 优化集 (Optimization Set)                   │
│       │              保留集 (Holdout Set)                      │
│       ▼                                                      │
│   ③ 跑基线 (Baseline) ──→ 记录优化集和保留集的初始分数            │
│       │                                                      │
│       ▼                                                      │
│   ┌─────────────────────────────────────┐                    │
│   │  ④ 优化循环 (每轮一次)               │                    │
│   │                                     │                    │
│   │   ⑤ 做一个定向修改                   │                    │
│   │      (改 Prompt / 加工具 / 调逻辑)   │                    │
│   │       │                             │                    │
│   │       ▼                             │                    │
│   │   ⑥ 验证                            │                    │
│   │      新评估通过了？ ───── 是 ──→ 接受  │                    │
│   │      旧评估退化了？ ───── 是 ──→ 拒绝  │                    │
│   │       │                             │                    │
│   │       └──── 下一轮 ─────────────────┘                    │
│   │                                                          │
│   └─────────────────────────────────────────────────────────┘│
│                                                              │
│   保留集分数持续监控 ──→ 防止过拟合                               │
└──────────────────────────────────────────────────────────────┘
```

### 逐步详解

#### 步骤 ① 收集 & 标记评估

混合使用手工编写、轨迹挖掘和外部数据集。**关键：移除已饱和的评估**——如果某条评估 Agent 已经能稳定通过，它不再提供有用的梯度信号，保留它只会浪费计算资源。

#### 步骤 ② 按类别拆分数据

```
全部评估
  │
  ├── 工具选择类 ──→ 优化集 70% │ 保留集 30%
  ├── 多步推理类 ──→ 优化集 70% │ 保留集 30%
  ├── 默认参数类 ──→ 优化集 70% │ 保留集 30%
  └── ...
```

> **为什么重要**  
> 这是整个方法论中最关键的一步。如果只在优化集上调参，很容易出现"考试作弊"——Agent 在你测试的场景上表现完美，在新场景上一塌糊涂。保留集是你的"反作弊机制"。

#### 步骤 ③ 跑基线

在**任何修改之前**，先在优化集和保留集上各跑一次，记录初始分数。没有基线，你无法判断后续的修改是真正的改进还是噪声。

#### 步骤 ④ 优化循环

每轮迭代可以自主运行，也可以加入人工审查 (Human-in-the-loop)。核心纪律：**一次只改一件事**。

#### 步骤 ⑤ 做一个定向修改

常见的线束修改类型：

| 修改类型 | 示例 | 典型问题 |
|---------|------|---------|
| **提示词 / 指令更新** | 在 System Prompt 中增加指导 | Agent 误读工具输出；Agent 过于频繁地调用工具 |
| **添加或更新工具** | 新增 API 工具、修改工具描述 | 工具之间功能模糊导致 Agent 选错；链式调用失败 |
| **逻辑调整** | 调整编排流程、增加防护规则 | Agent 在不该提问时反复追问用户 |

> **实战发现**  
> 在用 Claude Sonnet 4.6 和 Z.ai 的 GLM-5 测试时，一个关键发现是："当请求明确暗示了合理默认值时，直接使用默认值而不是反复追问用户。"这个规则作为 Prompt 指令加入后，显著减少了不必要的澄清问题。

#### 步骤 ⑥ 验证

双重检查：

- **正向验证：** 目标评估通过了吗？
- **回归检查：** 之前通过的评估还通过吗？

只有两个都满足，才接受这次修改。

## 四、为什么"一次只改一件事"如此重要

```
  ✗ 错误做法                       ✓ 正确做法
┌────────────────┐              ┌────────────────┐
│ 同时修改了      │              │ 迭代 1:         │
│ · Prompt       │              │   只改 Prompt   │
│ · 工具描述      │              │   → 验证         │
│ · 编排逻辑      │              │                 │
│                │              │ 迭代 2:          │
│ 评估分数提升了   │              │   只改工具描述   │
│ 但不知道是      │              │   → 验证         │
│ 哪个改动的功劳   │              │                 │
│                │              │ 迭代 3:          │
│ 下次出问题      │              │   只改编排逻辑   │
│ 也不知道        │              │   → 验证         │
│ 该回退哪一个     │              │                 │
└────────────────┘              │ 每步因果清晰     │
                                │ 可回退可归因     │
                                └────────────────┘
```

> **类比理解**  
> 就像医生治病：不会同时换三种药然后说"看看效果"。必须一次换一种，观察反应，才能知道哪种药在起作用。

## 五、评估的维护与"大扫除"

评估不是写完就一劳永逸的。随着模型版本迭代和线束优化，评估集也需要定期维护：

| 维护动作 | 判断标准 | 原因 |
|---------|---------|------|
| **移除饱和评估** | Agent 已稳定通过 N 次 | 不再提供有用信号，浪费计算 |
| **更新过时评估** | 评估反映的是旧模型的行为模式 | 新模型可能有不同的失败模式 |
| **补充新评估** | 生产中发现新的失败类型 | 覆盖之前未预料的场景 |

> **类比理解**  
> 评估集就像一本练习册。如果学生已经掌握了加法，继续做 100 道加法题没有意义——应该换成乘法题。"大扫除"就是定期审视哪些题目还有训练价值。

## 六、终局：从手动爬山到自动化飞轮

Better-Harness 的当前版本需要人工参与实验设计和审查。但未来的方向是**全自动化**：

```
┌────────────────────────────────────────────────────────┐
│                   自动化飞轮 (Flywheel)                   │
│                                                        │
│   ┌──────────┐                                         │
│   │ 用户使用  │                                         │
│   │ Agent    │                                         │
│   └────┬─────┘                                         │
│        │ 产生生产轨迹 (Traces)                           │
│        ▼                                               │
│   ┌──────────────┐                                     │
│   │ 自动错误检测  │ ←── 从轨迹中自动识别失败模式            │
│   └────┬─────────┘                                     │
│        │                                               │
│        ▼                                               │
│   ┌──────────────┐                                     │
│   │ 自动生成评估  │ ←── 失败轨迹 → 评估用例                │
│   │              │ ←── 用户纠正 → 更好的评估               │
│   └────┬─────────┘                                     │
│        │                                               │
│        ▼                                               │
│   ┌──────────────┐                                     │
│   │ 自动优化线束  │ ←── 爬山法自动迭代                     │
│   └────┬─────────┘                                     │
│        │                                               │
│        ▼                                               │
│   ┌──────────────┐                                     │
│   │ 更好的 Agent  │───→ 更多使用 → 更多轨迹 → ...         │
│   └──────────────┘                                     │
│                                                        │
│   飞轮效应: 使用量 ↑ → 轨迹 ↑ → 评估 ↑ → 线束质量 ↑       │
└────────────────────────────────────────────────────────┘
```

三个关键自动化目标：

1. **从生产轨迹自动推导错误** —— 不再依赖人工发现问题
2. **从生产数据自动生成评估** —— 失败轨迹直接转化为评估用例；用户纠正行为直接转化为更好的预期行为
3. **通过并排轨迹对比来评估线束版本** —— 两个线束版本处理同一请求，直接比较执行路径

## 七、Better-Harness 方法论总结

整套方法论可以用一句话概括：**像对待 ML 训练数据一样对待你的评估集，像对待超参数调优一样对待你的线束迭代。**

```
Better-Harness = 数据工程 + 实验设计 + 优化 + 审查验收

   数据工程        实验设计           优化           审查验收
┌───────────┐  ┌───────────┐  ┌───────────┐  ┌───────────┐
│ 收集评估    │  │ 拆分数据    │  │ 定向修改   │  │ 正向验证   │
│ 标记分类    │→│ 优化 vs 保留│→│ 一次一件事  │→│ 回归检查   │
│ 移除饱和    │  │ 跑基线     │  │ 自主迭代   │  │ 保留集监控  │
└───────────┘  └───────────┘  └───────────┘  └───────────┘
```

## 延伸思考

1. **评估的"标签体系"如何设计？** 行为类别的粒度应该多细？太粗（"工具使用"）会掩盖问题，太细（"在周三下午处理退款时的工具选择"）会导致数据稀疏。是否可以借鉴 ML 中的层次标签 (Hierarchical Labels) 来平衡？
2. **爬山法的局限性：** 爬山法只能找到局部最优。如果当前的线束架构本身就有根本性问题，逐步微调永远到不了全局最优。是否需要周期性地做"大重构"来跳出局部最优？这和 ML 中的学习率调度 (Learning Rate Scheduling) 有什么相似之处？
3. **评估与模型版本的耦合：** 当底层模型升级时（比如从 Sonnet 4.6 到下一代），现有评估集是否仍然有效？新模型可能有完全不同的失败模式，旧的评估可能全部饱和。如何高效地为新模型重建评估集？
4. **自动化飞轮的风险：** 如果评估完全由生产轨迹自动生成，是否会出现"回音室效应"——Agent 只学会处理已经遇到过的问题类型，对全新场景毫无准备？如何平衡自动化效率与人工创造力？
