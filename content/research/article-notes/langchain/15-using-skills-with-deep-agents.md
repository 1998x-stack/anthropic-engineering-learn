# 用技能 (Skills) 武装深度 Agent：从专用工具到文件系统优先

**作者:** Lance Martin  
**来源:** [LangChain Blog](https://www.langchain.com/blog/using-skills-with-deep-agents)  
**日期:** 2025 年 11 月 25 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> Anthropic 推出的技能 (Skills) 机制将 Agent 的能力从"硬编码工具列表"解放为"文件系统中的可发现指令"。技能 = 文件夹 + SKILL.md，Agent 按需发现、按需加载，实现了 Token 效率和认知负载的双重优化。

---

## 核心要点

1. **通才 Agent 正在取代专才 Agent** —— Claude Code 仅用约 12 个工具，Manus 用不到 20 个，关键不是给 Agent 更多工具，而是给它一台计算机
2. **技能是文件系统优先范式的自然产物** —— 一个文件夹 + 一个 SKILL.md（YAML 前言 + Markdown 指令），将动作从工具卸载到文件系统
3. **渐进式披露 (Progressive Disclosure) 解决 Token 膨胀** —— 默认只加载 YAML 前言摘要，按需读取完整指令，比传统工具定义全量上文的方式节省大量 Token
4. **技能支持运行时学习** —— Agent 可以在执行过程中创建新技能，实现跨会话、跨 Agent 的知识复用

---

## 一、通才 Agent 的崛起

### 从"给更多工具"到"给一台计算机"

传统 Agent 架构的思路是：需要什么能力，就注册什么工具。搜索网页？注册一个 `web_search` 工具。执行代码？注册一个 `code_interpreter` 工具。这种思路的终点是一个拥有数十甚至上百个工具的 Agent —— 每个工具都需要占用上下文窗口的 Token，每个工具的描述都增加模型的选择负担。

但现实中，最强大的编程 Agent 反其道而行：

| Agent | 工具数量 | 核心理念 |
|-------|---------|---------|
| **Claude Code** | ~12 个 | Bash + 文件系统 = 通用能力 |
| **Manus** | <20 个 | 将动作卸载到文件系统中的脚本和指令 |

> **类比理解**  
> 传统思路像给员工发一箱专用工具 —— 扳手、螺丝刀、锤子各一把，每种尺寸一把，最后工具箱比人还重。通才 Agent 的思路是给员工一台多功能工作台 + 一个操作手册文件夹。工作台（Bash + 文件系统）能做几乎所有事，手册（技能）告诉它怎么做。

### 关键洞察

这个转变的核心是一句话：**给 Agent 一台计算机。**

有了 Bash 和文件系统，Agent 就像一个拥有终端的人类开发者 —— 不需要为每个动作注册专用 API，而是通过组合通用原语（读文件、写文件、执行命令）来完成任意任务。

```
传统 Agent 架构                    通才 Agent 架构
┌──────────────────┐             ┌──────────────────┐
│      Agent       │             │      Agent       │
│                  │             │                  │
│  ┌──────┐        │             │  ┌──────┐        │
│  │ LLM  │        │             │  │ LLM  │        │
│  └──┬───┘        │             │  └──┬───┘        │
│     │            │             │     │            │
│  ┌──┴──────────┐ │             │  ┌──┴──────────┐ │
│  │ 30+ 专用工具 │ │             │  │ ~12 通用工具 │ │
│  │             │ │             │  │             │ │
│  │ web_search  │ │             │  │ bash        │ │
│  │ code_exec   │ │             │  │ read_file   │ │
│  │ send_email  │ │             │  │ write_file  │ │
│  │ create_pr   │ │             │  │ ...         │ │
│  │ run_test    │ │             │  └──────┬──────┘ │
│  │ lint_code   │ │             │         │        │
│  │ ...         │ │             │  ┌──────┴──────┐ │
│  └─────────────┘ │             │  │  文件系统     │ │
│                  │             │  │  + 技能文件夹  │ │
│  每个工具 = Token │             │  │  + 脚本      │ │
│  工具越多负担越重  │             │  └─────────────┘ │
└──────────────────┘             └──────────────────┘
```

> **为什么重要**  
> 工具数量是 Agent 架构的隐性成本。每增加一个工具定义，就多消耗上下文窗口中的 Token，模型在"选择用哪个工具"上的认知负载也随之增加。通才架构将这个 O(n) 的成本压缩到了近乎常数。

## 二、技能：通才 Agent 的能力扩展机制

### 从 Manus 到 Anthropic Skills

Manus 率先验证了一个模式：**将动作从工具定义卸载到文件系统。** 不是注册更多工具，而是在文件系统中放置脚本和指令文件，让 Agent 按需发现和执行。

Anthropic 的技能 (Skills) 将这一模式标准化：

```
~/.claude/agent/skills/
├── web-research/
│   ├── SKILL.md          ← YAML 前言 + Markdown 指令
│   ├── search_template.sh
│   └── summarize.py
├── code-review/
│   ├── SKILL.md
│   └── checklist.md
└── deploy/
    ├── SKILL.md
    └── deploy.sh
```

### SKILL.md 的结构

每个技能就是一个文件夹，核心是 `SKILL.md` 文件，采用 YAML 前言 (Frontmatter) + Markdown 正文的结构：

```yaml
---
name: web-research
description: 搜索网页并生成结构化摘要
trigger: 当用户要求搜索或调研某个主题时
tools_required: [bash, read_file, write_file]
---

# Web Research 技能

## 执行步骤
1. 使用 bash 调用搜索 API
2. 解析搜索结果
3. 生成结构化摘要并写入文件

## 输出格式
- Markdown 文件，包含来源链接
- 每个来源标注可信度评分
...
```

> **类比理解**  
> SKILL.md 就像一份"标准操作规程" (SOP)。YAML 前言是 SOP 的封面 —— 标题、适用场景、所需资源。Markdown 正文是 SOP 的详细步骤。员工（Agent）看到封面就知道该不该翻开看，翻开后按步骤执行。

## 三、技能相比传统工具的两大优势

### 优势一：Token 效率 —— 渐进式披露

传统工具架构要求在对话开始时就将所有工具定义放入上下文：

```
传统工具加载                        技能加载（渐进式披露）

┌─────────────────────┐           ┌─────────────────────┐
│   系统提示            │           │   系统提示            │
│                     │           │                     │
│   工具 1: 完整定义    │  ← 始终   │   技能 1: YAML 摘要   │  ← 始终
│   (200 tokens)      │    加载   │   (30 tokens)       │    加载
│                     │           │                     │
│   工具 2: 完整定义    │  ← 始终   │   技能 2: YAML 摘要   │  ← 始终
│   (180 tokens)      │    加载   │   (25 tokens)       │    加载
│                     │           │                     │
│   工具 3: 完整定义    │  ← 始终   │   技能 3: YAML 摘要   │  ← 始终
│   (220 tokens)      │    加载   │   (35 tokens)       │    加载
│                     │           │                     │
│   ...               │           │   ...               │
│   工具 N: 完整定义    │  ← 始终   │   技能 N: YAML 摘要   │  ← 始终
│   (xxx tokens)      │    加载   │   (xx tokens)       │    加载
│                     │           │                     │
│   总计: N × ~200     │           │   总计: N × ~30      │
│        tokens       │           │        tokens       │
└─────────────────────┘           └─────────────────────┘
                                           │
                                   按需读取完整 SKILL.md
                                           │
                                           ▼
                                  ┌─────────────────┐
                                  │  技能 2 完整指令   │
                                  │  (仅在需要时加载)  │
                                  │  (~200 tokens)   │
                                  └─────────────────┘
```

**Token 节省估算：** 假设 Agent 拥有 20 个技能，每个技能的完整定义约 200 tokens，YAML 摘要约 30 tokens。传统方式始终占用 4,000 tokens；技能方式默认只占用 600 tokens，仅在触发时才加载相关技能的完整内容。

### 优势二：认知负载 —— 更少的工具选择

传统架构下，Agent 面对 30+ 工具时需要在每一步选择"用哪个工具"。工具之间可能有功能重叠（例如 `run_python` 和 `execute_code`），模型需要理解它们的细微差别才能做出正确选择。

技能架构下，Agent 只需操作一小组原子工具（bash、read、write），技能文件中的指令告诉它如何组合这些原子操作来完成复杂任务：

| 维度 | 传统工具架构 | 技能架构 |
|------|------------|---------|
| **模型需要理解的工具数** | 30+ | ~12 |
| **每步选择复杂度** | 从 30+ 中选 1 | 从 ~12 中选 1 |
| **功能重叠风险** | 高（工具间边界模糊） | 低（原子工具职责明确） |
| **新能力的添加方式** | 注册新工具 + 修改提示 | 放一个文件夹进去 |
| **能力的可发现性** | 硬编码在代码中 | 文件系统中动态发现 |

> **为什么重要**  
> 认知负载不仅消耗 Token，还降低准确率。研究表明，当模型面对过多工具选择时，错误调用的概率显著上升。技能机制将"选择正确的能力"和"执行具体的步骤"解耦 —— 前者通过 YAML 摘要在轻量上下文中完成，后者通过加载完整指令在执行阶段完成。

## 四、超越 Token 节省：技能的深层价值

### 运行时学习 —— Agent 创造新技能

技能不仅是预定义的 —— Agent 可以在运行时创建新技能：

```
会话 1                             会话 2
┌─────────────────────┐          ┌─────────────────────┐
│ 用户: "帮我部署到     │          │ 用户: "部署新版本"    │
│       Fly.io"        │          │                     │
│                     │          │ Agent: 发现已有       │
│ Agent:              │          │   deploy-fly/ 技能    │
│  1. 研究 Fly.io 部署 │          │                     │
│  2. 成功完成部署      │          │ Agent: 读取 SKILL.md │
│  3. 将步骤保存为     │          │   按步骤执行          │
│     新技能 ──────────┼─────────→│   一次成功            │
│                     │          │                     │
│ 创建:               │          │ 复用，无需重新研究     │
│  skills/deploy-fly/ │          │                     │
│    SKILL.md         │          │                     │
└─────────────────────┘          └─────────────────────┘
```

### 跨 Agent 共享

技能是纯文件，天然支持共享：

- **团队内共享：** 将技能文件夹放入版本控制，团队成员的 Agent 自动获得相同能力
- **社区共享：** 公开发布技能文件夹，其他人 `cp -r` 即可使用
- **组合使用：** 多个技能可以在同一个会话中按需加载和组合

### 会话内组合

一次会话中，Agent 可以动态发现并组合多个技能。例如，面对"调研竞品并生成分析报告"的需求，Agent 可能先触发 `web-research` 技能进行搜索，再触发 `report-generation` 技能生成文档 —— 无需预先编排，由 Agent 自主决定。

## 五、实战：Deep Agents CLI + 技能

### 快速上手

deepagent-CLI 是一个开源的编程助手，拥有本地文件系统访问能力。它已原生支持技能机制，并提供了不断增长的公共技能集合。

**安装技能：**

```bash
# 创建技能目录
mkdir -p ~/.deepagents/agent/skills

# 复制技能文件夹
cp -r examples/skills/web-research ~/.deepagents/agent/skills/
```

**查看已安装技能：**

```bash
deepagents skills list
```

### 运行机制

```
┌──────────────────────────────────────────────────────────┐
│                 deepagent-CLI 启动流程                     │
│                                                          │
│  1. 扫描 ~/.deepagents/agent/skills/ 目录                 │
│     └─ 读取每个技能的 YAML 前言（名称、描述、触发条件）      │
│                                                          │
│  2. 将所有技能摘要注入系统提示                               │
│     └─ 仅加载 YAML 前言，不加载完整 SKILL.md               │
│                                                          │
│  3. 用户发送消息                                           │
│     └─ Agent 判断是否匹配某个技能的触发条件                  │
│                                                          │
│  4. 匹配成功 → 读取完整 SKILL.md                          │
│     └─ 按指令执行，使用原子工具（bash, read, write）        │
│                                                          │
│  5. 执行完毕 → SKILL.md 从活跃上下文中卸载                  │
│     └─ 释放 Token，保持上下文窗口清洁                      │
└──────────────────────────────────────────────────────────┘
```

> **类比理解**  
> 这个流程就像一个经验丰富的技工。他不会把所有操作手册同时打开放在工作台上（那会占满桌面），而是脑子里记着"我有哪些手册"（YAML 摘要），遇到具体问题时才翻开对应手册（完整 SKILL.md），做完后合上放回架子（卸载）。

## 六、技能 vs 工具 vs MCP：三种能力扩展范式对比

| 维度 | 传统工具 (Tools) | MCP 服务 | 技能 (Skills) |
|------|-----------------|---------|--------------|
| **定义位置** | 代码中硬编码 | 远程服务器 | 本地文件系统 |
| **加载方式** | 全量预加载 | 全量预加载 | 渐进式披露 |
| **Token 成本** | 高（始终占用） | 高（始终占用） | 低（按需加载） |
| **新增能力** | 改代码 + 重部署 | 部署新服务 | 放一个文件夹 |
| **运行时创建** | 不支持 | 不支持 | 支持 |
| **共享方式** | 代码库 | API 注册 | 文件复制 |
| **执行方式** | 专用 API 调用 | RPC 调用 | 组合原子工具 |

> **为什么重要**  
> 工具、MCP 和技能不是互斥的，而是互补的。技能最适合封装**流程性知识**（"如何一步步完成某类任务"），而工具和 MCP 更适合封装**原子能力**（"调用某个 API"）。最强大的 Agent 架构是三者的组合：少量原子工具 + MCP 服务提供外部集成 + 技能提供流程编排。

## 延伸思考

1. **技能的质量控制问题：** 当社区产生大量公共技能时，Agent 如何判断一个技能是否可信、是否过时、是否与其他技能冲突？是否需要"技能注册表"或"技能评分"机制？
2. **技能发现的上限：** 渐进式披露在技能数量较少时效果显著，但当 Agent 拥有数百个技能时，仅 YAML 摘要的 Token 消耗也会变得可观。是否需要分层索引 —— 先分类、再匹配、最后加载？
3. **技能与模型训练的耦合：** 如果模型在预训练阶段就接触过大量技能格式的数据，它在运行时发现和执行技能的能力会显著提升。这是否意味着技能格式本身也会影响模型的训练数据策略？
4. **安全边界：** 技能本质上是让 Agent 从文件系统中动态加载指令并执行。这与传统的"代码注入"风险有何异同？在多租户场景下，如何防止恶意技能被加载和执行？
