# 评估深度 Agent：五条实战经验 (Evaluating Deep Agents: Our Learnings)

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/evaluating-deep-agents-our-learnings)  
**日期:** 2025 年 12 月 3 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 深度 Agent (Deep Agent) 的评估不能套用传统 LLM 的"数据集 → 评估器 → 分数"流水线。五条核心经验：每个测试用例需要定制断言逻辑、单步评估高效且必要、完整轮次提供全局视角、多轮对话需要条件化模拟、环境隔离是评估可靠性的基石。

---

## 核心要点

1. **每个测试用例需要定制断言逻辑** —— 深度 Agent 的行为高度上下文相关，通用评估器无法覆盖其复杂性，必须为每个数据点编写专属的验证逻辑
2. **单步评估是最高效的回归检测手段** —— 约 50% 的测试用例只需检查 LLM 在收到输入后的第一个决策，定位问题又快又准
3. **完整轮次评估 = 集成测试** —— 从轨迹 (Trajectory)、最终响应 (Final Response)、外部状态 (Other State) 三个维度评估，才能得到完整画面
4. **多轮模拟需要条件化执行** —— 每一轮的输出决定下一轮的输入，必须引入条件分支和早停机制，避免级联失败
5. **评估环境必须隔离** —— 深度 Agent 是有状态的 (Stateful)，每次评估必须在全新的隔离环境中运行，否则结果不可信

---

## 一、传统评估为什么在深度 Agent 面前失效？

### 从流水线到手术刀

> **类比理解**  
> 传统 LLM 评估像工厂质检——所有产品走同一条检测线，用同一组标准打分。深度 Agent 的评估更像手术后的临床评估——每个病人的术后指标不同，检查重点不同，"成功"的定义也不同。你不能用一张通用的体检表来评估心脏手术和膝盖置换手术的效果。

传统 LLM 评估的三板斧：

```
传统 LLM 评估流水线
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  数据集 (Dataset)
     │
     ▼
  评估器 (Evaluator)  ←── 通用的，所有数据点共用
     │
     ▼
  分数 (Score)        ←── 准确率 / BLEU / F1
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

这种流水线对深度 Agent 失效的根本原因：**深度 Agent 的"正确行为"高度依赖上下文，无法用统一的评估函数覆盖。**

| 维度 | 传统 LLM 评估 | 深度 Agent 评估 |
|------|-------------|---------------|
| 评估逻辑 | 通用评估器，所有数据点共用 | 每个数据点有专属断言逻辑 |
| 检查粒度 | 最终输出 | 单步决策 + 完整轨迹 + 外部状态 |
| 交互模式 | 单轮 | 多轮条件化对话 |
| 环境要求 | 无状态 | 每次评估需要隔离环境 |
| 评估维度 | 输出质量 | 工具选择 + 参数正确性 + 执行路径 + 产出物 |

> **为什么重要**  
> 如果你用传统的"跑一遍数据集、看个总分"的方式来评估深度 Agent，你会得到一个看起来"还行"的分数，但完全无法定位具体哪些能力退化了、哪些场景下 Agent 会做出错误决策。评估的价值不在分数本身，而在于它能多精准地告诉你"哪里出了问题"。

## 二、经验 #1：每个测试用例需要定制断言逻辑 (Bespoke Test Logic)

### 问题

传统评估的一个隐含假设是：**所有数据点可以用同一个评估函数判断对错。** 比如分类任务，判断标准就是"预测标签是否等于真实标签"，对所有样本一视同仁。

深度 Agent 完全打破了这个假设。考虑一个编程 Agent 的评估：

```
测试用例 A: "修复这个 bug"
  ✅ 正确断言: 修改了正确的文件 && 测试通过 && 没有引入新的 lint 错误

测试用例 B: "重构这个模块"
  ✅ 正确断言: 函数签名未变 && 所有测试通过 && 代码行数减少 > 20%

测试用例 C: "添加日志功能"
  ✅ 正确断言: 新增了日志调用 && 日志格式符合规范 && 没有修改业务逻辑
```

这三个测试用例的"正确"定义完全不同，无法用同一个评估函数覆盖。

### 解决方案

为每个测试用例编写专属的断言逻辑 (Assertion Logic)：

```
深度 Agent 评估模式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  测试用例 1 ──→ 断言逻辑 A ──→ ✅ / ❌
  测试用例 2 ──→ 断言逻辑 B ──→ ✅ / ❌
  测试用例 3 ──→ 断言逻辑 C ──→ ✅ / ❌
  ...
  测试用例 N ──→ 断言逻辑 N ──→ ✅ / ❌
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  每个测试用例有自己的"什么算对"定义
```

> **类比理解**  
> 这就像高考和面试的区别。高考所有考生做同一张卷子、按同一个标准打分。面试则是每个岗位有不同的考察标准——招工程师看代码能力，招设计师看作品集，招产品经理看业务分析。深度 Agent 的评估更接近面试：每个"岗位"(测试用例) 需要量身定制的考察标准。

### 实践建议

| 做法 | 说明 |
|------|------|
| **断言与数据绑定** | 每条测试数据附带自己的断言函数，而非全局共享一个评估器 |
| **断言可组合** | 构建断言原子操作库 (如 `file_modified()`、`tests_pass()`、`no_lint_errors()`)，通过组合生成测试用例的断言 |
| **断言要具体** | "输出合理"不是好的断言；"调用了 `search_api` 且参数包含用户指定的关键词"才是 |

## 三、经验 #2：单步评估高效且必要 (Single Step Evals)

### 核心发现

LangChain 团队在实践中发现，**约 50% 的测试用例只需要检查 Agent 在收到输入后的第一个决策**。

```
单步评估的典型检查项
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  输入 → Agent → 第一个决策
                    │
                    ├── 调用了正确的工具？
                    ├── 传递了正确的参数？
                    ├── 查看了正确的目录？
                    ├── 选择了正确的 API？
                    └── 生成了合理的初始计划？
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

回归问题 (Regression) 往往出现在**单个决策点**上——不是 Agent 的整体策略变了，而是某个具体的工具选择或参数拼装出了差错。

### 实现方式：LangGraph interrupt_before

LangGraph 提供了 `interrupt_before` 机制，可以在指定节点执行前中断 Agent，让你检查此刻的状态：

```python
# 在工具调用之前中断，只看 Agent 的第一个决策
state = await agent.ainvoke(inputs, interrupt_before=["tools"])

# 检查 Agent 决定调用什么工具、传什么参数
print(state["messages"])
```

这段代码的关键在于 `interrupt_before=["tools"]`——它让 Agent 完成推理但在实际执行工具之前暂停，你可以检查 Agent 的决策而不必等待工具执行完成。

### 单步评估 vs. 完整评估

> **类比理解**  
> 单步评估就像驾考中的"路口判断题"——你只需要看考生在遇到红灯时是否踩了刹车，不需要看他开完整条路线。大量的驾驶安全问题都可以在这些单一决策点上发现。

| 特性 | 单步评估 | 完整轮次评估 |
|------|---------|------------|
| 速度 | 快 (毫秒级) | 慢 (秒到分钟级) |
| 成本 | 低 (1 次 LLM 调用) | 高 (多次 LLM + 工具调用) |
| 适用场景 | 工具选择、参数校验、初始规划 | 端到端任务完成度 |
| 回归检测 | 精准定位到具体决策点 | 知道"整体变差了"但不知道哪步出了问题 |
| 覆盖范围 | 约 50% 的测试用例 | 100% |

> **为什么重要**  
> 单步评估的最大优势是**性价比**。你用最少的计算资源覆盖了一半的测试用例，而且定位问题的精度远超完整轮次评估。当你的评估预算有限时，优先建设单步评估是最理智的选择。

## 四、经验 #3：完整轮次提供全局视角 (Full Agent Turns)

### 与单步评估的关系

如果说单步评估是"单元测试 (Unit Test)"，那么完整轮次评估就是"集成测试 (Integration Test)"。两者不是替代关系，而是互补关系。

```
评估金字塔
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

          ┌───────────┐
          │  多轮模拟   │  ← 最全面，成本最高
          │           │
        ┌─┴───────────┴─┐
        │  完整轮次评估    │  ← 集成测试
        │               │
      ┌─┴───────────────┴─┐
      │    单步评估         │  ← 单元测试，最快最便宜
      └───────────────────┘

  从底向上构建: 先覆盖单步，再补充完整轮次，最后加多轮模拟
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 完整轮次的三个评估维度

完整轮次评估不是简单地"看最终输出对不对"。它需要从三个维度来检查：

| 维度 | 检查内容 | 典型场景 | 评估方式 |
|------|---------|---------|---------|
| **轨迹 (Trajectory)** | Agent 在某个时刻是否调用了特定工具 | "Agent 是否在某个步骤使用了搜索工具？" | 检查工具调用序列 (顺序不重要，关键是"是否出现") |
| **最终响应 (Final Response)** | 输出的质量和正确性 | 编程任务：代码能跑；研究任务：结论正确 | LLM-as-Judge 或人工检查 |
| **外部状态 (Other State)** | Agent 在环境中产生的副作用 | 写入了哪些文件？查询了哪些数据源？创建了什么 artifact？ | 检查文件系统、数据库、API 调用记录 |

#### 维度一：轨迹评估

轨迹评估的核心问题是：**Agent 有没有在正确的时机调用正确的工具？**

注意：这里的"正确"不要求严格的调用顺序。对于大多数深度 Agent 任务，你关心的是"这个工具有没有被调用过"，而不是"它是在第三步还是第五步被调用的"。

```
轨迹评估示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Agent 实际执行序列:
    ① read_file("config.yaml")
    ② search_codebase("database connection")
    ③ read_file("db.py")
    ④ edit_file("db.py", ...)
    ⑤ run_tests()

  轨迹断言 (顺序无关):
    ✅ search_codebase 被调用了？  → 是
    ✅ run_tests 被调用了？        → 是
    ✅ edit_file 被调用了？        → 是
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

#### 维度二：最终响应评估

对于某些任务，**路径不重要，结果才重要**。比如编程任务——不管 Agent 是先读代码再写测试，还是先写测试再读代码，只要最终提交的代码通过了所有测试就算成功。研究任务也是如此——Agent 用了哪些搜索词不重要，最终的研究报告质量才是关键。

#### 维度三：外部状态评估

深度 Agent 经常产生**超出对话上下文的副作用**——它会写文件、创建目录、调用外部 API。这些副作用也需要被检查：

- 写入了正确的文件？
- 引用了正确的数据源？
- 创建的 artifact 格式正确？

> **为什么重要**  
> 只看最终响应的评估会遗漏大量信息。一个 Agent 可能给出了正确的答案，但用了完全错误的方法——这在当前测试用例上侥幸通过，却会在类似的新场景中失败。三维度评估是唯一能捕获这类"侥幸通过"问题的方法。

## 五、经验 #4：多轮模拟需要条件化执行 (Multiple Turns)

### 问题

真实的用户交互不是"发一条消息、等一个回复"——用户会连续提问、修改需求、提供反馈。评估深度 Agent 必须模拟这种多轮对话。

但多轮评估面临一个棘手问题：**级联失败 (Cascade Failure)**。

```
级联失败示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  轮次 1: 用户 "帮我查一下这个 bug 的原因"
     │
     ▼
  Agent 回复: (回答错误 ❌)
     │
     ▼
  轮次 2: 用户 "好的，那帮我修复它"
     │
     ▼
  Agent 回复: (基于错误的诊断修复，必然失败 ❌❌)
     │
     ▼
  轮次 3: 用户 "修复后请跑一下测试"
     │
     ▼
  Agent 回复: (测试当然不通过 ❌❌❌)

  问题: 轮次 2 和 3 的失败不是独立的——它们是轮次 1 错误的必然后果
  如果不加区分，你会以为 Agent 有 3 个 bug，实际上只有 1 个
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

```

### 解决方案：条件化执行 + 隔离测试

两个关键策略：

**策略一：条件化执行 (Conditional Execution)**

每一轮结束后检查输出，决定是否继续：

```
多轮评估的条件化执行
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  轮次 1: 发送输入，运行 Agent
     │
     ├── 输出符合预期？ ──── 否 ──→ 记录失败，终止 (早停)
     │
     └── 是 ──→ 继续
                 │
  轮次 2: 发送下一条输入，运行 Agent
     │
     ├── 输出符合预期？ ──── 否 ──→ 记录失败，终止
     │
     └── 是 ──→ 继续
                 │
  轮次 3: ...
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  关键: 任何一轮失败就立即停止，不让错误级联到后续轮次
```

**策略二：隔离测试后续轮次**

如果你想单独测试轮次 2 或轮次 3 的行为，可以**构造一个正确的初始状态**，从那个状态开始运行：

```
隔离测试轮次 2
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  手动构造轮次 1 的正确输出 (Golden State)
     │
     ▼
  从 Golden State 开始，运行轮次 2
     │
     ▼
  检查轮次 2 的输出

  优势: 轮次 2 的评估不受轮次 1 实际表现的影响
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 这就像赛车比赛中的"分段计时"。你不仅记录全程成绩，还记录每个赛段的成绩。如果赛车在第一个弯道失误，你不会因此否定它在直道上的速度——你会单独分析每个赛段，找到真正的短板。

> **为什么重要**  
> 没有条件化执行的多轮评估会产生大量误报——一个根因 (Root Cause) 导致的级联失败被当成多个独立的 bug 来追踪。这不仅浪费调试时间，还会让团队对评估结果的严重性产生错误判断。

## 六、经验 #5：正确的评估环境至关重要 (Right Eval Environment)

### 核心问题：状态污染

深度 Agent 是有状态的 (Stateful)——它们会读写文件、修改数据库、调用外部服务。如果两次评估共享同一个环境，前一次评估的副作用会污染后一次评估的结果。

```
状态污染示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  评估 1: "在 /tmp/project 中创建一个 utils.py 文件"
     │
     └── Agent 创建了 /tmp/project/utils.py ✅

```

### 解决方案：环境隔离

每次评估运行前，确保 Agent 处于一个全新的、干净的环境中：

| Agent 类型 | 隔离方案 | 说明 |
|-----------|---------|------|
| **编程 Agent** | Docker 容器 / 沙箱 (Sandbox) | 每次评估启动一个新容器，评估完即销毁 |
| **编程 Agent (轻量)** | 临时目录 (Temp Directory) | 每次评估创建新的临时目录，评估后清理 |
| **研究 Agent** | Mock API 请求 | 避免外部 API 的状态变化影响评估结果 |
| **通用 Agent** | 快照/恢复 (Snapshot/Restore) | 评估前拍快照，评估后恢复 |

### 实践技巧：Mock 外部请求

> **类比理解**  
> 评估环境隔离就像实验室做实验时的"控制变量法"。每次实验都要回到相同的初始条件——相同的温度、相同的试剂浓度、相同的设备状态。如果你在前一个实验用过的烧杯里直接做下一个实验，残留物会让结果不可信。

除了文件系统隔离，还要特别注意**外部 API 请求的隔离**。深度 Agent 经常调用搜索引擎、数据库、第三方服务——这些外部依赖的返回值可能随时间变化，导致评估结果不可重复。

推荐做法：**Mock 外部请求**。录制一次真实的 API 响应，在后续评估中回放。这既保证了结果的确定性，又避免了重复调用外部 API 带来的成本和速率限制问题。

> **为什么重要**  
> 评估结果的可重复性 (Reproducibility) 是评估系统的基本要求。如果同一个 Agent、同一个测试用例在不同时间点跑出不同的结果，你无法判断一次线束修改到底是改进还是退化。环境隔离是可重复性的前提条件。

## 七、五条经验的协作关系

这五条经验不是孤立的最佳实践，而是一个**层层递进的评估体系**：

```

  基础设施层                       评估执行层
  ─────────                       ─────────

       │
       │  之上构建
       ▼
  #1 定制断言  ──────────────────→  每个用例有专属的"正确"定义

       ▼
  ┌────┴────────────────────────┐
  │                             │
  ▼             ▼               ▼
  #2 单步评估   #3 完整轮次      #4 多轮模拟

  快/便宜       中等             慢/贵

  构建顺序: #5 → #1 → #2 → #3 → #4 (从基础设施到完整覆盖)
```

### 构建评估体系的推荐顺序

| 优先级 | 经验 | 投入产出比 | 为什么这个顺序 |
|--------|------|-----------|-------------|
| P0 | #5 环境隔离 | 一次搭建，长期受益 | 没有可靠的环境，其他评估都不可信 |
| P1 | #1 定制断言 | 中等投入，精准反馈 | 定义清楚"什么算对"，才能有效评估 |
| P2 | #2 单步评估 | 低投入，高覆盖 | 50% 的用例用最低成本覆盖 |
| P3 | #3 完整轮次 | 中等投入，全局视角 | 补充单步无法覆盖的集成问题 |
| P4 | #4 多轮模拟 | 高投入，最全面 | 模拟真实用户行为，发现交互级别的问题 |

## 延伸思考

1. **定制断言的维护成本：** 每个测试用例都有专属的断言逻辑，意味着评估集的维护成本与数据量线性增长。当评估集达到数百甚至数千条时，如何降低维护负担？是否可以用 LLM 自动生成或更新断言逻辑？这本身又引入了"用 AI 评估 AI"的可靠性问题。

2. **单步评估的盲区：** 约 50% 的问题可以在单步被发现，但另外 50% 呢？是否存在某些类型的 bug 只有在完整轮次甚至多轮模拟中才会暴露？如何系统性地识别这些单步评估的盲区，避免产生"我们的评估覆盖率很高"的错觉？

3. **环境隔离的性能代价：** 每次评估启动一个新的 Docker 容器或沙箱会带来显著的启动开销。当评估集很大时，这个开销可能成为瓶颈。是否可以借鉴数据库的 MVCC (多版本并发控制) 思路，在逻辑层面实现隔离而不需要物理层面的完全重建？

4. **多轮评估中的"用户模拟"质量：** 多轮评估需要模拟用户的行为——但模拟的用户和真实用户之间的差距有多大？如果模拟用户的行为过于理想化 (总是按预期回复)，你的评估可能高估了 Agent 在真实场景中的表现。如何构建更真实的用户模拟器？
