# Agent 如何用文件系统做上下文工程：一个接口解决无限上下文

**作者:** Nick Huang / LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-agents-can-use-filesystems-for-context-engineering)  
**日期:** 2025 年 11 月 21 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> 文件系统 (Filesystem) 是 Agent 上下文工程的统一接口 —— 通过 `ls`、`grep`、`read_file`、`write_file` 等原语，Agent 可以灵活地存储、检索和更新无限量的上下文信息，解决四种典型的上下文失败模式。

---

## 核心要点

1. **上下文工程的目标是让"检索到的上下文"无限逼近"需要的上下文"** —— 多了浪费 Token、干扰推理；少了缺乏关键信息；错了比没有更糟
2. **文件系统是天然的 Agent 上下文接口** —— 模型在预训练中大量接触文件系统操作，信息天然以目录结构组织，可以精确到行级粒度访问
3. **四种上下文失败模式各有对应的文件系统解法** —— Token 过载用"写出 + 按需读回"、海量信息用"子 Agent 写文件 + 主 Agent 读摘要"、精准检索用"grep + 行级读取"、持续学习用"Agent 自写指令文件"
4. **文件系统天然支持多 Agent 协作** —— 多个 Agent 共享同一个文件系统工作区，通过文件读写实现异步通信和知识共享

---

## 一、上下文工程的三圈模型

上下文工程 (Context Engineering) 的核心挑战可以用一个三圈韦恩图 (Venn Diagram) 来理解：

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│           全量上下文 (Total Context)                       │
│       Agent 有权访问的所有信息                              │
│                                                          │
│        ┌──────────────────────────────┐                  │
│        │                              │                  │
│        │   必要上下文                   │                  │
│        │   (Needed Context)           │                  │
│        │   当前任务真正需要的信息         │                  │
│        │                              │                  │
│        │      ┌──────────────┐        │                  │
│        │      │              │        │                  │
│        │      │  检索到的上下文 │        │                  │
│        │      │  (Retrieved  │        │                  │
│        │      │   Context)   │        │                  │
│        │      │              │        │                  │
│        │      │  ← 目标：让   │        │                  │
│        │      │   这个圈 ≈    │        │                  │
│        │      │   中间那个圈  │        │                  │
│        │      └──────────────┘        │                  │
│        └──────────────────────────────┘                  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**目标：** 让"检索到的上下文"尽可能等于"必要上下文" —— 不多、不少、不错。

> **类比理解**  
> 你是一位律师准备出庭辩护。你的事务所档案室里有几千份案卷（全量上下文），这场官司真正需要的证据和法条大约有 30 份（必要上下文），你实际塞进公文包带进法庭的文件就是"检索到的上下文"。带多了 —— 翻找浪费时间；带少了 —— 关键证据缺失；带错了 —— 引用了不相关的判例，更糟糕。

> **为什么重要**  
> 这三个圈之间的错位，就是 Agent 在实际运行中犯错、卡住、甚至失控的根本原因。下文的四种失败模式，本质上就是这三个圈之间的四种错位方式。

## 二、四种上下文失败模式与文件系统解法

### 失败模式 1：Token 过载 —— 检索到的远超必要的

| 维度 | 说明 |
|------|------|
| **错位关系** | 检索到的 >> 必要的 |
| **典型场景** | Web 搜索返回 10,000 tokens 的结果，全部堆积在对话历史中 |
| **后果** | 无关信息淹没关键信息，干扰模型推理；Token 预算被浪费 |

**传统做法的问题：**

Agent 执行 Web 搜索后，搜索结果直接插入上下文窗口。执行多次搜索后，历史中堆满了大段大段的搜索结果，模型需要从中"大海捞针"。

**文件系统解法：Agent 把搜索结果写入文件，按需检索**

```
┌─────────────────┐      ┌──────────────────────────┐
│  Agent 执行      │      │    文件系统（草稿板）       │
│  web_search()   │      │                          │
│                 │      │  /scratch/               │
│  返回 10,000    │─写入──→│    search_result_1.txt   │
│  tokens         │      │    search_result_2.txt   │
│                 │      │    search_result_3.txt   │
└────────┬────────┘      └──────────┬───────────────┘
         │                         │
         ▼                         │
┌─────────────────┐                │
│  上下文窗口中     │                │
│  只保留一行：     │                │
│                 │    按需 grep ──→│
│  "搜索结果已保   │    或 read_file │
│   存至 /scratch/ │                │
│   search_*.txt" │                │
└─────────────────┘                │
                                   ▼
                          ┌───────────────────┐
                          │  只读回需要的几行    │
                          │  而不是全部 10,000  │
                          │  tokens            │
                          └───────────────────┘
```

> **类比理解**  
> 不要把图书馆的整面书架搬进你的书房（上下文窗口），而是在图书馆做好索引卡片，需要时去取具体的那本书、翻到具体的那一页。文件系统就是那个图书馆。

---

### 失败模式 2：海量信息需求 —— 必要的超出上下文窗口

| 维度 | 说明 |
|------|------|
| **错位关系** | 必要的 > 上下文窗口容量 |
| **典型场景** | 大型代码重构、跨文件分析、需要读取整个代码库的任务 |
| **后果** | 即使不浪费任何 Token，窗口也装不下所有需要的信息 |

**文件系统解法：分层写入 + 子 Agent 并行处理**

```
┌──────────────────────────────────────────────────────┐
│                   主 Agent                            │
│                                                      │
│  1. 将计划 (Plan) 写入 /workspace/plan.md             │
│  2. 派遣子 Agent 并行执行子任务                         │
│  3. 读取子 Agent 写入的结果文件                         │
└───────────────────┬──────────────────────────────────┘
                    │ 派遣
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   ┌─────────┐ ┌─────────┐ ┌─────────┐
   │ 子Agent1 │ │ 子Agent2 │ │ 子Agent3 │
   │ 分析模块A │ │ 分析模块B │ │ 分析模块C │
   └────┬────┘ └────┬────┘ └────┬────┘
        │           │           │
        ▼           ▼           ▼
┌──────────────────────────────────────────────────────┐
│                   文件系统                             │
│                                                      │
│   /workspace/                                        │
│   ├── plan.md              ← 全局计划                 │
│   ├── findings/                                      │
│   │   ├── module_a.md      ← 子 Agent 1 的发现        │
│   │   ├── module_b.md      ← 子 Agent 2 的发现        │
│   │   └── module_c.md      ← 子 Agent 3 的发现        │
│   └── skills/                                        │
│       └── analysis.md      ← 可复用的技能指令           │
└──────────────────────────────────────────────────────┘
```

三种关键的文件写入模式：

| 写入模式 | 文件类型 | 作用 |
|---------|---------|------|
| **计划写入** | `plan.md` | 主 Agent 将总体计划持久化，子 Agent 可随时参考 |
| **发现写入** | `findings/*.md` | 子 Agent 将分析结果写入文件，主 Agent 按需读取 |
| **技能写入** | `skills/*.md` | 将可复用的指令存为技能文件，按需动态加载 |

> **为什么重要**  
> 当必要信息超出上下文窗口时，唯一的出路是将信息**外部化**。文件系统充当了上下文窗口的延伸 —— 一个理论上无限大的"外部工作记忆"。子 Agent 的每一份发现都持久化在文件中，主 Agent 只需读取摘要就能保持全局视野。

### 失败模式 3：精准检索失败 —— 检索到的不等于需要的

| 维度 | 说明 |
|------|------|
| **错位关系** | 检索到的 ≠ 必要的（质量问题，不是数量问题） |
| **典型场景** | 在技术文档中搜索特定 API 参数、配置选项、错误代码 |
| **后果** | 语义搜索返回"相关但不是你要的"结果，Agent 基于错误信息行动 |

**为什么语义搜索 (Semantic Search) 会失败？**

语义搜索基于向量相似度，擅长找到"语义相近"的内容，但对技术文档中的精确查询力不从心：

```
查询: "CUDA_VISIBLE_DEVICES 环境变量的默认值"

语义搜索返回:                          实际需要的:
┌──────────────────────┐             ┌──────────────────────┐
│ "GPU 配置与环境变量    │             │ 第 847 行:            │
│  概述..." (相关但泛泛) │             │ CUDA_VISIBLE_DEVICES  │
│                      │             │ 默认值为空字符串，      │
│ "NVIDIA 驱动安装指南   │             │ 表示使用所有可用 GPU   │
│  ..." (沾边但不对)    │             └──────────────────────┘
│                      │
│ "PyTorch GPU 加速     │
│  ..." (主题相关但      │
│       答非所问)       │
└──────────────────────┘
```

**文件系统搜索的四个优势：**

| 优势 | 文件系统操作 | 效果 |
|------|------------|------|
| **模型天然擅长** | `ls`, `cd`, `find` | 模型在预训练中大量接触文件系统遍历，执行可靠 |
| **信息天然有结构** | 目录 → 子目录 → 文件 | 信息已经按层级组织，不需要额外索引 |
| **精确到行** | `grep -n "CUDA"` | 直接定位到包含关键字的具体行号 |
| **范围可控** | `read_file(line=845, end=850)` | 只读取需要的几行，不浪费 Token |

**文件系统检索的典型流程：**

```
步骤 1: ls docs/
        → 发现 gpu_config.md, network.md, storage.md ...

步骤 2: grep -rn "CUDA_VISIBLE_DEVICES" docs/
        → docs/gpu_config.md:847: CUDA_VISIBLE_DEVICES ...

步骤 3: read_file("docs/gpu_config.md", line=840, end=855)
        → 精确读取目标行及上下文，共 15 行
```

> **类比理解**  
> 语义搜索像是问一个读过整本百科全书的人"CUDA_VISIBLE_DEVICES 默认值是什么"——他会给你讲一堆 GPU 的背景知识，但可能说不准那个具体的值。文件系统搜索像是直接翻开书的索引页，找到"CUDA_VISIBLE_DEVICES"对应的页码，翻过去看那一行。

> **为什么重要**  
> 文件系统搜索和语义搜索不是替代关系，而是互补关系。语义搜索擅长"我不确定该找什么"的探索性查询，文件系统搜索擅长"我知道要什么，帮我精确定位"的确定性查询。实践中，两者组合使用效果最佳。

### 失败模式 4：持续学习缺失 —— 全量上下文缺少必要信息

| 维度 | 说明 |
|------|------|
| **错位关系** | 全量上下文 ≠ 必要的（Agent 根本没有这些信息） |
| **典型场景** | 项目特有的约定、用户偏好、团队编码规范、之前踩过的坑 |
| **后果** | Agent 反复犯同样的错误，每次都需要用户重新纠正 |

**传统做法的问题：**

用户发现 Agent 的行为不符合预期 → 给 Agent 一些纠正提示 → Agent 当次改正 → 下次会话又忘了 → 用户再次纠正 → 循环往复。

**文件系统解法：Agent 自我编写指令文件**

```
会话 1                              会话 2
┌───────────────────────┐          ┌───────────────────────┐
│ 用户: "我们项目用       │          │ 用户: "重构这个模块"    │
│ tab 缩进，不用 space"  │          │                       │
│                       │          │ Agent:                │
│ Agent:                │          │  1. 读取 .agent/       │
│  1. 理解了！           │          │     instructions.md   │
│  2. 将这条规则写入 ────┼─────────→│  2. 发现缩进规则       │
│     .agent/           │          │  3. 自动使用 tab 缩进  │
│     instructions.md   │          │                       │
│                       │          │ 用户无需重复说明        │
└───────────────────────┘          └───────────────────────┘
```

**自我学习的工作流：**

```
   用户纠正 Agent 行为
          │
          ▼
   Agent 理解纠正意图
          │
          ▼
   Agent 将规则写入指令文件
   (.agent/instructions.md
    或 CLAUDE.md 等)
          │
          ▼
   下次会话启动时自动加载
          │
          ▼
   Agent 行为自动符合规则
          │
          ▼
   用户不再需要重复纠正
```

> **类比理解**  
> 传统做法是每天早上给新来的实习生口头交代一遍公司的编码规范。文件系统做法是把规范写成文档，实习生（Agent）来了自己先读一遍，还能在发现新规则时主动往文档里添加。

> **为什么重要**  
> 这是 Agent 自我改进 (Self-Improving) 的新兴模式。Agent 不再是一个被动执行指令的工具，而是一个能够积累经验、主动更新自身行为规则的实体。这个模式自动化了"更新提示词 (Prompt)"的人工步骤 —— 用户不需要手动编辑系统提示，Agent 自己完成这一步。

## 三、为什么文件系统是 Agent 上下文的理想接口

将四种失败模式的解法汇总，可以看出文件系统之所以成为统一解法，有四个根本原因：

| 原因 | 解释 | 对 Agent 的意义 |
|------|------|----------------|
| **模型天然擅长** | LLM 在预训练阶段接触了大量文件系统操作的代码和文档 | `ls`、`grep`、`cat` 等操作几乎零学习成本，可靠性高 |
| **信息天然有结构** | 文件系统本身就是树形结构，目录 = 分类，文件 = 内容 | 无需额外构建索引或数据库，信息自然组织 |
| **粒度可精细控制** | 可以精确到行、甚至字符级别访问 | 不需要读取整个文档，只取需要的片段 |
| **多 Agent 共享** | 多个 Agent 可以读写同一个文件系统 | 天然的异步通信通道，无需额外的消息传递机制 |

```
┌────────────────────────────────────────────────────────────┐
│              文件系统：统一的上下文工程接口                     │
│                                                            │
│   失败模式 1              失败模式 2                         │
│   Token 过载              海量信息                           │
│   ┌──────────┐           ┌──────────┐                      │
│   │ write +  │           │ 子Agent  │                      │
│   │ grep/read│           │ 写文件   │                      │
│   └────┬─────┘           └────┬─────┘                      │
│        │                      │                            │
│        └──────┐    ┌──────────┘                            │
│               ▼    ▼                                       │
│          ┌──────────────┐                                  │
│          │              │                                  │
│          │   文件系统     │                                  │
│          │   ls / grep  │                                  │
│          │   read/write │                                  │
│          │              │                                  │
│          └──────────────┘                                  │
│               ▲    ▲                                       │
│        ┌──────┘    └──────────┐                            │
│        │                      │                            │
│   ┌────┴─────┐           ┌────┴─────┐                      │
│   │ grep +   │           │ Agent    │                      │
│   │ 行级读取  │           │ 自写指令  │                      │
│   └──────────┘           └──────────┘                      │
│   失败模式 3              失败模式 4                         │
│   精准检索                持续学习                           │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

## 四、文件系统 vs 其他上下文管理方案

| 维度 | 文件系统 | 向量数据库 | 对话历史 | 专用 API |
|------|---------|-----------|---------|---------|
| **模型熟悉度** | 极高（预训练数据中大量出现） | 低（需要专用工具） | 极高（原生支持） | 中（需要工具定义） |
| **信息结构** | 树形，天然分层 | 扁平，靠 metadata 分类 | 线性，时间序列 | 取决于 API 设计 |
| **访问粒度** | 行级 / 字符级 | 文档块级 | 消息级 | API 返回值级 |
| **持久化** | 天然持久 | 天然持久 | 会话结束即丢失 | 取决于后端 |
| **多 Agent 共享** | 天然支持 | 需要共享数据库 | 不支持 | 需要共享 API |
| **Agent 可写** | 是 | 通常只读 | 隐式（对话即写入） | 取决于 API |
| **Token 效率** | 高（按需读取任意片段） | 中（返回固定大小的块） | 低（累积不可控） | 中（返回固定格式） |

## 延伸思考

1. **文件系统的安全边界：** 当 Agent 拥有文件系统的读写权限时，如何防止它误删关键文件、覆盖重要数据、或者读取不该读的敏感信息？沙盒 (Sandbox) 和权限控制是否足够，还是需要更细粒度的访问策略？

2. **从文件系统到知识图谱：** 文件系统的树形结构适合层级化的信息，但有些知识天然是网状的（例如代码中的调用关系、概念之间的关联）。文件系统是否会成为 Agent 上下文管理的"最终形态"，还是只是通往更丰富知识表示的过渡方案？

3. **Agent 自写指令的可控性：** 如果 Agent 可以修改自己的指令文件，理论上它可以改变自己的行为准则。这种"自我修改"何时有益（学习用户偏好），何时危险（偏离设计意图）？是否需要对 Agent 可修改的指令范围设置边界？

4. **文件系统操作的可靠性幻觉：** 虽然模型在预训练中接触了大量文件系统操作，但它并不真正"理解"文件系统的语义（例如权限、符号链接、并发写入冲突）。当 Agent 的文件系统操作遇到预训练数据中少见的边缘情况时，是否会产生新型的幻觉？
