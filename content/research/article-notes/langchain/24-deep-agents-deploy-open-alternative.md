# Deep Agents Deploy：一条命令部署生产级 Agent 的开放替代方案

**作者:** LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/deep-agents-deploy-open-alternative)  
**日期:** 2026 年 5 月  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> `deepagents deploy` 一条命令将 Agent 编排、记忆、沙箱和 API 端点打包部署到生产环境。它是 Claude Managed Agents 的开放替代方案 —— 同样的高层架构，但你拥有代码、记忆和选择权。

---

## 核心要点

1. **一条命令，完整部署** —— `deepagents deploy` 将模型配置、指令文件 (AGENTS.md)、技能 (Skills)、工具 (MCP) 和沙箱五大要素打包为可运行的生产服务
2. **30+ 端点，三大协议** —— 部署后自动暴露 MCP、A2A (Agent-to-Agent)、Agent Protocol 端点，加上人机协作 (HITL) 和记忆管理 API
3. **开放生态 vs 围墙花园** —— MIT 许可、任意模型供应商、任意沙箱、可自托管，与 Claude Managed Agents 的封闭架构形成鲜明对比
4. **记忆是开放性最重要的战场** —— 模型无状态可以随时切换，但记忆一旦被锁在封闭 API 背后就无法迁移 —— 这才是真正的锁定

## 一、你在部署什么？

### 五大参数，定义一个 Agent

`deepagents deploy` 接受五个核心参数，每一个都对应 Agent 架构中的一个关键层：

| 参数 | 说明 | 示例 |
|------|------|------|
| **model** | 使用的模型（任意供应商） | `claude-sonnet-4-20250514`、`gpt-4o`、`gemini-2.5-pro` |
| **AGENTS.md** | Agent 指令文件（开放标准） | 系统提示、行为规范、角色定义 |
| **skills** | 技能文件夹（开放标准） | 专业知识、工作流程、领域专长 |
| **mcp.json** | 工具配置（MCP 协议） | 文件系统、数据库、API 集成 |
| **sandbox** | 代码执行沙箱 | Daytona / Modal / Runloop / LangSmith |

## 二、部署后你得到什么？

### 30+ 端点的 LangSmith Deployment Server

部署完成后，你获得一个完整的 LangSmith Deployment Server，暴露 30 多个 API 端点，覆盖六大类能力：

| 端点类别 | 协议/功能 | 用途 |
|----------|----------|------|
| **MCP 端点** | Model Context Protocol | 让你的 Agent 成为其他 Agent 的工具 |
| **A2A 端点** | Agent-to-Agent Protocol | Agent 间直接通信与协作 |
| **Agent Protocol 端点** | 标准化 Agent 接口 | 通用的 Agent 交互方式 |
| **HITL 端点** | 人机协作 (Human-in-the-Loop) | 关键决策点的人类审批与介入 |
| **Memory 端点** | 记忆管理 API | 查询、更新、导出 Agent 记忆 |
| **管理端点** | 部署管理 | 健康检查、配置更新、日志查看 |

## 三、开放生态：每一层都可替换

### Deep Agents Deploy 的开放承诺

这是 Deep Agents Deploy 与 Claude Managed Agents 最根本的差异 —— **每一个组件都有替代品，每一层都不锁定**：

| 维度 | Deep Agents Deploy | 状态 |
|------|-------------------|------|
| 源码许可 | MIT（Python + TypeScript） | 完全开放 |
| 指令标准 | AGENTS.md（开放标准） | 跨线束通用 |
| 技能标准 | Agent Skills（开放标准） | 可迁移复用 |
| 模型供应商 | 任意（Anthropic / OpenAI / Google / 开源） | 无锁定 |
| 沙箱供应商 | Daytona / Modal / Runloop / LangSmith | 可替换 |
| 工具协议 | MCP（开放标准） | 跨生态通用 |
| 通信协议 | A2A、Agent Protocol | 开放标准 |
| 部署方式 | LangSmith 托管或自托管 | 你的数据库 |

## 四、与 Claude Managed Agents 的正面对比

### 同一架构，两种哲学

Claude Managed Agents 和 Deep Agents Deploy 在高层架构上惊人地相似 —— 都包含模型、指令、工具、沙箱和端点。差异不在技术架构，而在**所有权哲学**。

| 维度 | Claude Managed Agents | Deep Agents Deploy |
|------|----------------------|-------------------|
| **源码** | 闭源（Anthropic 控制） | MIT 开源 |
| **模型** | 仅限 Claude 系列 | 任意模型供应商 |
| **指令格式** | CLAUDE.md（Anthropic 专有） | AGENTS.md（开放标准） |
| **记忆存储** | Anthropic API 背后 | 你的数据库 |
| **记忆可见性** | 不透明 | 完全可查询 |
| **记忆可迁移性** | 不可导出 | 标准格式，随时导出 |
| **沙箱** | Anthropic 托管 | 多供应商可选 |
| **定价** | 按 Anthropic 定价 | 自主选择各层成本 |
| **协议支持** | 有限 | MCP + A2A + Agent Protocol |
| **自托管** | 不支持 | 完全支持 |

## 五、记忆 = 开放性最重要的战场

### 为什么记忆比模型更难切换？

这是整篇文章最关键的洞察：

- **切换模型很容易** —— 因为模型调用是无状态的 (Stateless)。把 `claude-sonnet-4` 换成 `gpt-4o`，改一行配置就行。模型不记得你是谁，也不记得上一次对话。
- **切换记忆几乎不可能** —— 因为记忆是有状态的 (Stateful)。你的 Agent 在数百次交互中积累的知识、偏好、学到的模式，全部存在记忆系统中。如果记忆被锁在封闭 API 背后，迁移意味着**从零开始**。

```
无状态 vs 有状态：切换成本的本质差异

模型（无状态）                    记忆（有状态）
┌──────────────────┐           ┌──────────────────┐
│                  │           │                  │
│  调用 1: f(x)→y  │           │  第 1 周: 学会 A  │
│  调用 2: f(x)→y  │           │  第 4 周: 学会 B  │
│  调用 3: f(x)→y  │           │  第 8 周: 学会 C  │
│                  │           │  第 12 周: 学会 D │
│  每次独立         │           │                  │
│  没有历史         │           │  层层叠加         │
│  换一个一样用     │           │  不可替代         │
│                  │           │                  │
│  切换成本: ≈ 0    │           │  切换成本: ∞      │
└──────────────────┘           └──────────────────┘
```

### 案例一：SDR Agent（销售开发代表）

想象一个帮你做销售外联 (Outreach) 的 Agent：

1. **第 1 周：** Agent 发送标准模板邮件，回复率 2%
2. **第 4 周：** Agent 学会了哪些主题行吸引技术决策者，回复率升至 5%
3. **第 8 周：** Agent 掌握了最佳跟进时机（周二上午 10 点），学会了避开假期
4. **第 12 周：** Agent 已积累了数百条交互数据 —— 哪些话术有效、哪些行业响应更快、哪些信号预示着高意向

> **在封闭平台上：** 这 12 周的学习成果全部存在 Anthropic 的 API 背后。想换模型？记忆跟不过来。想换平台？从零开始。想自己分析这些数据？API 不提供。  
> **在 Deep Agents Deploy 上：** 记忆以标准格式（AGENTS.md、技能文件、本地文件）存在你的数据库中。换模型、换平台、做分析 —— 数据始终在你手里。

### 案例二：客户服务 Agent

一个面向客户的服务 Agent 更能体现记忆锁定的严重性：

```
客户记忆积累的飞轮效应

     交互 ──────► 学习 ──────► 更好的服务
      ▲                           │
      │                           │
      └──── 客户满意，更多交互 ◄────┘

这个飞轮的核心资产 = 记忆

封闭平台：飞轮归平台所有
开放部署：飞轮归你所有
```

客户 A 不喜欢被推荐高价方案。客户 B 偏好邮件沟通而非电话。客户 C 每次投诉前会先在社交媒体发帖。这些都是 Agent 在数百次交互中学到的宝贵知识。

- **在封闭平台上：** 这些客户记忆是你**无法拥有的数据飞轮** (Data Flywheel)。它让你的 Agent 越用越好，但所有权不在你手里。平台涨价？你别无选择。平台关停？记忆归零。
- **在 Deep Agents Deploy 上：** 记忆存在你自己的数据库中，通过 Memory API 可查询、可导出。你拥有这个数据飞轮的完整控制权。

> **为什么重要**  
> 记忆不仅仅是"方便切换"的问题。对于商业 Agent 来说，记忆就是核心资产 —— 它是 Agent 从"通用工具"进化为"专属助手"的全部积累。把这个资产交给封闭平台，等于把公司最重要的数据集放在了你不拥有的基础设施上。

## 六、Deep Agents Deploy 的记忆架构

### 开放记忆的三层设计

Deep Agents Deploy 的记忆系统基于三个核心原则：**标准格式、可查询、可自托管**。

| 记忆层 | 存储方式 | 特点 |
|--------|---------|------|
| **指令记忆** | AGENTS.md 文件 | 开放标准，纯文本，版本可控 |
| **技能记忆** | Skills 文件夹 | 开放标准，可迁移复用 |
| **交互记忆** | 本地文件 + 数据库 | 通过 Memory API 查询和导出 |

```

│  │  skills/   ──── 技能记忆（文件夹）          │   │
│  │  memory/   ──── 交互记忆（结构化数据）       │   │

│                     ▼                            │
│  ┌───────────────────────────────────────────┐   │
│  │     你的数据库                              │   │
│  │     PostgreSQL / MongoDB / SQLite / ...    │   │
│  │     你的服务器，你的控制权                    │   │
│  └───────────────────────────────────────────┘   │
└──────────────────────────────────────────────────┘
```

### 对比：封闭 vs 开放的记忆可见性

| 操作 | Claude Managed Agents | Deep Agents Deploy |
|------|----------------------|-------------------|
| 查看 Agent 学到了什么 | 不可见 | `GET /memory/query` |
| 导出全部记忆 | 不支持 | `GET /memory/export` |
| 手动修正错误记忆 | 不可能 | `POST /memory/update` |
| 审计记忆变化 | 无审计日志 | Git 版本控制 + API 日志 |
| 迁移到新平台 | 从零开始 | 标准格式直接导入 |

## 七、一条命令的背后

### 部署流程拆解

```bash
deepagents deploy \
  --model claude-sonnet-4-20250514 \
  --instructions ./AGENTS.md \
  --skills ./skills/ \
  --tools ./mcp.json \
  --sandbox daytona
```

这一条命令背后，系统自动完成了以下步骤：

```
deepagents deploy 执行流程

  ① 解析配置
     │  读取 AGENTS.md、skills/、mcp.json
     │  验证模型访问权限
     │  检查沙箱可用性
     │
  ② 构建运行时
     │  初始化 Agent 线束
     │  加载指令和技能到上下文
     │  注册 MCP 工具
     │  连接沙箱环境
     │
  ③ 启动服务
     │  创建 LangSmith Deployment Server
     │  注册 30+ API 端点
     │  初始化记忆存储
     │  配置 HITL 审批流程
     │
  ④ 就绪
     └─► 生产级 Agent 服务已上线
         MCP / A2A / Agent Protocol 端点可用
         Memory API 可用
         HITL 端点可用
```

> **类比理解**  
> `deepagents deploy` 之于 Agent 部署，就像 `docker compose up` 之于微服务部署 —— 一条命令把所有复杂性封装掉，你只需要关心业务逻辑（指令 + 技能），不需要关心基础设施。

## 延伸思考

1. **开放标准的网络效应：** AGENTS.md 和 Skills 作为开放标准，其价值随采用者数量增长。如果多个线束（Deep Agents、Pi、OpenCode）都支持同一标准，是否会形成类似 Docker 镜像生态的共享效应 —— 技能成为可复用的"Agent 容器"？

2. **记忆的监管维度：** 当客户服务 Agent 积累了大量用户偏好和行为数据后，这些记忆是否应该受到数据保护法规（如 GDPR）的约束？封闭平台在这方面的合规风险是否被低估了？

3. **"足够好"的封闭 vs "更灵活"的开放：** Claude Managed Agents 的优势在于开箱即用、零运维。对于小团队来说，"不需要管基础设施"可能比"拥有选择权"更有吸引力。开放方案需要达到什么样的易用性水平，才能让这个权衡真正倾斜？

4. **多 Agent 协作的互操作性：** 当你的 Agent 需要与其他团队的 Agent 协作时（通过 A2A 协议），如果对方使用封闭平台，互操作性会受到怎样的限制？开放协议能否成为跨组织 Agent 协作的基础？

5. **记忆可迁移性的实际成本：** 理论上记忆可以导出和导入，但不同系统对记忆的表示方式不同。实际迁移中，语义损失有多大？是否需要一个"记忆翻译层"来实现真正的无损迁移？
