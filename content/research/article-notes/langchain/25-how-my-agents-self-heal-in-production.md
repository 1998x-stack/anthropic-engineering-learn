**作者:** LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-my-agents-self-heal-in-production)  
**日期:** 2026 年 5 月  
**阅读时间:** 约 12 分钟

---

> **一句话总结**  
> 部署不是终点，而是循环的起点。通过 GitHub Actions + Open SWE（异步编码 Agent），搭建一套"部署 → 监控 → 分诊 → 修复"的全自动闭环，让生产环境中的 Agent 能够自我修复 —— 不需要人类半夜起床看报警。

---

## 核心要点

1. **两条修复路径** —— Docker 构建失败直接将错误日志 + git diff 发给 Open SWE 开 PR；部署后错误需要统计检测 + 因果分诊才能行动
2. **泊松分布 (Poisson Distribution) 做异常检测** —— 用 7 天基线估算错误发生率，在 60 分钟部署窗口内判断错误是否异常激增（p < 0.05）
3. **分诊 Agent 是防止误报的关键** —— 统计异常不等于代码缺陷，分诊 Agent 必须在 diff 和错误之间建立具体的因果链，才能触发修复
4. **Open SWE 关闭循环** —— 分诊通过后，Open SWE 自动调查问题并开 PR，全程无需人工干预
5. **最擅长捕捉"沉默故障"** —— 错误的默认值、配置不匹配、级联回归，这些人类最容易漏掉的问题恰好是自动修复最擅长的

## 一、自我修复的完整循环

### 从"人盯报警"到"机器关闭循环"

传统的部署后监控依赖人类：告警响了 → 工程师醒了 → 看日志 → 定位问题 → 写修复 → 提 PR → 合并。这个流程快则几小时，慢则几天。

自我修复的核心思想是把这个循环全部自动化：

```
自我修复循环 (Self-Healing Loop)

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │    ① 部署 (Deploy)                                       │
  │    │  GTM Agent + LangSmith Deployments                  │
  │    │                                                      │
  │    ▼                                                      │
  │    ② 监控 (Monitor)                                       │
  │    │  收集基线 → 检测异常 → 签名对比                        │
  │    │                                                      │
  │    ▼                                                      │
  │    ③ 分诊 (Triage)                                        │
  │    │  分类变更文件 → 建立因果链 → 输出结构化判定             │
  │    │                                                      │
  │    ▼                                                      │
  │    ④ 修复 (Fix)                                           │
  │    │  Open SWE 调查 → 自动开 PR → 合并后回到 ①             │
  │    │                                                      │
  │    └──────────────── 回到 ① ◄────────────────────────────┘
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

> **类比理解**  
> 传统部署监控像医院的急诊室 —— 病人来了才看，全靠医生判断。自我修复更像 ICU 的持续监护系统：传感器 24 小时采集数据（监控），异常信号自动触发诊断流程（分诊），确认病因后直接启动治疗方案（修复），全程不需要医生盯着屏幕。

### GitHub Action 触发的两条路径

部署后的 GitHub Action 根据失败类型分为两条完全不同的路径：

| 路径 | 触发条件 | 处理方式 | 为什么可以这么做 |
|------|---------|---------|----------------|
| **路径 A：构建失败** | Docker 构建报错 | 错误日志 + git diff → 直接发给 Open SWE | 构建失败几乎总是最近一次提交引起的，因果关系明确 |
| **路径 B：运行时错误** | 部署成功但出现新错误 | 统计检测 + 分诊 Agent → 条件性修复 | 运行时错误成因复杂，可能是 API 宕机而非代码问题 |

```
GitHub Action 触发后的两条路径

                    GitHub Action 触发
                          │
                ┌─────────┴─────────┐
                │                   │
                ▼                   ▼
         Docker 构建失败？      部署成功？
                │                   │
                ▼                   ▼
         路径 A: 直接修复     路径 B: 统计监控
                │                   │
                │                   ▼
                │            收集 7 天基线
                │                   │
                │                   ▼
                │            60 分钟窗口采样
                │                   │
                │                   ▼
                │            泊松检验 (p < 0.05?)
                │                   │
                │              ┌────┴────┐
                │              │         │
                │            异常       正常
                │              │         │
                │              ▼         ▼
                │         分诊 Agent    结束
                │              │
                │         ┌────┴────┐
                │         │         │
                │       代码问题   非代码问题
                │         │         │
                ▼         ▼         ▼
           Open SWE   Open SWE    结束
           开 PR       开 PR
```

> **为什么重要**  
> 路径 A 和路径 B 的区分不是技术细节，而是工程判断的体现。构建失败的因果链是确定性的（代码改了，编译不过了），所以可以直接行动。运行时错误的因果链是概率性的（可能是代码、可能是下游服务、可能是流量变化），必须先证明因果关系才能行动。盲目修复比不修复更危险。

## 二、错误签名与统计检测

### 将混沌的日志变成可比较的信号

生产环境的错误日志是"脏"的 —— 同一个错误每次触发时，日志中的 UUID、时间戳、数字都不同。如果直接逐字比较，同一个错误会被识别为成千上万个"不同"的错误。

**错误签名归一化 (Error Signature Normalization)** 解决这个问题：

```
原始错误日志:
"Connection to db-7a3f2e1b timed out at 2026-05-14T03:22:17Z after 30000ms"
"Connection to db-9c4d8f2a timed out at 2026-05-14T03:25:41Z after 30000ms"
"Connection to db-1e5b6c3d timed out at 2026-05-14T03:28:09Z after 30000ms"

                    │
                    ▼  正则替换 (Regex Normalization)
                    │  · UUID → <ID>
                    │  · 时间戳 → <TS>
                    │  · 数字 → <N>
                    │  · 截断到 200 字符
                    │
                    ▼

归一化签名:
"Connection to db-<ID> timed out at <TS> after <N>ms"

三条不同的日志 → 同一个签名
```

归一化的三个步骤：

| 步骤 | 操作 | 目的 |
|------|------|------|
| ① 替换变量部分 | 正则移除 UUID、时间戳、数字 | 消除"噪声差异"，保留"结构差异" |
| ② 截断长度 | 保留前 200 字符 | 栈追踪的前几行通常最有信息量 |
| ③ 去重统计 | 按签名聚合计数 | 从"1000 条日志"变成"5 种错误，各出现 N 次" |

### 用泊松分布检测部署后的异常

归一化后的签名可以按小时统计出现频率。接下来用泊松分布 (Poisson Distribution) 判断部署后的错误率是否异常。

**为什么用泊松分布？**

泊松分布建模的是"在固定时间间隔内，已知平均速率下，事件发生特定次数的概率"。错误日志天然符合这个模型：

- 固定时间间隔 = 部署后的 60 分钟观察窗口
- 已知平均速率 = 7 天基线中该签名的平均每小时出现次数

```
泊松检验的工作原理

  ① 收集 7 天基线
     │  "Connection timeout" 签名平均每小时出现 3 次
     │  → λ (lambda) = 3
     │
  ② 部署后 60 分钟观察
     │  该签名出现了 12 次
     │
  ③ 泊松检验
     │  P(X ≥ 12 | λ = 3) = ?
     │
     │  如果 p < 0.05 → 统计显著，该签名异常激增
     │  如果 p ≥ 0.05 → 在正常波动范围内，不告警
     │
  ④ 新签名处理
     │  基线中不存在的签名 → 如果重复出现则标记
     │  单次出现可能是瞬态问题，重复才值得关注
```

> **类比理解**  
> 泊松检验就像体检时的血液指标参考范围。医生不会因为你的白细胞计数从 6000 变成 7000 就紧张（正常波动），但从 6000 跳到 20000 就一定要查原因。λ 是你的"正常范围"，部署后的观测值就是"今天的化验结果"。

### 统计检测的局限性

**关键洞察：统计异常 ≠ 代码缺陷。**

泊松检验只能告诉你"这个错误出现得比平时多了"，但不能告诉你"是不是你的代码改坏了"。

| 场景 | 统计结果 | 真实原因 | 应该修复吗？ |
|------|---------|---------|-------------|
| 部署后数据库超时激增 | p < 0.01 | 下游数据库在做维护 | 否 |
| 部署后 API 错误翻倍 | p < 0.05 | 第三方 API 宕机 | 否 |
| 部署后新签名反复出现 | 新签名 | 代码引入了错误的默认值 | 是 |
| 部署后 HTTP 500 激增 | p < 0.01 | 配置文件格式错误 | 是 |

这就是为什么需要分诊 Agent —— 它在统计信号和修复行动之间插入了一层**因果推理**。

## 三、分诊 Agent：防止误报的关键

### 从"相关性"到"因果性"

分诊 Agent (Triage Agent) 的核心任务是回答一个问题：**这次部署的代码变更，是否是观测到的错误的直接原因？**

它分两步完成这个判断：

#### 步骤一：文件分类

分诊 Agent 首先对本次 diff 中变更的文件进行分类：

| 文件类别 | 英文标签 | 能否导致运行时错误？ | 示例 |
|---------|---------|------------------|------|
| 运行时代码 | `runtime` | 可以 | `agent.py`, `handler.ts` |
| 提示词文件 | `prompt` | 可以（行为变化） | `system_prompt.md` |
| 配置文件 | `config` | 可以 | `config.yaml`, `.env` |
| 测试文件 | `test` | 极不可能 | `test_agent.py` |
| 文档文件 | `docs` | 极不可能 | `README.md`, `CHANGELOG.md` |
| CI 文件 | `ci` | 极不可能 | `.github/workflows/*.yml` |

```
文件分类的过滤效果

  diff 包含 8 个变更文件
      │
      ▼
  ┌─────────────────────────────────┐
  │  分类:                           │
  │  · README.md          → docs    │  ──► 极不可能导致错误
  │  · test_handler.py    → test    │  ──► 极不可能导致错误
  │  · .github/ci.yml     → ci      │  ──► 极不可能导致错误
  │  · CHANGELOG.md       → docs    │  ──► 极不可能导致错误
  │  · agent.py           → runtime │  ──► 需要深入分析
  │  · config.yaml        → config  │  ──► 需要深入分析
  │  · handler.ts         → runtime │  ──► 需要深入分析
  │  · system_prompt.md   → prompt  │  ──► 需要深入分析
  └─────────────────────────────────┘
      │
      ▼
  8 个文件 → 4 个需要深入分析（50% 噪声被过滤）
```

> **为什么重要**  
> 如果你只改了 `README.md` 和 `test_handler.py`，即使部署后出现了统计显著的错误激增，那也几乎不可能是你的代码导致的。文件分类这一步砍掉了大量误报 (False Positive)，避免 Open SWE 浪费时间在不可能有用的修复上。

#### 步骤二：因果链建立

对于分类为 `runtime` / `prompt` / `config` 的文件，分诊 Agent 必须在 **diff 中的具体代码行** 和 **观测到的错误签名** 之间建立具体的因果链 (Causal Link)。

不是"这个文件可能有问题"，而是"第 47 行把默认超时从 30s 改成了 5s，而观测到的错误签名是 'timeout after 5000ms'"。

```
因果链建立示例

  diff (agent.py):                    观测到的错误签名:
  ┌─────────────────────────┐        ┌──────────────────────────┐
  │ - timeout = 30          │        │ "Request timed out       │
  │ + timeout = 5           │   ──►  │  after <N>ms"            │
  │   (第 47 行)            │  因果链 │  (部署后频率 x10)         │
  └─────────────────────────┘        └──────────────────────────┘

  具体到行 + 具体到签名 = 高置信度因果链
```

### 分诊输出的结构化判定

分诊 Agent 输出一个结构化的判定 (Verdict)，而不是自然语言的"我觉得可能有问题"：

| 字段 | 类型 | 说明 |
|------|------|------|
| `decision` | `fix` / `ignore` | 是否应该触发修复 |
| `confidence` | `high` / `medium` / `low` | 因果链的置信度 |
| `reasoning` | string | 因果推理的完整链条 |
| `attributed_signatures` | list | 被归因到本次变更的错误签名列表 |

```json
{
  "decision": "fix",
  "confidence": "high",
  "reasoning": "agent.py 第 47 行将默认超时从 30s 改为 5s。
    部署后 'timeout after <N>ms' 签名出现频率从基线的 3次/小时
    激增到 38次/小时 (p < 0.001)。超时时间与代码变更精确匹配。",
  "attributed_signatures": [
    "Request timed out after <N>ms"
  ]
}
```

> **类比理解**  
> 分诊 Agent 就像法庭上的检察官，而不是嫌疑人甄别器。统计检测只是"这里发生了犯罪"（异常），文件分类排除了"不在场的嫌疑人"（文档和测试文件），但最终定罪需要**完整的证据链** —— 犯罪手法（具体的代码变更）与犯罪现场（具体的错误签名）的精确匹配。没有证据链，就不起诉（不触发修复）。

## 四、Open SWE 关闭循环

### 从判定到修复

当分诊 Agent 输出 `decision: "fix"` 时，Open SWE（异步编码 Agent）接管：

```
Open SWE 修复流程

  分诊判定: fix
      │
      ▼
  ┌──────────────────────────────────────┐
  │  Open SWE 接收:                       │
  │  · 错误签名 + 出现频率                  │
  │  · 归因的 diff 行                      │
  │  · 分诊 Agent 的因果推理               │
  └───────────────┬──────────────────────┘
                  │
                  ▼
  ┌──────────────────────────────────────┐
  │  ① 调查阶段                           │
  │     阅读完整代码上下文                  │
  │     理解变更意图和副作用                 │
  │                                      │
  │  ② 修复阶段                           │
  │     编写修复代码                       │
  │     确保不引入新问题                    │
  │                                      │
  │  ③ 提交阶段                           │
  │     自动开 PR                         │
  │     附带修复说明和因果分析               │
  └───────────────┬──────────────────────┘
                  │
                  ▼
          PR 合并 → 重新触发部署
          → 回到监控循环 ①
```

### 自动修复最擅长的三类问题

不是所有生产问题都适合自动修复。以下三类问题是自我修复循环的"甜点区"(Sweet Spot)：

| 问题类型 | 为什么适合自动修复 | 示例 |
|---------|-----------------|------|
| **沉默故障 (Silent Failures)** | 不会立刻崩溃，但行为错误；人类很难在 code review 中发现 | 默认值从 `True` 改成 `False`，导致功能静默失效 |
| **配置不匹配 (Config Mismatches)** | 代码逻辑正确但配置与期望不符；diff 可以精确定位 | 环境变量名拼写错误、YAML 缩进错误 |
| **级联回归 (Cascading Regressions)** | 一个小变更在远处触发连锁反应；人类难以预测影响半径 | 修改了共用工具函数的签名，下游调用者静默失败 |

> **为什么重要**  
> 这三类问题有一个共同特点：**人类在 code review 阶段很容易漏掉它们**。沉默故障不会让测试报红，配置不匹配不会让编译报错，级联回归的影响范围超出了 reviewer 的注意力半径。自我修复循环补上了人类认知的盲区。

### 关键设计决策总结

| 设计决策 | 选择 | 理由 |
|---------|------|------|
| 基线窗口 | 7 天 | 覆盖工作日/周末差异，足够稳定 |
| 观察窗口 | 60 分钟 | 长到能捕捉延迟暴露的问题，短到能快速反应 |
| 显著性阈值 | p < 0.05 | 统计学标准阈值，5% 的误报率可接受 |
| 新签名处理 | 重复才标记 | 单次出现可能是瞬态问题 |
| 文件分类 | 6 类 | 覆盖常见变更类型，非运行时文件直接过滤 |
| 分诊输出 | 结构化 JSON | 机器可读，便于 Open SWE 消费 |

## 六、未来改进方向

### 已知的限制和演进路径

当前系统能工作，但远不完美。三个已知方向：

#### 1. 更宽的回溯窗口 (Wider Lookback)

7 天基线能覆盖大多数场景，但某些季节性错误（月末结算、季度报表）需要更长的回溯。代价是更宽的窗口引入更多噪声，λ 估计可能偏高，导致真正的异常被掩盖。

#### 2. 更智能的错误分组 (Smarter Error Grouping)

正则归一化是粗暴但有效的方案。更先进的方法：

| 方法 | 思路 | 优势 | 代价 |
|------|------|------|------|
| **嵌入 + 聚类** | 用嵌入模型 (Embedding Model) 将错误日志向量化，然后做聚类 | 能捕捉语义相似但措辞不同的错误 | 需要额外的推理成本 |
| **小模型分类** | 用轻量模型将错误分类到预定义类别 | 分类一致性高 | 需要维护分类体系 |

#### 3. 修复前进 vs 回滚 (Fix-Forward vs Rollback)

当前系统总是尝试"修复前进"（写新代码修复问题）。但有些情况下回滚 (Rollback) 是更好的选择：

```
修复前进 vs 回滚的决策矩阵

                    置信度高              置信度低
              ┌──────────────────┬──────────────────┐
  严重度高    │  回滚             │  回滚             │
              │  (快速止血最重要)  │  (不确定就别赌)    │
              ├──────────────────┼──────────────────┤
  严重度低    │  修复前进          │  观察等待          │
              │  (有把握就往前走)  │  (可能是噪声)      │
              └──────────────────┴──────────────────┘
```

## 延伸思考

1. **自我修复的"信任边界"在哪里？** 自动开 PR 修复构建失败是低风险的，但自动修复运行时逻辑错误呢？如果修复本身引入了新 bug，自我修复系统会不会陷入"修复→破坏→修复→破坏"的死循环？需要什么样的熔断机制 (Circuit Breaker) 来防止这种情况？

2. **分诊 Agent 的准确率能到多少？** 在代码变更和错误之间建立因果链，本质上是一个程序理解 (Program Understanding) 问题。当 diff 涉及多个文件、多层调用链时，当前的分诊方式是否足够？是否需要更深入的静态分析或动态追踪来增强因果推理？

3. **从"事后修复"到"事前预防"：** 如果自我修复系统积累了足够多的"变更类型 → 常见错误"的模式数据，是否可以在 code review 阶段就预警 —— 在代码被部署之前就阻止潜在问题？这本质上是把事后修复的知识前移到开发阶段。

4. **多 Agent 系统的故障归因更难：** 当你的系统由多个 Agent 协作完成（通过 A2A 协议），一个 Agent 的代码变更可能导致另一个 Agent 出错。跨 Agent 的因果链建立比单 Agent 场景复杂得多 —— 分诊 Agent 需要理解整个 Agent 网络的拓扑结构。

5. **"沉默故障"的沉默检测：** 文章提到自我修复最擅长捕捉沉默故障，但沉默故障的定义就是"不会产生明显的错误信号"。如果一个默认值从 `True` 变成 `False` 后功能静默失效但不抛异常，泊松检验根本捕捉不到。这类问题是否需要基于业务指标 (Business Metrics) 而非错误日志的监控方式？
