# Agent 基础设施的三层架构：框架、运行时与线束

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/agent-frameworks-runtimes-and-harnesses)  
**日期:** 2025 年 10 月 25 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> Agent 基础设施正在分化为三个层次：框架 (Framework) 提供抽象、运行时 (Runtime) 提供生产基础设施、线束 (Harness) 提供开箱即用的完整体验。理解这三层的边界和关系，是选择技术栈和判断行业方向的前提。

---

## 核心要点

1. **框架管"怎么写"** —— LangChain、Vercel AI SDK、CrewAI 等提供结构化内容、Agent 循环、中间件等抽象，降低开发者的认知负担
2. **运行时管"怎么活"** —— LangGraph、Temporal、Inngest 等解决持久执行、人机协作、记忆管理等生产问题，比框架更底层，可以为框架提供动力
3. **线束管"怎么用"** —— Deep Agents、Claude Code 等在框架之上叠加默认提示词和工具集，让用户拿来就能干活，而不是自己从零搭建
4. **边界是模糊的** —— LangGraph 同时扮演运行时和框架的角色；Claude Code 既是产品也在尝试成为线束平台。这个领域仍在定义自己的心智模型
5. **"Agent 线束"是一个新术语** —— 它描述了比框架更高一层的抽象，正在成为独立的产品品类

---

## 一、为什么需要区分三层？

当你说"我要构建一个 Agent"时，你其实在面对三组完全不同的问题：

| 问题层次 | 典型问题 | 你需要的 |
|----------|----------|----------|
| **开发时** | 如何定义工具？如何编排多个 Agent？如何处理结构化输出？ | 框架 (Framework) |
| **运行时** | Agent 崩溃了怎么恢复？长时间运行怎么暂停？多用户怎么隔离？ | 运行时 (Runtime) |
| **使用时** | 用什么提示词？配什么工具？如何让 Agent 立即开始工作？ | 线束 (Harness) |

> **类比理解**  
> 把它想象成做菜。框架是厨具（锅、刀、灶台）——它们提供基本能力，但你得自己决定做什么菜。运行时是厨房基础设施（水电气、排烟系统、冷链）——没有它们，厨房无法运转。线束是一份完整的预制菜套餐——食材已经配好、步骤已经写好，你按说明操作就能出菜。

## 二、第一层：Agent 框架 (Agent Frameworks)

### 框架做什么？

框架提供**开发者抽象 (Developer Abstractions)**——把构建 Agent 过程中的重复性工作标准化。

```
┌───────────────────────────────────────────────────┐
│              Agent 框架提供的抽象                    │
│                                                   │
│  ┌─────────────┐  ┌──────────────┐  ┌───────────┐ │
│  │ 结构化内容    │  │  Agent 循环   │  │  中间件    │ │
│  │ (Structured  │  │ (Agent Loop) │  │(Middleware)│ │
│  │  Content)    │  │              │  │           │ │
│  │             │  │ 调用模型      │  │ 钩子      │ │
│  │ 工具定义     │  │ ↓            │  │ 拦截器    │ │
│  │ 输出解析     │  │ 解析响应      │  │ 日志      │ │
│  │ Schema 校验  │  │ ↓            │  │ 重试      │ │
│  │             │  │ 执行工具      │  │ 护栏      │ │
│  │             │  │ ↓            │  │           │ │
│  │             │  │ 循环 ↑       │  │           │ │
│  └─────────────┘  └──────────────┘  └───────────┘ │
└───────────────────────────────────────────────────┘
```

### 主要玩家

| 框架 | 主导方 | 核心定位 |
|------|--------|----------|
| **LangChain** | LangChain | 最早的 Agent 框架之一，丰富的集成生态 |
| **Vercel AI SDK** | Vercel | 面向前端开发者的 AI 工具包 |
| **CrewAI** | CrewAI | 多 Agent 协作框架 |
| **OpenAI Agents SDK** | OpenAI | OpenAI 官方 Agent 开发工具 |
| **Google ADK** | Google | Google 的 Agent 开发套件 |
| **LlamaIndex** | LlamaIndex | 以数据索引和检索为核心 |

### 框架的核心价值

框架的价值在于**抽象的复用**：

1. **结构化内容 (Structured Content)** —— 统一定义工具的输入输出 Schema，处理模型返回值的解析和校验
2. **Agent 循环 (Agent Loop)** —— 标准化"调用模型 → 解析响应 → 执行工具 → 反馈结果"的核心循环
3. **中间件 (Middleware)** —— 在 Agent 循环的各个环节插入确定性逻辑（日志、重试、护栏、压缩）

> **为什么重要**  
> 没有框架，每个开发者都要自己实现工具调用的解析、错误处理、重试逻辑。这些代码高度重复且容易出错。框架将它们标准化，让开发者聚焦于业务逻辑而不是基础管道。

## 三、第二层：Agent 运行时 (Agent Runtimes)

### 运行时做什么？

运行时解决的是**生产环境的基础设施问题**——那些在原型阶段不会出现、但在上线后立刻暴露的挑战。

```
┌───────────────────────────────────────────────────┐
│             Agent 运行时的核心能力                    │
│                                                   │
│  ┌─────────────┐  ┌──────────────┐  ┌───────────┐ │
│  │ 持久执行      │  │  人机协作     │  │  记忆管理  │ │
│  │ (Durable     │  │ (Human-in-   │  │ (Memory   │ │
│  │  Execution)  │  │  the-Loop)   │  │Management)│ │
│  │             │  │              │  │           │ │
│  │ 崩溃恢复     │  │ 暂停等待审批  │  │ 短期记忆  │ │
│  │ 检查点       │  │ 分支中断     │  │ 长期记忆  │ │
│  │ 跨进程恢复   │  │ 恢复执行     │  │ 语义搜索  │ │
│  └─────────────┘  └──────────────┘  └───────────┘ │
└───────────────────────────────────────────────────┘
```

### 关键区分：运行时 vs. 框架

| 维度 | 框架 (Framework) | 运行时 (Runtime) |
|------|-----------------|-----------------|
| 解决的问题 | "怎么写 Agent 代码" | "Agent 怎么在生产中存活" |
| 抽象层级 | 较高（面向开发者） | 较低（面向基础设施） |
| 关注点 | 工具定义、输出解析、循环编排 | 持久执行、状态管理、崩溃恢复 |
| 是否可独立使用 | 是 | 是，但通常为框架提供动力 |
| 最近的类比 | React、Express | Docker、Kubernetes |

> **类比理解**  
> 框架像 React——它帮你写 UI 组件。运行时像 Kubernetes——它帮你让这些组件在生产中稳定运行、自动扩缩容、崩溃自动重启。你可以用 React 写出一个应用，但没有 Kubernetes（或类似的运行时），这个应用很难在大规模生产中存活。

### LangGraph 作为运行时

LangGraph 被设计为生产级 Agent 运行时 (Production-Ready Agent Runtime)。它与传统运行时（如 Temporal、Inngest）的定位最为接近，但专门针对 Agent 场景做了优化：

| 传统运行时 | Agent 运行时 (LangGraph) |
|-----------|------------------------|
| 持久执行工作流 | 持久执行 Agent 循环 |
| 任务编排 | Agent 编排 + 子 Agent 调度 |
| 状态管理 | Agent 状态 + 对话历史 + 记忆 |
| 重试策略 | 重试 + 人机协作中断 |

> **为什么重要**  
> 运行时是框架与生产之间的桥梁。你可以用任何框架写 Agent，但要让 Agent 在崩溃后自动恢复、在关键节点暂停等待人类审批、在多用户场景下隔离状态——这些能力只能由运行时提供。LangChain 1.0 就是构建在 LangGraph 运行时之上的，这体现了"运行时为框架提供动力"的设计思路。

## 四、第三层：Agent 线束 (Agent Harnesses)

### 线束做什么？

线束在框架之上再加一层——**默认的提示词、默认的工具集、开箱即用的体验**。

```
┌─────────────────────────────────────────────────────┐
│                 Agent 线束的层级关系                    │
│                                                     │
│   ┌───────────────────────────────────────────────┐ │
│   │            线束 (Harness)                      │ │
│   │                                               │ │
│   │  默认提示词 + 默认工具 + 默认行为                 │ │
│   │  "拿来就能干活"                                 │ │
│   │                                               │ │
│   │   ┌───────────────────────────────────────┐   │ │
│   │   │         框架 (Framework)                │   │ │
│   │   │                                       │   │ │
│   │   │  抽象 + Agent 循环 + 中间件              │   │ │
│   │   │  "帮你写代码"                           │   │ │
│   │   │                                       │   │ │
│   │   │   ┌───────────────────────────────┐   │   │ │
│   │   │   │      运行时 (Runtime)           │   │   │ │
│   │   │   │                               │   │   │ │
│   │   │   │  持久执行 + 记忆 + 人机协作      │   │   │ │
│   │   │   │  "让它活着"                     │   │   │ │
│   │   │   └───────────────────────────────┘   │   │ │
│   │   └───────────────────────────────────────┘   │ │
│   └───────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

### 框架 vs. 线束的关键区别

| 维度 | 框架 (Framework) | 线束 (Harness) |
|------|-----------------|----------------|
| 目标用户 | 开发者 | 终端用户 / 快速启动的开发者 |
| 交付物 | 库 / SDK | 可运行的产品 |
| 提示词 | 无（开发者自己写） | 有默认提示词 |
| 工具集 | 提供工具定义的抽象 | 预装了具体工具 |
| 使用方式 | `import` 后编程 | 安装后直接使用 |
| 类比 | 买一套厨具 | 买一个预制菜套餐 |

### 主要玩家

| 线束 | 构建基础 | 说明 |
|------|----------|------|
| **Deep Agents** | 构建在 LangChain 之上 | 通用型 Agent 线束，可以看作"Claude Code 的开源通用版" |
| **Claude Code** | Claude Agent SDK | Anthropic 的编程 Agent，同时也在尝试成为线束平台 |
| **各类编码 CLI** | 各异 | Cursor Agent、Windsurf 等编码 CLI 本质上都是线束 |

> **类比理解**  
> 如果框架是 Django（一套 Web 开发框架），那么线束就是 WordPress（一个开箱即用的博客系统）。WordPress 底层用的就是 PHP 生态的各种框架和库，但用户不需要了解这些——安装后就能发布内容。同理，线束的用户不需要了解底层的框架和运行时——启动后就能让 Agent 干活。

> **为什么重要**  
> 线束代表了 Agent 生态的一个重要趋势：**从"帮你构建 Agent"到"直接给你一个能用的 Agent"**。这不仅降低了使用门槛，也定义了一个新的产品品类。所有编码 CLI（Claude Code、Cursor、Windsurf 等）都可以被理解为特定领域（编程）的 Agent 线束。

## 五、三层关系全景

### 依赖关系

```
线束 (Harness)
  │  构建在框架之上
  ▼
框架 (Framework)
  │  可以构建在运行时之上
  ▼
运行时 (Runtime)
```

### 具体案例

```
Deep Agents (线束)
  │
  ├─→ LangChain (框架)     ──→  LangGraph (运行时)
  │
  └─→ 默认提示词 + 默认工具 + 默认行为

Claude Code (线束)
  │
  ├─→ Claude Agent SDK (框架)
  │
  └─→ 系统提示 + Bash/文件/浏览器工具 + 安全沙箱

LangChain 1.0 (框架)
  │
  └─→ LangGraph (运行时)
```

### 边界是模糊的

这是一个早期领域，三层之间的边界并不清晰：

| 案例 | 身份模糊之处 |
|------|------------|
| **LangGraph** | 同时是运行时（持久执行、检查点）和框架（图编排、状态管理） |
| **Claude Code** | 既是一个产品（线束），也在通过 Claude Agent SDK 试图成为构建其他线束的框架 |
| **OpenAI Agents SDK** | 名义上是框架，但内置了 Tracing、Guardrails 等运行时特征 |

> **为什么重要**  
> "Agent 线束 (Agent Harness)"作为一个术语本身就是新的。这个分类体系不是最终定论，而是当前阶段帮助我们理清思路的心智模型 (Mental Model)。随着行业演进，这些边界可能会进一步移动、合并或重新定义。

## 六、如何选择？

### 决策树

```
你的目标是什么？
│
├─ "我想直接用一个能干活的 Agent"
│   └─→ 选择线束 (Harness)
│       Deep Agents / Claude Code / 编码 CLI
│
├─ "我想构建自己的 Agent，有定制需求"
│   └─→ 选择框架 (Framework)
│       LangChain / Vercel AI SDK / CrewAI / OpenAI Agents SDK
│
└─ "我的 Agent 需要在生产环境稳定运行"
    └─→ 确保有运行时 (Runtime)
        LangGraph / Temporal / Inngest
```

### 组合使用

三层并不互斥。一个生产级 Agent 系统通常需要所有三层的能力：

```
用户请求 ──→ 线束接收请求
              │
              ├─ 线束的默认提示词 + 工具集定义任务边界
              │
              ├─ 框架的抽象处理工具调用、输出解析、中间件
              │
              └─ 运行时确保持久执行、崩溃恢复、状态管理
```

## 延伸思考

1. **线束会吞噬框架吗？** 如果线束越来越强大、越来越可定制，开发者还需要直接使用框架吗？还是说框架会退化为线束的内部实现细节？
2. **通用线束 vs. 领域线束：** 当前的线束主要围绕编程任务。对于客服、数据分析、科学研究等领域，是否会出现各自的专用线束？还是一个通用线束足以覆盖所有场景？
3. **运行时的标准化：** 如果运行时负责 Agent 的"生存"问题，那么不同运行时之间是否需要标准接口？Agent 能否在不同运行时之间无缝迁移？
4. **三层分化的终局是什么？** 是保持分化（各做各的），还是走向垂直整合（一家公司通吃三层）？Web 生态的历史（前端框架 + 部署平台 + CDN）能给我们什么启示？
