# 评估技能 (Skills)：用评估驱动 Agent 提示工程的改进闭环

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/evaluating-skills)  
**日期:** 2026 年 3 月 5 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> 技能 (Skills) 本质上是动态加载的提示 (Prompt)，和所有提示一样，它们需要严格的评估才能证明自己有效。通过"无技能 vs 有技能"的对照实验，一组编码任务的完成率从 9% 跃升至 82% —— 但这个数字不是终点，而是可观测性 (Observability) + 评估 (Evaluation) 迭代闭环的起点。

---

## 核心要点

1. **技能 = 动态加载的提示** —— 和任何提示一样，技能必须经过测试才能上线。直觉上"应该有用"的技能，可能在实际运行中毫无帮助甚至适得其反
2. **对照实验是黄金标准** —— 同一组任务，分别在"无技能"和"有技能"条件下运行 Agent，比较完成率、调用轮次、耗时等指标
3. **干净的测试环境是前提** —— 编码 Agent 会修改文件系统，每次测试必须从干净状态开始，否则测量的不是技能效果而是环境污染
4. **迭代的粒度是段落，不是字词** —— 对于 300-500 行的大型技能文件，逐字打磨格式的收益极低；按段落级别调整内容结构才能产生可测量的差异
5. **可观测性是迭代的眼睛** —— 没有 Trace 级别的执行记录，你无法回答"技能为什么没起作用"，也就无法有针对性地改进

---

## 一、为什么技能需要评估？

### 技能不是"写完就完"的文档

技能 (Skills) 是动态加载到 Agent 上下文中的提示文件（详见文章 15《用技能武装深度 Agent》）。它们告诉 Agent 在特定场景下应该如何行动 —— 用哪些工具、按什么步骤、注意什么边界。

但一个关键事实经常被忽视：**技能就是提示，提示需要测试。**

```
技能的本质
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  技能文件 (SKILL.md)
       │
       ▼
  动态注入到系统提示 / 上下文
       │
       ▼
  影响 Agent 的推理和行为
       │
       ▼
  = 提示工程 (Prompt Engineering)
       │
       ▼
  所有提示工程都需要评估

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 技能就像新员工入职时收到的操作手册。你不会写完手册就直接下发 —— 你会让几个人试用，观察他们按手册操作时是否真的更高效，有没有步骤写得不清楚导致执行偏差。技能评估做的就是这件事：让 Agent "试用"技能，测量效果，再修订。

## 三、Step 1：搭建干净的测试环境

### 问题：编码 Agent 对起始条件极度敏感

编码 Agent (Coding Agent) 不是无状态的 API 调用 —— 它会读写文件、安装依赖、执行脚本。如果上一次测试的残留物还在，下一次测试的结果就不可信。

```
环境污染的影响
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  干净环境:                      污染环境:
  ┌────────────────────┐        ┌────────────────────┐
  │  空白项目目录        │        │  上一次测试残留:      │
  │  标准依赖            │        │    node_modules/    │
  │  无缓存              │        │    .cache/          │
  │                    │        │    已修改的配置文件     │
  │  Agent 行为 = 真实   │        │                    │
  │  测量 = 有效         │        │  Agent 行为 = 受干扰  │
  └────────────────────┘        │  测量 = 不可信        │
                                └────────────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 解决方案：容器化脚手架

每次测试都在一个全新的 Docker 容器中运行，保证：

| 需求 | 实现方式 |
|------|---------|
| **隔离性 (Isolation)** | 每次测试启动新容器，测试结束后销毁 |
| **可复现性 (Reproducibility)** | 相同的镜像 = 相同的起始状态 |
| **安全性 (Safety)** | Agent 的文件系统操作限制在容器内 |

可选替代方案包括 Harbor（LangChain 的评估编排框架）和各类云端沙箱服务 (E2B, Modal 等)。

> **为什么重要**  
> 如果测试环境不干净，你观察到的"技能提升了 10%"可能只是环境差异的噪声。干净环境是评估可信度的地基 —— 地基不牢，上面所有的数据分析都是空中楼阁。

## 四、Step 2：定义任务与指标

### 约束性任务优于开放式任务

评估技能时，任务设计决定了信号质量。关键原则：**约束性任务 (Constrained Tasks) 远优于开放式任务 (Open-ended Tasks)。**

| 任务类型 | 示例 | 评估信号质量 |
|---------|------|-------------|
| **约束性** | 修复一段有已知 Bug 的代码 | 高 —— 结果可自动验证 |
| **约束性** | 按规格实现一个具体函数 | 高 —— 测试用例给出明确的通过/失败 |
| **开放式** | "写一个 Web 应用" | 低 —— 什么算"好"？无法自动判断 |
| **开放式** | "优化这段代码的性能" | 中 —— 可测量但标准模糊 |

> **类比理解**  
> 就像考试出题："把这个有语法错误的句子改正确"比"写一篇关于春天的作文"更容易客观评分。约束性任务给你明确的对/错信号，开放式任务给你的只是"看起来还行"的模糊感觉。

### 四维度指标体系

不要只看"任务完成了没有"。一个完整的技能评估需要四个维度：

```
技能评估指标体系
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  指标 1: 技能是否被调用？(Skill Invoked?)
  ────────────────────────────────────────
  Agent 遇到对应场景时，是否真的发现并加载了技能？
  如果技能从未被调用，后面的指标都没有意义。

  指标 2: 任务是否完成？(Task Accomplished?)
  ────────────────────────────────────────
  加载技能后，Agent 是否成功完成了任务？
  这是最核心的效果指标。

  指标 3: 消耗了多少轮次？(Turns Taken?)
  ────────────────────────────────────────
  完成任务用了多少次工具调用？
  技能应该让 Agent 更高效，而不是增加无意义的步骤。

  指标 4: 实际耗时？(Real-time Duration?)
  ────────────────────────────────────────
  端到端消耗了多少时间？
  包括模型推理时间和工具执行时间。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 不要过度追求难度

一个常见的陷阱是为了"挑战" Agent 而设计过于困难的任务。但评估的目标不是难倒 Agent，而是**测量技能的增量效果**。如果无技能和有技能的条件下 Agent 都做不出来，这个任务就没有提供任何关于技能效果的信号。

### 实测结果

在实际实验中，对照组与实验组的差异令人瞩目：

| 条件 | 任务完成率 |
|------|-----------|
| **无技能** (控制组) | 9% |
| **有技能** (实验组) | 82% |
| **增量效果** | +73 个百分点 |

9% 到 82% 的跃升表明：对于这组特定任务，技能不是"锦上添花"，而是"从不能到能"的质变。没有技能时 Agent 基本在盲目摸索，有了技能提供的结构化指引后，大部分任务都能顺利完成。

> **为什么重要**  
> 这个数字的意义不在于"82% 很高"，而在于**没有对照实验你永远不知道 82% 是技能的功劳还是任务本身简单**。9% 的基线证明了任务确实有难度，82% 的实验值才真正归因于技能的效果。

## 六、Step 3 的关键决策：技能设计

### AGENTS.md vs 技能文件

在定义技能时，首先要决定加载策略：

| 方式 | 加载时机 | 适用场景 | Token 成本 |
|------|---------|---------|-----------|
| **AGENTS.md** (预加载) | 每次会话开始自动加载 | 全局性规则，Agent 始终需要遵守 | 高 —— 始终占用上下文 |
| **技能文件** (按需加载) | 匹配触发条件时动态加载 | 特定场景的专项能力 | 低 —— 仅在需要时加载 |

### 一个大技能 vs 多个小技能

| 策略 | 优点 | 缺点 |
|------|------|------|
| **一个大技能** (300-500 行) | 上下文完整，Agent 不会遗漏关联信息 | 始终加载全部内容，Token 消耗大 |
| **多个小技能** (各 50-100 行) | 按需加载，Token 效率高 | Agent 可能漏掉需要组合使用的技能 |

### A/B 测试技能的局部修改

当你想测试技能中某个特定段落的效果时，使用 XML 标签包裹待测内容是一种实用技巧：

```xml
<!-- SKILL.md 中的 A/B 测试标记 -->

## 错误处理策略

<variant-a>
遇到编译错误时，先阅读完整的错误信息，
定位到具体的文件和行号，再尝试修复。
</variant-a>

<variant-b>
遇到编译错误时，先执行 `grep -r` 搜索相关的
类型定义和接口，理解上下文后再修复。
</variant-b>
```

通过在不同实验轮次中激活不同的变体，可以精确测量每个段落级修改的效果。

### 大型技能的迭代经验

对于 300-500 行的大型技能文件，LangChain 团队积累了一条关键经验：

> **小的格式调整（标点、缩进、措辞微调）对 Agent 行为几乎没有可测量的影响。真正产生差异的是段落级别的内容调整 —— 增删一整个步骤、重新组织执行顺序、调整条件判断的逻辑。**

```
迭代粒度与效果
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  字词级修改    "使用" → "利用"           效果: ≈ 0
  格式级修改    调整 Markdown 缩进         效果: ≈ 0
  段落级修改    重写"错误处理"步骤          效果: 可测量 ✓
  结构级修改    重新排列执行步骤顺序         效果: 显著 ✓✓

  结论: 迭代段落，不要打磨字词

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 七、Step 5：可观测性驱动的迭代闭环

### 为什么对比结果不够？

知道"有技能时完成率是 82%"只回答了"有没有用"。但要迭代改进，你还需要回答：

- 那 18% 失败的任务，失败在哪一步？
- 技能被调用了但任务仍然失败，是技能指令有误还是模型没跟对？
- 有些任务无技能也能完成，技能是否反而增加了不必要的步骤？

这些问题只能通过**执行轨迹 (Trace)** 级别的可观测性来回答。

### 用 LangSmith 实现对比分析

LangChain 使用 LangSmith 的 pytest 集成来实现评估的结构化对比：

```python
import pytest
from langsmith import test

# 每个测试用例在 LangSmith 中记录完整的执行轨迹
@test
def test_fix_type_error_with_skill():
    """
    测试: Agent 在加载 'typescript-debugging' 技能后，
    能否修复一个已知的 TypeScript 类型错误。

    预期: 技能被调用 → 正确定位错误 → 修复通过编译
    """
    # 设置干净的 Docker 环境
    env = create_clean_container(template="typescript-project")

    # 注入已知的 Bug
    env.inject_bug("type-mismatch-in-handler.patch")

    # 运行 Agent（加载技能）
    result = run_agent(
        env=env,
        task="修复 handler.ts 中的类型错误",
        skills=["typescript-debugging"],  # 加载目标技能
    )

    # 四维度断言
    assert result.skill_invoked("typescript-debugging")  # 技能是否被调用
    assert result.task_completed                          # 任务是否完成
    assert result.turns <= 5                              # 轮次是否合理
    assert result.duration_seconds <= 60                  # 耗时是否合理
```

### 闭环工作流：Trace → 诊断 → 修复 → 重跑

评估不是一次性的 —— 它是一个持续迭代的闭环：

```
可观测性驱动的迭代闭环
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌──────────┐     ┌────────────────┐     ┌──────────────┐
  │ 运行评估  │────→│ 查看 Trace      │────→│ 定位失败原因   │
  └──────────┘     │ (LangSmith)    │     │              │
       ▲           └────────────────┘     └──────┬───────┘
       │                                         │
       │           ┌────────────────┐             │
       │           │ 重跑评估       │             ▼
       └───────────│ 验证修复效果    │←────┌──────────────┐
                   └────────────────┘     │ 修改技能文件   │
                                          │ (段落级调整)   │
                                          └──────────────┘

  关键: 每次修改都要重跑评估，确保改进可测量

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

在 LangChain 的实践中，Claude Code 甚至使用了自己的 Tracing 技能来自动化这个闭环：

1. **Agent 检查自己的 Trace** —— 通过 Tracing 技能读取 LangSmith 中的执行轨迹
2. **自动总结问题** —— 识别失败模式（如"Agent 在第 3 步选错了工具"）
3. **人类提出修复方案** —— 基于总结，人类决定如何调整技能文件
4. **重跑验证** —— 修改后立即重跑评估，确认修复有效

> **为什么重要**  
> 没有可观测性的评估就像闭着眼睛射箭 —— 你知道有没有中靶，但不知道偏了多远、偏向哪个方向。Trace 级别的执行记录让你从"猜测为什么失败"变成"看到失败发生在哪一步"，将技能迭代从黑盒优化变成白盒调试。

## 八、实践启示

### 1. 永远先跑"无技能"基线

没有基线，你不知道 82% 是技能的功劳还是任务本身的简单。基线是归因的前提。

### 2. 隔离环境不是可选项

编码 Agent 的评估如果不在隔离容器中运行，所有数据都不可信。投资 Docker 或 Harbor 等沙箱方案是评估可信度的地基。

### 3. 任务设计决定信号质量

约束性任务（修复已知 Bug）比开放式任务（写个应用）提供更强的评估信号。难度要适中 —— 太简单则无技能也能通过，太难则有技能也做不出来，两种情况都不提供关于技能效果的信息。

### 4. 迭代段落，不要打磨字词

对于大型技能文件，格式微调的收益趋近于零。把时间花在"增删一个步骤"或"重新组织执行顺序"上，这些才是能被评估捕捉到的变化。

### 5. 可观测性 + 评估 = 技能迭代的引擎

评估告诉你"有没有用"，可观测性告诉你"为什么没用"。两者缺一不可。

## 延伸思考

1. **技能评估的成本与收益：** 每次评估都需要启动容器、运行 Agent、消耗模型 Token。当技能数量增长到数十甚至数百个时，全量评估的成本会迅速膨胀。是否需要一种"增量评估"机制 —— 只测试被修改的技能及其依赖？如何识别技能之间的依赖关系？
2. **9% vs 82% 背后的任务选择偏差：** 这组任务是否恰好是"没有指引就不会做、有了指引就一定会做"的类型？如果换一组更依赖推理能力而非流程知识的任务，技能的增量效果会缩小到多少？技能真正解决的是"知识缺口"还是"注意力分配"问题？
3. **自动化技能迭代的可能性：** 目前的闭环仍需人类在"修改技能文件"这一步做判断。如果让 Agent 读取自己的失败 Trace 并自动修改技能，是否会形成自我改进的飞轮？这种自我修改的收敛性和安全性如何保证？
4. **技能评估与模型版本的耦合：** 同一个技能在 Sonnet 上有效但在 Haiku 上无效，或在模型 A 的 v1 上有效但在 v2 上失效 —— 技能评估是否需要跨模型、跨版本运行？这会让评估矩阵爆炸式增长，如何取舍？
