# 用子 Agent 和技能构建多 Agent 应用 (Building Multi-Agent Applications with Deep Agents)

**作者:** LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/building-multi-agent-applications-with-deep-agents)  
**日期:** 2026 年 5 月  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 多 Agent 应用的两大构建基元是子 Agent (Subagent) 和技能 (Skill)：子 Agent 通过独立上下文窗口解决"上下文腐烂"问题，适合复杂多步骤工作；技能通过渐进式披露 (Progressive Disclosure) 提供可复用的标准操作规程，适合跨 Agent 共享流程知识。两者可以组合使用，构建既深度又灵活的多 Agent 系统。

---

## 核心要点

1. **子 Agent 是上下文隔离的利器** —— 主 Agent 只接收最终结果，而非 20 次中间工具调用的全部痕迹，从根本上解决上下文膨胀 (Context Bloat) / 上下文腐烂 (Context Rot)
2. **通用子 Agent 是最被低估的模式** —— 不需要专门定制，仅靠上下文隔离就能显著提升主 Agent 的推理质量
3. **技能 = 文件夹 + SKILL.md** —— 遵循 agentskills.io 规范，Agent 启动时只加载名称和描述，按需读取完整指令
4. **子 Agent vs 技能不是二选一** —— 技能定义"怎么做"，子 Agent 负责"在隔离环境中做"，组合使用效果最佳
5. **最小工具集原则** —— 子 Agent 的工具越精简，执行越聚焦，错误率越低

---

## 一、问题：上下文腐烂

### 当主 Agent 的上下文窗口变成垃圾场

深度 Agent 在执行复杂任务时，上下文窗口会快速累积大量中间信息——搜索结果、文件内容、调试日志、工具调用的返回值。这些信息在产生时有用，但随着任务推进，它们变成了"噪声"，稀释了真正重要的上下文。

```
上下文腐烂 (Context Rot) 的形成过程

步骤 1:  [用户指令] [搜索结果]
步骤 5:  [用户指令] [搜索结果] [文件A内容] [调试输出] [文件B内容]
步骤 10: [用户指令] [搜索结果] [文件A] [调试] [文件B] [API响应]
         [测试日志] [错误追踪] [文件C] [中间计算]...
         ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
         上下文窗口已被低价值的中间结果填满
         模型开始"忘记"最初的任务目标  ← 这就是"笨区"(Dumb Zone)
```

> **类比理解**  
> 想象一个项目经理让工程师去调研一个技术方案。如果工程师把每一次 Google 搜索的结果、每一个打开又关掉的网页、每一次编译报错都实时发到项目经理的聊天窗口里，项目经理的注意力很快就被淹没了。他需要的只是最终的调研结论——一份清晰的技术方案对比。这就是子 Agent 要解决的问题。

> **为什么重要**  
> 上下文窗口不是无限的，即使有上下文压缩 (Compaction)，信噪比的下降也会直接导致模型推理质量退化。**上下文腐烂不是"慢"的问题，是"蠢"的问题**——Agent 做出低质量决策，不是因为能力不足，而是因为关键信息被噪声淹没了。

## 二、子 Agent：隔离的工作者

### 核心机制

子 Agent 拥有独立的上下文窗口。主 Agent 派发任务，子 Agent 在自己的上下文中执行所有中间步骤，最终只将结果返回给主 Agent。

```
无子 Agent（所有中间步骤污染主上下文）:

┌────────────────────────────────────────────────────┐
│  主 Agent 上下文窗口                                 │
│                                                    │
│  [用户指令]                                         │
│  [工具调用 1: 搜索] → [搜索结果 3000 tokens]          │
│  [工具调用 2: 读文件] → [文件内容 2000 tokens]        │
│  [工具调用 3: 搜索] → [搜索结果 2500 tokens]          │
│  [工具调用 4: 读文件] → [文件内容 1500 tokens]        │
│  ... 重复 20 次 ...                                 │
│  [最终结论: 200 tokens]                              │
│                                                    │
│  总计: ~20,000+ tokens 的中间噪声 + 200 tokens 有效信息│
└────────────────────────────────────────────────────┘

有子 Agent（中间步骤隔离在子上下文中）:

┌─────────────────────────┐     ┌───────────────────────┐
│  主 Agent 上下文窗口      │     │  子 Agent 上下文窗口    │
│                         │     │  (独立、隔离)           │
│  [用户指令]              │     │                       │
│  [派发任务给子 Agent]     │────▶│  [工具调用 1: 搜索]     │
│                         │     │  [工具调用 2: 读文件]   │
│  ... 主 Agent 继续工作 ...│     │  ... 20 次中间步骤 ... │
│                         │     │                       │
│  [子 Agent 返回: 结论]   │◀────│  [返回: 最终结论]      │
│  (仅 200 tokens)        │     │                       │
└─────────────────────────┘     └───────────────────────┘
```

### 四大使用场景

| 场景 | 说明 | 示例 |
|------|------|------|
| **上下文保护** (Context Preservation) | 防止中间步骤污染主上下文 | 研究型任务：搜索 → 阅读 → 摘要，主 Agent 只需要摘要 |
| **专业化** (Specialization) | 为特定任务定制系统提示和工具集 | SQL 子 Agent 只有数据库工具，代码审查子 Agent 只有文件读取工具 |
| **多模型** (Multi-model) | 不同子 Agent 使用不同模型 | 便宜的模型做数据清洗，强模型做推理决策 |
| **并行化** (Parallelization) | 多个子 Agent 同时执行独立任务 | 同时调研 3 个竞品，分别由 3 个子 Agent 处理 |

### 创建子 Agent

子 Agent 通过字典配置定义，传给 `create_deep_agent()` 使用：

```python
from deepagents import create_deep_agent

# 定义一个专门做代码搜索的子 Agent
code_searcher = {
    "name": "code_searcher",
    "description": "在代码库中搜索相关文件、函数和模式",  # 主 Agent 根据描述决定何时调用
    "system_prompt": """你是一个代码搜索专家。
    - 使用 grep 和 find 工具定位相关代码
    - 返回文件路径、函数签名和关键代码片段
    - 不要返回完整文件内容，只返回与查询相关的部分""",
    "tools": ["bash", "read_file"],  # 最小工具集：只给需要的
    "model": "anthropic:claude-sonnet-4-6",  # 可以用更便宜的模型
}

# 定义一个做代码审查的子 Agent
code_reviewer = {
    "name": "code_reviewer",
    "description": "审查代码变更，检查潜在 bug 和风格问题",
    "system_prompt": """你是一个严格的代码审查者。
    - 检查逻辑错误、边界条件、类型安全
    - 对照项目编码规范检查风格
    - 输出结构化的审查报告""",
    "tools": ["bash", "read_file"],
    "model": "anthropic:claude-sonnet-4-6",
}

# 创建主 Agent，配备两个专项子 Agent
agent = create_deep_agent(
    model="anthropic:claude-opus-4-6",
    subagents=[code_searcher, code_reviewer],
)
```

### 通用子 Agent：最被低估的模式

不是所有场景都需要专门定制的子 Agent。`deepagents` 内置了**通用子 Agent** (General-purpose Subagent)——它完全镜像主 Agent 的能力，唯一的区别是拥有独立的上下文窗口。

```
通用子 Agent 的价值

┌────────────────────────────────────────────────────────────┐
│  问题: 主 Agent 需要完成一个耗费大量上下文的子任务，         │
│        但不想让中间步骤污染自己的上下文                      │
│                                                            │
│  方案 A: 定制子 Agent                                      │
│  ✅ 定制提示和工具集                                        │
│  ❌ 需要提前预判任务类型，编写专门配置                       │
│                                                            │
│  方案 B: 通用子 Agent    ← 往往是更好的默认选择              │
│  ✅ 零配置，开箱即用                                        │
│  ✅ 与主 Agent 能力完全一致                                 │
│  ✅ 纯粹的上下文隔离——不需要专业化也能获益                   │
│  ❌ 没有针对性优化                                          │
└────────────────────────────────────────────────────────────┘
```

> **类比理解**  
> 通用子 Agent 像项目经理派出的"另一个自己"。不是找一个专科医生（专项子 Agent），而是克隆一个全科医生（通用子 Agent），让他在独立的诊室里看完病人，只把诊断结论带回来。关键不在于"更专业"，而在于"不污染"。

### 子 Agent 设计最佳实践

| 原则 | 说明 | 反面教材 |
|------|------|---------|
| **描述要精确** | 主 Agent 根据描述决定何时调用，模糊描述导致误调用或漏调用 | `"一个有用的助手"` — 太泛，主 Agent 不知道何时该用 |
| **系统提示要详尽** | 包含输入输出格式、约束条件、少样本示例 | `"搜索代码"` — 没有告诉子 Agent 该返回什么格式 |
| **工具集要最小化** | 只给子 Agent 完成任务所需的工具，减少选择噪声 | 把所有 30 个工具都给子 Agent — 违背了隔离的初衷 |

## 三、技能：渐进式披露的可复用流程

### 什么是技能？

技能 (Skill) 是遵循 [agentskills.io](https://agentskills.io) 规范的文件夹，核心是一个 `SKILL.md` 文件，采用 YAML 前言 (Frontmatter) + Markdown 正文的结构。

```
技能目录结构

~/.deepagents/agent/skills/
├── data-analysis/
│   ├── SKILL.md              ← YAML 前言 + Markdown 指令
│   ├── templates/
│   │   └── report.md
│   └── scripts/
│       └── clean_csv.py
├── deploy-fly/
│   ├── SKILL.md
│   └── deploy.sh
└── code-review/
    ├── SKILL.md
    └── checklist.md
```

### SKILL.md 的结构

```yaml
---
name: data-analysis
description: 对 CSV/JSON 数据集进行探索性分析并生成可视化报告
trigger: 当用户要求分析数据集、生成图表或数据洞察时
tools_required: [bash, read_file, write_file]
---

# 数据分析技能

## 执行步骤
1. 读取数据文件，检查格式和数据质量
2. 使用 pandas 进行探索性分析（缺失值、分布、相关性）
3. 生成关键指标的可视化图表
4. 输出结构化分析报告

## 输出格式
- Markdown 报告，包含内嵌图表路径
- 每个发现标注置信度
```

### 渐进式披露：Token 效率的关键

技能的精髓在于**Agent 启动时只加载 YAML 前言（名称和描述），按需读取完整指令**：

```
Agent 启动时加载的内容:

┌─────────────────────────────────────────────────────────────┐
│  系统提示中注入的技能摘要                                     │
│                                                             │
│  技能 1: data-analysis                                      │
│    "对 CSV/JSON 数据集进行探索性分析并生成可视化报告"            │
│    (~25 tokens)                                             │
│                                                             │
│  技能 2: deploy-fly                                         │
│    "将应用部署到 Fly.io 平台"                                │
│    (~15 tokens)                                             │
│                                                             │
│  技能 3: code-review                                        │
│    "按照团队规范审查代码变更"                                  │
│    (~15 tokens)                                             │
│                                                             │
│  总计: ~55 tokens (而非 3 × ~200 = 600 tokens 的完整定义)    │
└─────────────────────────────────────────────────────────────┘
                              │
                    用户说 "分析这个 CSV"
                              │
                              ▼
              Agent 读取 data-analysis/SKILL.md 的完整内容
              (~200 tokens, 仅在此刻加载)
```

> **类比理解**  
> 渐进式披露就像一本操作手册的"目录 + 正文"分离。你不会把所有章节同时摊开在桌上（占满桌面），而是先看目录（YAML 前言）找到需要的章节，再翻到那一页（完整 SKILL.md）。看完后合上放回书架（从活跃上下文中卸载）。

### 添加技能到 Deep Agent

```python
from deepagents import create_deep_agent

# 通过 skills 参数指定技能目录
agent = create_deep_agent(
    model="anthropic:claude-opus-4-6",
    skills="./skills",  # 指向技能文件夹的路径
)

# Agent 启动时自动扫描目录，加载所有 SKILL.md 的 YAML 前言
# 用户触发相关任务时，Agent 按需读取完整指令
```

## 四、子 Agent vs 技能：如何选择？

| 需求 | 推荐方案 | 原因 |
|------|---------|------|
| 复杂多步骤工作 | **子 Agent** | 需要独立上下文窗口隔离中间步骤 |
| 可复用的标准操作流程 | **技能** | 纯文件，易于版本控制和跨 Agent 共享 |
| 需要专门工具集的任务 | **子 Agent + 定制工具** | 子 Agent 可以配备不同于主 Agent 的工具 |
| 跨 Agent / 跨团队共享知识 | **技能** | 只是文件，`cp -r` 即可复用 |
| Agent 拥有大量能力但不想撑爆上下文 | **技能** | 渐进式披露按需加载，避免 Token 膨胀 |
| 需要使用不同模型 | **子 Agent** | 每个子 Agent 可以指定独立的模型 |

### 组合使用：技能定义流程，子 Agent 执行工作

子 Agent 和技能不是互斥的——最强大的模式是**组合使用**：

```
组合模式: 技能 + 子 Agent

┌──────────────────────────────────────────────────────┐
│  主 Agent                                             │
│                                                      │
│  1. 接到用户任务: "部署新版本并验证"                     │
│                                                      │
│  2. 匹配到技能: deploy-and-verify                     │
│     └─ 读取 SKILL.md，获取标准部署流程                  │
│        步骤 a: 运行测试                                │
│        步骤 b: 构建镜像                                │
│        步骤 c: 部署到 staging                          │
│        步骤 d: 运行冒烟测试                             │
│        步骤 e: 部署到 production                       │
│                                                      │
│  3. 将步骤 a-c 派发给子 Agent (独立上下文)              │
│     ┌──────────────────────────────┐                 │
│     │  子 Agent: deploy-worker     │                 │
│     │  执行构建、测试、部署          │                 │
│     │  20+ 次工具调用              │                 │
│     │  返回: "staging 部署成功"     │                 │
│     └──────────────────────────────┘                 │
│                                                      │
│  4. 主 Agent 上下文保持清洁，继续步骤 d-e               │
└──────────────────────────────────────────────────────┘

技能提供了"做什么"和"怎么做"的知识
子 Agent 提供了"在隔离环境中做"的能力
```

> **为什么重要**  
> 单独使用技能，你得到了可复用的流程知识，但中间步骤仍会污染主上下文。单独使用子 Agent，你得到了上下文隔离，但缺乏标准化的操作流程。**两者组合，才是多 Agent 应用的完整解**。

## 五、设计启示

### 1. 上下文质量 > 上下文数量

子 Agent 模式的核心洞察：**不是给模型更多上下文，而是给模型更干净的上下文**。20 次中间工具调用的结果可能有 20,000 tokens，但对主 Agent 的决策有用的可能只有 200 tokens 的最终结论。子 Agent 做的就是这个"蒸馏"。

### 2. 默认选择通用子 Agent

在不确定是否需要专项子 Agent 时，先用通用子 Agent。仅靠上下文隔离这一个特性，就能带来显著收益。只有当你观察到通用子 Agent 在特定任务上持续犯错时，再考虑添加定制化的系统提示和专项工具。

### 3. 技能是 Agent 的"组织记忆"

技能将团队的最佳实践从个人经验固化为文件系统中的标准操作规程。新加入的 Agent（或新配置的实例）可以立即获得团队积累的所有流程知识——这就是知识管理在 Agent 时代的落地形式。

### 4. 少即是多

子 Agent 的工具集应该尽可能小。给一个代码搜索子 Agent 配备文件编辑工具，不仅浪费 Token，还可能导致它在搜索过程中"顺手"做出不期望的修改。**工具越少，行为越可预测。**

## 延伸思考

1. **子 Agent 的嵌套深度：** 子 Agent 是否可以再派生子 Agent？理论上可以，但嵌套过深会带来延迟累积和调试噩梦。是否存在一个"最优嵌套深度"的经验法则？两层（主 Agent → 子 Agent）是否已经覆盖了绝大多数场景？

2. **技能的版本管理：** 当一个技能的执行流程发生变化（比如部署平台升级了 API），如何确保所有使用该技能的 Agent 都能感知到更新？是否需要技能版本号和兼容性检查？

3. **通用子 Agent 的经济学：** 通用子 Agent 的 Token 成本高于直接在主 Agent 中执行（因为子 Agent 也需要加载系统提示）。在什么任务复杂度阈值之上，上下文隔离带来的质量收益才能抵消额外的 Token 开销？

4. **动态子 Agent 生成：** 主 Agent 是否应该在运行时根据任务特征动态决定子 Agent 的配置（模型、工具集、提示词），而非依赖预定义的静态配置？这样做的灵活性收益是否值得引入的复杂性？
