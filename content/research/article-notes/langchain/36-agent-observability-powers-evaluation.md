# Agent 可观测性驱动 Agent 评估 (Agent Observability Powers Agent Evaluation)

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/agent-observability-powers-evaluation)  
**日期:** 2026 年 1 月 28 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 不理解 Agent 如何推理，就无法构建可靠的 Agent。可观测性 (Observability) 与评估 (Evaluation) 不是两个独立系统——它们共享同一套数据基底，必须从第一天就一起建设。

## 核心要点

1. **Agent 可观测性 ≠ 传统软件可观测性** —— 传统软件是确定性的，代码即行为；Agent 是非确定性的，行为在运行时涌现，调试对象从"代码路径"变成了"推理路径"
2. **Agent 评估 ≠ 传统软件测试** —— 你测试的不是代码逻辑，而是推理质量；评估分三个层级：单步决策、完整轮次、多轮对话
3. **三个可观测性原语** —— Run (单次执行步骤)、Trace (完整执行轨迹)、Thread (多轮会话) 与三级评估精确对应
4. **生产环境是最好的老师** —— 大多数 Agent 故障只在生产中暴露，追踪数据既是调试工具也是评估数据集的来源
5. **从第一天就同时建设追踪 + 评估的团队，交付的 Agent 才能真正工作**

## 一、Agent 可观测性 ≠ 传统软件可观测性

### 确定性 vs. 非确定性

传统软件可观测性的基本假设是：**代码是行为的权威来源**。你读代码就能知道应用做了什么——如果函数 A 调用了函数 B，那它每次都会调用函数 B。

Agent 系统彻底打破了这个假设。

> **类比理解**  
> 传统软件像一条铁轨——列车每次经过同样的站点、同样的路径，你只需要检查铁轨本身就能预测列车的行为。Agent 更像一个出租车司机——虽然他知道所有可能的路线（工具和能力），但每次载客时走哪条路、在哪里转弯，取决于当时的路况、乘客的要求、甚至他自己的判断。你必须看 GPS 行车记录（追踪），而不是看地图（代码），才能知道他实际做了什么。

| 维度 | 传统软件 | Agent 系统 |
|------|---------|-----------|
| 行为来源 | 代码 (确定性) | 运行时推理 (非确定性) |
| 调试对象 | 代码路径 (Code Path) | 推理路径 (Reasoning Path) |
| 典型问题 | "为什么函数 X 返回了 null？" | "为什么 Agent 在第 23 步调用了 edit_file 而不是 read_file？" |
| 可复现性 | 高——相同输入必然产生相同输出 | 低——相同输入可能产生不同决策序列 |
| 错误定位 | 堆栈追踪 (Stack Trace) | 决策追踪 (Decision Trace) |

```
传统软件调试                        Agent 系统调试
━━━━━━━━━━━━━━━━━                  ━━━━━━━━━━━━━━━━━
  读代码                              读追踪
    │                                   │
    ▼                                   ▼
  找到出错的函数                       找到出错的决策步骤
    │                                   │
    ▼                                   ▼
  修改代码                             修改 prompt / 工具 / 约束
    │                                   │
    ▼                                   ▼
  测试通过 ✅                          但下次可能走不同的路径 ⚠️
```

> **为什么重要：** 如果你还在用传统软件可观测性的思路来监控 Agent——只看错误率、延迟、吞吐量——你会漏掉 Agent 最核心的问题：**推理质量**。Agent 可以在不触发任何异常的情况下做出完全错误的决策。

## 二、Agent 评估 ≠ 传统软件测试

### 测试推理，而非测试代码

传统软件测试的对象是**代码路径**——给定输入 X，函数应该返回 Y。测试通过意味着代码逻辑正确。

Agent 评估的对象是**推理质量**——不是"代码能不能跑"，而是"Agent 做了正确的决定吗？"

```
传统软件测试                        Agent 评估
━━━━━━━━━━━━━━━━━━━                ━━━━━━━━━━━━━━━━━━━
                                   
  assert add(2, 3) == 5             Agent 选对了工具吗？
                                    Agent 传对了参数吗？
  输入确定 → 输出确定                Agent 的推理链合理吗？
  ✅ 或 ❌，没有灰色地带             任务最终完成了吗？
                                    多轮对话中上下文维持住了吗？
```

### 三级评估体系

Agent 评估不是"跑一遍、看结果"这么简单。推理行为需要在三个层级上分别检验：

| 层级 | 评估问题 | 典型场景 |
|------|---------|---------|
| **单步评估 (Single-Step)** | Agent 在这一步做了正确的决定吗？ | 收到用户请求后，Agent 选择调用 search_api 而非 edit_file——这个选择对吗？ |
| **完整轮次评估 (Full-Turn)** | Agent 正确地完成了整个任务吗？ | 用户要求修复 bug，Agent 经过 15 步操作后提交了 fix——bug 真的修好了吗？ |
| **多轮评估 (Multi-Turn)** | Agent 在多轮对话中维持了上下文吗？ | 用户在第三轮修改了需求，Agent 是否正确理解了变更并调整了行为？ |

```
三级评估体系
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  单步评估          完整轮次评估         多轮评估
  ──────           ────────           ──────
  这一步对吗？      整个任务完成了吗？   上下文维持住了吗？

  ┌───┐            ┌───────────┐      ┌─────────────────┐
  │ ● │            │ ●→●→●→●→● │      │ ●→●→●  对话 1   │
  └───┘            └───────────┘      │ ●→●→●  对话 2   │
                                      │ ●→●→●  对话 3   │
  检查单个           检查完整            └─────────────────┘
  决策点             执行序列            检查跨轮次一致性

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  粒度: 细 ──────────────────────────────→ 粗
  成本: 低 ──────────────────────────────→ 高
```

### 生产环境才是真正的考场

一个容易被忽视的事实：**大多数 Agent 故障只在生产环境中暴露。**

你可以在测试环境里验证 Agent 能正确处理 50 种预设场景，但第 51 种——那个你从未想过的边缘情况——只会在真实用户触发时出现。这意味着生产环境不仅仅是"部署的地方"，更是 Agent 最重要的学习来源。

> **为什么重要：** 如果你的评估体系只有离线测试，没有生产追踪，你就像一个只在考试中学习却从不去实习的学生——你在模拟环境中得了高分，但到了真实世界却处处碰壁。

## 三、三个可观测性原语

LangChain 定义了三个核心可观测性原语 (Observability Primitives)，它们是理解 Agent 行为的最小构建块：

### 1. Run (运行)：单次执行步骤

一个 Run 代表 Agent 执行过程中的**一个原子步骤**——一次 LLM 调用加上相关的输入/输出。

```
Run 示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  输入: "用户说: 帮我查一下这个 bug"
    │
    ▼
  LLM 推理
    │
    ▼
  输出: 决定调用 read_file("main.py")
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  一个 Run = 一次决策 + 对应的 I/O
```

### 2. Trace (追踪)：完整执行轨迹

一个 Trace 是**所有 Run 的有序集合**，外加它们之间的父子关系和因果关系。它记录了 Agent 从收到任务到完成任务的完整推理路径。

```
Trace 示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Run 1: 读取用户请求 → 决定先搜索代码库
    │
    ├── Run 2: 搜索代码库 → 找到 3 个相关文件
    │     │
    │     ├── Run 3: 读取 file_a.py → 发现可疑逻辑
    │     └── Run 4: 读取 file_b.py → 无异常
    │
    ├── Run 5: 分析可疑逻辑 → 确认 bug 根因
    │
    └── Run 6: 修复 file_a.py → 提交修改
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  一个 Trace = 完整的执行轨迹 + Run 之间的关系
```

### 3. Thread (会话线程)：多轮对话容器

一个 Thread 将**多个 Trace 按时间顺序组织在一起**，代表一段持续的多轮对话。

```
Thread 示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  用户消息 1: "帮我查一下这个 bug"
    └── Trace 1: [Run 1 → Run 2 → ... → Run 6]

  用户消息 2: "修复方案看起来不对，能换一种思路吗？"
    └── Trace 2: [Run 7 → Run 8 → ... → Run 12]

  用户消息 3: "好的，请加上单元测试"
    └── Trace 3: [Run 13 → Run 14 → Run 15]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  一个 Thread = 多个 Trace 按对话轮次组织
```

### 原语与评估层级的精确映射

这三个可观测性原语不是随意设计的——它们与三级评估体系之间存在 **1:1 的映射关系**：

| 可观测性原语 | 评估层级 | 回答的问题 |
|-------------|---------|-----------|
| **Run** | 单步评估 (Single-Step) | 这一步的决策正确吗？ |
| **Trace** | 完整轮次评估 (Full-Turn) | 整个任务执行正确吗？ |
| **Thread** | 多轮评估 (Multi-Turn) | 跨轮次的上下文维持住了吗？ |

```
可观测性原语          评估层级
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Run    ◄──── 1:1 ────►  单步评估
    │                        │
    │  组成                   │  深入
    ▼                        ▼
  Trace  ◄──── 1:1 ────►  完整轮次评估
    │                        │
    │  组成                   │  深入
    ▼                        ▼
  Thread ◄──── 1:1 ────►  多轮评估

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  同一套数据，既用于可观测性，也用于评估
  这就是"可观测性驱动评估"的核心含义
```

> **为什么重要：** 这个映射关系意味着你**不需要为可观测性和评估分别建设两套数据管道**。追踪系统记录的数据天然就是评估系统的输入。这不仅降低了基础设施成本，更重要的是保证了"你调试的东西"和"你测试的东西"始终是同一个东西——没有脱节。

## 四、可观测性如何驱动评估

有了三个原语和它们与评估层级的映射关系，接下来的问题是：**具体怎么用追踪数据来驱动评估？**

### 路径一：Trace → 手动调试

最基本的用法：当 Agent 出错时，打开对应的 Trace，逐步检查每个 Run 的决策。

```
手动调试流程
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  用户报告: "Agent 修改了错误的文件"
    │
    ▼
  打开该次执行的 Trace
    │
    ▼
  逐步检查每个 Run:
    Run 1: 搜索代码库 ← 搜索词合理吗？
    Run 2: 读取文件   ← 读对了吗？
    Run 3: 分析代码   ← 分析正确吗？
    Run 4: 编辑文件   ← 改对了吗？ ← ❌ 这里出了问题
    │
    ▼
  定位到具体的决策失误点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 路径二：Trace → 离线评估数据集

这是追踪数据最有价值的用法：**将生产中发现的 bug 转化为永久性测试用例。**

```
从生产 bug 到评估用例的转化流程
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  1. 生产中发现 bug
     │
     ▼
  2. 提取失败时的 Trace
     │
     ▼
  3. 从 Trace 中提取关键状态:
     - 输入: Agent 当时收到了什么
     - 上下文: Agent 当时的记忆/历史
     - 环境: 文件系统、API 状态等
     │
     ▼
  4. 编写断言逻辑:
     - Agent 应该调用什么工具？
     - Agent 不应该调用什么工具？
     - 最终输出应该满足什么条件？
     │
     ▼
  5. 加入评估数据集
     │
     ▼
  6. 修复 Agent (修改 prompt / 工具 / 约束)
     │
     ▼
  7. 在评估数据集上验证修复
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  每一次生产故障都让评估集更厚实
  这就是"生产环境是最好的老师"的具体机制
```

> **类比理解**  
> 这个流程就像飞机的"黑匣子 → 安全改进"循环。每次飞行事故后，调查人员从黑匣子 (Trace) 中提取完整的飞行数据，分析出根因，然后将这个故障模式编入飞行员训练教材和飞机设计标准 (评估数据集)。航空业的安全记录之所以不断提升，正是因为每一次事故都被系统性地转化成了预防措施。

### 路径三：Trace → 轨迹检查

除了事后调试和构建评估集，追踪数据还可以用于**实时异常检测**——自动标记不寻常的工具调用模式。

```
轨迹检查 (Trajectory Check) 示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  正常模式:
    read_file → analyze → edit_file → run_tests
                                                
  异常模式 (被自动标记):
    edit_file → edit_file → edit_file → edit_file
    ▲
    Agent 在没有先读取/分析的情况下连续编辑文件
    这通常意味着它在盲目试错
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

典型的轨迹检查规则：

| 异常模式 | 可能问题 | 检测规则 |
|---------|---------|---------|
| 连续多次调用相同工具 | Agent 陷入循环 | 同一工具连续调用 > 3 次触发告警 |
| 跳过读取直接编辑 | 盲目修改，缺乏上下文 | edit_file 前未出现 read_file |
| 工具调用总数异常高 | Agent 迷失方向 | 单个 Trace 中 Run 数量超过阈值 |
| 出现未预期的工具调用 | Agent 误解了任务 | 调用了当前任务不应涉及的工具 |

### 统一基底

关键洞察：**上述三条路径使用的是同一套追踪数据。**

```
统一数据基底
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

                  追踪数据 (Traces)
                 ┌──────────────┐
                 │              │
                 │  Run + 关系   │
                 │  输入 / 输出  │
                 │  元数据       │
                 │              │
                 └──────┬───────┘
                        │
            ┌───────────┼───────────┐
            │           │           │
            ▼           ▼           ▼
       手动调试      离线评估      轨迹检查
       (Debug)     (Eval Dataset)  (Trajectory)
                        
       逐步检查      提取失败状态    自动标记
       决策链        构建测试用例    异常模式

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  一份追踪数据，三种用途
  这就是可观测性与评估"不可分割"的原因
```

> **为什么重要：** 很多团队把可观测性和评估当作两个独立项目来推进——一个团队建追踪系统，另一个团队建评估系统，两套数据互不连通。这不仅浪费资源，还会导致一个致命问题：你调试的故障场景无法自动转化为测试用例，导致同样的 bug 反复出现。统一数据基底让"调试 → 修复 → 验证"成为一个无缝闭环。

## 五、从第一天开始的正确做法

文章的核心主张可以浓缩为一句话：

> **从第一天就同时建设追踪和评估的团队，交付的 Agent 才能真正工作。**

为什么强调"从第一天"？因为追踪和评估之间存在**复利效应**——越早开始积累追踪数据，越早开始从生产故障中学习，评估数据集就越快变厚实，Agent 的可靠性就越快提升。

```
追踪 + 评估的复利效应
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  时间 →
  ────────────────────────────────────────────►

  第 1 周:  追踪上线，发现 5 个故障模式
            → 转化为 5 个评估用例

  第 2 周:  修复了 3 个，新发现 4 个
            → 评估集: 9 个用例

  第 1 月:  评估集: 30+ 用例
            → 开始自动检测常见的轨迹异常

  第 3 月:  评估集: 100+ 用例
            → 每次修改 Agent 前，自动跑完全部评估
            → 回归检测精度大幅提升

  第 6 月:  评估集成为 Agent 的"免疫系统"
            → 已知的故障模式不会再出现
            → 团队精力集中在新型故障上

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  起步越早，复利效应越强
```

反之，如果你等 Agent 上线三个月后才开始建追踪系统，这三个月里的所有生产故障——你本可以从中学习的宝贵数据——全部丢失了。

---

## 核心观点

> 可观测性告诉你 Agent 如何推理。评估告诉你推理是否正确。两者共享同一套数据——Run、Trace、Thread。把它们拆开建设是浪费，把它们合在一起才是正确的系统设计。**不理解 Agent 如何推理的团队，无法构建可靠的 Agent。**

---

## 延伸思考

1. **可观测性的粒度边界：** 追踪的粒度越细（记录每一步的中间状态），调试能力越强，但存储和性能开销也越大。在实践中，什么粒度是"刚好够用"的？如何根据 Agent 的复杂度动态调整追踪粒度，而不是一刀切？

2. **评估数据集的过拟合风险：** 从生产故障中构建评估集是好的，但评估集会逐渐偏向"已知的故障模式"。Agent 可能在评估集上得高分，却在全新的故障模式面前毫无防备。如何确保评估集的覆盖面不断拓宽，而不仅仅是不断加深已知场景？

3. **非确定性与评估的矛盾：** Agent 的非确定性意味着同一个输入可能产生不同的执行路径——今天通过评估不代表明天也能通过。如何设计评估体系来应对这种固有的不确定性？是多次运行取统计值，还是收紧 Agent 的行为空间来换取更高的可预测性？

4. **轨迹检查的规则爆炸：** 手动编写轨迹检查规则在 Agent 能力范围小的时候可行，但当 Agent 拥有数十个工具、处理数百种任务类型时，规则数量会爆炸。是否可以用 LLM 来自动学习"正常的工具调用模式"，从而自动标记异常？这又引入了"用 AI 监控 AI"的递归信任问题。
