# Agent 的规划与推理：让 AI 学会"想清楚再做"

**作者:** Harrison Chase  
**来源:** [LangChain Blog](https://blog.langchain.dev/planning-for-agents/)  
**日期:** 2024 年 7 月 20 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> Agent 要做好事情，光靠"聪明"不够，还得会"规划"。短期规划（下一步做什么）模型已经做得不错，但长期规划（完成整个任务的步骤序列）仍然很难——最有效的解决方案是由工程师为特定领域设计专门的认知架构。

---

## 核心要点

1. **规划 = LLM 思考该采取什么行动** —— 分为短期规划（下一步）和长期规划（整个任务路线）
2. **工具调用 (Function Calling) 是 Agent 行动的核心机制** —— 模型不是直接输出文字，而是选择调用哪个工具
3. **长期规划是当前 Agent 的最大瓶颈** —— 上下文越长，模型越容易"分心"
4. **通用认知架构理论上很美，实践中太泛** —— plan-and-solve、Reflexion 等方法缺乏针对性
5. **领域特定认知架构才是生产环境的最优解** —— 工程师用代码替 LLM 做规划，效果最好

---

## 一、什么是 Agent 的规划？

### 一个简单的定义

```
规划 = LLM 决定"接下来该做什么"
```

> **类比理解**  
> 想象你在做一道复杂的菜。"规划"就是你在脑子里想：先切菜还是先烧水？调料什么时候放？哪些步骤可以并行？规划能力的好坏，直接决定了你做菜的效率和结果。

### 两种规划

| 类型 | 含义 | 例子 | 难度 |
|------|------|------|------|
| 短期规划 | 决定下一步做什么 | "现在该查数据库了" | 模型已经做得不错 |
| 长期规划 | 规划完成整个任务的步骤序列 | "先搜集数据，再清洗，再分析，最后生成报告" | 仍然很难 |

短期规划是"走一步看一步"，长期规划是"先画地图再出发"。大多数 Agent 的问题出在后者。

---

## 二、工具调用：Agent 行动的双手

### 工具调用 (Function Calling) 是什么？

你可能以为 Agent 就是在"聊天"。其实不是。Agent 的核心能力是**选择并调用工具**。

> **类比理解**  
> 你是一个项目经理，手下有好几个专业团队：搜索团队、数据库团队、计算团队、写作团队。你的工作不是自己干活，而是**决定把任务分给谁**。这就是工具调用——Agent 选择调用哪个"团队"（工具）来完成当前步骤。

### 工具调用的流程

```
用户提问
   │
   ▼
┌─────────────┐
│  LLM 思考   │  ← "这个问题需要查数据库"
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  选择工具    │  ← 调用 query_database()
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  执行工具    │  ← 数据库返回结果
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  LLM 整合   │  ← 把结果组织成回答
└─────────────┘
```

现在的大模型（GPT-4、Claude 等）在**短期规划**——即"当前这一步该调用什么工具"——上已经做得相当好了。问题出在下一个层面。

---

## 三、长期规划：为什么这么难？

### 两个核心难点

**难点 1：同时想"远"和"近"**

长期规划要求模型在脑子里同时装两件事：远期目标（"最终要完成什么"）和近期动作（"现在该做什么"）。这对 LLM 来说非常困难。

> **类比理解**  
> 想象你在下棋。新手只能看到下一步该怎么走，高手能看到后面五六步。让 LLM 同时思考"全局战略"和"当前一步"，就像要求一个新手棋手瞬间变成高手一样难。

**难点 2：上下文越长，模型越"分心"**

现在的上下文窗口越来越大（128K、甚至 1M tokens）。你可能觉得这是好事——能装更多信息了。但实际上，**信息太多反而让模型难以抓住重点**。

> **类比理解**  
> 你在考试前复习。如果只有 10 页笔记，你能很快抓住重点。但如果给你 1000 页材料，你反而会迷失在细节里，忘了最初要解决什么问题。LLM 面对超长上下文时也是同样的困境。

---

## 四、怎么改善规划？三条路

### 路线一：确保 LLM 有足够信息

> **为什么重要**  
> 很多时候 Agent 表现差，不是因为模型"笨"，而是因为它**没看到关键信息**。在调模型之前，先检查你给模型的输入是否完整。

具体做法：

| 检查项 | 方法 |
|--------|------|
| 系统提示是否清晰 | 手动审查 prompt |
| 工具描述是否准确 | 检查每个工具的 description |
| 上下文是否完整 | 用 LangSmith 等工具查看模型实际收到的输入 |
| 是否有干扰信息 | 移除不相关的上下文 |

> **类比理解**  
> 如果你给厨师的菜谱上写着"加适量盐"，但没告诉他是做甜品还是做汤，他大概率会做错。给 LLM 足够且准确的信息，是最基础也最重要的一步。

---

### 路线二：通用认知架构

学术界提出了不少通用的规划方法：

| 方法 | 核心思路 | 局限 |
|------|----------|------|
| Plan-and-Solve | 先列计划，再逐步执行 | 计划太抽象，容易脱离实际 |
| Reflexion | 执行后反思，修正下一步 | 反思质量取决于模型能力 |
| Chain-of-Thought | 让模型"一步一步想" | 只改善推理，不改善规划 |

> **为什么重要**  
> 这些方法提供了有价值的思路，但在实际生产中**太泛了**。它们试图用一套通用方案解决所有领域的规划问题，就像试图用一把万能钥匙开所有的锁——理论上可能，实践中不靠谱。

---

### 路线三：领域特定认知架构（最有效）

这是 Harrison Chase 在这篇文章中最核心的观点：**真正在生产中管用的，是针对特定领域设计的认知架构**。

#### AlphaCodium 的例子

AlphaCodium 是一个针对"代码生成"这个特定领域设计的系统。它没有让 LLM 自己规划，而是由工程师**预先定义了一套固定流程**：

```
┌───────────────────────────────────────────────────┐
│            AlphaCodium 的固定流程                   │
├───────────────────────────────────────────────────┤
│                                                   │
│  1. 理解问题描述                                    │
│     │                                             │
│     ▼                                             │
│  2. 分析公开测试用例                                │
│     │                                             │
│     ▼                                             │
│  3. 生成额外测试用例                                │
│     │                                             │
│     ▼                                             │
│  4. 生成初始代码方案                                │
│     │                                             │
│     ▼                                             │
│  5. 用测试用例验证代码                              │
│     │                                             │
│     ▼                                             │
│  6. 迭代修复失败的测试                              │
│     │                                             │
│     ▼                                             │
│  7. 输出最终代码                                    │
│                                                   │
└───────────────────────────────────────────────────┘
```

注意：**每一步里 LLM 只需要做短期规划**（"这一步该怎么做"），而长期规划（"先做什么后做什么"）已经由工程师用代码写死了。

> **类比理解**  
> 想象一个新手厨师。如果你只告诉他"做一顿法式大餐"，他会手足无措。但如果你给他一本详细的食谱——第一步准备食材，第二步切配，第三步煎牛排，第四步做酱汁——他就能一步一步完成。领域特定认知架构就是这本"食谱"。

---

## 五、核心洞察：工程师替 LLM 做规划

这是整篇文章最重要的一个观点：

> **领域特定认知架构的本质，是工程师把自己对领域的理解，用代码表达成"应该先做什么、后做什么"的固定流程。LLM 只需要在每一步里做好短期规划就行。**

为什么这样做有效？

| 分工 | 谁来做 | 为什么 |
|------|--------|--------|
| 长期规划（步骤顺序） | 工程师用代码写死 | 工程师比 LLM 更了解领域 |
| 短期规划（每步怎么做） | LLM 实时决策 | LLM 在短期规划上已经很强 |

```
传统方式：LLM 同时做长期 + 短期规划  →  容易出错
优化方式：工程师做长期规划 + LLM 做短期规划  →  效果好得多
```

> **为什么重要**  
> 这个思路改变了构建 Agent 的方法论。你不需要等模型变得更"聪明"，而是可以**现在就通过好的架构设计**让 Agent 更可靠。这也是为什么 LangGraph 这类框架强调"把工作流写成图（Graph）"——图的节点和边就是工程师为 LLM 做的长期规划。

## 六、未来展望

Harrison Chase 对未来的判断很务实：

| 趋势 | 预测 |
|------|------|
| 通用推理能力 | 会逐步进入模型层（训练时学会） |
| 领域特定架构 | **永远需要** |

为什么领域特定架构不会消失？因为每个领域都有自己独特的最佳实践、约束条件和工作流程。即使模型的通用推理能力提升了，针对特定任务设计专门的流程仍然会带来更好的效果。

> **类比理解**  
> 即使一个人再聪明，到了新公司也需要熟悉公司的流程和规范。通用智能解决不了所有问题，领域知识永远有价值。

## 延伸思考

1. **你的 Agent 项目中，规划是由 LLM 自主完成的，还是你已经用代码"写死"了部分流程？** 如果是前者，考虑把长期规划的部分固化成代码。

2. **你有没有检查过 LLM 实际收到的输入？** 很多规划失败的根源不是模型能力不足，而是输入信息不完整或有干扰。用 LangSmith 等工具看看模型到底"看到了"什么。

3. **通用推理 vs 领域架构的边界在哪里？** 随着模型能力提升，哪些你现在用代码写死的流程，未来可以交给模型自主完成？哪些永远需要人工设计？

4. **如果你要为自己的领域设计认知架构，第一步会怎么做？** 试着把你完成某个复杂任务的步骤写下来——这就是领域特定认知架构的雏形。
