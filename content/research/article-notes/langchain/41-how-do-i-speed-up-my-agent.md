# 如何加速你的 Agent：五个实战策略

**作者:** Harrison Chase  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-do-i-speed-up-my-agent)  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> Agent 跑得慢？先找到瓶颈在哪，然后从五个方向下手：降低感知延迟、减少 LLM 调用次数、加速单次调用、并行执行调用。

---

## 核心要点

1. **先诊断，再治病** —— 用 LangSmith 的瀑布视图 (Waterfall View) 看清每一步到底花了多少时间
2. **感知速度 > 实际速度** —— 用户觉得快比真的快更重要。流式返回中间步骤、后台运行 Agent 都能大幅改善体验
3. **代码能做的事别交给 LLM** —— 从单次调用到 ReAct 到多 Agent 再到 LangGraph，架构越精细，冗余调用越少
4. **更快的模型 + 更短的输入 = 更快的响应** —— 模型选型和上下文长度控制是两个直接杠杆
5. **能并行就并行** —— 护栏检查、多文档提取、多模型调用都可以同时跑

---

## 一、找到瓶颈在哪

> **类比理解**  
> 你点了一份外卖，等了 40 分钟。是餐厅出餐慢？骑手绕路了？还是你的楼下门禁耽误了时间？不搞清楚原因，催单也没用。Agent 的延迟问题也一样 —— 你得先知道时间花在了哪里。

Agent 运行的每一步都会消耗时间：调用 LLM、执行工具、等待 API 返回。有些步骤是一个大 LLM 调用吃掉了大部分时间，有些是十几个小调用累加起来的。不诊断就优化，等于盲人摸象。

LangSmith 提供了一个 **瀑布视图 (Waterfall View)**，可以像 Chrome DevTools 的网络面板一样，把每一步的耗时画成时间条。一眼就能看出：哪一步是瓶颈。

```
┌─── Agent 运行时间线 ──────────────────────────────────────────┐
│                                                              │
│  步骤 1: 解析用户意图     ██░░░░░░░░░░░░░░░░░░░░░░  0.8s     │
│  步骤 2: 检索知识库       ████████░░░░░░░░░░░░░░░░  2.1s     │
│  步骤 3: LLM 推理         ████████████████████████  6.3s  ◄─ 瓶颈！│
│  步骤 4: 格式化输出       █░░░░░░░░░░░░░░░░░░░░░░░  0.3s     │
│                                                              │
│  总耗时: 9.5s                                                │
└──────────────────────────────────────────────────────────────┘
```

> **为什么重要**  
> 如果瓶颈在一个大 LLM 调用上，你应该考虑换更快的模型或压缩输入。如果瓶颈在多个小调用的累加上，你应该考虑减少调用次数或并行执行。方向搞反了，努力就白费。

## 二、降低"感知延迟"

> **类比理解**  
> 去医院看病，等候区有电视、有叫号屏幕、有预估等待时间。实际等待时间没变，但你不会那么焦虑。Agent 的道理也一样 —— 有时候不需要真正变快，只需要让用户"觉得快"。

有两种主要做法：

### 2.1 流式返回中间步骤

大多数 LLM 应用已经支持逐字流式返回 (Streaming)。但你还可以更进一步：把 Agent 的**思考过程**也展示出来。

| 展示内容 | 效果 | 例子 |
|---------|------|------|
| 正在执行的步骤 | 用户知道 Agent 没有卡死 | "正在搜索相关文档..." |
| 检索到的资料 | 用户可以提前浏览 | 列出搜索到的 3 篇文档标题 |
| 推理过程 / 思考链 | 增强信任感 | 展示 thinking tokens |

Perplexity 就是一个典范。它在搜索时会实时展示"正在搜索的来源""正在分析的文档"等中间步骤。他们的数据表明：这个 UI 改动让用户满意度显著提升 —— **尽管总完成时间完全没变**。

### 2.2 后台运行 Agent

有些场景下，用户根本不需要盯着 Agent 跑。这时候最好的策略是：让 Agent 在后台默默执行，完成后再通知用户。

> **类比理解**  
> 你把衣服丢进洗衣机，设好程序就去做别的事了。洗完了它会响铃通知你。你不会站在洗衣机前面盯着它转 45 分钟。

Harrison Chase 自己的邮件助手就是这么做的：由一封新邮件触发 Agent，Agent 在后台处理，只有遇到问题才通知用户。用户完全感知不到任何延迟。

## 三、减少 LLM 调用次数

> **类比理解**  
> 搬家时，你不会每搬一件小东西就开一趟车。你会先打包好，把能一次带走的东西归到一起，减少来回跑的次数。Agent 也一样 —— 能用代码解决的事，就别浪费一次 LLM 调用。

Agent 的核心思想是 **LLM + 代码的混合体**。不是所有步骤都需要 LLM 介入。比如：

- **JSON 解析** → 代码搞定，不需要 LLM
- **格式转换** → 代码搞定，不需要 LLM
- **条件分支判断**（如果字段 A > 100 就走路径 B）→ 代码搞定，不需要 LLM

### 架构进化路径

开发者通常会经历以下进化路径：

```
单次 LLM 调用 ──→ ReAct Agent ──→ 多 Agent 架构 ──→ LangGraph
    简单              灵活           通用但低效          精准控制
    1 次调用          N 次调用        很多次调用          最少必要调用
```

| 阶段 | 特点 | 痛点 |
|------|------|------|
| 单次 LLM 调用 | 最简单，一问一答 | 能力有限，复杂任务做不了 |
| ReAct Agent | 能使用工具，循环推理 | 工具太多时效果下降 |
| 多 Agent 架构 | Supervisor / Swarm 模式，多个 Agent 协作 | Agent 之间通信开销大，LLM 调用次数爆炸 |
| LangGraph | 精确控制 Agent 之间的通信方式和时机 | 需要更多设计工作 |

> **为什么重要**  
> 多 Agent 架构（Supervisor、Swarm）虽然通用，但它们是**通用设计**，不会针对你的场景做优化。Agent 之间的每次通信都可能是一次 LLM 调用。LangGraph 让你精确指定"谁和谁通信、什么时候通信、用什么方式通信"，从而大幅减少不必要的调用。

## 四、加速单次 LLM 调用

即使调用次数已经优化到最少，每次调用本身的速度也很重要。两个直接杠杆：

### 4.1 用更快的模型

| 策略 | 代表模型 | 权衡 |
|------|---------|------|
| 超快模型 | Gemini Flash | 速度极快，但能力弱于大模型 |
| 中等模型 | Claude Haiku, GPT-4o-mini | 速度和能力的平衡点 |
| 专用推理平台 | Groq, Fireworks (开源模型加速) | 同模型更快的推理速度 |

> **注意：** 快通常意味着牺牲准确度。更快的模型一般是更小的模型，推理能力相对较弱。这是一个需要根据你的场景来权衡的取舍。

### 4.2 减少输入长度

LLM 的响应时间与输入长度**成正比**。输入越长，模型需要处理的 token 越多，耗时越久。

```
输入 token 数    ──→    响应时间
  500 tokens            ~1s
  2000 tokens           ~2.5s
  8000 tokens           ~6s
  32000 tokens          ~15s+
  
  (示意比例，非精确数据)
```

减少输入长度的方法：

- **精简系统提示 (System Prompt)**：去掉冗余指令
- **控制检索结果数量**：RAG 场景中，只返回最相关的 top-K 结果
- **压缩历史对话**：只保留关键信息，而非完整对话记录
- **去除工具返回的冗余数据**：过滤掉不必要的字段

> **为什么重要**  
> 你需要对每次 LLM 调用的输入有**完全的控制和可见性**。如果你用的框架会偷偷往 prompt 里塞东西（隐藏 prompt），那你就无法优化输入长度。这正是 LangGraph 不含任何隐藏 prompt 的原因 —— 你完全控制进入 LLM 的每一个字符。

## 五、并行执行 LLM 调用

> **类比理解**  
> 工厂流水线上，喷漆和组装螺丝可以在不同工位同时进行，但装车门必须等车架焊好之后。Agent 的多个步骤之间也是如此 —— 找出那些不互相依赖的步骤，让它们同时跑。

三个典型的并行场景：

### 场景一：护栏检查 + 内容生成

```
            ┌── 护栏检查 (Guardrail) ──┐
用户输入 ──┤                          ├──→ 合并结果
            └── 内容生成 (Generate)  ──┘

护栏检查和内容生成互不依赖，完全可以同时执行。
如果护栏检查发现问题，丢弃生成的内容即可。
```

### 场景二：多文档并行提取

```
            ┌── 提取文档 A 的信息 ──┐
            ├── 提取文档 B 的信息 ──┤
输入文档 ──┤── 提取文档 C 的信息 ──├──→ 汇总
            └── 提取文档 D 的信息 ──┘

每份文档的提取是独立的，串行跑是纯粹的浪费。
```

### 场景三：多模型并行调用

```
            ┌── 模型 A 生成答案 ──┐
用户问题 ──┤── 模型 B 生成答案 ──├──→ 选择/合并最优答案
            └── 模型 C 生成答案 ──┘

不同模型各有擅长，并行调用后取最优结果。
```

> **为什么重要**  
> 并行不适用于所有场景 —— 有些步骤天然有先后依赖。但只要步骤之间没有数据依赖，串行执行就是在浪费时间。LangGraph 原生支持并行分支 (Branching)，实现起来很简单。

## 总结：五大策略速查表

| # | 策略 | 核心思路 | 适用场景 | 难度 |
|---|------|---------|---------|------|
| 1 | 找到瓶颈 | 先诊断，再优化 | 所有场景（第一步必做） | 低 |
| 2 | 降低感知延迟 | 流式返回 / 后台运行 | 面向用户的交互场景 | 低 |
| 3 | 减少 LLM 调用 | 代码替代 + 精确架构 | 调用次数多、成本高的场景 | 中 |
| 4 | 加速单次调用 | 快模型 + 短输入 | 单次调用耗时长的场景 | 中 |
| 5 | 并行调用 | 独立步骤同时执行 | 存在无依赖关系步骤的场景 | 中 |

> 加速 Agent 的本质是**在性能、成本和能力之间做出明智的取舍**。先搞清楚你的瓶颈在哪，然后针对性地选择策略。有时候最有效的方法不是技术层面的 —— 而是重新思考用户如何与 Agent 交互。

---

## 延伸思考

1. **你的 Agent 最大的瓶颈是什么？** 是单个大调用太慢，还是小调用太多？诊断工具 (如 LangSmith) 能帮你一眼看出答案。

2. **你的场景真的需要用户实时等待吗？** 如果不需要，后台运行 Agent + 完成通知可能是 ROI 最高的优化。

3. **你的多 Agent 架构是否存在冗余通信？** 如果 Agent A 和 Agent B 之间每次交互都是一个完整的 LLM 调用，考虑用 LangGraph 精确控制通信路径。

4. **你的 prompt 里有多少是"废话"？** 用 LangSmith 看看每次 LLM 调用的实际输入。你可能会惊讶地发现，很大一部分 token 是不必要的。

5. **有哪些步骤可以并行？** 画一张你的 Agent 流程图，标出步骤之间的依赖关系。没有箭头连接的步骤，都是并行的候选者。
