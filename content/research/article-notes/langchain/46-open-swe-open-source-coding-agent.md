# Open SWE：企业内部编程 Agent 的开源框架

**作者:** LangChain 团队  
**来源:** [LangChain Blog](https://www.langchain.com/blog/open-swe-an-open-source-framework-for-internal-coding-agents)  
**日期:** 2026 年 3 月 17 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> Open SWE 是一个开源框架，把 Stripe、Ramp、Coinbase 等公司各自摸索出的内部编程 Agent 架构模式，提炼成一套可定制的通用方案，让你的团队不用从零开始造轮子。

---

## 核心要点

1. **生产级编程 Agent 已趋同** —— Stripe、Ramp、Coinbase 独立开发，却收敛到相同的架构模式：沙箱隔离、精选工具、子 Agent 编排、开发者工作流集成
2. **组合优于分叉** —— Open SWE 基于 Deep Agents 框架组合而成，既能享受上游升级，又能保留你的定制层
3. **隔离先行，权限后给** —— 每个任务在独立云沙箱中运行，沙箱内部拥有完整权限，错误被限制在隔离环境中
4. **工具精选比工具堆叠更重要** —— 15 个精选工具比 500 个乱堆工具更容易测试和维护
5. **中间件 + 子 Agent 双轨编排** —— 模型驱动的灵活决策与确定性中间件的可靠保障并行

---

## 一、行业趋势：巨头们不约而同在建什么？

过去一年，多家大型工程团队独立构建了内部编程 Agent。Stripe 做了 Minions，Ramp 做了 Inspect，Coinbase 做了 Cloudbot。这些系统有一个共同点：它们不要求工程师学新工具，而是直接嵌入 Slack、Linear、GitHub 等已有工作流。

> **类比理解**  
> 想象三家不同城市的餐厅，各自研究怎么做好一碗面。虽然没有互相交流，但最终都发现：好汤底（沙箱环境）+ 精选配料（精选工具）+ 标准化流程（编排逻辑）= 好面。Open SWE 就是把这个"不约而同的配方"写成了公开的菜谱。

### 五大趋同模式

| 模式 | 含义 | 类比 |
|------|------|------|
| 隔离执行环境 (Isolated Sandbox) | 每个任务在独立沙箱中运行，错误不会影响生产 | 实验室里做化学实验，炸了也不伤人 |
| 精选工具集 (Curated Toolset) | 工具不在多，在于精心维护 | 厨师用 5 把好刀，而非 50 把钝刀 |
| Slack 优先触发 (Slack-first) | 在工程师已有的沟通工具里触发 Agent | 不用跑去另一栋楼下单，微信群里说一声就行 |
| 启动时注入上下文 (Rich Context) | 从 Linear issue 或 Slack 线程提取完整信息 | 新同事入职第一天，先看完所有相关邮件 |
| 子 Agent 编排 (Subagent Orchestration) | 复杂任务拆解成多个专注的子 Agent | 项目经理把大任务拆成小任务分给不同组员 |

## 三、Agent 线束：组合而非分叉

Open SWE 没有从零造轮子，也没有 fork 一个现有 Agent 然后魔改，而是在 Deep Agents 框架上"组合"而成。这和 Ramp 在 OpenCode 上构建 Inspect 的思路一致。

> **类比理解**  
> 分叉 (Fork) 就像复印一本书然后在上面涂改 —— 原书更新了你得重新复印。组合 (Compose) 就像在书上贴便签 —— 原书更新了，你的便签还在，直接享受新版本的改进。

组合的两个核心好处：

| 优势 | 说明 |
|------|------|
| 升级路径 (Upgrade Path) | Deep Agents 改进了上下文管理或 token 优化，你不用重写定制代码就能受益 |
| 无需分叉的定制 (Customization) | 你的组织特定工具、提示词、工作流作为"配置"存在，而非对核心代码的修改 |

Deep Agents 提供的内置能力：

- `write_todos` —— 结构化规划和进度追踪
- 文件系统记忆 —— 大量中间数据卸载到文件，防止上下文溢出
- `task` 工具 —— 原生子 Agent 派生
- 中间件钩子 —— 在 Agent 循环的特定点注入确定性逻辑

## 四、沙箱：先隔离，再放权

每个任务在独立的云沙箱中运行。沙箱是一个远程 Linux 环境，有完整的 shell 访问权限。代码仓库被克隆进去，Agent 在里面拥有完全权限，任何错误都被限制在这个环境内。

> **类比理解**  
> 给小孩一间专用画室，里面随便画、随便泼颜料，但画室的门关着 —— 客厅的沙发不会受影响。这就是"隔离先行、权限后给"的原则。

### 支持的沙箱供应商

| 供应商 | 特点 |
|--------|------|
| Modal | 容器级隔离，按使用付费 |
| Daytona | 开发环境管理 |
| Runloop | 云端沙箱 |
| LangSmith | LangChain 生态原生 |
| 自定义 | 实现接口即可接入你的内部基础设施 |

关键细节：
- 同一个对话线程复用同一个沙箱
- 沙箱不可达时自动重建
- 多个任务各自拥有独立沙箱，并行运行

## 五、工具：精选 15 个，而非堆砌 500 个

Stripe 的 Agent 有约 500 个工具，但那是精心挑选和维护的结果。Open SWE 选择从一个更小的起点出发。

| 工具 | 用途 |
|------|------|
| `execute` | 在沙箱中执行 shell 命令 |
| `fetch_url` | 抓取网页并转为 markdown |
| `http_request` | 发起 API 调用 (GET/POST 等) |
| `commit_and_open_pr` | Git 提交并创建 GitHub Draft PR |
| `linear_comment` | 在 Linear 工单上发布更新 |
| `slack_thread_reply` | 在 Slack 线程中回复 |

此外还有 Deep Agents 内置工具：`read_file`、`write_file`、`edit_file`、`ls`、`glob`、`grep`、`write_todos`、`task`。

> **为什么重要**  
> 工具越少，越容易测试、维护和让模型理解。当你需要对接公司内部 API、部署系统或测试框架时，显式地添加即可 —— 不要预设一堆"可能有用"的工具。

## 六、上下文工程：仓库知识 + 任务信息

Open SWE 的上下文来自两个层次：

```
┌─────────────────────────────────────┐
│       第一层：仓库级知识              │
│                                     │
│  AGENTS.md (放在仓库根目录)           │
│  - 编码规范                          │
│  - 测试要求                          │
│  - 架构决策                          │
│  - 团队约定                          │
│                                     │
│  → 注入系统提示词，每次运行都生效      │
└─────────────────────────────────────┘
              +
┌─────────────────────────────────────┐
│       第二层：任务级信息              │
│                                     │
│  Linear issue 完整内容               │
│  Slack 线程历史                      │
│  GitHub PR 评论                      │
│                                     │
│  → 启动前组装好，无需额外工具调用      │
└─────────────────────────────────────┘
```

> **类比理解**  
> 第一层像公司的《员工手册》—— 不管做什么任务都适用的通用规则。第二层像你收到的具体工作邮件 —— 这次要解决什么问题、背景是什么、同事说了什么。两层结合，Agent 既懂大方向又知道小细节。

## 七、编排：子 Agent + 中间件双轨制

Open SWE 的编排分为两条轨道，各司其职。

### 轨道一：子 Agent（模型驱动，灵活）

主 Agent 通过 `task` 工具派生子 Agent。每个子 Agent 有独立的上下文、中间件栈、待办列表和文件操作空间。不同子任务之间互不污染。

### 轨道二：中间件（确定性，可靠）

中间件在 Agent 循环的固定位置执行，不依赖模型判断：

| 中间件 | 作用 |
|--------|------|
| `check_message_queue_before_model` | 在下一次模型调用前注入新消息（用户在 Agent 运行期间发来的补充信息） |
| `open_pr_if_needed` | 兜底保障 —— Agent 没开 PR，中间件自动补上 |
| `ToolErrorMiddleware` | 优雅地捕获和处理工具错误 |

> **为什么重要**  
> 灵活性和可靠性是一对矛盾。子 Agent 提供灵活性 —— 让模型决定怎么拆任务。中间件提供可靠性 —— 关键步骤必须发生，不靠模型"记得"。两者结合，Agent 既聪明又靠谱。

## 八、触发方式：嵌入已有工作流

```
开发者的日常工作流
         │
    ┌────┴────┬──────────┐
    ▼         ▼          ▼
  Slack     Linear     GitHub
    │         │          │
    │ @bot    │ @openswe  │ @openswe
    │ repo:   │ 读取完整   │ 在 Agent
    │ owner/  │ issue 上下文│ 创建的 PR
    │ name    │ 回复评论   │ 上回复反馈
    │         │          │
    └────┬────┴──────────┘
         ▼
    同一个 Agent 实例
   (通过确定性线程 ID 路由)
```

核心设计原则：不要求开发者切换到新应用。在他们已经待的地方触发 Agent，结果也回到同一个地方。每个触发创建一个确定性的线程 ID，后续消息自动路由到同一个运行中的 Agent。

## 九、验证：提示词驱动 + 安全网兜底

Agent 被指示在提交代码前运行 linter、formatter 和测试。但"被指示"意味着模型可能忘记。所以 `open_pr_if_needed` 中间件作为兜底 —— Agent 结束时如果没开 PR，中间件自动处理。

你还可以扩展验证层，添加：
- 确定性 CI 检查
- 可视化验证
- 人工审批门控

> **类比理解**  
> 提示词驱动像告诉员工"出门前记得锁门"。中间件兜底像在门上装自动锁 —— 就算人忘了，门也会自己锁上。关键动作不能只靠"记得"。

## 十、与巨头实现的对比

| 维度 | Open SWE | Stripe (Minions) | Ramp (Inspect) | Coinbase (Cloudbot) |
|------|----------|-------------------|-----------------|---------------------|
| 线束 (Harness) | 组合 (Deep Agents) | 分叉 (Goose) | 组合 (OpenCode) | 从零构建 |
| 沙箱 (Sandbox) | 可插拔 (Modal 等) | AWS EC2 预热 | Modal 容器预热 | 内部方案 |
| 工具数 | ~15 个精选 | ~500 个精选 | OpenCode SDK + 扩展 | MCP + 自定义技能 |
| 上下文 | AGENTS.md + Issue | Rule 文件 + 预加载 | OpenCode 内置 | Linear + MCP |
| 编排 | 子 Agent + 中间件 | 蓝图 (确定性 + 智能体) | 会话 + 子会话 | 三种模式 |
| 触发 | Slack / Linear / GitHub | Slack + 嵌入按钮 | Slack + Web + 插件 | 原生 Slack |
| 验证 | 提示词 + PR 兜底 | 三层 (本地 + CI + 1 次重试) | 可视化 DOM 验证 | Agent 评审 + 自动合并 |

> 核心模式相似，差异在实现细节和组织特定集成上 —— 这正是框架需要可定制的原因。

## 十一、为什么选择 Deep Agents 作为基座？

| Deep Agents 能力 | 解决什么问题 |
|-------------------|-------------|
| 上下文管理 (Context Management) | 长时编码任务产生大量中间数据，文件式记忆避免上下文溢出 |
| 规划原语 `write_todos` | 结构化拆解复杂工作，追踪进度，适应变化 |
| 子 Agent 隔离 | 不同子任务不污染彼此的对话历史，推理更清晰 |
| 中间件钩子 (Middleware) | 在 Agent 循环的特定点注入确定性逻辑，保障关键步骤可靠执行 |
| 升级路径 | 上下文压缩、提示缓存、规划效率改进自动流入，无需重建定制 |

## 延伸思考

1. **工具精选的边界在哪里？** Stripe 用 500 个精选工具，Open SWE 用 15 个。对你的团队来说，最优数量是多少？工具太少会限制能力，太多会让模型困惑 —— 找到平衡点需要实验。

2. **组合还是分叉？** 当你对基座框架的修改需求超过 30% 时，组合的收益可能不再明显。你的团队应该在什么节点考虑从组合转向分叉甚至自建？

3. **沙箱隔离的成本** —— 每个任务一个沙箱意味着更多的基础设施开支。预热策略（Stripe 和 Ramp 都在用）能减少延迟，但增加了闲置成本。冷启动 vs 预热，怎么选？

4. **中间件兜底的"信任问题"** —— 如果 Agent 知道有兜底机制，它会不会变得更"懒"？这是一个关于激励设计的有趣问题 —— 安全网的存在本身是否改变了 Agent 的行为？

5. **从内部工具到行业标准** —— 三家公司独立趋同的架构模式，是否正在形成编程 Agent 的"最佳实践"？Open SWE 把这些模式开源，会加速这个标准化过程吗？
