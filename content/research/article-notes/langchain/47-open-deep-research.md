# Open Deep Research：开源深度研究智能体

> 一句话总结：Open Deep Research 是一个基于 LangGraph 的开源多智能体研究系统，通过"确定范围-并行研究-撰写报告"三阶段流程，自动完成深度调研任务。

---

## 核心要点

| 要点 | 说明 |
|------|------|
| 三阶段流水线 | 范围界定(Scope) -> 研究(Research) -> 撰写(Write) |
| 多智能体并行 | 主管(Supervisor)拆分子课题，子智能体(Sub-Agent)并行搜索 |
| 上下文工程 | 压缩聊天为简报(Brief)，子智能体清洗原始数据后再上报 |
| 只在适合的地方用多智能体 | 研究阶段并行，写作阶段单次生成(One-Shot) |
| 可配置 | 用户可自带模型、搜索工具、MCP 服务器 |

---

## 1. 为什么需要"深度研究"智能体

研究是一项开放式任务，最佳策略无法事先确定。不同的问题需要完全不同的搜索策略和深度。一个比较两款产品的请求和一个验证某个事实的请求，所需的方法截然不同。

**三种典型研究需求：**

| 需求类型 | 示例 | 最佳策略 |
|----------|------|----------|
| 比较型 | "对比产品A和产品B" | 分别搜索，再综合对比 |
| 列举排序型 | "找出这个岗位的20个候选人" | 开放搜索，再筛选排名 |
| 验证型 | "X 说法是否属实？" | 迭代深挖特定领域，来源质量优先 |

### 类比理解

想象你是一个项目经理，接到老板一句"帮我调研一下竞品"。你不知道老板想要多深入——是看看价格就行，还是要做一份50页的分析报告。**深度研究智能体就是一个能自己判断"该查多深"的AI项目经理。**

## 3. Phase 1：范围界定(Scope)

这一阶段的目标是在正式研究前，把用户的模糊需求变成清晰的研究指令。它包含两步：用户澄清(User Clarification)和简报生成(Brief Generation)。

**用户澄清：** OpenAI 指出，用户提出研究请求时很少提供足够的上下文。系统会用聊天模型主动向用户追问，补齐缺失的背景信息。

**简报生成：** 聊天过程可能很冗长——有追问、有示例、有补充说明。系统会将这些对话压缩成一份精炼的研究简报(Research Brief)。这份简报就是后续所有工作的"北极星"，研究和写作阶段都会反复参照它。

### 类比理解

就像你去医院看病，医生不会听你说一句"我不舒服"就开药。他会追问：哪里不舒服？多久了？有什么诱因？最后在病历上写一份简明的诊断摘要。**用户澄清就是医生的问诊，简报就是那份病历摘要。**

---

## 4. Phase 2：并行研究(Research)

这是系统的核心阶段。研究由一个主管智能体(Supervisor Agent)协调，它决定如何拆分子课题并分配给子智能体。

```
                  +------------------+
                  |    Supervisor     |
                  | (研究主管)        |
                  +--------+---------+
                           |
            +--------------+--------------+
            |              |              |
     +------v------+ +----v------+ +-----v-----+
     | Sub-Agent A | | Sub-Agent B| | Sub-Agent C|
     | 子课题 A    | | 子课题 B   | | 子课题 C   |
     +------+------+ +-----+-----+ +-----+-----+
            |              |              |
            v              v              v
      清洗后的发现    清洗后的发现    清洗后的发现
            |              |              |
            +--------------+--------------+
                           |
                  +--------v---------+
                  |    Supervisor     |
                  | 判断是否足够      |
                  | 不够 -> 继续派遣  |
                  +------------------+
```

**主管智能体**的工作很简单：判断研究简报能否拆成独立的子课题，然后分配给各自隔离的子智能体。这样做的好处是可以并行搜索，更快获取信息。

**子智能体**各自只关注自己被分配的子课题，通过工具调用循环(Tool-Calling Loop)使用搜索工具和 MCP 工具完成调研。完成后，子智能体会做一次额外的 LLM 调用，将原始搜索结果清洗、提炼成结构化的回答并引用来源。

**迭代机制：** 主管收到子智能体的发现后，会判断是否已经覆盖了简报中的全部要求。如果还有缺口，主管会派遣新的子智能体继续深挖。

### 为什么子智能体要"清洗"结果？

原始搜索结果往往充斥着大量无关信息——抓取的整个网页、失败的工具调用、不相关的内容。如果把这些原始数据直接扔给主管，会导致 Token 用量暴涨，主管还要费力从中筛选有用信息。**让子智能体先整理好再汇报，就像让实习生先把资料整理成摘要再交给老板，而不是把一堆原始文件直接堆在桌上。**

---

## 5. Phase 3：报告撰写(Write)

当主管判断收集的信息足以覆盖研究简报的所有要求后，系统进入写作阶段。写作是一次性完成(One-Shot)的：将研究简报和所有子智能体清洗后的发现一起提供给 LLM，由它一次性生成最终报告。

### 为什么不让多个智能体并行写各自的章节？

LangChain 团队早期试过这种方案——快是快了，但生成的报告各章节之间脱节、不连贯。这正是 Cognition 公司指出的问题：并行工作的子智能体难以协调。**如果最终产出需要整体一致性(比如一篇连贯的报告)，就不适合并行。**

## 6. 三条关键经验

### 经验一：多智能体只用于可并行的任务

| 阶段 | 是否并行 | 原因 |
|------|---------|------|
| 研究阶段 | 并行 | 子课题独立，不需要互相参考 |
| 写作阶段 | 不并行 | 章节之间需要前后呼应，并行会导致脱节 |

### 经验二：上下文隔离避免长上下文失败

单智能体处理多个子课题时，所有搜索结果堆积在同一个上下文窗口(Context Window)里，会产生"上下文冲突"(Context Clash)等问题。实验显示，单智能体在处理多子课题时，对每个课题的搜索深度自然会变浅。

**具体例子：** 对比 OpenAI、Anthropic、Google DeepMind 的 AI 安全方法时，单智能体在一个上下文里同时处理三家公司的搜索结果。关于 OpenAI 的递归奖励建模的信息，对生成 DeepMind 的对齐哲学查询毫无帮助——但它们全挤在同一个窗口里，既浪费 Token 又干扰推理。

**多智能体方案：** 每个子智能体只处理一个公司的信息，上下文完全隔离，互不干扰。

### 经验三：上下文工程(Context Engineering)至关重要

Anthropic 报告其多智能体系统的 Token 用量是普通聊天应用的 **15倍**。Open Deep Research 通过以下方式控制 Token 膨胀：

```
上下文工程策略
+------------------------------------------+
| 1. 聊天 -> 压缩为研究简报                 |
|    避免冗长对话历史带来的 Token 膨胀       |
+------------------------------------------+
| 2. 子智能体清洗搜索结果后再上报           |
|    去除原始网页、失败调用等无关信息        |
+------------------------------------------+
| 3. 效果：省钱、避免超窗口限制、           |
|    避免触发模型速率限制(TPM Rate Limit)  |
+------------------------------------------+
```

### 类比理解

上下文工程就像搬家前的断舍离。你不会把家里所有东西都搬到新房子——旧报纸、过期食品、破损家具都应该丢掉。**只把真正需要的东西搬过去，新房子才不会被塞满。上下文窗口就是你的"新房子"，空间有限，得精打细算。**

## 7. 未来方向

Open Deep Research 是一个持续演进的项目，团队正在思考以下开放问题：

- **如何更好地处理 Token 密集型工具响应？** 过滤无关上下文、减少不必要的 Token 支出。
- **是否值得在智能体运行过程中加入评估？** 在热路径(Hot Path)中运行质量评估，确保响应质量。
- **能否利用长期记忆复用研究成果？** 深度研究报告生成成本高，如果能存储并复用，可以大幅提升效率。

## 为什么重要

深度研究是目前最受欢迎的 AI 智能体应用之一。OpenAI、Anthropic、Perplexity、Google 都推出了自己的深度研究产品。理解 Open Deep Research 的架构设计，你不仅能学到多智能体系统的核心模式——任务拆分、上下文隔离、上下文工程——还能直接把它用在自己的项目里。更重要的是，这些经验教训(比如"写作不要并行""先清洗再汇报")适用于所有多智能体系统的设计。

## 延伸思考

1. **你的场景适合多智能体吗？** 判断标准很简单：子任务之间是否真正独立？如果最终输出需要子任务之间高度协调(比如一篇连贯的文章)，多智能体反而会帮倒忙。
2. **上下文工程是不是比提示工程更重要？** 当智能体的 Token 用量是普通聊天的15倍时，如何管理上下文比如何写提示词(Prompt)更决定成败。
3. **研究成果能否被"记住"？** 如果你上周让智能体调研了 React 和 Vue 的对比，下周又问类似的问题，系统能否复用之前的成果？这是长期记忆(Long-Term Memory)在智能体中的核心应用场景。
4. **如何评估研究质量？** 不同于代码可以跑测试，研究报告的质量很难自动评估。在智能体运行过程中嵌入评估节点，是一个值得探索的方向。
