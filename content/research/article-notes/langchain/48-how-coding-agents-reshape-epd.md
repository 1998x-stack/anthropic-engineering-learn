# 编程 Agent 如何重塑工程、产品与设计

**作者:** Harrison Chase  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-coding-agents-reshape-epd)  
**日期:** 2026 年 3 月 10 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> EPD（工程、产品、设计）的产出本质上就是代码。编程 Agent 让写代码变得极其容易——当"怎么做"不再是瓶颈时，"做什么"和"做得对不对"才是关键。

---

## 核心要点

1. **PRD 已死，PRD 万岁** —— 传统的"写文档→画设计稿→写代码"流水线结束了，但描述需求的文档比以前更重要
2. **瓶颈从实现转向评审** —— 谁都能让 Agent 写代码，但代码架构好不好、解决的问题对不对、用户体验行不行，需要人来判断
3. **通才碾压专家团队** —— 一个懂产品+工程+设计的人，胜过三个人的团队（省掉了沟通开销）
4. **好 PM 更好，坏 PM 更糟** —— 坏想法现在也能变成原型，反而消耗更多评审资源
5. **每个人都需要产品感 (Product Sense)** —— 不知道让 Agent 做什么，等于在批量制造垃圾
6. **你要么是构建者，要么是评审者** —— 中间地带正在消失

---

## 类比理解：从手工作坊到 3D 打印工厂

> 想象你开了一家家具工厂。过去，从设计图到成品需要木匠花几周手工打磨。现在你有了一台超级 3D 打印机——输入设计图，几分钟就能出成品。
>
> 这台打印机改变了什么？
> - 木匠不再是瓶颈，**设计师成了关键**——打印什么比怎么打印重要
> - 任何人都能打印，但**打印出来的东西好不好用，需要有人把关**
> - 你可以快速打印十个原型来比较，但**如果十个都是坏设计，你只是在浪费材料**
> - 最厉害的人是**既能设计又能评审的全能选手**
>
> 编程 Agent 就是软件行业的"3D 打印机"。代码生产不再是瓶颈，判断力才是。

---

## 一、PRD 已死，PRD 万岁

### 核心观点

传统 EPD 流程是一条流水线：PM 写 PRD（产品需求文档），设计师画设计稿，工程师写代码。每一步都要等上一步完成。编程 Agent 打破了这条流水线——你可以跳过中间步骤，直接从想法生成可用软件。

### 为什么重要

流水线死了，但需求文档反而更重要了。原因很简单：当任何人都能让 Agent 生成原型时，你必须说清楚"这个原型要解决什么问题"。否则评审者面对一堆没有上下文的代码，根本无法判断好坏。

> **关键洞察**  
> 未来的 PRD 也许就是一份结构化的提示词（Structured Prompt）。它不再是给工程师看的实现指南，而是给编程 Agent 的输入，同时也是给评审者的评判标准。

### 流程对比

| 维度 | 传统流程 | Agent 时代流程 |
|------|---------|---------------|
| 起点 | PRD 文档 | 想法 + 结构化提示词 |
| 中间步骤 | 设计稿 → 排期 → 开发 | Agent 直接生成原型 |
| 产出 | 代码 | 可运行原型 + 需求文档 |
| 时间 | 数周到数月 | 数分钟到数小时 |
| 瓶颈 | 工程师产能 | 评审者判断力 |

---

## 二、瓶颈大迁移：从实现到评审

### 核心观点

过去 EPD 的瓶颈是"把想法变成代码"。现在编程 Agent 让这一步几乎免费了。新的瓶颈变成了三个问题：代码架构好不好？解决的是正确的问题吗？用户体验行不行？

### 为什么重要

这不是简单的"效率提升"，而是整个团队角色的重新定义。EPD 从"执行者"变成了"评审者和仲裁者"。你的价值不再是"能写代码"，而是"能判断代码该不该写、写得对不对"。

```
传统 EPD 流程：
┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
│  PM  │───>│ 设计 │───>│ 工程 │───>│ 上线 │
│写 PRD│    │画设计│    │写代码│    │      │
└──────┘    └──────┘    └──────┘    └──────┘
                        ↑ 瓶颈在这里

Agent 时代 EPD 流程：
┌──────┐    ┌──────────┐    ┌──────────┐    ┌──────┐
│  想法 │───>│  Agent   │───>│  EPD     │───>│ 上线 │
│      │    │ 生成原型  │    │ 评审仲裁  │    │      │
└──────┘    └──────────┘    └──────────┘    └──────┘
                             ↑ 瓶颈在这里
```

### 类比理解

以前开餐厅，瓶颈是厨师——菜做得慢。现在你有了一台自动炒菜机，任何人都能"做菜"。但顾客吃到嘴里好不好吃，还得有人试菜。**试菜的人（评审者）成了整个餐厅最重要的角色。**

## 三、角色重塑：工程、产品、设计各受什么影响

### 全景对比表

| 维度 | 工程师 (Engineering) | 产品经理 (Product) | 设计师 (Design) |
|------|---------------------|-------------------|----------------|
| 过去核心价值 | 实现功能 | 定义需求 | 设计体验 |
| 现在核心价值 | 系统架构 + 代码评审 | 判断"做什么"+ 评审原型 | 在代码中直接迭代体验 |
| Agent 带来的变化 | 实现时间大幅缩短 | 可以直接建原型验证想法 | 不用等工程师，自己改代码 |
| 新的核心技能 | 系统思维 (Systems Thinking) | 产品感 (Product Sense) | 代码素养 + 交互判断 |
| 最大风险 | 变成 Agent 的"代码搬运工" | 坏想法被放大 | 被通才取代 |

### 对工程师的影响

工程师的时间从"写代码"转向"系统思考"。你不再需要亲手实现每个功能，但你需要判断 Agent 写的代码是否可维护、是否符合架构规范、是否会在生产环境出问题。**执行力让位于判断力。**

> **关键转变**  
> 以前：工程师 80% 时间写代码，20% 时间思考架构  
> 现在：工程师 20% 时间指导 Agent 写代码，80% 时间思考架构和评审

### 对产品经理的影响

PM 现在可以直接用编程 Agent 建原型来验证想法，不用等工程排期。但这是一把双刃剑——好 PM 能更快验证好想法，坏 PM 能更快把坏想法做成原型，消耗整个团队的评审资源。

```
好 PM + Agent = 快速验证 → 正确的产品决策
坏 PM + Agent = 批量产出垃圾原型 → 评审资源被耗尽
```

### 对设计师的影响

设计师不再需要画完设计稿后等工程师实现。你可以直接在代码中迭代交互细节。但这也意味着你需要一定的代码素养，至少能看懂 Agent 生成的前端代码并指导它修改。

## 四、通才的崛起

### 核心观点

当编程 Agent 降低了"执行"的门槛，一个同时懂产品、工程和设计的通才，价值远超三个各自专精的人组成的团队。原因很简单：三人团队有沟通开销（Communication Overhead），通才没有。

### 为什么重要

这不是说专家不重要了。而是说**纯粹的专家必须极其出色，并且能极快地完成评审**，才能在这个新世界里保持竞争力。如果你只懂设计不懂工程，又不够顶尖，你的位置会被一个"什么都懂一点"的通才取代。

| 团队类型 | 优势 | 劣势 |
|---------|------|------|
| 三人专家团队 | 各领域深度大 | 沟通成本高，协调慢 |
| 一个通才 + Agent | 决策快，无沟通损耗 | 单一领域深度有限 |
| 通才 + 专家评审 | 兼顾速度和深度 | 需要合理分工 |

### 类比理解

以前盖房子需要建筑师、结构工程师、室内设计师三个人反复开会。现在你有了一个建筑全能软件，一个懂点结构懂点设计的人就能直接出方案——**然后找专家来审核关键节点就行了。**

---

## 五、系统思维成为核心技能

### 核心观点

当执行成本趋近于零，"做什么"比"怎么做"重要一百倍。系统思维（Systems Thinking）——理解整个系统如何运作、各部分如何交互、改变一个地方会如何影响其他地方——成为最稀缺的技能。

### 为什么重要

编程 Agent 能写出功能正确的代码，但它不理解你的系统全局。它不知道这段代码会不会跟另一个服务冲突，不知道这个设计选择会不会在用户量增长后成为瓶颈，不知道这个功能会不会让另一个团队的工作变得更难。**这些判断只有理解全局的人才能做。**

```
┌─────────────────────────────────────────┐
│         技能价值重新排序                   │
│                                         │
│  过去：                                  │
│  1. 编码能力（实现功能）                   │
│  2. 系统设计（架构思考）                   │
│  3. 产品感（判断做什么）                   │
│                                         │
│  现在：                                  │
│  1. 产品感（判断做什么）                   │
│  2. 系统设计（架构思考）                   │
│  3. 评审能力（判断做得对不对）              │
│  ...                                    │
│  N. 编码能力（Agent 替你做）              │
└─────────────────────────────────────────┘
```

## 六、你要么是构建者，要么是评审者

### 核心观点

角色边界正在模糊化。PM 能写代码了，工程师要懂产品了，设计师要看代码了。但有一个新的分界线正在形成：你要么是用 Agent 快速构建原型的人，要么是评审这些原型并做出最终判断的人。

### 为什么重要

如果你两者都不是——既不能快速构建，也没有判断力来评审——你在 EPD 中的位置就会很尴尬。中间地带正在消失。

> **自我诊断**  
> 问自己两个问题：  
> 1. 我能用编程 Agent 在一天内从想法做出可用原型吗？  
> 2. 我能看一个原型后，在 30 分钟内判断它的架构、产品逻辑和用户体验是否合理吗？  
>  
> 至少有一个答案是"能"，你在 Agent 时代就有位置。

## 全文总结

| 论点 | 核心一句话 | 类比 |
|------|-----------|------|
| PRD 已死又重生 | 流水线死了，需求文档活了 | 3D 打印机需要设计图 |
| 瓶颈从实现到评审 | 谁都能写代码，不是谁都能判断 | 自动炒菜机还需要试菜师 |
| 通才碾压专家团队 | 一个全能 + Agent > 三人团队 | 全能建筑软件 vs. 三人开会 |
| 好 PM 更好坏 PM 更糟 | 坏想法现在也能变原型 | 印钞机印的可能是废纸 |
| 系统思维是核心 | "做什么"比"怎么做"重要 | 导航比发动机重要 |
| 每个人都要有产品感 | 不知道做什么 = 制造垃圾 | 不会点菜就别进厨房 |
| 构建者或评审者 | 中间地带消失 | 要么上场踢球，要么当裁判 |

## 延伸思考

1. **你的团队还在走传统 PRD 流程吗？** 试着让 PM 直接用编程 Agent 做一个原型，然后用传统 PRD 流程做同样的功能，比较一下时间和质量差异。你会发现流程的浪费有多大。

2. **你是构建者还是评审者？** 诚实地评估自己——如果 Agent 能替你写代码，你还剩下什么独特价值？如果答案是"没什么"，现在是时候投资系统思维和产品感了。

3. **通才 vs. 专家，你选哪条路？** 在 Agent 时代，纯专家需要极其出色才能存活。如果你的专业能力是 top 5%，专精没问题。如果不是，考虑拓宽你的能力面。

4. **你的团队有"坏 PM"问题吗？** 当编程 Agent 让任何人都能产出原型，原型的数量会爆炸，但质量不会自动提升。你需要一套评审机制来过滤低质量原型，否则团队会被垃圾原型淹没。

5. **想象五年后的 EPD 团队长什么样。** 可能不再有明确的"工程师"、"PM"、"设计师"头衔。取而代之的是"构建者"和"评审者"——或者，一个人同时扮演两个角色。这对你意味着什么？
