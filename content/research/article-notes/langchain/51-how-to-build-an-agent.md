# 如何构建一个 Agent——六步实操指南

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-to-build-an-agent)  
**日期:** 2025 年 7 月 10 日  
**阅读时间:** 约 15 分钟

---

> **一句话总结**  
> 构建 Agent 不是一次性的编程任务，而是一个六步迭代循环：定义任务 → 写出 SOP → 搭建 MVP → 接入数据 → 测试迭代 → 部署改进。从一个"聪明实习生能完成的任务"开始，逐步扩展。

---

## 核心要点

1. **先定义任务，再写代码** —— 找 5-10 个具体示例来验证你的 Agent 该做什么、不该做什么
2. **像写操作手册一样设计 Agent** —— 人类怎么做这个任务，Agent 就怎么做，SOP（标准操作流程）是 Agent 的灵魂
3. **MVP 只解决一个推理问题** —— 不要一上来就全自动化，先用手动数据验证核心逻辑
4. **连接和编排是工程的主战场** —— 接入真实 API、处理异常、管理状态，这些才是难点
5. **测试是从 demo 到产品的分水岭** —— 手动测试 → 自动化测试 → 扩展用例，逐层递进
6. **发布是迭代的起点，不是终点** —— 真实用户的行为永远比你的测试用例更有创意

---

## 贯穿案例：邮件助手 Agent

本文所有步骤都围绕一个案例展开：**你要构建一个能自动处理工作邮件的 Agent**。它需要阅读新邮件、判断优先级、草拟回复、安排日程、更新 CRM 记录。

> **为什么选邮件助手？**  
> 因为每个人都处理过邮件，你能直观感受每一步的价值。而且邮件处理涉及分类、生成、工具调用、多步决策——这些恰好覆盖了 Agent 构建的核心技术点。

---

## 第一步：定义 Agent 的工作 + 收集具体示例

### 一句话

找到一个"聪明实习生能完成"的任务，用 5-10 个真实例子画出边界。

### 怎么做

**选任务的标准：** 不是所有工作都适合交给 Agent。你需要找到一个甜蜜区——足够重复以值得自动化，又足够复杂以需要 LLM 的推理能力。如果规则就能解决（比如"含关键词 X 就标记为垃圾邮件"），你不需要 Agent，写个脚本就行。如果任务需要深度专业判断（比如"判断这封邮件是否涉及法律风险"），聪明实习生也做不了，Agent 也不该做。

**具体操作：** 打开你的邮箱，翻出最近一周的邮件，挑出 5-10 封有代表性的。对每一封，写下你期望 Agent 做什么。这些示例就是你的"黄金测试集"（Golden Dataset），后面每一步都会用到它们。

| 示例编号 | 邮件类型 | 期望 Agent 行为 | 难度 |
|---------|---------|----------------|------|
| 1 | 客户询价 | 查 CRM 找历史报价，草拟回复 | 中 |
| 2 | 会议邀请 | 检查日历冲突，接受或建议改时间 | 低 |
| 3 | 内部审批 | 转发给上级并附摘要 | 低 |
| 4 | 投诉邮件 | 标记高优先级，草拟安抚回复，通知负责人 | 高 |
| 5 | 垃圾广告 | 直接归档，不回复 | 低 |
| 6 | 多方讨论串 | 提取最新结论，草拟跟进行动 | 高 |
| 7 | 含附件的技术文档 | 摘要附件内容，回复确认收到 | 中 |

```
选任务的判断流程：

这个任务...
├── 能用简单规则完成？ ──是──> 写脚本，不需要 Agent
├── 聪明实习生能做？
│   ├── 是 ──> ★ 适合 Agent
│   └── 否 ──> 需要专家，暂不适合
└── 重复频率高？
    ├── 是 ──> 自动化价值大
    └── 否 ──> 优先级低
```

> **类比理解**  
> 想象你刚招了一个实习生来帮你处理邮件。你不会一上来就说"帮我管所有邮件"——你会先拿几封典型邮件，告诉他"这种回这样，那种转给老板"。这 5-10 个示例就是你给实习生的入职培训材料。

### 为什么重要

没有具体示例，你的 Agent 就是一个模糊的想法。"帮我处理邮件"不是任务定义，"收到客户询价邮件时，查 CRM 历史报价并草拟回复"才是。示例越具体，后面每一步的方向越清晰，返工越少。

### 延伸思考

- 你的 5-10 个示例是否覆盖了"正常情况"和"边界情况"？只有正常案例的测试集会让你在上线后被意外场景打个措手不及
- 你是否定义了 Agent **不该做** 的事情？明确"不做什么"和"做什么"一样重要

## 第二步：设计标准操作流程 (SOP)

### 一句话

把人类做这个任务的步骤写成操作手册，这就是 Agent 的灵魂。

### 怎么做

**核心方法：** 假装你就是那个实习生，从头到尾走一遍处理邮件的流程，把每一步写下来。不要跳步骤，不要用"然后做出判断"这种模糊描述——具体到"如果邮件包含价格询问，则查询 CRM 系统中该客户的历史报价记录"。

**SOP 模板（以邮件助手为例）：**

```
邮件助手 SOP（标准操作流程）：

步骤 1：读取新邮件
  → 获取发件人、主题、正文、附件列表

步骤 2：分类邮件
  → 判断类型：询价 / 会议 / 审批 / 投诉 / 垃圾 / 其他
  → 判断优先级：高 / 中 / 低

步骤 3：根据类型执行对应操作
  ├── 询价 → 查 CRM → 草拟报价回复
  ├── 会议 → 查日历 → 接受/建议改期
  ├── 投诉 → 标记高优 → 草拟安抚 → 通知负责人
  ├── 审批 → 生成摘要 → 转发上级
  ├── 垃圾 → 归档
  └── 其他 → 标记待人工处理

步骤 4：人工审核（可选）
  → 高风险操作（如发送报价、回复投诉）需要人工确认

步骤 5：执行发送/归档/日程操作
```

| SOP 设计时的关键问题 | 为什么问 | 邮件助手示例 |
|-------------------|---------|-------------|
| 输入是什么？ | 确定数据源 | Gmail 收件箱的未读邮件 |
| 分几步完成？ | 确定流程复杂度 | 5 步：读取→分类→操作→审核→执行 |
| 每步需要什么工具？ | 确定技术依赖 | Gmail API、Google Calendar、CRM 系统 |
| 哪些步骤需要人工介入？ | 确定自动化边界 | 高风险操作需人工确认 |
| 出错了怎么办？ | 确定容错策略 | 无法分类的邮件标记为"待人工处理" |

> **类比理解**  
> SOP 就像餐厅后厨的操作手册。新厨师来了，不需要你口口相传，翻开手册就知道"收到牛排订单→取 200g 肉→煎 3 分钟→翻面→加黑胡椒→出餐"。你的 Agent 就是这个新厨师，SOP 就是它的操作手册。没有 SOP，Agent 只能靠"猜"——而猜错的代价在生产环境中非常高。

### 为什么重要

SOP 有三个关键作用。第一，它帮你验证范围是否合理——如果 SOP 写出来有 50 步，说明任务太复杂，需要拆分。第二，它暴露你需要的工具——写到"查 CRM"时你才意识到需要 CRM API。第三，它是提示词工程的直接输入——好的 SOP 几乎可以直接转化为系统提示词（System Prompt）。

### 延伸思考

- 你的 SOP 中有没有"需要大量背景知识"的步骤？这些步骤可能需要 RAG（检索增强生成）或预加载上下文
- SOP 中的分支越多，Agent 出错的概率越大——能否简化？

## 第三步：用提示词构建 MVP

### 一句话

先解决最关键的一个 LLM 推理任务，用手动输入的数据验证，不急着接入任何 API。

### 怎么做

**核心原则：** MVP 不是"最小可用的完整 Agent"，而是"验证核心推理能力的最小实验"。对邮件助手来说，核心推理是**邮件分类**——如果 Agent 连邮件类型都判断不准，后面所有步骤都是白搭。

**具体操作：**

1. **从 SOP 中找到最关键的推理步骤。** 邮件助手的关键步骤是"步骤 2：分类邮件"
2. **用手动数据测试。** 把第一步收集的 5-10 封示例邮件的正文直接粘贴进来，不需要 Gmail API
3. **反复调整提示词（Prompt），直到准确率满意**

**提示词结构示例：**

```
你是一个邮件分类助手。根据邮件内容，完成以下判断：

1. 邮件类型（从以下选项中选择）：
   - 询价：客户询问产品价格或服务报价
   - 会议：会议邀请、时间变更、取消通知
   - 审批：需要上级审批的请求
   - 投诉：客户表达不满或提出问题
   - 垃圾：广告、推销、不相关内容
   - 其他：不属于以上任何类别

2. 优先级（高/中/低）：
   - 高：涉及客户投诉、紧急截止日期、高价值交易
   - 中：需要回复但不紧急
   - 低：仅供参考、无需操作

3. 建议操作：一句话描述应该怎么处理

输出格式：
类型: [类型]
优先级: [高/中/低]
建议操作: [描述]
理由: [简述判断依据]
```

```
MVP 构建流程：

                    ┌─────────────┐
                    │  SOP 中找到  │
                    │ 核心推理步骤 │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  手动输入    │
                    │  示例数据    │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  写提示词    │
                    │  (Prompt)   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
          ┌────────│  测试准确率  │────────┐
          │        └─────────────┘        │
          │ 不满意                   满意  │
   ┌──────▼──────┐              ┌────────▼────────┐
   │  调整提示词  │              │  扩展到下一步骤  │
   │  或换模型    │──────────>   │  (如草拟回复)   │
   └─────────────┘              └─────────────────┘
```

| MVP 阶段的常见错误 | 正确做法 |
|------------------|---------|
| 一上来就接 Gmail API | 先用复制粘贴的邮件文本测试 |
| 同时测试分类+回复+日程 | 先只测分类，准确后再加回复 |
| 用一两个例子就觉得"行了" | 至少用 5-10 个覆盖不同类型的例子 |
| 提示词写得模糊（"帮我分类邮件"） | 给出明确的类别定义和输出格式 |
| 忽略边界情况 | 故意测试模糊邮件（如同时像询价又像投诉） |

> **类比理解**  
> 假设你要开一家餐厅。MVP 不是把装修、菜单、服务员、收银系统全搞好再开业——而是先在家里做几道核心菜品，请朋友试吃，确认味道对了再往下推进。邮件分类就是你的"核心菜品"，提示词就是你的"配方"。配方不对，开多大的店都白搭。

### 为什么重要

MVP 阶段的目标是**快速验证可行性**，用最低成本回答一个问题："LLM 能不能胜任这个任务的核心推理？"如果分类准确率只有 60%，你需要换模型、改提示词、或者重新定义任务范围——而不是继续往前推进，在一个不稳固的地基上盖楼。

### 延伸思考

- 你测试的示例是否包含"故意刁难"的边界案例？比如一封同时包含询价和投诉内容的邮件
- 提示词中的类别定义是否有重叠？重叠的定义会导致分类不稳定
- 你是否尝试了不同的模型？同一个提示词在 GPT-4、Claude、Gemini 上的表现可能差异很大

## 第四步：连接与编排

### 一句话

把 MVP 从"实验室"搬到"真实世界"——接入真实数据源、编排多步工具调用、处理异常情况。

### 怎么做

**这一步是工程量最大的阶段。** MVP 阶段你用复制粘贴的数据测试，现在要接入真实的 API。对邮件助手来说，至少需要三个数据源：

| 数据源 | 用途 | 接入方式 | 需要处理的问题 |
|-------|------|---------|---------------|
| Gmail API | 读取和发送邮件 | OAuth 2.0 认证 | 权限管理、速率限制、分页 |
| Google Calendar API | 查询和创建日程 | OAuth 2.0 认证 | 时区处理、冲突检测 |
| CRM 系统 (如 HubSpot) | 查询客户历史 | API Key 认证 | 数据格式转换、字段映射 |

**编排逻辑的核心：** 你的 Agent 不只是调用一个 API，而是需要根据分类结果**动态选择**调用哪些 API、以什么顺序调用。这就是"编排"（Orchestration）。

```
邮件 Agent 编排流程：

收到新邮件
    │
    ▼
┌─────────┐     ┌──────────┐
│ Gmail   │────>│ 分类模块  │
│ API     │     │ (LLM)    │
└─────────┘     └────┬─────┘
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   ┌─────────┐ ┌─────────┐ ┌──────────┐
   │ 询价    │ │ 会议    │ │ 投诉     │
   │         │ │         │ │          │
   │ CRM API │ │Calendar │ │ 通知负责 │
   │ → 报价  │ │API→日程 │ │ 人+草拟  │
   └────┬────┘ └────┬────┘ └────┬─────┘
        │           │           │
        ▼           ▼           ▼
   ┌──────────────────────────────────┐
   │        人工审核 (高风险操作)       │
   └───────────────┬──────────────────┘
                   │
                   ▼
   ┌──────────────────────────────────┐
   │     执行：发送/归档/创建日程      │
   └──────────────────────────────────┘
```

**编排时的三个关键决策：**

1. **哪些操作需要人工确认？** 发邮件、修改日程等不可逆操作应该设人工审核门槛（Human-in-the-Loop）。归档、标记等低风险操作可以全自动
2. **失败了怎么办？** API 超时、返回空数据、格式异常——每一种都需要降级策略（Fallback）。比如 CRM 查不到客户时，不要让 Agent 编造报价，而是标记"待人工处理"
3. **状态怎么管理？** 邮件处理到一半断了怎么办？你需要持久化中间状态（State Persistence），比如记录"已分类但未回复"

| 编排模式 | 适用场景 | 邮件助手示例 |
|---------|---------|-------------|
| 顺序执行 (Sequential) | 步骤有严格依赖 | 先分类 → 再查 CRM → 再草拟回复 |
| 并行执行 (Parallel) | 步骤互不依赖 | 同时查 CRM 和查日历 |
| 条件分支 (Conditional) | 根据结果走不同路径 | 询价走报价流程，投诉走安抚流程 |
| 循环重试 (Retry Loop) | 外部 API 不稳定 | Gmail API 超时时重试 3 次 |

> **类比理解**  
> MVP 阶段，你的邮件助手像一个在白板上模拟演练的新员工。连接与编排阶段，他正式坐到工位上了——要登录邮箱、打开 CRM、查日历。他会发现密码过期了、CRM 系统在维护、日历显示的是美国时区。这些"真实世界的麻烦"才是工程的主战场。

### 为什么重要

90% 的 Agent demo 死在这一步。demo 里一切顺畅，是因为数据是手动准备的、API 永远成功、不需要处理异常。真实世界里，Gmail API 有速率限制、CRM 字段可能为空、日历可能有时区问题。连接与编排的质量，决定了你的 Agent 是"能演示"还是"能用"。

### 延伸思考

- 你是否为每个 API 调用设计了超时和重试机制？
- 当多个工具调用的结果矛盾时（比如 CRM 说客户是 VIP，但邮件内容看起来像垃圾邮件），Agent 怎么决策？
- 你是否考虑了成本？每封邮件调用一次 LLM + 三个 API，日均 500 封邮件的成本是多少？

## 第五步：测试与迭代

### 一句话

从 5 个手动测试开始，逐步扩展到自动化测试套件，用明确的指标衡量 Agent 的表现。

### 怎么做

**测试分三层，逐层递进：**

```
测试金字塔：

              /\
             /  \
            / 扩 \         第三层：扩展测试
           / 展  \         50-100 个用例
          / 测试  \        覆盖长尾场景
         /________\
        /          \
       /  自动化    \      第二层：自动化测试
      /  测试       \      20-30 个用例
     /   (CI/CD)    \      自动运行 + 回归检测
    /________________\
   /                  \
  /    手动测试        \   第一层：手动测试
 /    5-10 个核心用例   \   黄金测试集
/______________________\
```

**第一层：手动测试（5-10 个用例）**

用第一步收集的"黄金测试集"，逐个运行，人工检查结果。这一步不要跳过——自动化测试的前提是你知道"正确答案长什么样"。

**第二层：自动化测试（20-30 个用例）**

把手动测试转化为可重复运行的脚本。关键是定义**评估指标**：

| 评估维度 | 指标 | 测量方法 | 邮件助手的合格线 |
|---------|------|---------|---------------|
| 意图检测 (Intent Detection) | 分类准确率 | 预测类型 vs 标注类型 | >= 90% |
| 语气安全 (Tone Safety) | 不当回复率 | 人工或 LLM 评审回复语气 | <= 2% |
| 工具调用效率 (Tool Efficiency) | 平均工具调用次数 | 统计每封邮件的 API 调用数 | <= 5 次/封 |
| 端到端延迟 (E2E Latency) | 处理时间 | 从收到邮件到完成处理 | <= 30 秒 |
| 降级率 (Fallback Rate) | 转人工处理比例 | 统计标记为"待人工"的比例 | <= 15% |

**第三层：扩展测试（50-100 个用例）**

从真实邮件流中采样更多案例，覆盖长尾场景（罕见邮件类型、多语言邮件、超长邮件等）。用 LangSmith 等工具追踪每次运行的详细轨迹（Trace），找到失败模式。

**迭代循环：**

```
┌──────────────────────────────────────────┐
│                                          │
│  发现失败案例 → 分析根因 → 修复 → 回归测试  │
│       ▲                           │      │
│       └───────────────────────────┘      │
│                                          │
└──────────────────────────────────────────┘

常见根因和修复方式：

失败类型              │ 根因           │ 修复手段
─────────────────────┼───────────────┼──────────────────
分类错误              │ 提示词类别重叠  │ 细化类别定义
回复语气不当           │ 缺少语气约束   │ 在提示词中加语气示例
工具调用失败           │ API 异常处理差  │ 加重试和降级逻辑
处理时间过长           │ 不必要的 API 调用│ 优化编排流程
遗漏关键信息           │ 上下文窗口不足  │ 压缩无关信息
```

> **类比理解**  
> 测试就像餐厅的试营业。第一层是请朋友来试吃（手动测试），第二层是每天开门前厨师自己试菜（自动化测试），第三层是开放给公众、收集大众点评的反馈（扩展测试）。你不会跳过试营业直接开业——Agent 也不该跳过测试直接上线。

### 为什么重要

没有测试的 Agent 就是一个黑箱赌博。你不知道它什么时候会给客户发一封不当回复、错过一个紧急会议邀请、或者把重要邮件归档到垃圾箱。测试不只是"找 bug"，更是"建立信任"——你需要证据证明 Agent 足够可靠，才能让它接管你的邮箱。

### 延伸思考

- 你的测试集是否会随时间"过时"？邮件模式会变化（新客户、新业务），测试集也需要定期更新
- 你是否测试了"对抗性输入"？比如有人故意发一封邮件试图让 Agent 泄露内部信息
- 自动化评估中使用 LLM 来判断回复质量（LLM-as-Judge）时，评审 LLM 本身的偏差如何控制？

## 第六步：部署、扩展与持续改进

### 一句话

发布只是迭代的开始——监控真实使用、收集反馈、持续优化，Agent 才能从"能用"变成"好用"。

### 怎么做

**部署不是"代码上线"这么简单。** 你需要建立一套完整的监控和反馈循环。

**部署清单：**

| 部署前检查项 | 具体内容 | 邮件助手示例 |
|------------|---------|-------------|
| 权限控制 | Agent 能做什么、不能做什么 | 只能回复，不能删除邮件 |
| 人工审核门槛 | 哪些操作必须人工确认 | 发送报价、回复投诉 |
| 降级策略 | 出错时怎么处理 | 无法处理的邮件通知用户 |
| 成本预算 | 日均成本上限 | API 调用 + LLM 调用 <= $X/天 |
| 回滚方案 | 出大问题时怎么恢复 | 一键关闭自动回复 |

**监控什么？**

```
生产监控仪表盘：

┌─────────────────────────────────────────────┐
│  邮件 Agent 运行状态                          │
├──────────────┬──────────────┬───────────────┤
│  今日处理     │  分类准确率   │  平均延迟      │
│  127 封      │  93.2%       │  18.4s        │
├──────────────┼──────────────┼───────────────┤
│  转人工       │  API 错误    │  用户满意度     │
│  11 封 (8.7%)│  3 次        │  4.2/5        │
└──────────────┴──────────────┴───────────────┘
```

**持续改进循环：** 用 LangSmith 等可观测性（Observability）工具追踪每一次 Agent 运行的完整轨迹。重点关注三类信号：

1. **用户修改了 Agent 的回复** —— 说明回复质量不够好，把修改前后的对比加入训练数据
2. **Agent 转人工处理的邮件** —— 分析为什么 Agent 处理不了，是分类错误还是缺少工具
3. **处理时间异常的邮件** —— 可能存在死循环、不必要的 API 调用、或上下文溢出

```
持续改进的飞轮效应：

    ┌─────────────┐
    │  部署上线    │
    └──────┬──────┘
           │
    ┌──────▼──────┐
    │  监控真实    │
    │  使用数据    │
    └──────┬──────┘
           │
    ┌──────▼──────┐
    │  发现失败    │
    │  模式       │
    └──────┬──────┘
           │
    ┌──────▼──────┐
    │  修复并加入  │
    │  测试集     │
    └──────┬──────┘
           │
    ┌──────▼──────┐
    │  重新部署    │──────> 回到"监控"
    └─────────────┘

每一轮循环，Agent 都变得更强。
真实用户数据是最好的训练材料。
```

> **类比理解**  
> 餐厅正式开业后，你不会把厨师送回去重新培训。你会每天看大众点评的差评、观察哪些菜退回率高、统计哪些菜最受欢迎。然后调整菜单、改进配方、培训服务员。Agent 上线后也一样——你不是"建完了"，而是"开始学了"。

### 为什么重要

真实世界的邮件远比你的测试集复杂。客户会发奇怪的格式、混合多种语言、在一封邮件里同时询价和投诉。只有通过监控真实使用，你才能发现这些"你想不到的场景"。持续改进不是可选项，而是 Agent 长期可靠运行的唯一方式。

### 延伸思考

- 你的监控是否能区分"Agent 做错了"和"任务本身就模糊"？有些邮件连人类也很难分类
- 当 Agent 处理量增长 10 倍时，成本和延迟会怎么变化？
- 你是否建立了用户反馈渠道？让用户能方便地告诉你"这个回复不好"

## 三条核心原则

无论你在哪一步，这三条原则始终适用：

**1. 从小开始（Start Small）**

不要试图一步到位。先让 Agent 只处理最简单的邮件类型（比如会议邀请），验证可行后再逐步扩展。一个能稳定处理 3 种邮件的 Agent，比一个不稳定地处理 10 种邮件的 Agent 有用得多。

**2. 以用户为中心（User-Centric）**

Agent 的目标不是"技术上可行"，而是"用户真的愿意用"。如果用户每次都要修改 Agent 的回复，那 Agent 就没有节省时间，反而增加了负担。关注用户的修改率和满意度，而不是技术指标。

**3. 持续改进（Continuous Improvement）**

Agent 不是软件产品，更像是一个需要持续培训的员工。真实世界在变化，邮件模式在变化，用户需求在变化。建立反馈循环，让 Agent 跟着变化一起进化。

> **最终类比**  
> 构建 Agent 就像培养一个新员工。你不会在面试时就期望他独当一面——你会从简单任务开始（定义工作），给他操作手册（SOP），让他先做模拟题（MVP），再让他接手真实工作（连接编排），安排老员工带教检查（测试迭代），最后让他独立上岗但持续跟进（部署改进）。六步构建法，就是 Agent 的入职培训流程。
