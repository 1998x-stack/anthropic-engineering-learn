# AI Agent 的用户体验（三）：电子表格、生成式 UI 和协作式交互

> 一句话总结：除了聊天和环境式，Agent 还有三种新兴交互范式 -- 电子表格式（批量并行）、生成式 UI（Agent 自己画界面）、协作式（人和 Agent 同时编辑同一文档）。

---

## 核心要点

| 要点 | 说明 |
|------|------|
| 电子表格 UX 是批量任务的理想载体 | 每个格子就是一个独立的 Agent，天然支持并行和数据增强 |
| 生成式 UI 有两种路线 | 完全生成（灵活但粗糙）vs 组件映射（精致但受限） |
| 协作式 UX 是未来方向 | 人和 Agent 同时工作、互相"喂养"，类似 Google Docs 的实时协作 |
| UX 决定基础设施 | 不同的交互方式对底层架构有完全不同的需求 |

---

## 一、电子表格 UX（Spreadsheet UX）：每个格子都是一个 Agent

你一定用过 Excel 或 Google Sheets。现在想象一下：表格里的每一个格子都是一个独立的 AI Agent，各自去执行任务、获取信息、填回结果。

这就是电子表格 UX 的核心思路。作者最早在 Matrices（一个 AI 原生电子表格工具）上看到这个模式，后来 Clay 和 Otto 等产品也采用了类似的设计。

### 为什么表格 UX 这么好用？

| 优势 | 解释 |
|------|------|
| 天然支持批量 | 一行就是一个任务，100 行就是 100 个并行的 Agent |
| 用户超熟悉 | 几乎所有人都用过 Excel，零学习成本 |
| 完美匹配数据增强 | 每列代表一个属性，Agent 帮你逐行填充 |
| 结构清晰 | 输入输出一目了然，不需要复杂的界面解释 |

```
电子表格 UX 示意:

+----------+------------+----------+-----------+----------+
|  公司名  |  行业      |  融资轮次  | CEO 邮箱  | AI 摘要  |
+----------+------------+----------+-----------+----------+
| Acme Inc | [Agent 1]  | [Agent 2]| [Agent 3] | [Agent 4]|
|          |  正在搜索   |  正在查   |  正在查   |  正在写  |
+----------+------------+----------+-----------+----------+
| Beta Co  | [Agent 5]  | [Agent 6]| [Agent 7] | [Agent 8]|
|          |  SaaS      |  B 轮    |  已找到   |  正在写  |
+----------+------------+----------+-----------+----------+
| Gamma Ltd| [Agent 9]  | [Agent10]| [Agent11] | [Agent12]|
|          |  金融科技   |  正在查   |  未找到   |  等待中  |
+----------+------------+----------+-----------+----------+

每个格子 = 一个独立的 Agent 任务
```

### 类比理解

传统聊天式 Agent 像是你雇了一个助手，一次只能交代一件事。电子表格 UX 像是你有一个 100 人的团队，你在白板上列出任务清单，每个人各领一行、同时开工。

这种模式特别适合数据增强（Data Enrichment）场景 -- 比如你有一份公司名单，想批量查出每家公司的行业、融资情况、联系人信息。在聊天界面里你得一个一个问，但在表格里，所有查询同时进行。

## 二、生成式 UI（Generative UI）：让 Agent 自己画界面

"生成式 UI"（Generative UI）这个概念可以有两种理解：

### 路线一：完全生成 -- Agent 写 HTML

Agent 直接生成原始的 HTML/CSS/JS 代码来渲染界面。类似 WebSim 这样的应用就是这个思路。Agent 对展示内容有完全控制权，理论上可以画出任何界面。

**问题**：生成的 HTML 质量参差不齐，界面可能看起来很"野生"或不够精致。就像让一个什么都会的全栈工程师来画设计稿 -- 功能都在，但视觉效果可能让设计师看了想哭。

### 路线二：组件映射 -- Agent 选择预制组件

更克制的方式是：预先定义好一组 UI 组件（天气卡片、股票图表、日程表等），Agent 通过工具调用（Tool Call）来触发相应组件的渲染。比如 Agent 调了天气 API，就自动弹出一个漂亮的天气组件。

**优势**：界面精致、一致性好。**局限**：只能展示预定义的组件类型。

| 维度 | 完全生成 | 组件映射 |
|------|---------|---------|
| 灵活性 | 极高，理论上能画任何界面 | 受限于预定义组件库 |
| 视觉质量 | 不稳定，可能很丑 | 稳定，始终精致 |
| 开发成本 | 低，只需提示 Agent | 高，需要预先开发组件 |
| 适合场景 | 原型、探索性工具 | 生产环境、面向终端用户 |

```
路线一 - 完全生成:
  用户提问 --> Agent 思考 --> 直接输出 HTML --> 浏览器渲染
                                  |
                           质量不可控 (可能精美，也可能丑)

路线二 - 组件映射:
  用户提问 --> Agent 思考 --> 调用天气API --> 触发<WeatherCard>组件
                         --> 调用股票API --> 触发<StockChart>组件
                                              |
                                        质量稳定 (预制的精美组件)
```

### 类比理解

- **完全生成** 就像让一个人自由发挥画画 -- 可能画出惊艳的作品，也可能画出抽象画看不懂。
- **组件映射** 就像乐高积木 -- 你只能用现有的积木块拼，但拼出来的东西一定是整齐好看的。

## 三、协作式 UX（Collaborative UX）：人和 Agent 一起工作

这是目前探索最少但可能最有前景的方向。想象 Google Docs 的体验 -- 你在写文档，你的队友也在写，你们同时编辑、互相看到对方的修改。

现在把"队友"换成 AI Agent。

你在文档里写了一段大纲，Agent 实时帮你扩展细节；Agent 写了一段代码，你立刻在旁边修改。你们同时工作，互相"喂养"（feeding off each other's work）。

### 协作式 vs 环境式：关键区别在于"并发"

LangChain 的创始工程师 Nuno 指出了两者的核心差异：

| 维度 | 协作式 UX | 环境式 UX |
|------|----------|----------|
| 核心特征 | 并发 -- 人和 Agent 同时工作 | 异步 -- Agent 在后台，人做别的事 |
| 交互方式 | 互相看到对方的工作，实时协调 | Agent 自主运行，偶尔来问你 |
| 展示需求 | 需要展示 Agent 的细粒度工作过程 | 需要总结 Agent 做了什么，或高亮变更 |
| 触发方式 | 用户操作直接影响 Agent 行为 | 通常由外部事件触发（如收到邮件） |

```
协作式 UX:

  时间 -->
  
  用户:    [写大纲]----[修改Agent的建议]----[继续写]----
  Agent:   ----[扩展细节]----[优化措辞]----[添加引用]----
  
  两条线同时推进，互相影响
  
  
环境式 UX:

  时间 -->
  
  用户:    [做自己的事].......................[收到通知，给出指示]....
  Agent:   [后台处理]--[处理]--[遇到问题,求助]......[继续处理]--[完成]
  
  两条线独立运行，偶尔交汇
```

### 类比理解

- **协作式** = 双人台球搭档赛。你和搭档交替击球，每一杆都影响下一杆的策略。你们需要实时沟通、互相配合。
- **环境式** = 你请了个清洁阿姨。你出门上班，阿姨在家打扫。她遇到不确定的事（这个花瓶要不要扔？）给你发条消息问一下。

## 四、UX 决定基础设施

LangChain 本质上是一家基础设施公司，为什么要花这么多时间研究 UX？

答案很简单：**人类如何与 Agent 交互，直接决定了需要构建什么样的底层能力。**

以 LangGraph Cloud 为例，它提供了：

| 能力 | 对应的 UX 需求 |
|------|---------------|
| 多种流式模式 | 支持流式聊天、非流式聊天等不同交互方式 |
| "双发消息"支持 | 用户在 Agent 还没回复时又发了新消息 |
| 异步后台运行 | 支持环境式 Agent 在后台持续执行 |
| 状态检查点 | 支持协作式 UX 中的回退、分支、并发编辑 |

每一项技术能力都不是凭空设计的，而是由真实的 UX 需求倒推出来的。

## 五大 Agent UX 范式总览

回顾整个系列，我们讨论了五种 Agent 交互方式：

```
+------------------+------------------+------------------+
|   流式聊天        |   非流式聊天      |   环境式          |
|   (Streaming)    |   (Non-stream)   |   (Ambient)      |
|                  |                  |                  |
|  实时看到         |  等待结果         |  后台运行         |
|  Agent 思考       |  一次性返回       |  偶尔来问你       |
+------------------+------------------+------------------+
|   电子表格式       |   生成式 UI       |   协作式          |
|   (Spreadsheet)  |   (Generative)   |   (Collaborative)|
|                  |                  |                  |
|  批量并行         |  Agent画界面      |  同时编辑         |
|  每格一个Agent    |  动态渲染组件     |  互相喂养         |
+------------------+------------------+------------------+
```

---

## 为什么重要

这个系列的核心洞察是：**Agent 的价值不仅在于它"能做什么"，更在于它"怎么跟人配合"。**

同样的底层能力（比如搜索信息、写代码、分析数据），放在不同的 UX 里会产生完全不同的产品体验。选对交互方式，可能比优化模型本身更能影响用户满意度。

---

## 延伸思考

1. **你在工作中最需要哪种 Agent UX？** 是帮你批量处理数据的表格式，还是和你一起写代码的协作式？
2. **生成式 UI 的"两条路线"会走向融合吗？** 也许未来 Agent 能先用预制组件，组件库里没有的再实时生成？
3. **当协作式 Agent 足够成熟** -- 你和 AI 同时编辑一份文档 -- 你还分得清哪些是你写的、哪些是 AI 写的吗？这重要吗？
4. **下一个还没被发明的 Agent UX 会是什么？** 声音？AR？脑机接口？还是某种我们现在想象不到的全新范式？
