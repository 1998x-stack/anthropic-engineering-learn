# 为什么 Agent 基础设施至关重要：你的 AI 应用需要新的「地基」

> 一句话总结：Agent 应用需要持久执行、复杂状态管理和人机协作等全新能力，传统 Web 后端和分布式系统都搞不定，你需要一层专门为 Agent 设计的基础设施。

---

## 核心要点

| 要点 | 说明 |
|------|------|
| Agent 工作负载与传统 Web 完全不同 | 可能运行数分钟甚至数小时，中途暂停、恢复、等待人类反馈 |
| 持久执行是第一需求 | 普通 Serverless 环境会超时，Agent 需要能被挂起和恢复 |
| 状态管理远比聊天记录复杂 | 不只是消息列表，还有工具调用状态、中间结果、决策历史 |
| 人机协作需要原生支持 | Agent 经常需要暂停等人确认，这不是传统请求-响应模型能优雅处理的 |
| 这是一个全新的基础设施层 | 介于应用逻辑和云平台之间，专门解决 Agent 特有的问题 |

## 传统架构 vs Agent 架构对比

| 维度 | 传统 Web 后端 | Agent 基础设施 |
|------|-------------|---------------|
| 执行时长 | 毫秒到秒级 | 秒到小时级 |
| 状态管理 | 请求无状态，状态在数据库 | 运行时状态复杂，需要检查点 |
| 失败处理 | 重试整个请求 | 从最近的检查点恢复 |
| 扩缩容 | 按请求数扩缩 | 按任务队列深度扩缩 |
| 用户交互 | 请求-响应 | 暂停-等待-恢复 |
| 输出方式 | 一次性返回 | 逐 Token 流式输出 |

## 类比理解

想象你开了一家餐厅：

**传统 Web 后端**就像快餐店的柜台。顾客下单，厨房做好，几分钟端上来。如果超过 5 分钟没做好，系统就报错。每个订单都是独立的，做完就忘。

**Agent 基础设施**就像一家高端定制西餐厅。一道菜可能要炖 3 小时。中间厨师可能要问你「牛排几分熟」（人机协作）。如果停电了，恢复供电后要从上次的步骤继续，不能重新来过（可恢复运行）。厨房里有多个灶台同时工作（水平扩缩），服务员会一道一道上菜而不是等全做完（流式输出）。

快餐店的模式显然没法用来经营这种餐厅。你需要的是一套完全不同的运营体系。

## 为什么传统方案不行？

大多数 Serverless 环境（如 AWS Lambda）都针对短时任务优化。一个典型的 Agent 运行过程是这样的：

```
Agent 启动
   |
   v
调用 LLM (等待 3 秒)
   |
   v
执行工具 A (调用 API，等待 5 秒)
   |
   v
再次调用 LLM (等待 3 秒)
   |
   v
需要人类确认 --> [暂停...等待 10 分钟...人类确认]
   |
   v
执行工具 B (查询数据库，等待 2 秒)
   |
   v
调用 LLM 生成最终结果 (等待 4 秒)
   |
   v
完成 (总耗时: ~10 分 17 秒)
```

在这个过程中，Lambda 函数早就超时被杀掉了。即使你设置了最大超时时间，中间那 10 分钟的等待也是纯粹的资源浪费。

Agent 基础设施的做法是：在等待人类确认时，把 Agent 的状态保存到检查点（Checkpoint），释放计算资源。等人确认后，从检查点恢复继续执行。这就是**持久执行**（Durable Execution）的核心思想。

---

## 为什么重要

这篇文章揭示了一个正在发生的基础设施范式转移：

- **从无状态到有状态。** 传统 Web 追求无状态，但 Agent 天然是有状态的。这改变了你构建后端的基本假设。
- **从请求驱动到任务驱动。** Agent 不是「处理一个请求」，而是「完成一个任务」，任务可能跨越多次交互。
- **软件工程的每次大转型都需要新基础设施。** 从单体到微服务需要容器编排，从本地到云需要云平台，从传统应用到 Agent 应用同样需要专门的基础设施层。

如果你正在构建任何超出「一问一答」的 AI 应用，现在就应该认真考虑你的 Agent 基础设施选择。
