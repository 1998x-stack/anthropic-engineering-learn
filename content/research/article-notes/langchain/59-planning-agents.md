# 规划型智能体 (Planning Agents)

> 一句话总结：先想清楚再动手——把"边走边想"的 ReAct 模式升级为"先规划再执行"，让 Agent 更快、更省、更准。

---

## 核心要点

- **Plan-and-Execute** 模式将 Agent 拆分为"规划器"和"执行器"两个角色，各司其职
- 相比 ReAct 的逐步推理，规划型 Agent 有三大优势：更快执行、更省成本、更高完成率
- 本文介绍三种递进架构：基础 Plan-and-Execute、ReWOO、LLMCompiler
- 核心思想源自编译器设计——先分析依赖关系，再并行调度执行

---

## 三种规划架构对比

| 维度 | Plan-and-Execute | ReWOO | LLMCompiler |
|------|------------------|-------|-------------|
| 核心思路 | 规划 -> 逐步执行 -> 重新规划 | 规划时支持变量引用 | 流式DAG + 并行调度 |
| 执行方式 | 串行，每步一个LLM | 串行，但可跳过LLM | 并行，流式调度 |
| 变量传递 | 不支持 | 支持 (#E1, #E2) | 支持 (${1}, ${2}) |
| 速度提升 | 中等 | 中等 | 最高 (论文称 3.6x) |
| 重规划能力 | 有 | 无（一次规划到底） | 有（Joiner 决定） |
| 适用场景 | 通用多步任务 | 依赖链明确的任务 | 高并发工具调用 |

## 架构流程图

```
=== ReAct (传统方式，作为对比) ===

  用户输入 --> [思考] --> [行动] --> [观察] --> [思考] --> [行动] --> ...
                 |          |          |          |          |
                LLM       工具       结果       LLM       工具
                
  问题: 每一步都要调用大模型，慢且贵


=== Plan-and-Execute ===

  用户输入
     |
     v
  [规划器 (大模型)]  -->  步骤1, 步骤2, 步骤3, ...
                              |
                              v
                    [执行器 (小模型/工具)]  逐步执行
                              |
                              v
                    [重新规划?]  --> 是 --> 回到规划器
                         |
                         否
                         |
                         v
                      最终回答


=== ReWOO ===

  用户输入
     |
     v
  [规划器] --> Plan: 需要知道超级碗参赛队伍
               E1: Search["超级碗参赛队"]
               Plan: 需要知道四分卫
               E2: LLM["#E1 的四分卫"]     <-- 引用E1的结果
               E3: Search["#E2 的数据"]     <-- 引用E2的结果
     |
     v
  [Worker] --> 依次执行 E1, E2, E3，自动替换变量
     |
     v
  [Solver] --> 整合所有结果，生成最终答案


=== LLMCompiler ===

  用户输入
     |
     v
  [规划器] --流式输出--> 任务DAG (有向无环图)
                           |
                      [任务调度器]
                      /    |     \
                     v     v      v
                   [T1]  [T2]   [T3]    <-- 无依赖的任务并行执行
                     \     |
                      v    v
                       [T4]             <-- 等待T1,T2完成后执行
                         |
                         v
                     [Joiner]  --> 完成? --> 返回结果
                         |
                         否
                         v
                     [重新规划]
```

## 类比理解

想象你是一个项目经理，接到一个大任务。

**ReAct 模式**就像你事必躬亲：每做完一件小事，你都要停下来思考下一步做什么。你是唯一的决策者，团队成员必须等你的指令。效率低下，而且你这个"大脑"是最贵的资源。

**Plan-and-Execute 模式**是你学会了委派。你先花10分钟列出完整的任务清单，然后把每个小任务分给不同的团队成员（可以是更便宜的"实习生"）。执行完后你看一眼结果，决定要不要调整计划。

**ReWOO 模式**更聪明：你在列任务清单时，还标注了依赖关系——"等小王查完市场数据(E1)后，小李去分析E1中的竞品"。这样执行者不需要每步都回来问你，按照清单和依赖关系自动推进。

**LLMCompiler 模式**就像一个高效的编译器调度系统。你把任务组织成一张依赖关系图，然后调度器自动识别哪些任务可以并行执行。就像编译器把代码中的独立指令分配到多个CPU核心一样，多个工具调用可以同时进行，大幅缩短总耗时。

## 深入原理

### 为什么 ReAct 不够好？

ReAct (Reasoning and Acting) 的核心循环是"思考-行动-观察"。它有两个结构性缺陷：

1. **每步都要调用大模型**：如果一个任务需要调用5个工具，ReAct 就需要5次大模型推理（每次决定下一步做什么）。这既慢又贵。

2. **只看一步**：ReAct 每次只规划下一个动作，从不"抬头"看全局。这就像导航只告诉你"下个路口左转"，但不告诉你完整路线——你可能会走弯路。

### Plan-and-Execute 的分层设计

Plan-and-Execute 的精妙在于"分层"思想：

- **规划层**用大模型（如 GPT-4），负责全局思考
- **执行层**用小模型或直接调工具，负责具体操作

这和软件工程中的"策略模式"异曲同工：把"做什么"和"怎么做"解耦。规划器定义策略，执行器实施策略。重规划机制则保证了系统能从错误中恢复。

### ReWOO 的变量引用机制

ReWOO 的关键创新是在规划阶段引入变量引用语法：

```
E1: Search["超级碗参赛队伍"]
E2: LLM["#E1 的四分卫是谁"]     <-- #E1 会被替换为 E1 的实际结果
E3: Search["#E2 的赛季数据"]     <-- #E2 会被替换为 E2 的实际结果
```

这意味着规划器可以在**不知道中间结果**的情况下，提前规划好整条执行链。执行时，Worker 按顺序执行，自动将变量替换为实际值。

好处是显而易见的——任务上下文被精确控制。每个执行步骤只看到它需要的输入和变量值，而不是整个对话历史。这减少了无关信息的干扰。

### LLMCompiler 的三大加速机制

LLMCompiler 的名字来源于编译器优化，它的三个核心优化策略也确实来自编译器世界：

1. **流式规划 (Streaming Planning)**：规划器不是等全部规划完再执行，而是边规划边输出。解析器一看到完整的任务描述，就立刻交给调度器。

2. **依赖感知调度 (Dependency-Aware Scheduling)**：调度器维护一个依赖图。一旦某个任务的所有前置依赖完成，立刻触发执行——不用等其他无关任务。

3. **变量延迟绑定 (Late Binding)**：任务参数可以包含变量如 `search("${1}")`，在实际执行时才替换为前置任务的输出。这允许规划器构建比"尴尬并行"（embarrassingly parallel）更复杂的并行模式。

## 速度与成本对比

```
执行速度 (越长越快):

ReAct         |===                           |  (基准)
Plan-Execute  |==========                    |  ~2x
ReWOO         |==========                    |  ~2x
LLMCompiler   |=========================     |  ~3.6x


大模型调用次数 (5步任务):

ReAct         |==========| 5次 (每步1次)
Plan-Execute  |======    | 3次 (规划+重规划+最终)
ReWOO         |====      | 2次 (规划+整合)
LLMCompiler   |=====     | 2-3次 (规划+Joiner)
```

## 为什么重要

规划型 Agent 解决的是一个非常实际的工程问题：**如何让 AI 系统在处理多步骤任务时既快又省？**

在真实的生产环境中，一个 Agent 可能需要调用十几个 API，如果每次都要"请示"大模型，不仅响应时间长达分钟级别，API 费用也会快速累积。规划型架构通过"想清楚再动手"的策略，把大模型调用从 O(n) 降到 O(1)（理想情况下），从根本上改变了成本结构。

更重要的是，显式规划强制 Agent "通盘考虑"——这本身就是一种经过验证的提示技巧（Chain-of-Thought 的延伸）。仅仅是让模型列出完整的步骤计划，就能显著提升最终结果的质量。

## 延伸思考

1. **规划的粒度**：计划应该多详细？太粗糙会导致执行偏差，太精细会限制灵活性。实践中，每个步骤应该恰好对应一次工具调用。

2. **何时重规划**：Plan-and-Execute 和 LLMCompiler 都支持重规划，但重规划本身也有成本。一种策略是只在"执行结果与预期严重不符"时才触发重规划。

3. **规划与反思的结合**：规划和反思并不矛盾。你可以在执行完每个步骤后加入反思环节，评估是否需要调整后续计划。LATS（上一篇的树搜索）某种程度上就是这种结合。

4. **动态任务图**：LLMCompiler 的 DAG 是静态的（一次生成），但真实任务的依赖关系可能随执行而变化。如何构建"动态 DAG"是一个有趣的研究方向。
