# 何时以及如何构建多智能体系统 (Multi-Agent Systems)

> 一句话总结：多智能体不是银弹——"读"任务适合并行拆分，"写"任务应由单一 Agent 统一完成，而上下文工程 (Context Engineering) 是一切的基础。

---

## 核心要点

- **上下文工程 (Context Engineering)** 是构建可靠 Agent 系统的第一要务，比提示工程更进一步
- 多智能体系统在"读取型"任务（如研究调研）上更容易成功，在"写入型"任务（如编码）上容易翻车
- 生产级 Agent 还需解决持久执行、可观测性、评估三大工程挑战
- 选择单 Agent 还是多 Agent 没有通用答案，取决于任务的并行度、价值密度和上下文共享需求

---

## 关键概念对比

| 维度 | 单智能体 (Single Agent) | 多智能体 (Multi-Agent) |
|------|------------------------|----------------------|
| 上下文管理 | 天然共享，简单 | 需要精心设计分发和同步 |
| 适合任务 | 依赖强、写入多 | 可并行、读取多 |
| Token 消耗 | 较少 | 较多（但可处理更大任务） |
| 调试难度 | 较易 | 较难（非确定性决策） |
| 典型案例 | 编码 Agent | 研究调研 Agent |
| 经济可行性 | 低价值任务也可用 | 需要高价值任务覆盖成本 |

## 核心架构图

```
=== 多智能体系统的"读"与"写" ===

  "读"为主的多智能体（研究型，适合并行）:

       [主 Agent / 领导者]
       /        |        \
      v         v         v
  [子Agent A] [子Agent B] [子Agent C]     <-- 并行研究不同方向
  (搜索方向1) (搜索方向2) (搜索方向3)
      \         |         /
       v        v        v
       [主 Agent 统一撰写报告]              <-- 写入由单一Agent完成
              |
              v
          最终报告


  "写"为主的多智能体（编码型，难以并行）:

       [主 Agent / 领导者]
       /        |        \
      v         v         v
  [子Agent A] [子Agent B] [子Agent C]     <-- 并行写不同模块
  (模块1)     (模块2)     (模块3)
      \         |         /
       v        v        v
      冲突! 冲突! 冲突!                    <-- 隐含决策互相矛盾
              |
              v
         合并噩梦...
```

## 类比理解

**上下文工程**就像给新员工做入职培训。再聪明的人，如果不了解项目背景、代码规范、团队分工，也没法有效工作。2025年的大模型已经足够聪明了，但如果你喂给它的上下文不对，它照样会犯低级错误。"提示工程"(Prompt Engineering) 是静态的——写好一个提示模板。"上下文工程"是动态的——在一个运行中的系统里，自动为每个步骤组装正确的上下文。

**读 vs 写的区别**可以类比为图书馆研究 vs 合著一本书。让三个人同时去不同图书馆查资料（读），很容易——最多有些重复劳动。但让三个人同时写一本书的不同章节（写），就容易出问题：一个人把主角写死了，另一个还在写主角的后续冒险。"行动携带隐含决策，冲突的决策带来糟糕的结果。"

**持久执行**就像长途飞行中的自动驾驶。如果中途遇到气流（错误），你不能让乘客下机重新登机（重启）。系统必须能从错误点恢复（resume），而不是每次都从头来过。

## 深入原理

### 上下文工程：从提示到系统

Cognition 团队（Devin 的创建者）提出了"上下文工程"这个概念。他们的洞察是：

> "2025 年的模型已经极其聪明了。但即使是最聪明的人，如果不了解自己被要求做什么的上下文，也无法有效完成工作。"

在多 Agent 系统中，上下文工程的难度急剧上升。你需要回答这些问题：
- 每个子 Agent 需要知道什么？
- 什么信息应该共享，什么应该隔离？
- 当对话超过上下文窗口长度时，怎么办？

Anthropic 的 Claude Research 团队分享了他们的具体做法：
- **分阶段总结**：完成一个阶段的工作后，Agent 会总结核心信息并存入外部记忆
- **子 Agent 孵化**：当上下文即将溢出时，启动一个干净的子 Agent，通过精心设计的"交接"传递关键信息
- **详细任务描述**：每个子 Agent 需要明确的目标、输出格式、可用工具和任务边界

他们发现，简单的指令如"研究半导体短缺"会导致子 Agent 各自为政——有的研究2021年的汽车芯片危机，有的重复搜索2025年的供应链，完全没有分工。

### 读 vs 写：并行化的根本限制

这个洞察简洁而深刻：

- **读操作天然可并行**：多个 Agent 同时搜索不同方向，即使有些重叠也无害
- **写操作难以并行**：多个 Agent 同时修改代码/内容，冲突几乎是必然的

Anthropic 的 Claude Research 在设计上体现了这一原则：多 Agent 架构只用于研究（读取）阶段，最终的报告撰写（写入）由单一主 Agent 在一次统一调用中完成。这不是偷懒——这是刻意的架构选择。

### 生产环境的三大挑战

**1. 持久执行与错误恢复**

Agent 是有状态的，而且错误会累积。一个长期运行的 Agent 可能跨越几十次工具调用，维持着复杂的中间状态。如果在第15步出错，你不能重头开始——太贵了，用户体验也差。系统必须能从断点恢复。

**2. 调试与可观测性**

传统软件是确定性的——给相同输入，得到相同输出。Agent 是非确定性的——同样的提示，每次可能做出不同决策。当用户反馈"Agent 没找到明显的信息"，你需要看到完整的决策链：用了什么搜索词？选了哪些来源？哪一步工具调用失败了？

**3. 评估 (Evaluation)**

Anthropic 团队的实用建议：
- 从小规模开始，20个测试数据点就够启动
- 用 LLM-as-a-Judge 自动化评分
- 但人工测试始终不可替代

## 多智能体系统的适用条件

```
适合多智能体的任务特征:

  并行度      |==========================| 高 (多个独立方向)
  任务价值    |==========================| 高 (值得花更多Token)
  读取比例    |==========================| 高 (以搜索/研究为主)
  上下文独立性 |==========================| 高 (子任务不共享状态)


不适合多智能体的任务特征:

  依赖度      |==========================| 高 (步骤间强耦合)
  写入比例    |==========================| 高 (以修改/创建为主)
  实时协调    |==========================| 高 (需要Agent间频繁沟通)
  上下文共享   |==========================| 高 (所有Agent需要同一信息)
```

## 为什么重要

这篇文章的价值在于它打破了"多智能体 = 更强"的迷思。Cognition 说"别建多智能体"，Anthropic 说"看我们如何建多智能体"——表面矛盾，实则一致：**不是要不要用多 Agent，而是要在正确的场景用正确的架构。**

核心决策框架：
1. 你的任务能分解为独立的、以"读"为主的子任务吗？如果是，多 Agent 可能有价值
2. 任务价值是否高到可以覆盖多 Agent 带来的额外 Token 成本？
3. 你有能力做好上下文工程吗？——包括任务分发、结果汇总、错误恢复

如果三个问题都是"是"，多 Agent 是合理的选择。否则，一个精心设计的单 Agent 可能更可靠。

## 延伸思考

1. **上下文工程会成为新的核心技能**：正如 Cognition 所言，"上下文工程"是2025年 AI 工程师的第一技能。它不仅仅是写提示词，而是设计一个动态系统来在正确的时间向正确的模型提供正确的信息。

2. **读写分离的架构模式**：这个洞察可以推广——任何多 Agent 系统都应该把"读"和"写"分开设计。读可以并行、冗余、容错；写必须串行、统一、原子化。

3. **经济可行性的门槛**：多 Agent 系统本质上是"用更多 Token 换更好结果"。随着模型价格持续下降，这个经济门槛会不断降低，未来可能有更多任务值得用多 Agent 方案。

4. **评估的关键地位**：无论选择什么架构，没有评估就是在盲飞。先建立评估基线，再决定是否需要多 Agent。数据表明你需要更多并行性时，才加入多 Agent。
