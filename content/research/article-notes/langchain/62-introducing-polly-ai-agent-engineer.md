# Polly：你的 AI Agent 调试搭档

> 一句话总结：Polly 是 LangSmith 内置的 AI Agent 工程师，它能帮你分析长达数百步的 Agent 执行轨迹、跨越多轮对话定位问题根因、用自然语言帮你改写系统提示词——本质上，它用 AI 来调试 AI。

---

## 核心要点

| 要点 | 说明 |
|------|------|
| Agent 调试比传统软件难得多 | 提示词上千行、执行轨迹上百步、对话跨越数天，人工排查几乎不可能 |
| Polly 做三件事 | 调试单次执行轨迹、分析完整对话历史、用自然语言优化提示词 |
| 底层依赖 LangSmith 追踪数据 | Runs（单步执行）、Traces（单次完整执行）、Threads（多轮对话）三层数据结构 |
| 用自然语言交互 | 不需要写代码或手动翻日志，直接用中文/英文提问即可 |
| 提示词工程的终极助手 | 告诉 Polly 你想要什么行为，它自动修改系统提示词 |

## 为什么 Agent 调试这么难？

```
传统软件调试                          Agent 调试
+-----------+                    +------------------+
| 一个函数   |                    | 1000 行系统提示词 |
| 一个报错   |                    | 300 步执行轨迹    |
| 一个堆栈   |                    | 跨 3 天的对话     |
+-----------+                    +------------------+
     |                                    |
     v                                    v
  找到行号                           哪一步出了问题？
  修复 Bug                           哪条指令矛盾了？
  Done.                              改了 A 会不会破坏 B？
                                     ???
```

传统软件出了 Bug，你有堆栈跟踪（Stack Trace），能精确定位到出错的那一行代码。但 Agent 不是这样的。Agent 的问题往往是**弥散性的**——可能是系统提示词里第 847 行的一条指令和第 12 行的另一条指令冲突了，也可能是第 156 步的工具调用返回了意外结果导致后续 200 步全部跑偏。

这就好比你去医院看病，症状是"最近总是觉得累"。传统调试像验血——直接看数值。Agent 调试像中医问诊——需要综合分析望闻问切的大量信息，才能找到根因。

## Polly 的三大能力

### 1. 调试单次执行轨迹（Trace 视图）

当一个 Agent 执行了上百步后给出了错误结果，你可以直接问 Polly：

- "Agent 有没有做什么低效的事情？"
- "Agent 犯了什么错误？"
- "为什么 Agent 选择了 A 方案而不是 B 方案？"
- "问题到底出在哪一步？"

Polly 不只是帮你搜索信息，它理解 Agent 的行为模式（Behavior Patterns），能发现你手动检查时容易遗漏的问题。

### 2. 分析完整对话历史（Thread 视图）

有些问题只看单次执行是看不出来的。比如"Agent 之前一直好好的，突然就不行了"。Polly 可以跨越整个对话历史来分析：

- 总结多轮交互中发生了什么
- 识别 Agent 行为随时间变化的规律
- 精确定位 Agent 何时、为何偏离了正确轨道
- 发现 Agent 在哪个时刻丢失了关键上下文

### 3. 自然语言优化提示词（Prompt 工程）

这是 Polly 最强大的能力。你只需要用自然语言描述你想要的行为，Polly 会自动修改系统提示词。再也不用在上千行指令里手动找、手动改、手动测了。

Polly 还能帮你：
- 定义结构化输出的 Schema
- 配置工具定义（Tool Definitions）
- 添加或优化 Few-shot 示例
- 在不丢失关键指令的前提下压缩提示词长度

## Polly 的工作原理

```
你的 Agent 应用
     |
     | 自动上报执行数据
     v
+---------------------------+
|        LangSmith          |
|  +-------+  +---------+  |
|  | Runs  |  | Traces  |  |     Runs = 每个单步 (LLM 调用、工具执行)
|  +-------+  +---------+  |     Traces = 一次完整执行 (由 Runs 组成的树)
|       +---------+         |     Threads = 完整对话 (由多个 Traces 组成)
|       | Threads |         |
|       +---------+         |
+---------------------------+
     |
     | Polly 读取所有追踪数据
     v
+---------------------------+
|         Polly             |
|  理解 Agent 行为模式       |
|  定位异常和根因            |
|  自然语言修改提示词         |
+---------------------------+
     |
     v
  你的问题得到解答
  你的提示词自动优化
```

Polly 的智能来源于 LangSmith 的追踪基础设施。LangSmith 会捕获你的 Agent 做的每一件事，分三层组织：

| 数据层级 | 含义 | 粒度 |
|---------|------|------|
| Runs（运行） | 单个步骤，如一次 LLM 调用或一次工具执行 | 最细 |
| Traces（轨迹） | 一次完整的 Agent 执行，由多个 Runs 组成的树 | 中等 |
| Threads（线程） | 一段完整对话，包含多个 Traces | 最粗 |

接入 LangSmith 的追踪只需要几分钟。数据流入后，Polly 就能立即开始帮你分析。

## 类比理解

想象你是一家餐厅的老板，你的厨师是一个 AI Agent：

- **没有 Polly 的情况：** 客人投诉菜难吃。你得翻遍厨房的监控录像（几百个小时），一帧一帧看厨师到底在哪一步搞砸了——是切菜的时候？调味的时候？还是火候的时候？然后你还得自己改菜谱（提示词），改完又怕影响其他菜品。
- **有 Polly 的情况：** 你直接问 Polly"这道菜为什么翻车了"，Polly 告诉你"第 47 步放盐的时候，厨师误读了菜谱第 12 条和第 89 条的矛盾指令"。你说"我希望所有菜的盐量都偏淡一点"，Polly 自动帮你改好菜谱，还确保不影响其他菜品。

## 为什么重要

Agent 正在变得越来越复杂。系统提示词从几十行膨胀到上千行，执行轨迹从几步变成几百步，对话从一次性变成持续数天。传统的调试方法——手动看日志、凭直觉改提示词——已经完全跟不上了。

Polly 代表了一个重要趋势：**用 AI 来管理 AI。** 当 Agent 系统的复杂度超过人类的认知带宽时，你需要另一个 AI 来充当"翻译官"和"工程师"。

这也是 LangChain 从"框架公司"向"平台公司"转型的标志性产品。他们不只提供搭建 Agent 的工具，还提供运维和优化 Agent 的智能助手。

## 延伸思考

1. Polly 本身也是一个 AI Agent。当 Polly 自己犯错（比如给出错误的诊断或修改了不该改的提示词），谁来调试 Polly？这是不是一个"元问题"？

2. 如果 Polly 能自动优化提示词，是否意味着"提示词工程师"这个职业会被 AI 取代？还是说 Polly 只是把提示词工程从"手工活"变成了"更高层次的设计活"？

3. Polly 的前提是你的 Agent 跑在 LangSmith 上。如果你用其他追踪平台（或者自建追踪），就用不了 Polly。这种平台绑定策略是好事还是坏事？
