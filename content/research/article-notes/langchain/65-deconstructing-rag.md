# 拆解 RAG：检索增强生成的完整技术地图

> 一句话总结：RAG 不是一个单一技术，而是由查询变换、路由、查询构造、索引设计、后处理五大模块组成的系统工程，每个模块都有多种可选策略。

---

## 核心要点

1. LLM 就像一个新型操作系统的内核，上下文窗口（Context Window）是它的 RAM，检索就是从"硬盘"加载信息到"内存"的过程
2. RAG 之所以重要，是因为它比微调更简单、更灵活，尤其适合需要事实准确性的场景
3. RAG 的五大模块各自解决一个核心问题：怎么问、去哪找、用什么语法查、怎么建索引、怎么筛选结果
4. 检索质量的关键不只是向量相似度，还包括查询改写、数据路由、结构化查询、分块策略和结果重排序

---

## RAG 五大模块总览

| 模块 | 核心问题 | 解决方案 |
|------|----------|----------|
| 查询变换 (Query Transformation) | 用户输入不够好怎么办？ | 查询扩展、改写、压缩 |
| 路由 (Routing) | 数据分散在多个数据源怎么办？ | LLM 动态路由到正确的数据存储 |
| 查询构造 (Query Construction) | 目标数据库需要特定查询语法？ | Text-to-SQL、Text-to-Cypher、元数据过滤 |
| 索引设计 (Indexing) | 如何组织数据以获得最佳检索效果？ | 分块大小调优、嵌入与检索解耦 |
| 后处理 (Post-Processing) | 检索回来的文档太多或有冗余？ | 重排序（Re-ranking）、分类 |

---

## 模块一：查询变换

用户的提问往往不是最适合检索的形式。查询变换就是在检索之前，先对用户输入进行优化处理。

```
                     查询变换的三种策略

原始问题: "红袜队和爱国者队谁最近赢了冠军？"
          |
          +---> [查询扩展] 拆成多个子问题
          |         |
          |         +--> "红袜队最后一次夺冠是什么时候？"
          |         +--> "爱国者队最后一次夺冠是什么时候？"
          |
          +---> [查询改写] 重新措辞以提升检索质量
          |         |
          |         +--> "红袜队 冠军 年份 最新"
          |
          +---> [查询压缩] 把对话历史浓缩为单一检索问题
                    |
                    +--> 用户说了10轮对话，最终问题是...
```

**查询扩展（Query Expansion）**：把一个复杂问题拆成多个更具体的子问题，分别检索，再合并去重。Multi-query retriever 会生成子问题、分别检索、返回去重后的文档。RAG Fusion 在此基础上增加了排序。Step-back prompting 则反其道而行之，生成一个更高层次的"退一步"问题，用更抽象的概念来锚定答案。

**查询改写（Query Rewriting）**：用户的原始提问可能措辞不当。Rewrite-Retrieve-Read 方法先让 LLM 改写问题，再去检索，再生成回答。就像你去图书馆找书，如果你的关键词不对，图书管理员会先帮你换个更准确的说法。

**查询压缩（Query Compression）**：在多轮对话中，当前问题的含义可能依赖之前的对话历史。查询压缩把完整的对话上下文浓缩成一个独立的、适合检索的问题。

## 模块二：路由

在演示中数据通常只存在一个向量库里，但在生产环境中，数据往往分散在多个数据源中：关系型数据库、图数据库、向量库、文档系统等等。路由就是让 LLM 根据问题的性质，把查询导向正确的数据源。

这就像一个医院的分诊台：病人（用户问题）来了之后，分诊护士（LLM）根据症状（问题内容）决定应该去内科（SQL 数据库）、外科（图数据库）还是体检中心（向量库）。

---

## 模块三：查询构造

即使路由到了正确的数据源，自然语言还需要转换成该数据源能理解的查询语法。

| 转换类型 | 目标数据源 | 说明 |
|----------|------------|------|
| Text-to-SQL | 关系型数据库 | 将自然语言转为 SQL 查询，开源 LLM 也能胜任 |
| Text-to-Cypher | 图数据库 | 将自然语言转为 Cypher 查询语言，适合多对多关系 |
| Text-to-Metadata Filter | 向量库 | 将自然语言转为结构化元数据过滤条件 |

**Text-to-SQL** 的做法是把自然语言问题和相关表结构一起传给 LLM，让它生成 SQL。一个有趣的趋势是混合类型存储——关系数据库中嵌入向量列（如 PostgreSQL 的 pgvector 扩展），让 SQL 的表达力和语义搜索的灵活性结合起来。

**Text-to-Cypher** 适用于图数据库。图数据库的优势在于它能天然建模数据之间的关系，而且扩展关系类型不需要像关系数据库那样进行昂贵的模式变更。如果你的数据有大量多对多关系或复杂层级结构，图数据库比表格更合适。

**Text-to-Metadata Filter** 让你可以用自然语言描述过滤条件，LLM 会自动转换成向量库的结构化过滤语法。Self-query retriever 就是实现这个功能的组件。

## 模块四：索引设计

```
        索引设计的两个关键决策

  决策1: 分块大小 (Chunk Size)
  +--------+  +--------+  +--------+
  |  小块  |  |  中块  |  |  大块  |
  | 精确   |  | 平衡   |  | 完整   |
  | 但碎片 |  |        |  | 但冗余 |
  +--------+  +--------+  +--------+

  决策2: 嵌入策略 — 检索用的 vs 传给 LLM 的可以不同
  
  原始长文档
      |
      +---> [摘要/小块] --嵌入--> 用于检索匹配
      |
      +---> [完整原文] ----------> 匹配后传给 LLM 生成答案
```

**分块大小（Chunk Size）**：这是索引构建的核心参数。分块太小，语义信息被割裂；分块太大，嵌入向量的辨识度降低，还浪费上下文窗口空间。OpenAI 在实践中发现，仅仅调整分块大小就能带来显著的性能提升。你应该检查不同分块策略下，语义相关的内容是否被不自然地切断。

**嵌入策略解耦（Document Embedding Strategy）**：这是索引设计中最简洁也最有用的思想——把"用于检索的内容"和"传给 LLM 的内容"分离开来。比如一段冗长的文本，你可以嵌入它的摘要（更利于检索匹配），但检索命中后把原文传给 LLM（信息更完整）。Multi-vector retriever 和 Parent-document retriever 分别实现了这两种策略。

对于包含文本和表格混合内容的半结构化文档，可以单独提取每个表格，生成适合检索的摘要，但把原始表格返回给 LLM。对于包含图片的文档，可以用多模态 LLM 生成图片摘要并嵌入，检索时用摘要匹配，生成答案时把原图传给 LLM。

## 模块五：后处理

检索回来的文档可能有冗余、不相关或顺序不对的问题。后处理就是在把文档传给 LLM 之前做最后的筛选和排序。

**重排序（Re-ranking）**：初次检索返回大量文档后，用专门的重排序模型（如 Cohere ReRank）对文档进行二次排序，过滤冗余，保留最相关的。RAG Fusion 使用倒数排名融合（Reciprocal Rank Fusion）对多次检索的结果进行综合排序。

**分类（Classification）**：对每个检索到的文档进行内容分类，然后根据分类结果选择不同的提示词模板。比如，检索回来的文档有些是技术文档，有些是用户反馈，你可以用不同的提示词策略来处理它们。

## 类比理解

把 RAG 想象成你在一个巨大图书馆里回答问题的过程：

1. **查询变换** = 你先理清自己到底要找什么。"这两个球队谁更近赢了冠军"需要拆成两个问题分别查。
2. **路由** = 你决定去哪个阅览室。体育统计去数据库区，历史评论去期刊区。
3. **查询构造** = 你翻译自己的需求为图书馆的检索系统能理解的语言。数据库要用 SQL，卡片目录要用关键词。
4. **索引设计** = 图书馆管理员决定怎么组织书架。是每一章单独放，还是整本书放在一起？目录卡片上写摘要还是原文？
5. **后处理** = 你把找到的一堆资料摊开，去掉重复的，按相关度排序，只把最有用的几份带回桌子上细看。

---

## 为什么重要

RAG 看起来简单——检索文档，塞进提示词，让 LLM 回答。但这种朴素做法在遇到真实场景时会迅速暴露问题：用户问题措辞不当、数据分散在多个系统、检索回来的文档有噪音、分块策略切断了关键信息。理解 RAG 的五大模块，让你能系统性地诊断和优化检索质量，而不是在黑箱里反复调参。

## 延伸思考

1. 你的 RAG 系统中，检索质量的瓶颈到底在哪个模块？是查询本身的问题，还是索引设计的问题，还是后处理不够？
2. 对于你的数据类型（纯文本、表格、图片混合），嵌入策略解耦能带来多大的提升？
3. 随着上下文窗口越来越长（100K、1M Token），RAG 是否会被"把所有内容塞进上下文"的暴力方案取代？如果不会，为什么？
4. 在你的场景中，用开源小模型处理查询扩展、查询构造等窄定义任务是否可行？这能节省多少成本？
