# 构建 LangGraph：从第一性原理设计 Agent 运行时

> **一句话总结**：LangGraph 是 LangChain 团队从零设计的 Agent 运行时（Runtime），它针对 LLM 天生的高延迟和不确定性，提供了并行化、流式输出、任务队列、检查点、中断恢复和调试观测六大核心能力，让 Agent 真正可以上生产环境。

---

## 核心要点

1. **Agent 的核心挑战是延迟**：LLM 本身就慢，加上测试时计算（test-time compute）越来越重，一个 Agent 调用可能从毫秒级变成分钟甚至小时级。你需要在漫长的等待中让用户保持参与感。
2. **现有框架都不够用**：DAG 框架（如 Airflow）不支持循环，而 Actor 框架（如 Ray）抽象层级太高，不适合 Agent 需要的细粒度控制。LangGraph 因此诞生。
3. **设计哲学是"少假设、像写代码"**：框架应该尽量少对未来做假设，并且让开发者写 Agent 的感觉和写普通代码一样自然。
4. **运行时基于 Channel-Node 算法**：Channel 持有数据并带版本号，Node 是订阅 Channel 的函数——当 Channel 版本更新时，对应的 Node 被触发执行。这套机制天然支持并行和增量计算。
5. **六大特性作为积木自由组合**：并行化、流式输出、任务队列、检查点、中断/恢复、调试观测——开发者可以按需选用，不必全盘接受。

---

## 概念对照表

| 概念 | 含义 | 生活类比 |
|------|------|----------|
| Channel（通道） | 带版本号的数据容器，是 Node 之间传递状态的管道 | 快递柜：每个格子有编号和版本，放入新包裹时版本号递增 |
| Node（节点） | 订阅 Channel 的函数，Channel 更新时被触发 | 快递员：盯着特定柜子，一有新包裹就去取件处理 |
| StateGraph | 最常用的开发者 SDK，把 Channel/Node 封装成图结构 | 地铁线路图：车站是 Node，轨道是 Edge，乘客（数据）沿线路流动 |
| Checkpoint（检查点） | 某一时刻 Agent 全部状态的快照 | 游戏存档：随时可以读档回到之前的进度 |
| 流式输出（Streaming） | 在结果完全生成之前就逐步推送中间状态给用户 | 餐厅先上前菜：主菜还在做，但你已经有东西吃了 |
| 任务队列（Task Queue） | 把 Agent 执行与触发请求解耦，支持重试和公平调度 | 医院叫号系统：病人取号后可以离开，轮到时再回来 |

## 执行算法流程

```
  ┌─────────────┐
  │  写入输入    │  用户请求写入 Input Channel
  │  Channel     │
  └──────┬──────┘
         │ 触发版本更新
         v
  ┌─────────────┐
  │  调度器      │  比较 Channel 版本与 Node 上次见到的版本
  │  (Planner)   │  选出需要执行的 Node
  └──────┬──────┘
         │
         v
  ┌─────────────────────────┐
  │  并行执行选中的 Node     │  每个 Node 拿到 Channel 值的
  │  Node_A │ Node_B │ ...  │  独立副本，互不干扰
  └──────┬──────────┬───────┘
         │          │
         v          v
  ┌─────────────┐
  │  合并结果    │  用 Reducer 把多个 Node 的输出
  │  到 Channel  │  合并回 Channel，版本号+1
  └──────┬──────┘
         │
         v
  ┌─────────────┐
  │  有 Node     │──是──> 回到调度器
  │  需要执行？  │
  └──────┬──────┘
         │ 否
         v
  ┌─────────────┐
  │  读取 Output │  返回最终结果
  │  Channel     │
  └─────────────┘
```

## 类比理解：Agent 运行时就像一个餐厅后厨系统

想象你经营一家忙碌的餐厅。传统的后端服务就像快餐店——顾客下单、几秒出餐、交易完成。但 Agent 更像一家高级餐厅，一道主菜可能要做 20 分钟。

在这种场景下，你需要：
- **并行化**：多个厨师同时做不同菜品，而不是一个厨师从头做到尾。
- **流式输出**：先上前菜和饮料，主菜好了再端上来，让顾客不会干等。
- **任务队列**：用叫号系统管理订单，不让任何一桌被遗忘。
- **检查点**：如果某道菜做砸了，不用从头重来，从上一步重做即可。
- **中断/恢复**：主厨觉得某个步骤需要顾客确认（比如牛排几分熟），可以暂停制作，等顾客回复后继续。
- **调试观测**：后厨有监控摄像头，出问题时可以回看每个步骤。

LangGraph 做的事情，就是为 Agent 搭建这样一套完整的后厨管理系统。

## 为什么 DAG 框架不够用？

很多人的第一反应是："用 Airflow 之类的 DAG 框架不就行了？" 问题在于 DAG（有向无环图，Directed Acyclic Graph）从定义上就不支持循环。而 Agent 的核心模式恰恰是循环——LLM 调用工具、检查结果、决定是否再次调用，这是一个 while 循环。DAG 框架无法表达这种计算图。

Actor 框架（如 Ray、Erlang）虽然支持循环，但它们的抽象太高层：每个 Actor 是独立的消息收发单元，很难实现"暂停某一步等人类审批，然后精确恢复"这种 Agent 特有的需求。

LangGraph 的 Channel-Node 模型巧妙地取了中间路线：它像 DAG 一样有清晰的步骤结构，但通过版本驱动的触发机制天然支持循环。

## 性能特性

LangGraph 的性能由以下关键变量控制：

| 变量 | 说明 | 对性能的影响 |
|------|------|-------------|
| Node 数量 | Agent 中的步骤数 | 调度器选择时间线性增长 |
| Edge 数量 | Node 之间的连接 | 影响图遍历复杂度 |
| Channel 数量 | 状态对象中的键数 | 影响状态复制和合并的开销 |
| 并行 Node 数 | 同一步中并行执行的 Node | 越多越能利用并发，但内存开销也越大 |
| 调用历史长度 | 当前执行的步骤记录 | 影响检查点的存储和恢复时间 |
| 线程数 | 独立的调用实例 | 各线程之间完全隔离，水平扩展 |

关键设计：执行在没有 Node 需要运行时自然停止，不需要额外的"结束"动作。这意味着调度器的开销是最小的——它只在需要时才做事。

---

## 为什么重要

LangGraph 解决的不是"怎么调用一次 LLM"的问题，而是"怎么让 Agent 在生产环境中可靠运行"的问题。随着 Agent 从玩具变成产品，你会不可避免地遇到这些挑战：Agent 跑了 3 分钟后挂了怎么办？用户等不及怎么办？某个步骤需要人工审批怎么办？出了 bug 怎么定位？

这些问题在传统 Web 开发中已经被解决（数据库事务、消息队列、断点续传），但在 Agent 领域需要重新设计，因为 LLM 的不确定性和长延迟带来了全新的约束条件。LangGraph 的价值在于把这些基础设施抽象成开箱即用的积木。

## 延伸思考

1. **LangGraph 的 Channel-Node 模型和 React 的状态管理有什么异同？** 两者都是"状态变化触发重新计算"，但 React 是 UI 渲染，LangGraph 是 Agent 执行。思考：如果把 Agent 看作一种"后端 React"，会带来什么启发？
2. **检查点粒度如何选择？** 太细会增加存储开销，太粗会导致回退代价过大。这和数据库的 WAL（Write-Ahead Log）策略有什么类比？
3. **随着模型推理速度越来越快，LangGraph 的某些特性（比如流式输出）会不会变得不那么重要？** 还是说，Agent 的复杂度会同步增长，让这些特性始终必要？
