# Agent 中间件：用插件思维驯服复杂代理

> 一句话总结：LangChain 1.0 引入中间件（Middleware）机制，让你通过可组合、可复用的插件来定制代理的核心循环，而不是在一堆互相耦合的参数里迷路。

---

## 核心要点

| 要点 | 说明 |
|------|------|
| 核心问题 | Agent 框架做到生产级别时，上下文工程（Context Engineering）成为最大挑战 |
| 根本原因 | 需要精细控制输入模型的内容，但框架的简单循环不够用 |
| 旧方案的缺陷 | 暴露大量互相依赖的参数，难以组合和复用 |
| 新方案 | 中间件（Middleware）——像 Web 服务器中间件一样的可插拔组件 |
| 三个钩子 | `before_model`、`after_model`、`modify_model_request` |

---

## 为什么 Agent 框架这么难做好

所有 Agent 框架的核心都很简单：一个模型节点（Model Node）和一个工具节点（Tool Node）组成的循环。模型决定调用什么工具，工具执行后把结果返回给模型，如此反复。

```
最简 Agent 循环：

  +--------+     调用工具      +--------+
  | Model  | --------------> |  Tool  |
  | Node   | <-------------- |  Node  |
  +--------+   返回结果       +--------+
       |
       v
     输出结果
```

这个循环对入门项目完全够用。但当你把它推向生产环境，问题就来了：**上下文工程**（Context Engineering）——送进模型的内容决定了模型输出的质量。你想要精细控制送进去的每一部分，但简单循环给你的控制力太少了。

具体来说，随着复杂度提升，你会发现需要控制三件事：

| 你想控制什么 | 为什么需要 |
|-------------|----------|
| Agent 的状态不只是消息列表 | 可能需要存储用户偏好、任务进度等额外信息 |
| 送进模型的具体内容 | 需要动态裁剪消息、注入上下文、做摘要 |
| 步骤的执行顺序 | 需要在特定步骤前后插入逻辑，如安全检查、人工审核 |

---

## 类比理解

想象你开了一家餐厅。最初菜单简单，厨师一个人从备料到出菜全搞定。但随着菜品复杂度提升，你需要专门的备菜员、质检员、摆盘师。Agent 中间件就像这些专业角色——你不需要重写整个厨房流程，只需要在"做菜"这个核心步骤前后插入专业环节。

```
餐厅类比：

  [备菜员]    [厨师做菜]    [质检员]    [摆盘师]
  (before)    (核心步骤)    (after)     (after)

Agent 中间件：

  [before_model]  -->  [模型调用]  -->  [after_model]
  [modify_model_request]
```

## 旧方案：参数爆炸

LangChain 团队在过去两年里尝试通过不断添加参数来解决定制化需求。他们依次允许用户指定：

| 参数 | 功能 |
|------|------|
| 运行时配置 | 传入连接字符串、只读用户信息 |
| 任意状态模式（State Schema） | 用户或代理都能更新的自定义状态 |
| 动态提示函数 | 返回提示词的函数而非固定字符串 |
| 消息列表函数 | 完全控制发送给模型的消息列表 |
| 模型前钩子（Pre-model Hook） | 模型调用前运行，可更新状态或跳转节点 |
| 模型后钩子（Post-model Hook） | 模型调用后运行，用于人工审核或安全护栏 |

这些参数确实提供了高度定制能力，但代价很大：参数之间互相依赖，难以协调；无法方便地组合多种定制；也很难提供开箱即用的方案给其他开发者复用。

---

## 新方案：中间件模式

LangChain 1.0 用中间件（Middleware）彻底重新设计了这个问题。核心 Agent 循环保持不变——依然是模型节点 + 工具节点。但现在你可以通过中间件在循环的关键位置插入逻辑：

| 钩子 | 执行时机 | 能做什么 |
|------|---------|---------|
| `before_model` | 模型调用之前 | 更新状态、跳转到其他节点（如摘要压缩长对话） |
| `after_model` | 模型调用之后 | 更新状态、跳转到其他节点（如人工审核、安全护栏） |
| `modify_model_request` | 模型调用之前 | 临时修改工具列表、提示词、消息、模型配置、输出格式 |

关键设计：你可以为一个 Agent 提供多个中间件。它们的执行顺序和 Web 服务器中间件一样——进入时正序执行（`before_model`、`modify_model_request`），返回时倒序执行（`after_model`）。

```
多中间件执行顺序（类比洋葱模型）：

  请求进入
    |
    v
  [中间件A: before_model]
    |
    v
  [中间件B: before_model]
    |
    v
  [中间件A: modify_model_request]
    |
    v
  [中间件B: modify_model_request]
    |
    v
  ======= 模型调用 =======
    |
    v
  [中间件B: after_model]    <-- 注意：倒序
    |
    v
  [中间件A: after_model]
    |
    v
  继续循环或输出
```

中间件还可以声明自己需要的自定义状态和工具，真正做到自包含和可复用。

## 三个开箱即用的中间件

LangChain 1.0 alpha 版本附带了三个实用的中间件实现：

| 中间件 | 使用的钩子 | 功能 |
|--------|-----------|------|
| 人工审核（Human-in-the-Loop） | `after_model` | 在工具调用前插入中断，获取人工反馈 |
| 对话摘要（Summarization） | `before_model` | 当消息量超过阈值时自动压缩历史消息 |
| Anthropic 提示缓存（Prompt Caching） | `modify_model_request` | 为消息添加特殊缓存标记，节省 API 费用 |

安装方式：

```
# Python
pip install --pre -U langchain

# JavaScript
npm install langchain@next
```

## 为什么重要

中间件模式解决了 Agent 框架发展中的一个根本矛盾：框架需要足够简单让人入门，又需要足够灵活让人用于生产。以前的方案是不断给框架加参数，结果变成了一个臃肿的"万能函数"。中间件把每个定制点封装成独立的、可组合的单元，就像乐高积木一样。

这也打开了生态共建的大门——社区可以开发和分享中间件，开发者长期以来一直在要求"可以插入 LangGraph Agent 的节点集合"，中间件正是这个需求的答案。

对你来说，最重要的启示是：**不要在核心循环里硬编码定制逻辑，而是用中间件把它们解耦出来。** 这个设计原则不限于 LangChain，适用于任何 Agent 系统。

## 延伸思考

1. 中间件的执行顺序至关重要——如果摘要中间件在安全检查中间件之前运行，可能会把关键信息压缩掉。你怎么设计中间件的优先级和依赖关系？
2. Web 服务器中间件的"洋葱模型"已经被验证了几十年。Agent 中间件是否会面临不同的挑战？比如模型调用的不确定性带来的问题？
3. 当中间件数量增多，调试变得困难。Agent 中间件的可观测性应该怎么设计？
4. 未来是否会出现"中间件市场"，让开发者像安装 npm 包一样选择和组合 Agent 能力？
