# 基于图的元数据过滤：提升 RAG 向量搜索的精度

> 一句话总结：把知识图谱（Knowledge Graph）中的结构化关系当作元数据过滤条件，在向量搜索之前先用图查询缩小候选文档范围，从而实现传统向量数据库做不到的复杂条件检索。

---

## 核心要点

### 1. 向量搜索的盲区

向量相似度搜索擅长理解语义（"这段文字和那段文字意思接近吗？"），但完全不擅长处理结构化条件。比如你问"2021年有没有新政策发布？"，向量搜索只能找到语义相关的文档，却无法按年份精确过滤。元数据过滤（Metadata Filtering）就是为了弥补这个盲区——先按结构化条件缩小范围，再在子集里做向量搜索。

### 2. 图数据库的独特优势

传统的元数据过滤只能处理扁平属性（日期、分类标签），但真实世界的数据是高度关联的。比如你想问"Rod Johnson 担任董事的公司有没有实施远程办公政策？"，这需要跨越"人物 -> 董事会 -> 公司 -> 文章"多层关系。图数据库（如 Neo4j）天然擅长表达和查询这种多跳关系，这是传统向量数据库做不到的。

### 3. 动态 Cypher 查询生成

这篇文章的核心实现是一个 `get_organization_news` 函数，它接收四个可选参数（topic、organization、country、sentiment），根据用户输入动态拼接 Cypher 查询语句。如果只有 topic 没有过滤条件，就直接用向量索引搜索；如果有过滤条件，就先构造 WHERE 子句缩小范围，再在子集中做余弦相似度排序。这个过程是确定性的（Deterministic），不是让 LLM 自由生成 Cypher，而是用程序逻辑拼接。

### 4. 实体消歧与安全防护

当用户提到一个组织名时，系统先用全文索引（Full-text Index）查找候选实体。如果找到多个匹配项（比如用户说"Apple"，数据库里有"Apple Inc."和"Apple Records"），就让 LLM 追问用户具体指哪一个。同时，所有查询参数都通过参数化查询传递（而非字符串拼接），防止 Cypher 注入攻击。

### 5. Agent 工具封装

整个函数被包装为一个 LangChain Agent 工具（Tool），Agent 根据用户自然语言输入自动提取参数并调用。通过 few-shot 示例和枚举值约束，确保 LLM 正确理解每个参数的含义。

## 对比表格

| 维度 | 纯向量搜索 | 扁平元数据过滤 | 图元数据过滤 |
|------|-----------|---------------|-------------|
| 语义理解 | 强 | 弱（依赖向量搜索部分） | 强（结合向量搜索） |
| 结构化过滤 | 不支持 | 单层属性（日期/标签） | 多跳关系（人 -> 公司 -> 文章） |
| 查询示例 | "远程办公" | "2021年 + 远程办公" | "Rod Johnson 董事公司 + 远程办公" |
| 数据模型 | 扁平文档 | 文档 + 键值元数据 | 知识图谱（节点 + 关系） |
| 适用数据库 | Pinecone, Weaviate | Pinecone, Chroma | Neo4j, Amazon Neptune |

## 类比理解

想象你在一个大型企业集团的档案室里找资料。

**纯向量搜索**：你告诉管理员"我要找关于远程办公的资料"，管理员根据内容相似度给你一堆文件。但这些文件可能来自任何子公司、任何年份、任何情感倾向——你要自己筛选。

**扁平元数据过滤**：管理员先按标签（年份=2023、类别=人力资源）缩小范围，再按内容相似度找。好了一些，但你没法表达"找集团投资的那些公司的资料"这种跨公司关系。

**图元数据过滤**：管理员打开一张巨大的关系网络图——谁投资了谁、谁的董事是谁、谁在哪个国家。你说"找 Rod Johnson 当董事的公司里，关于远程办公的正面新闻"，管理员先在关系图上走几步定位到目标公司，再在这些公司的档案里做内容搜索。这就是图的力量。

## 为什么重要

1. **真实世界的数据是关联的**：企业数据不是孤立的文档，而是一张关系网。供应链、投资关系、人员组织——这些结构化信息蕴含着巨大的检索价值。
2. **预过滤比后过滤更高效**：先用结构条件缩小候选集，再做向量搜索，比先搜索再过滤（Post-filtering）的精度和效率都更高，因为后者可能在 top-k 中丢失相关结果。
3. **确定性查询生成更可靠**：这篇文章没有让 LLM 自由生成 Cypher（容易出错），而是用程序逻辑根据参数拼接查询，LLM 只负责从自然语言中提取参数。这种"LLM 做理解、代码做执行"的分工模式更加稳健。

---

## 延伸思考

1. **动态拼接 vs. LLM 直接生成 Cypher？** 本文选择了动态拼接，牺牲了灵活性但换取了可靠性。对于更复杂的查询需求，可以考虑让 LLM 生成 Cypher，但需要加上校验和重试机制（参见 Query Construction 一文）。
2. **如何构建这样的知识图谱？** 文章使用了 Neo4j 的示例数据集，但真实场景中你需要从非结构化数据中抽取实体和关系（Named Entity Recognition + Relation Extraction），这本身就是一个值得深入的课题。
3. **图 + 向量 + SQL 三合一？** 随着 Neo4j 等图数据库也开始原生支持向量索引，未来的 RAG 系统可能在一个数据库中同时完成图查询、向量搜索和结构化过滤，而不需要拼接多个系统。
