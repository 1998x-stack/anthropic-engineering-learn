# Agent 授权的两种模式：代理用户 vs 自主身份

> 原文: [Two different types of agent authorization](https://www.langchain.com/blog/two-different-types-of-agent-authorization) | LangChain Blog | 2026-03-23

## 一句话总结

Agent 的授权分两种模式：**Assistant（代理用户）** 用终端用户的身份和权限操作，**Claw（自主身份）** 拥有独立的固定凭证——两种模式适用于截然不同的场景，理解区别是设计安全 Agent 的关键。

---

## 核心要点

### 1. On-behalf-of 模式：Agent 代替用户行动

在这种模式下，Agent 就像用户的"分身"——它用的是用户自己的身份凭证。当 Alice 使用一个连接了 Notion 和 Rippling（HR 系统）的入职引导 Agent 时，Agent 能看到的内容完全等同于 Alice 自己登录后能看到的内容。Alice 看不到 Bob 的私人文档，Agent 也看不到。

实现这种模式需要两步：第一，识别当前用户是谁（是 Alice 还是 Bob？）；第二，把用户的身份凭证在运行时传递给工具调用。

```
On-behalf-of 模式的数据流
=========================

  Alice 使用 Agent          Bob 使用 Agent
       |                        |
       v                        v
  +----------+            +----------+
  | Agent    |            | Agent    |
  | 携带     |            | 携带     |
  | Alice 的 |            | Bob 的   |
  | 凭证     |            | 凭证     |
  +----------+            +----------+
       |                        |
       v                        v
  +---------+             +---------+
  | Notion  |             | Notion  |
  | Alice   |             | Bob 的  |
  | 的页面  |             | 页面    |
  +---------+             +---------+

  Alice 的 Agent 看不到 Bob 的私密文档
  Bob 的 Agent 看不到 Alice 的私密文档
```

### 2. Claw 模式：Agent 拥有独立身份

OpenClaw 的出现催生了第二种思路。Alice 创建了一个 Agent，配置好它能访问的工具和数据，然后分享给其他人使用。此时 Agent 不再使用终端用户的凭证，而是使用 Alice（或一个专用账户）预先配置的固定凭证。

这里有一个微妙的安全考量：如果直接用 Alice 自己的账号凭证，Agent 就能看到 Alice 的所有数据——包括她可能不希望别人通过 Agent 查看的私密文档。因此实践中，开发者通常会在 Notion、Rippling 等服务中创建**专用的服务账户**，精确控制 Agent 能访问的范围。所有使用这个 Agent 的人，实际上共享同一套凭证。

### 3. 两种模式的对比

| 维度 | Assistant（代理用户） | Claw（自主身份） |
|------|---------------------|-----------------|
| 凭证来源 | 终端用户自己的凭证 | 创建者/专用账户的固定凭证 |
| 权限范围 | 因用户而异 | 所有使用者权限相同 |
| 数据隔离 | 天然隔离（用户只能看自己的） | 需要手动控制（通过专用账户限制） |
| 适用场景 | 用户数据敏感、需要个性化访问 | 共享知识库、自动化任务 |
| 典型例子 | 入职引导 Agent（查看个人 HR 信息） | 产品竞品监控 Agent |
| Human-in-the-Loop | 通常不需要（用户已授权） | 强烈建议（共享凭证风险更高） |

### 4. LangSmith Fleet 的实践

LangSmith Fleet 同时支持两种模式，并用不同的名称区分：

- **Assistants**：对应 On-behalf-of 模式，使用终端用户的凭证
- **Claws**：拥有自己的固定凭证

Fleet 还引入了**通道（Channels）**的概念——Agent 可以通过 Slack、邮件等不同渠道暴露给用户。通道与授权模式的组合进一步强调了**人机协同审批（Human-in-the-Loop）**的必要性：当你用固定凭证创建一个 Agent 并通过公开渠道暴露时，任何人都可能触发它执行操作。对于敏感操作（如发送邮件、修改数据），必须设置审批门禁。

### 5. 三个真实案例

```
案例对照表
==========

+--------------------+------------+----------------------------------+
| Agent              | 类型       | 授权逻辑                          |
+--------------------+------------+----------------------------------+
| 入职引导 Agent      | Assistant  | 连接 Slack + Notion，使用终端     |
| (Onboarding)       |            | 用户自己的凭证。Alice 只能看到    |
|                    |            | 自己的入职文档和 Slack 消息。      |
+--------------------+------------+----------------------------------+
| 邮件 Agent          | Claw       | 自动回复收到的邮件。无论谁发邮    |
| (Email)            |            | 件，Agent 都用创建者的日历判断    |
|                    |            | 会议可用性。发邮件和创建日历邀    |
|                    |            | 请需要人工审批。                   |
+--------------------+------------+----------------------------------+
| 产品 Agent          | Claw       | 监控竞品、回答产品问题和路线图。  |
| (Product)          |            | 拥有专用 Notion 账户，通过自定    |
|                    |            | 义 Slack Bot 暴露。               |
+--------------------+------------+----------------------------------+
```

邮件 Agent 是一个典型的"需要 Human-in-the-Loop"的案例——它可以查看日历来判断你是否有空，但发送邮件和创建会议邀请这种不可逆操作，必须经过人工确认。

## 类比理解

把两种模式想象成**公司前台的两种工作方式**：

- **Assistant 模式**像一个临时前台，每来一个访客就拿着访客自己的工牌去帮他取文件。Alice 来了就用 Alice 的权限，Bob 来了就用 Bob 的权限，前台本身没有任何数据访问权。
- **Claw 模式**像一个常驻前台，公司给了他一把特定的钥匙，只能打开"公共资料室"。不管谁来问，前台都用这把固定的钥匙去取资料——所以你必须确保这把钥匙只能打开该让所有人看到的房间。

---

## 为什么重要

- **选错模式会导致安全漏洞**：用 Claw 模式处理个人敏感数据（如 HR 信息），可能导致数据泄露给其他用户
- **选错模式会导致体验割裂**：用 Assistant 模式做共享知识库查询，每个用户都需要单独授权，增加不必要的摩擦
- **Human-in-the-Loop 不是可选项**：在 Claw 模式下，Agent 用固定凭证执行操作，如果没有人工审批门禁，一次误触可能影响所有人
- **混合模式是趋势**：未来的 Agent 可能在一个任务中同时需要两种模式——查个人数据用 Assistant，查公共知识库用 Claw

---

## 延伸思考

1. **权限的"时间维度"**：Claw 模式的固定凭证是持久的，如果凭证泄露，影响范围是所有用户和所有历史数据。是否需要定期轮换？是否需要设置凭证的有效期？
2. **从两种到 N 种**：LangChain 团队暗示这只是"Agent 授权的起点"。未来可能出现更细粒度的模式，比如"部分代理用户"——Agent 用用户的身份读数据，但用专用账户写数据。
3. **多 Agent 编排中的授权链**：当一个 Agent 调用另一个 Agent 时，Claw A 调用 Assistant B，B 应该用谁的身份？这种"授权链"的设计将成为复杂 Agent 系统的核心挑战。
