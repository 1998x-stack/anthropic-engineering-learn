# 96 | 重建 Chat LangChain：从向量检索到多源智能体的实战复盘

> 原文: Why We Rebuilt LangChain's Chatbot and What We Learned (LangChain Blog, 2025-11)

## 一句话总结

LangChain 团队发现自己的客服聊天机器人不好用，于是复制了内部工程师"查文档 + 查知识库 + 查代码"的三步工作流，用 Deep Agent + 子图架构重建了 Chat LangChain，响应时间降到 15 秒以内，引用精确到行号。

---

## 核心要点

### 1. 内部人不用，说明产品有问题

Chat LangChain 最初基于传统向量检索 RAG 构建。但 LangChain 自己的技术支持工程师并不用它——因为回答太浅，缺乏上下文。他们的真实工作流是：先查官方文档了解功能设计，再查知识库看别人踩过的坑，最后用 Claude Code 翻源码确认实际实现。这三步合在一起才能解决真正的生产问题。

### 2. 放弃向量嵌入，拥抱直接 API 访问

向量检索对结构化的产品文档有三个硬伤：分块破坏文档结构(Chunking breaks structure)、频繁更新需要不断重索引(Constant reindexing)、引用模糊无法溯源(Vague citations)。团队的突破性认识是——文档本身就是有组织的，不需要"更聪明的检索"，而是让 Agent 直接访问原始结构。于是他们改用 Mintlify API 返回完整页面、用 ripgrep 搜索代码库、用 Pylon API 查知识库文章。

### 3. 双模架构：快速 Agent + 深度 Agent

简单问题用 `createAgent`(Create Agent) 处理，3-6 次工具调用、15 秒内回答，搭配 Claude Haiku 4.5 做工具调用速度极快。复杂问题启用 Deep Agent，下挂三个专属子图(Subgraph)——文档搜索、知识库搜索、代码搜索——各自独立检索、过滤、提炼后再汇总给主 Agent，耗时 1-3 分钟但深度到位。

### 4. 子图解决上下文爆炸

如果把所有搜索结果(5 页文档、12 篇知识库文章、20 段代码)直接塞给主 Agent，上下文窗口会爆掉，回答要么冗长要么遗漏关键点。子图架构让每个子 Agent 只向上传递"黄金数据"(Golden Data)——文档子 Agent 读了 5 页可能只返回 2 段，代码子 Agent 搜了 50 个文件可能只返回关键的 10 行代码。

### 5. 工具设计模拟人类工作流

每类工具都是两步式：先扫描标题/模式匹配缩小范围，再精读具体内容。文档搜索返回完整页面而非碎片。知识库先列 50 篇文章标题，选 2-3 篇相关的再读全文。代码搜索先 ripgrep 匹配模式、再 tree 看目录结构、最后读具体行号。

### 6. 生产级中间件不可少

Agent 设计再优雅也需要基础设施兜底：Guardrails(过滤无关问题)、Retry(API 失败自动重试)、Fallback(模型不可用时自动切换)、Cache(相同查询结果缓存)。这些对用户透明，但对可靠性至关重要。

## 架构演进对照表

| 维度 | 旧版 (向量 RAG) | 新版 (多源 Agent) |
|------|-----------------|-------------------|
| 检索方式 | 向量相似度搜索 | API 直接访问 + 模式匹配 |
| 数据粒度 | 500-token 碎片 | 完整页面/完整文章/精确行号 |
| 数据源 | 仅文档 | 文档 + 知识库 + 代码库 |
| 更新机制 | 需要重新分块、嵌入、上传 | 实时访问，无需重索引 |
| 引用质量 | 模糊，难以溯源 | 精确到页面 URL 或代码行号 |
| 响应时间 | 变化大 | 简单问题 < 15秒，复杂问题 1-3分钟 |
| 架构 | 单一 RAG 链 | 双模(快速 Agent + 深度 Agent) |

## 工具调用示意

```
知识库搜索 (两步法):

Step 1: search_support_articles()
  --> 返回 50 篇文章标题
  --> Agent 扫描, 选出 3 篇相关

Step 2: get_article_content([id1, id2, id3])
  --> 返回 3 篇完整文章
  --> Agent 提取关键段落

代码搜索 (三步法):

Step 1: search_public_code("streaming buffer")
  --> ripgrep 返回匹配行

Step 2: list_public_directory("callbacks/")
  --> tree 返回目录结构

Step 3: read_public_file("callbacks/streaming.py", 47, 36)
  --> 返回第47-83行具体实现
```

## 类比理解

旧版 Chat LangChain 就像一个只有"全文搜索"功能的客服——你问它问题，它从一堆碎片化的索引卡片中找最像的几张念给你听。新版则像一个经验丰富的技术支持工程师：先翻官方手册确认功能设计，再查内部工单看别人是否遇到过同样的坑，最后打开代码编辑器验证实际实现。三个信息源交叉印证后，才给你一个有理有据的答案。

---

## 为什么重要

1. **"吃自己的狗粮"是最好的产品检验**：当你自己的团队都不用自己的产品时，说明产品确实没解决核心痛点。LangChain 团队把内部最佳实践产品化的过程，是一个极好的产品迭代案例。
2. **向量检索不是万能的**：对于结构化文档，直接 API 访问往往比分块嵌入更有效。这个经验值得所有在做企业知识库 RAG 的团队参考。
3. **子图架构是处理多源复杂检索的利器**：让每个子 Agent 做域内专家，过滤噪声后再汇总，比把所有原始结果塞进一个大上下文窗口要可靠得多。
4. **Agent 不只是模型调用**：生产级 Agent 需要中间件(重试、降级、缓存、护栏)才能真正可靠，这些"无聊"的工程工作往往决定了产品能否上线。

---

## 延伸思考

1. LangChain 团队放弃向量检索的理由是"结构化文档不适合分块"。但如果你的文档既有结构化部分(API 文档)又有非结构化部分(用户论坛帖子)，你会如何设计混合方案？
2. 深度 Agent 耗时 1-3 分钟，在客服场景中这个延迟是否可接受？你会用什么交互设计让用户在等待时不焦虑？
3. 子图架构中，每个子 Agent 独立判断"什么是黄金数据"。如果某个子 Agent 过滤太激进把关键信息丢了怎么办？你会如何做质量保障？
