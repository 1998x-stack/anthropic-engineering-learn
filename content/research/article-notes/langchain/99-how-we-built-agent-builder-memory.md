# Agent Builder 的记忆系统是怎么造出来的

> 一句话总结：LangSmith Agent Builder 把 Agent 的记忆表示为"虚拟文件系统"中的文件（AGENTS.md、skills、tools.json 等），Agent 通过读写文件来管理自己的记忆，用户通过自然语言反馈来纠正 Agent，记忆就在使用中自然积累和进化。

---

## 核心要点

### 1. 为什么 Agent Builder 要优先做记忆？

大多数 AI 产品在上线时都没有记忆功能，但 Agent Builder 团队做了一个反直觉的决定：从一开始就把记忆作为核心功能。原因很简单——Agent Builder 不是通用聊天助手，它是给用户定制特定任务的专用 Agent。

通用助手（ChatGPT、Claude）每次对话可能做完全不同的事，上一次的经验未必和下一次有关。但专用 Agent 是"反复做同一件事"——写会议纪要、筛选简历、回复邮件。这种场景下，每一次的经验几乎都和下一次相关。如果没有记忆，用户就不得不每次都重复告诉 Agent 同样的偏好。

### 2. 记忆 = 文件系统

Agent Builder 做了一个大胆的设计选择：**用文件系统来表示记忆**。Agent 的全部"记忆"就是一组文件，Agent 通过读写这些文件来管理自己的知识。

| 文件/目录 | 对应的记忆类型 | 作用 |
|-----------|----------------|------|
| `AGENTS.md` | 程序记忆（Procedural） | 定义 Agent 的核心指令和行为规则 |
| `skills/` | 语义记忆（Semantic） | 存储特定任务的专业知识和操作指南 |
| `tools.json` | 程序记忆（Procedural） | 定义 Agent 可以使用的 MCP 工具 |
| `subagents/` | 程序记忆（Procedural） | 定义子 Agent 的配置 |
| 其他知识文件 | 语义记忆（Semantic） | 存储领域知识、JD 等业务文档 |

为什么选文件系统？因为 LLM 天然擅长和文件系统打交道——读文件、写文件、改文件是模型做得最好的操作之一。这样就不需要给 Agent 专门的"记忆工具"，直接用文件操作就行了。

实际上，这些"文件"并不存储在真实的文件系统里，而是存在 PostgreSQL 数据库中，以"虚拟文件系统"的形式暴露给 Agent。这样既保留了 LLM 擅长的操作方式，又享受了数据库在基础设施层面的优势。

### 3. 记忆是怎么"长出来"的：一个真实例子

这是最能说明问题的部分。以一个会议纪要 Agent 为例：

```
第 0 周 ─── AGENTS.md: "Summarize meeting notes."
    |
    v  用户纠正："用列表，别用段落"
第 1 周 ─── AGENTS.md: + "User prefers bullet points"
    |
    v  用户补充："把 action items 单独提出来"
第 2 周 ─── AGENTS.md: + "Extract action items separately"
    |
    v  持续使用，自动应用已有规则
第 4 周 ─── 两条规则自动生效，用户不需要重复
    |
    v  3 个月的纠正和学习积累
第 3 月 ─── AGENTS.md 已包含：格式偏好、领域术语、
             人物角色、会议类型处理规则、边界情况处理...
```

关键洞察：**AGENTS.md 是通过纠正"长"出来的，不是通过预先编写**。用户从来不需要手动编辑配置文件，只需要在对话中给反馈，Agent 自己会更新记忆。

### 4. 五条实战教训

| 教训 | 问题 | 解决方案 |
|------|------|----------|
| 最难的是提示词工程 | Agent 记错时机、记错位置、格式错误 | 一个人全职做记忆相关的提示词优化 |
| 必须验证文件格式 | Agent 写出无效的 tools.json 或 skills | 加验证层，格式错误时把错误信息返回给 LLM 重试 |
| Agent 只会"加"不会"压缩" | 记忆越来越长，列出 50 个具体供应商而不是归纳为"忽略冷推广" | 需要手动或定时触发"压缩"操作 |
| 用户有时需要显式触发记忆 | Agent 在工作中可能遗漏该记住的东西 | 提供"反思并更新记忆"的显式指令 |
| 记忆编辑需要人工审批 | 提示注入（Prompt Injection）风险 | 默认需要人工确认，提供"YOLO 模式"给不担心风险的用户 |

### 5. 文件系统表示带来的三个好处

**免代码体验**：Markdown 和 JSON 是大多数人都熟悉的格式，比学习一套新的 DSL 门槛低得多，而且不会随着复杂度增加而"崩塌"。

**更好的 Agent 构建体验**：构建 Agent 本身就是一个高度迭代的过程。有了记忆，用户不需要每次手动修改配置，用自然语言给反馈就行——Agent 自己改自己的"配置文件"。

**可移植性**：文件是最通用的格式。用 Agent Builder 构建的 Agent 可以轻松迁移到 Deep Agents CLI、Claude Code 或其他 Agent 框架，只要它们支持相同的文件约定（AGENTS.md、MCP 等）。

### 6. 未来方向

| 方向 | 说明 |
|------|------|
| 情景记忆（Episodic Memory） | 把历史对话作为文件暴露给 Agent，让它能回顾过去的交互 |
| 后台记忆处理 | 定时任务（如每日一次）回顾所有对话并更新记忆，弥补"热路径"中遗漏的内容 |
| `/remember` 命令 | 显式触发 Agent 反思当前对话并更新记忆 |
| 语义搜索 | 超越 glob/grep，让 Agent 按语义检索自己的记忆文件 |
| 多层级记忆 | 区分 Agent 级、用户级、组织级记忆，通过不同目录暴露 |

## 类比理解

把 Agent Builder 的记忆系统想象成一个新助理的"工作手册"。

刚入职时，手册只有一句话："帮我整理会议纪要。"第一天你告诉助理"用列表格式"，助理就在手册上加了一条。第二天你说"把待办事项单独列出来"，手册又多了一条。三个月后，这本手册已经密密麻麻写满了你的偏好、常见同事的角色、不同会议类型的处理方式。

关键是：你从来没有亲手写这本手册。你只是在工作中给反馈，助理自己维护了这本手册。这就是 Agent Builder 记忆系统的核心思想——**记忆是用出来的，不是写出来的**。

而"虚拟文件系统"的设计，就像是把手册做成活页夹的形式——每个部分（核心规则、专业技能、工具列表）都是独立的活页，可以单独添加、修改、替换。这比把所有东西写在一张纸上要灵活得多。

---

## 为什么重要

1. **"文件即记忆"是一个优雅的抽象**：LLM 天然擅长操作文件，不需要专门的记忆 API 或工具，降低了实现复杂度。同时文件格式（Markdown/JSON）是人类可读可编辑的，方便调试和审计。
2. **"记忆通过使用生长"改变了 Agent 构建范式**：传统方式是"先写配置，再运行 Agent"。Agent Builder 的方式是"先用起来，边用边通过反馈完善配置"。这更接近人类培训新员工的方式。
3. **人工审批（Human-in-the-Loop）是安全底线**：Agent 自动修改自己的记忆带来了提示注入风险——如果恶意输入让 Agent 改写了自己的核心规则怎么办？默认要求人工确认是一个务实的安全策略。
4. **"只会加不会压缩"揭示了当前 LLM 的局限**：Agent 擅长从具体场景中提取信息并记录，但不擅长把多个具体案例归纳为通用规则。这提示我们在设计记忆系统时，需要额外的"压缩/归纳"机制。

---

## 延伸思考

1. 文件系统的容量终会成为瓶颈。当 AGENTS.md 长到几千行时，每次对话都把它塞进上下文窗口，成本和延迟都会上升。这时可能需要把"始终加载的核心规则"和"按需检索的知识"分开管理。
2. Agent 修改自己的代码/配置，本质上是一种"自修改程序"（Self-Modifying Program）。这既是强大的能力，也是危险的能力。如何设计"不可篡改的核心约束"（类似宪法层级的规则），值得深思。
3. "可移植性"是一个被低估的优势。如果整个行业都收敛到 AGENTS.md + MCP 这样的标准，那 Agent 就真正成为"可迁移的数字员工"——换一个运行框架，记忆和技能全部带走。这可能催生一个"Agent 记忆/技能市场"。
