# Data Agents：让 LLM 不只是回答问题，还能动手干活

> **一句话总结：** Data Agent 是一种能自主推理、选择工具、执行操作的 LLM 驱动智能体，让你从"只能提问"升级到"让 AI 帮你干活"。

---

## 核心要点

1. **Agent 不等于聊天机器人。** 聊天机器人只能一问一答，而 Agent 拥有推理循环（Reasoning Loop），能自己决定下一步该做什么、调用哪个工具、何时停止。
2. **两种推理引擎可选。** OpenAI Function Agent 依赖 OpenAI 内置的函数调用能力，ReAct Agent 则通过提示词模板驱动推理，兼容任何 LLM。
3. **工具（Tool）是 Agent 的双手。** 你可以把任意 Python 函数、查询引擎、甚至整套 API 服务包装成工具，Agent 会自己判断该用哪个。
4. **Utility Tools 解决上下文爆炸问题。** 当 API 返回的数据量超过 LLM 的上下文窗口时，OnDemandLoaderTool 和 LoadAndSearchToolSpec 会先索引再检索，避免信息溢出。

---

## 概念对比表

| 概念 | 是什么 | 类比 |
|------|--------|------|
| Agent（智能体） | 具备推理和行动能力的 LLM 封装 | 有独立思考能力的员工 |
| Tool（工具） | Agent 可调用的功能单元 | 员工手边的工具箱 |
| ToolSpec（工具规范） | 一组相关工具的集合 | 一整套专业工具包（如电工工具包） |
| Reasoning Loop（推理循环） | Agent 反复思考-行动-观察的过程 | 员工的"想-做-看结果-再想"工作节奏 |
| QueryEngine（查询引擎） | 针对数据的受限检索模块 | 图书馆的检索系统 |
| FunctionTool（函数工具） | 将普通函数包装为 Agent 可用的工具 | 给螺丝刀贴上标签，让员工知道它能干嘛 |

## 工具层级结构

```
工具体系
|
+-- BaseTool (基础抽象)
|   |-- metadata: name + description + fn_schema
|   |-- __call__(): 执行并返回 ToolOutput
|
+-- FunctionTool (函数工具)
|   把任意 Python 函数 --> Tool
|   自动推断参数 schema
|
+-- QueryEngineTool (查询引擎工具)
|   把 LlamaIndex 查询引擎 --> Tool
|   适合 RAG 检索场景
|
+-- ToolSpec (工具规范)
|   一个类 = 一组相关工具
|   例: SlackToolSpec --> load_data / send_message / fetch_channels
|
+-- Utility Tools (实用工具)
    +-- OnDemandLoaderTool: 加载 + 索引 + 查询一步完成
    +-- LoadAndSearchToolSpec: 先 load 建索引，再 search 查询
```

## 类比理解

把 Data Agent 想象成一个**新入职的实习生**：

- **推理循环**就是实习生的思考过程——看到任务后，他会想"我该先做什么？用什么工具？"做完一步后检查结果，再决定下一步。
- **Tool** 就是你给实习生准备的工具清单。每个工具上都贴着标签（name + description），告诉他"这个工具能干什么、怎么用"。
- **ToolSpec** 相当于把"Slack 相关的所有操作"打包成一个工具包，而不是让实习生面对一堆零散的按钮。
- **Utility Tools** 则像是给实习生配了一个笔记本——当某个 API 返回了 100 页数据时，实习生不会把全部内容背下来，而是先做笔记（索引），需要时再翻（检索）。

---

## 为什么重要

- **从"问答"到"执行"的跨越。** 传统 RAG 只能回答问题，Data Agent 能创建邮件草稿、发送消息、查询数据库——真正帮你干活。
- **工具抽象统一了接口。** 无论是简单的 Python 函数还是复杂的 API 服务，都通过同一套 Tool 接口暴露给 Agent，降低了集成成本。
- **解决了上下文窗口瓶颈。** Utility Tools 的"先索引再检索"模式，让 Agent 能处理远超 LLM 上下文限制的数据量。

---

## 延伸思考

1. **Agent 的可靠性问题。** ReAct 循环的自由度越高，出错的概率也越大。你在设计 Agent 时，是选择更自由的推理循环，还是更受限但更可控的路由模式？
2. **工具设计的艺术。** 一个好的 Tool 描述（description）直接决定 Agent 能否正确选择它。写工具描述就像写 API 文档——目标读者从人类变成了 LLM。
3. **安全边界在哪？** 当 Agent 可以发送邮件、操作数据库时，如何防止它做出错误甚至危险的操作？这是从"玩具"到"生产"必须回答的问题。
