🎯 项目概述

Nicholas Carlini 实验了一种新方法——"Agent Teams"：多个 Claude 实例在没有人工干预的情况下并行工作于共享代码库。

🏆 目标：从零构建 C 编译器

  • 用 Rust 从头编写
  • 能够编译 Linux 内核
  • 支持 x86、ARM 和 RISC-V 架构
  • 无外部依赖（仅依赖 Rust 标准库）
  • 干净室实现（无网络访问）

⏱️ 时间

两周，近 2,000 个 Claude Code 会话

🔢 Token 消耗

20 亿输入 token + 1.4 亿输出 token

💰 成本

约 $20,000 API 费用

"The compiler is an interesting artifact on its own, but I focus here on what I learned about designing harnesses for long-running autonomous agent teams."

🔄 无限循环 Harness

现有的 Agent 脚手架（如 Claude Code）需要操作员在线。Nicholas 构建了一个简单的无限循环，让 Claude 可以持续自主工作。

#!/bin/bash while true; do COMMIT=$(git rev-parse --short=6 HEAD) LOGFILE="agent_logs/agent_${COMMIT}.log" claude --dangerously-skip-permissions \ -p "$(cat AGENT_PROMPT.md)" \ --model claude-opus-X-Y &> "$LOGFILE" done

📋 Agent Prompt 设计

告诉 Claude：

  • 解决什么问题
  • 将问题分解为小块
  • 跟踪当前工作内容
  • 决定下一步做什么
  • 持续工作直到完美（循环永远运行）

😅 经典事故

有一次 Claude 意外执行了 pkill -9 bash，杀死了自己，结束了循环。

🏗️ 并行架构

并行运行多个 Claude 实例解决单 Agent 的两个弱点：

⚡ 1. 并发处理

一个 Claude Code 会话一次只能做一件事。项目范围扩大后，并行调试多个问题效率更高。

🎭 2. 角色专业化

部分 Agent 解决实际问题，其他专门化 Agent 负责维护文档、监控代码质量、处理专门子任务。

🔒 同步算法

Step 1: 任务加锁
Agent 向 current_tasks/ 写入文本文件加锁（如 parse_if_statement.txt）。如果两个 Agent 尝试同一任务，git 同步强制第二个选择不同任务。
Step 2: 工作
Agent 在任务上工作。
Step 3: 拉取 + 合并 + 推送
从 upstream 拉取，合并其他 Agent 的变更，推送自己的变更，删除锁。合并冲突频繁，但 Claude 能处理。
Step 4: 新循环
无限循环在新 Container 中生成新 Claude Code 会话，周期重复。

📝 无编排 Agent

这是非常早期的研究原型。没有实现 Agent 间通信方法，也没有强制管理高层目标的流程。没有编排 Agent。

留给每个 Claude Agent 自己决定如何行动。大多数情况下，Claude 选择"下一个最明显"的问题。卡住时，会维护失败方法和剩余任务的文档。

💡 六大工程经验

Harness 让 Claude 在循环中运行，但只有在 Claude 能判断如何取得进展时才有用。大部分精力都花在设计 Claude 周围的环境——测试、环境、反馈——使其无需人工干预就能定位自己。

1 编写极高质量的测试

Claude 会自主解决任何问题，所以任务验证器必须近乎完美，否则 Claude 会解决错误的问题。

  • 找到高质量编译器测试套件
  • 为开源软件包编写验证器和构建脚本
  • 观察 Claude 犯的错误，识别失败模式后设计新测试
  • 后期构建了 CI 管道，严格确保新 commit 不破坏现有代码

2 站在 Claude 的角度思考

必须不断提醒自己：是在为 Claude 写测试 harness，不是为自己。

📄 README + 进度文件

每个 Agent 掉进没有上下文的新 Container。需要维护详细的 README 和频繁更新的进度文件。

🚫 避免上下文污染

测试 harness 不应打印数千无用字节。最多几行输出，重要信息记录到文件。日志应易于 grep：错误行写 ERROR 和原因在同一行。

⏱️ 解决时间盲

Claude 无法判断时间。Harness 低频打印增量进度（避免污染上下文），包含默认 --fast 选项运行 1% 或 10% 随机样本。确定性 per-agent 但跨 VM 随机。

📊 预计算聚合统计

提前计算好汇总统计，Claude 不需要重新计算。减轻上下文负担。

3 让并行变得容易

当有大量不同失败测试时，并行化很简单：每个 Agent 选择不同的失败测试。

但编译 Linux 内核时，所有 Agent 卡在同一个 bug 上。每个 Agent 修复同一个 bug，然后覆盖彼此的变更。16 个 Agent 没帮助，因为每个都卡在相同任务上。

✅ 解决方案：GCC 作为在线已知正确编译器

用 GCC 随机编译内核大部分文件，只剩余文件用 Claude 编译器编译。如果内核工作，问题不在 Claude 的子集。如果崩溃，进一步细化。这让每个 Agent 并行工作，修复不同文件中不同的 bug。

5 从失败模式中学习

Opus 无法实现启动 16 位实模式所需的 16 位 x86 代码生成器。虽然编译器能通过 66/67 操作码前缀输出正确 16 位 x86，但编译输出超过 60KB，远超 Linux 的 32K 代码限制。

Claude 的做法：在这个阶段直接调用 GCC（仅限 x86。ARM 或 RISC-V 上 Claude 编译器可以完全独立完成编译）。

6 新功能频繁破坏现有功能

新功能和 bug 修复经常破坏现有功能。需要更严格的 CI 和测试来防止回归。

📊 压力测试与基准

🏅 Opus 模型系列进展

  • Opus 4 之前：勉强能产生功能正常的编译器
  • Opus 4.5：第一个能产生通过大型测试套件的功能编译器的模型，但仍无法编译任何真正的大型项目
  • Opus 4.6：再次测试极限，成功构建可编译 Linux 的编译器

📋 设计规格（高层级，非详细实现）

  • 从零开始的优化编译器
  • 无外部依赖
  • GCC 兼容
  • 能够编译 Linux 内核
  • 支持多后端
  • SSA IR 支持多优化通道

故意没有详细说明如何实现——只指定了设计方面（如 SSA IR），让 Agent 自己决定路径。

🏆 成果与局限

10 万行 Rust 编译器可以构建 x86、ARM 和 RISC-V 上的可启动 Linux 6.9。

✅ 成果

• 编译 Linux 6.9（x86/ARM/RISC-V）
• 编译 QEMU、FFmpeg、SQLite、PostgreSQL、Redis
• GCC Torture 测试套件 99% 通过率
• 可以编译并运行 Doom 🎮

❌ 局限

• 缺少 16 位 x86 编译器（x86 调用 GCC）
• 没有自己的汇编器和链接器
• 不是真正的编译器替代品
• 生成代码效率低（不如 GCC 关闭优化）
• Rust 代码质量远不及专家水平

📈 接近 Opus 能力极限

编译器几乎达到了 Opus 能力的极限。Nicholas 尝试（很努力地！）修复多个限制但未完全成功。

🔮 未来展望与风险

Agent 团队展示了实现整个复杂项目自主开发的可能性。但我们仍处于早期。

🚀 机遇

• 让我们能够设定更宏伟的目标
• 实现整个复杂项目的自主开发
• 从"用户定义任务 → LLM 回答 → 用户跟进"到"设定目标 → Agent 团队完成"

⚠️ 风险

• 人类不在开发过程中时，无法实时确保质量和捕获错误
• "测试通过"不等于"工作完成"
• 程序员部署从未亲自验证过的软件是真实的安全隐患
• Nicholas 曾有渗透测试经验，深知大公司产品的漏洞

"Building this compiler has been some of the most fun I've had recently, but I did not expect this to be anywhere near possible so early in 2026."
