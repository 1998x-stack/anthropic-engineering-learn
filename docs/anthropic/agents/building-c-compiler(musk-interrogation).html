问题一 你的故事——你做了什么决策，为什么？
我花了 $20,000 让 16 个 Claude 实例在几乎零人工干预的情况下，用 Rust 从零写了一个能编译 Linux 内核的 C 编译器。这不是为了省成本——我自己写可能更便宜。这是为了回答一个问题："AI agent 在不需人类的情况下，能独立完成多复杂的工程任务？"
决策一
团队自主运行 vs. 人类在循环中——故意把人踢出去

主流做法：所有 agent scaffold 都假设人类操作员在线。人类在循环中是默认的安全机制。

我的方案：一个 bash while-true 循环。每次 Claude 完成任务，立刻塞进下一个——循环永远运行。

#!/bin/bash
while true; do
  claude --dangerously-skip-permissions \
       -p "$(cat AGENT_PROMPT.md)" \
       --model claude-opus-X-Y
done

物理本质：把 Claude 从"交互式协作工具"变成"自主执行引擎"。人类工程师的三个职责被分解为可自动化替代品——验证（测试）、持久化（文件）、协调（git）。

决策二
16 个 Agent 并行但没有编排器——让个体智能涌现集体行为

反直觉决定：多 agent 系统的标准范式是 orchestrator-worker。我不用——因为我想测试涌现行为，不是编排行为。

极简协调：基于 git 的文件锁。Agent 在 current_tasks/ 目录写文件来 claim 任务。Git 同步强制避免冲突。合并冲突频繁——Claude 自己解决。

深刻洞察：不加编排器有时更好。编排器是单点——错误的分解决策导致全队走错。16 个平等 agent 中，错误独立可恢复。

决策三
测试质量 > 代码质量——AI agent 的"道德罗盘"是它的测试套件

真正的工程智慧：不是 prompt、不是架构、不是协调算法——是我花在测试上的时间。

当 agent 完全自主运行时，测试是它与"正确性"的唯一连接。测试套件有盲区 → agent 在盲区里"优化"——产出通过测试但实际错误的代码。

迭代循环：观察 agent 行为 → 识别失败模式 → 设计新测试覆盖 → 重复。为 Claude 设计的测试沟通方式——上下文污染控制、--fast 随机抽样、预计算统计。

决策四
干净室实现 + 无网络——不是约束，是能力标尺

不是安全原因：是测量纯 LLM 能力。如果 Claude 能上网——它找到现有实现、教程、模式。不是"构建"——是"复制+改编"。

能力边界测绘：Opus 4.5 → 首个通过大测试套件但不能编译大型项目。Opus 4.6 → Linux 6.9、QEMU、FFmpeg、Redis、Doom。但 Opus 4.6 无法实现 16-bit x86 代码生成器——到了极限。

从决策链到最难问题

所有决策就位后，16 个 agent 撞上了同一个根本障碍

问题二 你解决过最难的问题是什么？
编译 Linux 内核——所有 16 个 agent 全部卡死在同一个 bug 上。互相覆盖修改。并行化完全失效。不是 16 个人在合作——是 16 个人在同一个键盘上打字。
Situation & Task（情境与任务）

测试套件达到 99% 通过率后，每个 agent 可以独立工作。但编译 Linux 内核是一个巨大的、不可分解的单一任务——没有 1000 个独立测试。所有 agent 遇到同一个编译错误，修复同一个 bug，然后覆盖彼此的工作。

Action（核心行动）
失败尝试
  • 给 agent 分配不同文件——编译错误发生在哪个文件事前不知道
  • 让一个 agent 做内核编译——其他 15 个闲着
  • 分模块编译——同一个基础 bug 影响多个模块
突破方案
  • GCC 作为已知正确编译器的 Oracle
  • 随机用 GCC 编译大部分文件，少部分给 Claude 编译器
  • 逐步缩小失败范围——文件级别的二分查找
  • delta debugging 找"单独工作但合起来失败"的文件对
GCC 是已知正确的编译器。让 GCC 来做文件级别的二分查找。这就像 git bisect，但在文件级别、编译器级别。"已知正确的编译器"是 oracle，"已知失败的文件集合"在每次迭代中减半。

这个方案把编译 Linux 内核——一个不可分解的任务——变成了数百个独立的文件级子任务。16 个 agent 终于可以并行工作，每个处理不同的文件、不同的 bug。

成就
  • 2000 个 Claude Code 会话，持续两周
  • 干净室实现——无网络，仅依赖 Rust stdlib
  • 能编译 Linux 6.9 在三个架构上
  • GCC torture suite 99% 通过率
诚实局限
  • 生成代码效率低于关闭优化的 GCC
  • 16-bit x86 代码生成器未成功
  • 新功能频繁破坏已有功能
  • 模型能力极限——不是工程问题

核心洞察：这个实验追问的不是"agent 团队能否构建编译器"，而是"人类在循环中的角色能否被自动化替代"。测试质量替代人类判断；文件系统替代人类记忆；git 替代人类协调。用 GCC oracle 将一个不可分解任务转化为数百个可并行子任务的二分策略——是"已知正确参照物 + 问题分解"这一工程原理的极致应用。

最不安的发现：作为一个前渗透测试工程师——人们在部署自己从未亲自验证过的软件。测试只覆盖你想到的东西。AI 写了 10 万行代码——你不可能逐行审查。
