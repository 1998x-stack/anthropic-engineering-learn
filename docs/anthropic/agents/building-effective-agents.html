🤖 什么是 Agent

"Agent"可以有多种定义。Anthropic 将所有变体统称为 Agentic Systems，但在架构上区分 Workflows 和 Agents。

📋 Workflows（工作流）

LLM 和工具通过预定义的代码路径编排。

开发者控制流程走向，LLM 在固定步骤中执行。适合可预测的、定义良好的任务。

🧠 Agents（智能体）

LLM 动态指挥自己的流程和工具使用。

LLM 自主控制如何完成任务，动态决定下一步行动。适合需要灵活性和模型驱动决策的场景。

🎯 何时使用（何时不用）Agent

构建 LLM 应用时的核心建议：找到最简单的解决方案，只在需要时才增加复杂度。

✅ 足够简单的场景

对于大多数应用，用检索和 in-context 示例优化单次 LLM 调用就足够了。不需要 agentic 系统。

📋 使用 Workflow 当...

• 任务可以分解为固定的子任务
• 需要可预测性和一致性
• 不同类别的输入需要专门处理
• 需要并行处理以提高速度或置信度

🧠 使用 Agent 当...

• 无法预测所需的子任务数量
• 无法硬编码固定路径
• 需要灵活性和模型驱动决策
• 可以信任模型的判断

⚠️ 权衡考虑

Agentic 系统通常用延迟和成本换取更好的任务性能。需要考虑这个权衡是否值得。Agent 的自主性意味着更高的成本和复合错误的风险。

🛠️ 何时以及如何使用框架

有很多框架使 agentic 系统更容易实现，但需要谨慎使用。

🔗 Claude Agent SDK

Anthropic 官方的 Agent 开发工具包

🌿 Strands Agents SDK

AWS 的开源 Agent SDK

🎛️ Rivet / Vellum

GUI 工作流构建和测试工具

✅ 框架的好处

• 简化 LLM 调用、工具定义、链式调用
• 快速上手

❌ 框架的陷阱

• 额外抽象层遮蔽底层 prompts 和 responses
• 难以调试
• 诱惑添加不必要的复杂度

💡 建议

从直接使用 LLM API 开始：许多模式只需几行代码就能实现。如果确实使用框架，确保理解底层代码。对底层的不正确假设是客户错误的常见来源。

🧱 基础构建块：增强 LLM

Agentic 系统的基础构建块是一个增强的 LLM——通过检索、工具和记忆来扩展能力。

🔄 5 种 Workflow 模式

从简单到复杂，这些是可组合的工作流模式。每个模式都是前一个模式的自然延伸。

🔗 1. Prompt Chaining（提示链）

将任务分解为步骤序列，每个 LLM 调用处理前一步的输出。可以在中间步骤添加程序化检查（Gate）确保仍在正轨。

输入
→
LLM 1
步骤 1
→
Gate
检查
→
LLM 2
步骤 2
→
输出
何时使用：任务可以清晰分解为固定子任务。目标是用准确率换延迟——让每个 LLM 调用变得更简单。
案例：生成营销文案 → 翻译成另一种语言；写大纲 → 检查标准 → 基于大纲写文档

🔀 2. Routing（路由）

将输入分类并导向专门的处理流程。允许关注点分离和构建更专门的 prompt。

何时使用：复杂任务有不同类别，分别处理更好。分类可以由 LLM 或传统分类模型处理。
案例：客服查询分流（一般问题/退款/技术支持）；简单问题用 Haiku，复杂问题用 Sonnet

⚡ 3. Parallelization（并行化）

LLM 同时处理任务并聚合输出。两种变体：

📐 Sectioning（分割）

将任务拆分为独立的并行子任务。用于提高速度。

🗳️ Voting（投票）

多次运行同一任务获取多样化输出。用于提高置信度。

案例：安全防护（一个处理查询，一个审查不当内容）；代码漏洞审查（多个 prompt 分别检查）；自动化 Eval（每个 LLM 评估不同方面）

🎭 4. Orchestrator-Workers（编排者-工作者）

中心 LLM 动态分解任务，委派给工作者 LLM，并综合结果。与并行化的关键区别：子任务不是预定义的，而是由编排者根据输入动态确定。

何时使用：无法预测所需子任务的复杂任务（如编码——每次需要修改的文件数量和性质都不同）。
案例：编码产品（每次修改多个文件）；搜索任务（从多源收集分析信息）

🔄 5. Evaluator-Optimizer（评估者-优化者）

一个 LLM 生成响应，另一个提供评估和反馈，形成循环。类比人类写作的迭代过程。

好的适配信号：① LLM 响应在人类反馈下可被证明改进 ② LLM 能提供有意义的反馈
案例：文学翻译（微妙之处需要迭代）；复杂搜索（需要多轮搜索和分析）

🧠 自主 Agent

当 LLM 在关键能力上成熟时——理解复杂输入、推理规划、可靠使用工具、从错误中恢复——Agent 开始在生产中出现。

Agent 工作流

用户命令
或讨论
→

规划 + 执行
→
环境反馈
工具结果
→
人类反馈
(Checkpoints)
→
完成
Agent 在每一步从环境获取"地面真相"（工具调用结果、代码执行）→ 评估进度 → 需要时请求人类反馈

Agent 的关键要素

🌍

地面真相

每步从环境获取真实反馈（工具结果、代码执行）

🛑

停止条件

最大迭代次数等，保持控制

👤

人类检查点

遇到阻碍或需要判断时暂停请求反馈

✅ 适合 Agent 的场景

• 无法预测所需步骤数
• 无法硬编码固定路径
• 可以信任模型决策
• 适合在受信任环境中扩展任务

⚠️ Agent 的风险

• 更高成本
• 复合错误风险
• 需要在沙盒环境中广泛测试
• 需要适当的防护措施

💡 经典案例

  • SWE-bench 编码 Agent：根据 PR 描述解决 GitHub Issue，涉及多个文件编辑
  • Computer Use：Claude 使用计算机完成任务的参考实现

🎯 三大核心原则

在 LLM 领域的成功不是构建最复杂的系统，而是构建适合你需求的系统。

🎯 1. 简单性（Simplicity）

保持 Agent 设计简单。从简单的 prompt 开始，用全面的评估优化它们，只在简单方案不足时才添加多步 agentic 系统。

从简单开始 需要时才增加

🔍 2. 透明性（Transparency）

明确展示 Agent 的规划步骤。让 Agent 的思考过程可见，便于调试和信任建立。

可见规划 便于调试

🔧 3. ACI 设计（Tool Documentation & Testing）

精心设计 Agent-Computer 接口。 thorough 的工具文档和测试。像设计人类界面一样投入精力设计 Agent 界面。

工具文档 测试迭代

🔄 实施建议总结

Step 1: 从简单 prompt 开始
尝试单次 LLM 调用，用检索和 in-context 示例优化
Step 2: 用评估驱动迭代
测量性能，只有在需要时才增加复杂度
Step 3: 只在简单方案不足时使用 Agent
添加多步 agentic 系统只在简单方案不够时

💼 附录 1：Agent 实战

与客户的合作揭示了两个特别有前景的 Agent 应用领域。

💬 A. 客户支持

结合聊天机器人界面与工具集成：

  • 对话流程 + 外部信息/操作
  • 拉取客户数据、订单历史、知识库
  • 退款、更新工单等程序化处理
  • 通过用户定义的解决衡量成功

趋势：按成功解决收费的定价模式，展示对 Agent 效果的信心。

💻 B. 编码 Agent

从代码补全到自主问题解决：

  • 代码解决方案可通过自动测试验证
  • Agent 可用测试结果作为反馈迭代
  • 问题空间定义明确、结构化
  • 输出质量可客观衡量

里程碑：Agent 现在能仅凭 PR 描述解决 SWE-bench Verified 中的真实 GitHub Issue。

🔑 Agent 增加最大价值的场景特征

需要对话 + 行动
不仅仅是聊天，还需要实际操作
有明确成功标准
可以客观衡量是否完成
支持反馈循环
可以从结果中学习和改进
有人类监督
关键节点需要人类判断

🔧 附录 2：Tool 提示工程

无论构建哪种 agentic 系统，工具都是重要组成部分。工具定义和规范应该像 prompt 一样得到充分的提示工程关注。

📐 工具格式建议

✅ 给模型思考空间

给模型足够的 token 在"写死自己"之前进行思考

✅ 接近自然文本

格式接近模型在互联网上自然看到的内容

❌ 避免格式"开销"

如需要准确计数数千行代码，或对写入的任何代码进行字符串转义

✅ 像设计人类界面一样

投入与 HCI 同等的精力设计 ACI（Agent-Computer Interface）

🔧 好工具定义的要素

  • 站在模型角度：基于描述和参数，使用这个工具是否显而易见？
  • 包含示例用法：边缘情况、输入格式要求、与其他工具的清晰边界
  • 像给初级开发者写 docstring 一样：更改参数名或描述使其更明显
  • 测试模型如何使用工具：在 workbench 中运行多个示例输入，查看模型犯的错误并迭代
  • Poka-yoke（防错）：更改参数使犯错变得更难

💡 SWE-bench 实战经验

在构建 SWE-bench Agent 时，花在优化工具上的时间比优化整体 prompt 还多。

例如：发现模型在 Agent 移出根目录后使用相对文件路径的工具会犯错。解决方案：改为始终要求绝对文件路径——模型完美使用这个方法。

"Think of this as writing a great docstring for a junior developer on your team."
