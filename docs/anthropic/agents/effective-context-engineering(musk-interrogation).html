问题一 你的故事——你做了什么决策，为什么？
全世界都在沉迷 prompt engineering 的时候，我在推动一个更根本的范式转移——从"写好 prompt"转向"管好 context"。这不是语义游戏。这是认知模型的根本改变。
决策一
从 Prompt Engineering 到 Context Engineering

主流做法：优化 prompt 的措辞、格式、few-shot 示例。

物理本质：Agent 不是分类器。它在循环中运行——每次推理产生新数据，context 是不断膨胀的信息宇宙，而上下文窗口是固定大小的容器。真正的问题是：哪些 token 值得放入那个有限的窗口？

反直觉立场：公开说 prompt 格式正在变得不重要。Transformer 的 n² 注意力机制决定了注意力预算的物理瓶颈。上下文腐烂（context rot）是跨模型普适现象。如果不管 context，agent 会在自己产生的信息海洋中淹死。

决策二
Just-in-Time 上下文 vs. 预加载

预加载的问题：不知道什么是真正相关的——倾向于"宁可多加载"。上下文里 70% 的 token 最终没被使用，但仍然消耗注意力预算。

Just-in-Time 方案：Agent 保持轻量级引用（文件路径、查询、链接），推理过程中确定需要时才动态加载。模仿人类认知——不背整本书，记住"在图书馆哪层哪个书架"。

物理洞察：对 agent 任务，空间成本（注意力预算）比时间成本（检索延迟）更致命。注意力耗尽的错误决策代价远大于额外检索延迟。混合策略——静态内容预加载，动态内容 Just-in-Time。

决策三
"正确的海拔"——在死板和模糊之间

两个极端：硬编码 if-else 规则树（脆弱的决策树）vs. 模糊高层指导（"请专业地完成任务"）。

Goldilocks 区域：给强启发式——不是操作手册，是行为框架。足够具体引导行为，足够灵活允许判断。

Few-shot 质量 > 数量：5 个高质量典范示例胜过 50 个覆盖所有边缘的——模型从模式中学习，不是从规则中学习。

从架构决策到根本困境

Transformer 的 n² 注意力 = 每个 token 都在消耗有限预算

问题二 你解决过最难的问题是什么？
Transformer 自注意力产生 n² 成对关系。10 万 token = 100 亿注意力关系。模型训练数据中短序列远常见于长序列。结果是渐进退化——不是硬断崖，是每个新 token 都在消耗"注意力预算"。
Situation & Task

Agent 在自身产生的信息洪流中溺水。把"一切可能相关"的信息塞进上下文——70% token 最终未被使用但全程消耗注意力。激进清理又丢掉"当时看起来不重要但后面变得关键"的信息。

Action（核心行动）
失败尝试
  • 把一切都塞进上下文——agent 在信息洪流中溺水，关键指令注意力权重被稀释
  • 激进清理——丢掉了后来变得关键的微妙上下文
  • 只优化 prompt——措辞再好也解决不了信息过载
突破洞察
  • 注意力经济——每个 token 有成本（注意力）和收益（信号）
  • 最优上下文不是信息最多的——是边际信号最高的那组 token
  • 解释了反直觉现象：删信息提升性能、5 个好示例 > 50 个边缘示例
上下文工程不是在优化一个"东西"——它是在管理一个"注意力经济"。每个 token 有成本和收益。最优上下文不是"信息最多的上下文"——是边际信号最高的那组 token。
解决方案——三个层面的工程实践：
  • 工具代币效率：返回"刚好够做下一个决策的信息"，紧凑结构化输出。最小可行工具集。
  • 渐进式信息揭示：agent 层层构建理解——文件大小暗示复杂度、命名暗示用途、时间戳代理相关性。
  • "先召回再精度"的压缩调优：先确保捕获所有相关信息，再消除冗余内容。顺序不能反。

核心原则
  • 注意力是最稀缺资源，不是 token 长度
  • 从"我该说什么"到"我该让模型看到什么"
  • 每个 token = 成本（注意力）+ 收益（信号）
实践证据
  • Claude Code 混合预加载 + Just-in-Time
  • Claude 玩宝可梦：零引导自主发展记忆策略
  • 内存工具在 Claude Developer Platform 公测

核心洞察：注意力是 LLM 最稀缺的资源，不是 token 长度。给模型再大的上下文窗口，如果不管理信息密度，模型照样被噪音淹没。上下文工程的本质：在每一个推理时刻，找到那组边际信号最高的 token——不多也不少。这就是从 prompt engineering 到 context engineering 的根本转变。

Transformer 物理现实：自注意力的 n² 机制意味着每个 token 都在消耗有限注意力预算。更大的窗口 = 更多可能的噪音 = 更需要主动管理。这是物理极限，不是工程选择。
