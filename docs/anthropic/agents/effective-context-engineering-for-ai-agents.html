🔄 上下文工程 vs 提示工程

构建 LLM 应用的重点正从"找到正确的提示词"转向"什么配置最可能产生期望行为"。

📝 Prompt Engineering

编写和组织 LLM 指令以获得最佳结果。主要关注如何写好 system prompt。在早期 AI 工程中是核心，因为多数用例是一次性分类或文本生成。

🧠 Context Engineering

在推理过程中策划和维护最优 token 集合。包括 system prompts、工具、MCP、外部数据、消息历史等所有内容。是循环迭代的过程。

两者的关系

Prompt Engineering
写指令
→
Context Engineering
管理整个上下文状态

Context Engineering = Prompt Engineering 的自然演进，范围更广，覆盖 Agent 多轮交互的完整生命周期

📐 核心定义

Context（上下文）：采样 LLM 时输入的 token 集合。

Engineering（工程化）：优化这些 token 的效用，克服 LLM 的固有限制，一致地达到期望结果。

Thinking in Context（上下文思维）：考虑 LLM 在任何时刻的完整状态，以及该状态可能产生的行为。

🎯 为什么上下文工程重要

尽管 LLM 速度快、能处理大量数据，但它们和人类一样，在某一点后会失去焦点或感到困惑。

⚠️ Context Rot（上下文腐烂）

随着上下文窗口中 token 数量增加，模型从上下文中准确回忆信息的能力下降。虽然不同模型退化曲线不同，但这个特征在所有模型中都会出现。

📊 架构根源：注意力机制

LLM 基于 transformer 架构，每个 token attend 到所有其他 token。这意味着 n 个 token 有 n² 个成对关系。

📉 性能梯度

位置编码插值等技术允许模型处理更长序列，但对 token 位置理解有退化。这创建了一个性能梯度而非硬性悬崖：模型在更长上下文中仍然强大，但信息检索和长程推理的精度降低。

短上下文
高精度
中等上下文
精度下降
长上下文
显著退化

上下文必须被视为有限资源，具有递减的边际回报。每个新 token 都会消耗模型的"注意力预算"。

🔬 有效上下文的解剖

鉴于 LLM 的有限注意力预算，好的上下文工程意味着找到最小的高信号 token 集合，最大化期望结果的概率。

📝 System Prompts

极其清晰，使用简单直接的语言。需要在两个极端之间找到"Goldilocks zone"：

❌ 太具体

硬编码复杂的 if-else 逻辑 → 脆弱、难维护

❌ 太模糊

高层指导不够具体 → 无法给出期望信号

✅ 最佳平衡

足够具体引导行为，足够灵活给模型启发式方法

🔧 工具设计

工具定义了 Agent 和信息/行动空间之间的契约。必须促进效率：

  • 返回 token 高效的信息
  • 鼓励高效 Agent 行为
  • 自包含、对错误鲁棒
  • 功能间最小重叠

📚 示例（Few-shot）

对 LLM 来说，示例是"一图胜千言"。但不推荐塞满所有边缘情况。

推荐：策划一组多样化、规范性的示例，有效描绘期望行为。

💬 消息历史

随着 Agent 循环运行，生成的数据越来越多。必须循环精炼。

保持上下文信息丰富但紧凑——这是所有上下文组件的指导原则。

🎯 Prompt 设计最佳实践

  • 用 XML 标签或 Markdown headers 组织不同部分
  • 追求最小信息集合，完全勾勒期望行为
  • 最小 ≠ 短：仍需提供足够信息确保 Agent 遵守期望行为
  • 从最小 prompt + 最强模型开始测试，然后基于失败模式添加指令和示例

🔍 上下文检索与 Agent 搜索

Anthropic 对 Agent 的定义趋向简单：LLM 在循环中自主使用工具。随着模型变强，Agent 的自主性可以扩展。

📥 预检索（Just-in-Case）

预处理好所有相关数据，基于嵌入的检索在推理前注入上下文。

快，但可能注入不相关信息，浪费注意力预算。

🎯 即时检索（Just-in-Time）

维护轻量标识符（文件路径、查询、链接），运行时动态加载数据。

更慢，但保持上下文紧凑，Agent 自主决定加载什么。

🏗️ Claude Code 的案例

Claude Code 使用即时检索方法处理大型数据库的复杂数据分析：

  • 模型编写针对性查询
  • 存储结果
  • 使用 head / tail 分析大量数据
  • 从未将完整数据对象加载到上下文中

💡 元数据的价值

引用元数据提供了精炼行为的高效机制。对操作文件系统的 Agent 来说：

tests/test_utils.py

暗示测试目的 → Agent 知道这是测试文件

src/core_logic/test_utils.py

暗示核心逻辑 → 即使同名，含义完全不同

文件夹层级、命名约定、时间戳都提供重要信号，帮助 Agent 理解何时如何使用信息。

🔄 渐进式披露（Progressive Disclosure）

让 Agent 自主导航和检索数据，允许逐步发现相关上下文：

文件大小暗示复杂度
Agent 决定先看哪个文件
命名约定暗示目的
理解文件用途
时间戳代理相关性
判断哪些信息最新
逐层组装理解，只保持必要的在工作记忆中

⚖️ 混合策略

最有效的 Agent 可能结合两种策略：预检索一些数据获得速度 + 允许自主探索获得更多上下文。

Claude Code 使用混合模式：CLAUDE.md 文件预先注入上下文，同时 glob / grep 允许即时检索。这有效绕过了过期索引和复杂语法树的问题。

📦 Compaction（上下文压缩）

长程任务要求 Agent 在超过上下文窗口的 token 计数下保持一致性。Compaction 是上下文工程的第一杠杆。

🔄 Compaction 流程

接近上下文限制
的对话
→
LLM 总结
关键内容
→
新上下文窗口
继续工作

Compaction 以高保真度蒸馏上下文窗口内容，使 Agent 能以最小性能退化继续工作。

📋 Claude Code 中的实现

  • 传递消息历史给模型进行总结
  • 压缩最关键细节
  • 保留：架构决策、未解决 bug、实现细节
  • 丢弃：冗余工具输出或消息
  • Agent 继续压缩上下文 + 最近访问的 5 个文件
  • 用户获得连续性，无需担心上下文窗口限制

🎯 Compaction 的艺术

Compaction 的艺术在于选择保留什么 vs 丢弃什么。过于激进的压缩会导致丢失微妙但关键的上下文，其重要性只在后来显现。

实施建议：

最大化 Recall
捕获所有相关信息
→
提高 Precision
消除多余内容

最低悬挂的果实：清除工具调用和结果——一旦工具在消息历史深处被调用，Agent 为什么还需要看原始结果？工具结果清除是最轻量级的压缩形式。

📝 结构化笔记（Agentic Memory）

Agent 定期写笔记持久化到上下文窗口外的内存中。这些笔记在稍后时间被拉回上下文窗口。

📋 Claude Code 的 TODO 列表

Agent 维护进度跟踪，跟踪复杂任务中的关键上下文和依赖关系。简单模式但效果显著。

🎮 Claude Plays Pokémon

Agent 在数千游戏步中维护精确计数——追踪目标如"过去 1,234 步我在 Route 1 训练 Pokémon，Pikachu 已升 8 级向目标 10 级"。还开发地图、记住成就、维护战斗策略笔记。

✅ 笔记系统的优势

  • 持久内存：最小开销的长期记忆
  • 跨会话连续性：上下文重置后 Agent 读取自己的笔记并继续
  • 支持长程策略：在 LLM 上下文窗口中保持所有信息是不可能的
  • 自动开发：Claude 无需提示就能开发笔记结构

🛠️ Anthropic Memory Tool

作为 Sonnet 4.5 发布的一部分，Anthropic 推出了Memory Tool公测版：

  • 基于文件的系统存储和咨询上下文窗口外的信息
  • 允许 Agent 随时间构建知识库
  • 跨会话维护项目状态
  • 参考之前工作而不必将所有内容保持在上下文中

📌 结论

上下文工程代表了构建 LLM 应用的根本性转变。随着模型变强，挑战不仅是制作完美提示——而是在每一步深思熟虑地策划什么信息进入模型的有限注意力预算。

🎯 核心原则

"找到最小的高信号 token 集合，最大化期望结果的概率。"

📈 趋势展望

更聪明的模型需要更少的规范性工程，允许 Agent 以更自主的方式运行。但随着能力提升，将上下文视为珍贵、有限资源的原则将仍然是构建可靠、有效 Agent 的核心。

💡 "做最简单有效的事"

鉴于该领域的快速进步，"做最简单有效的事"（do the simplest thing that works）可能仍然是构建 Agent 团队的最好建议。
