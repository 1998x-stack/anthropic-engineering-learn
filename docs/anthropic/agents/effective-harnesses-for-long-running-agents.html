🔄 长程 Agent 的核心问题

随着 AI Agent 越来越强大，开发者开始让它们承担需要数小时甚至数天才能完成的复杂任务。但核心挑战是：Agent 必须在离散的会话中工作，每个新会话开始都没有之前会话的记忆。

🎭 类比：换班制工程师

想象一个软件项目由轮班制工程师团队负责，每个新工程师到来时都不记得上一班发生了什么。这就是长程 Agent 面临的处境。

因为上下文窗口有限，且大多数复杂项目无法在单个窗口内完成，Agent 需要一种方法来桥接编码会话之间的间隙。

问题：单一 Agent 在多上下文窗口中的表现

给定高级 Prompt
"构建 claude.ai 克隆"
→
Agent 尝试
一次完成所有
→
上下文耗尽
一半实现
→
新 Agent 猜测
修复混乱

即使使用 compaction（上下文压缩），仍然无法完美传递指令到下一个 Agent

❌ 失败模式 1：一次做太多

Agent 试图 one-shot 整个应用 → 上下文耗尽 → 下一个会话从半成品开始 → 需要猜测并花费大量时间恢复

❌ 失败模式 2：过早宣布完成

Agent 看到已有进展 → 认为任务已完成 → 实际还有大量特性未实现

💡 两阶段解决方案

Anthropic 为 Claude Agent SDK 开发了两阶段方案，使 Agent 能在多个上下文窗口间有效工作。

整体架构

用户 Prompt
"构建一个应用"
→
Initializer Agent
初始化环境
→
Coding Agent × N
增量式推进
→
完整应用
特性逐项完成

🏗️ Initializer Agent

第一次运行：设置初始环境，创建 init.sh、claude-progress.txt、特性列表、初始 git commit

💻 Coding Agent

每次会话：增量式推进一个特性，写结构化更新，提交 git，更新进度文件

关键洞察：找到一种方法让 Agent 在全新的上下文窗口中快速理解工作状态——通过 claude-progress.txt 文件和 git 历史记录实现。灵感来自优秀软件工程师每天的实践。

🔑 两阶段解决的问题

问题 1：一次性做太多

Agent 试图在单个上下文中完成整个应用，导致半成品和混乱。

方案：特性列表 + 逐项完成

Initializer 创建 200+ 特性列表（全部标记 failing），Coding Agent 每次只做一个特性。

问题 2：过早宣布完成

Agent 看到部分进展就认为任务完成。

方案：结构化特性文件

Coding Agent 必须读取特性列表，选择最高优先级未完成的特性开始工作。

🏗️ 环境管理三要素

Initializer Agent 需要为后续所有 Coding Agent 创建必要的环境脚手架。

📋 特性列表（feature_list.json）

基于用户初始 prompt，创建包含所有特性的结构化 JSON 文件。在 claude.ai 克隆示例中，这意味着 200+ 个特性，全部初始标记为 "failing"。

{ "category": "functional", "description": "New chat button creates a fresh conversation", "steps": [ "Navigate to main interface", "Click the 'New Chat' button", "Verify a new conversation", "Check chat area shows welcome", "Verify sidebar shows convo" ], "passes": false }

为什么用 JSON 而非 Markdown？实验发现模型更不容易不当更改或覆盖 JSON 文件。

🚀 init.sh 脚本

可以运行开发服务器的初始化脚本。每个 Coding Agent 会话开始时读取并运行此脚本，确保环境可以立即启动。

这节省了每个会话的 token——Agent 不需要弄清楚如何运行应用。

📝 进度文件 + Git 历史

claude-progress.txt 记录每个 Agent 做了什么。结合 git log，让新 Agent 能快速了解最近的工作状态。

初始 git commit 显示哪些文件被添加。后续每个会话结束时都提交进度更新。

🔒 严格的编辑约束

Coding Agent 只能通过更改 passes 字段来编辑特性列表。强烈指示："因为移除或编辑测试可能导致缺失或有 bug 的功能，这是不可接受的。"

这些约束防止 Agent 通过删除测试来"作弊"。

📈 增量式进度管理

有了初始环境脚手架后，Coding Agent 被要求每次只做一个特性。

增量式方法的关键原则

  • 一次一个特性：解决 Agent 试图一次做太多的倾向
  • 干净状态：每次代码变更后，环境应该处于适合合并到 main 分支的状态——没有重大 bug，代码有条理且文档完善
  • Git 提交：要求模型用描述性提交信息提交进度，允许回退坏的代码更改
  • 进度总结：在进度文件中写入工作总结，帮助下一个 Agent 快速了解状态

✅ 效率提升

这些方法消除了 Agent 需要猜测发生了什么并花时间恢复基本功能的需求。每个新会话都可以从已知的良好状态开始工作。

🧪 端到端测试

观察到的最后一个主要失败模式：Claude 倾向于在没有适当测试的情况下将特性标记为完成。

❌ 没有显式提示时

Claude 会做代码更改，甚至用单元测试或 curl 命令测试，但无法识别特性端到端不工作。

✅ 显式提示后

提示使用浏览器自动化工具，像人类用户一样做所有测试。Claude 通过 Puppeteer MCP 截取截图，识别并修复仅从代码不明显的 bug。

📌 测试流程

对于构建 Web 应用，每个会话开始时：

运行 init.sh
启动本地开发服务器
使用 Puppeteer MCP 端到端测试
打开新 chat → 发送消息 → 接收响应。确保应用处于工作状态
如果基本功能损坏
先修复现有 bug，而不是开始实现新特性（否则会使问题更糟）
验证通过 → 开始新特性
从 tests.json 中选择下一个最高优先级的未完成特性

⚠️ 剩余限制

Claude 的视觉能力和浏览器自动化工具仍有局限。例如，Claude无法通过 Puppeteer MCP 看到浏览器原生的 alert 模态框，依赖这些模态框的特性往往因此更容易有 bug。

🚦 Agent 启动流程

每个 Coding Agent 在开始工作前需要执行一系列步骤来了解当前状态。

Step 1: 确认工作目录
运行 pwd 查看工作目录。只能编辑此目录中的文件。
Step 2: 读取进度文件
读取 claude-progress.txt 了解最近的工作内容。
Step 3: 读取特性列表
读取 feature_list.json，选择最高优先级未完成的特性。
Step 4: 检查 Git 历史
运行 git log --oneline -20 查看最近的工作。
Step 5: 启动开发服务器
运行 init.sh 启动开发服务器。
Step 6: 验证基本功能
使用浏览器自动化验证核心功能正常。如果损坏，先修复。
Step 7: 开始新特性工作
确认基本功能正常后，开始实现下一个特性。

📋 典型会话日志

[Assistant] I'll start by getting my bearings and understanding the current state of the project.
[Tool Use] <bash - pwd>
[Tool Use] <read - claude-progress.txt>
[Tool Use] <read - feature_list.json>
[Assistant] Let me check the git log to see recent work.
[Tool Use] <bash - git log --oneline -20>
[Assistant] Now let me check if there's an init.sh script to restart the servers.
<Starts the development server>
[Assistant] Excellent! Now let me navigate to the application and verify that some fundamental features are still working.
<Tests basic functionality>
[Assistant] Based on my verification testing, I can see that the fundamental functionality is working well. Now let me review the tests.json file to understand what needs to be implemented next.
<Starts work on a new feature>

🔧 失败模式与解决方案

四个常见的长程 Agent 失败模式及其解决方案。

过早宣布胜利

问题：Claude 过早宣布整个项目完成。

Initializer 方案：设置特性列表文件，包含端到端特性描述的结构化 JSON。

Coding Agent 方案：会话开始时读取特性列表，选择一个特性开始工作。

留下有 bug 的环境

问题：Claude 离开的环境有 bug 或进度未文档化。

Initializer 方案：创建初始 git 仓库和进度笔记文件。

Coding Agent 方案：开始时读取进度笔记和 git 日志，运行基本测试；结束时提交 git 和进度更新。

过早标记完成

问题：Claude 在没有适当测试的情况下标记特性为完成。

Initializer 方案：设置特性列表文件。

Coding Agent 方案：自我验证所有特性，只有在仔细测试后才标记为 "passing"。

浪费时间弄清运行方式

问题：Claude 需要花时间弄清楚如何运行应用。

Initializer 方案：编写 init.sh 脚本可以运行开发服务器。

Coding Agent 方案：开始时读取 init.sh。

🔮 未来方向

这个研究展示了使模型在多个上下文窗口间增量式推进的一种可能方案，但仍有开放问题。

🤖 多 Agent 架构？

目前不确定通用编码 Agent 是否表现最好，还是专用 Agent 能做得更好：

  • Testing Agent：专注于测试
  • QA Agent：质量保证
  • Code Cleanup Agent：代码清理

🔬 泛化到其他领域

这个 demo 针对全栈 Web 应用开发优化。未来方向是泛化到其他领域：

  • 科学研究
  • 金融建模
  • 其他需要长程 Agent 任务的领域

📚 核心设计原则总结

🎯 增量式
一次一个特性，避免一次做太多
📝 状态透明
进度文件 + Git 历史让每个 Agent 快速了解状态
🧪 端到端测试
像人类用户一样测试，而非仅看代码
🔒 干净状态
每个会话结束时环境应该适合合并到 main
