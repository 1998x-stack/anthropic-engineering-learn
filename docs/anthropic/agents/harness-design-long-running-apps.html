⚠️ 朴素实现为何失败

之前的长程 harness 已经解决了部分问题（Initializer Agent 分解任务列表 + Coding Agent 逐个特性），但仍有两个持续存在的失败模式。

❌ 失败模式 1：上下文焦虑（Context Anxiety）

模型在长任务中随着上下文窗口填满会失去连贯性。某些模型（如 Sonnet 4.5）表现出上下文焦虑——在接近它们认为的上下文限制时过早结束工作。

Compaction 不够：原地总结保留了连续性，但没有给 Agent 干净的白板，上下文焦虑仍然存在。

解决方案：上下文重置（Context Resets）——完全清除上下文窗口，通过结构化交接让下一个 Agent 接手。

❌ 失败模式 2：自我评估偏见

当被要求评估自己产生的工作时，Agent 倾向于自信地赞美自己的作品——即使在人类观察者看来质量明显平庸。

这个问题在主观任务（如设计）中尤为突出，没有二元检查可以等价于可验证的软件测试。

解决方案：分离工作 Agent 和评判 Agent。单独调优的评估者比让生成者自我批评要容易得多。

Compaction vs Context Reset

📝 Compaction

对话的早期部分就地总结 → 同一 Agent 继续 → 保留连续性但焦虑仍存

🔄 Context Reset

完全清除上下文 → 新 Agent 从零开始 + 结构化交接 → 干净白板但需要状态传递

"Separating the agent doing the work from the agent judging it proves to be a strong lever to address this issue."

🎨 前端设计：主观质量可量化

自我评估问题在前端设计中最明显。没有干预的情况下，Claude 倾向于产生安全、可预测但在视觉上平淡无奇的布局。

两大洞察

洞察 1：主观质量可以编码

"这个设计美吗？"很难一致回答，但"这个设计遵循我们的好设计原则吗？"给了 Claude 具体的评判标准。

洞察 2：分离生成和评分

分离前端生成和前端评分 → 创建反馈循环 → 推动生成者产生更强的输出。

🎯 1. 设计质量（权重最高）

设计是否感觉是一个连贯的整体，而非零件的集合？颜色、排版、布局、图像等是否结合创造出独特的氛围和身份。

💎 2. 原创性（权重最高）

是否有定制决策的证据，还是模板布局、库默认值和 AI 生成模式？人类设计师应该能认出有意的创意选择。未修改的库存组件或 AI 生成的典型标志（如白色卡片上的紫色渐变）在这里会失败。

🔧 3. 工艺

技术执行：排版层次、间距一致性、色彩和谐、对比度比率。这是一个能力检查而非创意检查。大多数合理实现默认就能通过。

✅ 4. 功能

独立于美学的可用性。用户能否理解界面做什么、找到主要操作、完成任务而无需猜测？

💡 关键设计决策

设计质量和原创性的权重高于工艺和功能。Claude 默认在工艺和功能上表现良好，但在设计和原创性上经常产生平淡的输出。标准明确惩罚高度通用的 "AI slop" 模式，并通过更重的权重推动模型进行更多的美学冒险。

🔄 GAN 启发的反馈循环

受 Generative Adversarial Networks（GAN）启发，设计了 Generator-Evaluator 多 Agent 结构。

Generator-Evaluator 循环

Generator
创建 HTML/CSS/JS
→
Evaluator (Playwright MCP)
导航页面 + 截图 + 评分
→
详细 Critique
反馈给 Generator
→
Generator 改进
refine 或 pivot
→
下一轮循环...

每轮 5-15 次迭代，每次迭代推动 Generator 向更独特的方向发展。完整运行可达 4 小时。

🔧 实现细节

  • 基于 Claude Agent SDK 构建，编排简单
  • Evaluator 使用 Playwright MCP 直接与实时页面交互（而非仅评分静态截图）
  • Evaluator 自行导航页面，截图并仔细研究实现后产出评估
  • 用 few-shot 示例校准 Evaluator，带有详细的评分细目，确保判断与人类偏好对齐
  • Generator 在每次评估后做战略决策：分数趋势好则 refine 当前方向，不好则 pivot 到全新美学

🎭 经典案例：荷兰艺术博物馆

到第 9 次迭代，产生了一个干净的深色主题着陆页——视觉打磨但符合预期。第 10 次迭代，它完全抛弃了原有方法，将网站重新想象为空间体验：CSS 透视渲染的棋盘地板 3D 房间，艺术品以自由形式挂在墙上，基于门的导航在画廊房间之间切换，而非滚动或点击。

这是单次生成中从未见过的创意飞跃。

⚠️ 评分不一定线性上升

虽然分数总体改善，但模式并非干净线性。后期实现整体更好，但经常发现更喜欢中间迭代而非最后一次。实现复杂性也往往在几轮中增加，Generator 响应 Evaluator 的反馈尝试更雄心勃勃的解决方案。

🏗️ 三 Agent 全栈架构

将 GAN 启发的模式应用到全栈开发。Generator-Evaluator 循环自然映射到软件开发生命周期，代码审查和 QA 扮演与前端评估相同的结构角色。

📋 Planner

1-4 句 prompt → 完整产品 Spec。强调产品上下文和高层技术设计，而非详细技术实现。编织 AI 特性。

💻 Generator

每次 Sprint 做一个特性。React + Vite + FastAPI + SQLite/PostgreSQL。每个 Sprint 结束时自我评估。

🔍 Evaluator

Playwright MCP 点击运行中的应用。四个维度评分 + 硬阈值。低于阈值则 Sprint 失败，Generator 获得详细反馈。

📝 Sprint Contract 机制

每个 Sprint 前，Generator 和 Evaluator 协商 Sprint Contract——在写任何代码之前就"完成"的定义达成一致。

为什么需要 Sprint Contract？

产品 Spec 故意是高层级的。需要一个步骤来桥接用户故事和可测试实现之间的差距。

  • Generator 提出构建什么以及如何验证成功
  • Evaluator 审查提案，确保 Generator 在构建正确的东西
  • 双方迭代直到达成一致
  • Generator 基于协商后的 Contract 构建
  • 完成后交给 QA 验证

🔧 调优 Evaluator 的过程

最初，Claude 作为 QA Agent 表现很差：

  • 识别了真正的问题，然后说服自己认为这些不是大问题并批准工作
  • 倾向于表面测试，而非探测边界情况，更微妙的 bug 经常溜过

调优循环：阅读 Evaluator 日志 → 找到判断与人类不同的例子 → 更新 QA prompt 解决这些问题 → 多轮迭代。

🆚 实战对比：Solo vs Full Harness

Prompt："创建一个 2D 复古游戏制作器，包括关卡编辑器、精灵编辑器、实体行为和可玩测试模式。"

❌ Solo（20 min / $9）

• 布局浪费空间，固定高度面板导致大部分视口为空
• 工作流僵硬——提示先创建精灵和实体，但 UI 没有引导
• 游戏完全坏了——实体出现但不响应输入
• 代码中实体定义和游戏运行时的连接断裂

✅ Full Harness（6 hr / $200）

• Planner 扩展为 16 特性 spec，10 个 Sprint
• Canvas 使用全视口，面板尺寸合理，一致的视觉身份
• 精灵编辑器更丰富——更干净的工具面板、更好的颜色选择器
• 内置 Claude 集成，通过提示生成游戏内容
• 游戏实际能玩——可以移动实体

📊 Planner Spec 亮点

从一句话 prompt 扩展出的 16 特性 spec 包括：

  • 核心编辑器（关卡、精灵、实体行为、测试模式）
  • 精灵动画系统
  • 行为模板
  • 音效和音乐
  • AI 辅助精灵生成器和关卡设计器
  • 游戏导出与可分享链接

🔧 简化与迭代

第一版 Harness 结果令人鼓舞，但臃肿、缓慢且昂贵。逻辑下一步：找到简化方法而不降低性能。

🔄 Harness 简化原则

"Harness 中的每个组件都编码了一个关于模型不能独自做什么的假设"。这些假设值得压力测试，因为它们可能不正确，并且可能随模型改进而快速过时。

Anthropic 的 Building Effective Agents 原则："找到最简单的解决方案，只在需要时增加复杂性"。

第一次尝试：激进简化
大幅削减 Harness 并尝试新创意 → 无法复制原始性能。难以判断哪些组件是 load-bearing 的。
第二次尝试：逐一移除
每次移除一个组件并审查对最终结果的影响 → 更方法化。
Opus 4.6 发布：进一步动机
Opus 4.6 计划更仔细、持续更长的 agentic 任务、在更大代码库中更可靠地运行、更好的代码审查和调试技能。Harness 原本就是为了补充这些能力而构建的。
关键移除：Sprint 结构
Sprint 结构帮助将工作分解为块。Opus 4.6 改进后，模型可能原生处理这个工作而无需分解。移除了 Sprint 结构，保留 Planner 和 Evaluator。
Evaluator 移到运行结束
从每个 Sprint 评分改为运行结束时的单次 QA。模型能力增强后，Evaluator 是否值得取决于任务相对于模型独立能力的难度边界。

💡 关键洞察：Evaluator 不是固定的 yes-or-no

当任务超出当前模型独立可靠完成的能力时，Evaluator 值得成本。当任务在模型能力边界内时，Evaluator 成为不必要的开销。

🔍 QA 仍然捕捉到真正的差距

Round 1 反馈："核心 DAW 特性是 display-only 没有交互深度——clips 无法在时间线上拖拽/移动，没有乐器 UI 面板，没有视觉效果编辑器。这些不是边缘情况——它们是使 DAW 可用的核心交互。"

Round 2 反馈："音频录制仍然是 stub-only、clip 调整大小和分割未实现、效果可视化是数字滑块而非图形（无 EQ 曲线）"。

🎵 最终成果

最终应用拥有功能齐全的音乐制作程序的核心组件：

  • ✅ 工作中的排列视图（Arrangement View）
  • ✅ 混音器（Mixer）
  • ✅ 传输控制（Transport）在浏览器中运行
  • ✅ 能够通过提示创作短歌曲片段——Agent 设置节拍和调性、布局旋律、构建鼓轨、调整混音器电平、添加混响
  • ✅ Agent 可以使用工具自主驱动简单的端到端制作

⚠️ 剩余限制

Claude 实际上听不到声音，这使得 QA 反馈循环在音乐品味方面效果较差。Agent 的歌曲创作技能仍需要大量工作。离专业音乐制作程序还很远。

💡 核心经验

从这项工作中提炼出的关键经验。

1. 实验 + 调优

始终应该针对正在构建的模型做实验，阅读真实问题上的 traces，调优性能以达到期望的结果。

2. 任务分解

处理更复杂任务时，有时可以通过分解任务并对问题的每个方面应用专用 Agent 来获得提升。

3. 新模型落地时重新审查

移除不再对性能 load-bearing 的部分，添加新的部分以实现以前不可能的更大能力。

4. Harness 空间在移动而非缩小

有趣 Harness 组合的空间不会随模型改进而缩小——它会移动。AI 工程师的工作是持续找到下一个新颖组合。

🎯 Harness 设计核心原则

分离生成和评估
自我评估不可靠 → 独立评估者 + 反馈循环 → 持续改进
主观质量可以编码
将"这个好吗？"转化为具体的、可评分的维度 → 给模型具体的评判标准
Harness 假设需要压力测试
每个组件编码了关于模型不能做什么的假设 → 这些可能不正确或快速过时
Evaluator 是动态决策
当任务超出模型独立能力时值得成本，否则是不必要的开销
从简单开始，需要时增加复杂性
找到最简单的解决方案，只在需要时增加复杂度

"From this work, my conviction is that the space of interesting harness combinations doesn't shrink as models improve. Instead, it moves, and the interesting work for AI engineers is to keep finding the next novel combination."
