🤔 为什么用多 Agent

研究涉及开放性问题，很难提前预测所需步骤。多 Agent 系统特别适合研究任务，因为研究需要灵活性来根据发现动态调整方向。

🧠 子 Agent 的核心价值

  • 压缩：从大量语料中提炼洞察。子 Agent 在并行中各自拥有独立上下文窗口，探索问题的不同方面
  • 关注点分离：不同的工具、提示和探索轨迹，减少路径依赖
  • 并行推理：扩展单 Agent 无法处理的任务容量

📊 内部评估结果

Claude Opus 4（Lead Agent）+ Claude Sonnet 4（Subagents） 在内部研究评估上超越单 Agent Claude Opus 4 达 90.2%。

案例：识别 S&P 500 信息技术板块所有公司董事会成员。多 Agent 系统通过分解任务给子 Agent 找到正确答案，单 Agent 系统因缓慢的顺序搜索而失败。

🔍 传统 RAG（静态检索）

获取与输入查询最相似的 chunks，用这些 chunks 生成响应。固定的、一次性检索。

🧠 多 Agent 研究（动态搜索）

多步搜索，动态找到相关信息，适应新发现，分析结果生成高质量答案。类似人类研究过程。

💡 模型升级 > Token 预算加倍

升级到 Claude Sonnet 4 的性能提升大于在 Claude Sonnet 3.7 上加倍 token 预算。最新 Claude 模型是 token 使用效率的大幅乘数。

⚠️ 适用场景限制

多 Agent 系统适合：高价值任务 + 大量并行化 + 信息超出单上下文窗口 + 需要多个复杂工具。不适合需要所有 Agent 共享同一上下文或 Agent 间有大量依赖的任务（如大多数编码任务）。

🏗️ 架构概览

🔄 Lead Agent 迭代流程

Step 1: 思考方法
使用 Extended Thinking 规划方法，评估工具适用性，确定查询复杂度和子 Agent 数量。
Step 2: 保存计划到 Memory
持久化上下文，因为如果上下文窗口超过 200K token 会被截断，保留计划很重要。
Step 3: 创建专用 Subagents
每个 Subagent 有特定研究任务，独立执行网页搜索、评估工具结果、返回发现。
Step 4: 综合 + 决策
Lead Agent 综合结果，决定是否需要更多研究——可以创建额外子 Agent 或优化策略。
Step 5: Citation Agent
收集足够信息后，退出研究循环，将发现传递给 Citation Agent 处理文档和识别引用位置。

📝 8 大提示工程原则

多 Agent 系统的协调复杂度快速增长。提示工程是改善这些行为的主要杠杆。

🧠 1. 像你的 Agent 一样思考

用与系统完全相同的提示和工具构建模拟，观察 Agent 逐步工作。立即揭示失败模式：结果足够时继续、搜索查询过长、选择错误工具等。

📋 2. 教协调者如何委派

每个子 Agent 需要：目标、输出格式、工具和来源指南、清晰的任务边界。模糊指令导致重复工作、遗漏或找不到必要信息。

⚖️ 3. 按查询复杂度缩放

简单事实查找：1 Agent，3-10 次工具调用。直接比较：2-4 Subagents，各 10-15 次。复杂研究：10+ Subagents，明确分工。

🔧 4. 工具设计和选择至关重要

Agent-工具接口与人类-计算机接口同样关键。给 Agent 明确启发式：先检查所有可用工具，匹配工具与用户意图，偏好专用工具。

🔄 5. 让 Agent 自我改进

Claude 4 模型是出色的提示工程师。给定提示和失败模式，能诊断失败原因并建议改进。创建工具测试 Agent 使任务完成时间下降 40%。

🔍 6. 先广后窄

搜索策略应镜像人类专家研究：先探索全景，再深入细节。Agent 倾向于过长、过具体的查询，提示它们从短而广的查询开始。

💭 7. 引导思考过程

Extended Thinking 模式作为可控草稿板。Lead Agent 用它规划，Subagents 用 Interleaved Thinking 在工具结果后评估质量和识别差距。

⚡ 8. 并行工具调用

两种并行：(1) Lead Agent 并行启动 3-5 Subagents；(2) Subagents 并行使用 3+ 工具。复杂查询研究时间缩减高达 90%。

📊 评估策略

评估多 Agent 系统有独特挑战。即使起点相同，Agent 可能采取完全不同但有效的路径到达目标。

🎯 三大评估原则

原则 1: 立即用小样本开始评估
早期开发中，少量测试（约 20 个查询）就能清晰看到变更影响。不要等到构建大规模评估才开始测试——效果大的变更用几个案例就能发现。
原则 2: LLM-as-Judge 可扩展评估
用 LLM 法官评估：事实准确性、引用准确性、完整性、来源质量、工具效率。单次 LLM 调用输出 0.0-1.0 分数和 pass-fail 最一致且与人类判断最对齐。
原则 3: 人工评估捕获自动化遗漏
人类测试者发现早期 Agent 一致选择 SEO 优化内容农场而非权威来源（如学术 PDF 或个人博客）。在提示中添加来源质量启发式解决了这个问题。

⚡ 涌现行为

多 Agent 系统有涌现行为——Lead Agent 的微小变更会不可预测地改变 Subagent 行为。成功需要理解交互模式，而不仅是单个 Agent 行为。最佳提示不是严格指令，而是协作框架：定义分工、解决问题方法和努力预算。

🔧 生产可靠性

在传统软件中，bug 可能破坏功能。在 Agent 系统中，微小变更会级联成大的行为变化。

Agent 有状态且错误累积

Agent 长时间运行，跨多工具调用维护状态。需要持久执行代码和处理错误。小失败对 Agent 可能是灾难性的。

调试需要新方法

Agent 做动态决策，运行间非确定性。添加全生产追踪来诊断失败原因。监控 Agent 决策模式和交互结构。

部署需要协调

Agent 系统是有状态的 prompts、工具和执行逻辑网络。使用 Rainbow Deployments 逐步迁移流量，避免中断运行中的 Agent。

同步执行创建瓶颈

Lead Agent 同步执行 Subagents，等待每组完成才继续。简化协调但创建信息流瓶颈。异步执行将带来额外并行化。

🔄 错误恢复策略

  • 不能从头重启：重启昂贵且让用户沮丧
  • 构建系统从 Agent 出错时所在位置恢复
  • 利用模型智能优雅处理问题：告诉 Agent 工具失败并让它适应
  • 结合 AI Agent 的适应性与确定性保障（重试逻辑、定期检查点）

📎 附录：额外技巧

🏁 多轮状态变更的终态评估

评估修改持久状态的 Agent 时，关注终态评估而非逐轮分析。评估是否达到正确最终状态，而非是否遵循特定过程。对复杂流程，分解为离散检查点。

💬 长程对话管理

生产 Agent 经常进行数百轮的对话。实施模式：Agent 总结已完成工作阶段，存储关键信息到外部内存。接近上下文限制时，生成具有干净上下文的新 Subagent，同时通过仔细交接保持连续性。

📁 Subagent 输出到文件系统

Subagent 输出可以直接绕过主协调者，写入外部系统，然后传回轻量引用给协调者。这防止多阶段处理中的信息丢失，减少通过对话历史复制大输出的 token 开销。特别适合结构化输出（代码、报告、数据可视化）。

📌 结论

构建 AI Agent 时，最后一英里通常成为大部分旅程。在开发者机器上工作的代码库需要大量工程才能成为可靠的生产系统。

🎯 成功要素

  • 精心工程（Careful engineering）
  • 全面测试（Comprehensive testing）
  • 注重细节的提示和工具设计（Detail-oriented prompt and tool design）
  • 稳健的运营实践（Robust operational practices）
  • 研究、产品和工程团队之间的紧密协作（Tight collaboration）
  • 对当前 Agent 能力的深入理解（Strong understanding of capabilities）
