📋 背景与声明

8 月到 9 月初，三个基础设施 bug 间歇性地降低了 Claude 的响应质量。这些 bug 现已全部解决。

📢 明确声明

"We never reduce model quality due to demand, time of day, or server load. The problems our users reported were due to infrastructure bugs alone."

我们绝不会因需求、时间段或服务器负载降低模型质量。用户报告的问题完全源于基础设施 bug。

🔍 为什么公开技术细节

通常不分享如此详细的基础设施技术细节，但这些问题的范围和复杂度证明了需要更全面的解释。

🏗️ Claude 大规模服务架构

通过第一方 API、Amazon Bedrock 和 Google Cloud Vertex AI 向数百万用户提供服务。部署在多种硬件平台上。

🔶 AWS Trainium

Anthropic 自研芯片，针对 Claude 优化。

🟢 NVIDIA GPUs

通用 GPU 加速推理。

🔵 Google TPUs

Google 张量处理单元，使用 XLA 编译器。

🎯 等价标准

每个硬件平台有不同特性和特定优化。但有严格的模型实现等价标准：用户应获得相同质量的响应，无论哪个平台服务请求。

这种复杂性意味着任何基础设施变更都需要在所有平台和配置上仔细验证。

🔀 Bug 1: 上下文窗口路由错误

部分 Sonnet 4 请求被错误路由到为即将到来的 1M token 上下文窗口配置的服务器。

❌ 错误路由

短上下文请求路由到 1M 上下文服务器。路由是"粘性"的——一旦请求被错误服务器服务，后续跟进很可能被同一错误服务器服务。

✅ 修复

修复路由逻辑确保短和长上下文请求定向到正确的服务器池。9 月 4 日部署，9 月 16-18 日全平台完成。

💥 Bug 2: 输出损坏

8 月 25 日部署到 Claude API TPU 服务器的错误配置导致 token 生成期间出错。

🔧 根因

运行时性能优化偶尔给本不应在上下文中产生的 token 赋予高概率。例如：

  • 对英文提示产生泰语或中文字符
  • 在代码中产生明显的语法错误
  • 用户可能在英文响应中间看到 "สวัสดี"

📅 受影响时间

Opus 4.1 和 Opus 4：8 月 25-28 日
Sonnet 4：8 月 25 日 – 9 月 2 日

🌐 受影响平台

仅第一方 Claude API。第三方平台未受影响。

✅ 修复

9 月 2 日识别问题并回滚变更。已在部署流程中添加意外字符输出检测测试。

🔬 Bug 3: 近似 top-k XLA:TPU 编译错误

8 月 25 日部署改进 Claude 选择 token 方式的代码，无意触发了 XLA:TPU 编译器中的潜在 bug。

🧠 TPU 上的文本生成复杂性

  • Claude 生成文本时计算每个可能下一个词的概率，然后从概率分布中随机采样
  • 使用 top-p 采样避免荒谬输出——只考虑累积概率达到阈值的词
  • 在 TPU 上，模型跨多个芯片运行，概率计算在不同位置发生
  • 排序这些概率需要芯片间协调数据，这很复杂

🔍 精度不匹配根因

模型用 bf16（16 位浮点）计算下一个 token 概率。但向量处理器是 fp32 原生，所以 TPU 编译器（XLA）可以通过将一些操作转换为 fp32 来优化运行时。

❌ 问题

应以最高概率 token 同意的操作在不同精度级别运行，导致它们不同意哪个 token 概率最高。最高概率 token 有时完全从考虑中消失。

✅ 修复

从近似 top-k 切换到精确 top-k，在 fp32 精度上标准化一些额外操作。接受轻微效率影响——模型质量不可协商。

🔀 Bug 行为的 frustrating 不一致性

  • 根据无关因素变化：之前或之后运行什么操作、是否启用调试工具
  • 相同提示可能在一个请求上完美工作，在下一个请求上失败
  • 12 月的 workaround 无意中掩盖了这个问题——修复它暴露了更深层的 bug

🔍 为什么检测困难

这些 bug 暴露了关键的检测差距。

评估未捕获降级

运行的评估没有捕获用户报告的降级。部分因为 Claude 通常能从孤立错误中恢复良好。

隐私限制调试

内部隐私和安全控制限制工程师何时能访问用户交互。保护隐私但阻止工程师检查识别或复现 bug 所需的有问题的交互。

不同症状

每个 bug 在不同平台以不同比率产生不同症状。看起来像随机、不一致的降级。

社区报告脱节

意识到在线报告增加，但缺乏清晰方式将这些与最近的每次变更联系起来。

🔮 改进措施

📊 更敏感的评估

开发了能更可靠区分工作和损坏实现的评估。持续改进以密切关注模型质量。

🔄 更多地方运行评估

在真实生产系统上持续运行评估，捕获上下文窗口负载均衡等错误。

⚡ 更快的调试工具

开发基础设施和工具以更好地调试社区来源反馈，同时不牺牲用户隐私。

📢 用户反馈至关重要

这些事件表明还需要用户在 Claude 响应达不到通常标准时的持续信号：

  • 观察到的具体变更报告
  • 遇到的意外行为示例
  • 不同用例的模式
  • 在 Claude Code 中使用 /bug 命令或在 Claude 应用中使用"踩"按钮

"Reports of specific changes observed, examples of unexpected behavior encountered, and patterns across different use cases all helped us isolate the issues."
