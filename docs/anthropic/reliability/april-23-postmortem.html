📋 问题概述

过去一个月，Anthropic 收到报告称 Claude 的响应对部分用户变差了。追踪发现这是三个独立变更的叠加效应，分别影响了 Claude Code、Claude Agent SDK 和 Claude Cowork。API 未受影响。

🎯 三个问题的叠加效应

因为每个变更影响不同的流量片、不同的时间表，综合效果看起来像是广泛的、不一致的降级。早期难以与正常用户反馈波动区分，内部使用和评估最初也没有复现问题。

📉 问题 1: 推理努力降级

默认推理努力从 high 降至 medium → 3 月 4 日 → 4 月 7 日恢复。影响 Sonnet 4.6、Opus 4.6。

🧠 问题 2: 缓存优化 Bug

清除旧推理的 bug 导致每轮都丢弃思考历史 → 3 月 26 日 → 4 月 10 日修复。影响 Sonnet 4.6、Opus 4.6。

📝 问题 3: 系统提示词变更

减少冗长的系统提示指令损害编码质量 → 4 月 16 日 → 4 月 20 日恢复。影响 Sonnet 4.6、Opus 4.6、Opus 4.7。

📉 问题 1: 推理努力降级

2 月发布 Opus 4.6 时，Claude Code 默认推理努力设为 high。但用户反馈高努力模式偶尔思考时间过长，导致 UI 看起来卡死。

🔄 决策过程

3 月 4 日: 降级到 medium
内部评估显示 medium 实现了略低的智能但显著更低的延迟，且没有同样的长尾延迟问题。通过产品内对话框解释理由后推出。
用户反馈: "感觉不那么智能了"
Anthropic 发布了多个设计迭代使当前努力设置更清晰（启动通知、内联选择器、恢复 ultrathink），但大多数用户保留了 medium 默认。
4 月 7 日: 恢复到 high/xhigh
听到更多客户反馈后逆转决定。Opus 4.7 默认 xhigh，其他模型默认 high。

💡 关键教训

在智能和延迟之间做权衡时，让用户选择比改变默认更好。用户宁愿默认更高的智能，然后为简单任务选择更低努力。

🧠 问题 2: 缓存优化 Bug

3 月 26 日推出了一项效率改进：如果会话空闲超过一小时，通过清除旧思考部分来降低用户恢复会话的成本。

🐛 Bug 机制

✅ 预期行为

会话空闲超过一小时后，清除一次旧思考。因为请求会是 cache miss，可以从请求中修剪不必要的消息以减少发送到 API 的 uncached token 数量。然后恢复发送完整推理历史。

❌ 实际行为

没有只清除一次，而是在会话剩余时间的每轮都清除。一旦会话跨越空闲阈值，之后每个请求都告诉 API 只保留最新的推理块，丢弃之前的一切。

🔍 复合效应

  • 如果在 Claude 使用工具中间发送后续消息，这会在新 flag 下启动新轮次，所以当前轮的推理也被丢弃
  • Claude 继续执行，但越来越没有记忆它为什么选择这样做
  • 表现为用户报告的健忘、重复和奇怪的工具选择
  • 持续丢弃思考块导致后续请求也产生 cache miss，驱动了使用限额消耗更快的单独报告

🔍 为什么难以发现

两个不相关的实验使最初复现困难：

  • 内部消息排队相关服务器端实验
  • 显示思考的正交变更在大多数 CLI 会话中抑制了此 bug
  • Bug 位于 Claude Code 上下文管理、Anthropic API 和扩展思考的交叉点
  • 通过了多个人工和自动代码审查、单元测试、端到端测试、自动验证和 dogfooding
  • 只在角落情况（过期会话）下发生

🤖 Opus 4.7 Code Review 发现 Bug

作为调查的一部分，用 Opus 4.7 回测了对抗违规 PR 的 Code Review。提供收集完整上下文所需的代码仓库时，Opus 4.7 找到了 bug，而 Opus 4.6 没有。

作为预防，现在正在为 Code Review 添加额外仓库作为上下文支持。

📝 问题 3: 系统提示词变更

Claude Opus 4.7 有一个显著的行为特点：相比前代，它倾向于非常冗长。这使它在难题上更聪明，但也产生更多输出 token。

📋 有问题的系统提示变更

"Length limits: keep text between tool calls to ≤25 words. Keep final responses to ≤100 words unless the task requires more detail."

4 月 16 日与 Opus 4.7 一起推出。经过多周内部测试，在运行的评估集中没有回归。

🔍 事后 Ablation 分析

使用更广泛的评估集运行更多 ablation（从系统提示中逐行移除以理解每行的影响）：

  • 其中一个评估显示 Opus 4.6 和 4.7 都有 3% 的下降
  • 立即在 4 月 20 日发布中恢复

⚠️ 关键教训

单个系统提示行可能对智能产生不成比例的影响。即使没有回归的评估集也可能遗漏重要影响面。

📅 时间线总览

3 月 4 日: 推理努力降至 medium
为减少长尾延迟，Opus 4.6 默认从 high 改为 medium。用户开始报告"感觉不那么智能"。
3 月 26 日: 缓存优化引入 Bug
旨在减少空闲会话恢复成本的变更引入了每轮清除思考历史的 bug。用户报告健忘和重复。
4 月 7 日: 推理努力恢复
Opus 4.7 默认 xhigh，其他模型默认 high。所有用户恢复更高智能默认。
4 月 10 日: 缓存 Bug 修复 (v2.1.101)
修复了每轮清除思考历史的 bug。调查中发现 Opus 4.7 Code Review 比 4.6 更好地找到 bug。
4 月 16 日: 系统提示变更推出
减少冗长的提示指令（≤25 词工具间文本，≤100 词最终响应）与 Opus 4.7 一起发布。
4 月 20 日: 提示恢复 (v2.1.116)
Ablation 发现 3% 下降后立即恢复。所有三个问题现在都解决了。
4 月 23 日: 用户额度重置
为所有订阅者重置使用限额。感谢使用 /feedback 命令和发布具体可复现示例的用户。

🔮 改进措施

为避免这些问题再次发生，Anthropic 将采取多项措施：

👥 内部测试改进

确保更大比例的内部员工使用确切的公共构建（而非用于测试新功能的版本）。

🔍 Code Review 增强

改进内部使用的 Code Review 工具，将此改进版本提供给客户。添加额外仓库作为上下文支持。

📝 系统提示严格控制

每个系统提示变更都运行广泛的每模型评估，继续 ablation 理解每行影响，构建新工具使提示变更更容易审查和审计。

🚦 发布流程改进

对于可能与智能权衡的变更，添加浸泡期、更广泛的评估套件和逐步推出，以便更早发现问题。

📢 透明沟通

创建了 @ClaudeDevs on X，深入解释产品决策和背后推理。在 GitHub 集中线程中分享相同更新。
