📋 问题背景

SWE-bench 和 Terminal-Bench 等 Agent 编码基准常用于比较前沿模型的软件工程能力——排行榜上的顶级位置通常只相差几个百分点。但这些分数往往被视为相对模型能力的精确测量。

🔍 发现

仅基础设施配置就能产生超过这些边际的差异。在内部实验中，Terminal-Bench 2.0 上资源最多和最少的设置之间的差距为 6 个百分点（p < 0.01）。

🆚 静态基准 vs Agent 基准

📝 静态基准

直接评分模型输出。运行环境不影响结果。运行时是被动的容器。

🤖 Agent 编码基准

模型获得完整环境，编写程序、运行测试、安装依赖、多轮迭代。运行时是问题解决过程的组成部分。

"Two agents with different resource budgets and time limits aren't taking the same test."

🧪 实验设计

在 Google Kubernetes Engine 集群上运行 Terminal-Bench 2.0，发现分数与官方排行榜不匹配，基础设施错误率高达 6%。

🔧 容器资源执行机制

容器运行时通过两个独立参数执行资源：

📦 保证分配（Guaranteed）

预先保留的资源。容器的最低保证。

🚫 硬限制（Hard Limit）

超过此值容器被杀死（OOM-kill）。硬性天花板。

当两者设为相同值时，瞬态内存波动没有余地——可能导致本应成功的容器被 OOM-kill。

📊 核心发现

成功率随资源余量增加而增加。主要由基础设施错误率在每个步骤单调下降驱动。

📈 成功率变化

1x → 3x: 在噪声范围内波动
成功率波动在噪声边际内（p=0.40）。大多数在 1x 崩溃的任务无论如何都会失败——Agent 探索、撞到资源墙、被抢占，但从未走在正确解决方案的道路上。
3x → 无上限: 成功率加速攀升
成功率增长快于基础设施错误下降。额外资源使 Agent 能尝试只在慷慨分配下有效的方法：拉取大型依赖、生成昂贵的子进程、运行内存密集型测试套件。
总体影响
3x 到无上限之间，基础设施错误额外下降 1.6 个百分点，成功率跳跃近 4 个百分点。无上限比 1x 总提升 +6 个百分点（p < 0.01）。

🔄 跨模型复制

在不同 Anthropic 模型上复制了核心发现。效应方向一致，幅度不同。相同趋势似乎适用于 Claude 以外的模型，但未严格测试。

📐 SWE-bench 交叉实验

在 SWE-bench 上运行交叉实验，227 个问题，每个 10 个样本，总 RAM 最高到基线的 5 倍。

  • 相同效应：分数随 RAM 单调增加
  • 但幅度更小：5x 比 1x 仅高 1.54 个百分点
  • SWE-bench 任务资源密集度较低，所以效应更小是预期的
  • 表明资源分配在 SWE-bench 中也不是中性的

🎯 对测量的影响

资源配置不仅影响稳定性，还改变评估实际测量的内容。

✅ 高达 ~3x: 修复基础设施可靠性

额外资源修复瞬态资源峰值问题。Terminal-Bench 维护者使用的沙盒提供者在后台隐式这样做。评估变得更稳定而没有变得更容易。

⚠️ 超过 3x: 积极帮助 Agent

额外资源开始积极帮助 Agent 解决之前无法解决的问题。限制实际上改变了评估测量的内容。

⚖️ 紧密限制 vs 慷慨限制的不同奖励

紧密限制意外地奖励非常高效的策略。慷慨限制更宽容，奖励能更好利用所有可用资源的 Agent。

编写精简高效代码的 Agent 在紧约束下表现好。用重量级工具暴力解决方案的 Agent 在慷慨约束下表现好。两者都是合法的测试目标，但将它们合并为单一分数而不指定资源配置，使得差异和真实世界泛化性难以解释。

📦 案例: bn-fit-modify 任务

需要贝叶斯网络拟合的 Terminal-Bench 任务。一些模型的第一个动作是安装标准 Python 数据科学栈：pandas、networkx、scikit-learn 及其所有工具链。

  • 在慷慨限制下：有效
  • 在紧密限制下：pod 在安装期间耗尽内存，Agent 还没写一行解决方案代码
  • 存在更精益的策略（仅使用标准库从头实现数学），一些模型默认这样做，其他不
  • 不同模型有不同默认方法，资源配置决定哪些方法碰巧成功

🌐 其他方差来源

资源分配不是唯一的隐藏变量。

⏱️ 时间限制

在某些配置中，时间限制也开始发挥作用。

🏥 集群健康

集群健康状况影响最终分数。

💻 硬件规格

不同硬件规格导致不同结果。

🔀 并发级别

并发级别影响性能和稳定性。

🌍 出站带宽

出站带宽影响依赖拉取等操作。

🕐 一天中的时间

通过率随时间波动，可能因为 API 延迟随流量模式变化。

"The boundary between 'model capability' and 'infrastructure behavior' is blurrier than a single benchmark score suggests."

📋 推荐方案

理想情况是在完全相同的硬件条件下运行每个评估。但这可能不总是实际。

🔧 关键建议：指定两个参数

鉴于容器运行时实际执行资源的方式——通过保证分配和单独的硬杀死阈值——建议评估为每个任务指定两个参数，而非单一固定值。

❌ 单一固定规格

保证分配 = 杀死阈值，零余量。瞬态内存波动足以 destabilize 评估。

✅ 分离两个参数

给容器足够呼吸空间避免虚假 OOM-kill，同时执行防止分数膨胀的硬天花板。

📐 经验校准原则

地板和天花板之间的带应校准，使分数在彼此噪声范围内。例如在 Terminal-Bench 2.0 中：

  • 每任务规格的 3x 天花板将基础设施错误率降低约三分之二（5.8% → 2.1%，p < 0.001）
  • 同时保持分数提升温和且在噪声范围内（p = 0.40）
  • 这是合理的权衡：基础设施混淆因素大部分中和，而不移除有意义的资源压力
  • 确切倍数因基准和任务分布而异，应报告

💡 为什么重要

这些发现对评估基础设施之外有实际后果。

⚠️ 排行榜差异的解读

基准分数越来越多地用作决策输入，但这种增加的注意力（和依赖）并不总是伴随着它们如何运行或报告的相应严格性。

排行榜上 2 分的领先可能反映真实的能力差异，也可能反映一个评估在更强大的硬件上运行，或在一天中更幸运的时间运行，或两者兼有。

📊 不同角色的启示

🏢 对 Anthropic 等实验室

Agent 评估的资源配置应被视为一级实验变量，以与提示格式或采样温度相同的严格程度记录和控制。

📝 对基准维护者

发布推荐资源规格（如 Terminal-Bench 2.0 所做）可以大有裨益，而指定执行方法将弥合我们发现的差距。

👀 对基准结果消费者

Agent 评估上的小分数差异携带的不确定性比报告数字的精度暗示的更多——尤其是一些混淆因素太难控制。

🎯 核心建议

在资源配置标准化之前，低于 3 个百分点的排行榜差异值得怀疑，除非评估配置被记录并匹配。

  • Terminal-Bench 中适中资源配置范围的观察 spread 略低于 2 个百分点
  • 天真二项式置信区间已经跨越 1-2 个百分点
  • 这里记录的基础设施混淆因素叠加在上面，而非在其中
  • 在分配范围的极端，spread 达到 6

"A few-point lead might signal a real capability gap—or it might just be a bigger VM."
