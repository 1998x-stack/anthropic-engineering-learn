📚 RAG 基础原理

当知识库超过 200,000 tokens（约 500 页），无法全部放入 prompt 时，Retrieval-Augmented Generation (RAG) 是标准方案。它通过检索相关信息片段来增强模型的回答能力。

⚡ 一个更简单的选项

如果你的知识库小于 200,000 tokens，可以直接将全部内容放入 prompt。配合 Prompt Caching，延迟降低 >2x，成本降低高达 90%。无需 RAG。

📈 Embedding（语义匹配）

将文本转为向量，通过语义相似度检索。擅长理解含义和同义表达，但可能错过精确的术语匹配。

📜 BM25（词法匹配）

基于 TF-IDF 的排名函数，通过精确词语匹配检索。对包含唯一标识符、错误码、专有名词的查询特别有效。

例子：用户查询 "Error code TS-999"。Embedding 模型可能找到关于"错误码"的通用内容，而 BM25 会精确匹配到包含 "TS-999" 的文档。两者结合才能提供完整的检索能力。

🚨 上下文缺失问题

传统 RAG 在分块时丢失了上下文信息，导致检索系统经常无法找到正确的信息片段。这是 RAG 系统最大的痛点。

❌ 丢失上下文的 Chunk

"The company's revenue grew by 3% over the previous quarter." // 哪家公司？哪个季度？ // 完全无法判断！

当用户查询 "ACME Corp Q2 2023 的收入增长"时，这个 chunk 缺少公司名和时间信息，很难被正确检索到。

✅ 保留上下文的 Chunk

This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million. "The company's revenue grew by 3% over the previous quarter."

通过在 chunk 前添加上下文说明，检索系统可以精确匹配 "ACME"、"Q2 2023" 等关键信息。

💡 SEC 文件检索案例

假设你的知识库中嵌入了大量 U.S. SEC 文件。用户问："What was the revenue growth for ACME Corp in Q2 2023?"

传统 RAG 分块后，原始 chunk 只包含 "revenue grew by 3%"，没有公司名称、没有时间信息。即使语义上相关，检索系统也很难将这个 chunk 与特定的查询匹配。

💡 Contextual Retrieval 核心思路

Contextual Retrieval 通过在每个 chunk 前添加 chunk 级别的解释性上下文来解决上下文丢失问题。包含两个子技术：Contextual Embeddings 和 Contextual BM25。

与其他方法的区别：之前提出的方案包括在 chunk 中添加通用文档摘要（效果有限）、假设文档嵌入（HyDE）和基于摘要的索引（性能较低）。Contextual Retrieval 为每个 chunk 生成针对性的上下文，而非通用摘要。

💻 实现方法

使用 Claude 3 Haiku 自动为每个 chunk 生成上下文描述。配合 Prompt Caching，成本极低。

📝 上下文生成 Prompt

<document> {{WHOLE_DOCUMENT}} </document> Here is the chunk we want to situate within the whole document <chunk> {{CHUNK_CONTENT}} </chunk> Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else.

将整个文档和目标 chunk 一起传入 Claude，让模型根据文档全文为 chunk 生成简洁的定位描述。生成的上下文文本（50-100 tokens）会被前置到 chunk 中，再进行 embedding 和 BM25 索引。

💰 Prompt Caching 降低成本

Contextual Retrieval 的低成本得益于 Claude 的 Prompt Caching 功能。无需为每个 chunk 重复传递完整文档 -- 只需将文档缓存一次，后续 chunk 的处理直接引用缓存内容。

成本估算参数：

  • Chunk 大小：~800 tokens
  • 文档大小：~8,000 tokens
  • 上下文指令：~50 tokens
  • 生成上下文：~100 tokens/chunk
  • 总成本：$1.02 / 百万文档 tokens（一次性）

🚀 Reranking 进一步优化

初始检索可能返回数百个 chunks。Reranking 是一种过滤技术，确保只有最相关的 chunks 被传递给模型，同时降低成本和延迟。

Step 1: 初始检索
使用 Contextual Embeddings + Contextual BM25 检索 top-150 个可能相关的 chunks。
Step 2: Reranking
将 top-N chunks 连同用户查询一起传入 reranking 模型（如 Cohere Reranker），为每个 chunk 评分。
Step 3: 选择 Top-K
根据 reranking 分数选出 top-20 最相关的 chunks。
Step 4: 生成回答
将 top-K chunks 作为上下文传入 LLM，生成最终回答。

⚠ 延迟与成本权衡

Reranking 在运行时增加了一个额外步骤，不可避免地增加少量延迟（虽然 reranker 会并行处理所有 chunks）。rerank 更多 chunks = 更好的性能，但更高的延迟和成本。需要在你的具体场景中实验找到最佳平衡点。

🔧 实施考量

在实际部署 Contextual Retrieval 时，需要在多个维度上做出权衡决策。

✂ Chunk 边界

chunk 大小、边界位置、重叠区域都会影响检索性能。需要根据文档结构和查询模式进行调优。

📊 Embedding 模型

Contextual Retrieval 在所有模型上都有提升，但 Gemini 和 Voyage embeddings 的效果最佳。

📝 自定义 Prompt

通用 prompt 效果不错，但领域定制的 prompt可能更好（如加入术语表）。

📈 Chunks 数量选择

测试了 5、10、20 个 chunks。Top-20 表现最好，但更多 chunks 可能分散模型注意力。需要针对具体场景实验。

🔬 持续评估（Evals）

响应生成可通过传递 contextualized chunk 并区分上下文和原始 chunk 内容来进一步优化。务必运行 evals 验证效果。

🏆 完整 Pipeline 总结

所有优化技术可以叠加使用，实现最大性能提升。以下是 Anthropic 大量实验后的核心发现。

🎯 核心发现

  • Embeddings + BM25 优于单独使用 Embeddings
  • Voyage 和 Gemini 提供最佳 embedding 效果
  • 传递 top-20 chunks 比 top-10 或 top-5 更有效
  • 为 chunks 添加上下文显著提升检索精度
  • Reranking 优于不做 reranking
  • 所有优化可以叠加：Contextual Embeddings (Voyage/Gemini) + Contextual BM25 + Reranking + Top-20 chunks
