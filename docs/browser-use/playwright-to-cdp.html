🚫 为什么离开 Playwright

Playwright 和 Puppeteer 对 QA 测试来说很棒，但对 AI 浏览器自动化来说，这些适配器遮蔽了浏览器底层的重要细节。当你窥探幕后，发现直接说浏览器的原生语言 CDP 才是正道。

❌ Playwright 的问题

  • 抽象层遮蔽底层行为
  • Node.js 中间层带来额外网络延迟
  • 数千次 CDP 调用的延迟累积
  • 半数 crash 场景处理不了

✅ Raw CDP 优势

  • 直接与浏览器通信，无中间层
  • 元素提取速度大幅提升
  • 新增 async 反应能力
  • 完整的跨域 iframe 支持

"Building AI browser automation is like building on top of a jenga tower of complexity." — Nick Sweeting

  • Chrome Extension APIs: chrome.tabs, chrome.automation, chrome.scripting

⚠️ Playwright 的锐利边缘

Playwright 的 happy path 通常没问题，但魔鬼在细节中。以下 7 个场景是 Playwright 处理不好或完全无法处理的。

📷 长页面截图

fullPage=True 在超过 16,000px 的页面上可靠地崩溃。

💬 Dialog 处理

alert() / confirm() / onbeforeunload 处理逻辑混乱。

⌨️ 输入焦点

没有 focus page 就尝试 keyboard/mouse/dialog 输入 —— 静默失败。

📥 文件上传下载

远程浏览器上的文件上传和下载处理几乎不可用。

📃 特殊页面

about:*, chrome://*, PDF tab 等特殊页面类型无法处理。

Crashed tab 的检测和恢复在 Playwright 中缺失。

✅ CDP 迁移关键改进

迁移到 CDP 后的三大架构改进：类型安全绑定、事件驱动架构、跨 OOPIF 元素处理。

CDP-USE 类型安全库
Python Type Bindings
从官方 CDP 协议规范自动生成 Python 绑定，提供 TypeScript 级别的类型安全。
事件驱动架构
Watchdog Services
不再只在 action 之间更新状态。订阅 CDP 事件，用 watchdog 监控下载、crash 等。downloads_watchdog 和 crash_watchdog.py 集中处理。
Super-Selector 跨 OOPIF
targetId + frameId + backendNodeId
Tab 不是 page，而是 targets 的集合。新的 "super-selector" 包含 targetId、frameId、backendNodeId、x/y 坐标和 fallback 选择器。

💡 核心洞察

抽象掉 target 层级意味着你失去了路由输入、关联事件和在 DOM churn 后重新定位元素的能力。这就是为什么 Browser Use 需要直接操作 CDP，而不是通过 Playwright 的简化视图。
