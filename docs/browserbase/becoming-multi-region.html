🏗️ 挑战：单区域瓶颈

当 Browserbase 最初构建时，所有服务都运行在 AWS us-west-1。随着全球客户增长，延迟成为头号反馈问题。

每个请求面临 70-80ms 的延迟，这些延迟不仅在累加，还在乘积 — 因为操作是顺序堆叠的。CDP (Chrome DevTools Protocol) 命令是一系列需要顺序执行的小指令，每条命令必须在下一条开始前完成，产生延迟的瀑布效应。

"Whether a customer was in London, Tokyo, or New York, their requests had to make a longer journey to where servers were running, us-west-1."

对于新加坡的用户来说，他们的浏览器命令需要在地球上往返近半圈 — 每一次操作都是如此。

🔍 根因分析：距离即延迟

团队尝试了增加资源、移除虚拟化层 — 但答案其实是物理距离。

尝试 1：增加浏览器资源
给浏览器分配更多计算资源 — 延迟未改善
尝试 2：移除虚拟化层
减少虚拟化开销 — 延迟仍然存在
发现根因：物理距离
CDP 命令需要顺序执行，每条命令的 RTT 都在积累。距离是根本瓶颈。
决策：多区域部署
不再优化流量穿过单区域的路径，而是将基础设施带到用户身边

为什么 CDP 放大延迟

CDP 是一个 "话痨" 协议 — 加载一个页面可能意味着数千次 CDP 请求。每条命令必须等前一条完成才能开始。在 RTT = 150ms 的情况下，1000 条命令意味着额外 150 秒的纯等待时间。

🌍 多区域方案

将浏览器基础设施部署到全球多个战略位置 — 整个迁移仅用一个月。

方案的核心不是在单区域内优化，而是从根本上重新思考如何最小化客户与浏览器 session 之间的物理距离。

❌ 之前：单区域

所有用户 → us-west-1

全球用户共享同一入口

延迟取决于用户到美西的距离

无法按需选择就近节点

✅ 之后：多区域

用户 → 最近的区域

us-east-1 / us-west-2 / eu-central-1 / ap-southeast-1 / ap-northeast-1

API 支持 region 参数

自由选择最佳节点

复合效应

这些延迟数值会随每条 CDP 命令复合累积。在执行需要多次顺序命令的复杂浏览器自动化任务时，实际性能改善远大于单次 RTT 的差异。例如 1000 条命令在 152ms RTT 下需要额外 152 秒，而在 3ms RTT 下仅需 3 秒。

🛠️ 接入指南与最佳实践

切换到多区域非常简单 — 创建 session 时指定 region 参数即可。

curl --request POST \ --url https://www.browserbase.com/v1/sessions \ --header 'Content-Type: application/json' \ --header 'X-BB-API-Key: YOUR_BROWSERBASE_API_KEY' \ --data '{ "projectId": "<YOUR_PROJECT_ID>", "region": "us-east-1" }'
