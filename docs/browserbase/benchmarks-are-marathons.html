🏆 优先级金字塔

Browserbase 的工程优先级排序：Security → Reliability → Performance。这个排序解释了为什么 Ramp、Lovable、Stripe 等领先 AI 公司信任 Browserbase。

  1. 1 Security — 安全第一，永远不妥协
  2. 2 Reliability — 可靠性优先于速度
  3. 3 Performance — 在前两者保障下追求极致性能

"Performance work starts with humility: if you can't measure it, you're guessing."

Browserbase 在 ComputeSDK 的新浏览器基准测试中名列前茅，这得益于过去一年在 "无聊" 的基础设施部分持续投入：session 创建、CDP 连接、导航开销和资源回收。

🌐 RTT 是最重要的指标

对于远程浏览器，Round-Trip Latency (RTT) 是所有指标之王。CDP 的 "话痨" 特性让 RTT 的影响被放大。

CDP 是一个 Chatty Protocol

加载一个页面可能意味着数千次 CDP 请求。如果你的客户端执行 request/response 工作（如路由、拦截或 instrumentation），页面加载通常依赖于对客户端的多次往返。

RTT 影响：1000 条命令
150ms RTT = 150s 额外等待
就近部署后
3ms RTT = 3s 额外等待

"Putting a browser closer to your agent can matter as much as any micro-optimization inside Chromium."

⏱️ CDP Connect Time 不说谎

"赢" benchmark 最简单的方法是让 create 看起来很快 — 然后把真正的工作推迟到后面。如果你单独测量 connect time，这种手法会立刻暴露。

延迟配置（看起来快）

把配置推迟到 connect — 你看起来快了，直到第一个真实用户操作

不确定性行为

提前配置（Browserbase 方式）

在 create 阶段完成所有配置 — 如果有问题，早期失败

确定性行为

重试行为差异

HTTP 请求库通常会自动重试 create 阶段的短暂 500 错误。

CDP 连接重试通常不内置在常见浏览器框架（如 Playwright）中。

Browserbase 的哲学：提前配置浏览器，如果有问题就提前失败，而不是在连接时才失败。

🔗 更少的 Hop，更快的速度

浏览器基础设施本质上是 "WebSockets as a Service"。每一层代理和负载均衡器都在增加延迟。

Load Balancers
流量入口的负载均衡层
Reverse Proxies
反向代理层增加处理延迟
Service Meshes
服务网格的 sidecar 开销
Application-Layer WebSocket Proxies
应用层 WebSocket 代理 — 这是移除后收益最大的层

"A major unlock for us was ruthlessly removing unnecessary hops — especially application-layer WebSocket proxies."

每一个 hop 增加的不仅仅是 "光速" RTT，还有真实的计算延迟。客户持有长连接并通过你的协议栈发送事件。随着系统成熟，团队很容易在遗留路径上堆叠越来越多的层。Browserbase 的关键突破是无情地移除不必要的 hop。

⚡ Goroutines vs Event Loops

CDP 流量天生是突发性的。当页面加载或动画播放时，短时间内会产生数千个事件。选择正确的并发模型至关重要。

Go Goroutines

在 burst 和 fan-out 场景下，Go 的并发模型（goroutines）简单地更适合热路径的 WebSocket 和 CDP 代理

适合热路径

单线程 Event Loop

在 burst 场景下，单事件循环模型在尾部延迟方面表现不如 goroutine 模型

通用场景仍可用

关键洞察

这不意味着 "Go 好，Node 差"。而是说：应该为承载最多数据包的路径选择正确的工具。CDP 流量的突发性和 fan-out 特性让 goroutine 模型在热路径上有天然优势。
