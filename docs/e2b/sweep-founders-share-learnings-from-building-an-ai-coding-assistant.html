🔧 Sweep：Issue → Pull Request

Sweep 通过 embedding-based 代码搜索，将 GitHub Issue 直接转化为 Pull Request。

GitHub Issue 提交
→

→
Agent 规划方案
→
生成 Pull Request
→
用户评论迭代

核心特点

开源线性执行无需 IDE评论迭代

目标强开发者用户群，限制使用次数（5 次/月 GPT-4，其余 GPT-3.5），确保用户用于真实工作而非探索实验。

🐛 内部调试可视化工具

Sweep 团队用 2 小时构建了自己的 chat 可视化工具来调试 Agent。

调试挑战

Agent 偶尔从一开始就走错方向或使用错误格式；无行业共识的调试工具

Sweep 的方案

2 小时构建的 chat 可视化工具 + 线性 Agent 架构 = 简化问题定位，出问题就整体重启

"由于 Agent 以线性方式运行，通常很容易确定问题原因并将过程分解为步骤。"

用户报告问题
大约每天一次，用户联系 Sweep 团队（终端用户无法访问可视化工具）
获取用户许可
征得用户许可查看日志后进行调试
可视化对话历史
通过内部工具查看 Agent 与 LLM 的完整对话记录
修复并重新投递
修复问题后点击"redeliver"重新运行

👥 用户体验策略

服务器中心化架构 + 限制使用次数 = 确保用户将 Agent 用于有意义的工作。

限制使用策略

5 次/月 GPT-4，其余 GPT-3.5。发现早期用户多为技术探索而非真实工作，限流后使用质量大幅提升。

实际工作导向

"我们希望用户将 Agent 用于有意义的工作，而不是玩测试仓库或实验。"

未来方向

深入研究传统代码索引方式，目标是在代码理解和 Agent 理解两方面都变得精通。

💡 核心洞察

从 Sweep 的 YC 创业经验中提取的关键认知。

线性架构 = 简化调试

线性 Agent 无需在中间停止，出错重启全流程是最务实的方式

2 小时内建工具

简单的内部可视化工具比复杂的 Agent 调试框架更实用

限流提升价值

限制使用次数迫使用户认真使用，反而提高了产品的感知价值
