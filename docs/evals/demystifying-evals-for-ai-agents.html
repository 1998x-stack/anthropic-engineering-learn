📋 什么是 Eval

Eval（Evaluation）是对 AI 系统的测试：给 AI 一个输入，然后对输出应用评分逻辑来衡量成功与否。

单轮 Eval vs 多轮 Agent Eval

🔄 单轮 Eval

输入 Prompt
→
模型响应
→
评分器检查

🤖 多轮 Agent Eval

任务 + 工具
→
Agent Loop
(多轮工具调用)
→
单元测试
验证结果

⚡ Agent Eval 的独特挑战

Agent 使用工具、跨多轮修改环境状态、根据中间结果自适应——这意味着错误会传播和累积。前沿模型还可能找到超越静态 Eval 限制的创造性解决方案。

经典案例：Opus 4.5 在 τ²-bench 中关于预订航班的题目中发现了策略漏洞。按题目描述它"失败"了，但实际上想出了对用户更好的方案。

📖 Eval 核心术语

理解这些术语是构建有效 Eval 的基础。

术语定义示例
Task
任务		 一个单独的测试，有定义的输入和成功标准 "修复 auth bypass 漏洞"
Trial
试验		 对同一个任务的一次尝试（模型输出有随机性） 同一任务跑 10 次 = 10 trials
Grader
评分器		 对 Agent 表现的某个方面进行评分的逻辑 单元测试、LLM 评分、人工评分
Transcript
轨迹		 一次 Trial 的完整记录：输出、工具调用、推理、中间结果 Anthropic API 中的完整 messages 数组
Outcome
结果		 Trial 结束时环境中的最终状态 航班是否真的在数据库中存在（而非 Agent 是否说"已预订"）
Eval Harness
评测框架		 端到端运行 Eval 的基础设施 提供指令和工具、并发运行、记录、评分、聚合结果
Agent Harness
Agent 脚手架		 让模型作为 Agent 运行的系统 Claude Code、Agent SDK
Evaluation Suite
评测套件		 一组测量特定能力或行为的任务集合 客服 Eval 套件：退款、取消、升级

🎯 为什么要做 Eval

团队在没有 Eval 的情况下会陷入被动循环——修复一个问题，制造另一个问题，无法区分真正的回归和噪声。

❌ 没有 Eval 的团队

• 只在生产环境中发现问题
• 调试是被动的：等投诉 → 手动复现 → 修复 → 祈祷没引入新问题
• 无法区分真实回归和噪声
• "Agent 感觉变差了"但无法验证
• 新模型升级需要数周测试

✅ 有 Eval 的团队

• 问题在影响用户之前就可见
• 每次提交自动测试数百个场景
• 用指标代替猜测
• 新模型几天内就能升级
• 免费获得基线和回归测试（延迟、token 用量、成本）

📈 Eval 的价值随时间复利增长

早期：Eval 迫使产品团队明确 Agent 的成功标准。后期：Eval 维持一致的质量基准。一旦 Eval 存在，延迟、token 用量、每次任务成本、错误率都可以在静态任务库上追踪。

案例：Descript 的 Agent 帮助编辑视频，他们围绕三个维度构建 Eval：不破坏东西、做我要求的事、做得好。从人工评分 → LLM 评分 + 定期人工校准 → 现在定期运行两个独立套件（质量基准 + 回归测试）。

🔧 三种评分器

Agent Eval 通常组合三种评分器：基于代码的、基于模型的、人工的。每个评分器评估 Transcript 或 Outcome 的某一部分。

💻 代码评分器 推荐首选

✅ 快速 / 便宜 / 客观 / 可复现 / 易调试

❌ 对有效但非预期的变化脆弱 / 缺乏细微差别

方法：字符串匹配、二进制测试、静态分析、结果验证、工具调用验证、Transcript 分析

🤖 模型评分器 灵活补充

✅ 灵活 / 可扩展 / 捕捉细微差别 / 处理开放任务

❌ 非确定性 / 更贵 / 需要与人工评分校准

方法：基于 Rubric 评分、自然语言断言、成对比较、参考基准、多法官共识

👤 人工评分器 黄金标准

✅ 黄金标准质量 / 匹配专家判断 / 校准模型评分器

❌ 昂贵 / 慢 / 需要大规模人类专家

方法：SME 评审、众包判断、抽样检查、A/B 测试、标注者间一致性

⚖️ 评分组合策略

对于每个任务，评分可以是：

  • 加权：组合评分器分数必须达到阈值
  • 二元：所有评分器都必须通过
  • 混合：关键指标必须通过，其他可以加权

⚖️ 能力评测 vs 回归评测

两种不同类型的 Eval 服务于不同的目的，需要并行维护。

🚀 能力/质量评测

"这个 Agent 能做好什么？"

• 从低通过率开始

• 针对 Agent struggling 的任务

• 给团队一个"爬坡目标"

• 随着能力提升，高通过率的任务"毕业"成为回归套件

🛡️ 回归评测

"Agent 还能处理以前能处理的所有任务吗？"

• 应该有接近 100% 通过率

• 防止倒退

• 分数下降 = 有东西坏了

• 持续运行以捕捉漂移

任务的生命周期

能力评测
(低通过率)
→
爬坡优化
(通过率上升)
→
"毕业"
加入回归套件
→
持续监控
(防止倒退)

从"我们能做到吗？" → "我们还能可靠地做到吗？"

🤖 四类 Agent 的评测方法

不同类型的 Agent 有不同的评测重点，但不需要从零发明。

💻 编码 Agent

编写、测试、调试代码，导航代码库并运行命令。Eval 通常依赖明确定义的任务、稳定的测试环境、对生成代码的全面测试。

单元测试 SWE-bench Terminal-Bench 代码质量 LLM Rubric

关键洞察：SWE-bench 上 LLM 从 40% 提升到 >80%，仅用了一年。

💬 对话 Agent

在支持、销售、教练等场景与用户交互。需要维护状态、使用工具、在对话中采取行动。通常需要第二个 LLM 模拟用户。

τ²-Bench LLM Rubric 状态检查 模拟用户

多维度成功：工单是否解决（状态检查）+ 是否 <10 轮完成（Transcript 约束）+ 语气是否合适（LLM Rubric）

🔬 研究 Agent

收集、综合、分析信息，产生答案或报告。Eval 面临的独特挑战：专家可能对"全面"有不同意见、地面真相随参考内容不断变化。

BrowseComp 基础检查 覆盖检查 来源质量

策略：基础检查验证声明有来源支持 + 覆盖检查定义关键事实 + 来源质量确认权威性 + LLM 标记不支持的声明

🖥️ 电脑使用 Agent

通过屏幕截图、鼠标点击、键盘输入与软件交互（而非 API）。需要在真实或沙盒环境中运行，检查是否达到预期结果。

WebArena OSWorld DOM vs 截图 工具选择评估

关键权衡：DOM 交互快但 token 多，截图交互慢但 token 少。Claude for Chrome 的 Eval 检查 Agent 是否为每个场景选择了正确的工具。

🎲 非确定性：pass@k vs pass^k

Agent 行为在运行间有差异，同一个任务可能这次通过、下次失败。两个关键指标捕捉这种细微差别。

pass@k

P(至少 1 次成功 | k 次尝试)

"k 次尝试中至少有一次正确的概率"

随着 k 增加，pass@k 上升。更多"射门机会" = 更高至少 1 次成功的几率。

适用场景 编码（一次成功就行）、工具推荐

k=1
50%
k=3
87.5%
k=10
~100%

pass^k

P(全部 k 次都成功)

"k 次尝试全部成功的概率"

随着 k 增加，pass^k 下降。要求更多次一致性是更高的门槛。

适用场景 面向客户的 Agent（用户期望每次都可靠）

k=1
75%
k=3
42%
k=10
~6%

⚠️ 关键洞察

在 k=1 时，两个指标相同（都等于每次试验的成功率）。到 k=10 时，它们讲述相反的故事：pass@k 接近 100%，而 pass^k 接近 0%。选择哪个取决于产品需求。

🗺️ 从 0 到 1：Eval 路线图

Anthropic 的实战经验，从没有 Eval 到可信赖的 Eval 套件。

Step 0: 尽早开始
不需要数百个任务。20-50 个来自真实失败的任务就是很好的起点。早期开发中，每次变更都有明显影响，小样本量就够用。等待越久，Eval 越难构建。
Step 1: 从已有的手动测试开始
从开发期间运行的手动检查开始——每次发布前验证的行为、终端用户常见的任务。如果已上线，查看 bug 追踪器和支持队列。将用户报告的失败转换为测试用例。
Step 2: 编写明确的任务和参考方案
好任务的标准：两个领域专家会独立得出相同的通过/失败判定。每个任务都应该有参考方案（已知能通过所有评分器的输出），这证明任务是可解的且评分器配置正确。0% pass@100 通常是任务坏了，不是 Agent 不行。
Step 3: 构建平衡的问题集
测试应该发生行为的场景和不应该发生的场景。单向 Eval 导致单向优化。例如 Claude.ai 网页搜索 Eval：既测试模型应该搜索的查询（天气），也测试不应该搜索的查询（"谁创立了苹果？"）。
Step 4: 构建健壮的 Eval 框架 + 稳定环境
Eval 中的 Agent 应与生产中的 Agent 大致相同。每次 Trial 应从干净环境开始。不必要的共享状态（遗留文件、缓存数据）会导致相关故障。观察到 Claude 通过检查之前 Trial 的 git 历史获得了不公平优势。
Step 5: 精心设计评分器
尽可能选择确定性评分器，必要时使用 LLM 评分器增加灵活性，谨慎使用人工评分器验证。避免过于刚性：Agent 常找到 Eval 设计者没预料到的有效方法。分级评分：部分完成任务的 Agent 比立即失败的有意义得多。给 LLM 评分器"退出"机制（返回 "Unknown"）。
Step 6: 检查 Transcript
不读 Transcript 就不知道评分器是否工作正常。当任务失败时，Transcript 告诉你 Agent 是真的犯了错，还是你的评分器拒绝了一个有效方案。Anthropic 投入了查看 Eval Transcript 的工具，并定期花时间阅读它们。
Step 7: 监控评测饱和度
Eval 达到 100% 时只能追踪回归，无法提供改进信号。SWE-bench Verified 从今年 30% 开始，前沿模型现在接近饱和 >80%。随着 Eval 接近饱和，进度也会放缓。大的能力提升可能只表现为分数的小幅增长。

⚠️ 经典踩坑案例

CORE-Bench 事件：Opus 4.5 最初得分 42%，后发现多个问题：评分器刚性（期望 "96.124991..." 但 "96.12" 被拒绝）、模糊的任务规范、无法精确复现的随机任务。修复 bug 并使用约束更少的脚手架后，分数跃升至 95%。

METR 发现：时间范围 benchmark 中几个任务配置错误，要求 Agent 优化到 stated 分数阈值，但评分要求超过该阈值。这惩罚了遵循指令的 Claude，而忽略 stated 目标的模型反而得分更高。

🧩 多维度评测体系

自动化 Eval 只是理解 Agent 表现的众多方法之一。完整的方法组合像瑞士奶酪模型——没有一层能捕捉所有问题，但多层组合时，穿过一层的失败会被另一层拦截。

🔄 自动化 Eval

无需真实用户，编程运行测试
  • ✅ 更快迭代 / 完全可复现 / 无用户影响
  • ✅ 每次提交都能运行
  • ❌ 需要前期投入构建
  • ❌ 可能产生虚假信心

📊 生产监控

追踪实时系统中的指标和错误
  • ✅ 揭示真实用户行为
  • ✅ 捕捉合成 Eval 遗漏的问题
  • ❌ 被动：问题先影响用户
  • ❌ 信号可能有噪声

🔀 A/B 测试

用真实用户流量比较变体
  • ✅ 测量真实用户结果
  • ✅ 控制混杂因素
  • ❌ 慢：需要数天或数周
  • ❌ 只测试你部署的变更

👤 用户反馈

踩 / bug 报告等显式信号
  • ✅ 揭示未预料的问题
  • ✅ 来自真实用户的真实案例
  • ❌ 稀疏且自选的
  • ❌ 偏向严重问题

📖 Transcript 人工审查

人类阅读 Agent 对话
  • ✅ 建立对失败模式的直觉
  • ✅ 捕捉自动检查遗漏的细微问题
  • ❌ 耗时 / 不可扩展
  • ❌ 覆盖不一致

👥 系统性人类研究

训练有素的评分员结构化评分
  • ✅ 黄金标准质量判断
  • ✅ 处理主观/模糊任务
  • ❌ 昂贵且慢
  • ❌ 难以频繁运行

各方法在 Agent 生命周期中的位置

自动化 Eval

→

"The most effective teams combine these methods: automated evals for fast iteration, production monitoring for ground truth, and periodic human review for calibration."

🛠️ Eval 框架推荐

选择合适的框架取决于 Agent 类型、现有栈、需要离线评估还是生产可观测性。

框架特点适用场景
Harbor 容器化环境运行、云规模 Trial、标准化任务格式 运行 Terminal-Bench 2.0 等标准 benchmark + 自定义 Eval
Braintrust 离线评估 + 生产可观测性 + 实验追踪 开发迭代 + 生产质量监控都需要
LangSmith 追踪、离线/在线评估、数据集管理 LangChain 生态深度集成
Langfuse 开源自托管替代方案 有数据驻留要求的团队
Arize Phoenix/AX LLM 追踪、调试、离线/在线评估 大规模、优化和监控

💡 核心建议

框架只是载体，Eval 任务的质量才是关键。最佳实践是快速选择一个适合工作流的框架，然后把精力投入到 Eval 本身——迭代高质量的测试用例和评分器。

📌 结论

🎯 核心要点

  • 尽早开始，不要等待完美套件
  • 从看到的失败中提取真实任务
  • 定义明确、稳健的成功标准
  • 精心设计评分器并组合多种类型
  • 确保问题对模型来说足够难
  • 迭代 Eval 以提高信噪比
  • 阅读 Transcript！

"AI agent evaluation is still a nascent, fast-evolving field. As agents take on longer tasks, collaborate in multi-agent systems, and handle increasingly subjective work, we will need to adapt our techniques."
