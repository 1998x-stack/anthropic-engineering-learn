📸 什么是 Memory Snapshot

冻结整个 Linux 容器的状态——文件系统变更、进程树、内存映射——然后瞬间恢复

Modal Memory Snapshot 是一组文件，代表了 Linux 容器在即将接受请求前的完整状态。包括文件系统变更和整个进程树——每个进程的内存映射、文件描述符表、寄存器、环境变量、PID 等等。

🛡️ gVisor 的角色

Modal 使用 gVisor (runsc) 而非 runc——安全性与可定制性的双重优势

runc (标准容器)

容器直接运行在宿主内核上，通过 /proc VFS 暴露进程状态

gVisor runsc (Modal)

实现用户空间内核，kernel.go 包含 C/R 代码，18+ 系统组件支持 save_restore.go

⚡ 性能：为什么更快

将 26,000 个 syscalls 变成（大约）一次文件加载

Python Import 的问题

Python 的模块导入系统基于文件系统，执行数千个慢速、顺序的文件操作。import torch 执行 26,000 个 syscalls！再经过 OverlayFS + FUSE 层的间接寻址，开销巨大。

📄 Pages 文件加载

大部分性能取决于 Pages 文件（100MiB-10GiB）的加载速度——80/20 法则

gVisor 不需要等待读取整个 state 文件就可以让恢复的容器继续执行。它可以在后台读取页面，优先处理恢复进程阻塞等待的页面。FUSE 文件系统的激进预加载确保了最小的 page fault 延迟。

🔄 Snapshot 生命周期

按需创建、多次快照、匹配特定 Worker 硬件

  • 按需创建：仅在调度器找不到可用快照时才创建
  • 硬件匹配：快照需与 Worker 的 CPU 特性集、NVIDIA 驱动版本、容器运行时版本兼容
  • 自动管理：Modal 控制整个快照生命周期，确保跨动态 Worker 集群的一致恢复

🛠️ 使用方法

一行参数开启快照加速

@app.function(enable_memory_snapshot=True) def f(x): return model.predict(x) # GPU 状态需要特殊处理 @app.cls(gpu="A10G", enable_memory_snapshot=True) class Inference: @modal.enter(snap=True) # CPU RAM 阶段拍快照 def load_model(self): self.model = load_model_to_cpu() @modal.enter(snap=False) # 恢复后移至 GPU def move_to_gpu(self): self.model = self.model.to("cuda")

⚖️ 权衡与挑战

冻结容器并序列化到磁盘——有力但需要与"疯狂"共处

  • 程序需要理解它会被暂停不定时间并在不同机器上恢复
  • 快照前建立的状态会被反复重用——熵的假设可能被违反
  • 网络连接和 GPU 状态无法被快照，需要额外处理
  • Modal client 已做了大量兼容性工作，失败时自动回退到标准启动
