📡 为什么选择 WebRTC

WebRTC 将低延迟音视频传输的核心难题标准化了——连接建立、NAT 穿透、加密传输、编解码协商、质量控制和客户端回声消除——让 OpenAI 专注于将实时媒体连接到模型。

WebRTC 协议栈 — 标准化的难题

ICE
连接建立 + NAT 穿透（Interactive Connectivity Establishment）
DTLS
数据报传输层安全（Datagram Transport Layer Security）
SRTP
安全实时传输协议（Secure Real-time Transport Protocol）
Codec
编解码协商 — 压缩和解码音频/视频的 coder-decoder 选择
RTCP
实时传输控制协议 — 质量反馈和自适应调整

🔑 对 AI 最重要的特性：连续音频流

语音 agent 可以在用户还在说话时就开始转录、推理、调用工具或生成语音——而不是等待完整上传。这是"对话式"系统与"按键通话"系统的本质区别。

📐 Transceiver 模型

WebRTC edge service 终结客户端连接，然后将媒体和事件转换为更简单的内部协议——推理、转录、语音生成、工具调用和编排各自独立。

🎯 Session 所有权集中

Transceiver 是唯一拥有 WebRTC 会话状态的服务——ICE 检查、DTLS 握手、SRTP 密钥、会话生命周期。后端服务像普通服务一样扩缩。

🧩 核心部署难题：WebRTC vs Kubernetes

传统 one-port-per-session WebRTC 模型与 Kubernetes 的弹性伸缩特性天然冲突——大规模 UDP 端口范围难以暴露、保护和维持。

🔌

端口爆炸

高并发 = 上万 UDP 端口。Cloud LB 和 K8s Service 不是为此设计的。

🔒

安全风险

大范围 UDP 端口扩大攻击面，网络策略难审计。

📏

弹性缩放困难

Pod 频繁增删重调，每个 Pod 预留大端口范围使弹性变脆弱。

第二个难题：有状态协议的 Session 保持

即使解决了端口问题（单端口 + 应用层解复用），ICE 和 DTLS 是有状态协议。创建 session 的进程必须持续接收该 session 的包——否则握手失败或媒体中断。

目标：向公网暴露小而固定的 UDP 表面，同时将每个包路由到拥有对应 WebRTC session 的 transceiver。

🏗️ Relay + Transceiver 分层架构

核心思路：将包路由与协议终结分离。Relay 是轻量 UDP 转发层（小公网足迹），Transceiver 是有状态的 WebRTC 端点。

🔄 Relay 的职责

• 不解密媒体
• 不运行 ICE 状态机
• 不参与编解码协商
• 只读取足够的 packet metadata 选择目标，然后转发

🧠 Transceiver 的职责

• 完成 ICE/DTLS/SRTP 握手
• 拥有所有 WebRTC 协议状态
• 管理 session 生命周期
• 从客户端视角，WebRTC session 完全标准

🗝️ 基于 ICE 凭证的路由

利用 WebRTC 协议内置的 ICE ufrag（username fragment）作为路由钩子——无需外部查找服务就能完成首包路由。

1. Signaling 阶段
Transceiver 分配 session 状态，在 SDP answer 中返回共享的 Relay VIP + UDP 端口（如 203.0.113.10:3478）。生成的 server-side ufrag 编码了路由元数据。
2. 首包到达 Relay
客户端发送 STUN binding request（ICE 连通性验证）。Relay 解析 STUN 头中的 server ufrag，解码路由提示。
3. 转发到 Transceiver
Relay 将包转发到拥有该 session 的 Transceiver。Transceiver 监听共享 UDP socket（一个 OS 端点绑定内部 IP:Port，不是每 session 一个 socket）。
4. Session 建立完成
Relay 创建 client source IP:Port → Transceiver 的 session 映射。后续 DTLS、RTP、RTCP 包在 session 内流动，无需重新解码 ufrag。

"Encoding routing metadata into a protocol-native field gave us deterministic first-packet routing, a small public UDP footprint, and enough flexibility to place ingress close to users around the world."

🌐 Global Relay 与 Geo-steered Signaling

地理分布的 Relay 入口点缩短了客户端到 OpenAI 的第一跳——用户的包在附近入网，而非穿越公网到远端。

全球路由架构

🌏
Geo Steering
Cloudflare 地理和近邻路由，Signaling HTTP/WS 到达最近的 Transceiver Cluster
📡
Global Relay
SDP Answer 中提供最近的 Relay 地址，ufrag 编码目标 cluster 和 transceiver
🎯
Session Anchoring
Signaling + Media 都走近端入口，session 锚定到一个 Transceiver

效果

Geo-steered signaling 和 Global Relay 共同将 setup 和 media 放在近端路径上。这直接缩短了：

  • Signaling 往返时间
  • 首次 ICE 连通性检查延迟
  • 用户从连接到开口说话的等待时间

更低的延迟、更少的 jitter、更少的可避免 loss bursts。

⚡ Relay 实现与性能优化

用 Go 编写，刻意保持实现窄而精——运行在 userspace，无需 kernel-bypass 框架。

🚫 无协议终结

只解析 STUN headers/ufrag；后续 DTLS/RTP/RTCP 使用缓存状态，包保持opaque。

💨 临时状态

维护小型、短超时的内存 map（client address → transceiver destination）。重启只造成短暂流量丢失。

📏 水平扩展

多个 Relay 实例在负载均衡器后并行运行。状态不是硬 WebRTC 状态，恢复快速。

关键性能优化

SO_REUSEPORT
多 worker 绑同端口，内核分发包
runtime.LockOSThread
goroutine 固定 OS 线程，CPU 缓存局部性
Pre-allocated Buffers
避免 GC 压力，最小化分配
Minimal Copying
低解析开销，减少上下文切换

💡 设计哲学

先为常见场景优化，再考虑 kernel bypass。一个窄且精的 Go 实现配合 SO_REUSEPORT、线程固定和低分配解析，对 OpenAI 的 workload 已经足够。

🎯 成果与核心经验

在 Kubernetes 中运行 WebRTC 媒体无需暴露上千 UDP 端口——更小更固定的 UDP 表面更易安全和负载均衡。

经验详细说明
在边缘保留协议语义 客户端仍然说标准 WebRTC，保持浏览器和移动端互操作性不变
硬状态集中管理 Transceiver 拥有 ICE/DTLS/SRTP/session lifecycle；Relay 只转发包
利用已有信息路由 ICE ufrag 提供首包路由钩子，无需热路径查找依赖
SFU-less 是正确默认 大多数 session 是 point-to-point、延迟敏感的；推理服务不需要像 WebRTC peer 一样运作

"Real-time voice AI only works when infrastructure makes latency feel invisible. For us, that meant changing the shape of our WebRTC deployment without changing what clients expect from WebRTC itself."

更广泛的教训

添加复杂性的最佳位置是在一个薄路由层中——而非每个后端服务或自定义客户端行为。将路由元数据编码到协议原生字段中，获得了确定性首包路由、小公网 UDP 足迹，以及足够的灵活性将入口部署在全球用户附近。
