📂 从空仓库开始

2025 年 8 月底，OpenAI 团队向一个空的 Git 仓库提交了第一个 commit。五个月后，这个仓库包含了约一百万行代码，全部由 Codex agent 生成 -- 零行手写代码。这不是一个实验性 demo，而是一个真正交付给用户的产品。

💡 核心哲学：No Manually-Written Code

团队始终坚持一个核心原则：不允许手写代码。初始脚手架（仓库结构、CI 配置、格式化规则、包管理器、应用框架）全部由 Codex CLI + GPT-5 生成。甚至引导 agent 的 AGENTS.md 文件本身也是 Codex 写的。

这不是为了输出而输出 -- 产品已被数百名内部用户使用，包括每日活跃的内部 power user。

👥 重新定义工程师角色

当工程师不再写代码时，他们做什么？答案是：设计环境、指定意图、构建反馈循环。人类掌舵，Agent 执行。真正稀缺的资源是人类的时间和注意力。

❌ 传统工程师角色

  • 手写应用代码和测试
  • 手动调试和修复
  • 人工 code review
  • 手动部署和监控
  • 知识在脑海中、Slack 中、Google Docs 中

✅ Agent-First 工程师角色

  • 设计环境和抽象层
  • 编写 prompt 描述任务意图
  • 构建 feedback loop 给 agent
  • 诊断「什么能力缺失？」
  • 知识全部进入仓库（versioned artifacts）

"当某件事失败时，解决方案几乎不是'更努力地尝试'。因为让工作推进的唯一途径是让 Codex 去做，人类工程师总是会问：'缺少什么能力？如何让它对 agent 来说既可读又可执行？'"

🔄 Ralph Wiggum Loop

为了将 PR 推进到完成，团队使用了 Ralph Wiggum Loop 模式：指示 Codex 在本地自审、请求其他 agent review（本地和云端）、响应所有反馈、循环迭代直到所有 agent reviewer 满意。人类可以 review PR，但不是必须的。

👁 提升应用可读性

随着代码吞吐量增加，瓶颈变成了人类的 QA 能力。解决方案不是增加人手，而是让应用本身对 Codex 更加可读 -- UI、日志、指标都需要能被 agent 直接理解和操作。

🌐

Chrome DevTools Protocol

将 CDP 接入 agent runtime，创建了操作 DOM snapshot、截图、页面导航的 skills。Codex 可以直接复现 bug、验证修复、推理 UI 行为。

📊

Observability Stack

日志/指标/traces 通过本地可观测性栈暴露给 Codex。每个 worktree 一个隔离实例，任务完成后自动销毁。Agent 可以用 LogQL 和 PromQL 查询。

🔨

Per-Worktree Boot

应用可以按 git worktree 启动，每个变更一个独立实例。Codex 可以启动、驱动、验证应用，完全隔离互不干扰。

⏳ 长时间自主运行

得益于这些能力，团队经常看到 单次 Codex 运行持续工作 6 小时以上（通常在工程师睡觉的时候）。类似 "确保服务启动在 800ms 内完成" 或 "这四个关键用户旅程中没有 span 超过 2 秒" 这样的 prompt 变得可执行。

📚 知识库即系统记录

Context 管理是让 agent 在大规模复杂任务上有效的最大挑战之一。团队的核心经验：给 Codex 一张地图，而不是一本 1000 页的说明书。

❌ "One Big AGENTS.md" 失败了

  • Context 是稀缺资源 -- 巨型指令文件挤占了任务、代码和相关文档的空间
  • 过多引导 = 无引导 -- 当一切都"重要"时，什么都不重要
  • 即刻腐烂 -- 单体手册变成过时规则的坟场
  • 难以验证 -- 无法做机械化的覆盖率、新鲜度、所有权检查

✅ AGENTS.md 作为目录

  • ~100 行精简入口 -- 指向更深层的真实来源
  • 渐进式披露 -- agent 从稳定入口开始，按需深入
  • 机械化执行 -- linter + CI 验证知识库的更新性和交叉引用
  • 自动园丁 -- 定期 agent 扫描过时文档并提交修复 PR

"从 agent 的角度来看，任何它在运行 context 中无法访问的东西，实际上就是不存在的。Google Docs、聊天线程、人脑中的知识对系统来说都是不可访问的。那个在 Slack 中对齐了架构模式的讨论？如果 agent 发现不了，它就像对一个三个月后加入的新人一样不可见。"

🏟 架构与品味的执行

Agent 在具有严格边界和可预测结构的环境中最为有效。文档本身不能保持代码库一致性 -- 需要通过执行不变量（invariants），而非微管理实现来让 agent 快速交付而不破坏基础。

🔎 Custom Linters

Codex 自己生成的自定义 linter，验证依赖方向、文件大小限制、命名规范。错误消息专门为 agent 设计，包含修复指令。

📝 Structural Tests

结构化测试验证包分层和依赖边。强制 structured logging、schema 和 type 命名规范、平台可靠性要求。

🎓 Taste Invariants

编码"品味"：偏好 parse, don't validate 原则 -- 在边界验证数据形状。不规定具体库（Codex 倾向 Zod，但未被指定）。

⚖️ "Boring" Technology 原则

团队倾向于依赖那些可以被 agent 完全内化和推理的技术。所谓 "boring" 的技术因其可组合性、API 稳定性、训练集中的充分表示而更容易被 agent 建模。

某些情况下，让 agent 重新实现功能子集比绕过公共库的不透明行为更便宜。例如，团队自己实现了 map-with-concurrency helper（而非用通用 p-limit），紧密集成 OpenTelemetry instrumentation，100% 测试覆盖。

"在人类优先的工作流中，这些规则可能显得过于迂腐或限制性。但对 agent 来说，它们成为了乘数：一旦编码，它们可以同时应用到所有地方。"

♻️ 自治与熵管理

全 agent 自主也带来了新问题：Codex 会复制仓库中已有的模式 -- 包括不够好的那些。随着时间推移，这不可避免地导致漂移。如何对抗熵增？

🤖 端到端自主能力

仓库最近跨越了一个重要阈值 -- Codex 可以端到端驱动一个新功能。给定一个 prompt，agent 可以完成以下全部步骤：

❌ 之前：手动清理 AI Slop

团队曾每周五（20% 的时间）手动清理 "AI slop"。不可持续 -- 投入太大、效果不一致。

✅ 之后：Agent-Driven Garbage Collection

将 "golden principles" 编码进仓库，定期后台 Codex 任务扫描偏差、更新质量评分、提交重构 PR。大多数 PR 一分钟内可审核并自动合并。

🧰 Golden Principles 示例

  • 共享工具包优于手写 helper -- 保持不变量集中化
  • 不做 YOLO 式数据探测 -- 必须在边界验证或使用 typed SDK，防止 agent 基于猜测的数据形状构建
  • 技术债如高息贷款 -- 持续小额偿还永远优于累积后一次性解决

人类品味捕获一次，然后在每一行代码上持续执行。每天发现并解决坏模式，而非让它们在代码库中扩散数周。

💡 关键经验总结

五个月的全 Agent 开发实验，产生了一系列关于工程纪律如何在 agent-first 世界中进化的深刻洞察。以下是最核心的经验。

🎯

纪律转移到脚手架

构建软件仍然需要纪律，但纪律更多体现在脚手架而非代码上。工具、抽象和反馈循环越来越重要。

🛠

修正成本低于等待成本

在 agent 吞吐量远超人类注意力的系统中，修正是廉价的，等待是昂贵的。最小化阻塞式合并门控。

📈

集中边界，局部自治

如同领导大型工程平台组织：集中执行边界、正确性和可重复性，在边界内允许团队或 agent 自由表达。

📚

仓库即唯一真相源

Agent 看不到的知识等于不存在。所有决策、架构、文化规范都必须以 versioned artifact 形式存在于仓库中。

🧠

失败是系统信号

Agent 挣扎时不是 "试更多次"，而是问 "缺少什么？" -- 缺工具、guardrail 还是文档？然后让 Codex 自己写修复。

🌱

持续园丁式维护

Agent 会复制坏模式。编码 golden principles + 定期自动化扫描清理。GC 优于手动除草。

🤖 Agent 生成的全部内容

当说"代码库由 Codex agent 生成"时，意味着一切都由 agent 生成：

💻 产品代码和测试
⚙️ CI 配置和发布工具
🔧 内部开发工具
📝 文档和设计历史
📊 评估 harness
💬 Review 评论和回复
📄 仓库管理脚本
📈 生产 dashboard 定义文件

"我们最困难的挑战现在集中在设计环境、反馈循环和控制系统上 -- 帮助 agent 实现我们的目标：大规模构建和维护复杂、可靠的软件。"
