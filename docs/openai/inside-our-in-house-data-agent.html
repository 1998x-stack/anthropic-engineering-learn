🔍 为什么需要定制工具

OpenAI 的数据平台服务超过 3,500 名内部用户，跨越工程、产品和研究团队，覆盖 600+ PB 数据和 70,000+ 数据集。在这个规模下，仅仅找到正确的表就可能是分析中最耗时的部分。

"我们有很多非常相似的表，我花大量时间试图弄清楚它们之间的区别以及应该用哪个。有些包含未登录用户，有些不包含。有些字段重叠；很难分辨什么是什么。"

❌ 传统分析工作流的痛点

  • 找到正确的表可能花费数小时
  • 180+ 行 SQL 语句 -- 难以确认 join 和 column 是否正确
  • Many-to-many join 错误默默失效
  • Filter pushdown 错误
  • 未处理的 NULL 值悄悄使结果无效
  • 分析师被迫调试 SQL 语义和查询性能

✅ Data Agent 的价值

  • 从提问到洞察仅需几分钟而非几天
  • 降低所有职能（不仅是数据团队）的分析门槛
  • 自动推理表关系和数据转换
  • 发现中间结果异常时自动调查和调整
  • 分析师聚焦于定义指标和验证假设
  • 跨 Engineering/DS/GTM/Finance/Research 使用

⚙️ Agent 工作原理

用户可以提出复杂的开放式问题，Agent 端到端处理分析 -- 从理解问题、探索数据、运行查询到综合发现。关键能力是闭环自学习：如果中间结果看起来不对，Agent 会调查原因、调整方法、重试。

🧠 闭环自学习推理

与遵循固定脚本不同，Agent 会评估自己的进展。如果中间结果看起来错了（例如因为错误的 join 或 filter 导致零行），它会：

  • 调查哪里出了问题
  • 调整方法并重试
  • 保持完整上下文，跨步骤携带学习成果

这个闭环过程将迭代从用户转移到 Agent 内部，实现更快的结果和比手动工作流更高质量的分析。

🎓 六层 Context 体系

高质量的答案依赖于丰富、准确的 context。没有 context，即使强大的模型也会产生错误结果 -- 例如严重误估用户数量或误解内部术语。Agent 围绕六个 context 层构建，将其推理锚定在 OpenAI 的数据和机构知识中。

Layer 6: Runtime Context
实时查询数据仓库 + 连接 Airflow/Spark 等平台系统
Layer 5: Organizational Memory
Slack/Google Docs/Notion -- 发布信息、事故记录、指标定义
Layer 4: Code-Level Enrichment
通过 Codex 派生表的代码级定义 -- 唯一值、更新频率、数据范围
Layer 3: Curated Descriptions
领域专家编写的表/列描述 -- 意图、语义、业务含义、已知注意事项
Layer 2: Query Inference
历史查询模式 -- 表如何被查询、哪些表通常被 join
Layer 1: Metadata Grounding
Schema metadata (列名/数据类型) + 表血缘 (上下游关系)

🚀 Layer 4: Code-Level Enrichment（最关键的差异化层）

这是让 Agent 能够区分"看起来相似但在关键方面不同"的表的核心层。通过派生表的代码级定义，Agent 可以理解：

  • 数据中实际存储了什么以及如何从分析事件中派生
  • 值的唯一性、表数据的更新频率
  • 数据范围（例如表是否排除某些字段、粒度级别）
  • 表在 SQL 之外如何被使用（Spark、Python 等）

例如，它可以判断一个表是否只包含 ChatGPT 第一方流量。这些 context 自动刷新，无需手动维护。

🧠 Layer 5: Organizational Memory

Agent 可以访问 Slack、Google Docs、Notion，捕获关键公司 context：

📣 产品发布信息
⚠️ 可靠性事故记录
📄 内部代号和工具
📈 指标规范定义和计算逻辑

文档被嵌入、存储（含 metadata 和权限）。检索服务在运行时处理访问控制和缓存。Agent 收到纠正或发现数据问题的细微差别时，可以保存记忆供下次使用。记忆分为 global 和 personal 两个级别。

🤝 像队友一样协作

大多数问题不是一次就能回答对的。到达正确结果通常需要来回精炼和方向调整。Agent 被设计成你可以一起推理的队友 -- 对话式、始终在线，既能处理快速回答也能进行迭代探索。

💬 跨轮 Context 保持

用户可以提出后续问题、调整意图或改变方向，无需重述所有内容。完整 context 在对话轮次间传递。

🔄 中途重定向

如果 Agent 走错路，用户可以中途打断并重新引导 -- 就像和一个会倾听的人类协作者一样。

📝 主动澄清

当指令不清楚时，Agent 主动提问。如果没有回复，它应用合理默认值继续推进（例如默认最近 7 天或 30 天）。

🎯 精确查询模式

用户明确知道要什么时效果最好。

"Tell me about this table"

🔎 探索发现模式

用户在探索中发现问题时同样强大。

"I'm seeing a dip here, can we break this down by customer type and timeframe?"

🔄 Workflows：可复用的分析模板

上线后，团队发现用户经常对常规重复工作运行相同的分析。为了加速，Agent 的 Workflows 功能将重复分析打包为可复用的指令集。

  • 每周业务报告
  • 表数据验证
  • 编码 context 和最佳实践一次，跨用户确保一致结果

📊 质量保障与 Evals

构建一个持续进化的 Agent 意味着质量可能像提升一样容易漂移。没有紧密的反馈循环，回归是不可避免且不可见的。系统化评估是在不破坏信任的前提下扩展能力的唯一途径。

🧠 智能评估 vs 简单字符串匹配

评估不依赖简单的字符串匹配。生成的 SQL 可以在语法上不同但仍然正确，结果集可能包含不影响答案的额外列。评估系统同时比较 SQL 和结果数据，并将这些信号输入 OpenAI Evals Grader，产生最终评分和解释，捕捉正确性和可接受的变异。

🔧 开发阶段

Evals 作为单元测试在开发过程中持续运行，识别回归问题。团队可以自信地迭代能力扩展。

🐦 生产阶段

Evals 作为 canary（金丝雀）在生产环境运行，提前捕获问题。允许团队在能力扩展的同时保持信任。

🔒 安全与权限

Agent 直接接入 OpenAI 现有的安全和访问控制模型。它纯粹作为接口层运作，继承并执行管理 OpenAI 数据的相同权限和防护栏。

🔓 Pass-Through 访问

所有访问都是严格的 pass-through -- 用户只能查询他们已有权限访问的表。缺失权限时，Agent 标记或 fallback 到授权数据集。

👁 推理透明

暴露推理过程：总结假设和执行步骤。执行查询时直接链接到底层结果，用户可以检查原始数据。

✅ 可验证每一步

和任何系统一样可能出错。但设计为透明 -- 用户可以验证分析的每一个步骤和数据来源。

💡 经验教训

从零构建 Agent 暴露了关于 agent 行为、挣扎之处以及大规模可靠性的实用经验。以下是最关键的三个教训。

🛠

工具重叠 = Agent 困惑

早期暴露完整工具集后，功能重叠让 agent 困惑。冗余工具对人类来说还好，但对 agent 造成歧义。解决方案：限制和合并工具调用。

📜

过度指令 = 性能下降

高度规范性的 prompting 反而降低了结果质量。问题共享一般分析形状，但细节变化大，死板指令常把 agent 推向错误路径。高层级指导 + 让 GPT-5 推理选择执行路径效果更好。

💻

真正的意义在代码中

Schema 和查询历史描述表的形状和用法，但真正的含义在生成表的代码中。Pipeline 逻辑捕获了永远不会出现在 SQL 或 metadata 中的假设、新鲜度保证和业务意图。
