🚧 交互式 Coding Agent 的天花板

OpenAI 团队做了一个激进的决定：项目仓库中不允许任何人工编写的代码，所有代码必须由 Codex 生成。这一模式成功了，但很快碰到了新的瓶颈：人类注意力。

⚡ Context Switching 问题

每位工程师同时管理 3-5 个 Codex 会话已是极限。超过这个数量，生产力急剧下降：忘记哪个会话在做什么、在终端间跳转催促 Agent、调试中途卡住的长任务。Agent 很快，但人类注意力成了系统瓶颈。

"We had effectively built a team of extremely capable junior engineers, then assigned our human engineers to micromanaging them. That wasn't going to scale."

💡 思维转变：从会话管理到任务驱动

团队意识到他们在优化错误的东西。真正的工作单元不是 Codex 会话或 PR，而是 Issue、Task、Ticket、Milestone 这些交付物。

❌ 以会话为中心

• 工程师管理多个 Codex 终端
• 手动分配任务给每个会话
• 实时监控和引导 Agent
• 人工合并和检查 PR
• 瓶颈 = 人类注意力

✅ 以任务为中心（Symphony）

• Issue Tracker 成为控制平面
• 每个 Open Task 自动获得 Agent
• Agent 持续运行，不需睡眠
• 人类只需审查结果
• 瓶颈 = 任务质量

⚙️ Symphony 的完整工作流程

Symphony 将 Issue Tracker 变成 Agent 编排器。它通过 DAG（有向无环图）管理任务依赖，Agent 只处理未被阻塞的任务，执行自然地以最优并行度展开。

任务状态流转

Open
→
In Progress
→
Review
→
Merging
→
Done

Agent 自动推进状态 → 人类在 Review 阶段介入 → CI 通过后自动 Merge

1. 分析与规划
Agent 可以先分析代码库、Slack 或 Notion，然后生成实施计划。团队审查计划后，Agent 自动生成任务树，定义任务间依赖关系。
2. DAG 并行执行
Agent 只启动未被阻塞的任务。例如 React 升级被标记为阻塞 Vite 迁移时，Agent 先完成 Vite 迁移，再启动 React 升级。执行自然以最优并行度展开。
3. 自主创建后续任务
实施或审查过程中，Agent 常发现超出当前范围的改进——性能问题、重构机会、更好的架构方案。它们会自动创建新 Issue，由人类评估和调度。
4. CI/CD 自动化
Symphony 监控 CI，在需要时 rebase、解决冲突、重试 flaky test，自动引导变更通过流水线。到 Merging 阶段时，团队有高度信心变更能顺利进入主分支。
5. 证据附加
完成的任务附带 proof-of-work 视频、截图和变更描述。产品经理和设计师可以直接查看功能在真实产品中的运行效果，无需检出代码。

📱 随时随地工作

因为编排器在 devbox 上运行、永不休眠，工程师可以从任何地方添加任务。一位团队成员在只有不稳定 WiFi 的小木屋中，通过手机上的 Linear 应用完成了三个重要变更。

🔬 探索性开发的范式转变

Symphony 最深刻的影响不是产出量的增加，而是团队思考工作方式的根本转变。当代码变更的人力成本趋近于零时，探索变得廉价。

💡 投机性任务

尝试一个想法、探索一次重构、测试一个假设，只保留有前景的结果。失败的成本趋近于零。

👥 扩大参与者

产品经理和设计师可以直接在 Symphony 中提交 Feature Request。不需要检出代码库或管理 Codex 会话，描述功能即可收到运行效果视频。

🎯 工程师聚焦

工程师不再在琐碎任务间 context-switch，可以一次专注一个困难问题——通常是最有趣和最需要专业判断的任务。

"When our engineers no longer spend time supervising Codex sessions, the economics of code changes completely. The perceived cost of each change drops because we're no longer investing human effort in driving the implementation itself."

⚠️ 挑战与经验教训

从交互式引导转向任务级分配意味着失去了实时纠偏的能力。有时 Agent 完全偏离目标——但这些失败揭示了系统的不足，推动了改进。

难题：失去实时控制

• Agent 可能完全偏离方向
• 无法中途纠正和引导
• 某些任务需要强判断力
• 模糊问题难以仅靠描述解决

应对：系统性增强

• 添加 guardrails 和 skills 而非手动修补
• 增加端到端测试能力
• 集成 Chrome DevTools 驱动应用
• 改进文档，明确"好"的标准

🔑 核心认知转变：目标 vs 状态机

早期把 Agent 当做状态机中的刚性节点——只要求实现任务。这种方式过于限制性。模型越来越聪明，能解决更大的问题。最终转向给 Agent 目标（Objectives）而非严格的状态转换，就像好的管理者分配目标给团队成员一样。

"The power of models comes from their ability to reason, so give them tools and context and let them cook."

🔧 扩展的能力

给予 Agent 更多工具——gh CLI、CI 日志读取 skills 等。现在可以要求 Codex 做更多：关闭旧 PR、生成完成与放弃工作的报告等超出最初实现范围的任务。

📋 WORKFLOW.md

开发工作流不再是隐含知识。所有流程步骤（创建分支、更新状态、附加视频等）都记录在 WORKFLOW.md 中。Symphony 确保 Agent 遵循与人类相同的流程。

🔄 用 Symphony 构建 Symphony

Symphony 本质上只是一个 SPEC.md 文件——问题的定义和解决方案的描述。它不是一个复杂的监督系统，而是给 Agent 高层级的方向指导。

V1：tmux + 轮询
第一个版本就是一个 Codex 会话在 tmux 中运行，轮询 Linear 并为新任务生成子 Agent。工作了，但不够可靠。
V2：集成到主仓库
嵌入到已经为 Agent 优化的项目仓库中，复用已有的 Agent Harness（skills + context）。Symphony 只是将所有部分连接起来。
内部传播
Demo 展示系统管理任务并附加 proof-of-work 视频后，反响热烈。Symphony 项目频道增长，组织内多个团队自发开始使用。
提取为独立 SPEC.md
移除内部仓库和 Linear MCP 的依赖，简化为核心方法。让 Codex 用 Elixir 一次性实现参考实现。
多语言验证
让 Codex 用 TypeScript、Go、Rust、Java、Python 等多种语言实现 Spec，用结果识别歧义和简化系统。每种语言都成功了。

🧪 为什么选 Elixir

当代码实质上是"免费的"时，可以按语言优势来选择。Elixir 有优秀的并发、进程监督原语，天然适合编排和监督并发进程。

并发原语 进程监督 容错设计

🖥️ Codex App Server

使用 Codex 的 headless 模式，通过 JSON-RPC API 程序化交互。比 CLI 或 tmux 更方便和可扩展。用 Dynamic Tool Calls 避免向子 Agent 暴露 Linear access token。

JSON-RPC Dynamic Tools 安全隔离

🔮 未来展望

Symphony 是一个有意最小化的编排层。它不会作为独立产品维护，而是作为参考实现——展示 Codex App Server 与工作流工具结合的力量。

📄 作为参考实现

就像开发者将 Agent 指向 Harness Engineering 博文来搭建仓库一样，OpenAI 希望你将 Agent 指向 Symphony 的 SPEC.md 和仓库来构建自己的版本。

🔄 瓶颈转移

随着 Coding Agent 推理和指令遵循能力提升，瓶颈将从编写代码转向管理 Agent 工作。实验这些系统的门槛已经非常低。

"The power comes from Codex and its app server. Symphony was a way to connect Codex to Linear, two things we already used, to solve the work management problem."

📌 总结

🎯 核心要点

  • 人类注意力是真正的瓶颈，不是 Agent 的能力
  • 将 Issue Tracker 变成控制平面，每个 Open Task 自动获得 Agent
  • Symphony 是 SPEC.md——问题定义而非复杂系统
  • DAG 依赖管理让任务以最优并行度执行
  • 给 Agent 目标而非刚性转换，释放模型推理能力
  • WORKFLOW.md 将隐含知识显式化
  • 失败是有用信息——推动系统性增强而非手动修补
  • PR 产出可达 500% 提升，但更深层的变化是思维方式
