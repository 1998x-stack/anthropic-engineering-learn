🔄 Agentic Loop 的延迟解剖

当你让 Codex 修复一个 Bug 时，它会扫描代码库、读取相关文件、编辑代码、运行测试。底层是数十次 Responses API 往返：确定下一步动作 → 在本地运行工具 → 将结果发回 API → 重复。

🔍 结构性问题

核心问题是结构性的：每个 Codex 请求都被视为独立的，在每次后续请求中重新处理对话状态和其他可复用上下文。即使大部分对话内容没有变化，仍然需要为完整历史付出代价。随着对话变长，重复处理的成本越来越高。

🔧 前期优化：单请求延迟压缩

2025 年 11 月启动了 Responses API 的性能冲刺，针对单次请求的关键路径延迟进行了多项优化。

💾 Token 缓存

在内存中缓存已渲染的 Token 和模型配置，跳过昂贵的 Tokenization 和网络调用，对多轮对话效果显著。

🔗 减少网络跳数

消除对中间服务的调用（如图像处理），直接调用推理服务，减少每次请求的网络往返延迟。

🛡️ 安全栈提速

改进安全分类器，使某些检查更快地标记对话，减少安全检查在关键路径上的开销。

⚠️ 瓶颈未消除

TTFT（Time to First Token）改善了约 45%，API 响应感觉更快了。但对于 GPT-5.3-Codex-Spark 的速度来说仍然不够快——API 开销相对于模型速度仍然太大。用户在 GPU 运行前，就已经在等 CPU 处理 API 请求了。

🌐 WebSocket 持久连接设计

核心思路：保持持久连接并缓存状态，而不是每次都建立新的 HTTP 连接并发送完整对话历史。只发送新信息，在连接生命周期内复用可重用状态。

❌ HTTP 模式（每次请求独立）

• 每次建立新连接
• 发送完整对话历史
• 重新 Tokenize 全部内容
• 重新运行所有安全检查
• 重新解析模型配置
• 延迟随对话长度线性增长

✅ WebSocket 模式（持久连接）

• 保持长连接
• 只发送新增内容
• 复用缓存的 Token
• 增量安全检查
• 缓存模型路由结果
• 延迟接近恒定

HTTP 模式：N 次完整往返

→
response.create（完整历史）
←
模型回复 + tool_call
→
response.create（完整历史 + tool_result）
←
模型回复 + tool_call
→
response.create（更长的完整历史...）
每次都重复处理完整历史

WebSocket 模式：增量传输

→
response.create（首次完整）
←
response.done + tool_call
→
response.create + previous_response_id（仅新内容）
←
response.done + tool_call
→
response.create + previous_response_id（仅新内容）
缓存复用，增量处理

🤔 为什么选择 WebSocket 而非 gRPC

团队考虑了 WebSocket 和 gRPC 双向流。最终选择 WebSocket 的原因：作为简单的消息传输协议，开发者不需要改变 Responses API 的输入输出格式。开发者友好，且适配现有架构，几乎没有破坏性。

🧪 从原型到产品的演进

第一个 WebSocket 原型由 Codex 团队的一位工程师在一夜之间完成——他让 Codex Agent 构建了这个原型。结果颠覆了团队对 API 延迟极限的认知。

原型：长连接 + 异步阻塞
将整个 Agent Rollout 建模为单个长运行 Response。使用 asyncio 在采样循环中异步阻塞等待 tool call 结果。Tool Call 发回 response.done 事件，客户端用 response.append 回传结果。
类比：本地工具 = 托管工具
将本地 tool call 视为 hosted tool call。就像模型调用 web search 时推理循环阻塞、调用搜索服务、将结果放入上下文一样——只是通过 WebSocket 发给客户端而非调用远程服务。
效果惊人但 API 不够友好
消除了 Agent Rollout 中的重复 API 工作——预推理工作只做一次，暂停等待工具执行，后推理工作在最后只做一次。但代价是API 接口变得不熟悉，需要开发者重写集成逻辑。
最终方案：熟悉的 API + 增量缓存
回归到熟悉的 response.create 接口，通过 previous_response_id 继续上下文。服务器在连接范围内维护内存缓存。

"The first WebSocket prototype changed what we thought was possible for Responses API latency. An engineer on the Codex team pulled together a prototype by running a Codex agent overnight."

📦 增量处理的四大优化

WebSocket 连接上，服务器维护一个连接级别的内存缓存。使用 previous_response_id 时，从缓存获取状态而非重新构建。

🛡️ 增量安全检查

安全分类器和请求验证器只处理新输入，不再每次都检查完整历史。对长对话的效果尤其显著。

💾 Token 追加缓存

在内存中维护已渲染 Token 的缓存，新轮次只追加新 Token，跳过不必要的 Tokenization。

🔀 复用模型路由

成功的模型解析和路由逻辑在跨请求间直接复用，不需要每次重新解析。

⏱️ 计费与后续请求重叠

非阻塞的后推理工作（如计费）与下一个请求并行执行，不占用关键路径。

缓存状态说明复用效果
Previous Response Object 上一次响应的完整对象 跳过重建对话状态
Prior Input/Output Items 历史输入和输出项 增量添加新项
Tool Definitions 工具定义和命名空间 避免重复解析
Rendered Tokens 已 Tokenize 的采样 artifact 追加而非重新 Tokenize
Model Route 模型解析和路由结果 直接复用成功路由

🔮 更深层的启示

WebSocket 模式不仅降低了延迟，更支撑了一个核心趋势：随着模型推理越来越快，围绕推理的服务和系统也需要同步加速，才能将推理速度的提升真正传递给用户。API 基础设施的优化与模型优化同等重要。

📌 总结

🎯 核心要点

  • 推理变快后，API 服务层成为 Agentic 工作流的新瓶颈
  • 单请求优化（缓存、减少跳数、安全栈加速）带来 45% TTFT 改善，但不够
  • 核心问题是结构性的：每次请求都重新处理完整历史
  • WebSocket 持久连接 + previous_response_id 实现增量处理
  • 保持 API 接口向后兼容：开发者只需更换传输协议
  • 生产效果：端到端 40% 加速，GPT-5.3 达到 1,000-4,000 TPS
  • Vercel、Cline、Cursor 等生态伙伴集成后均获得 30-40% 提速
  • 从想法到生产仅数周——API 与 Codex 团队紧密协作
