📚 App Server 起源

Codex 存在于多个不同的产品表面：Web App、CLI、IDE 扩展、macOS 桌面应用。它们底层都由同一个 Codex Harness 驱动 -- agent loop 和逻辑的核心引擎。App Server 是连接它们的关键纽带：一个客户端友好的、双向的 JSON-RPC API。

📅 App Server 演进历程

Codex CLI (TUI)
起点
Codex 最初是一个 TUI（终端用户界面），通过终端访问。Agent loop 和 UI 在同一进程中直接交互。
VS Code Extension 需求
复用 harness
构建 VS Code 扩展时，需要在不重新实现 agent loop 的情况下从 IDE UI 驱动相同的 harness -- 支持探索 workspace、流式进度、diff 发射等丰富交互。
MCP Server 尝试
不够契合
尝试将 Codex 暴露为 MCP server，但在 VS Code 语义下维护 MCP 语义证明困难。
JSON-RPC 协议诞生
App Server v1
引入一个镜像 TUI loop 的 JSON-RPC 协议。最初并未预期其他客户端会依赖它。
平台化演进
稳定 API
JetBrains、Xcode、Desktop App 等需求推动设计为稳定平台表面 -- 易集成、向后兼容、可独立演进。

⚙️ Codex Harness 内部结构

Codex Harness 不仅是核心 agent loop。完整的 agent 体验包括线程生命周期管理、配置与认证、工具执行与扩展三大部分。所有这些逻辑都存在于代码库中被称为 "Codex Core" 的部分。

🔄 Thread 生命周期

Thread 是 Codex 会话。支持创建、恢复、fork、归档。持久化事件历史，客户端可重连并渲染一致的时间线。

🔑 配置与认证

加载配置、管理默认值，运行认证流程（如 "Sign in with ChatGPT"），包括凭据状态管理。

🔧 工具执行与扩展

在 sandbox 中执行 shell/file 工具，连接 MCP servers 和 skills，在一致的策略模型下参与 agent loop。

App Server 进程架构（4 大组件）

Stdio Reader
读取客户端 JSON-RPC 请求
Codex Message Processor
翻译客户端请求 ↔ Core 操作
Thread Manager
为每个 thread 启动一个 core session
Core Threads
每个 thread 的 agent loop 实例

Stdio Reader + Message Processor = 翻译层，将 JSON-RPC 转换为 Core 操作，将 Core 内部事件流转换为稳定的 UI-ready 通知

"一个客户端请求可以产生多个事件更新，这些详细事件是我们在 App Server 之上构建丰富 UI 的基础。JSON-RPC 协议是完全双向的 -- 服务器也可以在 agent 需要输入（如审批）时发起请求，并暂停 turn 直到客户端响应。"

🧰 三大对话原语

为 agent loop 设计 API 很棘手 -- 用户/agent 交互不是简单的 request/response。一个用户请求可以展开为结构化的动作序列。团队设计了三个核心原语，具有清晰的边界和生命周期。

🔬

Item（原子单元）

Codex 中输入/输出的原子单元。有类型（用户消息、agent 消息、工具执行、审批请求、diff）和显式生命周期。

🔄

Turn（工作单元）

由用户输入发起的一个 agent 工作单元。从客户端提交输入开始，到 agent 完成该输入的所有输出时结束。包含一系列 items。

📄

Thread（持久容器）

用户和 agent 之间的持久会话容器。包含多个 turns。支持创建、恢复、fork、归档。历史持久化以支持重连。

🔬 Item 生命周期

每个 Item 都有显式的三阶段生命周期，让客户端可以立即开始渲染：

item/started
Item 开始 -- 客户端可立即渲染占位
item/*/delta
流式增量更新（可选，用于流式 item 类型）
item/completed
Item 完成 -- 携带最终终态载荷

原语层级关系

Thread（持久会话容器）
创建 / 恢复 / Fork / 归档
Turn 1 · Turn 2 · Turn 3 ...
每个 turn = 一次用户输入到 agent 完成的全过程
Item: msg | tool_call | approval | diff ...
每个 item = started → delta* → completed

💬 对话交互协议

App Server 的 JSON-RPC 协议是完全双向的。一个典型的 thread 包含客户端请求和多个服务器通知。服务器也可以在 agent 需要输入时主动发起请求。

🔄 典型对话流程

1. Initialize Handshake
Client → Server
客户端发送 initialize 请求（必须在其他方法之前）。服务器响应能力通告、协议版本、feature flags 和默认值。
2. Create Thread + Turn
Client → Server → Notifications
客户端创建 thread 和 turn。服务器返回 thread/started 和 turn/started 通知，以及注册的 user message item。
3. Tool Calls + Approval
Server ↔ Client
工具调用作为 item 发回客户端。服务器可能发起审批请求（server request），暂停 turn 直到客户端回复 "allow" 或 "deny"。
4. Agent Response
Server → Client (streaming)
Agent 消息通过 item/*/delta 事件流式传回，最终以 item/completed 完成。然后 turn/completed 结束本轮。

🚀 客户端集成模式

不同的客户端表面以不同模式嵌入 Codex。核心传输方式统一为 JSON-RPC over stdio (JSONL)。已有 Go、Python、TypeScript、Swift、Kotlin 等语言的客户端实现。

💻 本地应用 / IDE

捆绑或拉取平台特定的 App Server binary，作为长生命周期子进程启动，保持 stdio 双向通道。VS Code 和 Desktop App 固定到经过测试的版本。

pinned binary 稳定版本

🌐 Codex Web

Worker 在容器中配置 workspace + 启动 App Server binary。浏览器通过 HTTP + SSE 与 Codex backend 通信，backend 流式传输 worker 产生的事件。

container runtime SSE streaming

📱 TUI（终端）

历史上 TUI 是 "native" 客户端，在同一进程中直接与 Rust core types 交互。计划重构为使用 App Server，解锁远程 agent 连接能力。

重构中 remote agent

📦 捆绑 Binary 模式

VS Code、Desktop App 使用。shipped artifact 包含平台特定 binary，固定到经过测试的版本。

  • 客户端与服务器版本始终匹配
  • 无需独立更新服务器
  • 适合频繁发布的产品

🔄 解耦 Binary 模式

Xcode 等合作伙伴使用。客户端稳定，指向可更新的 App Server binary。

  • 采用服务端改进无需等待客户端发布
  • 向后兼容：旧客户端可与新服务器通信
  • 适合发布周期较长的产品

🌐 Web 场景的特殊考虑

Web 会话是临时的（tab 关闭、网络断开），因此浏览器不能是长时间运行任务的真相源。将状态和进度保存在服务器端意味着即使 tab 消失，工作也会继续。流式协议和保存的 thread session 让新会话可以重连、续接、追赶状态。

⚖️ 集成方式对比

App Server 是推荐的一等集成方式，但也有其他功能更受限的替代方案。以下是五种常见的 Codex 驱动方式和各自的适用场景。

集成方式 适用场景 优势 局限
App Server
(JSON-RPC)		 完整 agent 体验、IDE 集成、桌面应用 完整 harness 功能 + 稳定 event stream + Sign in with ChatGPT 需要构建客户端 JSON-RPC binding
MCP Server 已有 MCP 工作流，将 Codex 作为可调用工具 即插即用、与 MCP 生态兼容 仅暴露 MCP 能力，丰富的 session 语义映射困难
Portable Interface 协调多个 agent/模型提供者 一个抽象层统一多个 agent 趋向能力交集，provider 特定语义难表达
Headless CLI CI/CD 自动化、脚本化任务 单命令运行到完成，结构化输出，清晰退出码 非交互式，功能受限
TypeScript SDK 程序化控制本地 Codex agent 原生库接口，无需构建 JSON-RPC 客户端 语言支持较少，surface area 较小

💡 总结与展望

App Server 将 Codex harness 转化为一个稳定的、客户端友好的协议，支持从 TUI 到 IDE 集成再到 Web runtime 的各种表面。核心设计哲学：让客户端说 JSON-RPC，让 harness 处理复杂性。

🧰

统一协议层

所有 Codex 表面共享同一个 harness，通过 App Server 的 JSON-RPC 协议统一访问。一处改进，处处受益。

🔄

向后兼容设计

协议设计为可演进而不破坏现有客户端。旧客户端可以安全地与新服务器通信，无需同步升级。

💻

开源与开放

所有源代码在 Codex CLI 开源仓库中。社区可以贡献反馈和功能请求，共同推进 agent 可访问性。

🌍

远程 Agent 未来

TUI 重构完成后，终端可连接到远程 Codex server -- agent 靠近计算资源，笔记本睡眠也不中断工作。

"如果这篇文章激发了你将 Codex 集成到自己工作流中的想法，值得试试 App Server。所有源代码都在 Codex CLI 开源仓库中。我们很期待听到你的反馈，继续让 agent 对每个人都更加可及。"
