🔧 工具是什么

在计算中，确定性系统给定相同输入总是产生相同输出。而非确定性系统——如 Agent——即使相同起始条件也能产生不同响应。

💻 传统软件

确定性系统之间的契约。getWeather("NYC") 每次都以完全相同的方式获取纽约天气。

🤖 Agent 工具

确定性系统和非确定性 Agent 之间的新契约。用户问"今天带伞吗？"，Agent 可能调用天气工具、凭一般知识回答，或先问位置。

💡 核心洞察

为 Agent 编写工具时，需要从根本上重新思考方法：不是像为其他开发者写函数和 API 那样写工具和 MCP 服务器，而是为 Agent 设计它们。对 Agent 最"符合人体工程学"的工具最终对人类来说也出奇地直观。

🧪 构建原型

不亲手实践很难预测 Agent 会发现哪些工具符合人体工程学。

Step 1: 快速原型
用 Claude Code 快速搭建工具原型（可能一次完成）。给 Claude 提供工具依赖的软件库、API 或 SDK 文档（如 MCP SDK）。LLM 友好的文档通常以 llms.txt 形式存在于官方文档站点。
Step 2: 本地 MCP 服务器包装
用本地 MCP 服务器或 Desktop 扩展（DXT）包装工具，在 Claude Code 或 Claude Desktop 中连接和测试。
Step 3: 亲自测试
自己测试工具识别粗糙边缘。从用户收集反馈建立对预期用例和提示的直觉。

🔗 连接命令

# Claude Code: 添加本地 MCP 服务器 claude mcp add <name> <command> [args...] # Claude Desktop: Settings > Developer 或 Settings > Extensions # Anthropic API: 直接传入工具调用进行编程测试

📊 运行评估

需要测量 Claude 使用工具的效果。从生成大量基于真实世界用途的评估任务开始。

🎯 强 vs 弱评估任务

✅ 强任务示例

"安排下周与 Jane 开会讨论最新 Acme Corp 项目。附上上次项目规划会议笔记并预留会议室。"

需要多个工具调用——可能数十个。基于真实数据源和服务。

❌ 弱任务示例

"安排下周与 jane@acme.corp 开会。"

过于简单或表面化的"沙盒"环境，没有用足够复杂性压力测试工具。

⚙️ 运行评估建议

  • 用直接 LLM API 调用以编程方式运行评估
  • 使用简单 Agent 循环（while 循环包装交替 LLM API 和工具调用）
  • 系统提示中指示 Agent 输出结构化响应块（用于验证）以及推理和反馈块
  • 在工具调用和响应块之前输出这些可能通过触发思维链行为增加 LLM 有效智能
  • 开启 interleaved thinking获得类似开箱即用功能

💡 内部经验

本文大部分建议来自用 Claude Code 反复优化内部工具实现。评估建立在内部工作空间之上，镜像内部工作流复杂性，包括真实项目、文档和消息。

使用保留测试集确保不过度拟合"训练"评估。这些测试集显示即使超越"专家"工具实现也能提取额外性能改进。

🎯 为 Agent 选择正确工具

更多工具不总是导致更好结果。常见错误是仅包装现有软件功能或 API 端点的工具——无论这些工具是否适合 Agent。

📦 Agent 的不同"能力"

LLM Agent 有有限的"上下文"（一次能处理的信息量有限），而计算机内存便宜且丰富。

❌ list_contacts

返回所有联系人，Agent 必须逐个 token 阅读每个——浪费有限上下文在不相关信息上。像通过从上到下阅读每页来搜索通讯录。

✅ search_contacts / message_contact

先跳到相关页面（可能按字母顺序找到）。对 Agent 和人类都更好的方法。

🔀 工具整合示例

📅 日程安排

不实现 list_users、list_events、create_event，而是实现 schedule_event 工具查找可用性并安排事件。

📋 日志搜索

不实现 read_logs，而是实现 search_logs 只返回相关日志行和一些周围上下文。

👤 客户上下文

不实现 get_customer_by_id、list_transactions、list_notes，而是实现 get_customer_context 一次性编译客户所有最近相关信息。

🎯 清晰目的

确保每个工具都有清晰、独特的目的。工具应使 Agent 能像人类一样细分和解决任务。

🏷️ 工具命名空间

Agent 可能获得对数十个 MCP 服务器和数百个不同工具的访问——包括其他开发者的工具。当工具功能重叠或目的模糊时，Agent 会困惑该使用哪个。

📐 命名空间策略

🔧 按服务

asana_search、jira_search

📂 按资源

asana_projects_search、asana_users_search

前缀和后缀命名空间选择对工具使用评估有非平凡影响。效果因 LLM 而异，鼓励根据自己的评估选择命名方案。

💡 命名空间的好处

  • 帮助 Agent 在正确时间选择正确工具
  • 减少加载到 Agent 上下文的工具和描述数量
  • 将 Agent 计算从 Agent 上下文卸载回工具调用本身
  • 减少 Agent 犯错的总体风险

📝 返回有意义的上下文

工具实现应谨慎只向 Agent 返回高信号信息。优先考虑上下文相关性而非灵活性，摒弃低级技术标识符。

❌ 低级标识符

uuid、256px_image_url、mime_type

✅ 语义名称

name、image_url、file_type

🔑 关键发现

  • Agent 处理自然语言名称、术语或标识符比加密标识符成功得多
  • 仅将任意字母数字 UUID 解析为语义上有意义的语言（甚至 0 索引 ID 方案）就显著提高 Claude 在检索任务中的精度，通过减少幻觉

🎛️ ResponseFormat 枚举

暴露简单的 response_format enum 参数，让 Agent 控制工具返回 "concise" 还是 "detailed" 响应：

enum ResponseFormat { DETAILED = "detailed", // 206 tokens CONCISE = "concise" // 72 tokens (~⅓ token) }

"concise" 返回仅线程内容，排除 ID。"detailed" 返回包括 thread_ts、channel_id、user_id 等 ID 以启用需要这些的进一步工具调用。

⚡ Token 效率优化

📦 默认参数建议

对可能消耗大量上下文的任何工具响应，实现分页、范围选择、过滤和/或截断的组合，使用合理的默认参数值。

  • Claude Code 默认将工具响应限制为 25,000 token
  • 预计 Agent 的有效上下文长度会随时间增长，但对上下文高效工具的需求将保持

📋 截断响应指南

如果选择截断响应，确保用有帮助的指令引导 Agent：

❌ 无帮助的错误

不透明错误代码或 traceback

✅ 有帮助的错误

清晰传达具体和可操作的改进，引导 Agent 采取更 token 高效的策略（如过滤器或分页）

📝 提示工程工具描述

提高工具最有效的方法之一：提示工程你的工具描述和规范。

📋 编写工具描述的思维模型

想象如何向团队新员工描述你的工具。考虑你可能隐含带来的上下文——专用查询格式、利基术语定义、底层资源之间的关系——并使其显式化。

  • 通过清晰描述（并用严格数据模型执行）预期输入和输出来避免歧义
  • 输入参数应明确命名：用 user_id 而非 user
  • 即使对工具描述的微小改进也能产生戏剧性改进

🏆 案例: SWE-bench Verified

Claude Sonnet 3.5 在 SWE-bench Verified 评估上实现了最先进性能——在对工具描述进行精确改进后，大幅降低错误率并提高任务完成度。
