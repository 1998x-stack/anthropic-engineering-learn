# 中间件如何让你自由定制 Agent 线束

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-middleware-lets-you-customize-your-agent-harness)  
**日期:** 2026 年 3 月 26 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> Agent 中间件 (Middleware) 通过在核心循环的关键节点插入钩子 (Hook)，让你无需重写线束代码就能注入业务逻辑、安全策略和动态控制——就像给发动机加装涡轮增压器，而不是重新设计发动机。

---

## 核心要点

1. **线束的核心循环是固定的** —— 模型调用 → 工具执行 → 反馈循环，但不同场景需要在这个循环的不同位置注入自定义逻辑
2. **中间件提供六个钩子** —— 覆盖 Agent 生命周期的每一个关键节点，从启动前到完成后
3. **中间件是可组合的** —— 多个中间件像乐高积木一样叠加，各自独立、互不干扰
4. **某些需求"不可能靠提示词解决"** —— PII 脱敏、合规审计等确定性需求，必须在代码层面用中间件实现
5. **Deep Agents 完全构建在中间件之上** —— 验证了中间件作为线束定制核心机制的可行性

---

## 一、从核心循环说起

### Agent 线束的本质

每个 Agent 线束的核心都是同一个循环：

```
┌──────────────────────────────────────┐
│           Agent 核心循环              │
│                                      │
│   ┌─────────┐                        │
│   │  LLM    │◄──────────────┐        │
│   │  模型调用 │               │        │
│   └────┬────┘               │        │
│        │ 模型输出             │        │
│        ▼                    │        │
│   ┌─────────┐          ┌───┴────┐   │
│   │ 判断：   │──工具──→│ 执行工具 │   │
│   │ 工具调用  │          │ 返回结果 │   │
│   │ or 最终  │          └────────┘   │
│   │ 回复？   │                       │
│   └────┬────┘                       │
│        │ 最终回复                     │
│        ▼                            │
│   ┌─────────┐                       │
│   │  输出    │                       │
│   └─────────┘                       │
└──────────────────────────────────────┘
```

LangChain 的 `create_agent` 就是这个核心循环的抽象。指令 (Instructions) 和工具 (Tools) 很容易定制——改个系统提示、换几个工具就行。

### 但有些定制改的是循环本身

如果你的需求是：

- 每次模型调用**之前**自动检查上下文中的敏感信息？
- 每次工具执行**之后**对结果做合规审计？
- 模型调用失败时**自动重试**并切换到备用模型？

这些需求不是在"循环里面加东西"，而是要**改变循环本身的行为**。直接修改核心代码既危险又不可维护。

> **为什么重要**  
> 需求的多样性是无限的，但核心循环应该保持稳定。中间件在"保持核心循环不变"和"允许无限定制"之间找到了平衡点。

## 二、什么是 Agent 中间件 (AgentMiddleware)？

### 一个类比

> **类比理解**  
> 想象一个工厂的流水线。核心流水线负责"组装产品"，你不需要改造流水线本身。但你可以在流水线的关键节点加装"检查站"——原料进来时检查质量，成品出来时贴合格标签，发现次品时自动拦截。中间件就是这些检查站。

### 定义

中间件暴露一组**钩子 (Hooks)**，让你在 Agent 执行的关键节点运行自定义逻辑。它们有以下特性：

| 特性 | 说明 |
|------|------|
| **可组合** | 多个中间件可以叠加使用，各自独立 |
| **非侵入** | 不需要修改核心循环代码 |
| **可复用** | 同一个中间件可以在多个 Agent 中使用 |
| **可扩展** | 开发者可以继承 `AgentMiddleware` 创建自定义中间件 |

LangChain 还提供了预建中间件 (Prebuilt Middleware)，开箱即用：摘要压缩、自动重试、PII 脱敏等。

## 三、六个钩子：Agent 生命周期的全覆盖

中间件通过六个钩子覆盖了 Agent 从启动到结束的完整生命周期：

```
Agent 生命周期与钩子位置
═══════════════════════════════════════════════════════

  ① before_agent          ─── Agent 启动，仅执行一次
        │
        ▼
  ┌─────────── 核心循环开始 ───────────┐
  │                                    │
  │  ② before_model       ─── 每次模型调用前
  │        │                           │
  │        ▼                           │
  │  ③ wrap_model_call    ─── 包裹模型调用（端到端）
  │        │                           │
  │        ▼                           │
  │  ④ after_model        ─── 模型回复后，工具执行前
  │        │                           │
  │        ▼                           │
  │  ⑤ wrap_tool_call     ─── 包裹工具执行（端到端）
  │        │                           │
  │        └──────── 循环回到 ② ────────┘
  │
  ⑥ after_agent           ─── Agent 结束，仅执行一次

═══════════════════════════════════════════════════════
```

### 各钩子详解

| 钩子 | 触发时机 | 频率 | 典型用途 |
|------|---------|------|---------|
| `before_agent` | Agent 被调用时 | 一次 | 加载记忆、连接外部资源、验证输入 |
| `before_model` | 每次模型调用前 | 每轮 | 裁剪历史、检测 PII、注入动态上下文 |
| `wrap_model_call` | 包裹整个模型调用 | 每轮 | 缓存、自动重试、动态切换模型 |
| `after_model` | 模型回复后、工具执行前 | 每轮 | 人工审核 (Human-in-the-loop)、输出过滤 |
| `wrap_tool_call` | 包裹整个工具执行 | 每次工具调用 | 注入上下文、拦截结果、权限门控 |
| `after_agent` | Agent 完成全部工作后 | 一次 | 保存结果、发送通知、清理资源 |

> **类比理解**  
> 把 Agent 的一次执行想象成一趟航班。`before_agent` 是登机检查，`before_model` 是每次起飞前的安全检查，`wrap_model_call` 是空中管制全程监控飞行，`after_model` 是落地后的入境审查，`wrap_tool_call` 是对每件行李的安检，`after_agent` 是到达目的地后的签收。

## 四、实战：中间件解决了什么问题

### 4.1 合规与业务逻辑：提示词做不到的事

> **核心观点**  
> 你不可能靠提示词 (Prompt) 来实现 HIPAA 合规。

有些需求必须是**确定性的**——不能依赖模型"大概率会遵守"：

| 需求类型 | 为什么提示词不够 | 中间件方案 |
|---------|----------------|-----------|
| PII 脱敏 | 模型可能遗漏敏感信息 | `PIIMiddleware` 在代码层面扫描并遮蔽 |
| 内容审核 | 模型可能生成不合规内容 | 审核中间件在输出前拦截 |
| 审计日志 | 必须记录每一次操作 | 中间件在每个钩子点写日志 |

### PII 检测中间件示例

`PIIMiddleware` 实现了 `before_model` 和 `after_model` 两个钩子：

```
用户输入                 模型                    最终输出
   │                     │                       │
   ▼                     │                       │
before_model             │                       │
┌──────────────┐         │                       │
│ 扫描输入      │         │                       │
│ 发现 PII     │         │                       │
│ 遮蔽/脱敏     │─────→  模型处理  ─────→  after_model
│ "张三"→"[姓名]"│        (看不到真实    ┌──────────────┐
└──────────────┘         PII)         │ 扫描输出      │
                                      │ 还原或保持遮蔽 │
                                      └──────┬───────┘
                                             │
                                             ▼
                                          安全输出
```

支持三种处理策略：遮蔽 (Mask)、脱敏 (Redact)、哈希 (Hash)。

### 4.2 动态 Agent 控制

中间件让你可以**在运行时**根据状态动态调整 Agent 行为：

- **动态注入工具** —— 根据当前任务阶段，只暴露相关工具
- **运行时切换模型** —— 简单任务用快速模型，复杂推理切换到强模型
- **动态更新系统提示** —— 根据对话进展注入新的指令

> **为什么重要**  
> 这意味着 Agent 不再是"出厂配置固定"的静态系统。中间件让 Agent 具备了根据环境自适应的能力——同一个 Agent 在不同场景下展现出不同的行为。

## 五、Deep Agents 案例：中间件架构的验证

Deep Agents 是 LangChain 构建的完整 Agent 产品，**完全基于 `create_agent` + 中间件** 架构。这证明了中间件不是玩具——它能撑起生产级系统。

```
┌──────────────────────────────────────────────────┐
│                Deep Agents 架构                   │
│                                                  │
│   ┌──────────────────────────────────────────┐   │
│   │           create_agent (核心循环)          │   │
│   └──────────────────────────────────────────┘   │
│                      │                           │
│   ┌──────────────────┼──────────────────────┐   │
│   │              中间件层                     │   │
│   │                                          │   │
│   │  ┌──────────────────────────────────┐    │   │
│   │  │ FilesystemMiddleware             │    │   │
│   │  │ 文件系统上下文的加载/卸载 + 长期记忆 │    │   │
│   │  └──────────────────────────────────┘    │   │
│   │  ┌──────────────────────────────────┐    │   │
│   │  │ SubagentMiddleware               │    │   │
│   │  │ 子 Agent 管理 + 上下文隔离         │    │   │
│   │  └──────────────────────────────────┘    │   │
│   │  ┌──────────────────────────────────┐    │   │
│   │  │ SummarizationMiddleware          │    │   │
│   │  │ 上下文溢出管理 (压缩/摘要)         │    │   │
│   │  └──────────────────────────────────┘    │   │
│   │  ┌──────────────────────────────────┐    │   │
│   │  │ SkillsMiddleware                 │    │   │
│   │  │ 能力按需加载 (渐进式暴露)          │    │   │
│   │  └──────────────────────────────────┘    │   │
│   └──────────────────────────────────────────┘   │
└──────────────────────────────────────────────────┘
```

| 中间件 | 解决的问题 | 用到的钩子 |
|--------|-----------|-----------|
| FilesystemMiddleware | 上下文窗口有限，需要将信息卸载到文件系统 | `before_agent`, `wrap_tool_call` |
| SubagentMiddleware | 子 Agent 需要独立上下文，防止互相污染 | `wrap_tool_call` |
| SummarizationMiddleware | 长对话导致上下文溢出 | `before_model` |
| SkillsMiddleware | 启动时加载所有技能描述会浪费上下文空间 | `before_model`, `wrap_tool_call` |

> **类比理解**  
> Deep Agents 的架构就像一栋建筑：`create_agent` 是钢筋混凝土骨架（简单、稳定、不变），四个中间件是水电气暖四大系统（各自独立安装、各自维护、按需升级）。你不需要为了换暖气而拆掉承重墙。

## 六、为什么我们押注中间件

### 模型会变强，但中间件不会消失

随着模型能力提升，部分中间件的功能可能会被模型"吸收"——比如模型可能原生支持更长的上下文窗口，不再需要摘要压缩。

**但有三类需求永远需要中间件：**

| 需求类型 | 为什么模型不能替代 | 例子 |
|---------|-------------------|------|
| **确定性策略执行** | 合规要求 100% 执行，不能有概率性 | PII 脱敏、访问控制 |
| **生产级护栏** | 必须在代码层面兜底 | 速率限制、成本控制、审计日志 |
| **业务专属逻辑** | 每个组织的规则不同 | 行业合规、内部审批流程 |

### 中间件的架构优势

```
传统方式：业务逻辑硬编码在核心循环中

┌─────────────────────────┐
│  核心循环                │
│  + PII 检查              │   高耦合
│  + 审计日志              │   难复用
│  + 重试逻辑              │   改一处影响全局
│  + 合规审查              │
└─────────────────────────┘

中间件方式：业务逻辑解耦

┌─────────────────────────┐
│  核心循环 (保持简单干净)   │
└────────────┬────────────┘
             │
   ┌─────────┼─────────┐
   │         │         │
   ▼         ▼         ▼
┌──────┐ ┌──────┐ ┌──────┐
│ PII  │ │ 审计  │ │ 重试  │   低耦合
│ 中间件│ │ 中间件│ │ 中间件│   可复用
└──────┘ └──────┘ └──────┘   独立维护
```

> **核心结论：** 中间件让业务逻辑与核心 Agent 代码彻底解耦。一个中间件写一次，可以在整个组织的所有 Agent 中复用。

## 延伸思考

1. **中间件的执行顺序问题：** 当多个中间件叠加时，执行顺序会影响结果（比如 PII 脱敏中间件应该在摘要压缩之前还是之后运行？）。如何设计中间件的优先级和依赖管理机制？
2. **中间件与模型能力的边界迁移：** 随着模型越来越强，哪些当前用中间件实现的功能会被模型原生支持？哪些永远不会？这条边界将如何移动？
3. **中间件的可观测性：** 当 Agent 行为异常时，如何追踪是哪个中间件导致了问题？是否需要为中间件本身建立专门的调试和监控工具？
4. **跨线束的中间件标准：** 目前中间件绑定在 LangChain 的 `AgentMiddleware` 接口上。如果行业建立了跨线束的中间件标准，是否能形成一个"中间件市场"？
