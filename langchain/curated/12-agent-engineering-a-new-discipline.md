# Agent 工程：一个正在诞生的新学科 (Agent Engineering: A New Discipline)

**作者:** The LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/agent-engineering-a-new-discipline)  
**日期:** 2025 年 12 月 9 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> Agent 工程 (Agent Engineering) 是将不确定性的 LLM 系统打磨成可靠生产体验的迭代过程。它不是传统软件工程的变种，而是一个融合了产品思维、工程实践和运维运营的全新学科。

---

## 核心要点

1. **"在我机器上能跑"和"在生产环境能跑"之间存在巨大鸿沟** —— Agent 的输入不可预测、输出不确定，传统软件的确定性假设全部失效
2. **Agent 工程是一个循环，不是一条直线** —— 构建 → 测试 → 上线 → 观测 → 优化 → 重复，每一轮都让系统更可靠
3. **评估驱动开发取代测试驱动开发** —— 单元测试无法覆盖非确定性行为，必须用统计置信度替代通过/失败的二元判断
4. **可观测性不是"有了更好"而是"没有就死"** —— 无法追踪每一步执行路径，就无法调试 Agent
5. **人机协作是架构决策，不是权宜之计** —— Human-in-the-loop 应在设计阶段就纳入，而非出了问题再补

---

## 一、什么是 Agent 工程？

### 传统软件 vs. Agent 系统

> **类比：** 传统软件像工厂流水线——你知道原料是什么，知道每个工位做什么，产出物是标准化的。Agent 系统更像一个实习生——你给他任务描述，他理解了大意，但具体怎么做、做出什么结果，每次都可能不一样。

| 维度 | 传统软件工程 | Agent 工程 |
|------|------------|-----------|
| 输入 | 已知、有限、结构化 | 未知、无限、自然语言 |
| 输出 | 确定性、可预测 | 非确定性、概率性 |
| 测试 | 单元测试、集成测试 | 评估套件 (Eval Suite)、统计分布 |
| 调试 | 断点、日志 | 全链路追踪 (Tracing) |
| 质量保证 | 边界条件测试 | 行为分布度量 |
| 人的角色 | 用户 | 用户 + 监督者 + 协作者 |

### Agent 工程的核心循环

```
         ┌──────────┐
         │  1. 构建  │  定义 Agent 的任务边界、工具和上下文
         │  Build   │
         └────┬─────┘
              │
              ▼
         ┌──────────┐
         │  2. 测试  │  编写评估套件，度量行为分布
         │  Test    │
         └────┬─────┘
              │
              ▼
         ┌──────────┐
         │  3. 上线  │  部署到生产环境
         │  Ship    │
         └────┬─────┘
              │
              ▼
         ┌──────────┐
         │  4. 观测  │  全链路追踪 + 用户反馈
         │ Observe  │
         └────┬─────┘
              │
              ▼
         ┌──────────┐
         │  5. 优化  │  基于数据调整 Agent
         │  Refine  │──────────┐
         └──────────┘          │
              ▲                │
              └────────────────┘
              循环往复，每轮更可靠
```

> **为什么重要**  
> 传统软件可以"写完测完就上线"。Agent 系统必须持续迭代——因为你永远无法在上线前穷举所有可能的用户输入和 Agent 行为。这个循环不是可选的，而是 Agent 工程的本质。

## 二、Agent 工程的三大支柱

Agent 工程不是单一技能，而是三个领域的交叉：

```
              ┌─────────────────────┐
              │     产品思维         │
              │  (Product Thinking)  │
              └────────┬────────────┘
                       │
            ┌──────────┼──────────┐
            │          │          │
            ▼          ▼          ▼
     ┌───────────┐ ┌────────┐ ┌──────────┐
     │   工程     │ │ Agent  │ │  运维     │
     │Engineering │ │  工程  │ │Operations│
     └───────────┘ └────────┘ └──────────┘
```

### 支柱一：产品思维 (Product Thinking)

在写第一行代码之前，需要回答两个问题：

1. **Agent 要完成的"工作"到底是什么？** (Job to Be Done)
2. **如何度量"完成得好不好"？** (Evaluation Criteria)

> **类比：** 你不会先造一辆车再决定它是轿车还是卡车。但很多团队在构建 Agent 时恰恰犯了这个错误——先接好 API，再想"它应该干什么"。

### 支柱二：工程实践 (Engineering)

Agent 工程在技术层面有五个核心关注点：

| 关注点 | 说明 | 挑战 |
|--------|------|------|
| **交互设计** | 流式输出、中断处理、进度展示 | 用户不知道 Agent 在想什么时会失去信任 |
| **鲁棒运行时** | 持久化执行、人机协作暂停、内存管理 | Agent 可能运行数分钟甚至数小时 |
| **上下文工程** | 规则、系统提示、少样本示例、记忆、工具描述 | 给多了噪音太大，给少了能力不足 |
| **编排原语** | 多 Agent 协作、路由、任务交接 (Handoff) | 协调复杂度随 Agent 数量指数增长 |
| **评估框架** | 自动化评估、黄金数据集、A/B 测试 | 评估器本身也需要校准和验证 |

### 支柱三：运维运营 (Operations)

Agent 上线只是开始。运维包含四个维度：

```
┌─────────────────────────────────────────────────┐
│                  Agent 运维                      │
│                                                 │
│  ┌───────────┐  ┌───────────┐  ┌─────────────┐ │
│  │  可观测性  │  │  反馈回路  │  │   安全护栏   │ │
│  │           │  │           │  │             │ │
│  │ 实时监控   │  │ 用户反馈   │  │ 内容过滤    │ │
│  │ 执行流追踪 │  │ → 改进循环 │  │ 成本限制    │ │
│  │ 异常告警   │  │           │  │ 速率限制    │ │
│  └───────────┘  └───────────┘  └─────────────┘ │
│                                                 │
│  ┌─────────────────────────────────────────────┐│
│  │                合规治理                      ││
│  │  审计日志 / 数据治理 / 权限控制               ││
│  └─────────────────────────────────────────────┘│
└─────────────────────────────────────────────────┘
```

> **为什么重要**  
> 传统软件的 bug 通常是确定性的——同样的输入总会触发同样的错误。Agent 的问题可能只在特定上下文组合下才出现。没有全链路可观测性，你连"到底哪里出了问题"都无法回答。

## 三、Agent 工程 vs. 传统软件工程：五个根本差异

### 差异一：非确定性 (Non-determinism)

```
传统软件：  input A ──→ 总是 output X
Agent：    input A ──→ 可能 output X, Y, Z, 或完全意外的 W
```

这意味着你不能用"通过/失败"来测试 Agent。你需要的是**统计置信度**——"在 1000 次运行中，95% 的结果符合预期"。

### 差异二：评估驱动 (Evaluation-driven)

传统的边界条件测试在 Agent 世界里远远不够。你需要**评估套件 (Eval Suite)**，度量 Agent 在整个行为分布上的表现，而不只是几个边界情况。

> **类比：** 测试传统软件像考试——出几道题，答对了就过。测试 Agent 像面试——你要观察候选人在各种场景下的反应模式，而不是只看几个固定问题的答案。

### 差异三：提示词即代码 (Prompt as Code)

提示词 (Prompt) 不是随便写在某个地方的文本，而是代码库的一部分。它需要：

- **版本控制** —— 每次修改都有 diff 可查
- **代码审查** —— 提示词的修改和代码修改一样需要 review
- **自动化测试** —— 提示词变更后自动跑评估套件

### 差异四：可观测性是必需品 (Observability is Mandatory)

在传统软件中，日志和监控是"最佳实践"。在 Agent 系统中，没有可观测性就等于闭着眼睛开车。

你需要追踪的不只是"输入→输出"，而是中间的每一步：模型的推理过程、工具调用的参数和返回值、上下文窗口的内容变化。

### 差异五：人机协作是设计选择 (Human-in-the-Loop by Design)

Human-in-the-loop 不是"Agent 不够聪明时的退路"，而是一个**主动的架构决策**。

它是一个学习机制：
- Agent 遇到不确定的情况时请求人类介入
- 人类的决策被记录下来
- 这些记录成为未来训练和评估的数据

## 四、Agent 工程技术栈

一个完整的 Agent 工程技术栈包含五层：

```
┌─────────────────────────────────────────────┐
│  第 5 层：部署层 (Deployment)                │
│  LangGraph Platform / Modal / ...           │
├─────────────────────────────────────────────┤
│  第 4 层：记忆层 (Memory)                    │
│  LangGraph Memory / Zep / ...               │
├─────────────────────────────────────────────┤
│  第 3 层：评估层 (Evaluation)                │
│  LangSmith Evals / Ragas / ...              │
├─────────────────────────────────────────────┤
│  第 2 层：可观测性层 (Observability)          │
│  LangSmith / Braintrust / ...               │
├─────────────────────────────────────────────┤
│  第 1 层：编排层 (Orchestration)              │
│  LangGraph / CrewAI / AutoGen / ...         │
└─────────────────────────────────────────────┘
```

每一层解决不同的问题：

| 层 | 解决什么问题 | 缺失的后果 |
|----|------------|-----------|
| 编排层 | Agent 如何组织工作流、调度工具、协调多 Agent | 只能写最简单的单轮对话 |
| 可观测性层 | 如何知道 Agent 在做什么、哪里出了问题 | 无法调试，只能猜 |
| 评估层 | 如何知道 Agent 做得好不好 | 无法量化改进，凭感觉迭代 |
| 记忆层 | Agent 如何跨会话保持状态和知识 | 每次对话都是"失忆"的 |
| 部署层 | 如何将 Agent 稳定地运行在生产环境 | 只能在笔记本上演示 |

## 五、来自生产团队的五条经验

Clay、Vanta、LinkedIn、Cloudflare 等公司在 Agent 工程实践中积累了宝贵经验：

### 经验 1：从窄范围开始

> **做一件事做到极致的 Agent，胜过什么都能做但什么都做不好的通用 Agent。**

从一个具体的、边界清晰的任务开始。等这个任务做到可靠后，再逐步扩展范围。

### 经验 2：尽早投资评估

建立评估套件的团队迭代速度是不建立的 **3 倍**。

原因很简单：没有评估套件，每次修改后你只能手动测试几个例子，然后祈祷没有破坏其他场景。有了评估套件，修改后一键跑完所有场景，几分钟就知道结果。

### 经验 3：人机协作是学习机制

Human-in-the-loop 不是承认失败，而是构建数据飞轮的入口：

```
Agent 遇到不确定情况
        │
        ▼
请求人类介入 ──→ 人类做出决策 ──→ 决策被记录
                                     │
                                     ▼
                            成为训练/评估数据
                                     │
                                     ▼
                          Agent 下次自主处理
```

### 经验 4：可观测性的回报是即时的

这不是"等到出大问题才庆幸有了"的东西。从第一天起，可观测性就在帮你理解 Agent 的行为模式、发现优化机会、定位问题根因。

### 经验 5：Agent 工程是团队运动

它不是一个人能搞定的事情。你至少需要三种角色：

- **产品人员** —— 定义"Agent 应该做什么"和"做到什么程度算好"
- **工程人员** —— 构建系统、设计架构、编写评估
- **领域专家** —— 提供隐性知识，校准评估器，审查边界案例

## 延伸思考

1. **Agent 工程会成为独立岗位吗？** 就像 DevOps 从"运维"中分化出来成为独立学科一样，Agent 工程是否会从"后端开发"中分化，形成独立的职业路径和技能树？
2. **评估的极限在哪里？** 当 Agent 的行为空间足够大时，任何评估套件都只能覆盖其中一小部分。我们如何在"足够的置信度"和"无限的可能性"之间找到平衡？
3. **非确定性的组织挑战：** 传统软件团队习惯了"这个 bug 修好了就是修好了"。Agent 系统中"修好了 A 场景可能恶化了 B 场景"是常态。这对团队文化、发布流程和质量标准提出了什么挑战？
4. **从工具到学科：** 文中提到的技术栈（LangGraph、LangSmith 等）只是当前的实现方式。如果抽象掉具体工具，Agent 工程的"第一性原理"是什么？哪些原则会在工具迭代中保持不变？
