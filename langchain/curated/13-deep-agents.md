# 深度 Agent：从浅层循环到深度智能体 (Deep Agents)

**作者:** Harrison Chase (LangChain Team)  
**来源:** [LangChain Blog](https://www.langchain.com/blog/deep-agents)  
**日期:** 2026 年 5 月  
**阅读时间:** 约 12 分钟

---

> **一句话总结**  
> 深度 Agent (Deep Agent) 与浅层 Agent 共享同一核心算法——"LLM 在循环中调用工具"——但通过精心设计的系统提示、规划工具、子 Agent 和文件系统四大机制，将简单的工具调用循环升维为能够深入探索、长时间执行、自主规划复杂任务的智能体。

---

## 核心要点

1. **同一算法，天壤之别** —— 深度 Agent 和浅层 Agent 的底层架构完全相同（LLM + 工具循环），差异全部来自工程层面的设计选择
2. **提示词依然是王牌** —— Claude Code 等顶级编程 Agent 的系统提示极其详尽，包含工具使用指南和少样本示例，证明提示工程 (Prompt Engineering) 远未过时
3. **规划工具可以是"空操作"** —— Claude Code 的 Todo List 工具本质上是一个 no-op，但它作为上下文工程手段，显著提升了 Agent 的任务执行能力
4. **子 Agent 是上下文管理的利器** —— 拆分任务到独立上下文窗口的子 Agent，是深度 Agent 处理复杂任务的关键模式
5. **文件系统是长时记忆** —— 深度 Agent 运行时间长、上下文累积快，文件系统既是任务执行工具，也是跨步骤的"外部记忆"

---

## 一、深度 Agent 的崛起

### 占主导地位的 Agent 架构

当前 Agent 系统的核心架构已经收敛到一个简洁的模式：

```
┌──────────────────────────────────────────┐
│           主流 Agent 架构                 │
│                                          │
│     ┌─────────┐                          │
│     │   LLM   │◄────────────┐            │
│     └────┬────┘             │            │
│          │ 决策              │ 反馈       │
│          ▼                  │            │
│     ┌─────────┐        ┌────┴────┐       │
│     │ 选择工具  │───────→│ 执行工具  │       │
│     └─────────┘        └────┬────┘       │
│          ▲                  │            │
│          └──────────────────┘            │
│              循环，直到任务完成             │
└──────────────────────────────────────────┘
```

这就是全部了。**LLM 在循环中调用工具** (LLM running in a loop, calling tools)。

但同一个架构，不同的实现方式，产出的 Agent 能力天差地别。

### 浅层 Agent vs. 深度 Agent

> **类比理解**  
> 浅层 Agent 像一个只会按步骤执行清单的新手实习生——你说"查一下这个数据"，他查了就停；你说"写个函数"，他写了就交。深度 Agent 像一个资深工程师——给他一个模糊的任务描述，他会自己规划步骤、深入研究背景、把复杂问题拆解成子任务、做笔记记录中间发现，最终交付一个完整的解决方案。

| 维度 | 浅层 Agent (Naive) | 深度 Agent (Deep) |
|------|-------------------|-------------------|
| 系统提示 | 简短、通用 | 详尽、包含工具指南和示例 |
| 规划能力 | 无 | 有专门的规划工具 |
| 任务分解 | 单线程执行 | 拆分为子 Agent 并行/串行处理 |
| 中间状态 | 仅存在于上下文窗口 | 写入文件系统，持久化保存 |
| 执行时长 | 短（几步完成） | 长（可能持续数十分钟） |
| 适合场景 | 简单查询、单步操作 | 复杂研究、多文件编辑、长时任务 |

> **为什么重要**  
> 理解深度 Agent 的关键洞察是：**差异不在算法，而在工程**。你不需要发明新的架构范式。你需要的是在现有的 LLM + 工具循环之上，叠加四层精心设计的工程机制。

## 二、深度 Agent 的四大特征

### 特征一：详尽的系统提示 (Detailed System Prompt)

Claude Code 的系统提示以其长度和细节著称。最优秀的编程 Agent 和研究 Agent 几乎无一例外地使用复杂的系统提示。

系统提示中通常包含：

| 内容类型 | 说明 | 作用 |
|----------|------|------|
| **工具使用指南** | 每个工具的详细使用说明和约束条件 | 减少工具误用，提升首次调用成功率 |
| **少样本示例** (Few-shot Examples) | 展示工具调用的正确方式和输出格式 | 让模型学会"正确的做事方式" |
| **行为规范** | 何时应该规划、何时应该执行、何时应该验证 | 引导 Agent 遵循高效的工作流程 |
| **约束条件** | 不应做什么、边界在哪里 | 防止 Agent 越界或做出危险操作 |

```
系统提示的信息密度对比

浅层 Agent:
┌────────────────────────────────────────────────┐
│ "You are a helpful assistant. Use tools to     │
│  complete tasks."                              │
│                                                │
│  ~20 tokens                                    │
└────────────────────────────────────────────────┘

深度 Agent (如 Claude Code):
┌────────────────────────────────────────────────┐
│ 工具描述: 每个工具 50-200 tokens               │
│ 使用规范: 300+ tokens                          │
│ 少样本示例: 500+ tokens                        │
│ 行为指南: 200+ tokens                          │
│ 约束条件: 200+ tokens                          │
│                                                │
│  ~2000+ tokens                                 │
└────────────────────────────────────────────────┘
```

> **关键结论：提示工程 (Prompt Engineering) 依然重要！**  
> 在 Agent 时代，系统提示不是简单的一句话指令，而是一份精心编写的"操作手册"。它是 Agent 行为的根基。

---

### 特征二：规划工具 (Planning Tool)

Claude Code 使用一个 Todo List 工具来进行规划。这个工具的实现令人意外——**它本质上是一个空操作 (no-op)**。

什么是 no-op 规划工具？

```
┌──────────────────────────────────────────────────┐
│              No-op 规划工具的工作方式               │
│                                                  │
│  Agent 调用 Todo List 工具                        │
│       │                                          │
│       ▼                                          │
│  ┌──────────────────────────────┐                │
│  │  工具接收输入:                │                │
│  │  - 任务 1: 分析需求           │                │
│  │  - 任务 2: 实现功能           │                │
│  │  - 任务 3: 编写测试           │                │
│  │                              │                │
│  │  工具实际操作: 几乎什么都不做   │                │
│  │  返回: "OK" 或确认信息         │                │
│  └──────────────────────────────┘                │
│       │                                          │
│       ▼                                          │
│  但关键效果: 计划已经写进了上下文窗口！              │
│  Agent 后续的每一步都能"看到"这个计划               │
└──────────────────────────────────────────────────┘
```

> **类比理解**  
> 这就像一个人在做复杂任务前先在白板上列出步骤。白板本身不会帮你干活（no-op），但**写下计划这个动作**让你的思路变得清晰，而且你可以随时回头看白板确认自己做到了哪一步。规划工具的价值不在于它"做了什么"，而在于它迫使 Agent 将计划外化到上下文中。

这是**上下文工程 (Context Engineering)** 的一个精妙应用：

- **规划过程**迫使 Agent 结构化思考任务
- **规划结果**留存在上下文窗口中，成为后续步骤的锚点
- **规划更新**（标记完成、调整顺序）帮助 Agent 跟踪进度

> **为什么重要**  
> 规划是深度 Agent 的一大核心组件 (Planning is a big component)。即使规划工具的实现极其简单（甚至是 no-op），它作为上下文管理手段的效果是显著的。这揭示了一个重要的设计原则：**工具的价值不仅在于它的功能，还在于它对上下文的影响。**

### 特征三：子 Agent (Sub Agents)

Claude Code 能够生成子 Agent (spawn sub agents) 来拆分任务。这不仅仅是并行加速，更是**上下文管理和提示快捷方式** (context management and prompt shortcuts)。

```
深度 Agent 的子 Agent 架构

┌─────────────────────────────────────────────────────┐
│  主 Agent (Orchestrator)                             │
│                                                     │
│  系统提示: 全局上下文 + 任务分解策略                    │
│  上下文: 高层计划 + 各子任务状态                        │
│                                                     │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐         │
│  │ 子Agent 1 │   │ 子Agent 2 │   │ 子Agent 3 │         │
│  │          │   │          │   │          │         │
│  │ 独立提示  │   │ 独立提示  │   │ 独立提示  │         │
│  │ 独立上下文│   │ 独立上下文│   │ 独立上下文│         │
│  │ 独立工具  │   │ 独立工具  │   │ 独立工具  │         │
│  │          │   │          │   │          │         │
│  │ 专注:     │   │ 专注:     │   │ 专注:     │         │
│  │ 代码搜索  │   │ 文件编辑  │   │ 测试验证  │         │
│  └─────┬────┘   └─────┬────┘   └─────┬────┘         │
│        │              │              │               │
│        └──────────────┼──────────────┘               │
│                       ▼                              │
│              结果汇总到主 Agent                        │
└─────────────────────────────────────────────────────┘
```

子 Agent 的三重价值：

| 价值 | 说明 |
|------|------|
| **上下文隔离** | 每个子 Agent 只加载与自己子任务相关的信息，避免上下文污染 |
| **提示定制** | 可以为不同类型的子任务编写专门的系统提示，比通用提示更高效 |
| **控制粒度** | 主 Agent 可以选择创建通用子 Agent，也可以创建高度定制的子 Agent |

深度 Agent 会针对具体任务生成专注的子 Agent (Deep agents spin up focused sub agents for individual tasks)。这里的关键词是"专注"——子 Agent 不是主 Agent 的复制品，而是被精心裁剪后只负责一件事的执行单元。

---

### 特征四：文件系统 (File System)

Claude Code 拥有完整的文件系统访问权限。但文件系统的用途**远不止任务本身**——它同时充当 Agent 的"外部记忆"。

```
文件系统的双重角色

┌────────────────────────────────────────────────────┐
│                                                    │
│  角色 1: 任务执行工具                                │
│  ┌──────────────────────────────────────┐          │
│  │  · 读取项目文件                       │          │
│  │  · 编辑代码                           │          │
│  │  · 运行脚本                           │          │
│  │  · 创建新文件                         │          │
│  └──────────────────────────────────────┘          │
│                                                    │
│  角色 2: 外部记忆 / 协作工作区                        │
│  ┌──────────────────────────────────────┐          │
│  │  · 记录中间发现和笔记                  │          │
│  │  · 保存研究结果供后续步骤使用            │          │
│  │  · 主 Agent 和子 Agent 之间共享信息     │          │
│  │  · 跨步骤持久化关键决策和上下文          │          │
│  └──────────────────────────────────────┘          │
│                                                    │
└────────────────────────────────────────────────────┘
```

> **类比理解**  
> 想象一个侦探在调查复杂案件。他不会把所有线索都记在脑子里（上下文窗口），而是在白板上钉满照片和便条，用红线连接关联线索。文件系统就是深度 Agent 的"侦探白板"——随时写入发现，随时回头查阅，不同的调查员（子 Agent）可以共享同一块白板。

Manus（另一个知名 Agent）也采用了类似的策略，利用文件系统实现"记忆"功能。

这一特征对深度 Agent 尤为关键，原因在于：

1. **深度 Agent 运行时间长** —— 数十分钟甚至数小时的执行过程中，上下文会快速累积
2. **上下文窗口有限** —— 即使有压缩 (Compaction)，也不可能把所有信息塞进窗口
3. **文件系统提供了无限的持久化存储** —— 随时写入、按需读取、多个 Agent 共享

> **为什么重要**  
> 文件系统把 Agent 的"工作记忆"从有限的上下文窗口扩展到了几乎无限的外部存储。这是深度 Agent 能够处理长时间、高复杂度任务的基础设施保障。

## 三、从浅到深：完整的能力光谱

四大特征不是独立的，它们构成了一个层层叠加的能力体系：

```
深度 Agent 能力栈

┌────────────────────────────────────────────────────┐
│  第 4 层: 文件系统                                   │
│  持久化记忆 + 共享工作区 + 长时执行基础设施              │
├────────────────────────────────────────────────────┤
│  第 3 层: 子 Agent                                   │
│  上下文隔离 + 任务并行 + 专注执行                      │
├────────────────────────────────────────────────────┤
│  第 2 层: 规划工具                                   │
│  结构化思考 + 进度跟踪 + 上下文锚定                    │
├────────────────────────────────────────────────────┤
│  第 1 层: 详尽系统提示                                │
│  行为规范 + 工具指南 + 少样本示例                      │
├────────────────────────────────────────────────────┤
│  基础: LLM + 工具循环                                │
│  所有 Agent（包括浅层）共享的核心架构                   │
└────────────────────────────────────────────────────┘
```

每一层都放大了下一层的效果：详尽的提示让 Agent 知道**如何**规划；规划工具让 Agent 知道**何时**分派子 Agent；子 Agent 通过文件系统**协作**完成复杂任务。

## 四、构建你自己的深度 Agent

Harrison Chase 发布了开源包 `deepagents`，提供了一个通用的深度 Agent 框架，可以针对特定垂直领域定制。

### 安装

```bash
pip install deepagents
```

### 内置组件

| 组件 | 说明 | 灵感来源 |
|------|------|----------|
| **系统提示** | 受 Claude Code 启发，修改为通用场景 | Claude Code 的详尽提示风格 |
| **规划工具** | No-op Todo List 工具 | Claude Code 的 Todo List |
| **子 Agent 生成** | 内置生成子 Agent 的能力 | Claude Code 的子 Agent 机制 |
| **虚拟文件系统** | 用 Agent 状态 (State) 模拟文件系统 | LangGraph 的状态管理概念 |

> **关于虚拟文件系统**  
> `deepagents` 没有直接使用操作系统的文件系统，而是利用 LangGraph 的状态 (State) 概念模拟了一个"虚拟文件系统"。Agent 可以像使用真实文件系统一样读写数据，但所有内容实际存储在 Agent 的运行时状态中。这种设计避免了文件系统权限和安全问题，同时保留了文件系统作为"外部记忆"的核心价值。

### 定制接口

```
定制你的深度 Agent

┌──────────────────────────────────────────────┐
│                                              │
│  deepagents.create(                          │
│                                              │
│    prompt = "你的自定义系统提示",               │
│    ──────────────────────────────             │
│    覆盖默认提示，注入领域知识和行为规范            │
│                                              │
│    tools = [自定义工具列表],                    │
│    ──────────────────────────────             │
│    添加领域特定工具（数据库查询、API 调用等）      │
│                                              │
│    subagents = [自定义子 Agent 配置],           │
│    ──────────────────────────────             │
│    定义专门的子 Agent（代码审查、测试、部署等）    │
│                                              │
│  )                                           │
└──────────────────────────────────────────────┘
```

三个定制维度：

| 维度 | 传入内容 | 适用场景 |
|------|---------|---------|
| **自定义提示** (Custom Prompt) | 领域特定的行为指南和约束 | 让通用 Agent 变成领域专家 |
| **自定义工具** (Custom Tools) | 领域特定的外部能力 | 数据库操作、API 集成、专有系统交互 |
| **自定义子 Agent** (Custom Subagents) | 预定义的专项 Agent | 代码审查 Agent、安全检查 Agent 等 |

## 五、设计启示

### 1. 工程大于算法

深度 Agent 的核心教训：**你不需要更好的算法，你需要更好的工程**。同一个 LLM + 工具循环，通过四层工程设计（提示、规划、子 Agent、文件系统），就能从"玩具"升级为"生产力工具"。

### 2. 上下文工程是统一线索

四大特征的底层逻辑都指向同一个目标——**管理上下文**：

- 系统提示 → 在上下文中注入正确的指令
- 规划工具 → 在上下文中锚定执行计划
- 子 Agent → 通过隔离保持上下文纯净
- 文件系统 → 将上下文扩展到窗口之外

### 3. "空操作"也有巨大价值

Todo List 工具是 no-op 这一事实，是整篇文章最反直觉的洞察。它告诉我们：工具的价值不仅在于它执行了什么外部动作，更在于**调用工具这个过程本身**对 Agent 推理和上下文的影响。

### 4. 从单体到分布式

深度 Agent 的架构演化路径与微服务架构异曲同工：

```
单体 Agent                    分布式深度 Agent
┌──────────────┐              ┌──────────────┐
│              │              │  主 Agent     │
│  一个 LLM    │              │  (编排层)     │
│  做所有事    │    ──→       ├──┬──┬──┬──────┤
│              │              │子│子│子│ 文件  │
│              │              │A │B │C │ 系统  │
└──────────────┘              └──┴──┴──┴──────┘
```

## 延伸思考

1. **No-op 工具的极限在哪里？** Todo List 工具作为 no-op 就能显著提升 Agent 表现。这是否意味着还有其他"伪工具"可以发挥类似作用？比如一个"自我反思"工具、一个"不确定性评估"工具——它们不执行任何外部动作，但迫使 Agent 在上下文中留下特定类型的思考痕迹。

2. **子 Agent 的粒度如何决定？** 什么时候应该拆分子 Agent，什么时候应该让主 Agent 自己处理？拆得太细会增加协调成本和 token 开销，拆得太粗又失去了上下文隔离的优势。是否存在一个"最优拆分粒度"的启发式规则？

3. **文件系统 vs. 结构化状态：** `deepagents` 用 LangGraph 状态模拟文件系统，而 Claude Code 直接使用操作系统文件系统。这两种方式的权衡是什么？在哪些场景下虚拟文件系统更优，在哪些场景下真实文件系统不可替代？

4. **深度 Agent 的可调试性挑战：** 当一个深度 Agent 出错时——它可能在第 15 步的第 3 个子 Agent 中做出了错误决策——如何高效定位问题？深度 Agent 的调试体验是否会成为其大规模采用的瓶颈？
