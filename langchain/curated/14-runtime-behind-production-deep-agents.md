# 生产级深度 Agent 背后的运行时：线束之下的 11 层基础设施

**作者:** Sydney Runkle, Vivek Trivedy  
**来源:** [LangChain Blog](https://www.langchain.com/blog/the-runtime-behind-production-deep-agents)  
**日期:** 2026 年 4 月 20 日  
**阅读时间:** 约 18 分钟

---

> **一句话总结**  
> 一个好的线束 (Harness) 给 Agent 提供了提示词、工具和技能，但生产环境还需要持久执行、记忆、多租户、人机协作、可观测性等 11 项运行时能力 (Runtime Capabilities)。这些基础设施不在线束之内，而在线束之下。

---

## 核心要点

1. **线束 ≠ 运行时** —— 线束定义 Agent "做什么"，运行时决定 Agent "怎么活着"：崩溃恢复、状态持久化、多用户隔离，这些问题线束管不了
2. **持久执行 (Durable Execution) 是第一块基石** —— 长时运行的 Agent 必须能在进程崩溃后恢复，跨进程边界暂停和恢复，否则一次网络抖动就前功尽弃
3. **记忆分两层** —— 短期记忆 (Short-term) 活在单次对话中，随检查点而存；长期记忆 (Long-term) 活在对话之间，用 key-value 存储 + 语义搜索实现
4. **人机协作不是补丁而是一等原语** —— `interrupt()` 暂停 + `Command(resume=...)` 恢复，可以放在代码的任何位置，支持并行分支中断
5. **开源、模型无关、开放协议** —— MIT 许可，支持 MCP / A2A / Agent Protocol，不绑定任何供应商

---

## 一、线束之上 vs. 线束之下

在前面的系列文章中，我们拆解了 Agent 线束的方方面面：系统提示、工具、中间件、记忆、上下文工程。但当你真正把 Agent 部署到生产环境时，会发现**还有一整层基础设施问题**是线束本身管不了的。

> **类比理解**  
> 线束像一个厨师的食谱和厨具——定义了做什么菜、用什么工具。但运行时是这家餐厅的水电气、冷链物流、食品安全体系和排班系统。你可以有世界上最好的厨师和食谱，但如果停电了、食材断供了、同时来了 100 桌客人却没有排队系统，这家餐厅照样开不下去。

```
┌─────────────────────────────────────────────────────────┐
│                     开发者看到的                           │
│                                                         │
│   ┌───────────────────────────────────────────────────┐ │
│   │              Agent 线束 (Harness)                  │ │
│   │                                                   │ │
│   │  系统提示 · 工具 · 技能 · 中间件 · 编排逻辑         │ │
│   │  "Agent 做什么"                                   │ │
│   └───────────────────────────────────────────────────┘ │
│                         │                               │
│   ══════════════════════╪═══════════════════════════════ │
│                         │                               │
│   ┌───────────────────────────────────────────────────┐ │
│   │           运行时基础设施 (Runtime)                   │ │
│   │                                                   │ │
│   │  持久执行 · 记忆 · 多租户 · 人机协作 · 流式交互     │ │

```

> **为什么重要**  
> 从原型到生产的鸿沟，80% 不是模型或提示词的问题，而是运行时的问题。没有持久执行，Agent 崩溃了就白跑；没有多租户，你无法服务多个用户；没有人机协作，关键决策无法介入。这些能力不是"有了更好"——**没有它们，Agent 根本无法上线。**

## 三、持久执行 (Durable Execution)

### 为什么 Agent 比 API 调用更脆弱？

传统 API 请求通常在毫秒到秒级完成。Agent 可能运行数分钟甚至数小时。在这么长的时间窗口内，进程崩溃、网络中断、机器重启的概率不可忽视。

> **类比理解**  
> 普通 API 调用像寄一封信——交给邮局，几分钟后对方收到。Agent 执行像搬家——搬家公司的卡车在路上跑了三个小时，如果车半路抛锚了，你不会希望搬家公司说"不好意思，从头来"，而是希望他们换一辆卡车，从抛锚的地方继续搬。

### 核心机制

| 机制 | 说明 |
|------|------|
| **检查点 (Checkpointing)** | Agent 每执行一步，状态自动持久化到 PostgreSQL |
| **暂停 / 恢复 (Pause / Resume)** | Agent 可以跨进程边界暂停，在另一个进程中恢复执行 |
| **Worker 崩溃恢复** | Worker 进程崩溃后，新 Worker 从最近的检查点接管 |
| **可配置重试策略** | 针对不同错误类型配置不同的重试逻辑 |

```
Worker A                 PostgreSQL              Worker B
┌──────┐                ┌──────────┐            ┌──────┐
│ 执行  │──检查点 1──→  │ 状态存储  │            │      │
│ 步骤1 │               │          │            │      │
│      │──检查点 2──→  │ ✓ 步骤1  │            │      │
│ 执行  │               │ ✓ 步骤2  │            │      │
│ 步骤2 │               │          │            │      │
│      │               │          │            │      │
│  💥   │               │          │            │      │
│ 崩溃! │               │          │──恢复──→   │ 从步骤│
└──────┘               │          │            │ 2继续 │
                       └──────────┘            │ 执行  │
                                               └──────┘
```

> **为什么重要**  
> 持久执行是所有其他运行时能力的前提。没有它，记忆、人机协作、时间旅行都无从谈起——因为 Agent 的状态随时可能因一次崩溃而全部丢失。

## 四、记忆 (Memory)

### 两层记忆架构

Agent 的记忆分为两个明确的层次，解决完全不同的问题：

```
┌─────────────────────────────────────────────────────────┐
│                    Agent 记忆架构                         │
│                                                         │
│  ┌───────────────────────┐  ┌─────────────────────────┐ │
│  │    短期记忆             │  │    长期记忆               │ │
│  │    (Short-term)        │  │    (Long-term)           │ │
│  │                       │  │                         │ │
│  │  范围: 单次对话内       │  │  范围: 跨对话、跨会话     │ │
│  │  生命周期: 检查点作用域  │  │  生命周期: 永久           │ │
│  │                       │  │                         │ │
│  │  · 当前对话的消息历史   │  │  · key-value 存储        │ │
│  │  · 工具调用和结果       │  │  · 命名空间元组 (tuple)   │ │
│  │  · Agent 的中间推理     │  │  · 语义搜索 (Semantic)   │ │
│  │  · 随检查点自动持久化   │  │  · PostgreSQL 后端       │ │
│  │                       │  │  · API 可查询            │ │
│  └───────────────────────┘  └─────────────────────────┘ │
└─────────────────────────────────────────────────────────┘
```

### 短期记忆 (Short-term Memory)

短期记忆存活在单次对话中，与检查点绑定。每当 Agent 创建一个检查点，短期记忆的当前状态就被一并持久化。

这意味着：即使 Worker 崩溃，短期记忆也不会丢失——因为它已经写入了检查点。

### 长期记忆 (Long-term Memory)

长期记忆用于跨对话保持信息。它的底层是一个 key-value 存储，通过**命名空间元组 (Namespace Tuples)** 组织数据。

```
命名空间元组结构：

("user", "alice", "preferences")     → { "language": "zh", "style": "concise" }
("user", "alice", "project-context") → { "repo": "my-app", "stack": "React" }
("team", "engineering", "standards") → { "linting": "strict", "tests": "required" }
```

长期记忆还支持**语义搜索 (Semantic Search)**——不需要精确知道 key，也能通过语义相似性找到相关记忆。

> **类比理解**  
> 短期记忆像你桌上的便签纸——记着当前任务的要点，任务结束就清理掉。长期记忆像你的笔记本——记着所有项目的经验教训，随时可以翻阅。命名空间元组就是笔记本的目录结构，语义搜索就是"我记得之前遇到过类似的问题，让我翻一下"。

## 五、多租户 (Multi-tenancy)

### 三层安全架构

生产 Agent 服务多个用户。每个用户的数据必须隔离，Agent 代替用户执行操作时需要获取正确的权限，运营人员对系统的访问也需要控制。

```
┌─────────────────────────────────────────────────────┐
│                 多租户三层安全架构                      │
│                                                     │
│  第 1 层：用户数据隔离 (User Data Isolation)           │
│  ┌─────────────────────────────────────────────┐    │
│  │  认证处理器 (Auth Handler)                    │    │
│  │  确保用户 A 看不到用户 B 的数据               │    │
│  │  确保用户 A 的 Agent 只能操作用户 A 的资源     │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  第 2 层：Agent 代理授权 (Agent Auth / OAuth)          │
│  ┌─────────────────────────────────────────────┐    │
│  │  Agent 代替用户操作第三方服务时：               │    │
│  │  · OAuth 获取用户授权                         │    │
│  │  · 凭证安全存储和刷新                          │    │
│  │  · 最小权限原则                               │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  第 3 层：运营访问控制 (Operator RBAC)                 │
│  ┌─────────────────────────────────────────────┐    │
│  │  基于角色的访问控制 (RBAC)                     │    │
│  │  · 管理员可以查看所有线程                      │    │
│  │  · 普通运维只能看自己负责的 Agent               │    │
│  │  · 审计日志记录所有操作                        │    │
│  └─────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────┘
```

> **为什么重要**  
> 在原型阶段，"只有我一个人在用"所以不需要多租户。但生产环境可能同时运行数百个 Agent 实例，服务数千个用户。没有多租户，你面临的不是性能问题，而是安全事故。

## 六、人机协作 (Human-in-the-Loop)

### 两个原语

人机协作在运行时层面被简化为两个核心原语：

| 原语 | 作用 | 特点 |
|------|------|------|
| `interrupt()` | 暂停 Agent 执行，将载荷 (Payload) 发送给人类 | 可以放在代码的**任何位置** |
| `Command(resume=...)` | 人类审核后，恢复 Agent 执行并传入决策 | 接受任何 JSON 可序列化的响应 |

### 工作流程

```
Agent 代码                    人类                    Agent 继续
┌──────────────┐            ┌──────────┐           ┌──────────────┐
│  正常执行     │            │          │           │              │
│  ...         │            │  审核载荷  │           │  收到人类决策  │
│  遇到关键决策  │──interrupt──→│          │──resume──→│  根据决策     │
│  interrupt({ │   (暂停)    │  做出决策  │  (恢复)   │  继续执行     │
│    type:     │            │          │           │              │
│    "approve",│            │ Command(  │           │              │
│    action:   │            │  resume={ │           │              │
│    "delete"  │            │   ok:true │           │              │
│  })          │            │  })       │           │              │
└──────────────┘            └──────────┘           └──────────────┘
```

### 关键设计特性

**动态放置 (Dynamic Placement)**：`interrupt()` 不需要预先声明在某个固定节点。你可以在代码的任何位置、任何条件分支中调用它。

```python
# 伪代码示意
if risk_level > THRESHOLD:
    human_decision = interrupt({
        "type": "high_risk_action",
        "details": action_details,
        "risk_score": risk_level
    })
    if not human_decision["approved"]:
        return abort()
```

**并行分支中断 (Parallel Branch Interrupts)**：当多个子 Agent 并行执行时，每个分支都可以独立发起 `interrupt()`。所有中断的载荷被收集后一起呈现给人类审核。

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  子 Agent A  │     │  子 Agent B  │     │  子 Agent C  │
│  (正常执行)   │     │  (需要审核)   │     │  (需要审核)   │
│             │     │  interrupt() │     │  interrupt() │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
       │                   ▼                   ▼
       │            ┌─────────────────────────────┐
       │            │     人类审核面板              │
       │            │     · 子 Agent B 的请求       │
       │            │     · 子 Agent C 的请求       │
       │            │     (一次性审核所有中断)        │
       │            └──────────────┬──────────────┘
       │                           │ Command(resume=...)
       ▼                           ▼
┌───────────── 所有分支恢复执行 ──────────────┐
```

> **类比理解**  
> `interrupt()` 就像工厂里的"停线按钮"(Andon Cord)。任何工人在任何工位发现质量问题时都可以按下去，整条产线暂停，主管来做决策后再恢复。并行中断就像多条产线同时停线——主管在一个控制室里看到所有停线请求，一次性处理。

## 七、实时交互 (Real-time Interaction)

### 流式输出 (Streaming)

Agent 的执行可能需要几分钟。如果等执行完再返回结果，用户体验会极差。流式输出让用户实时看到 Agent 在做什么。

| 流式模式 | 说明 | 适用场景 |
|---------|------|---------|
| **状态快照 (State Snapshots)** | 每次状态变更推送完整状态 | 需要完整状态视图的前端 |
| **状态更新 (State Updates)** | 只推送变更的部分 (diff) | 高频更新、带宽敏感的场景 |
| **逐 Token 流式** | 每个 Token 生成后立即推送 | 对话式界面，实时显示打字效果 |

### 双重输入策略 (Double-Texting)

"Double-texting" 描述的是用户在 Agent 执行过程中发送了新消息的情况。不同业务场景需要不同的处理策略：

```
用户消息 1 ──→ Agent 正在处理...
用户消息 2 ──→ ? 怎么办 ?

┌──────────────────────────────────────────────────┐
│              四种 Double-Texting 策略              │
│                                                  │
│  ┌──────────┐  排队 (Enqueue)                     │
│  │ 消息 2   │  等 Agent 处理完消息 1 后，再处理消息 2│
│  │ → 排队   │  适用: 顺序敏感的工作流               │
│  └──────────┘                                     │
│                                                  │
│  ┌──────────┐  拒绝 (Reject)                      │
│  │ 消息 2   │  直接拒绝，告知用户"请等待"           │
│  │ → 丢弃   │  适用: 防止状态污染                   │
│  └──────────┘                                     │
│                                                  │
│  ┌──────────┐  中断 (Interrupt)                    │
│  │ 消息 2   │  停止当前任务，立即处理新消息           │
│  │ → 打断   │  适用: 用户改变了意图                  │
│  └──────────┘                                     │
│                                                  │
│  ┌──────────┐  回滚 (Rollback)                    │
│  │ 消息 2   │  撤销消息 1 的执行，从头处理消息 2      │
│  │ → 回滚   │  适用: 用户纠正了指令                  │
│  └──────────┘                                     │
└──────────────────────────────────────────────────┘
```

> **为什么重要**  
> 在真实用户场景中，用户不会乖乖等 Agent 处理完才说话。如果系统没有明确的 Double-texting 策略，就会出现状态不一致、丢失消息、或重复执行等混乱。

## 八、护栏 (Guardrails)

### 确定性策略，不靠提示词

护栏是在运行时层面实施的**确定性策略 (Deterministic Policies)**——用代码而非提示词来保证执行。

> **核心原则：** 合规、安全和成本控制不能依赖模型"大概率会遵守"。它们必须在代码层面 100% 执行。

| 护栏类型 | 实现方式 | 示例 |
|---------|---------|------|
| **PII 脱敏** | 中间件钩子 (Middleware Hook) | 在输入/输出中扫描并遮蔽敏感信息 |
| **工具调用限制** | 中间件钩子 | 限制单次对话中工具调用的总次数 |
| **内容审核** | 中间件钩子 | 拦截不合规内容，触发审核流程 |
| **成本控制** | 运行时策略 | Token 消耗超过预算时自动暂停 |

```
                    中间件护栏的执行位置
═══════════════════════════════════════════════════════

  用户输入 ──→ [PII 脱敏] ──→ 模型 ──→ [内容审核] ──→ 输出
                  │                         │
                  │                         │
              代码层面                   代码层面
              100% 执行                  100% 执行
              不依赖模型                  不依赖模型
```

> **类比理解**  
> 护栏像机场的安检系统。你不能靠告诉旅客"请不要携带违禁品"（提示词）来保证安全，必须用 X 光机扫描每个行李（代码检查）。模型可能遵守提示词的概率是 99%，但在 10 万次调用中，1% 的遗漏就是 1000 次安全事故。

## 九、可观测性 (Observability)

### 三大支柱

| 支柱 | 说明 | 解决的问题 |
|------|------|-----------|
| **全链路追踪 (Full Execution Tree Tracing)** | 记录 Agent 执行的每一步：模型调用、工具执行、状态变更 | "Agent 到底做了什么？" |
| **Polly AI 助手** | AI 驱动的 Trace 分析工具，自动识别故障模式 | "为什么 Agent 做错了？" |
| **在线评估 (Online Evals)** | 生产环境中持续运行评估器，捕获回归 | "Agent 是不是变差了？" |

```
Agent 执行
    │
    ├── 模型调用 #1
    │   ├── 输入: { system_prompt, user_message }
    │   ├── 输出: { tool_call: "search_docs" }
    │   └── 延迟: 1.2s, tokens: 450
    │
    ├── 工具执行: search_docs
    │   ├── 参数: { query: "..." }
    │   ├── 结果: { docs: [...] }
    │   └── 延迟: 0.3s
    │
    ├── 模型调用 #2
    │   ├── 输入: { ..., tool_result }
    │   ├── 输出: { response: "..." }
    │   └── 延迟: 2.1s, tokens: 820
    │
    └── 完成 (总延迟: 3.6s, 总 tokens: 1270)
         │
         ▼
    ┌────────────────┐     ┌────────────────┐
    │  Polly AI 分析  │     │  Online Evals  │
    │  自动识别模式   │     │  持续回归检测   │
    └────────────────┘     └────────────────┘
```

**在线评估 (Online Evals)** 特别值得关注——它不是在测试环境中跑评估套件，而是在生产环境中对每一次真实 Agent 执行持续评估。这能捕获那些只在真实用户场景中才会出现的问题。

> **为什么重要**  
> Agent 的行为是非确定性的。你不能靠上线前的测试覆盖所有情况。可观测性是 Agent 上线后唯一的"眼睛"——没有它，出了问题你连"到底发生了什么"都无法回答。

## 十、时间旅行 (Time Travel)

### 回溯、修改、分叉

时间旅行建立在检查点系统之上。因为 Agent 的每一步状态都已经被持久化，你可以：

| 操作 | 说明 | 用途 |
|------|------|------|
| **回溯 (Rewind)** | 回退到任意历史检查点 | 定位 Agent 做错决策的那一步 |
| **修改状态 (Modify State)** | 在回溯的检查点上修改 Agent 状态 | 测试"如果当时给了不同的上下文会怎样" |
| **分叉线程 (Fork Thread)** | 从任意检查点创建新的执行分支 | 不影响原执行路径，探索替代决策 |

```
原始执行:  ①──→②──→③──→④──→⑤ (错误结果)
                     │
时间旅行:            │ 回溯到检查点 ③
                     ▼
           ③' (修改状态) ──→④'──→⑤' (正确结果)
                │
                │ 或者分叉
                ▼
           ③'' (另一种修改) ──→④''──→⑤'' (探索结果)

原始线程和分叉线程独立存在，互不影响
```

> **类比理解**  
> 时间旅行就像视频游戏中的存档/读档系统。Agent 的每个检查点就是一个自动存档。当 Agent 在第 5 步犯了错误，你不需要从头开始——读取第 3 步的存档，调整参数，继续执行。你甚至可以保留多个存档分支，同时探索不同的策略。

> **为什么重要**  
> 传统调试方式是"复现问题 → 打断点 → 逐步执行"。对于运行几分钟甚至几小时的 Agent 来说，每次从头跑一遍来调试是不现实的。时间旅行让你直接跳到出问题的那一步，省去了所有重新执行的成本。

## 十一、代码执行 (Code Execution)

### 沙箱后端 (Sandbox Backends)

Agent 需要在隔离的环境中执行代码，同时还要考虑性能和安全。运行时支持多个沙箱后端：

| 沙箱后端 | 特点 |
|---------|------|
| **Daytona** | 云端开发环境 |
| **Modal** | 无服务器计算 |
| **Runloop** | 轻量级沙箱 |
| **LangSmith Sandboxes** | LangChain 原生集成 |

### 三个关键机制

```
┌─────────────────────────────────────────────────────┐
│              代码执行的三大关键机制                     │
│                                                     │
│  ┌───────────────┐                                  │
│  │  认证代理       │  Agent 需要访问外部 API 时，      │
│  │  (Auth Proxy)  │  通过代理注入凭证，避免            │
│  │               │  凭证暴露在沙箱环境中               │
│  └───────────────┘                                  │
│                                                     │
│  ┌───────────────┐                                  │
│  │  预热池         │  沙箱环境提前启动并保持待命         │
│  │  (Warm Pools)  │  消除冷启动延迟                    │
│  │               │  Agent 要执行代码时"即来即用"        │
│  └───────────────┘                                  │
│                                                     │
│  ┌───────────────┐                                  │
│  │  环境隔离       │  每个用户/Agent 实例拥有           │
│  │  (Isolation)   │  独立的沙箱环境，互不干扰           │
│  └───────────────┘                                  │
└─────────────────────────────────────────────────────┘
```

**认证代理 (Auth Proxy)** 解决了一个棘手的安全问题：Agent 运行在沙箱中执行代码时需要调用外部 API（比如数据库、第三方服务），但你不能把真实的凭证放进沙箱——因为沙箱中运行的是 Agent 生成的代码，可能存在安全风险。Auth Proxy 作为中间层，在沙箱外部持有凭证，只对经过验证的请求注入认证信息。

**预热池 (Warm Pools)** 解决了冷启动问题。如果每次 Agent 要执行代码都要从零启动一个沙箱，几秒到几十秒的等待会严重拖慢 Agent 的工作效率。预热池提前准备好一批就绪的沙箱实例，Agent 需要时直接分配。

## 十三、定时任务 (Cron)

### 有状态 vs. 无状态

定时任务有两种模式，适用于不同场景：

| 模式 | 说明 | 线程行为 | 适用场景 |
|------|------|---------|---------|
| **有状态 (Stateful)** | 每次执行使用同一个线程 | 保留历史上下文 | 持续监控、趋势追踪 |
| **无状态 (Stateless)** | 每次执行创建新线程 | 从零开始 | 定期报告生成、数据清理 |

### 实际应用

```
有状态定时任务 (同一线程)
──────────────────────────────
执行 1 ──→ 执行 2 ──→ 执行 3   同一个 Agent 实例
│ 线程 T1  │ 线程 T1  │ 线程 T1  记住之前的执行结果
                                可以做趋势比较

无状态定时任务 (新线程)
──────────────────────────────
执行 1     执行 2     执行 3    每次全新 Agent 实例
│ 线程 T1  │ 线程 T2  │ 线程 T3  互相独立
                                无状态副作用
```

**Sleep-time Compute（休眠期计算）**：在两次定时执行之间，Agent 可以进行后台计算——预处理数据、预热缓存、更新知识库。这样当正式执行触发时，Agent 已经准备好了所有需要的信息。

**监控循环 (Monitoring Loops)**：有状态定时任务的典型用例。Agent 定期检查系统状态，保留历史数据，在发现异常时发出告警。因为使用同一个线程，Agent 可以比较"今天和昨天的差异"，而不只是"现在的状态是否正常"。

> **类比理解**  
> 无状态定时任务像每天早上新雇一个保安巡逻一圈——他不知道昨天的情况，只检查当前是否正常。有状态定时任务像一个固定的保安——他知道哪扇门昨天就有问题、哪个区域最近频繁出状况，能做出更有判断力的决策。

              ┌─────────┼─────────┐

         ┌────────┐ ┌────────┐ ┌────────┐
         │时间旅行 │ │  护栏   │ │实时交互 │
         └───┬────┘ └────────┘ └────────┘
             │
         ┌───┴────┐

## 延伸思考

1. **运行时的标准化问题：** 目前每个 Agent 框架都在构建自己的运行时。是否会出现一个"Agent 运行时标准"（类似容器领域的 OCI 标准），让 Agent 可以在不同运行时之间无缝迁移？还是说运行时天然是差异化竞争的领域，标准化会扼杀创新？

2. **持久执行的成本权衡：** 每一步都做检查点意味着大量的 I/O 开销。在 Agent 执行频率极高的场景中（比如每秒处理数百个请求），如何在持久性和性能之间找到平衡？是否可以用"分级检查点"——关键步骤强制持久化，普通步骤延迟持久化？

3. **时间旅行与隐私：** 时间旅行意味着 Agent 的所有中间状态（包括用户的输入、模型的推理过程）都被永久保存。在 GDPR 等数据保护法规下，这些数据的保留和删除策略如何设计？"被遗忘权"如何与"完整执行历史"共存？

4. **从运行时到操作系统：** 如果把这 11 项能力放在一起看——进程管理（持久执行）、内存管理（记忆）、权限控制（多租户）、I/O 管理（集成）、调度（定时任务）——它们几乎就是一个操作系统的核心模块。Agent 运行时是否正在演变为"Agent 操作系统 (Agent OS)"？
