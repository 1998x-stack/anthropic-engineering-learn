# 深度 Agent 的上下文管理：让长任务 Agent 不迷路、不失忆

**作者:** LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/context-management-for-deep-agents)  
**日期:** 2026 年 4 月  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> Deep Agents 通过三层递进机制管理上下文——卸载大型工具结果 (Offloading Tool Results)、卸载大型工具输入 (Offloading Tool Inputs)、摘要化 (Summarization)——并用文件系统作为"规范记录"，使 Agent 在长会话中既保持目标意识，又能按需恢复细节。

---

## 核心要点

1. **上下文管理是三层递进防线** —— 先卸载输出、再卸载输入、最后才摘要化，每一层只在上一层不够用时触发
2. **文件系统是上下文的"规范记录" (Canonical Record)** —— 摘要替代的不是信息本身，而是信息在上下文窗口中的占用；原始内容始终完整保存在文件系统中
3. **双轨设计是核心架构模式** —— Agent 用摘要保持目标意识 (Awareness)，用文件系统恢复具体细节 (Recovery)
4. **压力测试比功能测试更重要** —— 通过人为提前触发摘要化（如在 10-20% 而非 85% 时触发），可以暴露出正常条件下隐藏的问题
5. **针对性评估胜过端到端测试** —— 用小型隔离测试验证单个上下文管理机制，比全流程测试更高效、更可归因

---

## 一、为什么深度 Agent 需要上下文管理？

深度 Agent (Deep Agents) 执行的任务不是"一问一答"，而是跨越数十甚至数百个工具调用的长链任务。在这个过程中，上下文窗口会不断累积工具的输入和输出，直到逼近容量上限。

> **类比理解**  
> 想象你在一张书桌上做一个大型研究项目。每查一份资料、每写一段笔记，文件就堆高一层。如果任由文件堆积，桌面很快被淹没——你连正在写的那页都找不到了。上下文管理就是：把暂时不用的文件归档到书架上（文件系统），桌上只放当前需要的摘要索引卡，需要时随时去书架上取。

### 三层防线的递进关系

```
上下文窗口使用率
0%                                                 100%
├─────────────────────────────────────────────────────┤

[━━━━━━━━━━━━━] 正常执行
                                 ↓ 工具返回 >20,000 tokens
[━━━━━━━━━━━━━━━━━━━━━━━━━]  → 触发 ① 卸载工具结果

                                        ↓ 达到 85% 容量
[━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━]  → 触发 ② 卸载工具输入

                                               ↓ 仍然不够
[━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━]  → 触发 ③ 摘要化
```

## 二、机制一：卸载大型工具结果 (Offloading Large Tool Results)

### 问题

工具调用返回的结果可能非常庞大。一次代码搜索可能返回数万 token 的代码片段；一次日志查询可能返回整个堆栈跟踪。如果全部保留在上下文窗口中，几次调用就能耗尽容量。

### 解法

当工具返回结果超过 **20,000 tokens** 时，Deep Agents 自动执行：

```
┌──────────────────┐         ┌──────────────────┐
│   工具执行完毕     │         │   文件系统         │
│                  │         │                  │
│   返回 50,000    │ ──写入──→│ /tmp/tool_out_   │
│   tokens 的结果  │         │ 42a7f.txt        │
│                  │         │ (完整 50,000      │
│                  │         │  tokens)         │
└────────┬─────────┘         └──────────────────┘
         │
         ▼
┌──────────────────────────────────────────────┐
│   替换进上下文窗口的内容                        │
│                                              │
│   文件路径: /tmp/tool_out_42a7f.txt           │
│   预览 (前 10 行):                            │
│   ┌────────────────────────────────────┐     │
│   │ Line 1: import torch              │     │
│   │ Line 2: from model import ...     │     │
│   │ ...                               │     │
│   │ Line 10: def forward(self, x):    │     │
│   └────────────────────────────────────┘     │
│                                              │
│   Token 占用: ~200 (原来 50,000)              │
└──────────────────────────────────────────────┘
```

### 关键设计

| 设计要素 | 说明 |
|---------|------|
| **阈值** | 20,000 tokens —— 低于此值保留原文，高于则卸载 |
| **预览** | 前 10 行 —— 给 Agent 足够线索判断是否需要深入查看 |
| **可恢复性** | Agent 可随时通过文件读取或搜索工具重新获取完整内容 |

> **为什么重要**  
> 这一层处理的是"信息洪水"问题。一个 Agent 在调试过程中可能连续调用日志查询、代码搜索、测试运行等工具，每次返回几万 token。如果不卸载，三五次调用就耗尽上下文窗口，Agent 还没开始真正工作就"满了"。

## 三、机制二：卸载大型工具输入 (Offloading Large Tool Inputs)

### 问题

工具调用不只有大输出，还有大输入。文件写入 (File Write) 和文件编辑 (File Edit) 操作会把**完整的文件内容**留在对话历史中。一个 500 行的文件被编辑 5 次，就产生 5 份完整副本——每份都占据上下文空间。

### 解法

当上下文使用率达到 **85%** 时，Deep Agents 开始截断历史中较早的工具调用，用文件指针 (File Pointer) 替换：

```
上下文窗口（85% 触发前）
┌──────────────────────────────────────────────┐
│ [消息 1] 用户: "重构 auth 模块"                │
│ [消息 2] Agent: 读取 auth.py                  │
│ [消息 3] 工具返回: auth.py 完整内容 (800 行)    │ ← 占大量空间
│ [消息 4] Agent: 编辑 auth.py                  │
│ [消息 5] 工具确认: auth.py 新内容 (850 行)      │ ← 又占大量空间
│ [消息 6] Agent: 编辑 auth.py                  │
│ [消息 7] 工具确认: auth.py 新内容 (830 行)      │ ← 第三份副本
│ ...后续消息...                                │
└──────────────────────────────────────────────┘

上下文窗口（85% 触发后）
┌──────────────────────────────────────────────┐
│ [消息 1] 用户: "重构 auth 模块"                │
│ [消息 2] Agent: 读取 auth.py                  │
│ [消息 3] → [已截断] 完整内容见: auth.py         │ ← 几个 token
│ [消息 4] Agent: 编辑 auth.py                  │
│ [消息 5] → [已截断] 完整内容见: auth.py         │ ← 几个 token
│ [消息 6] Agent: 编辑 auth.py                  │
│ [消息 7] 工具确认: auth.py 新内容 (830 行)      │ ← 保留最新版本
│ ...后续消息（完整保留）...                      │
└──────────────────────────────────────────────┘
```

### 设计要点

- **只截断较早的工具调用** —— 最近的操作保持完整，确保 Agent 知道文件的当前状态
- **文件本身始终在磁盘上** —— 截断的只是上下文窗口中的副本，Agent 随时可以重新读取
- **85% 是触发阈值** —— 给后续操作留出足够的上下文空间

> **类比理解**  
> 这就像你在文档编辑器中工作——你不需要在屏幕上同时看到文件的每一个历史版本。只需要看到当前版本，以及一个"修改记录"告诉你之前改了什么。需要的时候，点开某个版本就能看到完整内容。

## 四、机制三：摘要化 (Summarization)

当前两层机制都不足以控制上下文增长时，Deep Agents 启用最后一道防线：对整个对话历史进行摘要化。

### 双轨摘要架构

```
┌─────────────────────────────────────────────────────────┐
│                摘要化的双轨设计                             │
│                                                         │
│   轨道 A: 上下文内摘要 (In-context Summary)               │
│   ┌───────────────────────────────────────────────┐     │
│   │  LLM 生成结构化摘要，替换完整对话历史              │     │
│   │                                               │     │
│   │  摘要字段:                                     │     │
│   │  · 会话意图 (Session Intent)                   │     │
│   │  · 已创建的产出物 (Artifacts Created)           │     │
│   │  · 关键决策 (Key Decisions)                    │     │
│   │  · 下一步计划 (Next Steps)                     │     │
│   │                                               │     │
│   │  目的: 保持 Agent 的目标意识                     │     │
│   └───────────────────────────────────────────────┘     │
│                                                         │
│   轨道 B: 文件系统保留 (Filesystem Preservation)          │
│   ┌───────────────────────────────────────────────┐     │
│   │  完整的原始消息序列写入文件系统                     │     │
│   │                                               │     │
│   │  保留内容:                                     │     │
│   │  · 每一条原始消息                               │     │
│   │  · 每一次工具调用和返回                          │     │
│   │  · 完整的推理过程                               │     │
│   │                                               │     │
│   │  目的: 作为规范记录，可按需恢复                   │     │
│   └───────────────────────────────────────────────┘     │
│                                                         │
│   Agent = 摘要 (知道该做什么) + 文件系统 (能查到细节)      │
└─────────────────────────────────────────────────────────┘
```

### 摘要替换示意

```
摘要化前                           摘要化后
┌────────────────────┐            ┌────────────────────┐
│ [消息 1-80]        │            │ [结构化摘要]         │
│                    │            │                    │
│ · 用户原始请求      │            │  会话意图:           │
│ · 60 次工具调用     │  ──替换──→  │  "重构 auth 模块,   │
│ · 推理过程         │            │   提取公共逻辑"      │
│ · 中间结果         │            │                    │
│                    │            │  已完成:             │
│ ~80,000 tokens     │            │  · 拆分了 3 个文件   │
│                    │            │  · 通过 12 个测试    │
│                    │            │                    │
│                    │            │  下一步:             │
│                    │            │  · 处理错误边界      │
│                    │            │  · 运行集成测试      │
│                    │            │                    │
│                    │            │ ~500 tokens         │
├────────────────────┤            ├────────────────────┤
│ [消息 81-100]      │            │ [消息 81-100]       │
│ 最近的消息(保留原文) │            │ 最近的消息(保留原文)  │
│ ~15,000 tokens     │            │ ~15,000 tokens      │
└────────────────────┘            └────────────────────┘

原始消息 1-80 → 写入 /tmp/session_history_xxx.jsonl
(规范记录，Agent 可搜索恢复)
```

> **为什么重要**  
> 摘要化是一把双刃剑：它释放了上下文空间，但不可避免地丢失了细节。双轨设计的精妙之处在于——它承认信息损失的不可避免性，然后用文件系统作为安全网。Agent 不需要在上下文中记住所有细节，它只需要知道"细节在哪里可以找到"。

## 五、如何验证上下文管理有效？

### 5.1 压力测试 (Stress Testing)

正常条件下，摘要化在 85% 上下文使用率时才触发——这意味着大多数短任务可能永远不会触发摘要化。Bug 就藏在这些"永远不触发"的路径中。

**解法：人为降低触发阈值**

| 参数 | 正常值 | 压力测试值 | 目的 |
|------|-------|-----------|------|
| 摘要化触发阈值 | 85% | 10-20% | 强制在几乎每个任务中都触发摘要化 |

这样做的好处：

- **生成更多摘要化事件** —— 从罕见事件变成每次执行都发生，便于统计分析
- **暴露隐藏问题** —— 摘要后 Agent 是否丢失了关键目标？是否无法恢复被摘要掉的信息？

### 5.2 摘要 Prompt 配置的对比实验

摘要的质量取决于生成摘要时的 Prompt 设计。不同的字段组合会产生截然不同的效果：

```
┌──────────────────────────────────────────────────────────┐
│               摘要 Prompt 配置对比实验                       │
│                                                          │
│   配置 A (基础版)              配置 B (增强版)               │
│   ┌────────────────┐          ┌────────────────┐         │
│   │ · 对话要点      │          │ · 对话要点      │         │
│   │ · 关键决策      │          │ · 关键决策      │         │
│   │ · 已完成内容    │          │ · 已完成内容     │         │
│   │                │          │ · 会话意图 ← 新  │         │
│   │                │          │ · 下一步 ← 新    │         │
│   └────────────────┘          └────────────────┘         │
│                                                          │
│   结果: Agent 摘要后             结果: Agent 摘要后          │
│   有时忘记原始目标               始终保持目标导向              │
│   容易偏离方向                   自然过渡到下一步             │
│                                                          │
│   ★ 增加 "会话意图" 和 "下一步" 字段显著提升了摘要后的表现     │
└──────────────────────────────────────────────────────────┘
```

> **实战发现**  
> 在 Deep Agents 的实验中，在摘要 Prompt 中添加 "会话意图 (Session Intent)" 和 "下一步计划 (Next Steps)" 两个字段后，Agent 在摘要化后继续执行任务的成功率明显提升。这两个字段解决的是"目标漂移 (Goal Drift)"问题——摘要化后 Agent 知道做了什么，但忘了为什么要做、接下来该做什么。

## 六、针对性评估 (Targeted Evals)

端到端测试能告诉你"Agent 整体表现如何"，但无法告诉你"某个具体的上下文管理机制是否正常工作"。Deep Agents 设计了小型隔离测试来验证单个机制。

### 评估一：摘要化是否保留了目标？

```
测试流程:
┌──────────┐     ┌──────────────┐     ┌──────────────┐
│ 分配任务  │────→│ 任务执行到   │────→│ 强制触发     │
│          │     │ 一半         │     │ 摘要化       │
└──────────┘     └──────────────┘     └──────┬───────┘
                                             │
                                             ▼
                                      ┌──────────────┐
                                      │ 观察 Agent   │
                                      │ 是否继续原    │
                                      │ 任务目标      │
                                      └──────────────┘

通过标准:
  ✓ Agent 继续朝原始目标推进
  ✗ Agent 偏离目标或重新开始
```

### 评估二：Agent 能否恢复被摘要的信息？

这是一个 **大海捞针 (Needle-in-a-Haystack)** 测试：

```
测试流程:
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ ① 在对话早期  │────→│ ② 继续执行   │────→│ ③ 强制触发   │
│    嵌入一个   │     │    更多步骤   │     │    摘要化    │
│    特定事实   │     │    (稀释事实) │     │             │
└──────────────┘     └──────────────┘     └──────┬───────┘
                                                  │
                                                  ▼
                                           ┌──────────────┐
                                           │ ④ 要求 Agent │
                                           │    回忆该事实 │
                                           └──────────────┘

示例:
  ① 嵌入: "数据库连接超时设置为 30 秒"
  ② 执行 50 步其他操作
  ③ 触发摘要化（该事实大概率被摘要掉）
  ④ 提问: "连接超时是多少？"

通过标准:
  ✓ Agent 搜索文件系统，找到原始记录，正确回答 "30 秒"
  ✗ Agent 编造答案或说"不知道"
```

> **为什么重要**  
> 这个测试验证的是双轨设计的核心承诺：摘要化可以丢失细节，但 Agent 必须能从文件系统中恢复这些细节。如果 Agent 在摘要化后既不记得事实，也不尝试搜索恢复，那整套文件系统保留机制就形同虚设。

## 七、实践指南

### 三层机制速查表

| 机制 | 触发条件 | 替换方式 | 恢复方式 | Token 节约 |
|------|---------|---------|---------|-----------|
| 卸载工具结果 | 工具返回 >20K tokens | 文件路径 + 前 10 行预览 | Agent 读取/搜索文件 | 99%+ |
| 卸载工具输入 | 上下文达到 85% | 旧工具调用截断为文件指针 | Agent 重新读取文件 | 因任务而异 |
| 摘要化 | 前两层仍不足 | 结构化摘要替换历史 | Agent 搜索文件系统中的规范记录 | 80-95% |

### 关键实践建议

1. **从真实基准测试开始** —— 先用端到端任务建立性能基线，再去测试单个机制
2. **用压力测试暴露隐藏问题** —— 将触发阈值从 85% 降到 10-20%，让每个任务都触发摘要化
3. **对比不同的摘要 Prompt 配置** —— "会话意图"和"下一步"字段是低成本高回报的改进
4. **验证可恢复性 (Recoverability)** —— 大海捞针测试是验证文件系统保留机制的最直接方法
5. **监控目标漂移 (Goal Drift)** —— 摘要化后 Agent 是否还在朝原始目标推进，是最关键的健康指标

## 延伸思考

1. **摘要的信息损失可以量化吗？** 每次摘要化都在做有损压缩。是否可以设计一个"摘要保真度"指标——比如用原始消息生成 100 个问题，对比摘要化前后 Agent 的回答准确率？这个指标能否自动化，成为上下文管理质量的持续监控信号？

2. **三层触发阈值的最优配置：** 工具结果卸载的 20K token 阈值和输入截断的 85% 阈值是如何确定的？不同类型的任务（调试 vs 代码生成 vs 数据分析）是否需要不同的阈值组合？是否可以让 Agent 自适应地调整这些阈值？

3. **目标漂移的深层原因：** 摘要化后的目标漂移，到底是因为摘要丢失了信息，还是因为模型本身在长会话中倾向于"遗忘"初始指令？如果是后者，那仅靠改进摘要 Prompt 是否触及根本？是否需要在每次摘要化后重新注入原始用户请求？

4. **从被动管理到主动管理：** 当前的三层机制都是**被动触发**的——等到阈值才启动。能否设计一种**主动**上下文管理策略，让 Agent 在执行过程中主动判断哪些信息可以提前卸载，而不是等到空间不足时才被迫压缩？
