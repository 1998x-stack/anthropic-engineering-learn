# 用 LangSmith 调试深度 Agent (Debugging Deep Agents with LangSmith)

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/debugging-deep-agents-with-langsmith)  
**日期:** 2025 年 12 月 10 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> 深度 Agent (Deep Agent) 的调试难度与简单 LLM 应用不在一个量级——追踪树更深、提示词更长、交互轮次更多。LangSmith 通过结构化追踪、AI 辅助分析 (Polly) 和 CLI 工具三板斧，让你在复杂执行轨迹中精准定位问题。

---

## 核心要点

1. **深度 Agent 的调试复杂度来自三个维度** —— 提示词长度 (数百到数千行)、执行步骤多 (数十到数百步)、多轮人机交互 (跨小时甚至跨天)
2. **追踪数据有三层结构** —— 运行 (Run) → 追踪 (Trace) → 线程 (Thread)，层层嵌套才能完整还原 Agent 行为
3. **Polly 是用 AI 分析 AI** —— 内置的 AI 助手可以在海量追踪数据中自动发现低效行为和错误决策，解放人类的调试精力
4. **CLI 工具弥合了"看到问题"和"修复问题"之间的鸿沟** —— 从 LangSmith UI 到本地开发环境的数据流打通，让调试闭环更紧凑

## 一、深度 Agent 为什么难调试？

### 简单 LLM 应用 vs. 深度 Agent

> **类比理解**  
> 调试一个简单的 LLM 应用就像检查一封信——输入、输出，一目了然。调试一个深度 Agent 更像审计一个跨国企业的财务报表——层层子公司、上百笔交易、跨越数月的往来，你必须沿着资金链一路追踪才能找到问题出在哪里。

| 维度 | 简单 LLM 应用 | 深度 Agent |
|------|--------------|-----------|
| 提示词长度 | 几行到几十行 | 数百到数千行 |
| 执行步骤 | 1-3 步 | 数十到数百步 |
| 执行时间 | 秒级 | 分钟级甚至小时级 |
| 交互模式 | 单轮请求-响应 | 多轮、人机协作 (Human-in-the-loop) |
| 调试难度 | 检查输入输出即可 | 需要在海量步骤中定位关键决策点 |

### 三个复杂度因子

深度 Agent 的调试复杂度不是线性增长的，而是三个因子叠加后的**乘法效应**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    深度 Agent 的调试复杂度                        │
│                                                                 │
│   ┌───────────────┐   ┌───────────────┐   ┌───────────────┐    │
│   │  因子 1        │   │  因子 2        │   │  因子 3        │    │
│   │  更长的提示词   │ × │  更长的追踪    │ × │  多轮交互      │    │
│   │               │   │               │   │               │    │
│   │  数百/数千行    │   │  数十/数百步   │   │  跨小时/跨天   │    │
│   │  系统提示      │   │  分钟级执行    │   │  多次人类介入   │    │
│   └───────────────┘   └───────────────┘   └───────────────┘    │
│                                                                 │
│   调试难度 = f(提示词复杂度 × 执行深度 × 交互轮次)                  │
└─────────────────────────────────────────────────────────────────┘
```

**因子 1：更长的提示词 (Longer Prompts)**

深度 Agent 的系统提示通常包含详细的行为规范、工具使用说明、错误处理策略等。数百行的提示词意味着任何一个措辞都可能影响 Agent 的行为——但你很难事先知道是哪个措辞导致了问题。

**因子 2：更长的追踪 (Longer Traces)**

一次执行可能包含数十甚至数百个步骤，每个步骤都是一个潜在的错误源。追踪数据量巨大，人工逐步检查既耗时又容易遗漏。

**因子 3：多轮交互 (Multiple Turns)**

深度 Agent 通常涉及人机协作——人类提供反馈、确认决策、补充信息。这意味着一个完整的调试上下文可能跨越数小时甚至数天的多轮对话。

> **为什么重要**  
> 这三个因子解释了为什么传统的日志检查方法在深度 Agent 面前几乎失效。你不能靠"多打几行 print"来调试一个运行了 200 步、涉及 5 轮人机交互、提示词有 800 行的 Agent。你需要专门的工具。

## 二、追踪的三层数据结构

LangSmith 用三个层级的数据概念来组织 Agent 的执行信息：

### Run → Trace → Thread

```
Thread (线程)
│  一次完整的对话（可能跨小时/天）
│
├── Trace 1 (追踪)
│   │  Agent 的一次完整执行
│   │
│   ├── Run: LLM 调用 (系统提示 + 用户输入)
│   │   └── Run: 工具调用 (搜索文档)
│   │       └── Run: LLM 调用 (处理搜索结果)
│   │           ├── Run: 工具调用 (写入文件)
│   │           └── Run: 工具调用 (执行测试)
│   │               └── Run: LLM 调用 (分析测试结果)
│   │
│   └── ... (可能还有几十个嵌套的 Run)
│
├── Trace 2 (追踪)
│   │  用户给了新指令后 Agent 的又一次执行
│   │
│   └── ... (另一棵 Run 树)
│
└── Trace 3 (追踪)
    └── ...
```

### 三层数据概念详解

| 层级 | 英文名 | 定义 | 类比 |
|------|--------|------|------|
| **运行** | Run | 单个步骤：一次 LLM 调用或一次工具调用 | 财务报表中的一笔交易 |
| **追踪** | Trace | Agent 的一次完整执行，由嵌套的 Run 组成树状结构 | 一个季度的财务报告 |
| **线程** | Thread | 多个 Trace 的集合，代表一次完整的对话 | 一整年的财务审计 |

> **类比理解**  
> 把深度 Agent 想象成一家公司的运营。每笔交易 (Run) 单独看可能没问题，但问题可能藏在交易之间的关联中。一个季度的报告 (Trace) 能看出业务趋势，但跨季度的年度审计 (Thread) 才能发现长期的结构性问题。

**Run 的嵌套特性**尤其关键：一个 LLM 调用可能触发一个工具调用，工具调用的结果又触发下一个 LLM 调用——这些 Run 不是扁平的列表，而是一棵深度可能很大的树。理解这棵树的结构，是定位问题的第一步。

## 三、Polly——用 AI 分析 AI

### 什么是 Polly？

Polly 是 LangSmith 的内置 AI 助手，专门用于分析 Agent 的线程 (Thread) 和追踪 (Trace) 数据。它不是一个通用聊天机器人，而是一个**专门训练来阅读和分析执行轨迹的工具**。

```
┌──────────────────────────────────────────────────┐
│                    Polly                          │
│                                                  │
│   ┌──────────────┐    ┌──────────────────────┐   │
│   │  输入         │    │  输出                 │   │
│   │              │    │                      │   │
│   │  Thread 数据  │───→│  低效行为识别          │   │
│   │  Trace 数据   │    │  错误决策定位          │   │
│   │  用户问题     │    │  改进建议              │   │
│   └──────────────┘    └──────────────────────┘   │
│                                                  │
│   典型问题：                                      │
│   • "Agent 做了什么低效的事情？"                    │
│   • "Agent 犯了哪些错误？"                         │
│   • "为什么 Agent 在第 47 步选择了错误的工具？"      │
└──────────────────────────────────────────────────┘
```

### Polly 的核心价值

> **类比理解**  
> 如果追踪数据是一份 500 页的审计报告，Polly 就是你雇来的资深审计师。你不需要自己逐页翻看，只需要问"有没有可疑的地方？"，审计师会帮你圈出关键问题。

Polly 对深度 Agent 特别有价值的三个原因：

| 场景 | 人工调试的痛点 | Polly 如何解决 |
|------|--------------|---------------|
| 追踪有 200 步 | 逐步检查需要数小时 | Polly 在秒级内扫描全部步骤并定位异常 |
| 跨天的多轮对话 | 人类难以保持完整上下文 | Polly 可以访问整个 Thread 的全部信息 |
| 微妙的低效行为 | 人类容易忽略"能跑但不对" | Polly 能识别冗余步骤、重复调用、次优路径 |

### 使用示例

与 Polly 的交互非常直接：

```
你:    "这个 Agent 有没有做什么低效的事？"

Polly: "在 Trace #3 中，Agent 在步骤 12-28 之间重复查询了同一个
        API 端点 6 次，每次只是微调了查询参数。前两次就已经获得了
        足够的信息。建议在系统提示中增加'避免对同一数据源重复查询
        超过 2 次'的规则。"

你:    "Agent 犯了什么错误？"

Polly: "在 Trace #7 的步骤 45 中，Agent 将用户的'删除草稿'请求
        理解为'删除已发布的文章'。根因是系统提示中'删除'操作的
        权限描述模糊，没有区分草稿和已发布内容。"
```

> **为什么重要**  
> 深度 Agent 的执行轨迹数据量可能非常庞大。一个运行了 2 小时的 Agent，涉及 150 个步骤、5 轮人机交互，产生的追踪数据可能有数万行。人类不可能高效地从中提取洞察。Polly 把调试从"大海捞针"变成了"按图索骥"。

## 四、LangSmith Fetch CLI——打通 UI 和本地开发

### 为什么需要 CLI？

LangSmith 的 Web UI 适合可视化查看和交互式分析，但调试闭环往往需要把数据拉到本地：喂给 LLM 做进一步分析、集成到自动化脚本中、或者与本地代码对照排查。

**LangSmith Fetch CLI** 就是连接 LangSmith UI 和本地工作流的桥梁。

```
┌───────────────────┐          ┌──────────────────┐
│   LangSmith UI    │          │   本地开发环境     │
│                   │          │                  │
│   可视化追踪      │          │   代码编辑器      │
│   交互式分析      │   CLI    │   LLM 分析脚本    │
│   Polly 对话      │ ◀──────▶ │   自动化工具链    │
│                   │  桥梁    │   版本控制        │
└───────────────────┘          └──────────────────┘
```

### 两种核心工作流

#### 工作流 1："我刚跑了一个 Agent"

场景：你刚执行完一个 Agent 任务，想立刻抓取最近的执行数据进行分析。

```bash
# 获取最近 5 个线程的追踪数据
langsmith-fetch traces --project-uuid <uuid> --limit 5

# 以人类可读格式查看（适合直接阅读）
langsmith-fetch traces --project-uuid <uuid> --format human

# 以 JSON 格式导出（适合程序处理）
langsmith-fetch traces --project-uuid <uuid> --format json

# 以紧凑 JSON 格式导出（节省空间）
langsmith-fetch traces --project-uuid <uuid> --format compact-json
```

#### 工作流 2：喂给 LLM 做深度分析

场景：你需要对一批追踪数据做更深入的分析——比如跨多次执行寻找共性失败模式。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  CLI 拉取     │────→│  格式化数据   │────→│  喂给 LLM     │
│  追踪数据     │     │  (JSON)      │     │  做分析       │
└──────────────┘     └──────────────┘     └──────┬───────┘
                                                  │
                                                  ▼
                                          ┌──────────────┐
                                          │  生成改进建议  │
                                          │  修改线束/提示 │
                                          └──────────────┘
```

这种工作流的典型用法：

```bash
# 拉取追踪数据并通过管道喂给 LLM
langsmith-fetch traces --project-uuid <uuid> --format json | \
  llm "分析这些追踪数据，找出最常见的失败模式"
```

### 输出格式对比

| 格式 | 命令参数 | 适用场景 |
|------|---------|---------|
| 人类可读 | `--format human` | 手动阅读和快速排查 |
| 美化 JSON | `--format json` | 程序处理、喂给 LLM 分析 |
| 紧凑 JSON | `--format compact-json` | 大批量导出、节省存储 |

> **为什么重要**  
> 调试深度 Agent 不应该被局限在一个 Web 页面里。CLI 工具让追踪数据成为你开发工具链中流动的数据，可以被任意组合、分析和处理。这把调试从"在 UI 里看"变成了"在工作流中用"。

## 五、三板斧如何协同工作

结构化追踪、Polly 和 CLI 不是三个独立的功能，而是一个完整调试流程的三个环节：

```
┌─────────────────────────────────────────────────────────────────┐
│                  深度 Agent 调试工作流                            │
│                                                                 │
│  步骤 1: 结构化追踪                                              │
│  ┌────────────────────────────────────┐                         │
│  │  Run/Trace/Thread 自动记录         │                         │
│  │  每个决策点、每次工具调用全部捕获     │                         │
│  └──────────────────┬─────────────────┘                         │
│                     │                                           │
│                     ▼                                           │
│  步骤 2: AI 辅助分析 (Polly)                                     │
│  ┌────────────────────────────────────┐                         │
│  │  "有什么低效行为？犯了什么错误？"    │                         │
│  │  在海量数据中快速定位问题            │                         │
│  └──────────────────┬─────────────────┘                         │
│                     │                                           │
│                     ▼                                           │
│  步骤 3: CLI 拉取到本地                                          │
│  ┌────────────────────────────────────┐                         │
│  │  导出追踪数据 → 本地分析 → 修改代码  │                         │
│  │  喂给 LLM → 批量分析 → 系统性改进   │                         │
│  └────────────────────────────────────┘                         │
│                                                                 │
│  ──→ 修改线束/提示词 ──→ 重新运行 ──→ 回到步骤 1 (循环)           │
└─────────────────────────────────────────────────────────────────┘
```

## 六、实践启示

### 1. 先建追踪，后写逻辑

在开发深度 Agent 时，追踪基础设施应该是**第一个搭建的组件**，而不是"等出了问题再加"。没有追踪数据，后续的一切分析和优化都是空中楼阁。

### 2. 善用 Thread 级别的分析

很多 bug 不是在单次执行中暴露的，而是在多轮交互的上下文中积累的。如果你只看单个 Trace，可能会遗漏跨轮次的问题——比如 Agent 在第 3 轮忘记了第 1 轮用户的约束条件。

### 3. 让 AI 做第一轮筛查

不要试图自己逐步检查 200 步的追踪。用 Polly 或其他 LLM 做第一轮筛查，找出"可疑"的步骤，然后再人工深入分析这些步骤。

### 4. 把 CLI 集成到你的开发循环中

最高效的调试循环是：运行 Agent → CLI 拉取追踪 → 分析问题 → 修改代码 → 重新运行。整个循环应该在终端里完成，而不是在 Web UI 和编辑器之间反复切换。

## 延伸思考

1. **调试工具本身的可扩展性：** 当 Agent 的执行步骤从数百增长到数千，追踪数据从 MB 级增长到 GB 级时，现有的可视化和分析方法是否还能有效工作？是否需要更激进的数据压缩和摘要策略？
2. **用 AI 分析 AI 的信任问题：** Polly 本质上是用一个 LLM 来判断另一个 LLM 的行为是否正确。但 Polly 自身也可能犯错——它可能遗漏关键问题，或者把正常行为标记为异常。如何校准和验证"AI 审计师"的可靠性？
3. **从被动调试到主动预防：** 目前的工具主要是"出了问题再分析"。是否可以在 Agent 运行过程中实时监控追踪数据，当检测到已知的失败模式时主动干预——比如自动触发中间件，而不是等执行完再事后分析？
4. **跨 Agent 的追踪关联：** 当多个 Agent 协作完成一个任务时，问题可能出在 Agent 之间的交接环节。如何将不同 Agent 的追踪数据关联起来，构建一个"全局执行视图"来调试多 Agent 系统？
