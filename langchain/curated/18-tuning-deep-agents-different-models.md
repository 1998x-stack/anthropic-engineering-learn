# 为不同模型调优深度 Agent：线束配置文件 (Harness Profiles)

**作者:** Vivek Trivedy, Mason Daugherty  
**来源:** [LangChain Blog](https://www.langchain.com/blog/tuning-deep-agents-different-models)  
**日期:** 2026 年 4 月 29 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> 同一个线束 (Harness) 不可能在所有模型上都表现最优。线束配置文件 (Harness Profiles) 让你为每个模型声明式地覆盖提示词、工具和中间件，在 tau2-bench 子集上将 GPT 5.3 Codex 和 Claude Opus 4.7 的得分从 33%-43% 分别提升到 53%。

---

## 核心要点

1. **"一个线束打天下"是个幻觉** —— 不同模型的提示指南 (Prompting Guide)、工具偏好、推理风格截然不同，共用线束必然牺牲某些模型的表现
2. **同一模型在不同线束下性能差距巨大** —— Terminal Bench 2.0 证明：线束的差异比模型的差异更决定性能上限
3. **Codex 和 Opus 的最优调整方向完全不同** —— Codex 需要换工具 + 调批处理策略，Opus 需要调提示词引导反思和直接观察
4. **Harness Profiles 是声明式的** —— 一个 YAML 或 Python 注册调用，即可为特定模型覆盖系统提示、工具集、中间件和子 Agent 配置

---

## 一、为什么需要"线束配置文件"？

### 问题的本质

> **类比理解**  
> 想象你是一个赛车队的调校工程师。你的团队同时使用三台不同品牌的引擎——每台引擎的进气特性、转速范围、热管理策略都不同。如果你用同一套悬挂参数、同一个换挡策略去跑所有引擎，结果只有一台车跑得快，另外两台都在拖后腿。线束配置文件就是"针对每台引擎的调校参数卡"。

每家模型厂商都有自己的最佳实践指南：

| 厂商 | 提示指南的核心差异 |
|------|-------------------|
| **OpenAI (Codex 系列)** | 推荐使用 `apply_patch` 替代行级编辑，强调工具调用的批处理 |
| **Anthropic (Claude 系列)** | 强调"先观察再行动"，鼓励工具结果的反思性回顾 |
| **Google (Gemini 系列)** | 不同的上下文窗口管理策略和工具调用格式 |

这些差异不是细微的偏好，而是**影响任务完成率的关键变量**。

> **为什么重要**  
> 当你的 Agent 平台需要同时支持多个模型（例如让用户选择后端模型），你必须为每个模型提供定制化的线束配置。否则，用户切换模型后性能骤降，他们会以为是"模型不行"——实际上是线束不匹配。

## 三、两个模型分别改了什么？

### 3.1 GPT 5.3 Codex：换工具 + 调批处理策略

Codex 的 Profile 主要是**工具层面的改动**——根据 OpenAI 官方的提示指南，切换到 Codex 系列原生支持的工具格式。

```
Codex Profile 的核心变更
═══════════════════════════════════════════════════════

工具变更:
  file_edit ──────────→ apply_patch
  (行级编辑工具)          (补丁式编辑，Codex 原生优化)

  execute ────────────→ shell_command
  (通用执行)              (显式 shell 调用，更匹配 Codex 预训练)

提示变更:
  + 批处理指导 ──────── "当多个独立操作可并行时，批量发起工具调用"
  + 规划指导 ─────────── "先制定完整计划再开始实现，避免边做边改"
```

| 变更类型 | 旧值 | 新值 | 为什么有效 |
|---------|------|------|-----------|
| 编辑工具 | `file_edit` | `apply_patch` | Codex 的预训练数据中大量使用 patch 格式，匹配度更高 |
| 执行工具 | `execute` | `shell_command` | 更明确的工具语义减少了 Codex 的歧义性调用 |
| 批处理 | 无指导 | 显式提示 | Codex 原生支持并行工具调用，但需要提示引导才会使用 |
| 规划 | 无指导 | 显式提示 | Codex 倾向于"立刻动手"，需要提示强制先规划 |

> **类比理解**  
> 这就像给一个说英语的工人换成英文工具手册——工具没变，但说明书从中文翻译成了他的母语，操作效率立刻提升。

### 3.2 Claude Opus 4.7：调提示词引导反思

Opus 的 Profile 几乎不涉及工具变更，**核心改动全在提示层面**——引导模型改变行为习惯。

```
Opus Profile 的核心变更
═══════════════════════════════════════════════════════

提示变更 (两条新的行为指令):

  ① tool_result_reflection (工具结果反思)
  ┌──────────────────────────────────────────────┐
  │ "每次收到工具执行结果后，先花一步反思：        │
  │  结果是否符合预期？是否有异常信号？             │
  │  再决定下一步行动。"                           │
  └──────────────────────────────────────────────┘

  ② tool_usage (工具使用方式)
  ┌──────────────────────────────────────────────┐
  │ "直接通过工具观察当前状态，                     │
  │  不要凭记忆推断文件内容或环境状态。              │
  │  眼见为实，记忆不可靠。"                        │
  └──────────────────────────────────────────────┘
```

| 指令 | 解决的问题 | 效果 |
|------|-----------|------|
| **tool_result_reflection** | Opus 执行完工具后倾向于直接进入下一步，跳过对结果的分析 | 强制"停下来想想"，减少基于错误结果继续推进的情况 |
| **tool_usage** | Opus 有时会"凭记忆"推断文件内容，而不是重新读取 | 强制"眼见为实"，消除因记忆过期导致的错误 |

> **为什么重要**  
> Codex 的问题出在"工具不匹配"——解法是换工具。Opus 的问题出在"行为习惯"——解法是调提示引导反思。**同一个框架、同一个评测，两个模型的瓶颈完全不同**。这就是为什么"一个线束打天下"行不通——你必须诊断每个模型的具体弱点，然后对症下药。

## 四、Harness Profile 的工作机制

### 设计理念

Harness Profile 是一个**声明式的覆盖层 (Declarative Override Layer)**——它不需要你重写线束代码，只需要声明"对于这个模型，哪些配置需要不同"。

```
Profile 如何叠加到基础线束上
═══════════════════════════════════════════════════════════════════

  ┌────────────────────────────────────┐
  │         基础线束 (Base Harness)     │
  │                                    │
  │  系统提示:  通用编程 Agent 指令      │
  │  工具集:    file_edit, execute, ... │
  │  中间件:    LoopDetection, ...     │
  │  子 Agent:  CodeReview, ...        │
  │  技能:     Trace 分析, ...          │
  └──────────────┬─────────────────────┘
                 │
                 │  模型匹配: openai:gpt-5.3-codex
                 ▼
  ┌────────────────────────────────────┐
  │     Profile 覆盖层 (Override)       │
  │                                    │
  │  系统提示后缀:  + 批处理/规划指导    │
  │  排除工具:      file_edit, execute  │  ← 移除不适配的工具
  │  添加工具:      apply_patch, ...    │  ← 替换为原生工具
  │  排除中间件:    Summarization       │
  └──────────────┬─────────────────────┘
                 │
                 │  合并
                 ▼
  ┌────────────────────────────────────┐
  │      最终线束 (Effective Harness)   │
  │                                    │
  │  = 基础线束 + Profile 覆盖          │
  │  针对 gpt-5.3-codex 优化            │
  └────────────────────────────────────┘
```

### 代码示例

#### Python 注册方式

```python
from harness import register_harness_profile, HarnessProfile

# 为 OpenAI GPT 5.4 注册 Profile
register_harness_profile(
    "openai:gpt-5.4",  # 模型标识符: 厂商:模型名
    HarnessProfile(
        # 系统提示后缀 —— 追加到基础系统提示末尾
        system_prompt_suffix="Respond in under 100 words.",

        # 排除的工具 —— 从基础工具集中移除
        excluded_tools={"execute"},

        # 排除的中间件 —— 从基础中间件栈中移除
        excluded_middleware={"SummarizationMiddleware"},
    ),
)
```

#### YAML 声明方式

```yaml
# profiles/openai-gpt-5.4.yaml
model: "openai:gpt-5.4"
profile:
  system_prompt_prefix: |
    你是一个高效的编程助手。
    优先使用 apply_patch 进行文件编辑。
  system_prompt_suffix: |
    在回复前，确认所有文件修改都已验证。
  excluded_tools:
    - file_edit       # 替换为 apply_patch
    - execute         # 替换为 shell_command
  included_tools:
    - apply_patch
    - shell_command
  excluded_middleware:
    - SummarizationMiddleware  # Codex 的上下文窗口足够大，不需要摘要压缩
  subagents:
    code_review:
      enabled: true
      model: "openai:gpt-5.4"  # 子 Agent 也使用同一模型
```

### Profile 的可覆盖维度

| 维度 | 说明 | 典型用途 |
|------|------|---------|
| **system_prompt_prefix** | 追加到系统提示开头 | 设定模型角色和行为基调 |
| **system_prompt_suffix** | 追加到系统提示末尾 | 添加特定模型的行为指导 |
| **excluded_tools** | 从工具集中移除 | 去掉该模型不擅长的工具 |
| **included_tools** | 额外添加到工具集 | 加入该模型原生优化的工具 |
| **tool_naming** | 工具重命名映射 | 匹配模型预训练中的工具命名习惯 |
| **excluded_middleware** | 移除中间件 | 去掉对该模型不必要的干预 |
| **included_middleware** | 添加中间件 | 加入该模型特需的行为矫正 |
| **subagents** | 子 Agent 配置 | 调整子 Agent 的模型、提示和行为 |
| **skills** | 技能配置 | 启用/禁用特定技能 |

## 五、Profile 作为可共享的插件

### 社区协作模型

Profile 的声明式设计天然适合社区共享——就像 VS Code 的配置文件或 ESLint 的规则集。

```
Profile 的生态模型
═══════════════════════════════════════════════════════

  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
  │  官方默认      │     │  社区贡献      │     │  团队私有      │
  │  Profiles     │     │  Profiles     │     │  Profiles     │
  ├──────────────┤     ├──────────────┤     ├──────────────┤
  │ openai:*     │     │ mistral:*    │     │ internal:*   │
  │ anthropic:*  │     │ deepseek:*   │     │ fine-tuned:* │
  │ google:*     │     │ qwen:*       │     │              │
  └──────┬───────┘     └──────┬───────┘     └──────┬───────┘
         │                    │                    │
         └────────────────────┼────────────────────┘
                              │
                              ▼
                    ┌──────────────────┐
                    │  Profile 注册表   │
                    │  (Registry)      │
                    └──────────────────┘
```

- **官方默认 Profile：** LangChain 为 OpenAI、Anthropic、Google 三大厂商维护默认 Profile，开箱即用
- **社区贡献 Profile：** 开发者可以通过 PR 提交针对其他模型的 Profile，经过测试验证后合入
- **团队私有 Profile：** 企业可以为内部微调模型 (Fine-tuned Model) 创建私有 Profile

> **类比理解**  
> Profile 就像 Docker 的多架构镜像——同一个应用 (线束)，为不同架构 (模型) 构建不同的镜像。开发者写一次代码，运行时自动选择匹配当前架构的镜像。

## 六、实践启示

### 1. 诊断先行，调优在后

不要盲目套用别人的 Profile。先在目标模型上运行基准测试，分析 Trace，找到**该模型的具体弱点**：

- 工具调用失败率高？→ 考虑换工具
- 跳过验证步骤？→ 考虑加反思提示
- 上下文膨胀导致截断？→ 考虑加摘要中间件

### 2. 工具改动和提示改动的 ROI 不同

| 改动类型 | 适用场景 | 风险 |
|---------|---------|------|
| **工具替换** | 模型有官方推荐的工具格式 | 低——工具层的变更是确定性的 |
| **提示调整** | 模型的行为习惯需要矫正 | 中——提示的效果依赖模型的指令跟随能力 |
| **中间件增减** | 模型需要额外的行为护栏或无需某些干预 | 中——可能与其他中间件产生交互 |

### 3. Profile 需要持续维护

模型在持续迭代——GPT 5.3 的最优 Profile 不一定适用于 GPT 5.4。每次模型版本更新后，应该：

1. 用基准测试验证现有 Profile 是否仍然有效
2. 重新分析 Trace，检查是否有新的故障模式
3. 根据新版本的提示指南调整 Profile

## 延伸思考

1. **Profile 的粒度应该多细？** 当前的 Profile 是按模型标识符 (如 `openai:gpt-5.4`) 匹配的。但同一个模型在不同任务类型（编程、数据分析、文本生成）上的最优配置也可能不同。是否需要支持"模型 × 任务类型"的二维 Profile？
2. **自动 Profile 发现：** 目前 Profile 需要人工编写。能否让 Agent 通过在评测上的迭代自动发现最优 Profile？这本质上是一个超参数搜索问题——搜索空间是提示、工具和中间件的组合。
3. **Profile 之间的迁移学习：** Codex 的 Profile 发现"换工具有效"，Opus 的 Profile 发现"加反思提示有效"。当一个全新的模型出现时，能否根据已有模型的 Profile 做"冷启动"——先猜一个接近的 Profile，再微调？
4. **线束标准化的张力：** Profile 机制让每个模型都能有定制化配置，但这也意味着线束的行为变得更不可预测——切换模型可能导致完全不同的工具集和行为逻辑。如何在"定制化"和"可预测性"之间找到平衡？
