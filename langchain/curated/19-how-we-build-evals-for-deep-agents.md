# 如何为深度 Agent 构建评估：少即是多的评估工程

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-we-build-evals-for-deep-agents)  
**日期:** 2026 年 3 月 26 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 更多的评估 (Eval) ≠ 更好的 Agent。每条评估都是一个改变 Agent 行为的向量——盲目堆叠数百条测试只会制造"改进的幻觉"。正确做法是：先明确你期望 Agent 具备哪些行为，再为每种行为精心策划可验证的评估。

---

## 核心要点

1. **每条评估都是行为向量** —— 它会把 Agent 的行为推向某个方向。如果向量方向错了或互相冲突，Agent 不会变得更好，只会变得更混乱
2. **评估数据有三个来源** —— 自用反馈 (Dogfooding)、外部基准测试 (Benchmark) 的筛选子集、以及为关键行为手工编写的"匠人评估"
3. **指标优先级：先正确、后高效** —— 正确性 (Correctness) 永远第一，效率指标 (Efficiency) 如延迟、成本、冗余工具调用只在正确性达标后才有意义
4. **SDK 测试 ≠ 模型评估** —— 单元测试和集成测试验证的是代码逻辑，不提供模型能力的信号，必须严格分离
5. **评估要像代码一样管理** —— 每条评估加文档字符串 (Docstring) 说明它测量什么能力，加分类标签 (Tag) 以便按需运行子集

---

## 一、评估塑造 Agent 行为

### 核心洞察：评估是向量，不是考试

很多团队把评估当作"通过/不通过"的考试——考完拿到分数就行了。但 LangChain 的实践揭示了一个更深刻的事实：

> **每条评估都是一个向量 (Vector)，它会把 Agent 的行为推向特定方向。**

这意味着：

```
盲目堆积评估的后果
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  评估 A ──→  (推向"详细输出")
  评估 B ←──  (推向"简洁输出")
  评估 C ──→  (推向"详细输出")
  评估 D   ↑  (推向"多轮确认")
  评估 E   ↓  (推向"直接执行")

  合力 = 混乱
  Agent 行为 = 在矛盾的信号中摇摆不定

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  精心策划的评估集

  评估 1 ──→  (测量"工具选择准确性")
  评估 2 ──→  (测量"工具选择准确性")
  评估 3    ↗  (测量"并行调用能力")
  评估 4    ↗  (测量"并行调用能力")

  合力 = 清晰的优化方向
  Agent 行为 = 朝期望能力稳步提升
```

> **类比理解**  
> 想象你在训练一只导盲犬。如果你同时训练它"遇到红灯停下来"和"主人说走就走"，但从来不教它"红灯 + 主人说走 = 仍然停"，这只狗会在交叉信号中崩溃。评估也一样——**不是越多越好，而是越对越好**。每条评估都必须指向你真正期望的行为。

### 正确的做法：行为目录 (Behavior Catalog)

在编写任何评估之前，先建立一份**行为目录**——列出你希望 Agent 具备的所有行为能力，然后为每种行为设计可验证的评估：

| 期望行为 | 评估设计 | 验证方式 |
|---------|---------|---------|
| 正确选择工具 | 给定任务描述，Agent 是否选了最合适的工具？ | 精确匹配预期工具名 |
| 并行调用独立操作 | 当两个操作互不依赖时，Agent 是否一次性发起？ | 检查工具调用轮次数 |
| 错误后自我纠正 | 工具返回错误后，Agent 是否尝试修复？ | 检查轨迹中是否有重试行为 |
| 合理使用默认值 | 上下文暗示了默认参数时，Agent 是否直接使用？ | 检查是否有不必要的追问 |

> **为什么重要**  
> 没有行为目录，评估会在"覆盖率焦虑"驱动下无限膨胀——你会不断添加测试用例，但越加越不确定 Agent 到底在哪些方面变好了、哪些方面变差了。行为目录让你从"我有多少条评估"转向"我的每种目标行为是否被覆盖"。

### 给评估加文档和标签

每条评估不是一个黑盒测试，而是一份**可读的行为规格**。LangChain 的做法是：

```python
@eval(
    category=["tool_use", "parallel_calls"],
    capability="Agent should parallelize independent tool calls"
)
def test_parallel_file_reads():
    """
    测量能力: 并行工具调用 (Parallel Tool Calls)
    
    场景: 要求 Agent 同时读取三个互不依赖的文件
    预期: Agent 在一个轮次中发起三个 read_file 调用，
          而非串行发起三个轮次
    
    失败意味着: Agent 没有识别出操作的独立性，
               或模型不支持并行工具调用
    """
    # 评估实现...
```

这样做有两个关键好处：

1. **可审查性** —— 任何团队成员看到这条评估，都能立刻理解它在测量什么、为什么重要、失败意味着什么
2. **可筛选性** —— 通过标签按需运行子集，避免每次都跑完整评估集

## 二、如何策划评估数据

### 三大来源

评估数据不是凭空编造的。LangChain 使用三种互补的来源，各有其独特价值：

```
评估数据的三大来源
═══════════════════════════════════════════════════════════════

  ① 自用反馈 (Dogfooding)
  ┌─────────────────────────────────────────────┐
  │ 团队每天使用自己构建的 Agent               │
  │ 每一次错误、每一次意外行为                   │
  │ 都是一条评估用例的种子                      │
  │                                             │
  │ 优势: 来自真实使用场景，贴近生产环境         │
  │ 原则: "自己吃自己的狗粮"                    │
  └─────────────────────────────────────────────┘

  ② 外部基准测试的筛选子集 (Selected Benchmarks)
  ┌─────────────────────────────────────────────┐
  │ Terminal Bench 2.0, BFCL 等公开基准测试      │
  │ 不是照搬全集，而是挑选与自己 Agent 相关的子集 │
  │                                             │
  │ 优势: 覆盖面广，有社区共识                   │
  │ 关键: 必须适配到自己的 Agent 配置上           │
  └─────────────────────────────────────────────┘

  ③ 手工编写的"匠人评估" (Artisanal Evals)
  ┌─────────────────────────────────────────────┐
  │ 针对特别重要的行为手工构造的评估              │
  │ 通常覆盖关键路径和已知的边界情况              │
  │                                             │
  │ 优势: 精确度最高，最贴合期望行为              │
  │ 适用: 核心功能、安全相关、已知陷阱            │
  └─────────────────────────────────────────────┘
```

> **类比理解**  
> 这三种来源就像厨师获取食谱的三种方式：自己做菜时发现的技巧 (Dogfooding)、参考米其林标准 (Benchmark)、以及为招牌菜精心研发的独门配方 (Artisanal)。只用一种来源，菜单会有明显的盲区。

### 关键分离：SDK 测试 vs 模型评估

这是很多团队容易犯的错误：**把 SDK 的单元测试和集成测试混入模型评估集中**。

```
必须严格分离的两类测试
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  SDK 单元 / 集成测试              模型能力评估
  ─────────────────              ────────────
  测试代码逻辑是否正确              测试模型行为是否符合预期
  输入/输出确定性                  输入确定，输出带有随机性
  跑一次就够                      需要多次采样评估稳定性
  对模型评分零贡献                 是优化线束的唯一信号

  ✗ 混在一起 → 评估集膨胀，但新增信号为零
  ✓ 分开管理 → 模型评估集精简，每条都有信号价值
```

> **为什么重要**  
> 单元测试验证的是"你的代码写对了吗"，模型评估验证的是"模型在你的线束下表现好吗"。前者对模型评分没有任何信号价值。如果你的评估集里 60% 是单元测试，那你的评估分数有 60% 是噪声。

### 用轨迹分析驱动覆盖率

仅仅收集评估数据不够——你还需要**理解失败模式 (Failure Modes)**。LangChain 使用 Polly 或 Insights 等工具，在规模化轨迹 (Trace) 分析中完成这个闭环：

```
轨迹分析闭环
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Agent 运行 ──→ 产生轨迹 (Trace)
       │
       ▼
  Polly/Insights 分析轨迹
       │
       ├──→ 发现失败模式 ──→ 提出修复方案
       │                        │
       │                        ▼
       │                   修改线束 / 提示词
       │                        │
       │                        ▼
       └──────────────── 重新运行 ──→ 追踪进展
```

目标不是"跑分"，而是一个有方向感的改进循环：**理解为什么失败 → 提出假设 → 验证假设 → 确认改进**。

## 三、如何定义评估指标

### 优先级：正确性第一，效率第二

指标设计有一个不可颠倒的优先级：

```
指标优先级金字塔
═══════════════════════════════

         ┌─────┐
         │效率  │  ← 只在正确性达标后才有意义
         │指标  │
        ─┤     ├─
       / └─────┘ \
      /           \
     ┌─────────────┐
     │  正确性指标   │  ← 永远第一
     │             │
     └─────────────┘
```

### 正确性指标 (Correctness Metrics)

正确性回答的核心问题是："Agent 做对了吗？" 根据任务性质，验证方式不同：

| 验证方式 | 适用场景 | 示例 |
|---------|---------|------|
| **自定义断言 (Custom Assertions)** | 输出有明确结构 | 检查生成的代码是否包含特定函数签名 |
| **精确匹配 (Exact Matching)** | 输出有唯一正确答案 | 检查数学计算结果是否等于 42 |
| **LLM-as-Judge (语义判断)** | 输出有多种正确表达 | 让另一个 LLM 判断回答是否语义等价于参考答案 |

> **类比理解**  
> 正确性指标就像考试的标准答案——可以有多种出题方式（选择题、填空题、论述题），但核心目标都是"答对了没有"。

### 效率指标 (Efficiency Metrics)

在正确性达标的前提下，效率指标衡量 Agent 是否"聪明地"完成了任务：

| 效率维度 | 测量内容 | 什么算"差" |
|---------|---------|-----------|
| **最少必要工具调用** | Agent 用了几次工具调用完成任务？ | 能一次完成的操作分成了三次 |
| **并行化独立调用** | 互不依赖的工具调用是否并行发起？ | 串行调用了五个独立的文件读取 |
| **无冗余中间轮次** | 是否有不必要的"自言自语"或重复操作？ | 读完文件后又读了一遍同一个文件 |
| **延迟与成本** | 端到端耗时和 Token 消耗量 | 简单任务耗费了大量 Token |

```
效率评估示例：文件搜索任务
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✗ 低效执行 (7 步)

  Step 1: read_file("a.py")         ← 串行
  Step 2: read_file("b.py")         ← 可以并行
  Step 3: read_file("c.py")         ← 可以并行
  Step 4: read_file("a.py")         ← 重复读取！
  Step 5: search("keyword")
  Step 6: read_file("d.py")
  Step 7: 输出结果

  ✓ 高效执行 (3 步)

  Step 1: read_file("a.py") + read_file("b.py") + read_file("c.py")
          ↑ 并行调用
  Step 2: search("keyword") → read_file("d.py")
  Step 3: 输出结果
```

> **为什么重要**  
> 一个"正确但低效"的 Agent 在原型阶段可以接受，但在生产环境中会带来巨额的 Token 成本和用户等待时间。效率指标帮你在正确性达标后继续优化，让 Agent 从"能用"进化到"好用"。

## 四、如何运行评估

### 基础设施：pytest + CI

LangChain 的评估运行基于 pytest 和 GitHub Actions，这意味着评估被当作"一等公民"集成到了持续集成 (CI) 流水线中：

```
评估运行架构
═══════════════════════════════════════════════════════════

  开发者提交代码
       │
       ▼
  GitHub Actions 触发 CI
       │
       ▼
  pytest 运行评估子集
       │
       ├── 每条评估创建一个独立的 Deep Agent 实例
       │   配置特定的模型、工具、提示词
       │
       ├── 通过标签 (Tag) 选择运行哪些评估
       │   避免每次都跑完整集合（节省成本）
       │
       └── 输出: 通过/失败 + 轨迹日志
```

### 按标签运行子集

标签系统让你可以精确控制运行哪些评估，而不是"全部跑一遍"：

```bash
# 只运行文件操作和工具使用类的评估
uv run pytest tests/evals \
    --eval-category file_operations \
    --eval-category tool_use \
    --model baseten:nvidia/zai-org/GLM-5

# 只运行正确性相关的评估（快速验证核心功能）
uv run pytest tests/evals \
    --eval-category correctness

# 运行全部评估（发版前）
uv run pytest tests/evals
```

> **为什么重要**  
> 完整评估集可能需要数百次 LLM 调用，成本和时间都不容忽视。标签系统让你在日常开发中只跑相关子集，在发版前才跑完整集合——就像单元测试和端到端测试的关系。

### 每条评估 = 一个独立的 Agent 实例

这是一个重要的设计决策：每条评估都创建一个全新的 Deep Agent 实例，配置特定的参数：

```python
def test_file_creation():
    """Agent 应该能够创建文件并写入内容"""
    agent = DeepAgent(
        model="anthropic:claude-sonnet-4-6",
        tools=["file_write", "file_read"],
        system_prompt="你是一个文件操作助手。",
    )
    result = agent.run("创建一个名为 hello.txt 的文件，内容为 'Hello World'")
    
    assert file_exists("hello.txt")
    assert read_file("hello.txt") == "Hello World"
```

这确保了：

- **隔离性** —— 评估之间互不影响，不会因为执行顺序产生偶发失败
- **可复现性** —— 同样的配置可以在任何环境中重现
- **灵活性** —— 不同评估可以使用不同的模型和配置

### 开源架构

整套评估架构已经在 Deep Agents 仓库中开源，任何团队都可以直接复用或基于它定制自己的评估流水线。

## 五、方法论总结：评估工程的核心原则

```
评估工程的四个步骤
═══════════════════════════════════════════════════════════════════

  ① 定义行为           ② 策划数据           ③ 设计指标          ④ 集成运行
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ 列出期望行为  │   │ Dogfooding   │   │ 正确性优先    │   │ pytest + CI  │
│ 建立行为目录  │ → │ Benchmark    │ → │ 效率次之      │ → │ 标签筛选     │
│ 拒绝"越多越好"│   │ Artisanal    │   │ 分离 SDK 测试 │   │ 独立实例     │
│              │   │ 分离 SDK 测试│   │              │   │ 开源架构     │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

### 常见误区对照表

| 误区 | 正确做法 | 为什么 |
|------|---------|-------|
| 评估越多越好 | 每条评估必须对应一个明确的期望行为 | 互相矛盾的评估会让 Agent 行为退化 |
| 照搬外部 Benchmark 全集 | 筛选与自己 Agent 相关的子集并适配 | 不相关的评估只增加成本，不增加信号 |
| 单元测试混入模型评估 | 严格分离 SDK 测试和模型能力评估 | 单元测试对模型评分无信号价值 |
| 只看通过率 | 分析失败轨迹，理解失败模式 | 通过率是结果，失败模式是原因 |
| 每次跑全集 | 用标签按需运行子集 | 节省成本和时间，提高迭代速度 |
| 评估是只读的 | 定期审查、更新、补充评估 | 模型和线束在演进，评估也必须跟上 |

## 延伸思考

1. **评估集的"向量冲突"检测：** 当评估集规模增长后，不同评估之间可能产生隐含的行为冲突（例如一条评估鼓励详细解释，另一条惩罚冗长输出）。是否可以构建自动化工具来检测评估集内部的向量冲突？这类似于软件工程中的"需求矛盾检测"。
2. **Dogfooding 的选择偏差：** 团队自用产生的评估数据天然偏向团队自己的使用模式。如何确保评估集也覆盖与团队习惯不同的用户行为？是否需要引入"对抗性 Dogfooding"——刻意以非常规方式使用 Agent？
3. **LLM-as-Judge 的递归问题：** 当使用 LLM 来判断另一个 LLM 的输出是否正确时，判断者自身的错误如何控制？如果 Judge 模型和被评估模型有相同的盲区，评估可能系统性地忽略某类错误。是否需要多个不同架构的 Judge 模型交叉验证？
4. **效率指标的基线问题：** "最少必要工具调用"的"最少"如何定义？对于复杂任务，最优工具调用序列可能本身就不确定。是否可以用人类专家的执行轨迹作为效率基线，还是说人类轨迹也未必是最优的？
