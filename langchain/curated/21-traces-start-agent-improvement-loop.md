# Agent 改进循环从追踪开始 (The Agent Improvement Loop Starts with a Trace)

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/the-agent-improvement-loop-starts-with-a-trace)  
**日期:** 2026 年 3 月 31 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> "在传统软件中，代码记录应用；在 AI 中，追踪 (Trace) 记录应用。"——Harrison Chase。追踪是 Agent 改进循环的原材料：原始追踪记录"发生了什么"，经过评分和标注的富化追踪 (Enriched Trace) 告诉你"该怎么办"。五步闭环将每一次生产失败转化为永久性测试用例，让 Agent 越跑越强。

---

## 核心要点

1. **追踪之于 Agent，等同于源代码之于传统应用** —— 代码只告诉你 Agent *能*做什么，追踪告诉你它*实际*做了什么
2. **原始追踪 ≠ 可行动信号** —— 必须经过在线评估器 (Online Evaluator) 和人工标注的富化，才能驱动改进
3. **五步改进循环形成正反馈** —— 构建 → 预发布观察 → 离线评估 → 部署 → 生产观察，每一圈都让测试套件更厚实
4. **在线评估 + 离线评估缺一不可** —— 在线捕捉漂移，离线做受控实验；两者共同构成安全网
5. **编码 Agent 可以加入循环** —— LangSmith CLI + Skills 让 Claude Code 在评估集上从 17% 跃升到 92%

## 一、追踪是 Agent 改进的原材料

### 传统应用 vs. Agent 系统

在传统软件中，**源代码**是应用行为的权威记录——你读代码就能知道它做了什么。但 Agent 系统不一样：代码只定义了 Agent 的**能力边界**（可以调用哪些工具、可以执行哪些工作流），真正的行为记录藏在**追踪 (Trace)** 里。

> **类比理解**  
> 代码就像一个厨师的全部菜谱——它告诉你这个厨师*会做*哪些菜。但如果你想知道今天午餐他*实际做了*什么、用了多少盐、炒了几分钟、有没有把菜烧糊——你需要的是厨房监控录像，也就是追踪。

一条追踪捕获的是 Agent 一次完整执行的全部轨迹：

| 追踪包含的内容 | 示例 |
|--------------|------|
| LLM 调用 | 每次向模型发送的 prompt 和返回的 completion |
| 工具调用 (Tool Invocation) | 调用了哪个工具、传入什么参数、返回什么结果 |
| 检索步骤 (Retrieval) | 查询了哪些文档、检索到了什么内容 |
| 中间输出 | 每一步的推理结果、决策分支 |
| 决策序列 | Agent 在多步执行中的选择路径 |

### 原始追踪 vs. 富化追踪

这里有一个关键区分：

```
原始追踪 (Raw Trace)              富化追踪 (Enriched Trace)
┌──────────────────────┐          ┌──────────────────────┐
│                      │          │                      │
│  记录"发生了什么"     │          │  记录"发生了什么"     │
│                      │   ───►   │  + 评分 (Scores)     │
│  ✓ 完整执行轨迹      │   评估    │  + 标注 (Annotations)│
│  ✗ 没有质量判断      │   & 标注  │  + 改进建议          │
│                      │          │                      │
└──────────────────────┘          └──────────────────────┘
      可以观察                          可以行动
```

> **为什么重要**  
> 团队常犯的错误是收集了大量追踪数据却不做富化——它们只是静静地躺在数据库里。原始追踪就像未冲洗的胶卷：信息都在，但你看不到画面。只有经过评分和标注，追踪才变成可以驱动改进的"行动信号"。

## 二、Agent 改进循环：五步闭环

Agent 的持续改进不是临时抱佛脚式的"出了 bug 就修"，而是一个结构化的五步循环：

```
         ┌──────────────────┐
         │ 1. 构建与改进     │  审查负面评分的追踪
         │    Build         │  从观测行为倒推修复方案
         └────────┬─────────┘
                  │
                  ▼
         ┌──────────────────┐
         │ 2. 预发布观察     │  在 Staging 环境中检查
         │    Observe       │  修复是否真正生效
         │    (预生产)       │
         └────────┬─────────┘
                  │
                  ▼
         ┌──────────────────┐
         │ 3. 离线评估       │  富化追踪 → 可复现测试用例
         │    Offline Evals │  前后对比，通过 → 进入永久测试套件
         └────────┬─────────┘
                  │
                  ▼
         ┌──────────────────┐
         │ 4. 部署          │  发布修复
         │    Deploy        │  新追踪开始累积
         └────────┬─────────┘
                  │
                  ▼
         ┌──────────────────┐
         │ 5. 生产观察       │  每次运行产生追踪
         │    Observe       │──────────┐
         │    (生产)        │          │
         └──────────────────┘          │
                  ▲                    │
                  └────────────────────┘
                   发现新问题 → 回到第 1 步
```

### 每一步在做什么

| 步骤 | 输入 | 核心动作 | 输出 |
|------|------|---------|------|
| **1. 构建与改进** | 带负面评分的追踪 | 审查失败案例，倒推根因，修改代码 | 修复补丁 |
| **2. 预发布观察** | Staging 环境的追踪 | 验证修复是否解决了原始问题 | 确认/打回 |
| **3. 离线评估** | 富化追踪 → 测试用例 | 前后对比，确认无退化 | 通过的评估进入永久测试套件 |
| **4. 部署** | 通过评估的修复 | 发布到生产 | 新版 Agent 上线 |
| **5. 生产观察** | 生产环境中的新追踪 | 在线评估器自动打分 | 新的富化追踪 → 回到第 1 步 |

> **类比理解**  
> 这个循环就像医院的持续质量改进 (CQI) 流程：发现不良事件 (负面追踪) → 做根因分析 (审查追踪) → 制定改进措施 (修复) → 试点验证 (Staging) → 全面推行 (部署) → 继续监测 (生产观察)。每一次不良事件最终都变成一条新的检查清单项，让系统越来越安全。

## 三、LangSmith 如何自动生成追踪数据

手动审查每一条生产追踪显然不现实。LangSmith 通过**在线评估器 (Online Evaluator)** 自动为生产追踪打分，实现规模化的数据富化。

### 两种打分方法

| 方法 | 适用场景 | 工作原理 | 优点 | 局限 |
|------|---------|---------|------|------|
| **LLM-as-Judge** | 定性判断 | 用另一个 LLM 评估目标 LLM 的输出 | 灵活、可评估开放式质量 | 需要校准、有成本 |
| **代码检查 (Code-based)** | 确定性规则 | 用代码逻辑判断对错 | 精确、零推理成本 | 只能覆盖可形式化的规则 |

#### LLM-as-Judge 的典型评估维度

```
┌─────────────────────────────────────────────────┐
│              LLM-as-Judge 评估维度               │
├─────────────────────────────────────────────────┤
│                                                 │
│  ✦ 有用性 (Helpfulness)                         │
│    → 回答是否真正解决了用户的问题？               │
│                                                 │
│  ✦ 语气 (Tone)                                  │
│    → 是否符合品牌调性和场景要求？                 │
│                                                 │
│  ✦ 相关性 (Relevance)                           │
│    → 是否紧扣用户意图，没有跑题？                 │
│                                                 │
│  ✦ 政策合规 (Policy Adherence)                  │
│    → 是否遵守业务规则和安全策略？                 │
│                                                 │
└─────────────────────────────────────────────────┘
```

#### 代码检查的典型规则

- **Schema 验证：** 输出是否符合预期的 JSON 格式？
- **精确匹配：** 关键字段是否与期望值一致？
- **业务规则：** 金额是否在允许范围内？日期格式是否正确？

> **实践建议**  
> 两种方法不是二选一，而是互补的。先用代码检查覆盖所有可形式化的规则（成本低、精度高），再用 LLM-as-Judge 覆盖那些无法用代码表达的质量维度。

## 四、自动化的边界：人类判断不可替代

### 在线评估器覆盖不了的场景

有些行为的好坏**无法被自动化评估器判断**——它需要领域专业知识 (Domain Expertise)：

- **法律引用：** Agent 引用的法条是否适用于当前案情？
- **医学指导：** Agent 给出的建议是否符合最新临床指南？
- **金融合规：** 投资建议是否违反了特定地区的监管规定？

对于这些场景，LangSmith 提供了**标注队列 (Annotation Queue)** 机制——将需要人工审查的追踪自动路由给合适的审查者。

### 标注队列的四种用法

| 用法 | 目标 | 谁来做 |
|------|------|--------|
| **1. 校准在线评估器** | 让 LLM-as-Judge 的打分对齐人类判断 | 领域专家 |
| **2. 创建离线评估的真值数据集** | 为离线评估提供"标准答案" | 领域专家 |
| **3. 为开放式输出打分** | 评估无法自动判断的创意性或策略性回答 | 通用审查者 + 领域专家 |
| **4. 自然语言标注** | 写下观察和建议，供洞察 Agent (Insights Agent) 分析 | 所有审查者 |

### 两类审查者

```
┌─────────────────────────────────────────────────────────┐
│                    审查者分工                             │
│                                                         │
│  通用审查者 (General Reviewer)                           │
│  ├── 关注点：表面质量                                    │
│  ├── 判断内容：回答是否流畅？格式是否正确？逻辑是否自洽？  │
│  └── 不需要特定领域知识                                   │
│                                                         │
│  领域专家 (Domain Expert)                                │
│  ├── 关注点：上下文正确性                                │
│  ├── 判断内容：法律引用是否准确？医学建议是否安全？         │
│  └── 需要深厚的行业经验                                   │
│                                                         │
│  二者互补: 通用审查者过滤明显问题，领域专家聚焦深层判断    │
└─────────────────────────────────────────────────────────┘
```

> **为什么重要**  
> 自动化评估器和人工审查不是竞争关系，而是层叠关系。自动化先筛掉 80% 的明确通过/失败案例，人工只需聚焦剩下 20% 的模糊地带。这把专家时间花在了刀刃上。

## 五、富化追踪能告诉你什么

### 从个案到模式

单条追踪告诉你一个具体的失败。但真正的洞察来自**跨多条追踪的模式级理解 (Pattern-level Understanding)**。

> **类比理解**  
> 一个病人发烧可能是感冒、也可能是感染。但如果一个病房里 20 个病人同时发烧——这是系统性问题，不是个案。追踪分析也是如此：个案可能是噪声，模式才是信号。

### 追踪揭示的常见问题及修复方向

| 追踪中观察到的模式 | 根因 | 修复方向 |
|------------------|------|---------|
| Agent 反复选错工具 | 工具描述 (Tool Description) 不清晰 | 重写工具描述，明确适用场景和限制 |
| 推理过程逐步偏离目标 | 推理漂移 (Reasoning Drift) | 用约束型提示 (Constrained Prompt) 限制推理路径 |
| 输出正确但不符合用户意图 | 对"好"的定义不明确 | 在 prompt 中显式定义什么算"好的回答" |
| 检索到了不相关的文档 | 检索策略有误 | 优化嵌入模型或调整检索参数 |

> **关键原则**  
> 修复方向取决于追踪揭示的具体模式，而不是凭直觉猜测。不同的模式指向不同的可调节面——这就是为什么必须先观察追踪，再决定改什么。

## 六、将生产失败转化为离线评估

每一个生产中发现的失败模式，都应该被**永久性地编码为评估用例**。这确保了同一类问题不会在未来版本中重新出现。

### 两种编码方式

```
方式一：真值正确性 (Ground Truth Correctness)
═══════════════════════════════════════════
输入:  用户查询 + 上下文
期望:  人工标注的正确输出
评估:  Agent 输出 vs. 标注答案
指标:  精确匹配 / 语义相似度

方式二：标准化评分 (Criteria-based Scoring)
═══════════════════════════════════════════
输入:  用户查询 + 上下文
评分标准:  从审查者标注中提炼的评分维度
评估:  LLM-as-Judge 按标准打分
指标:  各维度得分 + 总分
```

| 编码方式 | 适用场景 | 优点 | 成本 |
|---------|---------|------|------|
| **真值正确性** | 有明确正确答案的任务 | 评估精确 | 需要人工标注"正确答案" |
| **标准化评分** | 开放式/创意性任务 | 灵活、可覆盖主观质量 | 需要设计评分标准 |

> **铁律：每一个失败模式一旦被编码为评估用例，就永久留在测试套件中。** 测试套件只增不减——这是 Agent 质量的棘轮机制 (Ratchet)。

## 七、在线评估 + 离线评估 = 完整安全网

在线评估和离线评估不是替代关系，而是各司其职：

| 维度 | 在线评估 (Online Eval) | 离线评估 (Offline Eval) |
|------|----------------------|----------------------|
| **运行时机** | 生产环境中实时运行 | 代码变更后、部署前运行 |
| **核心目标** | 监控实时行为，捕捉漂移 (Drift) | 受控实验，验证修复不引入退化 |
| **数据来源** | 真实用户流量 | 累积的测试套件 |
| **反馈速度** | 持续的 | 批量的 |
| **发现的问题类型** | 新出现的、未预期的问题 | 已知问题是否被修复、旧问题是否复发 |

```
部署前                                    部署后
┌─────────────────────────┐              ┌─────────────────────────┐
│      离线评估            │              │      在线评估            │
│                         │              │                         │
│  累积测试套件            │              │  生产追踪               │
│       │                 │              │       │                 │
│       ▼                 │              │       ▼                 │
│  运行全部评估            │   ──部署──►  │  在线评估器自动打分      │
│       │                 │              │       │                 │
│       ▼                 │              │       ▼                 │
│  全部通过？              │              │  发现异常？              │
│  Y → 允许部署           │              │  Y → 进入标注队列        │
│  N → 阻断部署           │              │      → 新评估用例        │
│                         │              │      → 回到离线套件      │
└─────────────────────────┘              └─────────────────────────┘
```

> **核心理念：每一次代码变更在发布前都必须通过累积的全部评估用例。** 测试套件就像一面越来越密的筛网——早期可能只有 10 个用例，几个月后可能有 500 个。每一个曾经出过的问题都不会被遗忘。

## 八、编码 Agent 也能加入改进循环

### 一个惊人的数据

LangSmith CLI + Skills 赋予 Claude Code 对追踪数据的访问能力后，其在评估集上的通过率从 **17% 跃升到 92%**。

```
Claude Code 评估集表现

无追踪访问   ████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  17%

(CLI+Skills)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 为什么有效

当编码 Agent 可以访问追踪数据时，它的工作方式就像一个**资深工程师做 Code Review**：

1. **阅读失败追踪**——理解具体的失败场景和执行路径
2. **识别模式**——跨多条追踪发现系统性问题
3. **生成修复**——基于对问题的理解编写补丁
4. **验证修复**——在评估集上确认补丁有效

> **为什么重要**  
> 这意味着 Agent 改进循环本身也可以被（部分）自动化。编码 Agent 不是替代人类工程师，而是充当一个"永不疲倦的初级工程师"——它可以处理大量重复性的追踪分析和修复工作，让人类工程师聚焦在更高层次的架构决策上。

## 延伸思考

1. **追踪的粒度选择：** 追踪记录得越详细，信息量越大，但存储和分析成本也越高。对于一个日均处理百万级请求的 Agent 系统，如何在追踪粒度和成本之间找到平衡？是全量追踪还是采样追踪？采样策略对改进循环的有效性有什么影响？

2. **在线评估器的失效模式：** LLM-as-Judge 本身也是一个 LLM，它的判断可能随模型版本更新而漂移。如何检测"评估器本身开始变差"？是否需要一个"评估评估器的评估器"？这个递归问题有没有务实的终止条件？

3. **跨 Agent 的追踪关联：** 当一个复杂系统由多个 Agent 协作完成任务时，单个 Agent 的追踪只反映局部行为。如何将多个 Agent 的追踪关联起来，构建端到端的改进循环？这是否需要类似分布式追踪 (Distributed Tracing) 中 trace-id 传播的机制？

4. **编码 Agent 参与改进循环的安全边界：** Claude Code 在评估集上的表现令人印象深刻，但让 Agent 自己修复 Agent 存在"自我参照"风险——如果修复本身引入了新的、更隐蔽的问题怎么办？编码 Agent 的自主权应该止于哪里，人类审查应该从哪里介入？
