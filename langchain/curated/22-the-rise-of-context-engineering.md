# "上下文工程"的崛起 (The Rise of "Context Engineering")

**作者:** Harrison Chase  
**来源:** [LangChain Blog](https://blog.langchain.dev/the-rise-of-context-engineering/)  
**日期:** 2026 年 5 月  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> 上下文工程 (Context Engineering) 不是"写好提示词"那么简单——它是构建**动态系统**，在正确的时机、以正确的格式，为 LLM 提供恰当的信息和工具，使其能够合理地完成任务。这个定义来自 Harrison Chase 对 Tobi Lutke、Ankur Goyal、Walden Yan 等人观点的综合提炼。

---

## 核心要点

1. **上下文不是一段话，而是一个系统** —— 开发者指令、用户输入、历史对话、工具调用结果、外部数据，五类来源共同构成上下文
2. **静态提示词已死** —— 上下文必须根据任务状态动态组装，每一步看到的信息都不同
3. **格式和内容同等重要** —— 一条简短的错误消息远比一个巨大的 JSON blob 更有效
4. **工具也是上下文的一部分** —— 不只是"给 LLM 信息"，还要给它"获取信息和执行动作的能力"
5. **"能否合理完成"是判断标准** —— 区分"模型不行"和"上下文没给够"是诊断 Agent 失败的第一步

---

## 一、什么是上下文工程？

Harrison Chase 给出的定义：

> **Context Engineering = 构建动态系统，以正确的格式提供正确的信息和工具，使 LLM 能够合理地完成任务。**

这个定义的每一个词都有讲究。Chase 将其拆解为六个关键方面：

```
┌────────────────────────────────────────────────────────────────┐
│              上下文工程定义的六个关键方面                          │
│                                                                │
│  ① 它是一个系统        上下文不是一个静态字符串，               │
│     (System)           而是由多个来源动态汇聚的产物              │
│                                                                │
│  ② 系统是动态的        不是写好一个 prompt 就完了，              │
│     (Dynamic)          而是每一步都在重新组装上下文              │
│                                                                │
│  ③ 正确的信息          垃圾进，垃圾出——                        │
│     (Right Info)       缺失或错误的信息直接导致失败              │
│                                                                │
│  ④ 正确的工具          LLM 需要的不只是信息，                   │
│     (Right Tools)      还需要查询信息和执行动作的能力            │
│                                                                │
│  ⑤ 正确的格式          同样的信息，格式不同效果天差地别；        │
│     (Right Format)     短错误消息 >> 大 JSON blob               │
│                                                                │
│  ⑥ "能合理完成"        这是最终判断标准——                      │
│     (Plausibly)        区分失败是模型问题还是上下文问题          │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

> **类比理解**  
> 想象你在指挥一个远程团队完成一个项目。上下文工程就像你作为项目经理的全部工作：不只是写一封漂亮的邮件（提示词工程），而是搭建整个信息系统——确保每个人在每个阶段都能看到他需要的文档、联系到他需要联系的人、使用到他需要的工具。信息太少做不了事，信息太多淹没关键细节，格式混乱导致误解。

## 二、上下文从哪里来？

上下文不是一个单一来源，而是多个来源的动态汇聚：

| 上下文来源 | 英文术语 | 示例 |
|-----------|---------|------|
| 开发者编写的指令 | Developer Instructions | 系统提示词、规则文件、工具描述 |
| 用户输入 | User Input | 当前对话中的问题和需求 |
| 历史交互 | Previous Interactions | 对话历史、跨会话记忆 |
| 工具调用结果 | Tool Call Results | API 返回值、数据库查询结果 |
| 外部数据 | External Data | 检索到的文档、知识库内容 |

```
开发者指令        用户输入        历史交互        工具结果        外部数据
    │               │              │              │              │
    ▼               ▼              ▼              ▼              ▼
┌───────────────────────────────────────────────────────────────────┐
│                                                                   │
│                    上下文组装系统 (Context Assembly)                │
│                                                                   │
│    根据当前任务状态，动态决定：                                      │
│    · 哪些来源参与？                                                 │
│    · 各取多少信息？                                                 │
│    · 以什么格式呈现？                                               │
│    · 暴露哪些工具？                                                 │
│                                                                   │
└───────────────────────────────┬───────────────────────────────────┘
                                │
                                ▼
                    ┌───────────────────────┐
                    │   LLM 上下文窗口       │
                    │   (精心组装的结果)      │
                    └───────────────────────┘
```

> **为什么重要**  
> 大多数 Agent 失败的根本原因不是"模型不够聪明"，而是**没有给模型足够的上下文来完成任务**。当你调试 Agent 时，第一个问题应该是："上下文里有没有它完成任务所需要的全部信息？"——答案往往是"没有"。

## 三、上下文工程 vs. 提示词工程

这是最容易混淆的概念。Chase 的观点很明确：**提示词工程 (Prompt Engineering) 是上下文工程的一个子集**。

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│              上下文工程 (Context Engineering)              │
│                                                          │
│  ┌─────────────────────────────────────┐                 │
│  │                                     │                 │
│  │  · 工具使用 (Tool Use)              │                 │
│  │  · 短期记忆 (Short-term Memory)     │                 │
│  │  · 长期记忆 (Long-term Memory)      │                 │
│  │  · 检索 (Retrieval / RAG)           │                 │
│  │  · 动态上下文组装                    │                 │
│  │  · 格式优化                         │                 │
│  │                                     │                 │
│  │  ┌───────────────────────────┐      │                 │
│  │  │                           │      │                 │
│  │  │  提示词工程                │      │                 │
│  │  │  (Prompt Engineering)     │      │                 │
│  │  │                           │      │                 │
│  │  │  · 措辞优化               │      │                 │
│  │  │  · Few-shot 示例          │      │                 │
│  │  │  · 思维链引导             │      │                 │
│  │  │                           │      │                 │
│  │  └───────────────────────────┘      │                 │
│  │                                     │                 │
│  └─────────────────────────────────────┘                 │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

| 维度 | 提示词工程 (Prompt Engineering) | 上下文工程 (Context Engineering) |
|------|-------------------------------|-------------------------------|
| 关注点 | **措辞**——怎么问更好 | **系统**——怎么组装完整的输入 |
| 范围 | 单一输入的优化 | 多来源数据的动态编排 |
| 静态/动态 | 大多是静态模板 | 必须是动态系统 |
| 目标 | 让模型"更好地理解" | 让模型"有足够信息去完成" |
| 技术含量 | 偏文案技巧 | 偏系统架构 |

> **类比理解**  
> 如果把 LLM 比作一个新员工，提示词工程是**怎么给他写任务说明**（措辞清晰、结构分明），上下文工程是**怎么搭建他的整个工作环境**——包括任务说明，但也包括他的电脑里装了什么软件、他能联系哪些同事、他的文件柜里有哪些参考资料、他的工位上摆着哪些当前项目的文件。你不能只写一封漂亮的邮件就期望新员工搞定一切。

## 四、"能否合理完成"——诊断 Agent 失败的分界线

Chase 特别强调定义中"能合理完成 (plausibly accomplish)"这个词。它提供了一个清晰的失败诊断框架：

```
Agent 任务失败
      │
      ├──→ 上下文中包含了完成任务所需的全部信息？
      │         │
      │         ├── 是 → 模型问题 (Model Issue)
      │         │        · 模型推理能力不足
      │         │        · 模型不遵循指令
      │         │        · 需要更强的模型或微调
      │         │
      │         └── 否 → 上下文问题 (Context Issue)
      │                  · 缺少关键信息
      │                  · 信息格式不对
      │                  · 没有提供必要的工具
      │                  · 信息过多导致干扰
      │
      └──→ 现实中：大多数时候是上下文问题
```

> **为什么重要**  
> 很多团队在 Agent 出错时的第一反应是"换个更好的模型"。但 Chase 指出，**更多时候问题出在上下文**——缺少了关键信息，或者信息以错误的格式呈现。这个判断标准帮你避免在模型层面浪费时间，转而去修真正的问题。

## 五、格式为什么重要

上下文工程不只是"把信息塞进去"，**怎么塞**同样关键。

| 场景 | 差的格式 | 好的格式 | 为什么 |
|------|---------|---------|--------|
| API 错误 | 返回完整的 500 错误页面 HTML (数千 token) | `"Error 500: Database connection timeout"` (几个 token) | 关键信息被噪音淹没 |
| 搜索结果 | 返回 10 篇完整文档 | 返回 10 条摘要 + 最相关的段落 | 减少干扰，突出重点 |
| 工具描述 | 30 行冗长描述 | 5 行精准描述 + 2 个示例 | 模型更容易选择正确工具 |

> **类比理解**  
> 短错误消息 vs. 大 JSON blob 的区别，就像医生看病历和看原始 CT 影像数据的区别。病历是结构化的、提炼过的、直指核心问题的。原始 CT 数据虽然信息更"完整"，但没人能在 5 秒内从中提取诊断信息。

│  │             │ │  Memory)    │ │  Memory)    │               │
│  │ 让 LLM 能   │ │ 当前会话内   │ │ 跨会话持久   │               │
│  │ 调用外部 API │ │ 的状态保持   │ │ 化的知识     │               │

│  └──────────────────┘ └──────────────────┘                      │

每种实践都在回答一个问题：

| 实践 | 回答的核心问题 |
|------|--------------|

| 短期记忆 | "这次对话中之前发生了什么？" |
| 长期记忆 | "这个用户/项目在之前的对话中说过什么？" |
| 提示词工程 | "怎么措辞才能让 LLM 更准确地理解任务？" |
| 检索 | "哪些外部知识与当前任务相关？" |

## 七、LangGraph 如何支撑上下文工程

Chase 引用了 Dex Horthy 的 "12 Factor Agents" 理念，强调上下文工程需要**对每一步都有完全的控制权 (Full Control)**。

LangGraph 提供这种控制的方式：

```
LangGraph 的上下文工程控制点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  步骤编排                    你决定哪些步骤运行、以什么顺序
       │
       ▼
  上下文组装                   你决定每一步 LLM 看到什么内容
       │
       ▼
  输出路由                     你决定 LLM 的输出存到哪里
       │
       ▼
  工具选择                     你决定每一步暴露哪些工具
       │
       ▼
  全局状态管理                  你管理跨步骤的持久化状态

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **为什么重要**  
> 很多 Agent 框架把编排抽象掉了——你只需定义工具和提示词，框架自动决定怎么跑。这在简单场景下很方便，但在复杂场景下你就失去了精细控制上下文的能力。LangGraph 的设计哲学是：**你拥有每一步的完全控制权**——决定什么信息进入 LLM、什么工具暴露给 LLM、输出存储在哪里。这恰恰是上下文工程的基础。

## 八、用追踪调试上下文工程

上下文工程的难点之一是**不可见性**——你很难知道 LLM 在某一步实际看到了什么。Chase 指出 LangSmith 的追踪 (Tracing) 功能正是为此而生。

```
追踪解决的调试问题
┌─────────────────────────────────────────────────────┐
│                                                     │
│  问题 1: 上下文包含了必要的信息吗？                    │
│  ──────────────────────────────────                  │
│  追踪让你看到 Agent 每一步的完整 LLM 输入，           │
│  直接检查关键信息是否在上下文中                        │
│                                                     │
│  问题 2: 工具是否可用？                               │
│  ──────────────────────                              │
│  追踪显示每一步暴露了哪些工具，                        │
│  以及模型选择了哪个、为什么选择                        │
│                                                     │
│  问题 3: 格式对吗？                                   │
│  ──────────────                                      │
│  追踪让你看到工具返回值的原始内容，                    │
│  判断是否需要做格式优化                               │
│                                                     │
│  问题 4: 是上下文问题还是模型问题？                    │
│  ────────────────────────────────                    │
│  如果上下文完整且格式合理但模型仍出错 → 模型问题       │
│  如果上下文有缺陷 → 上下文工程问题                    │
│                                                     │
└─────────────────────────────────────────────────────┘
```

> **类比理解**  
> 追踪之于上下文工程，就像 X 光之于骨科诊断。没有 X 光，你只能根据病人"这里疼"来猜测是不是骨折。有了 X 光，你直接看到骨骼的状态。追踪让你"看到" LLM 在每一步实际处理的上下文，而不是猜测它看到了什么。

## 九、"通信即一切" (Communication is All You Need)

Chase 以这个致敬 Transformer 论文标题的表述作结：上下文工程正在成为 Agent 构建者**最重要的技能**。

这个判断的逻辑链条是：

```
LLM 的能力 ≈ 固定（对于给定模型）
      │
      ▼
Agent 的表现 = f(模型能力, 上下文质量)
      │
      ▼
模型能力固定时，上下文质量决定成败
      │
      ▼
上下文工程 = Agent 构建者能控制的最大杠杆
```

## 延伸思考

1. **从个人技能到系统能力：** 上下文工程目前严重依赖工程师的经验和直觉——知道什么时候该给 LLM 更多信息、什么时候该精简。未来是否会出现自动化的上下文工程工具，能够根据任务特征自动决定最优的上下文组装策略？

2. **上下文工程的评估困境：** 我们如何衡量"上下文工程做得好不好"？一个可能的方向是：给定一个固定模型，对比不同上下文组装策略在同一评估集上的表现差异。但这本身就是一个复杂的实验设计问题。

3. **格式优化的极限：** Chase 强调格式很重要（短错误消息 >> 大 JSON blob），但最优格式因模型而异。当模型升级换代时，之前精心优化的格式可能不再是最优的。如何构建格式优化策略，使其对模型变化具有鲁棒性？

4. **上下文工程与 Agent 安全：** 动态上下文组装意味着 LLM 在运行时看到的内容是不可预测的。如果外部数据源被注入恶意内容（间接提示注入，Indirect Prompt Injection），动态系统可能会把这些内容当作"正确信息"喂给模型。上下文工程如何在动态性和安全性之间取得平衡？
