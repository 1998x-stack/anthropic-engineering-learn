**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/from-traces-to-insights-understanding-agent-behavior-at-scale)  
**日期:** 2026 年 1 月 20 日  
**阅读时间:** 约 12 分钟

---

> **一句话总结**  
> 你无法预测 Agent 的行为——它不是传统软件，不能靠测试覆盖一切。你需要的是生产级分析能力 (Production Analytics)：不仅要知道"发生了什么"，更要从海量非结构化对话中自动发现你从未想过要找的模式。LangSmith 的洞察 Agent (Insights Agent) 通过聚类分析 (Clustering) 将这一切变成可能。

---

## 核心要点

1. **Agent 行为不可预测** —— 非确定性、提示敏感性、无界输入空间三大特性，让传统测试方法在 Agent 面前失效
2. **传统分析指标必要但不充分** —— 延迟、反馈、工具调用次数告诉你"发生了什么"，但无法揭示"为什么"
3. **在线评估只能回答已知问题** —— 你无法为尚未发现的模式编写评估器
4. **Agent 分析需要新范式** —— 从"聚合离散事件"转向"分析非结构化对话、发现未知模式、规模化浮现聚类"
5. **聚类分析是突破口** —— 自动从追踪中发现分层模式，将定量信号与定性分析结合

---

## 一、为什么你无法预测 Agent 的行为

### 传统软件 vs. Agent 系统：三个根本差异

传统软件工程的核心假设是：给定输入，行为可预测、可复现、可测试。Agent 系统打破了这三条假设中的每一条。

| 差异 | 传统软件 | Agent 系统 |
|------|---------|-----------|
| **确定性** | 相同输入 → 相同输出 | 相同输入 → 不同执行路径 |
| **输入敏感性** | 结构化输入，边界清晰 | 微小的措辞变化 → 截然不同的行为 |
| **输入空间** | 有限、可枚举（UI 表单、API 参数） | 无界——自然语言的所有可能表达 |

#### 1. 非确定性 (Non-determinism)

传统软件中，同一个 HTTP 请求打到同一个版本的服务，返回的结果是一样的。但 Agent 不同：给它完全相同的用户输入，它可能选择不同的工具、走不同的推理路径、生成不同的回复。

```
传统软件                          Agent 系统

输入 A ──► 输出 X                输入 A ──► 工具调用 1 → 推理 → 输出 X
输入 A ──► 输出 X                输入 A ──► 工具调用 2 → 搜索 → 输出 Y
输入 A ──► 输出 X                输入 A ──► 直接回复 → 输出 Z
     确定性                            非确定性
```

> **类比理解**  
> 传统软件像自动贩卖机——按 A3 永远掉出可乐。Agent 像一个真人店员——你说"来杯饮料"，他可能给你可乐、也可能给你果汁，取决于他当时的"推理链"怎么展开。同样的请求，不同的执行路径。

#### 2. 提示敏感性 (Prompt Sensitivity)

在传统软件中，把 `userId=123` 改成 `userId= 123`（多一个空格）不会改变行为。但在 Agent 系统中，用户输入的微小变化可能导致输出的剧烈变化。

```
"帮我总结这篇文章"     →  生成摘要，3 段话
"帮我简单总结这篇文章"  →  生成 1 句话
"帮我详细总结这篇文章"  →  生成 2 页长文 + 要点列表
"总结文章"            →  不确定哪篇文章，反问用户
```

一个词的差异——"简单"vs"详细"——导致了输出长度 10 倍的差异。这种敏感性让你不可能通过有限的测试用例覆盖所有可能的行为变体。

#### 3. 无界输入空间 (Unbounded Input Space)

传统软件的输入空间是由 UI 和 API 定义的——下拉菜单有 5 个选项，文本框有长度限制，日期选择器只接受合法日期。你可以枚举所有有效输入，甚至可以做到 100% 的边界测试。

Agent 的输入是自然语言。自然语言的输入空间是**事实上无限的**。

```
传统软件输入空间                     Agent 输入空间

┌──────────────────┐               ┌──────────────────────────────┐
│  ☐ 选项 A        │               │                              │
│  ☐ 选项 B        │               │  "帮我写一封邮件..."          │
│  ☐ 选项 C        │               │  "用莎士比亚风格写邮件..."     │
│                  │               │  "假装你是 CEO 写邮件..."     │
│  [数量: ___]     │               │  "不要用任何标点写邮件..."     │
│  [日期: ____]    │               │  "用 emoji 替代所有名词..."   │
│                  │               │  "把上次的邮件改短一点..."     │
│  有限、可枚举     │               │  ...（无限可能）              │
└──────────────────┘               └──────────────────────────────┘
```

> **为什么重要**  
> 这三个差异叠加在一起，意味着一件事：**你不可能在部署前通过测试覆盖 Agent 的所有行为**。传统软件可以在 CI 中达到高测试覆盖率，然后有信心地部署。Agent 系统必须接受一个现实——大多数有意义的失败模式只会在生产环境中浮现。

## 二、你需要生产级分析

### 传统软件的安全网在 Agent 面前失效

传统软件的质量保障模型是**前置的**：

```
传统软件质量保障

开发 → 单元测试 → 集成测试 → E2E 测试 → 部署
                                          │
                                          ▼
                                    大多数 bug
                                    已在此前被捕获
```

这个模型假设：如果测试通过了，生产环境大概率不会出问题。这个假设对传统软件基本成立——因为行为是确定性的、输入空间是有限的。

但对 Agent 系统，这个假设崩塌了：

```
Agent 系统质量保障

开发 → 有限测试 → 部署
                   │
                   ▼
             大多数有意义的失败
             在这里才首次出现

原因:
 ✗ 非确定性 → 同一测试用例下次可能通过
 ✗ 无界输入 → 测试只覆盖了用户表达的冰山一角
 ✗ 提示敏感 → 真实用户的措辞远比测试用例多样
```

自然语言意味着用户意图的表达方式近乎无限。每一种表达方式都可能触发不同的 Agent 行为。你的测试套件不管多大，都只是这个无限空间中的一个微小子集。

> **类比理解**  
> 传统软件质量保障像出厂前的质检——每辆车都按检查清单逐项检验，通过了就上路。Agent 质量保障更像道路安全监控——你不可能在出厂时模拟所有路况、天气、驾驶员行为，你必须在真实道路上持续监测，才能发现那些出厂检验覆盖不到的问题。

## 三、传统分析指标：必要但不充分

### 你已经在追踪的指标

大多数团队在部署 Agent 后，已经开始追踪一些基础指标：

| 指标类型 | 具体指标 | 告诉你什么 |
|---------|---------|-----------|
| **用户反馈** | 点赞/点踩、NPS、满意度评分 | 用户对结果是否满意 |
| **延迟** | 首次响应时间、端到端耗时 | 系统是否够快 |
| **工具调用** | 调用次数、成功率、耗时 | 工具使用是否正常 |
| **成本** | Token 消耗、API 调用次数 | 运行成本是否可控 |

这些指标回答的是 **"WHAT"** 问题——发生了什么。

### 它们回答不了的问题

但它们无法回答 **"WHY"** 问题：

```
WHAT (传统指标能回答)           WHY (传统指标回答不了)
──────────────────────         ──────────────────────────
用户给了差评                    差评的根因是什么？
                                ├── 回答错误？
                                ├── 回答正确但风格不合适？
                                ├── 工具调用失败导致信息不全？
                                └── 用户期望与 Agent 能力不匹配？

延迟飙升到 30 秒               为什么慢了？
                                ├── 模型推理时间长？
                                ├── 工具调用超时？
                                ├── Agent 在做无效循环？
                                └── 检索返回了太多无关文档？

工具 A 调用失败率 15%           为什么失败？
                                ├── 传参格式错误？
                                ├── 工具描述导致错误调用？
                                ├── 上下文缺失导致参数不完整？
                                └── 并发限制触发限流？
```

### 在线评估 (Online Evals) 能帮上一部分忙

在线评估器可以在每条生产追踪上自动运行，回答一些预定义的质量问题：

| 评估类型 | 它在问什么 | 示例 |
|---------|-----------|------|
| **情绪检测** | 用户是否表现出沮丧？ | "用户措辞是否包含负面情绪信号" |
| **主题标签** | 这次对话属于什么领域？ | "退款请求"、"技术支持"、"产品咨询" |
| **成功标准** | Agent 是否完成了目标任务？ | "用户的核心问题是否得到了解答" |
| **合规检查** | 是否违反了业务规则？ | "是否承诺了超出权限的退款" |

这些都是**已知问题**的检测器。它们非常有价值——但有一个根本性的局限：

> **你无法为尚未发现的模式编写评估器。**

如果你不知道"用户正在大量尝试用 Agent 做 X 但 Agent 根本不支持 X"，你不会想到去写一个检测"X 类请求"的评估器。在你发现这个模式之前，这些请求只是噪声中的隐形信号。

## 四、Agent 分析需要新范式

### 传统分析 vs. Agent 分析

传统数据分析的方法论建立在一个前提上：**事件是结构化的、离散的、可聚合的**。

```
传统分析                              Agent 分析
──────────────────────                ──────────────────────────

数据类型:  结构化事件                  数据类型:  非结构化对话
           (点击、购买、注册)                     (自然语言交互)

分析方法:  聚合离散事件                分析方法:  理解对话语义
           漏斗分析                              发现未知模式
           A/B 测试                              规模化聚类
           转化率                                层次化洞察

核心假设:  你知道要找什么               核心假设:  你不知道要找什么
           (预定义指标和维度)                     (模式需要被发现)
```

| 维度 | 传统分析 | Agent 分析 |
|------|---------|-----------|
| **输入数据** | 结构化事件日志 | 非结构化对话追踪 |
| **分析目标** | 验证已知假设 | 发现未知模式 |
| **方法** | 聚合、过滤、分组 | 语义聚类、层次化分解 |
| **规模处理** | SQL 查询、仪表盘 | LLM 驱动的批量分析 |
| **发现模式** | 需要人工假设在先 | 自动浮现 (Emergence) |

> **类比理解**  
> 传统分析像拿着一张清单去超市——你知道要买什么，逐项勾选。Agent 分析像一个侦探到达犯罪现场——你不知道发生了什么，你需要从散落的线索中**拼出故事**。你不能预设结论，你必须让证据自己说话。

### 三大需求缺口

把传统分析方法直接套用到 Agent 系统上，会留下三个关键缺口：

```
┌───────────────────────────────────────────────────────────────┐
│                  Agent 分析的三大需求缺口                       │
│                                                               │
│  1. 分析非结构化对话                                           │
│     ├── 传统: 分析 click_event、purchase_event                │
│     └── Agent: 分析 "用户说了什么、Agent 怎么回应、              │
│              对话如何展开、最终是否解决问题"                      │
│                                                               │
│  2. 发现未知模式                                               │
│     ├── 传统: 预定义指标 → 构建仪表盘 → 监控异常               │
│     └── Agent: 你不知道该监控什么 → 需要模式自动浮现            │
│                                                               │
│  3. 规模化浮现聚类                                             │
│     ├── 传统: GROUP BY + COUNT 就够了                          │
│     └── Agent: 需要语义理解才能把"相似但措辞不同"               │
│              的对话归到同一类                                   │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

> **为什么重要**  
> 如果你只用传统分析方法监控 Agent，你能看到的只是冰山一角——那些你已经知道要看的指标。水面下的、你不知道要找的模式，才是最可能导致系统性失败的部分。你需要一种分析方法，能把你不知道的东西**主动找出来**。

## 五、LangSmith 洞察 Agent (Insights Agent)

### 核心机制：聚类分析

LangSmith 的洞察 Agent 使用**聚类 (Clustering)** 技术自动从追踪数据中发现模式。它不需要你预定义"要找什么"——它自己找。

工作流程：

```
输入                     处理                        输出
──────                  ──────                      ──────

生产追踪           ┌──────────────┐           层次化报告
(大量对话记录)  ──► │  聚类分析     │ ──►      (Hierarchical Report)
                   │  Clustering  │
                   └──────────────┘
                         │
                         ▼
                   ┌──────────────────────────────────────┐
                   │                                      │
                   │  顶层聚类 (Top-level Clusters)        │
                   │  ├── 聚类 A: "退款相关请求" (35%)     │
                   │  │   ├── 子聚类 A1: 订单取消          │
                   │  │   ├── 子聚类 A2: 部分退款          │
                   │  │   └── 子聚类 A3: 退款政策咨询      │
                   │  ├── 聚类 B: "技术故障排查" (28%)     │
                   │  │   ├── 子聚类 B1: 登录问题          │
                   │  │   └── 子聚类 B2: 支付失败          │
                   │  └── 聚类 C: "功能探索" (22%)        │
                   │      ├── 子聚类 C1: 高级功能咨询      │
                   │      └── 子聚类 C2: 集成配置          │
                   │                                      │
                   └──────────────────────────────────────┘
```

报告的三层结构：

| 层级 | 内容 | 示例 |
|------|------|------|
| **顶层聚类** | 宏观模式分类 | "退款请求占 35%，技术问题占 28%" |
| **详细分组** | 每个聚类内的细分 | "退款请求中，60% 是订单取消，25% 是部分退款" |
| **个体运行** | 具体的追踪实例 | "用户 #4523 的退款对话，Agent 错误引用了旧政策" |

### 两个最常见的使用场景

#### 场景一："用户到底在怎么用我的 Agent？"

这个问题看起来简单，但传统方法很难回答。你不能靠主题标签——因为你不知道有哪些主题。你不能靠关键词搜索——因为用户的表达千变万化。

洞察 Agent 通过聚类自动回答这个问题：

```
提问: "用户在怎么用我的 Agent？"

聚类结果:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
聚类 1: 数据查询 (38%)     ██████████████████████░░░░░
聚类 2: 报告生成 (24%)     ████████████░░░░░░░░░░░░░░
聚类 3: 流程自动化 (18%)   █████████░░░░░░░░░░░░░░░░░
聚类 4: 学习/探索 (12%)    ██████░░░░░░░░░░░░░░░░░░░░
聚类 5: 非预期用途 (8%)    ████░░░░░░░░░░░░░░░░░░░░░░
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

洞察: 38% 的用户把 Agent 当数据查询工具用
      但你设计它的初衷是流程自动化
      → 是否应该强化数据查询能力？
```

#### 场景二："我的 Agent 可能在哪些地方失败？"

这个问题更关键。你可以过滤出带有负面反馈的运行记录，然后让洞察 Agent 只分析这个子集：

```
过滤条件: 仅包含 thumbs-down 反馈的运行

聚类结果:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
失败聚类 1: "工具选择错误" (42%)
  → Agent 在面对多步骤任务时，倾向于选择单步工具
  → 修复方向: 优化工具描述，明确多步骤场景

失败聚类 2: "过度谨慎" (31%)
  → Agent 在有能力回答时仍然拒绝，引用安全策略
  → 修复方向: 调整安全护栏的阈值

失败聚类 3: "上下文丢失" (27%)
  → 多轮对话中 Agent 忘记了早期的关键信息
  → 修复方向: 改进记忆管理策略
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 传统的 bug 追踪像拿着放大镜一个一个看——每次只能看到一个 bug。洞察 Agent 的聚类分析像航拍——你一次看到整个地形，哪里是高地、哪里是洼地、哪里有河流，一目了然。你第一次能看到**全局模式**，而不只是个案。

### 灵活配置

洞察 Agent 不局限于固定的分析模板。你可以配置任意的分析提示 (Prompt)，引导它关注特定维度：

| 配置方式 | 示例 | 效果 |
|---------|------|------|
| **自定义分析提示** | "分析用户在哪些场景下切换到人工客服" | 聚焦特定的逃逸模式 |
| **过滤运行条件** | 仅分析差评反馈、仅分析特定时间段 | 缩小分析范围 |
| **组合定量与定性** | 聚类结果 + 具体追踪的逐步分析 | 既看到模式，也看到细节 |

### 定量信号 + 定性分析

洞察 Agent 的核心优势在于**将两种分析模式融合**：

```
┌──────────────────────────────────────────────────────────┐
│                  定量 + 定性融合分析                       │
│                                                          │
│  定量信号 (Quantitative)                                  │
│  ├── "42% 的失败与工具选择有关"                            │
│  ├── "差评集中在多步骤任务场景"                             │
│  └── "平均失败对话比成功对话长 3.2 倍"                     │
│                                                          │
│          ┌──────────────┐                                │
│          │  融合         │                                │
│          │  Synthesis   │                                │
│          └──────┬───────┘                                │
│                 │                                        │
│  定性分析 (Qualitative)                                   │
│  ├── "工具选择错误的根因是工具描述中缺少                    │
│  │    '适用于多步骤流程'的说明"                             │
│  ├── "用户在第 3-4 轮对话后开始表现出明显沮丧"              │
│  └── "Agent 在检索失败后倾向于编造答案而非承认不知道"        │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

> **为什么重要**  
> 纯定量分析告诉你"42% 的失败与工具选择有关"——这是一个数字。纯定性分析告诉你"这条追踪里 Agent 选错了工具"——这是一个案例。融合分析告诉你"42% 的工具选择错误源于同一个根因：工具描述缺少多步骤场景说明"——这是一个**可操作的改进方向**。

## 六、从洞察到行动：闭环改进

聚类分析的价值不在于生成报告，而在于驱动改进。一个完整的洞察驱动改进闭环：

```
┌──────────────────────────────────────────────────────────────┐
│                   洞察驱动的改进闭环                           │
│                                                              │
│  1. 收集追踪                                                 │
│     生产 Agent → 积累追踪数据                                 │
│          │                                                   │
│          ▼                                                   │
│  2. 聚类发现                                                 │
│     洞察 Agent → 自动识别模式                                 │
│          │                                                   │
│          ▼                                                   │
│  3. 根因定位                                                 │
│     逐层下钻: 顶层聚类 → 详细分组 → 个体追踪                  │
│          │                                                   │
│          ▼                                                   │
│  4. 针对性修复                                               │
│     修改 prompt / 工具描述 / 检索策略 / 护栏设置               │
│          │                                                   │
│          ▼                                                   │
│  5. 验证效果                                                 │
│     重新运行聚类 → 该模式的占比是否下降？                      │
│          │                                                   │
│          └──── 新的追踪积累 → 回到第 1 步 ────►               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

关键区别在于：这个闭环中的"发现问题"步骤是**自动的**。你不需要先有假设，你不需要知道"要找什么"。聚类分析会把你不知道的东西找出来。

## 七、传统分析、在线评估、聚类洞察的关系

三种分析能力不是替代关系，而是层叠互补：

```
                    能力覆盖范围
                    ──────────────────────────────────────►

层次 1: 传统指标     ████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░
                     延迟、反馈、成本、调用量
                     回答"发生了什么"

层次 2: 在线评估     ░░░░░░░░████████████░░░░░░░░░░░░░░░░
                     情绪、主题、成功率、合规
                     回答"已知维度上表现如何"

层次 3: 聚类洞察     ░░░░░░░░░░░░░░░░░░░░████████████████
                     自动发现的未知模式
                     回答"有什么是我不知道的"
```

| 层次 | 回答的问题 | 前提条件 | 局限 |
|------|-----------|---------|------|
| **传统指标** | WHAT：发生了什么 | 预定义指标 | 不知道"为什么" |
| **在线评估** | HOW：在已知维度上表现如何 | 预定义评估器 | 无法发现未知模式 |
| **聚类洞察** | UNKNOWN：有什么是我不知道的 | 足够的追踪数据 | 需要人工解读和行动 |

> **为什么重要**  
> 大多数团队停留在层次 1——他们有仪表盘，有告警，但看到的都是已知的指标。少数团队到了层次 2——他们有在线评估，能自动评分。极少数团队到了层次 3——他们能发现自己不知道的东西。而层次 3，才是从"被动监控"到"主动改进"的分水岭。

## 延伸思考

1. **冷启动问题：** 聚类分析需要足够的追踪数据才能产生有意义的模式。对于刚上线的 Agent，追踪量不足时，如何在"等待数据积累"和"尽早发现问题"之间取得平衡？是否存在一种"小样本聚类"方法，能在数百条追踪时就开始产出有价值的洞察？

2. **聚类的粒度与噪声：** 聚类太粗，所有问题混在一起看不出区别；聚类太细，每个聚类只有几条追踪，统计上没有意义。最佳聚类粒度是由数据本身决定的，还是需要人工调节？如果 Agent 的使用场景发生变化（比如上了新功能），聚类结构会不会失效？

3. **从发现到修复的鸿沟：** 聚类分析能自动发现模式，但从"发现模式"到"知道怎么修"之间仍然需要人类工程师的判断。未来是否可能让一个 Agent 分析另一个 Agent 的追踪，自动生成修复方案？这是否就是 Agent 改进循环自动化的终极形态？

4. **隐私与聚类的矛盾：** 聚类分析需要访问完整的对话内容才能理解语义。但在医疗、金融等领域，对话中可能包含高度敏感的个人信息。如何在保护隐私的前提下进行有效的语义聚类？差分隐私 (Differential Privacy) 或联邦学习 (Federated Learning) 是否适用于这个场景？
