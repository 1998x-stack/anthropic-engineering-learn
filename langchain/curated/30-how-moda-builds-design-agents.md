# Moda 如何用 Deep Agents 构建生产级 AI 设计 Agent

**作者:** LangChain Team（案例研究，受访人：Ravi Parikh，Moda 联合创始人）  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-moda-builds-design-agents)  
**日期:** 2025 年  
**阅读时间:** 约 15 分钟

---

> **一句话总结**  
> 视觉设计领域没有 Flexbox —— PowerPoint XML 是绝对坐标，LLM 又不擅长数学。Moda 通过自定义 DSL、技能注入、动态工具加载三层上下文工程 (Context Engineering)，在 Deep Agents 框架上构建了三个协作 Agent（设计、研究、品牌），实现了"Cursor for Design"的产品体验。

---

## 核心要点

1. **视觉设计的核心难题不是生成，而是布局** —— HTML/CSS 有 Flexbox 和 Grid 做布局抽象，但 PowerPoint XML 只有绝对 XY 坐标。LLM 必须做像素级数学运算，而这恰恰是 LLM 最弱的能力
2. **自定义 DSL 是关键突破** —— Moda 没有让 LLM 直接操作原始场景图 (Scene Graph)，而是设计了一套包含布局抽象的领域特定语言，让 LLM 在它擅长的层级上推理
3. **三个 Agent 各司其职** —— 设计 Agent 做实时画布创作，研究 Agent 获取外部内容，品牌工具包 Agent 提取品牌资产。共享同一套轻量分诊 → 主循环 → 动态上下文架构
4. **上下文工程决定成败** —— 从技能预加载 (Skill Pre-loading) 到动态工具激活 (Dynamic Tool Activation)，每一层都在精确控制"给 LLM 看什么、不看什么"
5. **UX 不是生成替换，而是协作编辑** —— AI 在完全可编辑的 2D 矢量画布上工作，每个元素都可选中、移动、缩放，用户可以"接受或拒绝"，实现真正的人机协作

## 一、核心挑战：视觉设计没有布局抽象

### 为什么代码生成 Agent 更容易，设计 Agent 更难？

编码 Agent（如 Cursor、Deep Agents CLI）生成的是文本代码，代码本身就是结构化的：缩进表示层级，函数名表示语义，HTML/CSS 有 `display: flex` 和 `grid-template-columns` 来声明布局意图，浏览器负责计算每个元素的最终位置。

但视觉设计完全不同。PowerPoint 的 XML 格式长这样：

```xml
<p:sp>
  <p:spPr>
    <a:xfrm>
      <a:off x="3048000" y="1524000"/>   <!-- 绝对 X, Y 坐标 (EMU 单位) -->
      <a:ext cx="2438400" cy="914400"/>  <!-- 宽度, 高度 -->
    </a:xfrm>
  </p:spPr>
</p:sp>
```

没有 `align-items: center`，没有 `justify-content: space-between`。每个元素的位置都是硬编码的绝对坐标。

```
代码 vs 设计：布局抽象的差异
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  HTML/CSS 的世界                     PowerPoint XML 的世界
  ──────────────                      ─────────────────────
  "把这三个元素水平居中，            "元素 A 放在 (3048000, 1524000)
   间距相等"                           元素 B 放在 (5486400, 1524000)
                                       元素 C 放在 (7924800, 1524000)"
       │                                    │
       ▼                                    ▼
  display: flex;                      手动计算每个坐标
  justify-content: space-evenly;      如果画布宽度变了？全部重算
                                      如果加了第四个元素？全部重算
       │                                    │
       ▼                                    ▼
  ✅ 布局引擎自动计算                  ❌ LLM 必须自己做数学

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 让 LLM 直接操作 PowerPoint XML，就像让一个没有计算器的人做建筑设计 —— 每面墙、每扇窗都要手算精确位置，而不是画一张平面图然后让 CAD 软件自动标注尺寸。Moda 的自定义 DSL 就是那个"CAD 软件"，把数学问题变成设计意图问题。

### "LLMs are not good at math" —— Ravi Parikh

Moda 联合创始人 Ravi Parikh 对这个问题的总结一针见血。LLM 的强项是语义理解、模式识别、创意生成，弱项是精确的数值计算。让 LLM 计算"在 960 像素宽的画布上均匀排列 5 个元素，每个元素宽 120 像素，边距 20 像素"这种问题，错误率极高。

| LLM 擅长的 | LLM 不擅长的 |
|------------|-------------|
| "这里需要一个三列布局" | "第一列起始于 x=240" |
| "标题应该比正文大" | "标题字号 36pt，正文 14pt，行高 1.5" |
| "用品牌色做强调" | "#2563EB 透明度 80% 的渐变到 #1E40AF" |
| "这些卡片应该对齐" | "卡片 1 在 (100,200)，卡片 2 在 (340,200)..." |

> **为什么重要**  
> 这不是一个可以通过"更好的提示词"解决的问题。这是 LLM 架构层面的限制 —— Transformer 做精确数值推理天然不如做语义推理。解决方案不是让 LLM 变得更擅长数学，而是**改变问题的表述方式**，让 LLM 在语义层面（而非数值层面）做推理。

### 三个 Agent 的职责

| Agent | 核心功能 | 交互方式 | 状态 |
|-------|---------|---------|------|
| **设计 Agent (Design Agent)** | 实时创建和修改画布上的视觉元素 | 类 Cursor 侧边栏，用户在画布上实时看到 AI 操作 | 自定义 LangGraph 循环，正在迁移到 Deep Agents |
| **研究 Agent (Research Agent)** | 从外部来源获取结构化内容 | 后台运行，将结果写入用户专属文件系统 | 已运行在 Deep Agents 上 |
| **品牌工具包 Agent (Brand Kit Agent)** | 从网站、品牌手册、PPT 中提取品牌资产 | 用户提供品牌来源，Agent 提取颜色、字体、Logo、品牌调性 | 已运行在 Deep Agents 上 |

> **类比理解**  
> 把 Moda 的三 Agent 系统想象成一个广告公司的团队分工。**研究 Agent** 是市场调研员，负责搜集行业数据和竞品素材。**品牌工具包 Agent** 是品牌顾问，负责理解客户的品牌形象和视觉规范。**设计 Agent** 是设计师，拿着调研报告和品牌手册，坐在电脑前一页页做出 PPT。三个人各有专长，但用同一套项目管理流程（共享架构模式）协作。

## 三、上下文工程：让 LLM 在正确的层级上推理

上下文工程是 Moda 技术栈的核心竞争力。它解决的问题是：**在有限的上下文窗口内，给 LLM 提供恰好足够的信息，既不多（浪费 token、干扰推理）也不少（缺少关键信息、输出质量差）。**

### 第一层：自定义 DSL —— 改变问题的表述

Moda 没有让 LLM 直接读写原始的场景图 (Scene Graph)。原始场景图的问题是：

1. **冗长** —— 一个简单的三列布局可能需要上百行 XML
2. **坐标密集** —— 充满精确的数值坐标
3. **缺少语义** —— 看不出设计意图，只有像素位置

Moda 设计了一套**包含布局抽象的领域特定语言 (Domain-Specific Language)**：

```
原始场景图 vs Moda 自定义 DSL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  原始场景图 (Raw Scene Graph)：
  ┌─────────────────────────────────────────────────┐
  │  shape: rect                                    │
  │  x: 100, y: 200, width: 280, height: 400      │
  │  fill: #2563EB                                  │
  │  children:                                      │
  │    - shape: text                                │
  │      x: 120, y: 230, content: "Q3 Revenue"     │
  │      font-size: 24, font-weight: bold           │
  │    - shape: text                                │
  │      x: 120, y: 280, content: "$4.2M"          │
  │      font-size: 48, font-weight: bold           │
  │    - shape: rect                                │
  │      x: 120, y: 350, width: 240, height: 8     │
  │      fill: #60A5FA                              │
  │  ...（还有更多坐标）                               │
  └─────────────────────────────────────────────────┘
  约 200-500 tokens / 元素

                    │
                    ▼  Moda 的转换层

  Moda DSL：
  ┌─────────────────────────────────────────────────┐
  │  card(                                          │
  │    layout: vertical,                            │
  │    align: left,                                 │
  │    style: brand.primary,                        │
  │    children: [                                  │
  │      heading("Q3 Revenue"),                     │
  │      metric("$4.2M"),                           │
  │      progress_bar(value: 0.78)                  │
  │    ]                                            │
  │  )                                              │
  └─────────────────────────────────────────────────┘
  约 30-50 tokens / 元素

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

这个 DSL 做了三件关键的事：

| 设计决策 | 效果 | 为什么有效 |
|---------|------|-----------|
| **用布局语义替代坐标** | `layout: vertical` 代替 `y: 230, y: 280, y: 350` | LLM 理解"垂直排列"比理解"y 递增"容易得多 |
| **用品牌引用替代色值** | `style: brand.primary` 代替 `fill: #2563EB` | LLM 不需要记住具体色号，只需要表达设计意图 |
| **用语义组件替代原始形状** | `progress_bar(value: 0.78)` 代替手绘矩形 | LLM 在组件层级思考，转换层负责渲染 |

> **为什么重要**  
> 自定义 DSL 不只是"节省 token"。它从根本上改变了 LLM 需要解决的问题类型 —— 从"精确数值计算"变成"语义意图表达"。这是在 LLM 的能力甜蜜点 (Sweet Spot) 上做设计，而不是在它的能力盲区上硬推。

### 第二层：分诊 → 技能 → 主循环

用户请求到达后，不会直接进入主 Agent 循环。中间有一个精心设计的预处理流水线：

```
请求处理流水线
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  用户: "帮我做一个三页的季度汇报 PPT"
       │
       ▼
  ① 轻量分诊 (Haiku 模型)
       │  分类: 多页演示文稿
       │  格式: presentation
       │  复杂度: medium
       │  成本: ~0.001 美元 / 几十毫秒
       │
       ▼
  ② 技能加载
       │  根据 format=presentation 加载:
       │  · slide_layout.md (幻灯片布局技能)
       │  · chart_creation.md (图表创建技能)
       │  · brand_application.md (品牌应用技能)
       │
       │  注入方式: 作为 human message 插入
       │  带 prompt caching breakpoints
       │
       ▼
  ③ 主循环 (Main Agent Loop)
       │  已预装相关技能
       │  可以在运行中请求更多技能
       │  动态工具加载 (按需)
       │
       ▼
  ④ 输出: 画布上的设计元素

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**为什么用 Haiku 做分诊？**

| 考量 | 选择 | 理由 |
|------|------|------|
| 模型能力 | Haiku（轻量模型） | 分类任务不需要强推理，轻量模型足够 |
| 延迟 | ~几十毫秒 | 用户感知不到这一步的存在 |
| 成本 | ~$0.001/次 | 相比主循环的成本可忽略不计 |
| 准确率 | 足够高 | 分类空间有限（几种格式），轻量模型不容易出错 |

**技能 (Skills) 是什么？**

技能是 Markdown 格式的文档，包含特定任务的最佳实践、常见模式、约束条件。它们被注入为 human message（而非 system message），并在注入点设置提示缓存断点 (Prompt Caching Breakpoint)，确保重复请求命中缓存。

```
技能注入的消息结构
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  System Message (固定)
  ────────────────────
  "你是一个专业的设计 Agent..."
                                    ◄── prompt cache breakpoint
  Human Message (技能注入)
  ────────────────────
  "[slide_layout.md 的内容]"
  "[chart_creation.md 的内容]"
                                    ◄── prompt cache breakpoint
  Human Message (用户请求)
  ────────────────────
  "帮我做一个三页的季度汇报 PPT"

  Human Message (动态上下文)
  ────────────────────
  "[当前画布状态的 DSL 表示]"

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  缓存命中: System Message + 技能注入层在同类请求间共享
```

> **类比理解**  
> 技能注入就像考试前临时翻的参考手册。分诊模型先判断"这道题考的是什么"（微积分？线性代数？概率论？），然后只把相关章节的公式表放到你面前。你不需要带着整本教材上考场，但需要的公式一定在手边。

### 第三层：动态工具加载

Moda 的工具策略直接反映了上下文工程的核心原则 —— **少即是多**。

```
工具加载策略
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  核心工具 (Core Tools): 12-15 个
  ┌─────────────────────────────────────────────────┐
  │  · create_shape()     · modify_element()       │
  │  · add_text()         · apply_style()          │
  │  · create_slide()     · delete_element()       │
  │  · group_elements()   · align_elements()       │
  │  · set_layout()       · insert_image()         │
  │  · ... (共 12-15 个)                            │
  │                                                 │
  │  总 token 开销: 600-4500 tokens                  │
  │  每次请求都加载 ✅                                │
  └─────────────────────────────────────────────────┘

  按需工具 (On-Demand Tools): ~30 个
  ┌─────────────────────────────────────────────────┐
  │  通过 RequestToolActivation 动态加载             │
  │                                                 │
  │  · create_chart()         · animate_element()  │
  │  · import_data()          · apply_theme()      │
  │  · create_table()         · add_transition()   │
  │  · export_pdf()           · brand_audit()      │
  │  · ... (共 ~30 个)                              │
  │                                                 │
  │  每个工具: 50-300 tokens                         │
  │  只在 Agent 主动请求时加载 ✅                     │
  └─────────────────────────────────────────────────┘

  大多数请求只用核心工具 → 上下文窗口保持精简

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**RequestToolActivation 机制：**

Agent 在主循环中如果需要某个非核心工具，可以调用 `RequestToolActivation` 请求激活。这个机制的关键在于：**Agent 自己决定何时需要额外工具，而不是系统预先加载所有可能用到的工具。**

| 策略 | Token 开销 | 推理质量 |
|------|-----------|---------|
| 全量加载（12 + 30 = 42 个工具） | 2100-12600 tokens | 工具过多，LLM 容易选错或遗忘 |
| 仅核心工具 + 按需加载 | 600-4500 tokens（基线）+ 按需追加 | 精简上下文，LLM 注意力集中在相关工具上 |

### 第四层：画布大小自适应上下文

最后一层上下文工程是根据画布复杂度动态调整信息详细程度：

```
画布大小与上下文策略的关系
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  小画布 (1-3 页)
  ┌──────────────────────────────────────────┐
  │  策略: 完整视图 (Full View)                │
  │  · 每个元素的完整 DSL 描述                  │
  │  · 所有样式属性                             │
  │  · 元素间的空间关系                         │
  │  上下文大小: ~2000-5000 tokens              │
  └──────────────────────────────────────────┘

  大画布 (20+ 页)
  ┌──────────────────────────────────────────┐
  │  策略: 摘要 + 按需展开 (Summary + Drill)   │
  │  · 高层级摘要: 每页标题 + 布局类型          │
  │  · 当前聚焦页: 完整 DSL 描述                │
  │  · 其他页: 仅结构信息                       │
  │  上下文大小: ~3000-8000 tokens（可控）       │
  └──────────────────────────────────────────┘

  如果把 20 页完整展开:
  ~40000-100000 tokens → 超出上下文窗口，推理质量崩溃

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 这就像一个建筑师在不同尺度的项目上工作的方式。设计一间卧室时，你会关注每个开关的位置、每面墙的颜色。设计一栋 50 层的写字楼时，你不会同时思考每层楼的每个开关 —— 你先看总体规划（每层的功能分区），然后聚焦到当前正在设计的那一层。

## 四、UX：设计领域的 "Cursor Moment"

### 不是生成替换，而是协作编辑

大多数 AI 设计工具的模式是"生成 → 替换"：AI 生成一个完整的设计，用户要么接受、要么重新生成。这种模式的问题是：

```
"生成替换" vs "协作编辑"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  传统 AI 设计工具
  ──────────────
  用户: "做一个封面页"
    │
    ▼
  AI 生成完整设计 ──► 用户查看 ──► 不满意 ──► 重新生成
                                    │
                                    ▼
                              整体还行但标题位置不对
                                    │
                                    ▼
                              只能重新生成整页 😕
                              无法精确修改局部


  Moda 的方式
  ──────────
  用户: "做一个封面页"
    │
    ▼
  AI 在可编辑画布上逐步构建
    │
    ├─► 用户随时可以:
    │   · 选中任何元素直接拖动/缩放
    │   · 修改文字内容
    │   · 调整颜色和样式
    │   · 接受或拒绝 AI 的每一步操作
    │
    ▼
  真正的人机协作 ✅

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 为什么这很重要？

Moda 的目标用户是 B2B 企业销售团队 —— 他们需要精美的销售演示文稿 (Pitch Deck)，但没有时间从头设计，也无法接受"差不多就行"的 AI 生成物。

| 用户需求 | 传统 AI 工具 | Moda |
|---------|------------|------|
| 快速获得一个专业起点 | 可以 | 可以 |
| 精确调整特定元素 | 困难（必须通过提示词描述） | 直接在画布上操作 |
| 保持品牌一致性 | 靠运气 | Brand Kit Agent 自动应用品牌规范 |
| 融入外部数据和研究 | 手动复制粘贴 | Research Agent 自动获取并结构化 |
| 最终交付物完全可控 | 有限（AI 生成物不一定可编辑） | 每个元素都是标准矢量对象 |

> **为什么重要**  
> "Cursor Moment"的核心不是 AI 有多强，而是**AI 嵌入了用户已有的工作流**。Cursor 之所以成功，不是因为它的代码生成比 ChatGPT 更好，而是因为它在编辑器内工作 —— 用户不需要离开自己的环境。Moda 在设计领域做了同样的事：AI 在用户的画布上工作，而不是在另一个窗口里生成结果然后让用户想办法导入。

## 七、关键技术决策总结

| 决策 | 选择 | 替代方案 | 为什么这样选 |
|------|------|---------|------------|
| LLM 与设计的接口 | 自定义 DSL | 直接操作场景图 / 生成图片 | LLM 在语义层推理优于数值计算 |
| Agent 架构 | 三个专业化 Agent | 一个全能 Agent | 各 Agent 上下文更聚焦，工具集更精简 |
| 分诊模型 | Haiku（轻量模型） | 主模型做分诊 | 分类不需要强推理，轻量模型够快够便宜 |
| 技能注入位置 | Human message | System message | 配合 prompt caching breakpoint，跨请求复用 |
| 工具加载策略 | 12-15 核心 + ~30 按需 | 全量加载 | 精简上下文提升推理质量 |
| 画布表示 | 大小自适应（完整/摘要） | 固定详细程度 | 避免大项目撑爆上下文窗口 |
| UX 模式 | 可编辑画布上的实时协作 | 生成替换 | 用户需要精确控制最终交付物 |
| 可观测性 | LangSmith 全链路追踪 | 自建日志系统 | 开箱即用的 Agent 追踪、成本分析、提示词迭代 |

## 延伸思考

1. **DSL 设计的边界在哪里？** Moda 的自定义 DSL 在 LLM 和原始格式之间插入了一层抽象。但抽象总有代价 —— 它可能限制了 LLM 表达某些精细设计意图的能力。当用户说"把这个元素向右移 3 个像素"时，DSL 是否能精确传达？抽象的粒度如何在"语义友好"和"精确控制"之间找到平衡？

2. **多 Agent 的协调成本是否值得？** 三个 Agent 各有专用上下文窗口，避免了单个 Agent 的上下文过载。但 Agent 之间的通信需要序列化/反序列化，可能引入信息损失。如果品牌工具包 Agent 提取了品牌色板但设计 Agent 理解有偏差怎么办？是否需要一个"设计审计 Agent"来做质量把关？

3. **从"Cursor for Design"到"Devin for Design"有多远？** 当前的 Moda 是类 Cursor 模式 —— AI 辅助，人类主导。如果让 AI 完全自主完成一份 20 页的销售演示文稿，端到端不需要人类干预，现有的架构能支撑吗？瓶颈是 LLM 能力、DSL 表达力，还是审美判断？

4. **设计领域的评估问题：** 代码有测试用例可以判对错，但设计的"好不好看"是主观的。Moda 如何评估设计 Agent 的输出质量？是否需要一个专门的"设计评估 Agent"用视觉模型来打分？如何防止 LLM 生成"技术上正确但审美上平庸"的设计？

5. **上下文工程的可迁移性：** Moda 在设计领域发展出的"DSL 抽象 + 技能注入 + 动态工具 + 大小自适应"这套上下文工程方法论，是否可以推广到其他"LLM 不擅长精确数值但需要精确输出"的领域？比如 CAD 建模、电路设计、音乐编曲 —— 这些领域是否也需要类似的"中间语义层"来桥接 LLM 的能力和领域的需求？
