# 选择正确的多 Agent 架构：四种模式的取舍与决策

**作者:** Sydney Runkle  
**来源:** [LangChain Blog](https://www.langchain.com/blog/choosing-the-right-multi-agent-architecture)  
**日期:** 2026 年 1 月 14 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 默认从单 Agent 开始。只有当你遇到上下文管理瓶颈或分布式开发需求时，才考虑升级到多 Agent 架构。四种核心模式——子 Agent (Subagents)、技能 (Skills)、交接 (Handoffs)、路由器 (Router)——各有明确的适用场景和性能特征，选错模式的代价远大于晚升级一步。

---

## 核心要点

1. **单 Agent 是默认选择** —— 大多数场景下，一个 Agent + 工具集就够了。多 Agent 是手术刀，不是瑞士军刀
2. **四种模式解决四类问题** —— 子 Agent 做并行隔离、技能做按需扩展、交接做顺序流转、路由器做并行分发
3. **上下文隔离 vs. 上下文共享是核心权衡** —— 子 Agent 和路由器天然隔离上下文（Token 效率高），技能和交接共享上下文（连贯性强但成本累积）
4. **性能差异真实可测** —— 多领域查询场景下，隔离型架构比共享型架构节省约 67% 的 Token

---

## 一、什么时候需要多 Agent？

### 默认立场：不需要

单 Agent + 工具集是所有 Agent 系统的起点。在这个阶段，一个模型调用链配合足够的工具定义就能覆盖大多数场景。只有当你撞上两面墙时，才需要认真考虑多 Agent 架构。

```
升级到多 Agent 的两个触发条件
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  触发条件 1: 上下文管理瓶颈 (Context Management Limits)
  ─────────────────────────────────────────────────────
  单 Agent 的上下文窗口装不下所有领域知识，
  或者不同领域的提示词互相干扰、降低质量。

  触发条件 2: 分布式开发需求 (Distributed Development)
  ─────────────────────────────────────────────────────
  不同团队负责不同 Agent 的提示词和工具，
  需要独立开发、独立部署、独立迭代。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 单 Agent 就像一个全栈工程师——一个人搞定前端、后端、数据库。当项目足够小时，一个人比三个人协调更快。但当代码库膨胀到一个人记不住所有模块时（上下文瓶颈），或者当你需要三个团队并行交付时（分布式开发），拆分就不再是选择题，而是必然。

> **为什么重要**  
> 过早引入多 Agent 是最常见的架构错误之一。每多一个 Agent 就多一次模型调用、多一层状态管理、多一种故障模式。如果单 Agent 还能撑住，多 Agent 带来的复杂度是纯粹的成本。

## 三、模式 1：子 Agent (Subagents)

### 工作原理

一个监督者 Agent (Supervisor) 将子 Agent 作为工具调用。子 Agent 是无状态的 (Stateless)——接收输入、执行任务、返回结果，不保留历史。监督者掌握全局上下文，决定调用哪个子 Agent、何时调用。

```
子 Agent 架构
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

                    用户请求
                       │
                       ▼
              ┌─────────────────┐
              │   监督者 Agent    │
              │  (Supervisor)   │
              │                 │
              │  持有完整上下文   │
              │  决定调度策略     │
              └─────┬───────────┘
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
    ┌───────────┐ ┌──────┐ ┌──────┐
    │ 日历 Agent │ │ 邮件  │ │ CRM  │
    │ (Calendar)│ │Agent │ │Agent │
    │           │ │      │ │      │
    │  无状态   │ │无状态 │ │无状态 │
    │  隔离上下文│ │隔离   │ │隔离   │
    └───────────┘ └──────┘ └──────┘

    每个子 Agent = 一次工具调用 (Tool Call)
    子 Agent 之间完全隔离，互不干扰

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 核心特征

| 特征 | 说明 |
|------|------|
| **控制模式** | 集中式 —— 监督者统一调度 |
| **状态管理** | 子 Agent 无状态，监督者持有全局状态 |
| **上下文隔离** | 强隔离 —— 每个子 Agent 有独立的上下文窗口 |
| **并行能力** | 天然支持 —— 多个子 Agent 可同时执行 |

### 最佳场景

当你的系统有**多个彼此独立的功能领域**时，子 Agent 是最自然的选择。例如：日历管理、邮件处理、CRM 操作——这些领域的知识互不交叉，放进同一个上下文窗口是浪费。

### 代价

每次用户交互至少多一次模型调用（监督者本身需要一次调用来决定分派给谁）。

> **类比理解**  
> 子 Agent 模式就像一个项目经理带领多个专家团队。项目经理听取需求、拆分任务、分发给对应专家，专家完成后交回结果。专家之间不需要互相了解对方在做什么——项目经理负责整合。

## 四、模式 2：技能 (Skills)

### 工作原理

仍然是一个 Agent，但通过渐进式披露 (Progressive Disclosure) 按需加载专门的提示词。启动时只加载所有技能的名称和简短描述，当 Agent 判断需要某个技能时，再加载完整的提示内容。

```
技能模式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  启动阶段 (只加载摘要):
  ┌───────────────────────────────────────────────────────┐
  │  Agent 上下文                                         │
  │                                                       │
  │  可用技能:                                             │
  │    - "日历管理": 处理会议安排和日程冲突                    │
  │    - "邮件撰写": 根据上下文生成邮件草稿                    │
  │    - "数据分析": SQL 查询和可视化                         │
  │    - "代码审查": 检查代码质量和安全性                      │
  │                                                       │
  │  Token 开销: 极低 (仅名称 + 描述)                        │
  └───────────────────────────────────────────────────────┘

  触发加载 (按需加载完整提示):
  ┌───────────────────────────────────────────────────────┐
  │  Agent 上下文                                         │
  │                                                       │
  │  [所有技能摘要]                                        │
  │  +                                                    │
  │  [邮件撰写 - 完整提示词, 300 行]  ← 刚加载              │
  │                                                       │
  │  Token 开销: 仅加载实际需要的技能                        │
  └───────────────────────────────────────────────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 核心特征

| 特征 | 说明 |
|------|------|
| **控制模式** | 单 Agent 自主决定加载哪些技能 |
| **状态管理** | 单一上下文，天然连贯 |
| **上下文隔离** | 无隔离 —— 所有加载的技能共享同一上下文 |
| **并行能力** | 不适用 —— 单 Agent 顺序执行 |

### 最佳场景

当你有**大量专项能力需要组合使用**，但不想为每个能力创建独立 Agent 时，技能模式最合适。它是单 Agent 和多 Agent 之间的中间地带。

### 代价

上下文会随着技能加载而累积。如果一次对话中触发了多个技能，后加载的技能与先加载的技能共享同一上下文窗口，Token 消耗逐步增长。

> **类比理解**  
> 技能模式就像一个查阅操作手册的维修工。他不可能背下所有设备的维修流程，但他知道手册在哪、每本手册讲什么。遇到具体问题时，翻开对应的那一本，按步骤操作。手册越翻越多，桌子上就越拥挤——但他始终只是一个人在干活。

## 五、模式 3：交接 (Handoffs)

### 工作原理

当前活跃的 Agent (Active Agent) 根据对话状态决定将控制权移交给下一个 Agent。移交通过工具调用实现——调用一个"交接工具"来更新状态，指定下一个 Agent 接管。

```
交接模式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  用户: "我需要退货"

  ┌──────────────┐     工具调用:       ┌──────────────┐
  │  分诊 Agent   │───  handoff() ───→│  退货 Agent   │
  │  (Triage)    │    传递状态:        │  (Returns)   │
  │              │    - 用户 ID        │              │
  │  判断意图     │    - 订单号         │  处理退货流程  │
  │  收集信息     │    - 意图: 退货     │  检查政策     │
  └──────────────┘                    └──────┬───────┘
                                             │
                                      工具调用: handoff()
                                             │
                                             ▼
                                      ┌──────────────┐
                                      │  物流 Agent   │
                                      │  (Logistics) │
                                      │              │
                                      │  安排取件     │
                                      │  生成运单     │
                                      └──────────────┘

  状态随交接流转，每个 Agent 只负责一个阶段

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 核心特征

| 特征 | 说明 |
|------|------|
| **控制模式** | 去中心化 —— 当前 Agent 决定移交给谁 |
| **状态管理** | 有状态 —— 状态随交接显式传递 |
| **上下文隔离** | 部分隔离 —— 每个 Agent 有自己的提示词，但共享传递的状态 |
| **并行能力** | 不适用 —— 天然顺序执行 |

### 最佳场景

当你的业务流程是**明确的顺序阶段**时，交接模式最自然。典型案例：客服工单流转（分诊 → 专项处理 → 升级 → 关闭）。

### 代价

状态管理复杂度高。你必须明确定义：每次交接传递哪些状态？状态的 Schema 是什么？如果交接失败怎么回退？

> **类比理解**  
> 交接模式就像医院的就诊流程：挂号台把你分到对应科室，科室医生看完后如果需要手术，就转给外科。每一站都有自己的专业能力，每次转诊都带着你的病历（状态）。没有一个"总指挥"在协调——每个医生自己判断下一步该转给谁。

## 六、模式 4：路由器 (Router)

### 工作原理

一个路由层 (Router) 对输入进行分类，然后将请求并行分发到多个专门的 Agent。每个 Agent 独立处理，路由器收集所有结果后合成最终响应。整个过程是无状态的——每次请求都是全新的分派。

```
路由器模式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  用户: "帮我对比 AWS、GCP、Azure 的 GPU 实例定价"

                    ┌──────────┐
                    │  路由器   │
                    │ (Router) │
                    │          │
                    │ 分类输入  │
                    │ 并行分发  │
                    └────┬─────┘
                         │
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
     ┌──────────┐  ┌──────────┐  ┌──────────┐
     │ AWS Agent │  │ GCP Agent│  │Azure Agent│
     │          │  │          │  │          │
     │ 查询 AWS │  │ 查询 GCP │  │ 查询 Azure│
     │ GPU 定价 │  │ GPU 定价 │  │ GPU 定价  │
     └────┬─────┘  └────┬─────┘  └────┬─────┘
          │             │             │
          └─────────────┼─────────────┘
                        ▼
                  ┌──────────┐
                  │  合成层   │
                  │ 汇总结果  │
                  │ 生成对比  │
                  └──────────┘

  每次请求独立处理，无跨请求状态

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 核心特征

| 特征 | 说明 |
|------|------|
| **控制模式** | 集中式 —— 路由器统一分发和合成 |
| **状态管理** | 无状态 —— 每次请求独立处理 |
| **上下文隔离** | 强隔离 —— 每个 Agent 独立上下文 |
| **并行能力** | 天然并行 —— 多 Agent 同时执行 |

### 最佳场景

当你的查询需要从**多个独立数据源**并行获取信息并合成时，路由器最高效。典型案例：跨平台价格对比、多数据库联合查询。

### 代价

路由层本身需要一次模型调用来分类（路由开销）。且由于无状态，不保留对话历史——如果用户要追问"Azure 那个能便宜点吗？"，路由器不知道"那个"指什么。

> **类比理解**  
> 路由器模式就像一个搜索聚合引擎。你搜一个航班，它同时去查携程、飞猪、去哪儿，然后把结果汇总呈现。每次搜索都是独立的，它不记得你上次搜过什么。

## 七、四种模式横向对比

### 架构特征对比

| 维度 | 子 Agent | 技能 | 交接 | 路由器 |
|------|---------|------|------|--------|
| **分布式开发** | 强 —— 各团队独立开发子 Agent | 弱 —— 单 Agent，技能可分开写 | 中 —— 各阶段可独立开发 | 强 —— 各垂直领域独立开发 |
| **并行执行** | 支持 | 不支持 | 不支持 | 支持 |
| **多跳推理 (Multi-hop)** | 支持 —— 监督者可串联多个子 Agent | 支持 —— 单 Agent 天然连贯 | 支持 —— 状态逐步传递 | 弱 —— 无状态，不擅长连续推理 |
| **直接用户交互** | 弱 —— 用户只和监督者交互 | 强 —— 单 Agent 直接面对用户 | 强 —— 当前 Agent 直接面对用户 | 弱 —— 用户和路由器交互 |
| **上下文隔离** | 强 | 无 | 部分 | 强 |
| **状态性** | 子 Agent 无状态 | 有状态（单上下文） | 有状态（显式传递） | 无状态 |

### 性能特征对比

不同场景下的模型调用次数和 Token 消耗存在显著差异：

```
性能对比 (模型调用次数)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  场景 1: 单次请求 (One-shot)
  ──────────────────────────────
  技能      ███ 3 次调用
  交接      ███ 3 次调用
  路由器    ███ 3 次调用
  子 Agent  ████ 4 次调用  (+1 监督者调度)

  场景 2: 重复请求 (Repeat Request, 有状态优势)
  ──────────────────────────────
  交接/技能  节省 40-50% —— 上下文中已有历史，无需重新推理
  子 Agent   节省较少 —— 子 Agent 无状态，每次重新开始
  路由器     无节省 —— 完全无状态

  场景 3: 多领域查询 (Multi-domain)
  ──────────────────────────────
  技能      ████████████████████ 100% Token (所有领域知识共享一个上下文)
  子 Agent  ███████             ~33% Token (上下文隔离)
  路由器    ███████             ~33% Token (上下文隔离)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **为什么重要**  
> 多领域场景下，上下文隔离型架构（子 Agent、路由器）比上下文共享型架构（技能）节省约 67% 的 Token。这不仅是成本问题——上下文越臃肿，模型的注意力分配越分散，输出质量也会下降。选择架构模式直接影响系统的可扩展性和质量上限。

          │   │
          │   ├─ 需要并行执行？

### 场景速查表

| 你的场景 | 推荐模式 | 理由 |
|---------|---------|------|
| 日历 + 邮件 + CRM 集成 | 子 Agent | 领域独立，可并行，需要集中协调 |
| 编码 Agent 需要多种能力 | 技能 | 能力多但彼此可组合，单 Agent 连贯性重要 |
| 客服工单流转 | 交接 | 明确的顺序阶段，状态需要传递 |
| 跨平台价格对比 | 路由器 | 独立数据源，并行获取，无需对话历史 |
| 10 种专项能力，按需使用 | 技能 | 数量多但轻量，渐进式披露省 Token |
| 三个团队各负责一个模块 | 子 Agent | 分布式开发，独立部署，集中编排 |

## 九、渐进式升级路径

不要跳步。多 Agent 架构应该是逐步演化的结果，不是一开始就设计好的蓝图。

```
渐进式升级路径
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  阶段 1           阶段 2              阶段 3              阶段 4
  ─────           ─────              ─────              ─────
  单 Agent    →   单 Agent + 工具  →   单 Agent + 技能  →   多 Agent
                                                          (选择合适的模式)

  ┌────────┐    ┌────────────────┐  ┌──────────────────┐  ┌──────────────┐
  │  LLM   │    │  LLM           │  │  LLM             │  │  监督者/路由  │
  │        │    │   │            │  │   │              │  │   │          │
  │  无工具 │    │  ┌┴──────┐     │  │  ┌┴──────┐       │  │  ┌┴────┐    │
  │        │    │  │ 工具集 │     │  │  │ 工具集 │       │  │  │子/域│    │
  └────────┘    │  └───────┘     │  │  │+ 技能  │       │  │  │Agent│    │
                └────────────────┘  │  └────────┘       │  │  └─────┘    │
                                    └──────────────────┘  └──────────────┘

  每一步升级都应该有明确的理由：
  阶段 1→2: "Agent 需要和外部系统交互"
  阶段 2→3: "工具太多，上下文负担过重"
  阶段 3→4: "技能共享上下文导致干扰 / 团队需要独立迭代"

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **为什么重要**  
> 每一步升级都增加系统复杂度。阶段 1 的故障排查只需看一个模型的输出；阶段 4 的故障排查可能要追踪三个 Agent 之间的状态传递链。确保每一步升级都是被实际瓶颈逼出来的，而不是被架构图的美感诱惑出来的。

## 延伸思考

1. **混合架构的可行性：** 四种模式不是互斥的。一个系统能否在顶层使用路由器分发，子路由内部使用交接处理顺序流程，同时每个 Agent 又通过技能扩展能力？这种混合架构的调试复杂度是线性增长还是指数增长？

2. **上下文窗口扩大后多 Agent 还有意义吗？** 如果模型的上下文窗口从 128K 扩展到 1M 甚至更大，"上下文管理瓶颈"这个触发条件是否会消失？上下文隔离带来的 Token 节省，在超大窗口的时代是否还重要？

3. **Agent 间通信的标准化：** 四种模式中，子 Agent 和路由器通过工具调用通信，交接通过状态传递通信。如果出现一种标准化的 Agent 间通信协议（类似 MCP 对工具的标准化），是否会催生新的架构模式？

4. **评估多 Agent 系统的方法论：** 单 Agent 的评估相对直接——输入/输出/完成率。多 Agent 系统的评估应该在哪个粒度进行？是端到端评估整个系统，还是单独评估每个 Agent？如果一个子 Agent 表现完美但监督者调度失误，传统的端到端评估能捕捉到这个问题吗？
