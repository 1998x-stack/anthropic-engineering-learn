# Agentic Engineering：当 AI Agent 群体重新定义软件工程

**作者:** Renuka Kumar (Cisco) + Prashanth Ramagopal (Cisco)  
**来源:** [LangChain Blog](https://www.langchain.com/blog/agentic-engineering-how-swarms-of-ai-agents-are-redefining-software-engineering)  
**日期:** 2026 年 4 月 17 日  
**阅读时间:** 约 12 分钟

---

> **一句话总结**  
> 最大的范式跳跃不来自更强的单个 AI Agent，而来自那些**镜像真实团队协作方式**的系统。Agentic Engineering 是一种多 Agent 协调范式——AI Agent 作为数字化团队成员，拥有明确角色分工、共享长期记忆和统一可观测性，端到端覆盖从意图触发到成果验证的全链路。Cisco 的试点数据显示：根因定位时间缩短 93%，开发执行时间缩短 65%+，PR Review 反而成为瓶颈。

---

## 核心要点

1. **Agentic Engineering ≠ AI Coding Agent** —— Codex / Claude Code 在有界、用户驱动的会话中运行；Agentic Engineering 是跨团队端到端编排的**显式控制平面 (Explicit Control Plane)**
2. **Worker Agent 是核心执行单元** —— 解读意图 → 从记录系统 (Systems of Record) 获取上下文 → 通过工具/编码子代理执行 → 验证结果 → 向领导层汇报
3. **A2A + MCP 双协议架构** —— 原生 Agent 通过 A2A (Agent-to-Agent) 协议通信，非原生 Agent 通过 MCP (Model Context Protocol) 包装层接入
4. **LangChain 全家桶支撑三大支柱** —— LangGraph (编排)、LangMem (长期记忆)、LangSmith (可观测性)
5. **人类审查成为新瓶颈** —— Agent 执行足够快之后，PR Review 的人类在环 (Human-in-the-Loop) 暴露为限速步骤

## 一、问题：为什么"更强的单个 Agent"不够？

### 当前 AI Coding Agent 的局限

当前主流的 AI 编码工具——OpenAI Codex、Claude Code、GitHub Copilot Agent——都运行在一种基本模式下：**用户驱动的有界会话 (User-Driven Bounded Session)**。用户给出指令，Agent 在一个沙箱环境中执行，交付结果。

```
当前 AI Coding Agent 的工作模式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  用户 ──→ [Agent 会话] ──→ 输出
           │              │
           │  有界上下文    │
           │  单一任务      │
           │  用户触发      │
           │  会话结束即终止 │
           └──────────────┘

  特征：
  - 一个用户，一个 Agent，一个任务
  - Agent 不知道团队中其他人在做什么
  - 没有跨会话的持久记忆
  - 没有跨 Agent 的协调机制
  - 没有统一的可观测性

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

这些工具在**个人生产力**层面效果显著。但软件工程的核心挑战不在于"一个人写代码有多快"，而在于**团队协作的效率**——需求理解、上下文同步、跨系统集成、质量验证、知识传递。

> **类比理解**  
> 当前的 AI Coding Agent 就像给每个员工配了一个极其聪明的私人助理。助理能帮你搜索、写代码、跑测试。但它不知道隔壁工位的同事在重构同一个模块，不知道产品经理刚改了需求，也不知道运维团队昨天发现了一个生产环境的告警。**10 个互不通信的天才助理，不等于一个协调良好的 10 人团队。**

> **为什么重要**  
> 软件工程中 70% 以上的时间花在"理解上下文"和"协调沟通"上，而非"写代码"。如果 AI 只优化了"写代码"这 30%，整体效率的天花板很快就会碰到。要突破这个天花板，AI 必须参与到团队协作的层面——这就是 Agentic Engineering 要解决的问题。

## 二、Agentic Engineering：从单兵到军团

### 核心定义

Agentic Engineering 是一种多 Agent 协调范式，其中 AI Agent 作为**数字化团队成员 (Digital Team Members)**，具备三个关键属性：

| 属性 | 说明 | 对应技术 |
|------|------|---------|
| **明确角色** (Defined Roles) | 每个 Agent 有清晰的职责边界和专业能力 | LangGraph 状态机定义 |
| **共享记忆** (Shared Memory) | Agent 之间共享长期上下文和学习经验 | LangMem 长期记忆 |
| **统一可观测性** (Common Observability) | 所有 Agent 的行为可追踪、可审计、可调试 | LangSmith 全链路追踪 |

```
Agentic Engineering 与 AI Coding Agent 的本质差异
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

                AI Coding Agent              Agentic Engineering
                ──────────────              ──────────────────
  范围          单任务、单会话               跨团队、端到端编排
  触发          用户手动触发                 IDE/CLI/GitHub/Jira 自动触发
  上下文        会话级，用完即弃              长期记忆，跨会话持久
  协调          无                          显式控制平面
  可观测性      单 Agent 日志                全链路追踪
  人类角色      操作者 (Operator)            审查者 (Reviewer)

  关键洞察：
  "The biggest step change comes from systems
   that mirror real-world teams."

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 双协议设计

| 协议 | 适用对象 | 通信方式 | 典型场景 |
|------|---------|---------|---------|
| **A2A** (Agent-to-Agent) | 原生 Worker Agent | Agent 之间直接通信 | Worker A 请求 Worker B 执行代码审查 |
| **MCP** (Model Context Protocol) | 非 A2A 兼容的 Agent 或工具 | 通过 MCP 包装层桥接 | 接入已有的 CI/CD 工具、监控系统、数据库 |

> **类比理解**  
> A2A 协议就像公司内部的 Slack 频道——同一个组织的同事直接互相@，效率最高。MCP 包装层就像外包公司的对接人——外部团队不用你们的 Slack，但对接人帮他们翻译需求、转发结果，效果等价。两种协议共存，让系统既能高效协调内部 Agent，又能接入任意外部工具。

## 四、Worker Agent：核心执行单元

### 五步执行循环

Worker Agent 不是简单的"接任务 → 写代码"。它遵循一个完整的执行循环，模拟了一个优秀工程师解决问题的完整思路。

```
Worker Agent 执行循环
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌─────────────────────────────────────────────────────┐
  │                                                     │
  │  Step 1: 解读意图 (Interpret Intent)                 │
  │  ┌───────────────────────────────────────────────┐  │
  │  │ "修复 API 超时问题"                             │  │
  │  │  → 理解: 需要排查哪个 API？超时阈值是多少？     │  │
  │  │  → 澄清: 是单个端点还是全局性问题？             │  │
  │  └───────────────────────────────────────────────┘  │
  │                     │                               │
  │                     ▼                               │
  │  Step 2: 获取上下文 (Gather Context)                 │
  │  ┌───────────────────────────────────────────────┐  │
  │  │ 查询记录系统 (Systems of Record):              │  │
  │  │  - Git 历史: 最近哪些提交改了 API 层？          │  │
  │  │  - 监控数据: 超时从什么时候开始的？             │  │
  │  │  - 文档: 该 API 的设计规范是什么？              │  │
  │  │  - LangMem: 上次类似问题是怎么解决的？         │  │
  │  └───────────────────────────────────────────────┘  │
  │                     │                               │
  │                     ▼                               │
  │  Step 3: 执行 (Execute)                              │
  │  ┌───────────────────────────────────────────────┐  │
  │  │ 调用工具 / 编码子代理 / 其他 Worker Agent:      │  │
  │  │  - 分析日志、复现问题                           │  │
  │  │  - 生成修复代码                                 │  │
  │  │  - 运行测试套件                                 │  │
  │  └───────────────────────────────────────────────┘  │
  │                     │                               │
  │                     ▼                               │
  │  Step 4: 验证结果 (Validate Outcomes)                │
  │  ┌───────────────────────────────────────────────┐  │
  │  │  - 测试是否通过？                              │  │
  │  │  - 性能指标是否恢复正常？                       │  │
  │  │  - 是否引入了新的回归？                         │  │
  │  └───────────────────────────────────────────────┘  │
  │                     │                               │
  │                     ▼                               │
  │  Step 5: 汇报 (Report to Leadership Layer)           │
  │  ┌───────────────────────────────────────────────┐  │
  │  │  - 根因: 数据库连接池耗尽                       │  │
  │  │  - 修复: 增加连接池上限 + 添加超时重试           │  │
  │  │  - 验证: 全部 47 个测试通过，P99 延迟降至 200ms │  │
  │  └───────────────────────────────────────────────┘  │
  │                                                     │
  └─────────────────────────────────────────────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **为什么重要**  
> 步骤 2 ("获取上下文") 和步骤 4 ("验证结果") 是关键差异。传统 AI Coding Agent 通常跳过这两步——直接根据用户描述开始写代码，写完就交付。Worker Agent 强制要求"先理解全貌再动手"和"做完必须验证"，这正是资深工程师和初级工程师的行为差异。

### LangChain 全家桶的分工

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

| 支柱 | 解决的问题 | 如果缺失会怎样 |
|------|-----------|---------------|
| **LangGraph** (编排) | Agent 之间的协调、任务分配、流程控制 | Agent 各自为战，重复劳动，互相冲突 |
| **LangMem** (长期记忆) | 跨会话的知识积累和经验复用 | 同样的问题每次从零开始排查，无法学习 |
| **LangSmith** (可观测性) | 调试、性能优化、成本控制、审计 | Agent 出了问题无法定位根因，成本失控 |

> **类比理解**  
> 如果把 Agentic Engineering 类比为一个公司：LangGraph 是**组织架构图 + 流程手册**——谁向谁汇报、什么任务走什么审批流程。LangMem 是**企业知识库**——过去的项目经验、踩过的坑、最佳实践。LangSmith 是**管理仪表盘**——每个人在做什么、花了多少时间、产出质量如何。三者缺一不可。

### 为什么 PR Review 成为瓶颈？

这个结果本身就是一个重要信号。当 Agent 能在 1 小时内完成过去需要 10 小时的开发 + 调试工作时，**人类审查者的带宽**成为限速步骤。这揭示了一个更深层的问题：

| 阶段 | 自动化程度 | 速度 | 瓶颈？ |
|------|-----------|------|--------|
| 意图解读 | 高 | 分钟级 | 否 |
| 上下文获取 | 高 | 分钟级 | 否 |
| 代码编写 | 高 | 分钟级 | 否 |
| 测试验证 | 高 | 分钟级 | 否 |
| PR Review | 低（人类在环） | 小时到天级 | **是** |
| 部署 | 中（CI/CD） | 分钟级 | 否 |

> **为什么重要**  
> 这不是一个可以通过"加速 PR Review"来解决的问题。它暗示了一个根本性的方向：当 Agent 执行速度足够快且验证足够充分时，人类的角色需要从"逐行审查代码"转变为"审查 Agent 的验证逻辑和结果"。**审查的对象从"代码"变成了"Agent 的行为轨迹"**——而这正是 LangSmith 可观测性层存在的意义。

## 七、与 AI Coding Agent 的本质区别

### 不是程度差异，是范畴差异

很多人认为 Agentic Engineering 只是"更强大的 AI Coding Agent"。这是一个危险的误解。两者解决的是根本不同的问题。

| 维度 | AI Coding Agent | Agentic Engineering |
|------|----------------|---------------------|
| **定位** | 个人生产力工具 | 团队协作基础设施 |
| **范围** | 有界会话、单一任务 | 端到端编排、跨团队协调 |
| **触发方式** | 用户手动触发 | IDE / CLI / GitHub / Jira 事件触发 |
| **记忆** | 会话级（用完即弃） | 长期持久（跨会话、跨 Agent） |
| **Agent 间关系** | 无（独立运行） | 有角色、有层级、有通信协议 |
| **可观测性** | 单 Agent 输出日志 | 全系统分布式追踪 |
| **人类角色** | 操作者（驾驶 Agent） | 审查者（监督 Agent 群体） |
| **典型产品** | Codex, Claude Code, Copilot | Cisco Agentic Engineering 平台 |

```
本质区别的一个思维实验
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  场景: 生产环境出现 P1 故障

  AI Coding Agent 能做什么:
  ─────────────────────────
  工程师打开 IDE，描述问题，
  Agent 帮忙搜索代码、建议修复方案。
  工程师需要自己：
    - 判断是哪个服务出了问题
    - 手动拉取日志和监控数据
    - 协调其他团队配合排查
    - 决定修复方案并推动部署

  Agentic Engineering 能做什么:
  ─────────────────────────────
  告警触发 → Worker Agent 群体自动启动：
    - Agent A: 分析告警，定位故障服务
    - Agent B: 从监控系统拉取相关指标
    - Agent C: 检索 Git 历史，找到可疑提交
    - Agent D: 在沙箱中复现问题
    - Agent E: 生成修复补丁 + 测试
    - Agent F: 准备回滚方案作为兜底
  所有 Agent 共享发现（LangMem），
  全链路可追踪（LangSmith），
  编排层（LangGraph）协调先后顺序。
  人类工程师：审查 Agent 的分析结论和修复方案，
  决定是修复还是回滚。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> AI Coding Agent 就像给医生配了一个 AI 助手——帮忙查文献、建议诊断方案、起草处方。Agentic Engineering 就像搭建了一个 AI 驱动的急诊科——从分诊到检查到诊断到治疗到随访，每个环节都有专门的 AI 负责，彼此协调、共享病历、统一监控。前者提升个人效率，后者重构整个流程。

## 八、关键技术决策总结

| 决策 | 选择 | 替代方案 | 为什么这样选 |
|------|------|---------|------------|
| Agent 间通信协议 | A2A + MCP 双协议 | 纯 A2A 或纯 MCP | A2A 效率高但覆盖面窄；MCP 包装层让已有工具无缝接入 |
| 编排引擎 | LangGraph | 自研状态机 / Temporal | LangGraph 原生支持 Agent 抽象，与 LangMem/LangSmith 深度集成 |
| 记忆方案 | LangMem 长期记忆 | 向量数据库 RAG | LangMem 提供 Agent 级别的记忆管理，不只是文档检索 |
| 可观测性 | LangSmith | OpenTelemetry / Datadog | LangSmith 原生理解 Agent 调用链，不需要手动插桩 |
| 触发机制 | 多入口（IDE/CLI/GitHub/Jira） | 单一入口 | 意图可以从任何开发者日常使用的工具中发起 |
| 人类参与点 | PR Review | 每步审批 / 完全自主 | 平衡安全性和效率——Agent 自主执行但人类守住最后一道门 |

## 延伸思考

1. **PR Review 瓶颈的终局是什么？** 当 Agent 的执行速度快到人类审查跟不上时，是应该提升人类审查效率（例如用另一个 Agent 做预审），还是应该重新定义审查的粒度（例如审查 Agent 的验证逻辑而非逐行代码）？如果 PR Review 本身也被 Agent 化，人类的最终护栏应该放在哪个环节？

2. **共享记忆的双刃剑：** LangMem 让 Agent 之间共享长期记忆，但这也意味着一个 Agent 的错误判断可能通过记忆传播给所有 Agent。如果 Agent A 在记忆中写入了一个错误的故障根因模式，Agent B 在下次遇到类似问题时会直接复用这个错误判断。记忆系统需要什么样的"纠错机制"来防止错误知识的扩散？

3. **A2A 协议的生态效应：** 如果 A2A 成为多 Agent 通信的事实标准，会不会催生一个"Agent 市场"——就像今天的 SaaS 生态一样，不同厂商提供不同专长的 Agent，通过 A2A 协议互联？这种生态中的信任机制是什么——你怎么验证一个第三方 Agent 的行为是安全的？

4. **93% 的可推广性：** 调试工作流有一个天然优势：成功标准清晰（问题是否解决）。但对于模糊的创造性任务（例如"设计一个更好的用户体验"），Agentic Engineering 的效果如何衡量？"根因定位时间缩短 93%"不能简单外推到所有软件工程任务。

5. **组织结构的反射效应：** Conway's Law 说"系统的架构反映组织的沟通结构"。如果 Agent 群体的组织方式镜像了人类团队，那反过来，Agent 的组织方式是否会反过来重塑人类团队的组织结构？当 Agent 证明了某种协作模式更高效时，人类团队会不会被迫适配 Agent 的协作模式？
