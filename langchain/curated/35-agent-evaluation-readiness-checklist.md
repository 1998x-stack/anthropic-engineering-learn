# Agent 评估就绪清单：从零构建评估体系的 6 步方法论

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://www.langchain.com/blog/agent-evaluation-readiness-checklist)  
**日期:** 2026 年 3 月 27 日  
**阅读时间:** 约 12 分钟

---

> **一句话总结**  
> 构建 Agent 评估体系不是"写几个测试用例"那么简单——它需要一条结构化的路径：先手动审查真实轨迹 (Trace)、明确成功标准，再选择评估层级、构建数据集、设计评分器 (Grader)、集成到 CI/CD 流水线，最终实现从离线验证到线上监控的完整闭环。这份 6 步清单是一张可执行的施工蓝图。

---

## 核心要点

1. **先看再建** —— 在写任何评估代码之前，手动审查 20-50 条真实轨迹，建立对 Agent 行为的直觉；没有这一步，你不知道该评估什么
2. **能力评估 ≠ 回归评估** —— 能力评估 (Capability Eval) 回答"它能做什么？"，回归评估 (Regression Eval) 回答"它还能做吗？"，两者目的不同、运行频率不同、失败处理方式不同
3. **评估层级决定信号粒度** —— 单步 (Run)、完整轮次 (Trace)、多轮对话 (Thread) 三个层级提供不同粒度的信号，从轨迹层级 (Trace-level) 起步最具性价比
4. **评分器设计要匹配任务性质** —— 客观任务用代码断言、主观任务用 LLM-as-Judge、模糊任务用人工评审；优先使用二值判定 (Binary Pass/Fail)
5. **非确定性是 Agent 评估的核心挑战** —— 同一输入多次运行可能得到不同结果，必须多次试验 (Multiple Trials) 取统计结果
6. **评估不是一次性工程** —— 最终目标是将能力评估晋升为回归测试，集成到 CI/CD 门禁 (Gate) 中，同时持续从线上流量中发现新的评估信号

## 一、在构建评估之前：先看、先定义、先分类

### 第一件事：手动审查真实轨迹

> **类比理解**  
> 你不会在没有看过一个病人的情况下就设计体检表。同样，你不应该在没有手动审查过 Agent 的真实执行轨迹之前就开始写评估代码。先观察，再抽象。

很多团队犯的第一个错误是：**从"我觉得 Agent 应该做到 X"出发，而不是从"Agent 实际在做什么"出发。**

正确的起手式：

```
评估构建的起手式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ✗ 错误路径

  "我觉得 Agent 应该..." ──→ 写评估 ──→ 跑分
                                         │
                                         ▼
                               分数看着还行，但不知道
                               这些评估是否覆盖了
                               真正的失败模式

  ✓ 正确路径

  手动审查 20-50 条真实轨迹
       │
       ├── 发现: Agent 在步骤 3 经常选错工具
       ├── 发现: 错误恢复时会陷入循环
       ├── 发现: 简单任务表现好，复杂任务崩溃
       │
       ▼
  基于真实观察定义成功标准
       │
       ▼
  编写有针对性的评估
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

手动审查的三个关键输出：

| 审查输出 | 内容 | 目的 |
|---------|------|------|
| **行为模式清单** | Agent 在真实场景中表现出的典型行为 | 确认评估应覆盖哪些行为 |
| **失败模式目录** | Agent 最常犯的错误类型及其根因 | 确保评估能捕获这些失败 |
| **成功标准定义** | 对每种任务类型，什么算"做对了" | 为评分器提供不含歧义的判据 |

> **为什么重要**  
> 没有手动审查这一步，你的评估集会充满"看起来有道理但实际没有信号"的测试用例。手动审查是将评估从"凭感觉覆盖"转向"基于证据设计"的唯一路径。

### 关键分离：能力评估 vs 回归评估

在定义成功标准之后，必须将评估分为两类，它们的目的完全不同：

```
两类评估的生命周期
═══════════════════════════════════════════════════════════════

  能力评估 (Capability Eval)
  ┌──────────────────────────────────────────────┐
  │ 问题: "Agent 能做到 X 吗？"                   │
  │ 运行时机: 探索阶段，尝试新能力时               │
  │ 失败处理: 分析原因，调整 Agent 设计             │
  │ 数量: 通常较多，覆盖面广                       │
  │                                              │
  │ 生命周期:                                     │
  │   设计 ──→ 验证 Agent 具备该能力               │
  │                    │                          │
  │                    ▼ (确认稳定)                │
  │              晋升为回归评估 ──→                │
  └──────────────────────────────────────────────┘

  回归评估 (Regression Eval)
  ┌──────────────────────────────────────────────┐
  │ 问题: "Agent 还能做到 X 吗？"                  │
  │ 运行时机: 每次代码变更、每次 CI 构建            │
  │ 失败处理: 阻断发布，必须修复后才能合入          │
  │ 数量: 精选子集，每条都是"必须通过"的硬指标       │
  └──────────────────────────────────────────────┘
```

> **类比理解**  
> 能力评估就像驾校的路考训练——你需要练习各种场景，掌握之后才"毕业"。回归评估就像年检——一旦你拿到驾照，每年只需要验证核心能力没有退化。训练项目很多，年检项目精简但不可跳过。

## 二、选择评估层级：从哪个粒度开始？

### 三个层级

Agent 评估不是"跑一次看输出对不对"这么简单。根据检查粒度的不同，评估分为三个层级：

| 层级 | 英文 | 检查范围 | 信号类型 | 成本 |
|------|------|---------|---------|------|
| **单步** | Run | Agent 收到输入后的第一个决策 | 工具选择是否正确、参数是否合理 | 低 |
| **完整轮次** | Trace | 从输入到最终输出的完整执行轨迹 | 最终响应质量 + 执行路径合理性 + 状态变化正确性 | 中 |
| **多轮对话** | Thread | 多个轮次组成的完整会话 | 上下文保持、跨轮次一致性、长程推理 | 高 |

```
三个评估层级的关系
═══════════════════════════════════════════════════════════

                    Thread (多轮)
                 ┌──────────────────┐
                 │  轮次 1 (Trace)   │
                 │  ┌────────────┐  │
                 │  │ Run │ Run  │  │
                 │  └────────────┘  │
                 │                  │
                 │  轮次 2 (Trace)   │
                 │  ┌────────────┐  │
                 │  │ Run │ Run  │  │
                 │  │     │ Run  │  │
                 │  └────────────┘  │
                 │                  │
                 │  轮次 3 (Trace)   │
                 │  ┌────────────┐  │
                 │  │ Run        │  │
                 │  └────────────┘  │
                 └──────────────────┘

  建议起步策略:

  ① 从 Trace 层级开始 ←── 最佳性价比
  ② 用 Run 层级快速定位单步问题
  ③ 多轮场景成熟后再加 Thread 层级
```

### 每个层级测量什么

每个层级可以从三个维度提取信号：

| 维度 | 单步 (Run) | 完整轮次 (Trace) | 多轮 (Thread) |
|------|-----------|-----------------|--------------|
| **最终响应** (Final Response) | 第一步决策是否正确 | 最终输出是否满足需求 | 最后一轮回复是否完整 |
| **执行轨迹** (Trajectory) | 不适用 | 工具调用序列是否合理 | 跨轮次的决策路径是否一致 |
| **状态变化** (State Changes) | 不适用 | 文件/数据库等外部状态是否正确 | 多轮操作后系统状态是否一致 |

> **为什么重要**  
> 选错评估层级意味着要么"信号不足"（只看最终输出，不知道中间过程哪里出了问题），要么"成本过高"（每条评估都跑完整多轮对话，但其实单步检查就够了）。从 Trace 层级起步，再根据实际需要向上或向下扩展，是最务实的策略。

## 三、数据集构建：好的评估数据长什么样？

### 核心原则

评估数据集不是"凑够 N 条就行"——每一条都必须满足一组严格的质量标准：

```
评估数据集的质量标准
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✓ 任务描述无歧义 (Unambiguous)
    "修复 auth.py 中第 42 行的空指针异常"
    而不是 "修复认证模块的 bug"

  ✓ 附带参考解答 (Reference Solution)
    提供至少一种正确的执行路径/输出

  ✓ 包含正例和反例 (Positive + Negative Cases)
    正例: Agent 应该成功完成的任务
    反例: Agent 应该拒绝、报错或请求澄清的场景

  ✓ 结构匹配评估层级 (Structure Matches Level)
    单步评估: 单个输入 → 预期第一步动作
    轮次评估: 输入 → 预期最终输出 + 中间约束
    多轮评估: 对话序列 → 每轮预期行为

  ✓ 编程 Agent 特例: 包含单元测试套件
    用执行测试结果作为客观验证信号
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 正例与反例的平衡

很多团队只构建"Agent 应该成功完成"的正例，忽略了反例的价值：

| 数据类型 | 用途 | 示例 |
|---------|------|------|
| **正例** (Positive) | 验证 Agent 能完成预期任务 | "将文件从 A 目录复制到 B 目录" → 预期成功 |
| **反例** (Negative) | 验证 Agent 能正确处理异常情况 | "删除系统根目录" → 预期拒绝并说明原因 |
| **边界情况** (Edge Case) | 验证 Agent 在模糊场景下的判断力 | "文件不存在时创建它" → 预期创建而非报错 |

> **类比理解**  
> 如果你只用"正常驾驶"的场景来考核一个自动驾驶系统，你永远不知道它遇到逆行车辆时会怎么反应。反例不是"刁难"，而是"安全边界的验证"。一个连"什么时候该拒绝"都不知道的 Agent，不配上生产环境。

### 编程 Agent 的特殊考量

对于编写或修改代码的 Agent，数据集应包含可执行的单元测试套件：

```
编程 Agent 评估数据的理想结构
═══════════════════════════════════════════════════

  每条评估数据 = {
    task:        "修复 calculate_tax() 中的浮点精度问题"
    context:     { 代码库快照, 相关文件路径 }
    test_suite:  {
                   test_basic_rate()        ← 基础功能
                   test_edge_zero_income()  ← 边界: 收入为零
                   test_negative_input()    ← 反例: 负数输入
                   test_precision()         ← 精度: 小数点后两位
                 }
    reference:   { 参考修复方案 (可选) }
  }

  验证方式: 运行 test_suite
    全部通过 → Pass
    部分失败 → 分析哪些能力缺失
```

## 四、评分器设计：如何判断"做对了"

### 三种评分器，匹配三种任务性质

评分器 (Grader) 的选择不是偏好问题，而是**由任务的客观性决定的**：

| 评分器类型 | 适用场景 | 优势 | 劣势 |
|-----------|---------|------|------|
| **代码断言** (Code-based) | 有确定性正确答案的任务 | 确定性、可复现、速度快 | 无法处理语义等价 |
| **LLM-as-Judge** | 输出有多种合理表达的任务 | 能理解语义、灵活度高 | 需要校准、有偏差风险 |
| **人工评审** (Human Review) | 评判标准模糊或高度主观 | 最高准确度 | 成本高、速度慢、不可规模化 |

```
评分器选择决策树
═══════════════════════════════════════════════════

  任务输出是否有唯一正确答案？
       │
       ├── 是 ──→ 代码断言
       │         (精确匹配、正则表达式、单元测试)
       │
       └── 否 ──→ 输出是否有明确的"好/坏"标准？
                      │
                      ├── 是 ──→ LLM-as-Judge
                      │         (提供评分 Rubric + 示例)
                      │
                      └── 否 ──→ 人工评审
                                (标注团队 + 标注指南)
```

### 二值判定优先

评分器的输出应该优先采用**二值判定 (Binary Pass/Fail)**，而不是多级评分 (1-5 分)：

```
  ✗ 多级评分的问题

  评分: 3/5
  问题: 这意味着什么？比上次的 2.8/5 好了？
        3 分和 4 分的差距在哪？
        不同评审者的 3 分标准一样吗？

  ✓ 二值判定的优势

  评分: Pass 或 Fail
  优势: 无歧义，易聚合，趋势清晰
        通过率从 72% → 78% = 明确的进步信号
```

> **为什么重要**  
> 多级评分看似提供更丰富的信号，实际上引入了大量主观噪声。当你有 100 条评估时，"通过率从 72% 提升到 78%"比"平均分从 3.2 提升到 3.4"更容易解读和行动。

### LLM-as-Judge 的校准流程

如果你使用 LLM-as-Judge，必须经过严格的校准流程：

```
LLM-as-Judge 校准路径
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ① 准备 20+ 人工标注样本 (起步阶段)
     │
     ▼
  ② 让 Judge 模型对这些样本打分
     │
     ▼
  ③ 对比人工标注和 Judge 的一致率
     │
     ├── 一致率 > 85% → 基本可信，继续扩展
     │
     └── 一致率 < 85% → 调整 Prompt / Rubric
                              │
                              ▼
                         回到步骤 ②
     │
     ▼
  ④ 扩展到 100+ 标注样本 (成熟阶段)
     │
     ▼
  ⑤ 定期重新校准 (模型更新、任务变化时)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

两个关键细节：

- **Judge 输出必须包含推理过程 (Reasoning)**：不能只输出 Pass/Fail，必须说明为什么，这样当 Judge 犯错时你能快速定位原因
- **定期重新校准**：模型升级或任务范围变化后，Judge 的行为可能漂移，必须重新验证一致率

## 五、运行与迭代：让评估体系转起来

### 三种运行模式

评估不是"跑一次拿结果"，而是三种互补的运行模式共同工作：

| 模式 | 触发时机 | 目的 | 典型场景 |
|------|---------|------|---------|
| **离线评估** (Offline) | 代码变更、模型切换 | 在部署前验证 Agent 行为 | CI/CD 流水线中的自动化测试 |
| **线上评估** (Online) | 持续运行 | 在真实流量上监控 Agent 表现 | 生产环境中采样评估 |
| **即席评估** (Ad-hoc) | 手动触发 | 调查特定问题或验证假设 | "我怀疑 Agent 在 X 场景下有问题" |

### 应对非确定性

Agent 的行为具有天然的非确定性——同一输入多次运行可能得到不同结果。这意味着：

```
非确定性的应对策略
═══════════════════════════════════════════════════

  ✗ 跑一次就下结论

  Trial 1: Pass   →  "没问题！"
  (实际通过率可能只有 60%)

  ✓ 多次试验取统计结果

  Trial 1: Pass
  Trial 2: Pass
  Trial 3: Fail   ←── 暴露了不稳定性
  Trial 4: Pass
  Trial 5: Pass

  通过率: 4/5 = 80%
  置信度: 需要更多试验 或 标记为"不稳定"
```

> **类比理解**  
> 你不会因为一次考试的成绩就判断一个学生的能力——也许那天他状态特别好或特别差。对 Agent 也一样，单次运行的结果只是一个样本，不是真相。你需要多个样本的统计分布。

### 环境隔离

每次评估试验必须在全新的环境中运行，防止前一次试验的副作用污染结果：

| 隔离方式 | 适用场景 | 成本 |
|---------|---------|------|
| **容器** (Container) | 需要隔离的文件系统操作 | 低，秒级启动 |
| **预发环境** (Staging) | 需要访问外部服务 | 中，需要维护镜像环境 |
| **快照恢复** (Snapshot) | 需要特定的初始状态 | 高，但确定性最强 |

### 能力分类标签

用标签 (Tag) 对评估进行能力分类，实现按需运行：

```bash
# 只运行工具选择相关的评估
pytest tests/evals --tag tool_selection

# 只运行错误恢复相关的评估
pytest tests/evals --tag error_recovery

# 运行所有核心能力评估 (CI 门禁)
pytest tests/evals --tag core

# 运行完整评估集 (发版前)
pytest tests/evals
```

## 六、生产就绪：从实验到 CI/CD 的晋升路径

### 评估的生命周期

评估不是写完就放在那里的。它有一个从"实验性"到"生产门禁"的晋升路径：

```
评估的晋升路径
═══════════════════════════════════════════════════════════════

  能力评估 (Capability Eval)
       │
       │ 确认 Agent 稳定具备该能力
       │ 多次试验通过率 > 90%
       │
       ▼
  回归测试 (Regression Suite)
       │
       │ 集成到 CI/CD 流水线
       │ 每次代码变更自动运行
       │
       ▼
  CI/CD 门禁 (Gate)
       │
       │ 失败 → 阻断合并/部署
       │ 通过 → 允许继续
       │
       ▼
  生产监控 (Production Monitoring)
       │
       │ 线上评估 + 用户反馈
       │ 发现新的失败模式
       │
       ▼
  新的能力评估 (循环)
```

### CI/CD 集成流程

### 三个持续运行的实践

一旦评估体系集成到 CI/CD，以下三个实践必须持续运行：

| 实践 | 频率 | 目的 |
|------|------|------|
| **捕获用户反馈** (User Feedback) | 持续 | 将真实用户的满意/不满意信号转化为评估数据 |
| **线上采样评估** (Online Sampling) | 持续 | 在生产流量上运行评估，捕获离线评估覆盖不到的场景 |
| **手动轨迹审查** (Manual Trace Review) | 定期 (如每周) | 保持对 Agent 行为的直觉，发现评估集的盲区 |

> **为什么重要**  
> 评估体系最大的风险不是"测试失败"，而是"测试全部通过但 Agent 在真实场景中表现很差"——也就是**评估覆盖盲区**。持续的线上评估和人工审查是对抗这种风险的唯一手段。

## 延伸思考

1. **"先看再建"的规模化问题：** 手动审查 20-50 条轨迹对小团队可行，但当 Agent 每天处理数万请求时，如何在海量轨迹中高效找到"值得看的那些"？是否可以构建"异常轨迹检测器"——一个专门识别"看起来不太对"的轨迹的模型，帮助人工审查者聚焦于高价值样本？
2. **能力评估到回归评估的晋升标准：** "多次试验通过率 > 90%"是一个合理的门槛，但不同能力的通过率基线不同——简单任务 95% 可能不够好，复杂任务 70% 可能已经很优秀。是否需要为每种能力定义独立的晋升阈值？这本身就需要一个元评估 (Meta-Eval) 来确定。
3. **环境隔离的成本-收益权衡：** 容器化隔离保证了确定性，但也带来了启动延迟和资源成本。对于不涉及外部状态修改的纯推理任务（如问答、分类），是否可以安全地跳过隔离？如何自动判断一条评估是否需要环境隔离？
4. **评估体系本身的评估：** 当评估集增长到数百条时，如何知道这些评估作为一个整体是否"好用"？是否可以定义评估体系的元指标——比如"假阳性率"（好的改动被评估标记为失败）和"假阴性率"（坏的改动通过了所有评估）？评估体系本身也需要持续优化。
