# 什么是 Agent？—— 从"听话工具"到"自主决策"的光谱

**作者:** Harrison Chase  
**来源:** [LangChain Blog](https://blog.langchain.dev/what-is-an-agent/)  
**日期:** 2024 年 6 月 29 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 智能体 (Agent) 不是一个开关——它是一个光谱。LLM 在系统中掌握的决策权越多，系统就越"agentic"；越 agentic 的系统越强大，但也越需要编排框架、后台运行和实时观测。

---

## 核心要点

1. **Agent 是一个光谱，不是非黑即白** —— 从简单的路由器到完全自主的决策者，LLM 的控制程度逐级递增
2. **越 agentic = 越需要基础设施** —— 编排框架处理分支和循环，后台任务支撑持久执行，观测平台让你看到内部状态
3. **认知架构 (Cognitive Architecture) 是关键设计决策** —— 你需要为特定任务设计 LLM 的思考流程，而不是指望一个通用 Agent 搞定一切
4. **模型越强不等于不需要架构** —— 更好的模型让更多 agentic 的方案变得可行，但领域特定的流程设计仍然不可替代

---

## 一、重新定义 Agent：一个光谱

### 不要问"是不是 Agent"，要问"有多 agentic"

很多人把 Agent 理解为一个二元概念：要么是，要么不是。但实际上，Agent 更像一个连续的光谱——LLM 在整个系统中拥有的决策权越大，这个系统就越 agentic。

> **类比理解**  
> 想象你去餐厅吃饭。最不 agentic 的场景是"你点什么，厨房做什么"——LLM 只是按指令执行。最 agentic 的场景是"你只说'我饿了'，厨师自己决定做什么菜、用什么食材、做几道"——LLM 全权做主。大多数有用的系统落在这两个极端之间。

### Agentic 光谱的五个等级

| 等级 | 名称 | LLM 的角色 | 生活类比 |
|------|------|-----------|---------|
| 1 | 路由器 (Router) | 根据输入选择走哪条路 | 交通信号灯：红灯停、绿灯行 |
| 2 | 工具调用器 (Tool Caller) | 决定调用哪个工具、传什么参数 | 客服：判断你的问题属于哪个部门，然后转接 |
| 3 | 多步执行器 (Multi-step) | 连续调用多个工具完成任务 | 助理：帮你订机票、订酒店、租车，一步步来 |
| 4 | 状态机 (State Machine) | 在复杂流程中做分支和循环决策 | 项目经理：根据进展决定下一步做什么 |
| 5 | 自主 Agent (Autonomous) | 自己定义目标、规划步骤、执行并修正 | 创业者：自己找问题、想方案、执行、迭代 |

```
LLM 控制程度

低 ◄──────────────────────────────────────────────► 高

┌────────┐ ┌──────────┐ ┌────────┐ ┌────────┐ ┌──────────┐
│ 路由器  │→│ 工具调用  │→│ 多步骤  │→│ 状态机  │→│ 自主Agent │
│        │ │          │ │        │ │        │ │          │
│ 选一条路│ │ 调一个工具│ │ 调多个  │ │ 分支+循环│ │ 完全自主  │
└────────┘ └──────────┘ └────────┘ └────────┘ └──────────┘

     确定性高、可控               灵活性高、风险也高
```

## 二、越 Agentic，越需要什么？

当你的系统变得越来越 agentic，三个需求会同步增长。你可以把它们想象成三根同时升高的柱子。

### 2.1 编排框架 (Orchestration Framework)

简单的链式调用（A→B→C）不需要什么框架。但当 LLM 开始做**分支决策**（"如果 A 就走 B，否则走 C"）和**循环**（"一直重复直到满意"），你就需要一个编排框架来管理这些复杂的控制流。

> **类比理解**  
> 做一道菜只需要食谱。但管理一家餐厅的后厨——多个厨师同时工作、菜品之间有依赖关系、要根据客人反馈调整——你需要一个排班系统和流程管理工具。编排框架就是这个"后厨管理系统"。

### 2.2 后台运行与持久执行 (Background & Durable Execution)

简单系统可以在一次 API 调用中完成。但 agentic 系统可能需要运行几分钟、几小时甚至几天。这就要求：

- **后台运行** —— 不能让用户一直等着
- **持久执行** —— 中间崩了要能恢复，不能从头再来
- **人机交互** —— 运行过程中需要人来确认或纠正

### 2.3 实时观测 (Observability)

当 LLM 掌握更多决策权时，你必须能看到它内部在想什么、做了什么决定、为什么走了这条路。否则出了问题，你根本不知道哪里错了。

> **为什么重要**  
> 这三个需求不是"有了更好"，而是"没有就没法用"。一个自主 Agent 如果没有观测能力，就像一辆没有仪表盘的汽车在高速公路上自动驾驶——你看不到速度、油量、引擎状态，出事只是时间问题。

| 需求 | 低 agentic 时 | 高 agentic 时 |
|------|-------------|-------------|
| 编排框架 | 简单链式调用即可 | 必须支持分支、循环、并行 |
| 运行方式 | 同步、即时返回 | 后台异步、持久化、可恢复 |
| 观测需求 | 看看输入输出就行 | 需要追踪每一步决策、内部状态 |

## 三、认知架构：给 LLM 设计"思考流程"

### 什么是认知架构？

认知架构 (Cognitive Architecture) 这个词听起来很高大上，其实就是指：**你的系统里，LLM 是怎么思考和做决定的？** 它包括 LLM 调用的顺序、之间的逻辑关系、以及哪些步骤由 LLM 决定、哪些由代码决定。

> **类比理解**  
> 你可以把认知架构想象成一家公司的组织架构和决策流程。同样是"开发一个新产品"，不同公司的流程完全不同：有的是老板拍板（集中决策），有的是小组讨论投票（分布式决策），有的是先做原型再决定（迭代式决策）。认知架构就是决定 LLM 用哪种方式"工作"。

### 常见的认知架构模式

```
模式 1：路由器                模式 2：顺序链
┌─────┐                    ┌───┐  ┌───┐  ┌───┐
│ LLM │──→ 分支A           │LLM│→│LLM│→│LLM│
│     │──→ 分支B           └───┘  └───┘  └───┘
│     │──→ 分支C
└─────┘

模式 3：自主循环              模式 4：状态机
┌──────────────┐           ┌────┐
│  ┌───┐       │           │ S1 │──→ S2 ──→ S3
│  │LLM│→ 行动 │           │    │←── S4
│  └─┬─┘       │           └────┘
│    │  观察结果│           （LLM 决定状态转移）
│    └─────────┘
```

### 核心洞察：不存在"万能架构"

不同的任务需要不同的认知架构。一个处理客服工单的 Agent 和一个写代码的 Agent，它们的"思考方式"应该完全不同。**你需要为你的具体场景设计最合适的架构**，而不是套用一个通用模板。

## 四、模型越强，架构就不重要了吗？

很多人有一个直觉："等模型足够聪明，直接让它自由发挥就行了，不需要精心设计架构。" 这个直觉部分正确，但不完全对。

### 正确的部分

模型的规划能力和推理能力在不断增强。更强的模型确实能处理更复杂的 agentic 场景，让之前不可行的自主方案变得可行。

### 不正确的部分

即使模型再强，领域特定的认知架构仍然有巨大价值。原因很简单：

1. **可靠性** —— 在关键步骤上用确定性代码替代 LLM 决策，可以大幅减少出错
2. **效率** —— 不需要让 LLM "重新发明轮子"，已知的最佳流程直接固化到代码中
3. **可控性** —— 你能精确控制哪些步骤允许 LLM 自由发挥，哪些步骤必须按规矩来

> **类比理解**  
> 即使你雇了全世界最聪明的员工，你也不会让他从零开始"发明"公司的报销流程。你会给他一个现成的流程，让他把聪明才智用在真正需要创造力的地方。认知架构就是这个"现成的流程"。

## 五、LangGraph 与 LangSmith 的定位

理解了 agentic 光谱和三大需求之后，LangChain 的两个核心产品的定位就很清晰了：

| 产品 | 解决什么问题 | 在光谱中的位置 |
|------|-----------|-------------|
| **LangGraph** | 编排框架 —— 支持分支、循环、持久化的 Agent 编排 | 帮你构建中高 agentic 的系统 |
| **LangSmith** | 观测平台 —— 追踪、调试、评估 Agent 的每一步行为 | 帮你理解和改进 agentic 系统 |

## 六、实践指导：你该选择多 agentic？

这不是"越 agentic 越好"的问题。你需要根据实际场景找到合适的位置。

### 决策框架

> 问自己三个问题：
>
> 1. **任务的变化性有多大？** —— 变化越大，越需要 LLM 做决策
> 2. **出错的代价有多高？** —— 代价越高，越应该用确定性代码约束 LLM
> 3. **你能承受多少延迟和成本？** —— 越 agentic 通常意味着更多 LLM 调用

```
                    高
                     │
         ┌───────────┼───────────┐
  任务    │  状态机    │  自主Agent │
  变化性  │  用规则约束│  让LLM自由  │
         │  LLM的决策 │  探索和决策 │
         ├───────────┼───────────┤
         │  固定流程   │  工具调用器 │
         │  不需要LLM │  LLM选工具  │
         │           │  但流程固定 │
         └───────────┼───────────┘
                    低
              低 ─────── 高
              出错代价可控程度
```

## 延伸思考

1. **你现在的项目处于光谱的哪个位置？** 它是一个简单的路由器，还是一个需要循环和分支的状态机？有没有可能你把它设计得"过于 agentic"了？
2. **从"聪明模型"到"好用系统"的鸿沟：** 为什么即使 GPT-4、Claude 这样的强模型，直接当 Agent 用仍然经常翻车？认知架构在其中扮演了什么角色？
3. **编排与观测的先后：** 如果你只能先投资一个，你会先搭编排框架还是先搭观测平台？为什么？
4. **光谱的终点在哪里？** 随着模型越来越强，agentic 光谱的"右端"会不断扩展吗？还是说存在一个天然的上限，超过它之后 agentic 反而不如确定性代码？
