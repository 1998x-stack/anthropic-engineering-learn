# 如何把 Claude Code 变成领域专用编程 Agent

**作者:** Aliyan Ishfaq / LangChain Team  
**来源:** [LangChain Blog](https://www.langchain.com/blog/how-to-turn-claude-code-into-a-domain-specific-coding-agent)  
**日期:** 2025 年 9 月 11 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 让编程 Agent 掌握你的专属库，不是把文档全塞给它，而是写一份精炼的指导文件 (Claude.md) 告诉它"怎么想"，再配上文档查询工具 (MCP) 让它"按需翻书"。两者结合的效果最好。

---

## 核心要点

1. **编程 Agent 遇到冷门库就抓瞎** -- LLM 在热门库（如 React、Flask）上表现优秀，但面对自定义库、内部 API 或小众框架时错误百出
2. **直接灌文档适得其反** -- 把大量文档塞进上下文窗口会"挤占"思考空间，性能反而下降
3. **Claude.md 的性价比最高** -- 一份精炼的指导文件比 MCP 文档工具便宜约 2.5 倍，效果却更好
4. **最佳配置 = Claude.md + MCP** -- 指导文件提供方向感，MCP 工具提供深度细节，二者互补产出最佳结果
5. **有技能 vs 无技能 = 82% vs 9%** -- 经过评估验证，技能文件对任务完成率的提升是数量级的

---

## 一、问题：编程 Agent 的"知识盲区"

### 热门库 vs 冷门库

编程 Agent 写 Python、写 React 得心应手，因为 LLM 在训练时已经"读"过海量相关代码。但你让它用公司内部的自研框架、某个新版本的库、或者一个小众工具 -- 它就像一个从没学过这门课的学生，只能靠"猜"。

> **类比理解**  
> 编程 Agent 就像一个经验丰富的厨师。你让他做川菜、粤菜，他信手拈来。但你让他做你奶奶独创的家传菜谱 -- 他完全不知道放什么料、什么火候。他需要的不是一整本《中国烹饪大全》，而是一张写着关键步骤和注意事项的小卡片。

### LangChain 团队的亲身痛点

LangChain 团队自己开发了 LangGraph 和 LangChain 库。他们发现，连最先进的编程 Agent 写 LangGraph 代码时也会犯各种基础错误：用错 API、搞混模式、忽略最佳实践。于是他们做了一系列实验，测试不同的"投喂知识"方式。

## 二、四种配置方案对比

他们用 Claude 4 Sonnet 作为统一模型，测试了四种配置：

| 配置 | 说明 | 核心思路 |
|------|------|---------|
| **Claude 原版** | 开箱即用，零定制 | "裸考" |
| **Claude + MCP** | 接入文档 MCP 服务器 | "开卷考试" |
| **Claude + Claude.md** | 写一份领域指导文件 | "考前划重点" |
| **Claude + MCP + Claude.md** | 两者结合 | "划重点 + 开卷" |

### 什么是 MCP 文档工具？

LangChain 团队开源了一个叫 [MCPDoc](https://github.com/langchain-ai/mcpdoc) 的 MCP 服务器。它提供两个工具：

```python
# 工具 1：列出有哪些文档源
list_doc_sources()
# 返回可用的 llms.txt 文件 URL 列表

# 工具 2：获取指定文档的内容
fetch_docs(url="https://example.com/llms.txt")
# 返回该页面的纯文本内容
```

你可以把自己库的 `llms.txt` URL 配置进去，Agent 就能按需查阅你的文档。

### 什么是 Claude.md？

Claude.md 是一份放在项目根目录的指导文件，Claude Code 在每次会话开始时会自动读取。LangChain 团队在里面写了：

```
Claude.md 的内容结构
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  核心概念与原语
  ├── create_react_agent 的用法
  ├── supervisor 模式（多 Agent 协调）
  └── swarm 模式（动态切换）

  常见陷阱与反模式
  ├── interrupt() 的错误用法
  ├── state 更新的错误模式
  └── 过度复杂的实现方式

  框架特定的编码规范
  ├── 结构化输出验证
  ├── 消息处理的正确方式
  └── 调试步骤和方法

  参考 URL
  └── 每节末尾附上详细文档链接

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> Claude.md 和 llms.txt（MCP 拉取的原始文档）的区别，就像"老师划的考试重点"和"整本教材"的区别。教材内容全但信息密度低，重点笔记虽然不全但每一条都直击要害。

## 三、评估方法：怎么判断哪种配置更好？

LangChain 团队设计了一套三层评估体系，不仅看"代码能不能跑"，还看"代码写得好不好"。

### 三层评估

```
评估金字塔
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

         ┌───────────────┐
         │  代码质量评估   │  ← LLM-as-Judge
         │  (主观 + 客观)  │     用评分标准打分
         ├───────────────┤
         │  任务需求测试   │  ← 自动化测试
         │  (功能是否正确)  │     检查特定功能
         ├───────────────┤
         │   烟雾测试      │  ← 自动化测试
         │  (能不能跑起来)  │     编译、返回值
         └───────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

| 评估层 | 检查内容 | 方法 |
|--------|---------|------|
| **烟雾测试** | 代码能编译吗？暴露了 `.invoke()` 方法吗？返回值结构对吗？ | 加权求和 |
| **任务需求测试** | 部署配置文件对吗？HTTP 请求发到了正确的 API 吗？ | 加权求和 |
| **代码质量评估** | 设计选择合理吗？用了框架推荐的抽象吗？代码优雅吗？ | LLM 评审 |

### LLM-as-Judge 的评分公式

代码质量评估分两部分：

**客观检查** -- 二元判断（有没有特定节点、图结构对不对、模块分离了没有）：

```
客观得分 = 各检查项权重 x 通过与否(0/1) 的加权求和
```

**主观评估** -- 以专家代码为参考，按违规严重程度扣分：

```
主观得分 = 满分 - (严重违规数 x 严重扣分 + 主要违规数 x 主要扣分 + 次要违规数 x 次要扣分)
```

每种配置在每个任务上跑 3 次取平均，消除随机波动。

> **为什么重要**  
> 很多人评估编程 Agent 只看"代码能不能跑"（Pass@k 指标）。但在实际工程中，"能跑"和"写得好"之间差距巨大。一段能跑但满是反模式的代码，长期维护成本远高于一段按最佳实践编写的代码。三层评估让你同时衡量功能正确性和工程质量。

```
  Claude 原版           ██████░░░░░░░░░░░░░░░░░░░░  低
  Claude + MCP          ██████████░░░░░░░░░░░░░░░░  中 (+~10pp)
  Claude + Claude.md    ████████████████░░░░░░░░░░  高
  Claude + MCP+Claude.md████████████████████░░░░░░  最高

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
pp = percentage points (百分点)
```

### 关键发现

**发现一：Claude.md 单独就比 MCP 单独好。**

这出乎意料。Claude.md 只包含 MCP 能提供内容的一个子集，但效果更好。通过分析 Trace（执行记录），他们找到了原因：

```
Claude + MCP 的行为模式（问题）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  任务需要查阅 2-3 个关联页面
        │
        ▼
  Agent 调用 MCP 一次 ← 只调了一次！
        │
        ▼
  拿到主页面（只有概述）
        │
        ▼
  停下来，用概述信息硬写代码 ← 细节不够
        │
        ▼
  代码质量差，缺少深度理解

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

Agent 并没有像人类那样"追着链接一路深挖"，而是查了一次就停了。

**发现二：Claude.md + MCP 组合时，MCP 的使用方式完全不同。**

```
Claude + Claude.md + MCP 的行为模式（理想）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Claude.md 提供了方向感
  + 每节末尾附有参考 URL
        │
        ▼
  Agent 知道自己"不知道什么"
        │
        ▼
  主动多次调用 MCP 查阅细节
  甚至触发 web search 补充
        │
        ▼
  深度理解 → 高质量代码

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 没有 Claude.md 时，Agent 就像一个不知道该问什么的新人 -- 领导说"有问题查文档"，他翻了一页就觉得"大概够了"。有了 Claude.md 后，Agent 就像一个读过入职培训手册的新人 -- 手册告诉他"这里有个坑，详细情况查这个链接"，他就知道该主动去深挖。

## 五、三个实验任务详解

### 任务 1：Text-to-SQL Agent

**要求：** 构建一个能将自然语言转成 SQL、执行查询、返回自然语言结果的 Agent。

**常见失败原因：**
- 跨线程的内存数据库连接处理错误
- 把数据库 schema 硬编码到 LLM 提示中，而不是运行时动态读取
- 无法正确解析 LLM 输出中的 SQL（格式稍有不同就崩溃）

### 任务 2：公司调研 Agent

**要求：** 构建一个通过 Tavily API 搜索网页来调研公司信息的多节点 Agent，需要并行搜索和反思步骤。

**常见失败原因：**
- 反思节点形同虚设，未能触发补充搜索
- 信息没有正确结构化存储到 state 中

### 任务 3：记忆分类（编辑任务）

**要求：** 在已有代码基础上，增加记忆分类（个人/职业/其他）、分类检索、保存前人工确认功能。代码中还故意留了语法错误。

**常见失败原因：**
- 用 `input()` 做终端输入而非用 LangGraph 的 `interrupt()` 机制
- 用关键词匹配分类而非 LLM 分类
- 过度设计（为简单功能创建大量不必要的新节点）
- 几乎所有配置都没能发现故意留下的语法错误

## 六、核心经验

### 经验一：上下文超载会帮倒忙

```
上下文窗口的使用效率
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  灌入大量 llms.txt 文档后：

  ┌────────────────────────────────────────────┐
  │ 上下文窗口                                  │
  │ ┌──────────────────────┐  ┌──────┐         │
  │ │ 文档内容（占大量空间）  │  │ 思考  │  ← 被挤压 │
  │ │ 大部分内容与任务无关   │  │ 空间  │         │
  │ │ 甚至干扰判断          │  │      │         │
  │ └──────────────────────┘  └──────┘         │
  └────────────────────────────────────────────┘

  用精炼 Claude.md 后：

  ┌────────────────────────────────────────────┐
  │ 上下文窗口                                  │
  │ ┌────────┐  ┌──────────────────────────┐   │
  │ │ 精炼    │  │ 充足的思考空间             │   │
  │ │ 指导    │  │ + 按需调用 MCP 补充细节    │   │
  │ │ 信息    │  │                          │   │
  │ └────────┘  └──────────────────────────┘   │
  └────────────────────────────────────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

MCP 的朴素实现是把整页文档拉下来。哪怕只调用一次，Claude Code 就弹出上下文窗口即将占满的警告。如果你的文档很庞大，需要构建更智能的检索工具，只拉取相关片段。

### 经验二：Claude.md 的投入产出比最高

| 维度 | Claude + MCP | Claude + Claude.md |
|------|-------------|-------------------|
| **搭建成本** | 部署 MCP 服务器 | 写一个文件 |
| **运行成本** | 高（频繁拉取文档占 Token） | 低（只加载一次） |
| **任务 2 的费用对比** | 基准 | 约为 MCP 的 **1/2.5** |
| **效果** | 中等 | 更好 |

> **为什么重要**  
> 对于大多数团队来说，Claude.md 是最务实的起步方式。你不需要搭建任何基础设施，只需要花时间写一份好的指导文件。它可能就已经够用了。

### 经验三：写好指导文件的四个要素

一份优秀的 Claude.md（或 Agents.md）应该包含：

```
好的指导文件 = 四大要素
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. 核心概念和常用原语
     "这个库最重要的 3 个函数是..."
     "构建 Agent 的标准流程是..."

  2. 常见陷阱和反模式
     "不要用 input()，要用 interrupt()"
     "不要硬编码 schema，要运行时读取"

  3. 调试步骤
     "遇到导入错误时，先启动 dev server"
     "验证输出时，向服务器发送测试请求"

  4. 参考链接
     每节末尾附上详细文档的 URL
     引导 Agent 在需要时主动深挖

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

LangChain 团队发现，**反模式和调试步骤**的价值尤其大。很多 LLM 错误是"可预测的" -- 它们总是在同样的地方犯同样的错。把这些错误预先列出来，相当于提前打了预防针。

### 经验四：最终配置 = Claude.md + MCP

Claude.md 提供"每个 Token 最大价值"，但最强结果来自两者的组合：

```
最佳协作模式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Claude.md（地图）          MCP（百科全书）
  ┌──────────────┐         ┌──────────────┐
  │ "你需要关注   │         │ 完整的 API    │
  │  这些概念"    │         │ 文档和示例    │
  │              │         │              │
  │ "在这里容易   │  引导   │ 具体函数的    │
  │  犯错，注意"  │ ─────→ │ 参数和用法    │
  │              │  查阅   │              │
  │ "详细信息     │         │ 边界情况的    │
  │  请查阅..."  │         │ 完整说明      │
  └──────────────┘         └──────────────┘

       方向感                  深度细节

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **类比理解**  
> 出国旅行时，你不会只带一张地图或只带一本旅行指南。地图告诉你方向和路线（Claude.md），指南提供每个景点的详细介绍（MCP）。最好的旅行者两者都带：先看地图确定目标，再翻指南了解细节。

## 七、如何为你自己的库应用这套方法

### 第一步：写一份 Claude.md

从你的库中提炼出最重要的信息：

```markdown
# 你的库名 - Claude 编程指南

## 核心概念
- 概念 A：一句话解释 + 代码示例
- 概念 B：一句话解释 + 代码示例

## 必须遵守的模式
- 创建实例时必须用 X 方式
- 状态更新必须通过 Y 方法

## 常见错误（千万别这样做）
- 错误 1：不要用 old_api()，要用 new_api()
- 错误 2：不要直接修改 state，要用 reducer

## 调试清单
- 导入失败 → 检查 X
- 运行时错误 → 先启动 Y 服务

## 参考链接
- API 文档：https://...
- 示例项目：https://...
```

### 第二步（可选）：搭建 MCP 文档服务

如果你的库文档已经有 `llms.txt` 格式，可以直接用 MCPDoc：

```json
{
  "mcpServers": {
    "your-lib-docs": {
      "command": "uvx",
      "args": ["mcpdoc"],
      "env": {
        "URLS": "https://your-lib.dev/llms.txt"
      }
    }
  }
}
```

### 第三步：用三层评估验证效果

1. 定义 3-5 个代表性编码任务
2. 分别在"无配置"和"有配置"下运行
3. 用烟雾测试 + 需求测试 + LLM 评审对比结果
4. 根据失败模式迭代 Claude.md 内容

## 延伸思考

1. **Claude.md 的维护成本：** 库在不断更新，Claude.md 也需要跟着更新。有没有自动化方式从 Changelog 和 Breaking Changes 中提取更新？或者让 Agent 在遇到新问题后自动补充 Claude.md？

2. **MCP 的检索智能化：** 当前 MCPDoc 的实现是"整页拉取"，这在大型文档上代价很高。如果引入向量检索或关键词定位，只返回最相关的段落，MCP 的效果会不会超过 Claude.md？

3. **指导文件的通用模板：** LangChain 团队为 LangGraph 写的 Claude.md 包含了概念、陷阱、调试步骤。这个结构是否可以泛化为一套模板，让任何库的维护者都能快速产出高质量的指导文件？

4. **评估方法的可信度：** LLM-as-Judge 本身也是一个 LLM，它的评判标准是否与人类专家一致？当被评估的代码使用了 Judge 模型不熟悉的库时，评分会不会失真？这引出了"用 LLM 评估 LLM 写的代码"的循环可信度问题。

5. **成本和效果的 Pareto 前沿：** 在什么复杂度的任务上 Claude.md 就够了，什么时候值得投入 MCP？是否存在一个"任务复杂度阈值"，低于它用 Claude.md，高于它才值得加 MCP？
