# 沟通就是一切：Agent 出错，多半是你没说清楚

**作者:** Harrison Chase  
**来源:** [LangChain Blog](https://www.langchain.com/blog/communication-is-all-you-need)  
**日期:** 2024 年 10 月 26 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> Agent 表现不好，大多数时候不是模型太笨，而是你没跟它沟通清楚。把"跟 AI 沟通"这件事做好，是构建可靠 Agent 的核心技能。

---

## 核心要点

1. **提示工程 (Prompt Engineering) 不会消亡** —— 模型不会读心术，你必须给它清晰指令
2. **代码是认知架构的重要组成** —— 代码比自然语言更精确地表达"应该怎么做"
3. **你需要 Agent 框架** —— 通用基础设施交给框架，你专注业务逻辑
4. **框架必须高度可控** —— 不能限制你的认知架构
5. **Agent 框架不会消失** —— 沟通不会消失，代码不会消失，框架也不会
6. **构建 Agent 是多学科协作** —— 领域专家写最好的提示词，工程师写代码
7. **UI/UX 是最重要的创新方向** —— 人机协作的质量取决于沟通界面

---

## 类比理解：带新人的艺术

> 想象你是一个团队 leader，刚招了一个非常聪明的新人。  
> 这个新人智商 150，学什么都快——但他刚入职，对你们的业务一无所知。  
>  
> 你会怎么做？  
> - 给他一份新人手册（系统提示）  
> - 告诉他遇到不同情况该怎么处理（提示工程）  
> - 给他配好电脑、权限、开发工具（工具和基础设施）  
> - 定期 review 他的工作，给反馈（人机协作循环）  
>  
> 你绝不会只说一句"好好干"然后就消失。  
> **构建 Agent 也是一样的。**

## 一、提示工程不会消亡

### 核心观点

模型越来越聪明，但"聪明"不等于"懂你"。你不说清楚，它就会猜——猜错了你还怪它笨。

### 为什么重要

一些花哨的提示技巧（比如"给你 100 美元小费"）确实会被淘汰，但**清晰表达你的需求**这件事永远不会过时。提示工程的本质不是"hack"，而是"沟通"。

> **诊断技巧**  
> 当你的 Agent 出了问题，先别急着换模型。把发给模型的完整输入打印出来，读一遍，问自己：  
> "如果我把这段话发给一个聪明的人类同事，他能正确理解我要什么吗？"  
> 如果答案是"不能"，那问题出在你的提示上，不是模型上。

### 类比理解

```
你跟新人说：     "把那个文档整理一下。"
新人的内心 OS：  哪个文档？整理成什么样？给谁看？什么时候要？

你应该说：       "把上周的周报整理成带摘要的 PPT，
                 重点突出三个关键进展，明天下午给老板汇报用。"
```

跟 Agent 沟通也是一样：**越具体，越可靠。**

## 二、代码是认知架构的重要组成

### 核心观点

提示词 (Prompt) 用自然语言告诉模型"做什么"，但代码能更精确地告诉模型"怎么做"。两者结合，构成了 Agent 的**认知架构 (Cognitive Architecture)**。

### 为什么重要

自然语言天生有歧义。"先检查一下数据，没问题就提交"——这话人能懂，但机器需要精确定义什么叫"没问题"。代码不会产生这种歧义。

> **认知架构 = 提示词 + 代码**  
> 提示词负责模糊的、需要判断力的部分（"语气友好一点"）  
> 代码负责确定的、需要精确执行的部分（"如果金额 > 10000，必须走审批"）

### 对比表

| 维度 | 自然语言提示 | 代码 |
|------|-------------|------|
| 精确性 | 有歧义空间 | 100% 精确 |
| 灵活性 | 高，模型可发挥 | 低，按逻辑走 |
| 适合场景 | 需要判断力的任务 | 需要确定性的流程 |
| 类比 | 口头交代 | 写成 SOP 流程图 |

## 三、你需要 Agent 框架

### 核心观点

构建 Agent 时，有两类代码：一类是你的业务逻辑（你的竞争力），一类是通用基础设施（谁都要写的重复代码）。框架帮你解决后者，让你专注前者。

### 框架帮你处理什么？

```
┌─────────────────────────────────────────────────┐
│           Agent 框架帮你解决的通用问题             │
│                                                 │
│  ┌───────────┐  ┌───────────┐  ┌──────────────┐│
│  │ 流式输出   │  │ 持久化存储 │  │ 人机协作循环  ││
│  │ (Streaming)│  │(Persistence│  │    (HITL)    ││
│  │            │  │  & Memory) │  │              ││
│  └───────────┘  └───────────┘  └──────────────┘│
│                                                 │
│  ┌───────────────────────────────────────────┐  │
│  │ 容错 + 水平扩展 (Fault Tolerance & Scale)  │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

### 类比理解

你开一家餐厅，核心竞争力是你的菜品（认知架构）。但你还需要收银系统、排队叫号、厨房动线管理——这些是基础设施。没人会因为你的排队系统特别好而来吃饭，但没有它你根本开不了业。

框架就是餐厅的"基础设施套件"。

---

## 四、框架必须高度可控

### 核心观点

框架要帮忙，但不能碍事。如果框架内置了一堆你改不了的默认行为，它就从"助手"变成了"枷锁"。

### 为什么重要

Harrison 坦诚地反思了早期 LangChain 库的问题：

> "老版本的 langchain 确实让上手变简单了，但它有内置提示词、硬编码的 while 循环，不容易扩展。我们在 LangGraph 里修正了这些问题。"

LangGraph 的设计哲学：**低层级、高可控、高度可定制**。节点和边就是普通的 Python 函数，你想放什么逻辑进去都行。

### 对比表

| 特性 | 受限框架 | 可控框架 (如 LangGraph) |
|------|---------|----------------------|
| 上手难度 | 简单 | 需要理解概念 |
| 灵活度 | 低，框架说了算 | 高，你说了算 |
| 天花板 | 很快碰到 | 几乎没有 |
| 类比 | 预制菜，不能调味 | 食材+厨房，你自己炒 |

> **关键原则**  
> 框架不能限制你的认知架构。一旦框架妨碍了你向模型清晰传达意图，你的 Agent 就不可能可靠。

---

## 五、Agent 框架不会消失

### 核心观点

有人问："模型越来越强，框架是不是就不需要了？"答案是：**不会。**

### 为什么重要

这个问题的隐含假设是：模型强到不需要任何代码包裹。但事实上，大多数人用框架不是为了"让模型更聪明"，而是为了构建**垂直领域的定制化 Agent 应用**。

推理链条：

```
沟通是构建 Agent 的核心
    ↓
代码是沟通的重要方式
    ↓
沟通不会消失 → 代码不会消失
    ↓
框架帮你更高效地写代码
    ↓
∴ 框架不会消失
```

### 类比理解

汽车发动机越来越强劲，但你仍然需要方向盘、刹车和仪表盘。发动机再好，你也不可能骑着一台裸发动机上高速。

---

## 六、构建 Agent 是多学科协作

### 核心观点

构建 Agent 不只是工程师的事。**领域专家 (Domain Expert)** 在这个过程中扮演着不可替代的角色。

### 为什么重要

| 角色 | 擅长做的事 | 在 Agent 构建中的价值 |
|------|-----------|---------------------|
| 工程师 | 写代码、搭架构 | 实现认知架构的代码部分 |
| 领域专家 | 理解业务逻辑 | 写出最好的提示词，审查 Agent 逻辑 |
| 设计师 | 设计交互体验 | 打造人机协作的 UI/UX |

领域专家为什么能写出更好的提示词？因为他们**最懂业务应该怎么运转**。一个法律 Agent 的提示词，法律专家写得一定比纯技术人员好。

### 类比理解

拍一部电影，你需要导演（产品）、编剧（领域专家）、摄影师（工程师）、剪辑师（设计师）。只有编剧一个人，拍不出电影；只有摄影师一个人，也拍不出电影。**Agent 开发是团队运动。**

> **调试技巧**  
> Agent 出 bug 了，工程师的本能是查代码。但很多时候，让领域专家看一眼 Agent 的执行轨迹 (Trace)，他们能瞬间发现"这一步的逻辑不对"——因为他们最懂业务。

---

## 七、UI/UX 是最重要的创新方向

### 核心观点

你跟 Agent 的沟通质量，取决于沟通界面的设计。一个好的 UI/UX 能让人机协作事半功倍。

### 为什么重要

Agent 的价值不取决于模型有多强，而取决于**人和 Agent 协作得有多好**。而协作质量的上限，由 UI/UX 决定。

目前的 Agent 交互方式（聊天框）只是起点。未来会有更多形态：

```
┌──────────────────────────────────────────┐
│           Agent 交互方式演进               │
│                                          │
│  聊天式 (Chat)                           │
│    → 环境式 (Ambient)：Agent 在后台默默干活 │
│    → 协同式 (Collaborative)：并肩工作      │
│    → 可视化 (Visual)：像看仪表盘一样监控    │
│    → ???（还有更多可能）                   │
└──────────────────────────────────────────┘
```

### 类比理解

电脑从命令行进化到图形界面，生产力爆炸了。不是因为 CPU 变强了，而是因为人和电脑的"沟通界面"变好了。Agent 领域正在经历同样的阶段。

## 全文总结

| 推论 | 核心一句话 | 类比 |
|------|-----------|------|
| 提示工程不会消亡 | 模型不读心，你必须说清楚 | 给新人交代任务要具体 |
| 代码是认知架构的一部分 | 代码比自然语言更精确 | 口头交代 vs. 写成 SOP |
| 你需要 Agent 框架 | 通用基础设施不要自己造 | 餐厅的收银排队系统 |
| 框架必须高度可控 | 框架不能限制你的表达 | 食材+厨房 vs. 预制菜 |
| Agent 框架不会消失 | 沟通→代码→框架，链条不断 | 发动机再强也需要方向盘 |
| 多学科协作 | 领域专家 + 工程师 = 最佳组合 | 拍电影需要整个剧组 |
| UI/UX 最重要 | 人机协作质量取决于界面 | 命令行→图形界面的飞跃 |

## 延伸思考

1. **你的 Agent 出过什么"沟通事故"？** 回忆一下，是不是很多问题归根结底都是"没跟模型说清楚"？

2. **代码 vs. 提示词的边界在哪里？** 哪些逻辑应该写成代码硬性约束，哪些应该用自然语言让模型灵活判断？这个平衡点怎么找？

3. **你的团队里有领域专家参与 Agent 开发吗？** 如果没有，试着让他们看一次 Agent 的执行轨迹，你可能会惊讶于他们能发现多少问题。

4. **想象一下理想的 Agent UI 是什么样的？** 不是聊天框，不是命令行，而是一种全新的交互方式。你会怎么设计？

5. **"沟通的最大问题，是你以为沟通已经发生了。"** 萧伯纳这句话用在 Agent 开发上太合适了。你以为提示词写清楚了，但模型真的理解了吗？怎么验证？
