# Agent Protocol：Agent 互操作标准

**作者:** LangChain Accounts  
**来源:** [LangChain Blog](https://blog.langchain.dev/agent-protocol-interoperability/)  
**日期:** 2024 年 11 月 19 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> Agent Protocol 是一套框架无关的 API 标准，让不同框架构建的 Agent 能用统一的方式通信和协作——就像 USB 让所有设备都能互联一样。

---

## 核心要点

1. **当前的 Agent 世界像"万国插头"** —— 每个框架有自己的 API，彼此无法直接通信
2. **Agent Protocol 定义了三个核心概念** —— Runs（执行）、Threads（会话线程）、Store（长期记忆）
3. **框架无关** —— 无论你用 LangGraph、AutoGen、CrewAI 还是纯代码，都可以实现这个协议
4. **已有实际落地** —— LangGraph Studio 和 LangGraph Platform 已经基于此协议运行
5. **互操作性是多 Agent 时代的基础设施** —— 没有标准协议，Agent 之间就无法大规模协作

---

## 一、问题：Agent 世界的"万国插头"困境

### 现状

你用 LangGraph 构建了一个 Agent，你的同事用 AutoGen 构建了另一个，产品经理想把它们串起来。问题来了：两个 Agent 暴露的 API 完全不同——参数名不同、返回格式不同、会话管理方式不同。你得写一堆胶水代码来对接，而且每增加一个框架就要多写一份。

> **类比理解**  
> 想象一下如果没有 USB 标准，每个外设厂商都设计自己的接口形状。你买一个键盘需要一种线，买一个鼠标又需要另一种线，买一个移动硬盘还要第三种线。这就是今天 Agent 框架之间的现状——每个框架都有自己的"接口形状"。

### 这件事为什么难

| 维度 | 没有标准的情况 | 有标准之后 |
|------|--------------|-----------|
| 集成成本 | 每对框架写一份适配器 | 所有框架实现同一接口 |
| 工具生态 | 每个框架自己造轮子 | 通用工具服务所有框架 |
| Agent 协作 | 必须在同一框架内 | 跨框架自由组合 |
| 部署运维 | 每个框架一套部署逻辑 | 统一的部署平台 |

---

## 二、解决方案：Agent Protocol

Agent Protocol 是一套 **框架无关的 API 标准**。它不是一个框架，不是一个库，而是一份"合同"——任何框架只要按照这份合同暴露 API，就能被其他遵守合同的系统调用。

### 三个核心概念

```
┌─────────────────────────────────────────────────────┐
│                  Agent Protocol                      │
│                                                     │
│  ┌─────────────┐  ┌──────────────┐  ┌────────────┐ │
│  │   Runs      │  │   Threads    │  │   Store    │ │
│  │   执行 API   │  │  会话线程 API │  │ 长期记忆API│ │
│  │             │  │              │  │            │ │
│  │ • 创建执行   │  │ • 组织多轮    │  │ • 跨会话   │ │
│  │ • 传入输入   │  │   对话历史    │  │   持久存储  │ │
│  │ • 获取输出   │  │ • 串联多次    │  │ • 用户画像  │ │
│  │ • 流式响应   │  │   Run 执行   │  │ • 知识积累  │ │
│  └─────────────┘  └──────────────┘  └────────────┘ │
└─────────────────────────────────────────────────────┘
```

---

### 2.1 Runs：执行的 API

Run 是 Agent Protocol 最基本的单元——**一次 Agent 执行**。你给 Agent 一个输入，它处理，返回输出。就这么简单。

> **类比理解**  
> 把 Run 想象成一次函数调用。你传入参数（用户的问题），Agent 内部运行（调用工具、推理、生成），然后返回结果。Run API 定义了这个"调用-返回"过程的标准格式。

Run API 支持的关键能力：
- **创建**：启动一次 Agent 执行
- **输入**：以标准格式传入用户消息或数据
- **输出**：以标准格式获取 Agent 的响应
- **流式传输**：实时获取 Agent 正在生成的内容（不用等它全部想完）

---

### 2.2 Threads：组织多轮执行的 API

一个 Thread 把多次 Run 串在一起，形成一段连续的"对话"。Agent 可以在 Thread 内回顾之前的执行历史。

> **类比理解**  
> Thread 就是聊天软件里的一个"对话窗口"。你在同一个窗口里发了多条消息（多次 Run），每条消息都能看到之前的上下文。新开一个窗口（新的 Thread）就是一段全新的对话。

```
Thread-001
├── Run-1: 用户问 "北京天气怎么样？"
│   └── Agent 调用天气 API → 返回 "晴，25°C"
├── Run-2: 用户问 "那明天呢？"
│   └── Agent 知道 "那" = 北京 → 返回 "多云，22°C"
└── Run-3: 用户问 "帮我推荐穿什么"
    └── Agent 结合前两轮信息 → 返回建议
```

没有 Thread，每次 Run 都是"失忆"的——Agent 不知道你之前问过什么。Thread 解决了 **多轮对话的连续性** 问题。

---

### 2.3 Store：长期记忆的 API

Thread 解决了一段对话内的记忆，但 Store 解决的是 **跨对话的长期记忆**。用户上周说过的偏好、三个月前提到的项目背景——这些信息不在当前 Thread 里，但 Agent 需要记住。

> **类比理解**  
> Thread 是你和某人的一次聊天记录，Store 是你的通讯录备注。即使开了新的聊天窗口，你翻一下备注就能想起来"这个人喜欢简洁风格、用的是 Python、上次提到过要做一个电商项目"。

| 对比项 | Thread | Store |
|--------|--------|-------|
| 生命周期 | 一段对话 | 跨对话持久化 |
| 用途 | 当前上下文连续性 | 用户画像、知识积累 |
| 类比 | 聊天记录 | 通讯录备注 |

## 三、为什么要"框架无关"？

Agent Protocol 最重要的设计原则是 **框架无关 (framework-agnostic)**。

> **为什么重要**  
> 如果这个协议只能被一个框架使用，它就不是"标准"，而是"SDK"。真正的标准必须让所有人都能实现——就像 HTTP 协议并不要求你用 Apache 还是 Nginx，TCP/IP 并不要求你用 Windows 还是 Linux。

这意味着：
- 你用 **LangGraph** 构建的 Agent 可以实现 Agent Protocol
- 你用 **AutoGen** 构建的 Agent 可以实现 Agent Protocol
- 你用 **CrewAI** 构建的 Agent 可以实现 Agent Protocol
- 你 **不用任何框架**、纯 Python/JS 写的 Agent 也可以实现 Agent Protocol

只要你的 Agent 暴露了符合协议的 API，任何工具和平台都能与它对接。

## 四、实际应用场景

### 4.1 LangGraph Studio：本地开发利器

LangGraph Studio 是一个桌面应用，让你可以可视化地调试和测试 Agent。它通过 Agent Protocol 连接到你本地运行的 Agent。

关键改进：**不再需要 Docker**。之前你需要启动一个 Docker 容器来运行 Agent，现在只要你的 Agent 实现了 Agent Protocol，Studio 就能直接连接。

```
┌──────────────────┐        Agent Protocol        ┌──────────────┐
│  LangGraph Studio│ ◄──────────────────────────► │  你的 Agent   │
│  (桌面应用)       │     标准 API 调用            │  (本地运行)   │
└──────────────────┘                              └──────────────┘
         ↑
    无需 Docker
    无需特定框架
    只要实现协议即可
```

---

### 4.2 跨框架集成：在一个工作流中混用多个框架

这是 Agent Protocol 最强大的应用场景。你可以在一个 LangGraph 工作流的某个节点里，包裹一个用其他框架构建的 Agent：

```
LangGraph 工作流
│
├── 节点 1: LangGraph 原生 Agent（做数据分析）
│
├── 节点 2: AutoGen Agent（做多角色讨论） ← 通过 Agent Protocol 调用
│
├── 节点 3: CrewAI Agent（做任务分配）    ← 通过 Agent Protocol 调用
│
└── 节点 4: LlamaIndex Agent（做文档检索） ← 通过 Agent Protocol 调用
```

> **类比理解**  
> 这就像一个项目组里，有人用 Figma 做设计，有人用 VS Code 写代码，有人用 Excel 做数据分析。工具不同没关系，因为大家都通过同一种方式（比如 Git + Slack）协作。Agent Protocol 就是 Agent 世界的"协作协议"。

每个框架都有自己的强项。你不需要把所有事情都用一个框架做——用最合适的框架做最合适的事，然后通过 Agent Protocol 把它们串起来。

---

### 4.3 LangGraph Platform：统一部署

LangGraph Platform 是一个生产级的 Agent 部署平台。因为它基于 Agent Protocol，所以 **不限制你用什么框架构建 Agent**。

平台提供的能力：

| 能力 | 说明 |
|------|------|
| 水平扩展 | 根据负载自动增减 Agent 实例 |
| 任务队列 | 管理大量并发的 Agent 执行请求 |
| 持久化 | Agent 状态不会因为宕机而丢失 |
| 长期记忆 | 基于 Store API 的跨会话记忆管理 |
| 流式传输 | 实时推送 Agent 的执行过程 |

> **为什么重要**  
> 把 Agent 从"笔记本里跑通的 demo"变成"生产环境稳定运行的服务"，需要大量基础设施工作。Agent Protocol 让部署平台可以用一套统一的方式管理所有 Agent，而不是为每个框架写一套部署逻辑。

## 五、Agent Protocol 与其他标准的关系

你可能听说过 MCP (Model Context Protocol)。它和 Agent Protocol 解决的是不同层面的问题：

| 对比项 | Agent Protocol | MCP |
|--------|---------------|-----|
| 解决什么 | Agent 之间如何通信 | Agent 如何获取外部数据和工具 |
| 类比 | HTTP 协议（服务之间通信） | USB 接口（设备连接外设） |
| 定义的是 | Agent 的 API 格式 | 工具和数据源的接入方式 |
| 关系 | 互补，不替代 | 互补，不替代 |

两者可以同时使用：Agent 通过 MCP 获取工具能力，通过 Agent Protocol 暴露自己的服务接口。

## 六、总结

```
                    Agent Protocol 的价值
                    ━━━━━━━━━━━━━━━━━━━

    之前                              之后
    ────                              ────
    每个框架一套 API                   统一标准 API
    集成 = 写胶水代码                  集成 = 实现协议
    Agent 只能同框架协作              Agent 跨框架协作
    部署平台绑定框架                   部署平台框架无关
    工具生态碎片化                     工具生态共享
```

Agent Protocol 的核心思想很简单：**约定好 Agent 怎么被调用（Runs）、怎么保持对话（Threads）、怎么记住信息（Store），剩下的实现细节留给你自由选择。**

这和互联网的成功逻辑一样——HTTP 不关心你用什么语言写服务器，TCP/IP 不关心你用什么操作系统。标准协议释放的不是某个框架的能力，而是整个生态的协作潜力。

## 延伸思考

1. **标准的时机问题**：Agent Protocol 是在 Agent 生态还比较早期的时候提出的。过早标准化可能限制创新，过晚又会导致碎片化不可收拾。你觉得现在是提出 Agent 通信标准的好时机吗？

2. **谁来维护标准**：Agent Protocol 目前由 LangChain 主导推动。一个由单一公司主导的"开放标准"，和由社区或标准组织主导的标准，在采用率和中立性上会有什么不同？

3. **与 A2A 的演化**：Google 后来提出了 Agent2Agent (A2A) 协议，同样试图解决 Agent 互操作问题。多个竞争标准并存是标准化的常态（如 USB-A/B/C 的演进），你认为最终会走向统一还是分层共存？

4. **从协议到生态**：有了标准协议，下一步需要什么？Agent 注册中心？Agent 市场？身份认证？可信任评级？这些生态基础设施由谁来建？
