# Agent 连接沙箱的两种模式

**作者:** LangChain Team  
**来源:** [LangChain Blog](https://blog.langchain.dev)  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> 让 Agent 执行代码有两种架构——把 Agent 装进沙箱里，或者把沙箱当工具调用。前者像住在工厂里干活，后者像远程操控机器人。选哪种，取决于你更在意"手感"还是"安全"。

---

## 核心要点

1. **模式一：Agent 住在沙箱内** —— Agent 和执行环境打包在一起，像驻厂工程师，直接操作文件系统
2. **模式二：沙箱作为工具** —— Agent 在外部运行，需要执行代码时远程调用沙箱 API，像远程操控
3. **安全是核心分歧** —— 模式一中 Agent 和代码共享权限，密钥暴露在沙箱里；模式二天然隔离
4. **延迟是模式二的代价** —— 每次代码执行都要走一次网络往返，但换来了架构灵活性
5. **行业趋势偏向模式二** —— 关注点分离、按用付费、GPU 推理就绪，更适合生产环境

---

## 一、为什么需要沙箱？

Agent 最强大的能力之一是写代码并执行它。但你不可能让 Agent 在你的笔记本电脑上直接跑 `rm -rf /`。沙箱（Sandbox）就是给 Agent 准备的一间"隔离房间"——它可以在里面随便折腾，但破坏不了外面的世界。

问题是：Agent 和沙箱之间怎么连接？这看似简单，实际上是一个影响安全、性能和运维成本的架构决策。LangChain 团队总结出两种主流模式，各有取舍。

> **类比理解**  
> 想象你要雇一个实验员做化学实验。方案 A：让他住在实验室里，吃住都在里面，随时可以做实验。方案 B：他住在办公室，需要做实验时走到实验室，做完回来。两种方式都能完成工作，但安全性、效率、管理方式完全不同。

---

## 二、模式一：Agent 运行在沙箱内部

### 工作原理

你构建一个 Docker 镜像，把 Agent 代码、依赖库、运行环境全部打包进去。Agent 在这个沙箱容器内启动，外部系统通过网络（通常是 HTTP API）与它通信。Agent 直接在沙箱里读写文件、执行代码、安装包——所有操作都发生在同一个环境中。

```
┌──────────────────────────────────────────────────────┐
│                    沙箱容器 (Docker)                    │
│                                                      │
│  ┌──────────────┐    ┌──────────────────────────┐   │
│  │   Agent 进程  │───▶│    文件系统 / 代码执行      │   │
│  │              │    │    直接访问，无需网络       │   │
│  │  • LLM 调用   │    └──────────────────────────┘   │
│  │  • 工具链     │                                    │
│  │  • API 密钥 ⚠ │                                    │
│  └──────────────┘                                    │
│         ▲                                            │
└─────────┼────────────────────────────────────────────┘
          │ HTTP / WebSocket
          ▼
   ┌──────────────┐
   │   外部客户端   │
   │  发送任务/接收  │
   │  结果          │
   └──────────────┘
```

### 优点

- **直接文件系统访问**：Agent 读写文件就像在本地操作，没有任何中间层延迟
- **紧耦合开发体验**：本地构建镜像，调试时环境一致，所见即所得
- **低延迟执行**：代码执行不需要走网络，Agent 写完代码立刻就能跑

### 缺点

- **API 密钥在沙箱内** —— 这是最大的安全隐患。Agent 调用 LLM 需要 API Key，而这个 Key 存在沙箱里。如果 Agent 执行的代码是不可信的（比如用户提交的代码），恶意代码可以读取环境变量，偷走你的密钥
- **网络基础设施复杂** —— 外部要和沙箱通信，需要搭建 HTTP 服务、处理端口映射、管理容器生命周期
- **更新需重建镜像** —— Agent 逻辑改了一行代码？重新构建整个 Docker 镜像，重新部署
- **IP 泄露风险** —— 沙箱内的代码如果发起外部网络请求，暴露的是你的服务器 IP

### Nuno Campos 的安全警告

LangChain 核心开发者 Nuno Campos 指出一个本质问题：**当 Agent 运行在沙箱内部时，bash 工具和 Agent 拥有完全相同的权限**。Agent 能访问的所有东西——环境变量、文件系统、网络——沙箱里执行的任意代码也都能访问。

> **类比理解**  
> 就像你把保险柜的钥匙和一个陌生人关在同一个房间里。你让陌生人帮你干活，但你的钥匙也在那个房间。如果这个陌生人不怀好意，他随时可以打开保险柜。模式一的本质困境就是：**Agent 的权限和它执行的代码的权限无法分离**。

## 三、模式二：沙箱作为工具

### 工作原理

Agent 运行在你自己的服务器或本地环境中。当它需要执行代码时，调用一个远程沙箱的 API——把代码发过去，沙箱执行，把结果传回来。沙箱只是 Agent 工具箱里的一个"工具"（Tool），和搜索引擎、数据库查询没有本质区别。

```
┌──────────────────────────┐         ┌──────────────────────┐
│      Agent 运行环境        │         │    远程沙箱 (Sandbox)  │
│                          │  HTTP   │                      │
│  ┌──────────────────┐    │ ──────▶ │  ┌────────────────┐  │
│  │   Agent 进程      │    │         │  │  代码执行引擎    │  │
│  │                  │    │ ◀────── │  │  文件系统       │  │
│  │  • LLM 调用       │    │  结果    │  │  隔离环境       │  │
│  │  • API 密钥 🔒    │    │         │  └────────────────┘  │
│  │  • 工具链         │    │         │                      │
│  │    ├─ 搜索        │    │         │  ⚠ 无 API 密钥      │
│  │    ├─ 数据库       │    │         │  ⚠ 无敏感信息       │
│  │    └─ 沙箱 API ───┼────┼─────────┤                      │
│  └──────────────────┘    │         └──────────────────────┘
└──────────────────────────┘
```

### 优点

- **密钥在沙箱外** —— API Key 留在你自己的环境里，沙箱里只有代码和数据，泄露风险大幅降低
- **即时更新** —— Agent 逻辑改了就改了，不需要重建任何镜像，沙箱是独立服务
- **关注点分离**（Separation of Concerns）—— Agent 负责思考和决策，沙箱负责执行代码，各管各的
- **可并行扩展** —— 一个 Agent 可以同时调用多个沙箱实例，并行执行多段代码
- **按用付费**（Pay-per-use）—— 沙箱不用时不占资源，用多少付多少

### 缺点

- **网络延迟** —— 每次执行代码都要经历"发送代码 → 网络传输 → 沙箱执行 → 返回结果"的完整往返。如果 Agent 频繁执行小段代码，这个延迟会累积

### Ben Guo 的前瞻观点

Daytona 的 Ben Guo 指出：模式二的架构天然适配未来的 **GPU 推理**（GPU Inference）场景。当 LLM 推理需要 GPU 加速时，Agent 运行环境和代码执行环境本来就可能在不同的机器上。模式二从一开始就假设了网络分离，不需要再做架构迁移。

## 四、两种模式对比

| 维度 | 模式一：Agent 在沙箱内 | 模式二：沙箱作为工具 |
|------|---------------------|-------------------|
| 安全性 | ⚠ 密钥暴露在沙箱中 | ✅ 密钥与沙箱隔离 |
| 执行延迟 | ✅ 本地直接执行 | ⚠ 每次调用走网络 |
| 更新部署 | ⚠ 重建镜像 | ✅ 即时生效 |
| 架构复杂度 | 中（需要容器编排） | 低（API 调用） |
| 并行能力 | ⚠ 单容器执行 | ✅ 多沙箱并行 |
| 成本模型 | 容器常驻 | 按用付费 |
| 文件访问 | ✅ 直接读写 | ⚠ 需通过 API |
| 权限隔离 | ❌ Agent = 代码 | ✅ Agent ≠ 代码 |
| GPU 就绪 | ⚠ 需改架构 | ✅ 天然适配 |

## 五、选择指南

### 选模式一的场景

- Agent 和执行环境高度耦合，频繁读写文件系统
- 执行延迟要求极低（毫秒级）
- 运行的代码都是受信任的（你自己写的，不是用户提交的）
- 原型开发阶段，追求快速验证

### 选模式二的场景

- 安全是硬性要求（执行用户提交的代码、多租户环境）
- 需要快速迭代 Agent 逻辑，不想每次都重建镜像
- 需要并行执行多段代码
- 生产环境部署，追求成本可控
- 未来可能需要 GPU 推理

```
               你的代码可信吗？
                    │
          ┌─────────┴─────────┐
          │                   │
         是                  否
          │                   │
    延迟敏感吗？          ──▶ 模式二
          │
    ┌─────┴─────┐
    │           │
   是          否
    │           │
  模式一      模式二
```

## 六、代码示例：模式二实战（Daytona + Deep Agents）

以下是模式二的典型实现——Agent 在本地运行，通过 Daytona SDK 调用远程沙箱执行代码：

```python
from daytona_sdk import Daytona, DaytonaConfig, CreateSandboxParams

# 初始化 Daytona 客户端（Agent 侧）
daytona = Daytona(DaytonaConfig(api_key="your-api-key"))

# 创建一个远程沙箱
sandbox = daytona.create(CreateSandboxParams(language="python"))

# Agent 决定要执行的代码
code = """
import pandas as pd
df = pd.read_csv('data.csv')
print(df.describe())
"""

# 调用沙箱执行（走网络）
result = sandbox.process.code_run(code)
print(result.output)

# 用完释放沙箱（按用付费）
daytona.remove(sandbox)
```

关键点：`api-key` 在 Agent 侧，沙箱里只有执行引擎。即使沙箱里的代码尝试读取环境变量，也拿不到任何敏感信息。

## 类比理解：两种模式的本质区别

把 Agent 想象成一个厨师，沙箱是厨房：

- **模式一**：厨师住在厨房里。他随时可以拿到任何食材和调料（低延迟），但他的钱包、手机、家门钥匙也放在厨房里（安全风险）。如果厨房起火，所有东西一起烧。
- **模式二**：厨师住在办公室，需要做菜时走到厨房，做完回来。走路需要时间（网络延迟），但他的贵重物品安全地锁在办公室里。厨房着火了？换一间就行。

大多数生产环境选择模式二，因为**安全和可维护性的价值远大于几十毫秒的延迟**。

---

## 为什么重要

1. **安全不是附加功能，是架构决策**。你在设计阶段选择的模式，决定了系统的安全天花板。模式一的安全天花板就是"Agent 和代码同权"，这在执行不可信代码的场景下是不可接受的。

2. **Agent 正在从"玩具"走向"生产"**。玩具阶段你可以把所有东西塞进一个容器跑起来。生产阶段你需要关注点分离、弹性伸缩、成本控制——这些都指向模式二。

3. **架构选择影响团队速度**。模式一每次改 Agent 逻辑都要重建镜像、重新部署。模式二改完代码直接生效。在快速迭代阶段，这个差异会被放大数十倍。

---

## 延伸思考

1. **混合模式可行吗？** 能否让 Agent 在沙箱内运行，但通过安全代理（Proxy）访问密钥，既保留低延迟又隔离敏感信息？
2. **WebAssembly 沙箱** 能否解决模式二的延迟问题？WASM 在本地运行但有沙箱隔离，可能是两种模式的折中方案。
3. **当 Agent 需要长时间运行**（几小时甚至几天），模式一的"常驻容器"和模式二的"按用付费"成本差异会怎样变化？
4. **多 Agent 协作场景**中，如果多个 Agent 共享同一个沙箱，权限管理会变得更复杂还是更简单？
5. **从模式一迁移到模式二的成本有多高？** 如果你一开始选了模式一，后来发现需要模式二的安全性，重构的代价是什么？

---

> **总结**：模式一适合原型和受信任环境，模式二适合生产和安全敏感场景。如果你不确定选哪个——选模式二。从安全的架构迁移到不安全的很容易，反过来很痛苦。
