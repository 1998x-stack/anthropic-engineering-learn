# 自主上下文压缩：让 Agent 自己决定何时"清理记忆"

**作者:** LangChain Accounts  
**来源:** LangChain Blog  
**日期:** 2026 年 3 月 11 日  
**阅读时间:** 约 8 分钟

---

> **一句话总结**  
> 上下文压缩（Context Compression）不该由固定阈值触发，而应让 Agent 像人一样自主判断"什么时候整理笔记最合适"——时机比阈值重要得多。

---

## 核心要点

1. **固定阈值压缩是次优方案** —— 在 85% 容量处一刀切，完全忽略当前工作状态
2. **压缩有好时机和坏时机** —— 任务边界处压缩是理想的，复杂重构中途压缩是灾难性的
3. **解决方案：给 Agent 一个压缩工具** —— 让它自己决定何时压缩，而不是被动触发
4. **从用户命令进化为自主决策** —— 从 `/compact` 手动指令，到 Agent 主动选择最佳时机
5. **哲学意义：少调参，多放权** —— 与其精心设计规则，不如给模型更多控制权

---

## 一、问题：固定阈值的"手术室悲剧"

### 85% 阈值怎么了？

大多数系统的做法很简单：当上下文窗口用到 85%，自动触发压缩。听起来合理，但它有一个致命缺陷——**完全不看你在干什么**。你可能正在做一个涉及 12 个文件的复杂重构，脑子里（上下文里）装着所有文件的依赖关系、修改计划、中间状态。这时候系统说"满了，我来帮你清理"——然后把你精心维护的工作记忆全部摘要掉。恢复过来？几乎不可能。

> **类比理解**  
> 想象你是一个外科医生，正在做一台复杂手术。器械全部摆好，切口已经打开，每一步都在你脑子里。这时候护士说："台面太乱了，我来收拾一下。"她把你一半的器械收走，换上一张写着"之前用了这些器械"的纸条。你能继续手术吗？固定阈值压缩就是这个"好心办坏事"的护士。

### 时机 vs 阈值：为什么时机更重要

| 维度 | 固定阈值（85%） | 自主选择时机 |
|------|----------------|-------------|
| 触发条件 | 容量到达某个数字 | Agent 判断当前是否适合 |
| 感知工作状态 | 完全不感知 | 知道自己在做什么 |
| 最坏情况 | 关键操作中途丢失上下文 | 几乎不会发生 |
| 压缩质量 | 机械摘要，不分轻重 | 知道什么该保留什么可丢弃 |
| 可预测性 | 高（但质量差） | 稍低（但质量好） |

## 二、为什么时机比阈值重要：深入分析

这一节是本文最关键的部分。很多工程师的直觉是"设一个合理的阈值就行了"，但这里有一个根本性的认知错误：**上下文的价值不是均匀分布的**。

### 2.1 上下文价值的"潮汐模型"

上下文的价值随工作进展像潮水一样涨落。任务开始时，你在加载信息，价值逐步上升；任务进行中，所有信息紧密关联，价值达到峰值；任务完成后，这些细节变成可压缩的"结论"，价值回落。固定阈值完全无视这个潮汐——它可能在涨潮最高点切一刀。

```
上下文价值
    │
高  │        ╱──╲            ╱──╲
    │       ╱    ╲          ╱    ╲
    │      ╱      ╲        ╱      ╲
    │     ╱   任务A ╲      ╱  任务B  ╲
低  │────╱    进行中  ╲────╱   进行中   ╲────
    │
    └──────────────────────────────────────→ 时间
         ↑              ↑
         坏时机           好时机
         (A 进行中)       (A 完成, B 未开始)
```

### 2.2 三个"不可压缩"的场景

有些时刻压缩就等于破坏，因为丢失的不是文字，而是**关系和状态**：

**场景一：多文件重构中途。** 你在重命名一个核心接口，已经改了 6 个文件，还剩 4 个。上下文里保存着"哪些改了、哪些没改、改了的有没有连带影响"。压缩后这些状态全丢了——你甚至不知道自己改到哪了。

**场景二：调试到一半。** 你已经排除了 5 个假设，正在验证第 6 个。上下文里记录着每个假设为什么被排除。压缩后这些推理过程消失了——你会重新走一遍已经排除的老路。

**场景三：复杂计划执行中。** 你制定了一个 8 步计划，正在执行第 4 步。前 3 步的结果影响着后 4 步的决策。压缩后计划本身可能被保留了，但前 3 步的具体结果和微调丢了。

### 2.3 为什么 Agent 比规则更擅长判断时机

核心原因很简单：**Agent 理解语义，规则只理解数字**。

Agent 知道"我刚完成一个任务，用户还没提出新需求"——这是一个完美的压缩窗口。Agent 知道"我正在做一个复杂的多步操作，每一步的中间结果都很关键"——这时候碰都不该碰。Agent 还知道"我即将需要读取大量新文件，最好先腾出空间"——这是一个主动出击的好时机。

规则只知道："85% 了，压。"

## 三、好的压缩时机：四类黄金窗口

```
┌──────────────────────────────────────────────────────────┐
│              四类黄金压缩时机                               │
│                                                          │
│  ① 任务边界        ② 结果已提取      ③ 大量新输入前        │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐         │
│  │ 旧任务完成 │     │ 研究完毕   │     │ 即将读取   │         │
│  │ 新任务未启 │     │ 结论在手   │     │ 大量文件   │         │
│  │ 安全压缩   │     │ 过程可丢   │     │ 先腾空间   │         │
│  └──────────┘     └──────────┘     └──────────┘         │
│                                                          │
│  ④ 复杂流程启动前                                          │
│  ┌──────────────────────────────────────┐                │
│  │ 即将开始重构/迁移/多文件编辑              │                │
│  │ 先清理无关上下文，腾出最大工作空间          │                │
│  └──────────────────────────────────────┘                │
└──────────────────────────────────────────────────────────┘
```

### 3.1 干净的任务边界

用户说"好的，谢谢，接下来我想做另一件事"。前一个任务的详细过程不再需要——只需保留结论。这是最自然的压缩点，就像你做完一道数学题，把草稿纸翻到新的一页。

### 3.2 从大量上下文中提取结果后

你让 Agent 研究一个技术方案，它读了 20 篇文档，最终给出结论。那 20 篇文档的原文不需要保留，结论才是核心。就像你读完一本书做了笔记——书可以还给图书馆，笔记留下就够了。

### 3.3 即将消费大量新上下文前

Agent 知道接下来要读一个大型代码文件或一份长草稿。与其等到读完后被动触发阈值（那时候新旧信息混在一起，很难分清该丢什么），不如提前主动清理，为新信息腾出空间。这是"先收拾桌子再摊开新资料"的逻辑。

### 3.4 进入复杂多步骤流程前

即将开始一个大型重构或迁移任务。此时应该清理掉之前的闲聊和无关上下文，确保工作空间最大化。就像手术前清空手术台——你需要最大的操作空间。

## 四、工具实现：中间件方案

实现方式很简洁：把压缩能力包装成一个工具（Tool），通过中间件（Middleware）注入 Agent 的工具集。

```
Agent 工具集
    │
    ├── search_web()        ← 常规工具
    ├── read_file()         ← 常规工具
    ├── write_file()        ← 常规工具
    │
    └── compress_context()  ← 压缩工具 (由中间件注入)
            │
            ├── 保留最近 10% 的消息（完整保留）
            ├── 将其余 90% 生成摘要
            └── 替换原始上下文
```

| 实现细节 | 说明 |
|---------|------|
| 注入方式 | `create_summarization_tool_middleware` 中间件 |
| 保留策略 | 最近 10% 消息原封不动保留 |
| 摘要范围 | 其余 90% 消息生成结构化摘要 |
| 恢复机制 | 文件系统保留完整历史，摘要丢失信息可从文件恢复 |
| Agent 行为 | 保守调用，但选择的时机准确 |

## 五、实际经验：保守但精准

实际部署中观察到一个有趣现象：Agent 使用压缩工具的频率比你预期的**低得多**。它不会频繁压缩，而是倾向于"能不压就不压"——直到它真正判断"现在是好时机"。这种保守行为恰恰是正确的。频繁压缩的代价远大于偶尔容量吃紧的代价。

文件系统在这里扮演了安全网的角色。即使压缩丢失了某些细节，Agent 仍然可以重新读取文件来恢复信息。这意味着压缩不是不可逆的——上下文窗口里的信息可能丢了，但磁盘上的真相还在。

> **类比理解**  
> 这就像一个经验丰富的厨师管理灶台。他不会每隔 5 分钟就把灶台清空一次（那会打断烹饪节奏），也不会等到灶台完全乱套了才收拾（那会出事故）。他在一道菜出锅后、下一道菜开始前的间隙收拾——既高效又安全。而且就算他清掉了某个食材的包装，食谱还在抽屉里，随时可以翻出来看。

## 六、哲学意义：苦涩教训的又一例证

Rich Sutton 的"苦涩教训"（The Bitter Lesson）指出：在 AI 的历史上，每一次人类精心设计的规则和启发式方法，最终都被更通用的学习方法超越。上下文压缩的故事完美重现了这个模式：

```
手工方案的进化路径：
固定阈值 → 分级阈值 → 多条件触发 → 越来越复杂的规则
     ↓          ↓            ↓              ↓
    简单       还行        开始脆弱       维护噩梦

放权方案：
给 Agent 一个压缩工具，让它自己决定
     ↓
   开箱即用，持续随模型能力提升而改善
```

与其花几周时间调阈值、加特殊逻辑、处理边界情况，不如**给模型一个工具和基本的指导原则**，让它自己判断。这不是偷懒——这是对模型能力的合理利用。

---

## 为什么重要

1. **直接影响 Agent 的可靠性。** 在错误时机压缩上下文，Agent 会丢失关键工作状态，导致重复劳动甚至产出错误结果。这不是性能问题，是正确性问题。

2. **代表了一种重要的设计范式转移。** 从"人写规则控制 Agent"到"给 Agent 工具让它自己控制"——这个思路适用于远不止压缩的场景。任何需要判断"时机"的系统决策，都值得考虑交给 Agent。

3. **是构建长时运行 Agent 的关键基础设施。** 随着 Agent 任务越来越复杂、运行时间越来越长，上下文管理从"可选优化"变成"必须解决的核心问题"。自主压缩是目前最务实的方案。

## 延伸思考

1. **压缩粒度问题。** 当前方案是"保留 10%，摘要 90%"。但如果最近 10% 的消息里有一半是无关紧要的闲聊呢？未来是否应该让 Agent 不仅决定"何时压缩"，还决定"保留哪些、丢弃哪些"？

2. **多 Agent 场景的压缩协调。** 如果多个 Agent 共享上下文，一个 Agent 决定压缩会影响其他 Agent。如何协调？是否需要"压缩共识"？

3. **压缩作为可逆操作。** 当前依赖文件系统做恢复。如果上下文中的关键信息不在文件里（比如用户口头说的需求），丢了就真的丢了。是否应该设计"压缩回滚"机制？

4. **模型自我评估的可靠性。** 这个方案的前提是"模型能准确判断什么时候压缩合适"。如果模型判断失误呢？是否需要一个兜底机制——比如在自主压缩的基础上加一个宽松的硬性上限（95%）？

5. **从压缩到遗忘。** 人类不只是"压缩"记忆，还会主动"遗忘"不重要的东西。Agent 是否也应该有"选择性遗忘"的能力——不只是摘要，而是彻底删除某些低价值信息？
