# 什么是认知架构

**作者:** Harrison Chase / LangChain  
**来源:** [LangChain Blog](https://blog.langchain.dev/what-is-a-cognitive-architecture/)  
**日期:** 2024 年 7 月 6 日  
**阅读时间:** 约 6 分钟

---

> **一句话总结**  
> 认知架构（Cognitive Architecture）决定了你的 LLM 应用中"代码"和"大模型"各自扮演什么角色——是你写好剧本让它念台词，还是给它一个目标让它自由发挥。选对架构，比调好提示词更重要。

---

## 核心要点

1. **认知架构 = 系统的自主程度** —— 它回答一个核心问题：LLM 在你的应用中有多大的决策权？
2. **五级光谱，不是非此即彼** —— 从纯代码到全自主 Agent，中间有三个关键过渡地带，每一级都有明确的适用场景
3. **没有最优架构，只有最合适的** —— 选择认知架构应该像选择提示词一样频繁地实验，而不是一开始就锁死
4. **可控性与自主性是跷跷板** —— 自主程度越高，能力越强，但可预测性越低，调试越难
5. **LangGraph 的哲学转向** —— 从"预制积木"转向"底层控件"，把架构选择权还给开发者

---

## 类比理解：从自动售货机到全权管家

> 想象你要解决"每天吃午饭"这个问题，有五种方案：
>
> 1. **自己做饭**（纯代码）—— 你完全掌控每一步，但所有工作都是你干的
> 2. **点一份固定套餐**（单次 LLM 调用）—— 你说"来一份盖浇饭"，餐厅做好送来，简单直接
> 3. **先看菜单再点菜**（LLM 调用链）—— 服务员先推荐今日特供，你选好后厨房再做，两步完成
> 4. **问服务员"你看我吃什么好"**（路由器）—— 服务员根据你的口味帮你选餐厅和菜品，你可能会被带到意想不到的地方
> 5. **雇一个全权管家**（自主 Agent）—— 管家自己判断你饿不饿、想吃什么、去哪买、怎么做，你只说"安排午饭"
>
> 管家最省心，但你无法预知他会做什么。自动售货机最可控，但只能出固定的东西。认知架构的选择，就是在"省心"和"可控"之间找平衡点。

## 五级认知架构详解

### 总览表格

| 级别 | 架构类型 | LLM 参与度 | 确定性 | 典型场景 | 一句话特征 |
|:---:|---------|:--------:|:-----:|---------|----------|
| 1 | 纯代码（Code） | 0% | 100% | 传统软件 | 不算认知架构 |
| 2 | 单次调用（Single LLM Call） | 低 | 高 | 简单聊天机器人、文本分类 | 一问一答 |
| 3 | 调用链（Chain） | 中 | 中高 | 复杂 RAG、多步提取 | 串联流水线 |
| 4 | 路由器（Router） | 中高 | 中 | 客服分流、意图分发 | LLM 选路径 |
| 5 | 自主 Agent（Autonomous Agent） | 高 | 低 | 编程助手、研究分析 | LLM 开循环 |

### 架构光谱 ASCII 图

```
自主程度从低到高 ──────────────────────────────────>

  ┌─────────┐   ┌───────────┐   ┌─────────┐   ┌─────────┐   ┌───────────┐
  │  纯代码  │   │ 单次 LLM  │   │ 调用链   │   │  路由器  │   │ 自主 Agent │
  │         │   │   调用     │   │ (Chain)  │   │(Router) │   │           │
  └─────────┘   └───────────┘   └─────────┘   └─────────┘   └───────────┘
  代码 100%      代码主导        代码编排        LLM 决策       LLM 主导
  LLM 0%        LLM 执行        LLM 多步        代码执行       代码辅助

  <── 可控、可预测 ──────────────────────── 灵活、强大 ──>
  <── 调试容易 ──────────────────────────── 调试困难 ──>
```

## 第一级：纯代码

**什么是：** 传统软件开发，没有 LLM 参与。所有逻辑都写死在代码里。

**为什么提它：** 它是光谱的起点，提醒你一个重要事实——不是所有问题都需要 LLM。如果 `if-else` 就能解决，不要硬塞一个大模型进去。

**适用场景：** 规则明确、无需理解自然语言的任务。比如数据格式转换、数学计算、固定流程的表单校验。

> **延伸思考：** 很多团队犯的第一个错误就是"用 LLM 做不需要 LLM 的事"。当你的输入和输出都是结构化的，纯代码几乎总是更好的选择——更快、更便宜、100% 可预测。

---

## 第二级：单次 LLM 调用

**什么是：** 用户输入进来，调用一次 LLM，返回结果。中间没有额外的逻辑步骤。最简单的 LLM 应用形式。

**工作流程：**

```
用户输入 ──> [系统提示词 + 用户消息] ──> LLM ──> 输出
                                          │
                                     （一次调用，直来直去）
```

**适用场景：**

| 场景 | 为什么适合单次调用 |
|------|------------------|
| 简单聊天机器人 | 用户说一句话，回一句话，不需要外部信息 |
| 文本分类/情感分析 | 输入一段文本，输出一个标签，逻辑闭合 |
| 文本改写/翻译 | 输入原文，输出译文，无需中间步骤 |
| 简单摘要 | 文本长度在上下文窗口内，一次就能处理 |

**为什么重要：** 很多 LLM 应用到这一级就够了。不要因为"Agent 更酷"而过度设计。如果一次调用就能解决问题，加更多步骤只会增加延迟、成本和出错概率。

> **类比：** 就像你问一个朋友"这句话什么意思"——他想一下直接回答你，不需要去图书馆查资料，也不需要开会讨论。

---

## 第三级：LLM 调用链（Chain）

**什么是：** 多次 LLM 调用串联起来，前一步的输出是后一步的输入。每一步做什么由代码预先决定，LLM 只负责执行每一步。

**工作流程（以复杂 RAG 为例）：**

```
用户问题
   │
   v
┌──────────────┐
│ 第一步：LLM  │ ──> 生成搜索查询（把模糊问题变成精确检索词）
│ 生成查询     │
└──────┬───────┘
       │ 搜索查询
       v
┌──────────────┐
│ 第二步：检索  │ ──> 从向量数据库拿到相关文档（代码执行，非 LLM）
│ 相关文档     │
└──────┬───────┘
       │ 相关文档 + 原始问题
       v
┌──────────────┐
│ 第三步：LLM  │ ──> 基于检索到的文档生成最终答案
│ 生成答案     │
└──────────────┘
```

**适用场景：**

| 场景 | Chain 结构 |
|------|-----------|
| 复杂 RAG | 查询改写 → 检索 → 生成答案 |
| 多步提取 | 提取实体 → 验证 → 结构化输出 |
| 内容创作流水线 | 列大纲 → 写初稿 → 润色 |
| 数据清洗 | 解析格式 → 标准化 → 校验 |

**关键特征：** 每一步做什么是确定的（代码写死了流程），但每一步的输出是不确定的（LLM 生成的内容可能不同）。这意味着你在可控性和灵活性之间找到了一个不错的平衡点。

**为什么重要：** Chain 是大多数生产级 LLM 应用的最佳起点。它比单次调用强大得多（可以拆分复杂任务），又比路由器和 Agent 可控得多（流程是固定的）。

> **类比：** 像工厂流水线。每个工位做什么是固定的（第一个拧螺丝、第二个装外壳、第三个检测），但每个工人在自己工位上有一定的自由度。

---

## 第四级：路由器（Router）

**什么是：** LLM 不再只是执行者，而是开始做决策——它决定下一步走哪条路。代码提供若干可选路径，LLM 根据输入选择最合适的那条。

**工作流程：**

```
用户输入
   │
   v
┌────────────┐
│   LLM      │ ──> "这个问题应该走哪条路？"
│  （路由）   │
└──┬───┬───┬─┘
   │   │   │
   v   v   v
 路径A 路径B 路径C
 (退款) (技术) (投诉)
   │   │   │
   v   v   v
各自的处理逻辑（可以是代码、LLM 调用链、或更多路由）
```

**关键转折点：** 路由器是整个光谱中最重要的分界线。从这里开始，LLM 的决策引入了真正的不确定性——你无法 100% 预测系统会走哪条路。同样的输入在不同时间可能走不同路径。

**适用场景：**

| 场景 | 路由逻辑 |
|------|---------|
| 智能客服 | 根据问题类型分发到不同处理流程 |
| 多模型调度 | 简单问题用小模型，复杂问题用大模型 |
| 工具选择 | 根据用户意图决定调用计算器、搜索还是数据库 |
| 多语言处理 | 检测语言后路由到对应的处理管线 |

**为什么重要：** 路由器是从"可预测系统"到"不可预测系统"的转折点。一旦你让 LLM 做路由决策，你就必须接受一个事实：系统的行为不再完全由你的代码决定。你需要更强的监控、日志和回退机制。

> **类比：** 像医院的分诊台。护士（LLM）根据你的症状决定你该去内科、外科还是急诊。大多数时候分得对，但偶尔会分错，所以每个科室还有医生（代码逻辑）做二次确认。

---

## 第五级：自主 Agent

**什么是：** LLM 在一个循环中运行，自己决定下一步做什么、调用什么工具、什么时候结束。代码只提供工具和约束，不规定流程。

**工作流程：**

```
用户目标
   │
   v
┌─────────────────────────┐
│    Agent 循环            │
│  ┌──────────────────┐   │
│  │ LLM 思考：       │   │
│  │ 下一步做什么？    │   │
│  └────┬─────────────┘   │
│       │                  │
│       v                  │
│  ┌──────────────────┐   │
│  │ 选择并调用工具    │   │     可用工具：
│  │ (搜索/计算/写文件) │  │ <── [搜索] [计算] [代码执行]
│  └────┬─────────────┘   │     [文件读写] [API 调用] ...
│       │                  │
│       v                  │
│  ┌──────────────────┐   │
│  │ 观察工具结果      │   │
│  │ 是否完成目标？    │   │
│  └────┬─────────────┘   │
│       │                  │
│       ├── 否 ──> 回到"思考"│
│       │                  │
│       └── 是 ──> 输出结果 │
└─────────────────────────┘
```

**适用场景：**

| 场景 | 为什么需要 Agent | 风险提示 |
|------|----------------|---------|
| 编程助手 | 写代码→运行→看报错→改代码，循环次数无法预知 | Token 消耗大，可能陷入死循环 |
| 深度研究 | 搜索→阅读→追问→再搜索，信息需求不确定 | 可能偏离主题，结果质量波动 |
| 数据分析 | 探索数据→发现模式→验证假设→调整方向 | 分析路径不可预测 |
| 复杂工作流编排 | 子任务之间有动态依赖关系 | 调试极其困难 |

**关键特征：** LLM 不仅决定"走哪条路"（路由器也能做），还决定"走多少步"和"什么时候停"。这让 Agent 能处理事先无法完全规划的任务，但也意味着你交出了大部分控制权。

**为什么重要：** Agent 是能力最强的架构，但也是最难驯服的。生产环境中的 Agent 需要：超时机制（防止无限循环）、成本上限（防止烧钱）、人工审批节点（关键操作前让人确认）、详细日志（出问题时能回溯）。

> **类比：** 像给一个实习生布置开放性任务："去调研一下竞品"。聪明的实习生可能交出超预期的报告，但他也可能花三天钻进了一个无关紧要的兔子洞。你需要定期检查进度，而不是三天后才看结果。

## 如何选择认知架构

```
你的任务需要 LLM 吗？
   │
   ├── 不需要 ──> 纯代码（第一级）
   │
   └── 需要
        │
        一次 LLM 调用能搞定吗？
        │
        ├── 能 ──> 单次调用（第二级）
        │
        └── 不能
             │
             步骤是否固定？
             │
             ├── 固定 ──> 调用链（第三级）
             │
             └── 不固定
                  │
                  路径是有限的几条吗？
                  │
                  ├── 是 ──> 路由器（第四级）
                  │
                  └── 不是，步数和路径都不确定 ──> Agent（第五级）
```

**核心原则：** 从最简单的架构开始，只在需要时才升级。大多数生产应用停留在第三级（Chain）就够了。跳到第五级（Agent）之前，先问自己：第三级或第四级真的解决不了这个问题吗？

## LangGraph 的设计哲学转向

Harrison Chase 在文中反思了 LangChain 的演进路径。早期 LangChain 追求易用性，提供大量预制的 Chain（调用链），开发者几行代码就能搭出一个 RAG 应用。但这种"高层级封装"带来了一个问题：当你需要定制认知架构时，预制组件反而成了限制。

LangGraph 的哲学是反过来——提供低层级、高可控的基础设施。你自己定义状态（State）、节点（Node）和边（Edge），完全掌控信息的流向和 LLM 的决策权限。

| 维度 | 早期 LangChain | LangGraph |
|------|---------------|-----------|
| 抽象层级 | 高（预制 Chain） | 低（图节点 + 边） |
| 上手速度 | 快（几行代码） | 慢（需要理解图结构） |
| 定制能力 | 低（受限于预制模板） | 高（完全自定义） |
| 适合谁 | 快速原型验证 | 生产级应用开发 |
| 核心理念 | 让开发者少写代码 | 让开发者完全掌控架构 |

> **为什么重要：** 这种转变反映了整个 LLM 应用生态的成熟——从"能跑就行"到"跑得好、跑得稳、出了问题能查"。认知架构不是一次性选择，而是随着你对问题理解的深入不断调整的。

## 延伸思考

1. **你现在的项目用的是哪一级认知架构？** 是因为真的需要，还是因为"Agent 听起来更酷"？试试降一级看看能不能跑通——降级往往意味着更快、更便宜、更可控。

2. **混合架构才是常态。** 一个真实的 LLM 应用往往在不同子任务上使用不同级别的架构。比如：用 Chain（第三级）做 RAG 检索和回答，用 Router（第四级）做意图分发，只在需要开放探索的场景用 Agent（第五级）。

3. **"像选择提示词一样频繁地实验不同架构"** 这句话是全文最关键的一句。大多数团队在第一天选定了架构就再也不改了，但认知架构应该是你持续调优的对象，跟提示词一样。
