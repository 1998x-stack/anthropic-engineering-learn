# MCP：昙花一现还是未来标准？

**作者:** Harrison Chase (CEO) vs Nuno Campos (LangGraph Lead)  
**来源:** [LangChain Blog](https://blog.langchain.dev/mcp-fad-or-fixture/)  
**日期:** 2025 年 3 月 8 日  
**阅读时间:** 约 10 分钟

---

> **一句话总结**  
> MCP (Model Context Protocol) 的真正价值不在于帮开发者构建自己的 Agent，而在于让非开发者给别人的 Agent 添加工具——但当前的工具调用成功率和协议设计仍有硬伤。

---

## 核心要点

1. **MCP 的杀手场景是"给你控制不了的 Agent 加工具"** —— 你不是 Agent 的开发者，但你想让它多干一件事
2. **非开发者的赋能才是真正的增量** —— 开发者早就能自己集成工具，MCP 对他们没什么新价值
3. **"随便插工具就能用"是幻觉** —— Agent 需要针对每个工具定制提示词和架构，通用插拔目前行不通
4. **工具调用成功率约 50%** —— 基准测试显示，当前模型调用工具的能力远没到"开箱即用"的水平
5. **MCP 的上限是 Zapier** —— 长尾集成、自动化拼接，而不是高可靠的生产系统

---

## 一、MCP 到底解决什么问题？

### Harrison 的论点：控制权之外的集成

Harrison 认为，MCP 的核心价值可以用一句话概括：**给你控制不了的 Agent 添加工具**。你公司用了一个第三方 Agent 产品，你没法改它的代码，但你希望它能连上你的内部数据库。MCP 就是为这个场景而生的。

更重要的是，这个场景的用户往往不是开发者。产品经理、运营人员、业务分析师——他们没法写代码集成工具，但他们最清楚自己需要什么。MCP 把"给 Agent 加能力"这件事的门槛降到了"安装插件"的水平。

```
传统方式 (开发者专属)：
  业务需求 → 写代码 → 集成 API → 测试 → 部署
  ⏱️ 数天到数周

MCP 方式 (人人可用)：
  业务需求 → 安装 MCP Server → Agent 自动发现工具
  ⏱️ 数分钟
```

> **类比理解**  
> 想象你买了一台智能音箱（Agent），你没法改它的固件。但你希望它能控制你家新买的空气净化器。MCP 就像一个通用的智能家居协议——只要空气净化器支持这个协议，音箱就能控制它，不需要你会写代码。

### Nuno 的反驳：这个类比有致命缺陷

Nuno 直接泼冷水：智能家居协议之所以能工作，是因为"开灯"这个动作是确定性的——要么开，要么不开。但 Agent 调用工具是概率性的。模型要理解工具描述、构造正确参数、处理返回结果，每一步都可能出错。

LangChain 自己就有 500 个预建工具集成，存在了两年多。结果呢？**生产环境中几乎没人用这些通用工具**。大家最终都是针对自己的场景定制集成。500 个工具库没人用，MCP 凭什么认为自己会不同？

## 二、工具调用的成功率问题

### 现实数据：大约 50%

Nuno 指出，当前工具调用的基准测试 (Benchmark) 显示，模型正确调用工具的成功率大约在 **50%** 左右。这意味着你让 Agent 用一个工具，它有一半的概率会搞砸——参数错误、调错工具、甚至完全无视工具的存在。

```
工具调用成功率的现实：

理想状态         ████████████████████  100%
Harrison 预期    ████████████████░░░░   80%+ (模型会持续进步)
当前基准         ██████████░░░░░░░░░░   50%  (Nuno 的数据)
生产可接受线     ████████████████░░░░   80%  (通常要求)

差距 ═══════════════ 30%+ ═══════════════
```

| 失败类型 | 说明 | 频率 |
|----------|------|------|
| 参数错误 | 类型不对、缺少必填字段 | 高 |
| 工具选择错误 | 有 10 个工具，选了错的那个 | 中 |
| 忽略工具 | 明明该用工具，模型选择自己编答案 | 中 |
| 结果误解 | 工具返回了正确数据，模型理解错了 | 低-中 |

### Harrison 的回应：模型在进步

Harrison 不否认当前成功率低，但他认为这是**暂时的**。模型能力每隔几个月就上一个台阶。GPT-3 时代工具调用几乎不可用，GPT-4 就已经大幅改善，未来的模型只会更好。投资 MCP 生态就是在赌模型进步这条确定性趋势。

> **类比理解**  
> Harrison 的逻辑像是 2007 年投资移动互联网——当时手机网速慢、触屏不灵敏、App 生态为零。但你赌的是硬件和网络会持续进步，所以提前布局协议和生态是对的。Nuno 的反驳则是：你不能用一个 50% 成功率的系统去服务客户，然后告诉他们"等明年就好了"。

## 三、Agent 真的能"即插即用"工具吗？

### Nuno 的核心质疑

Nuno 认为，MCP 的隐含假设是：Agent 拿到一个新工具的描述后，就能正确使用它。但在实践中，**好的 Agent 需要针对每个工具深度定制**：

```
MCP 的隐含假设：

┌──────────┐    安装     ┌──────────┐    自动    ┌──────────┐
│ MCP 工具  │ ────────→ │  Agent   │ ────────→ │ 正确调用  │
│ (任意)    │           │ (通用)    │           │ (每次)    │
└──────────┘            └──────────┘            └──────────┘

现实情况：

┌──────────┐    安装     ┌──────────┐           ┌──────────┐
│ MCP 工具  │ ────────→ │  Agent   │ ────────→ │ 经常失败  │
│ (任意)    │           │ (通用)    │           │ (约50%)   │
└──────────┘            └──────────┘            └──────────┘
                              │
                              │ 要想可靠
                              ▼
                        ┌──────────┐
                        │ 定制提示词 │
                        │ 定制架构   │
                        │ 定制错误处理│
                        │ 定制重试逻辑│
                        └──────────┘
```

一个搜索工具和一个数据库查询工具，对 Agent 来说不只是"多了一个函数"。搜索工具需要 Agent 学会分解查询、处理空结果、合并多次搜索；数据库工具需要 Agent 理解 Schema、构造安全的 SQL、处理超时。这些都需要**针对性的提示词和执行逻辑**，不是靠一个通用协议就能解决的。

### Harrison 的让步

Harrison 在这一点上部分认同：**对于开发自己 Agent 的开发者来说，MCP 确实没什么用**。你完全可以直接集成工具，甚至写得更好。MCP 的价值场景是"你开发了一个 Agent 产品，你的用户想给它加工具，但你不知道用户需要什么工具"。

## 四、MCP 协议本身的设计问题

### Nuno 的四个改进方向

Nuno 不是反对 MCP 的需求，而是认为当前协议设计过度复杂，需要大幅简化：

| 问题 | 现状 | Nuno 的建议 |
|------|------|-------------|
| 功能臃肿 | 包含提示词 (Prompts) 和补全 (Completions) 功能 | 砍掉，只保留工具 (Tools) 和资源 (Resources) |
| 通信复杂 | 要求双向通信 (Bidirectional) | 改为单向请求-响应，降低实现难度 |
| 有状态 | 服务端需要维护会话状态 | 改为无状态 (Stateless)，方便服务端部署 |
| 质量损失 | 通用描述 vs 定制提示词 | 提供"增强元数据"机制，弥补精度损失 |

```
当前 MCP 协议架构：

┌────────────┐  双向通信   ┌────────────┐
│  MCP Client │ ◄────────► │ MCP Server  │
│  (Agent 端) │  有状态     │ (工具端)    │
│             │  Prompts    │             │
│             │  Completions│             │
│             │  Tools      │             │
│             │  Resources  │             │
└────────────┘             └────────────┘

Nuno 建议的简化版：

┌────────────┐  单向请求   ┌────────────┐
│  MCP Client │ ──────────►│ MCP Server  │
│  (Agent 端) │  无状态     │ (工具端)    │
│             │  Tools      │             │
│             │  Resources  │             │
└────────────┘◄────────────└────────────┘
                  响应
```

> **类比理解**  
> 当前的 MCP 像是在设计一个通用遥控器，不但要能控制电视，还内置了语音助手、游戏手柄、温度计等功能。Nuno 的观点是：先把"控制电视"做到极致，其他的等市场真正需要时再加。否则这个遥控器太复杂，没人愿意适配。

## 五、双方的共识：Zapier 是天花板

### 一致认同的两件事

尽管激烈辩论，Harrison 和 Nuno 在两个关键点上完全一致：

**共识一：MCP 对自建 Agent 的开发者没用。** 如果你在开发自己的 Agent，你会直接集成工具、写定制提示词、控制执行流程。MCP 在这个场景下只是多了一层没必要的抽象。

**共识二：MCP 的上限是成为"AI 时代的 Zapier"。** 大量长尾集成、非开发者自助操作、低代码自动化拼接。这已经是一个巨大的市场，但它不是"Agent 的通用工具协议"那样宏大的叙事。

```
MCP 价值谱系：

低价值 ◄─────────────────────────────────────────► 高价值

开发者自建Agent   │   企业内部集成   │   非开发者自助   │   长尾SaaS集成
(没什么用)        │  (有些用)       │  (核心价值)      │  (最大想象空间)
                  │                 │                  │
                  │       MCP 价值区间 ██████████████████
```

## 六、模型进步能解决一切吗？

### 这是双方分歧的根源

Harrison 的整个论点建立在一个核心假设上：**模型会持续变强，工具调用成功率会从 50% 涨到 95%+**。如果这个假设成立，今天 MCP 的所有问题都是暂时的，提前布局生态就是正确策略。

Nuno 则认为这种"等模型进步"的心态是危险的。即使模型进步到 95% 的工具调用成功率，**一个包含 5 步工具调用的任务，整体成功率是 0.95^5 ≈ 77%**。对于 10 步任务，就降到了 60%。在生产环境中，这仍然不够。

| 单步成功率 | 3 步任务 | 5 步任务 | 10 步任务 |
|-----------|---------|---------|----------|
| 50% | 12.5% | 3.1% | 0.1% |
| 80% | 51.2% | 32.8% | 10.7% |
| 90% | 72.9% | 59.0% | 34.9% |
| 95% | 85.7% | 77.4% | 59.9% |
| 99% | 97.0% | 95.1% | 90.4% |

> **为什么重要**  
> 这张表揭示了一个残酷的数学事实：即使单步看起来"够用"，多步串联后可靠性会急剧下降。这就是为什么 Nuno 坚持认为，光靠模型进步不够——你还需要更好的架构设计、重试机制和错误恢复策略。MCP 协议本身需要为这些提供支持，而不是假装它们不存在。

## 七、总结：MCP 的命运取决于什么？

```
MCP 成功的条件：

必要条件（缺一不可）：
├── 模型工具调用能力持续提升（Harrison 赌的方向）
├── 协议本身大幅简化（Nuno 的改进建议）
├── 非开发者生态真正繁荣（Zapier 类比成立的前提）
└── 足够多的 MCP Server 被构建和维护

充分条件（决定天花板高度）：
├── 是否出现"MCP 原生"的杀手应用
├── 大厂是否统一采纳（而不是各搞一套）
└── 是否解决多步任务的可靠性问题
```

Harrison 和 Nuno 的辩论本质上是**节奏之争**：Harrison 认为现在就该全力投入 MCP 生态，因为趋势不可逆；Nuno 认为协议需要先"修好"再推广，否则会像 LangChain 的 500 个工具库一样——建了没人用。

---

## 延伸思考

1. **标准之争的历史教训** —— USB 打败了无数竞品接口，但它成功的前提是"插上就能用"的可靠性。MCP 目前做不到这一点。在可靠性达标之前，"标准"只是一厢情愿。

2. **Zapier 模式真的够大吗？** —— Zapier 是一家价值数十亿美元的公司，但它从来没有成为"软件基础设施的核心协议"。如果 MCP 的上限是 Zapier，那它是一个好生意，但不是一场革命。

3. **谁会赢？** —— 也许双方都对。MCP 作为概念会存活下来（给别人 Agent 加工具的需求是真实的），但当前的协议实现可能会被大幅重写甚至替换。最终胜出的版本，大概率是 Nuno 描述的那个简化版——更少功能、更低门槛、更高可靠性。

---

> **一句话带走**  
> MCP 解决的是真问题（非开发者给 Agent 加工具），但当前的答案还不够好（50% 成功率 + 过度设计的协议）。方向对了，但路还没修好。
