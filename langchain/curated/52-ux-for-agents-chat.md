# AI Agent 的用户体验（一）：聊天界面

> 一句话总结：聊天（Chat）是我们与 AI Agent 交互的第一种方式，就像早期计算机的终端一样 -- 直接、透明、低门槛，但未来一定会演化出更多形态。

---

## 核心要点

| 要点 | 说明 |
|------|------|
| 流式聊天是当前主流 | 用户能实时看到 Agent 的思考过程和中间步骤 |
| 非流式聊天也有价值 | 结果一次性返回，适合"委托"场景，用户不需要盯着过程 |
| 聊天只是起点 | 就像计算机从命令行演化到图形界面，Agent 的交互方式也会持续进化 |

---

## 一、流式聊天（Streaming Chat）：让你看到 Agent 在想什么

流式聊天（Streaming Chat）是目前最常见的 Agent 交互方式。简单说，就是 Agent 一边思考、一边把结果"流"给你看 -- 你能实时看到每个 token 被生成出来。

为什么流式很重要？因为 LLM 的推理需要时间。如果你发了一个问题，然后盯着空白屏幕等 30 秒，体验会非常糟糕。流式输出让你知道"它在干活了"，而且你能看到它调了哪些工具、每一步的结果是什么。

编程 LLM 的核心方式是自然语言。在聊天界面里，你用自然语言直接和 LLM 对话，中间几乎没有任何障碍。这意味着你和模型之间的距离是最短的。

```
用户提问 --> [LLM 开始思考] --> 实时流出 token --> 调用工具 --> 返回结果 --> 继续生成 --> 最终回答
   |              |                    |               |              |
   你能看到      你能看到            你能看到        你能看到       你能看到
   一切过程      一切过程            一切过程        一切过程       一切过程
```

### 类比理解

想象你去餐厅，有两种体验：

- **流式聊天** = 开放式厨房。你坐在吧台前，看着厨师切菜、炒菜、装盘。全程透明，你随时可以说"少放点盐"。
- **传统 API 调用** = 封闭厨房。你点完菜就等着，菜上来之前完全不知道里面在发生什么。

流式聊天就是那个开放式厨房 -- 你对整个过程有完全的可见性。

---

## 二、非流式聊天（Non-Streaming Chat）：有时候"不看过程"反而更好

非流式聊天（Non-Streaming Chat）就是传统的请求-响应模式：你发消息，等一会儿，结果一次性返回。两年前我们管这个叫"聊天"，现在反倒要加个"非流式"来区分了。

非流式的最大问题是你看不到 Agent 在干嘛，"蒙在鼓里"的感觉不好。但换个角度想，这真的是问题吗？

Linus Lee 提出了一个关于"委托"（Delegation）的有趣观点。他在设计自己的 AI 工具时，刻意把界面做得尽可能不透明：

> "我故意把界面设计得尽可能不透明。"

这听起来反直觉，但逻辑是这样的：当你真正信任一个助手时，你不需要盯着他的每一步操作。你把任务交出去，然后去做自己的事，等结果就好。

```
流式聊天:    你 --> [实时观察每一步] --> 结果
                     (全程参与)

非流式聊天:  你 --> [黑盒处理中...] --> 结果
                     (你去做别的事)
```

### 类比理解

这就像你交代工作给同事：

- **流式** = 你站在同事身后看他做。适合你不太放心的新任务、或者需要随时纠正的场景。
- **非流式** = 你发条消息说"帮我搞定这个"，然后去开会了。适合你信任对方、任务明确的场景。

两种方式没有绝对的优劣，关键是场景匹配。

---

## 三、流式 vs 非流式：对比一览

| 维度 | 流式聊天 | 非流式聊天 |
|------|---------|-----------|
| 透明度 | 高，实时可见 | 低，结果一次性返回 |
| 用户参与度 | 高，可随时干预 | 低，发完就等 |
| 信任要求 | 低，眼见为实 | 高，需要信任 Agent |
| 适合场景 | 探索性任务、调试 | 成熟任务、批量处理 |
| 用户体验 | 感觉在"对话" | 感觉在"委托" |
| 延迟感知 | 低（逐步输出） | 高（等待黑盒） |

### 聊天 UX 的共同优势

不管流式还是非流式，聊天界面有两个核心优势：

- **直接与模型交互**：没有中间层，你说什么模型就收到什么
- **支持追问和纠正**：对话式交互天然支持多轮沟通，错了可以立刻纠正

## 四、聊天只是起点：Agent UX 的进化之路

聊天之于 LLM，就像终端（Terminal）之于早期计算机。

早期计算机只有命令行终端，用户直接输入指令、查看输出。终端提供了对底层操作系统最直接的访问方式。但随着时间推移，计算机发展出了图形用户界面（GUI）-- 窗口、图标、菜单、鼠标。

LLM 的交互方式也在走同样的路。聊天是我们发明的第一种交互方式，它直接、低门槛，但它不会是唯一的方式。

```
计算机的演化:     终端 (Terminal) --> 图形界面 (GUI) --> 触控 --> 语音 --> ...
                      |
LLM 的演化:       聊天 (Chat) --> 环境式 (Ambient) --> 协作式 --> 更多可能...
                      |
                   你在这里
```

### 为什么重要

理解"聊天只是起点"这件事非常重要，因为：

1. **产品设计者**：不要把自己局限在聊天框里。你的用户真的需要一个对话界面吗？也许他们需要的是一个能在后台帮他们干活的助手。
2. **开发者**：你的 Agent 架构应该与 UX 解耦。底层的推理和工具调用逻辑，不应该和"聊天"这种特定的交互方式绑死。
3. **用户**：流式聊天的价值在于学习阶段 -- 当你还在探索 LLM 能做什么的时候，实时看到过程很有价值。但当你熟悉了之后，你会想要更高效的交互方式。

## 延伸思考

1. **你现在用的 AI 工具，是流式还是非流式？** 想想看，如果换成另一种方式，体验会变好还是变差？
2. **什么时候你会希望"看不到过程"？** 比如你让 AI 写一篇长文，你真的需要盯着每个字被打出来吗？
3. **下一代 Agent UX 会是什么样？** 这个系列的后续文章会讨论"环境式"（Ambient）和"协作式"（Collaborative）等新范式 -- 那些可能才是 Agent 真正大规模落地的交互形态。
