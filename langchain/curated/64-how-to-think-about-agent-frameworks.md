# 如何正确理解 Agent 框架

> 一句话总结：构建可靠 Agent 系统的核心难题不在于选哪个框架，而在于确保 LLM 在每一步都能拿到正确的上下文（Context）。

---

## 核心要点

1. Agent 系统 = 工作流（Workflow）+ 智能体（Agent）+ 两者之间的一切组合
2. 大多数所谓的 Agent 框架其实只是一组抽象封装，并非真正的编排框架
3. Agent 抽象让你快速上手，但往往遮蔽了"LLM 到底收到了什么"这个关键问题
4. 框架的真正价值不在于 Agent 抽象本身，而在于持久化、容错、人机协作、流式输出、可观测性等生产级能力
5. LangGraph 的定位是一个编排框架（既有声明式 API 也有命令式 API），Agent 抽象只是在其上层构建的便利层

---

## 概念对照表

| 维度 | 工作流 (Workflow) | 智能体 (Agent) |
|------|-------------------|----------------|
| 控制权 | 开发者通过代码预定义路径 | LLM 动态决定下一步 |
| 可预测性 | 高：路径确定、行为一致 | 低：每次运行可能不同 |
| 可靠性 | 更容易保证 | 需要更多工程投入 |
| 上下文控制 | 开发者精确指定数据流向 | 框架/抽象可能遮蔽细节 |
| 适用场景 | 流程明确、对一致性要求高 | 需要灵活决策、动态工具调用 |
| 成本与延迟 | 通常更低 | 通常更高 |

## 什么是 Agent？

业界对 Agent 没有统一定义。OpenAI 给出的是一个高层次的思想领导式说法："Agent 是能独立替你完成任务的系统。" 这句话听起来很酷，但对实际工程几乎没有指导意义。

Anthropic 的定义更实用。他们把所有这些变体统称为 Agentic System（智能体系统），然后做了一个关键的架构区分：工作流是通过预定义代码路径编排 LLM 和工具的系统；Agent 则是 LLM 动态控制自身流程和工具使用的系统。简单来说，Agent 就是"LLM 在一个循环里不断调用工具、获取反馈、再调用工具"。

Andrew Ng 提出了一个更务实的思路：与其纠结某个东西"是不是 Agent"，不如思考它"有多 Agentic"。这个形容词比名词更有用，因为现实中几乎所有生产级系统都是工作流和 Agent 的混合体。

## 为什么构建可靠的 Agent 这么难？

```
构建 Agent 的核心难题

用户输入 --> [ 系统提示词 ] --> [ LLM ] --> [ 工具调用 ] --> [ 结果 ]
               |                    |            |              |
               v                    v            v              v
          提示词是否         上下文是否      工具描述是否     返回结果格式
          足够详细？         完整准确？      清晰准确？       是否合理？

               任何一个环节出错 --> LLM 做出错误决策
```

做一个 Agent 的原型很容易，做一个能支撑业务关键场景的可靠 Agent 很难。LangChain 团队做过调研，问 Agent 开发者"把更多 Agent 投入生产的最大障碍是什么？"排名第一的答案遥遥领先：性能质量。

LLM 出错的原因只有两个：一是模型本身能力不够，二是传给模型的上下文不对或不全。根据实际经验，第二个原因出现的频率远高于第一个。具体表现包括：系统提示词写得太短或太模糊、用户输入含义不清、没有给 LLM 提供合适的工具、工具描述写得不好、没有传入正确的上下文信息、工具返回的结果格式混乱。

这就引出了一个关键判断标准：**任何让你更难控制"什么东西被送进 LLM"的框架，都在给你帮倒忙。**

## 框架的三个维度

### 类比理解

想象你要组织一场大型婚礼。你有三种方式：

- **纯工作流**：像一份详细的时间表，几点迎宾、几点开席、几点切蛋糕，每一步都提前写好。可预测、可靠，但不灵活。
- **纯 Agent**：请一个全权负责的婚礼策划师，告诉他预算和偏好，剩下的让他自己决定。灵活但不可控，你无法确定他会做什么。
- **混合方式**（实际最常见）：大框架用时间表，但每个环节里留一定自由度给策划师。这就是工作流 + Agent 的组合。

现在来看框架本身的分类维度：

**维度一：工作流 vs Agent**。大多数框架只提供 Agent 抽象。少数框架同时支持工作流。LangGraph 作为底层编排框架，两者都支持。

**维度二：声明式 vs 命令式**。LangGraph 常被说成是声明式的（像 TensorFlow），而 Agents SDK 被说成是命令式的（像 PyTorch）。但这个类比不准确。LangGraph 的节点和边的连接方式是声明式的，但节点内部就是普通的 Python/TypeScript 函数。而 Agents SDK 既不是声明式也不是命令式，它本质上只是一组抽象类。

**维度三：Agent 抽象的陷阱**。大多数框架从一个简单的 Agent 类开始——接受提示词、模型、工具。然后不断加参数……最终你面对的是一堆参数控制的黑箱行为。如果你想知道 LLM 到底收到了什么，或者想修改内部逻辑，你必须深入源码。LangChain 团队在初代 LangChain 就吃过这个亏。

## 框架到底提供什么价值？

```
               框架提供的价值层次

   +----------------------------------------+
   |        Agent 抽象（快速上手）           |  <-- 大多数框架只到这里
   +----------------------------------------+
   |        短期记忆（多轮对话线程）          |
   +----------------------------------------+
   |        长期记忆（跨对话学习）           |
   +----------------------------------------+
   |     人在回路中（审批/反馈/编辑）         |
   +----------------------------------------+
   |     人在回路上（回溯/检查/重放）         |
   +----------------------------------------+
   |        流式输出（Token/步骤/事件）       |
   +----------------------------------------+
   |        容错（持久化工作流/重试）          |
   +----------------------------------------+
   |     调试与可观测性（LangSmith 集成）     |
   +----------------------------------------+
```

如果你的应用不需要这些能力，或者你愿意自己实现，那你可能不需要框架。有些（如短期记忆）实现起来不难，有些（如人在回路上的回溯重放、LLM 专用的可观测性）则复杂得多。

Anthropic 在他们的博客中给出了一条金句：如果你使用框架，请确保你理解底层代码。对底层实现的错误假设是用户犯错的常见来源。

## 模型越来越强，是不是工作流就没用了？

不是。即使模型变得更强，以下几点仍然成立：工具调用 Agent 的性能会提升；控制传给 LLM 的内容仍然至关重要（垃圾进，垃圾出）；对某些应用来说，简单的工具调用循环就够了；对另一些应用来说，工作流依然更简单、更便宜、更快、更好；对大多数应用来说，生产系统会是工作流和 Agent 的组合。

只有在你能针对特定任务训练/微调一个顶级模型的情况下，才可能只用简单的工具调用循环。目前只有大型模型实验室有能力做到这一点。编程是一个有趣的例子——因为编程任务相对通用，且基座模型在海量编码数据上训练过，所以 Claude Code 和 Codex CLI 这样的编码 Agent 可以用简单的工具调用循环。但即便如此，训练数据的形状也很重要。Ben Hylak 观察到，新模型针对终端场景优化后，在 Cursor 这样的编辑器场景中反而表现变差了。

## 主流框架对比

| 框架 | 类型 | 编排方式 | 关键特点 |
|------|------|----------|----------|
| LangGraph | 编排框架 + Agent 抽象 | 声明式 + 命令式 + 函数式 | 持久化、人机协作、流式、容错 |
| OpenAI Agents SDK | Agent 抽象 | 非编排框架 | Handoff 机制、简洁 API |
| Google ADK | Agent 抽象 | -- | Google 生态集成 |
| CrewAI | Agent 抽象 | -- | 多 Agent 角色协作 |
| Pydantic AI | Agent 抽象 | -- | 类型安全 |
| Temporal | 工作流框架 | 命令式 | 分布式容错、持久化 |
| DSPy | 优化框架 | -- | 基于评估数据集自动优化 |

## 类比理解

把 Agent 框架想象成盖房子的方式：

- **纯 Agent 抽象**（如 Agents SDK）就像买一套精装样板间：拎包入住很方便，但想改墙体结构就得砸墙重来。地板低（容易上手），天花板也低（很快碰到限制）。
- **纯编排框架**（如 Temporal）就像买毛坯房自己装修：自由度极高，但你得自己水电、贴砖、刷漆。地板高（上手难），天花板也高（想怎么装都行）。
- **LangGraph 的定位**是提供一个"精装+可改造"的方案：上层有样板间式的 Agent 抽象让你快速入住，但底层结构完全可定制。目标是地板低、天花板高。

---

## 为什么重要

如果你正在构建生产级的 AI 应用，选择框架的标准不应该是"哪个上手最快"，而是"哪个让我最容易控制传给 LLM 的上下文"。Agent 抽象的便利性是短暂的，上下文控制的能力才是长期的。在决定你的系统有多 Agentic 之前，先问自己：我真的需要这么多灵活性吗？更简单的工作流能不能解决问题？

---

## 延伸思考

1. 你当前的 AI 应用在"工作流-Agent"光谱上的什么位置？有没有过度 Agentic 的部分可以用确定性工作流替代？
2. 当你使用某个 Agent 框架时，你能清楚说出每一步 LLM 收到的完整输入是什么吗？如果不能，这就是一个风险信号。
3. 随着模型能力的提升，"工作流 vs Agent"的最优平衡点会如何移动？你的架构是否有足够的灵活性来适应这种变化？
4. OpenAI 的 Agents SDK 把"声明式 vs 非声明式"与"工作流 vs Agent"混为一谈，这种概念混淆在你评估其他工具时是否也出现过？
