# Agent Builder 的记忆系统是怎么构建的

> 一句话总结：LangSmith Agent Builder 用文件系统来表示 Agent 的记忆，让 Agent 在执行任务的过程中自己读写记忆文件，通过用户纠正逐步迭代出一个精确的 Agent 规范，而不需要用户手动编写任何配置。

---

## 核心要点

1. 与通用 AI 助手不同，专用 Agent 反复执行相同类型的任务，记忆的复用率极高——缺少记忆意味着用户必须反复向 Agent 重复相同的指令
2. 记忆被表示为文件系统中的一组文件（AGENTS.md、技能文件、tools.json 等），实际存储在数据库中，以虚拟文件系统的形式暴露给 Agent
3. Agent 在工作过程中自己读写这些文件，通过用户的纠正反馈逐步积累出一份越来越精确的行为规范
4. 记忆编辑默认需要人工审批（Human-in-the-loop），以防范提示注入攻击
5. 最大的挑战不是技术架构，而是提示词工程——几乎所有记忆行为的问题都通过改进提示词来解决

---

## 三种记忆类型（COALA 框架）

| 记忆类型 | 定义 | Agent Builder 中的对应物 | 比喻 |
|----------|------|--------------------------|------|
| 程序性记忆 (Procedural) | 决定 Agent 行为的规则集 | AGENTS.md + tools.json | 工作手册 |
| 语义记忆 (Semantic) | 关于世界的事实知识 | 技能文件 + 知识文件 | 百科全书 |
| 情景记忆 (Episodic) | Agent 过去行为的序列 | 暂未实现（计划中） | 日记本 |

---

## 为什么专用 Agent 比通用 Agent 更需要记忆？

通用 AI 助手（如 ChatGPT、Claude）每次对话可能处理完全不同的任务——今天写代码、明天查天气、后天翻译文档。上一次对话的经验未必适用于下一次。但 LangSmith Agent Builder 中的 Agent 是为特定任务定制的，比如邮件助手、文档助手、招聘助手。它反复做同一类事情，上一次学到的偏好和规则几乎 100% 适用于下一次。

如果没有记忆，用户每次开始新对话都要重复一遍相同的指令："用要点格式，不要段落""在末尾单独列出行动项""工程会议重点记录技术决策"。这就像你每天上班都要重新告诉同事你的名字一样荒谬。

## 记忆的文件系统架构

```
Agent 的虚拟文件系统

agent-root/
  |
  +-- AGENTS.md              <-- 程序性记忆：核心指令
  |
  +-- tools.json              <-- 程序性记忆：可用工具配置
  |
  +-- subagents/              <-- 子 Agent 定义
  |     +-- linkedin_search_worker
  |
  +-- skills/                 <-- 语义记忆：专项技能指令
  |
  +-- knowledge/              <-- 语义记忆：领域知识文件
  |     +-- jd-frontend.md
  |     +-- jd-backend.md
  |     +-- jd-infra.md
  |
  (底层存储: PostgreSQL，以虚拟文件系统形式暴露)
```

为什么选择文件系统作为记忆的表现形式？因为 LLM 天生擅长操作文件系统。它们在大量代码仓库数据上训练过，读文件、写文件、改文件是它们最熟练的操作之一。这样你不需要给 Agent 专门的记忆工具，只需给它文件系统访问权限就行了。

实际存储用的是 PostgreSQL 数据库，但以虚拟文件系统的形式暴露给 Agent。这是一个精巧的设计——LLM 看到的是它擅长的文件操作界面，工程团队用到的是易于管理的数据库后端。

文件格式尽量采用行业标准：AGENTS.md 定义核心指令集，Agent Skills 定义专项技能指令，MCP 配置使用自定义的 tools.json（而不是标准的 mcp.json，因为需要让用户只暴露 MCP 服务器中的部分工具，避免上下文溢出）。

## 记忆如何逐步迭代生长

这是整个系统最精妙的部分。Agent 的行为规范不是一次性写好的，而是通过用户的反复纠正逐步生长出来的。

```
记忆迭代时间线

[起点]  AGENTS.md: "总结会议笔记"
   |
   v
[第1周]  用户纠正: "用要点格式，不要段落"
         --> Agent 自动更新 AGENTS.md
   |
   v
[第2周]  Agent 自动使用要点格式，无需提醒
         用户补充: "行动项单独列在末尾"
         --> Agent 追加到 AGENTS.md
   |
   v
[第4周]  两个规则自动生效
         继续积累新的边界案例修正
   |
   v
[第3月]  AGENTS.md 包含:
         - 不同文档类型的格式偏好
         - 领域专用术语
         - "行动项"/"决策"/"讨论要点"的区分规则
         - 常见参会者的姓名和角色
         - 不同会议类型的处理方式
         - 通过使用积累的边界案例修正
```

关键洞察：AGENTS.md 是通过纠正自动构建的，不是通过预先文档化。用户从来不需要手动编辑配置文件。用了三个月之后，Agent 拥有了一份详细的行为规范，而用户只是在日常使用中偶尔说了几句"这里应该这样做"。

## 构建记忆系统的五个实践教训

| 教训 | 具体表现 | 解决方案 |
|------|----------|----------|
| 最难的部分是提示词 | Agent 该记不记、不该记的时候记了、写到了错误的文件 | 一个人全职专注记忆相关提示词 |
| 必须验证文件格式 | Agent 生成了无效的 tools.json 或缺少 frontmatter 的技能文件 | 写入前进行模式验证，失败则把错误反馈给 LLM |
| Agent 擅长添加但不擅长泛化 | 邮件助手逐一列出要忽略的供应商，而不是写一条"忽略所有冷推销" | 需要显式提示 Agent 进行记忆压缩 |
| 用户有时仍需显式管理记忆 | Agent 在工作中可能遗漏需要记住的内容 | 在任务结束时提示 Agent 反思并更新记忆 |
| 记忆编辑需要人工审批 | 提示注入可能篡改 Agent 的记忆 | 默认 Human-in-the-loop，可选"YOLO 模式"关闭 |

## 类比理解

想象你新雇了一个私人助理。第一天你告诉他"帮我整理会议纪要"。他写了一篇洋洋洒洒的散文。你说"用要点，别写文章"。他在笔记本上记下来。第二天他自动用要点格式了。后来你又说"行动项要单独列出""工程会议重点记技术决策"。每一次纠正，他都记在笔记本上。

三个月后，这个助理不需要你多说一句话就能精确地按照你的偏好整理任何类型的会议纪要。他的笔记本就是 AGENTS.md，这个逐步积累的过程就是记忆系统的工作方式。

关键区别在于：这个"助理"是 AI，它的"笔记本"是结构化文件。而且每次它要往笔记本上写东西之前，都会先给你看——"我打算记住这一条，你同意吗？"这就是 Human-in-the-loop。

## 未来方向

| 方向 | 说明 |
|------|------|
| 情景记忆 | 把之前的对话历史作为文件暴露给 Agent，让它能参考"上次我是怎么处理的" |
| 后台记忆整理 | 用定时任务在后台反思所有对话并更新记忆，弥补 Agent 在工作中遗漏的内容 |
| /remember 命令 | 让用户显式触发记忆反思，而不是等 Agent 自己想起来 |
| 语义搜索记忆 | 除了 glob 和 grep，增加基于语义的记忆检索能力 |
| 多层级记忆 | 区分 Agent 级别、用户级别、组织级别的记忆，通过不同目录暴露 |

## 为什么重要

大多数 AI 产品在没有记忆的情况下就发布了，即使后来加上记忆也没有带来变革性的改变。原因在于通用 AI 助手处理的任务太多样化，上一次对话的经验对下一次没什么用。但专用 Agent 的场景完全不同——它反复做同一类事情，记忆的复用率极高。

LangSmith Agent Builder 的记忆系统展示了一个重要的设计理念：**让 Agent 的行为规范通过使用自然生长，而不是预先工程化。** 这降低了构建 Agent 的门槛（你不需要一开始就写出完美的提示词），同时提高了最终质量（三个月的实际使用积累的规范比任何人一次性写出来的都更全面）。

## 延伸思考

1. 你的 Agent 系统中，哪些"反复向 AI 重复说的话"其实应该被记忆系统自动捕获？
2. "Agent 擅长添加但不擅长泛化"这个问题在你使用 AI 工具时是否也遇到过？比如 AI 列出了 10 个具体案例，但没有总结出一条通用规则。
3. 记忆编辑的 Human-in-the-loop 在安全性和便捷性之间如何取舍？什么场景适合开"YOLO 模式"，什么场景绝对不能？
4. 如果你要为自己的 Agent 设计记忆系统，你会从 COALA 框架的哪种记忆类型开始？为什么？
