# 少样本提示如何提升工具调用性能：用示范教 AI 正确使用工具

> 一句话总结：在提示词中加入少量"示范对话"（Few-shot Examples），可以大幅提高 LLM 调用工具的准确率，尤其是用消息格式（Message Format）而非字符串格式，且只需 3 个语义相似的示例就能接近最佳效果。

---

## 核心要点

| 维度 | 内容 |
|------|------|
| 核心问题 | LLM 调用工具时常选错工具、填错参数，性能不稳定 |
| 解决方法 | 少样本提示（Few-shot Prompting）-- 在提示词中提供输入/输出示范 |
| 关键发现 | 消息格式优于字符串格式；3 个动态选择的示例通常够用 |
| 最大提升 | Claude 3 Sonnet 从 16% 提升到 52%（查询分析任务） |
| 小模型逆袭 | Claude 3 Haiku + 少样本可媲美 Claude 3.5 Sonnet 零样本 |

---

## 两个实验任务

| 任务 | 场景 | 复杂度 | 特殊挑战 |
|------|------|--------|----------|
| 查询分析（Query Analysis） | 根据用户问题选择正确的搜索索引 | 单次 LLM 调用 | 需要领域知识判断数据源 |
| 多元宇宙数学（Multiverse Math） | 用"改过规则"的数学工具解题 | 多次 Agent 调用（ReAct 模式） | 必须忽略内置知识，信任工具输出 |

## 格式差异的深层原因

```
字符串格式 vs 消息格式

字符串格式（拼入系统提示词）：
+--------------------------------------------------+
| System Prompt                                     |
| ...                                               |
| 示例1: user说X, assistant回Y, 调用了tool Z        |
| 示例2: user说A, assistant回B, 调用了tool C        |
+--------------------------------------------------+
| User: 新问题                                      |
+--------------------------------------------------+

消息格式（作为独立的消息轮次）：
+--------------------------------------------------+
| System Prompt                                     |
+--------------------------------------------------+
| User(示例1): X                                    |
| Assistant(示例1): Y [tool_call: Z]                |
| Tool(示例1): 结果                                 |
+--------------------------------------------------+
| User(示例2): A                                    |
| Assistant(示例2): B [tool_call: C]                |
| Tool(示例2): 结果                                 |
+--------------------------------------------------+
| User: 新问题                                      |
+--------------------------------------------------+
```

消息格式更有效的原因在于，它让模型"亲历"了完整的对话过程。就像学做菜时，看视频（消息格式）比看文字食谱（字符串格式）更容易学会，因为你能看到每一步的上下文和因果关系。模型在消息格式中可以直接观察到"用户说了什么 -> 应该调用哪个工具 -> 工具返回了什么 -> 最终怎么回答"的完整链条。

## "多元宇宙数学"的精彩案例

这个实验设计非常巧妙。它定义了一套"平行宇宙"的数学规则，比如加法函数实际上会多加 1.2：

```
def add(a, b):
    """Add two numbers; a + b."""
    return a + b + 1.2
```

所以 1 到 10 求和的正确答案不是 55，而是 65.8（每次加法多加 1.2，共 9 次加法，多出 10.8）。这迫使模型必须信任工具输出，而不是依赖自己"知道"的数学知识。

更有趣的是构建少样本数据集的方法。研究者和 Claude Sonnet 对话，故意让它犯错，然后纠正它。比如 `negate(-100)` 在这个宇宙里实际是恒等函数（返回 -100 本身），但模型会"自作聪明"地返回 100。经过纠正后，模型学会了尊重工具输出。这些"犯错-纠正"的对话被直接用作少样本示例。

## 类比理解

**实习生和师傅的关系。** 想象你雇了一个聪明但没经验的实习生（LLM），让他帮你查资料（工具调用）。如果你只告诉他"去查查这个问题的答案"（零样本），他可能会查错数据库，或者用错误的关键词搜索。

但如果你先演示几次："上次有人问 RAG 相关的问题，我同时查了文档库和博客。搜索词不要照搬原问题，要提炼关键概念。"（少样本提示），实习生立刻就能举一反三了。

更关键的是演示的方式。把操作步骤写在备忘录上给他看（字符串格式），不如让他在旁边看你实际操作一遍（消息格式）。看你亲手操作时，他能理解每个动作的上下文和因果关系，而不是机械地记住步骤。

最让人惊喜的发现是：一个经验较少的实习生（Haiku），只要看了 3 个好的示范，就能达到高级实习生（Sonnet 3.5）零经验时的水平。这就像说，好的培训可以弥补基础能力的差距。

## 动态选择 vs 固定选择

在查询分析任务中，3 个语义相似的动态示例比 13 个固定示例效果还好。这说明"相关性"比"数量"更重要。就像学做宫保鸡丁时，看 3 个炒菜视频比看 13 个面点教程更有帮助。

动态选择的工作原理是：对新问题做向量嵌入（Embedding），然后在示例库中找到语义最接近的几个示例。这在输入多样化的任务中尤其关键，因为不同类型的问题需要不同类型的示范。

---

## 为什么重要

1. **最低成本的性能提升。** 少样本提示不需要微调模型，不需要修改架构，只需要几个高质量的示范就能获得显著提升。这是你能做的最简单、最便宜的优化。
2. **小模型的"平权"方案。** Claude 3 Haiku 加上少样本后能媲美 Sonnet 3.5 的零样本表现，这意味着你可以用更便宜、更快的小模型配合少样本提示，获得大模型级别的工具调用质量。
3. **格式比内容更重要。** 同样的示例，消息格式和字符串格式的效果可能天差地别。这提醒我们，提示词工程不只是"写什么"，还包括"怎么组织"。
4. **评估不可或缺。** 最佳配置因模型和任务而异，没有放之四海而皆准的方案。只有通过系统性评估，你才能找到自己场景下的最优解。

## 延伸思考

- 负面示例（展示错误做法）是否比正面示例更有效？"看别人怎么犯错"是否比"看别人怎么做对"更有教育意义？
- 在 Agent 场景中，展示"先犯错再纠正"的完整轨迹是否比只展示"一次做对"的轨迹更好？这有点像教学中的"错题本"方法。
- 少样本的边际收益在哪里递减？3 个和 9 个示例效果接近，是否意味着存在一个"信息饱和点"？
- 随着模型能力提升（从 Haiku 到 Sonnet 到 Opus），少样本的边际价值是增加还是减少？
