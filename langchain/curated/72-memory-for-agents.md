# Agent 的记忆系统

> **一句话总结**：Agent 的记忆不是通用的——"记住什么"和"怎么记住"都取决于具体应用场景。LangChain 借鉴认知科学的三种人类记忆类型（程序性记忆、语义记忆、情景记忆），为开发者提供了低层级的记忆存储原语（Memory Store），让你完全控制 Agent 的记忆行为。

---

## 核心要点

1. **记忆是应用特定的**：Replit 的编程 Agent 需要记住用户偏好的 Python 库，Unify 的研究 Agent 需要记住用户关注的行业领域——同一套通用记忆方案无法满足所有场景。
2. **三种记忆类型映射到 Agent 系统**：程序性记忆（Procedural Memory）对应 Agent 的"操作手册"，语义记忆（Semantic Memory）对应 Agent 积累的"知识库"，情景记忆（Episodic Memory）对应 Agent 的"经验回放"。
3. **记忆更新有两条路径**："热路径"（in the hot path）在响应前实时更新，"后台路径"（in the background）在对话结束后异步更新。前者延迟高但实时，后者延迟低但有滞后。
4. **用户反馈是第三种记忆来源**：当用户对某次交互给出正面或负面评价时，这个信号可以直接存入情景记忆，指导 Agent 未来的行为。
5. **LangGraph 的 Memory Store 提供底层控制**：不是给你一个"开箱即用"的记忆方案，而是给你积木和工具，让你根据自己的应用场景定制记忆策略。

---

## 三种记忆类型对照表

| 记忆类型 | 认知科学定义 | Agent 中的对应 | 实际应用举例 | 更新方式 |
|---------|------------|--------------|------------|---------|
| 程序性记忆（Procedural） | 如何执行任务的长期记忆，如骑自行车 | LLM 权重 + Agent 代码 + 系统提示词 | Agent 自动修改自己的 system prompt 以改进表现 | 极少自动更新；偶有 Agent 修改自身提示词的案例 |
| 语义记忆（Semantic） | 关于世界的事实性知识，如学校学到的知识 | 关于用户和世界的事实数据库 | 记住"用户偏好 TypeScript 而非 JavaScript" | 用 LLM 从对话中提取信息，存入结构化存储 |
| 情景记忆（Episodic） | 对特定过去事件的回忆 | Agent 过去行动的序列记录 | 用成功的操作序列作为 few-shot 示例指导未来行为 | 存储完整的交互序列，通过动态 few-shot 检索使用 |

   ┌─────────────┐              ┌─────────────┐

## 类比理解：Agent 的记忆就像一个好服务员

想象你是一家餐厅的常客。一个好服务员对你的"记忆"有三个层次：

- **程序性记忆**：服务员知道怎么点菜、怎么推荐、怎么处理投诉——这是他的"工作技能"。在 Agent 中，这对应 LLM 的训练权重和代码逻辑。你不会每天都重新培训一个服务员，同样，Agent 的程序性记忆也很少动态更新。

- **语义记忆**：服务员记住你"不吃香菜"、"偏好清淡口味"、"上次说在减肥"——这些是关于你的事实性知识。在 Agent 中，这对应从对话中提取的用户偏好和上下文信息。这是目前最常见的 Agent 个性化方式。

- **情景记忆**：服务员记住"上次你点了那道新菜，吃完说很好吃"——这是具体的事件回忆。在 Agent 中，这对应成功的操作序列记录。当类似的情况再次出现时，Agent 可以参考之前成功的做法。

至于"什么时候记"：
- **热路径**就像服务员一边和你聊天一边在小本子上记笔记——你能看到他在记，但你等他记完才能继续点菜。
- **后台路径**就像服务员回到后厨后才把你的偏好录入系统——你完全感知不到延迟，但下次你来之前才能用上。

## 语义记忆 vs 情景记忆：什么时候用哪种？

这两种记忆解决的是不同类型的问题：

| 场景特征 | 更适合的记忆类型 | 原因 |
|---------|----------------|------|
| Agent 经常遇到新任务，每次都不太一样 | 语义记忆 | 具体的操作序列帮助不大，但关于用户的事实性知识（偏好、背景）可以持续指导 |
| Agent 反复做类似的事，存在"正确做法" | 情景记忆 | 成功案例的完整序列可以直接作为 few-shot 示例，引导 Agent 复现正确行为 |
| Agent 需要个性化用户体验 | 语义记忆 | 用户的偏好和特征是事实性信息，适合提取和检索 |
| Agent 需要从错误中学习 | 情景记忆 | 对比成功/失败案例的完整序列，找到关键差异 |

## LangChain 提供了什么

LangChain 围绕 Agent 记忆构建了一套完整的工具链：

| 工具 | 功能 | 适用场景 |
|------|------|---------|
| LangGraph Memory Store | 低层级记忆存储抽象，完全可定制 | 需要完全控制记忆行为的生产级 Agent |
| Memory Template | 预构建的热路径/后台路径记忆模板 | 快速搭建记忆功能的起点 |
| LangSmith 动态 Few-Shot | 从数据集中动态选择示例注入提示词 | 需要情景记忆的场景，快速迭代 |

核心哲学是：**不告诉你应该记什么，而是给你工具让你自己决定。** 这和 LangGraph 整体"少假设、多灵活"的设计思想一致。

---

## 为什么重要

记忆是让 Agent 从"一次性工具"变成"持续有用的助手"的关键。没有记忆的 Agent 就像一个每天失忆的同事——每次你都要从头解释你的偏好、项目背景和工作方式。这不仅低效，还会让用户感到沮丧。

但记忆不是越多越好。错误的记忆比没有记忆更危险——如果 Agent 记住了过时的用户偏好或错误的操作模式，它会持续犯错，而且更难被发现和纠正。这就是为什么 LangChain 强调"记忆是应用特定的"：你需要根据你的场景仔细设计记什么、怎么记、什么时候用。

记忆系统设计的质量，将直接决定你的 Agent 产品能否建立用户粘性和信任。

## 延伸思考

1. **记忆的"遗忘"同样重要**：人类会遗忘不重要的信息来保持思维清晰。Agent 的记忆系统是否也需要"遗忘机制"？什么时候应该删除或降权某条记忆？
2. **记忆的隐私边界在哪里？** 如果 Agent 记住了用户的敏感信息（工资水平、健康状况），用户能否查看和删除？GDPR 等隐私法规对 Agent 记忆有什么影响？
3. **多用户共享的 Agent 如何处理记忆？** 一个团队共用的 Agent 应该对每个成员保持独立记忆，还是也应该有"团队级"的共享记忆？两者如何平衡？
4. **CoALA 论文描述了一个完整的认知架构框架。** 当前 Agent 的记忆实现离认知科学描述的理想状态还有多远？自动更新程序性记忆（让 Agent 真正"学会"新技能）是否是下一个突破方向？
