# 评估驱动开发：用 Eval 迭代出可靠的 LLM 应用

> 原文: [Iterating Towards LLM Reliability with Evaluation Driven Development](https://www.langchain.com/blog/iterating-towards-llm-reliability-with-evaluation-driven-development) | LangChain Blog | 2024-03-11

## 一句话总结

Dosu 团队通过"评估驱动开发"（Evaluation Driven Development, EDD）——类似测试驱动开发（TDD）但专为 LLM 应用设计——结合 LangSmith 的可观测性工具，实现了从手工逐条检查到大规模自动化质量保障的跨越。

---

## 核心要点

### 1. Dosu 是什么：一个真实的 LLM 产品案例

Dosu 是一个安装在 GitHub 仓库上的 AI 助手（AI Teammate），帮助开源项目维护者自动处理 Issue 分类、问题解答和 PR 标记等任务。它诞生于一个真实的痛点：开源维护者 85% 的时间花在非编码任务上——回答重复的问题、分类 Issue、处理各种杂事。很多维护者因此精疲力竭，甚至会宣布"Issue 破产"（Issue Bankruptcy），一次性关闭所有未处理的 Issue。

Dosu 就像一个不知疲倦的实习生，7x24 小时在 GitHub 上值班，遇到用户提问就尝试回答，遇到新 Issue 就自动分类。但问题是：你怎么确保这个"实习生"的回答质量持续可靠？

### 2. 从手工检查到系统化评估的演变

Dosu 的质量保障经历了三个阶段：

```
阶段演变：
==========

阶段 1: 手工时代（2023 年中）
+------------------------------------------+
| 每天用 grep + print 检查每一条回复        |
| 数据量: 低  |  人力成本: 可承受            |
| 收获: 深度理解用户需求和失败模式           |
+------------------------------------------+
           |
           v
阶段 2: EDD 时代（2023 年末）
+------------------------------------------+
| 建立评估数据集，每次改动都跑 eval          |
| 数据量: 中  |  人力成本: 可控              |
| 收获: 有信心地迭代 prompt 和架构           |
+------------------------------------------+
           |
           v
阶段 3: LangSmith 时代（2024 年）
+------------------------------------------+
| 生产环境全量追踪 + 自动发现失败模式         |
| 数据量: 高  |  人力成本: 杠杆化            |
| 收获: 从监控到评估的闭环自动化              |
+------------------------------------------+
```

### 3. EDD 的核心工作流

评估驱动开发（EDD）和测试驱动开发（TDD）的理念一脉相承：先定义"什么是好的"，再去实现"怎么做到"。

| 步骤 | 动作 | 类比 TDD |
|------|------|---------|
| 1. 创建初始评估集 | 为新功能手写几个输入-期望输出对 | 写失败的测试用例 |
| 2. 上线新功能 | 把功能推到生产环境 | 运行代码让测试通过 |
| 3. 监控生产表现 | 观察真实用户交互中的失败 | 发现边界情况 |
| 4. 扩充评估集 | 把失败案例加入离线评估数据集 | 添加回归测试 |
| 5. 迭代改进 | 修改 prompt/架构，确保新旧评估都通过 | 重构并保持测试绿灯 |
| 6. 重新上线 | 推送改进版本，重复循环 | 持续集成/持续部署 |

但 EDD 和 TDD 有一个根本区别：**LLM 的修改是不确定的**。在传统软件中，改一个函数只会影响调用这个函数的地方。但在 LLM 应用中，改一句 prompt 可能在修好 A 场景的同时搞坏 B 场景——这就是为什么"评估集"比"单元测试"更重要。

### 4. 为什么选择 LangSmith：四个硬性需求

当 Dosu 的规模增长到数千个仓库后，手工监控不再可行。团队选择 LangSmith 基于四个严格标准：

| 需求 | 理由 | 对应 EDD 环节 |
|------|------|-------------|
| Prompt 必须在 Git 中管理 | Prompt 就是代码，必须版本化、可审查 | 迭代改进 |
| 代码级追踪（Code-level Tracing） | 需要在一条追踪链中看到函数输入、渲染后的 prompt 和 LLM 输出 | 监控生产 |
| 数据易导出 | 团队已有评估数据集和工具，不能被锁定 | 扩充评估集 |
| 高度可定制 | LLM 领域没有标准实践，需要控制追踪的元数据 | 全流程适配 |

最让团队兴奋的不是 LangSmith 的 UI，而是它的 SDK。只需在关键函数上加一个 `@traceable` 装饰器，几分钟就能完成接入。推到生产环境后，LangSmith UI 中立刻涌入了追踪数据。

### 5. 发现失败模式的信号体系

在大规模运行中，团队建立了一套多维度的失败检测信号：

```
失败信号金字塔：
                    +--------+
                    | 显式   |  用户点赞/踩
                    | 反馈   |
                   +----------+
                   | 用户情绪  |  回复中的语气分析
                  +------------+
                  | 内部错误    |  输入过长、输出不合规范
                 +--------------+
                 | 响应时间      |  为什么某些请求特别慢？
                +----------------+
```

| 信号类型 | 检测方式 | 示例 |
|---------|---------|------|
| 显式反馈（Explicit Feedback） | 用户主动的赞/踩 | 用户给 Dosu 的回复点了踩 |
| 用户情绪（User Sentiment） | 分析用户后续回复的态度 | 用户说"这完全不是我问的" |
| 内部错误（Internal Errors） | 系统异常捕获 | 输入超长、输出格式不匹配 |
| 响应时间（Response Time） | 异常耗时检测 | 某个请求花了 30 秒而正常只需 3 秒 |

LangSmith 的高级搜索功能让团队能快速找到异常行为——按用户反馈、错误事件、响应延迟或负面情绪进行过滤。

**经典趣事：** 有一次用户要求 Dosu 给一个 PR 打标签。Dosu 不但没有打标签，反而开始告诉用户它今晚要去看演唱会有多激动。（团队至今没弄清楚 Dosu 是不是 Taylor Swift 的粉丝。）

### 6. 评估数据集的自动化收集

```
EDD 飞轮效应：
===============================

  LangSmith 帮 Dosu       Dosu 改进
  更快迭代  -------->  减轻 LangChain 团队
                        维护负担
      ^                     |
      |                     v
  LangSmith            LangChain 团队
  功能增强  <--------  有更多时间开发
                        LangSmith 新功能
```

团队正在将 LangSmith 进一步定制，实现自动构建评估数据集——从生产追踪中自动识别有价值的案例并添加到离线评估集。这把 EDD 循环中最耗人力的一环（"发现失败案例并手动加入评估集"）也自动化了。

## 类比理解

把 EDD 想象成一个**厨师不断改进菜谱**的过程。

一开始你开了一个小餐馆（Dosu 早期），每道菜出去你都亲自去问客人"好吃吗"，然后根据反馈调整。这时你能管得过来。

后来餐馆火了（规模增长），你不可能每道菜都去问了。你需要一个系统：装摄像头看客人表情（用户情绪），放留言卡让客人评分（显式反馈），记录每道菜出餐时间（响应时间），查看退菜记录（内部错误）。

EDD 就是你的菜谱迭代方法论：**先定义"好吃的标准"（评估集），再做菜（开发功能），吃出问题了就把那道菜的问题记录下来（扩充评估集），改良菜谱后确保所有之前好吃的菜还是好吃的（回归测试），然后继续迭代。**

LangSmith 就是你的后厨管理系统——帮你追踪每道菜从备料到上桌的全过程，在数千道菜中快速找到那几道出了问题的。

## 为什么重要

这篇文章之所以有价值，不在于推销 LangSmith，而在于它完整展示了一个真实 LLM 产品从 0 到规模化的质量保障演变过程。

1. **EDD 填补了 LLM 工程的方法论空白。** 传统的 TDD/BDD 对 LLM 应用不完全适用，EDD 提供了一个专为概率性系统设计的开发范式。
2. **"Prompt 即代码"的理念。** 很多团队把 prompt 当作配置随意修改。Dosu 团队坚持 prompt 必须在 Git 中版本管理、经过审查才能变更——这是工程纪律在 LLM 时代的延续。
3. **先手工再自动化。** 团队没有一上来就追求自动化，而是先用最笨的办法（每天手动检查每条回复）建立深度理解，再逐步引入工具。这个节奏值得所有 LLM 产品团队学习。
4. **监控和评估的闭环。** 生产监控的价值不止于发现 bug，更在于持续喂养评估数据集，形成"监控发现问题 -> 问题变成测试 -> 测试驱动改进"的正向循环。

## 延伸思考

1. **EDD 中的评估集应该多大？** 太小则覆盖不够，太大则运行成本高。是否存在一个"最小有效评估集"的概念？如何衡量边际收益？
2. **prompt 修改的回归风险**：文章提到改一个 prompt 可能在 A 场景改进的同时让 B 场景退步。是否可以借鉴传统软件的"变异测试"（Mutation Testing）思路，系统性地探测 prompt 修改的影响范围？
3. **从 EDD 到 EDD + RLHF**：Dosu 收集的大量"好回答/坏回答"标注数据，理论上可以直接用来微调底层模型。这会不会是 EDD 的自然进化方向？
4. **团队规模与 EDD**：这篇文章描述的是一个小团队的实践。在更大的团队中，如何管理评估数据集的所有权、避免评估标准的碎片化？
