# 查询构造：让 LLM 把自然语言变成数据库查询

> 一句话总结：查询构造（Query Construction）是让 LLM 把用户的自然语言问题转换成目标数据库的查询语法——对向量库生成元数据过滤、对关系库生成 SQL、对图数据库生成 Cypher——从而打通自然语言与各类数据源之间的桥梁。

---

## 核心要点

### 1. 为什么需要查询构造

标准的 RAG 流程是：用户提问 -> 向量化 -> 在向量库中找相似文档。但这只对纯非结构化数据有效。当用户问"1980年关于外星人的电影"时，"外星人"是语义查询，"1980年"是精确过滤条件。纯向量搜索无法处理后者。查询构造就是让 LLM 同时提取语义部分和结构化条件，生成对应数据库能理解的查询语句。

### 2. 四种查询构造策略

这篇文章介绍了四种策略，对应不同的数据类型和数据库。每种策略的核心思路一样：用 LLM 理解自然语言，生成目标查询语法。

- **Text-to-Metadata-Filter**：针对带元数据的向量库，把自然语言拆分为语义查询 + 过滤条件
- **Text-to-SQL**：针对关系型数据库，生成 SQL 语句
- **Text-to-SQL+Semantic**：针对 pgvector 等支持向量的关系库，同时生成 SQL 过滤和语义搜索
- **Text-to-Cypher**：针对图数据库，生成 Cypher 图查询语句

### 3. 自查询检索器的工作原理

以 Text-to-Metadata-Filter 为例，自查询检索器（Self-Query Retriever）的工作分四步：定义数据源的元数据字段（如 artist、length、genre）；让 LLM 把用户问题拆分为语义查询和过滤条件；从过滤条件中提取逻辑运算符（eq、lt、and、or）；组装成结构化请求。比如"Taylor Swift 或 Katy Perry 的舞曲风格的三分钟以内的青春爱情歌曲"会被拆成 `query="teenager love"` 和 `filter="and(or(eq('artist','Taylor Swift'),eq('artist','Katy Perry')),lt('length',180),eq('genre','pop'))"` 两部分。

### 4. Text-to-SQL 的挑战与技巧

LLM 生成 SQL 面临两个主要挑战：幻觉（编造不存在的表名或字段）和用户拼写错误。应对方法包括：在 prompt 中提供 `CREATE TABLE` 语句让 LLM 了解真实的数据库结构；用 few-shot 示例引导正确的查询模式；遇到错误时用 SQL Agent 自动重试；用向量库存储正确的专有名词拼写来纠正用户输入。

### 5. pgvector 的混合能力

pgvector 为 PostgreSQL 添加了向量搜索能力，使你可以在一条 SQL 中同时做结构化过滤和语义搜索。比如"找包含最多悲伤歌曲的专辑"——先用向量相似度找"悲伤的歌"，再用 SQL 的 GROUP BY 和 COUNT 聚合到专辑维度。这种混合查询在纯向量库中是不可能实现的。

### 6. Cypher 查询与知识图谱

图数据库用 Cypher 语言表达节点和关系，语法像 ASCII 艺术画：`(:Person {name:"Tomaz"})-[:LIVES_IN]->(:Country {name:"Slovenia"})`。Text-to-Cypher 把自然语言转成这种图模式查询。由于 Cypher 的复杂性，推荐使用 GPT-4 级别的模型来生成查询语句。

## 对比表格

| 策略 | 目标数据库 | 数据类型 | 查询语法 | 适用场景 |
|------|-----------|---------|---------|---------|
| Text-to-Metadata-Filter | 向量库（Pinecone, Chroma） | 非结构化 + 元数据 | 结构化过滤 + 向量搜索 | 带标签的文档检索 |
| Text-to-SQL | 关系型（PostgreSQL, MySQL） | 结构化 | SQL | 表格数据查询 |
| Text-to-SQL+Semantic | pgvector | 混合（结构化 + 非结构化） | SQL + 向量算子 | 需要同时过滤和语义搜索 |
| Text-to-Cypher | 图数据库（Neo4j） | 关系型图数据 | Cypher | 多跳关系查询 |

## 类比理解

想象你是一个旅行社的前台，客人用自然语言告诉你需求："我想找一个 2024 年夏天、预算 5000 以内、有海滩的度假目的地。"

**没有查询构造**：你只能把客人的话"丢给搜索引擎"找语义相似的结果，搜出来的可能有冬天的、超预算的、没海滩的——因为它只懂"意思接近"。

**有查询构造**：你先把客人的话拆解为"海滩度假"（语义搜索）+"时间=2024夏"+"价格<5000"（精确过滤），然后在你的旅行产品数据库中先按条件筛选，再按语义排序。结果又准又快。

查询构造就是这个"拆解翻译"的过程，而 LLM 就是那个聪明的前台，它能理解自然语言、也知道数据库"说什么语言"。

## 为什么重要

1. **大部分真实数据都有结构**：即使是"非结构化"的文档，也往往附带结构化元数据（作者、日期、标签）。只用向量搜索是浪费了这些信息。
2. **查询构造是 LUI（语言用户界面）的基石**：未来用户与数据交互的方式将从"写 SQL"变成"说人话"，查询构造是这个转变的技术基础。
3. **不同数据库需要不同策略**：没有一种万能方案。理解四种策略的适用场景，才能为你的数据选择最合适的检索方案。

## 延伸思考

1. **pgvector vs. 专用向量库？** pgvector 的优势在于"一个数据库搞定结构化+语义"，减少系统复杂度；劣势是在超大规模（十亿级向量）场景下性能可能不如专用向量库。选择取决于你的数据规模和团队运维能力。
2. **如何减少 LLM 生成错误查询？** 文章提到了几个技巧（CREATE TABLE 描述、few-shot 示例、错误重试、专有名词纠正），但更根本的方案是限制 LLM 的输出空间——比如只让它填参数，查询模板由代码控制（参见图元数据过滤一文的做法）。
3. **四种策略能组合使用吗？** 完全可以。一个复杂的 RAG 系统可能同时连接向量库、SQL 库和图数据库，由一个 Agent 根据问题类型路由到不同的查询构造器。LangChain 的 Agent 框架天然支持多工具调度。
