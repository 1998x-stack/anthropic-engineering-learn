# 自学习 GPT：用用户反馈自动改进你的 AI 应用

> 一句话总结：通过收集用户的"点赞/踩"反馈，自动将高质量交互筛选到数据集中，再在运行时作为少样本示例（Few-shot Example）注入提示词，让你的 AI 应用越用越好——不需要微调模型。

---

## 核心要点

1. **反馈驱动改进是 LLM 的核心范式**：从 ChatGPT 使用 RLHF（基于人类反馈的强化学习）开始，"收集反馈 --> 优化模型"就是 LLM 进化的基本逻辑。你的应用也可以借鉴这个思路。
2. **自动构建高质量数据集**：大部分团队面临的最大痛点不是"不知道该怎么优化"，而是"没有一份好的输入/输出样本数据集"。自学习 GPT 通过自动化解决了这个问题。
3. **四步闭环**：追踪（Trace）--> 反馈（Feedback）--> 自动筛选（Automation）--> 注入提示词（Few-shot），形成无需人工干预的持续改进循环。
4. **Trace 是关键**：你不能只记录 LLM 调用本身，必须记录完整的系统级 Trace。因为用户反馈是针对整个系统的，但你可能需要优化系统内部的某个特定 LLM 调用。
5. **少样本示例只是起点**：收集到的高质量数据还可以用来做回归测试、微调模型（Fine-tuning）、动态选择最相关的示例，或者用 DSPy 等框架做系统级优化。

---

## 自学习 GPT 四步工作流

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1. 追踪 | 记录完整 Trace | 不是只记 LLM 调用，而是记录整个系统的执行路径，包括工具调用、检索结果等 |
| 2. 反馈 | 收集用户反馈 | 最简单的形式：点赞/踩。反馈附加到对应的 Trace 上 |
| 3. 自动筛选 | 过滤 + 入库 | 自动筛选获得正面反馈的 Trace，提取输入/输出对，存入该 Agent 专属的数据集 |
| 4. 注入 | 运行时加载 | 运行时从数据集拉取示例，作为 Few-shot Example 注入到提示词中 |

## 收集到数据后还能做什么

| 用途 | 说明 | 难度 |
|------|------|------|
| Few-shot 示例注入 | 直接塞进提示词，最快见效 | 低 |
| 回归测试集 | 用好示例做基准，防止改动后质量下降 | 低 |
| 动态示例选择 | 根据新问题的相似度选最相关的示例 | 中 |
| 模型微调 | 用收集的数据对模型做 Fine-tuning | 高 |
| DSPy 系统优化 | 用框架算法自动优化整个 LLM 系统的提示词和参数 | 高 |

## 类比理解

想象你开了一家新餐厅。传统做法是：厨师按固定菜谱做菜，客人不满意就全靠厨师自己琢磨改进。自学习 GPT 的做法就像在每张桌上放了一个"好吃/不好吃"按钮。每当客人按下"好吃"，这道菜的做法就自动存入"招牌菜谱"。下次有新客人来，厨师可以参考这些经过验证的招牌做法来烹饪。菜谱越来越丰富，菜品越来越稳定，而这一切几乎不需要厨师额外操心。

---

## 为什么重要

大多数团队在构建 LLM 应用时最缺的不是技术能力，而是一份高质量的数据集。你可能知道该用 Few-shot、该做 Fine-tuning、该做评估，但没有好的输入/输出样本，一切都是空谈。自学习 GPT 把"收集好数据"这个最痛的环节自动化了：用户在正常使用中产生反馈，系统自动筛选和积累，最终形成一个越来越好的正反馈循环。这是从"一次性开发"到"持续改进"的关键跨越。

---

## 延伸思考

1. 用户的"点赞"真的可靠吗？如果用户标准不一致，会不会把有问题的回答也收录进数据集？是否需要额外的质量校验？
2. 随着数据集越来越大，塞进提示词的 Few-shot 示例越来越多，Token 成本和上下文窗口会成为瓶颈。怎么做动态选择？
3. 每个 Agent 都有自己的专属数据集，当你的系统有成百上千个 Agent 时，数据集管理本身会不会成为新的复杂性？
