# Agent 工具使用基准测试：你的 AI 真的会用工具吗？

> 原文: [Benchmarking Agent Tool Use](https://www.langchain.com/blog/benchmarking-agent-tool-use) | LangChain, 2023-12-20

## 一句话总结

LangChain 设计了 4 个基准测试任务（打字机单工具、打字机多工具、关系数据查询、平行宇宙数学），测试 7 个主流大模型在工具调用上的真实表现，发现即使是 GPT-4 在最简单的任务上也会犯低级错误。

---

## 核心要点

### 1. 为什么需要工具使用基准测试

Agent 应用的核心能力是"会用工具"。但"会用"到底是什么意思？能选对工具？能按正确顺序调用？能在该停的时候停下来？能处理复杂的多步推理？这些能力需要量化评估，而不是跑几个 demo 就宣称"支持工具调用"。

LangChain 设计了一套从简单到复杂的基准测试，帮你回答一个根本问题：**我的模型在工具使用上到底有多靠谱？**

### 2. 四个基准任务

| 任务 | 难度 | 核心考察点 | 描述 |
|------|------|-----------|------|
| Typewriter 单工具 | 简单 | 基本工具调用 + 知道何时停止 | 用一个 `type_letter(letter)` 工具逐字母拼出单词 |
| Typewriter 26 工具 | 中等 | 从多个工具中选择正确的 | 26 个工具（每个字母一个），无参数，选对并按序调用 |
| Relational Data | 较难 | 多步推理 + 跨数据源关联 | 用 17 个工具查询 3 张关系表回答复合问题 |
| Multiverse Math | 困难 | 抵抗预训练知识 + 组合推理 | 在"数学规则被篡改"的宇宙中用工具做计算 |

### 3. 四个评估指标

| 指标 | 英文术语 | 含义 |
|------|---------|------|
| 正确性 | Correctness | 最终答案是否与 ground truth 一致（LLM-as-Judge 评估） |
| 最终状态正确性 | Correct Final State | 工具调用后的环境状态是否正确（仅适用于 Typewriter 任务） |
| 工具调用次数准确度 | Tool Count Accuracy | 实际调用工具的次数是否等于最优次数 |
| 步数 | # Steps | Agent 总共执行了多少步（包含思考和工具调用） |

## 各任务深度解析

### 任务一：Typewriter 单工具

这是最简单的任务：给你一个单词（比如 "cat"），你需要调用 `type_letter("c")`、`type_letter("a")`、`type_letter("t")`，然后**停下来**。

你可能觉得这对 GPT-4 来说小菜一碟，但事实让人意外：

```
失败案例 1: 被要求拼 "keyboard"
GPT-4 的反应: 直接拒绝尝试

失败案例 2: 被要求拼 "head"
GPT-4 的反应: 不认识这个词(?!)
```

这说明即使是最强的模型，在最基本的工具调用任务上也可能出现莫名其妙的失败。

### 任务二：Typewriter 26 工具

跟任务一一样拼单词，但工具变了：不再是一个通用的 `type_letter(letter)`，而是 26 个独立工具——`type_a()`、`type_b()`...`type_z()`，每个都不接受参数。Agent 必须在 26 个工具中选对并按正确顺序调用。

```
失败案例: 被要求拼 "aaaa"
GPT-4 的表现:
  第1步: type_a()  -- 正确
  第2步: type_a()  -- 正确
  第3步: type_a()  -- 正确
  第4步: type_a()  -- 正确
  第5步: type_a()  -- 多余! 应该停了!
  第6步: type_a()  -- 继续多余!
  第7步: type_a()  -- 还在打!
  第8步: type_a()  -- 终于停了...

结果: 拼出了 "aaaaaaaa" 而不是 "aaaa"
```

问题出在"不知道什么时候停"。工具数量增多后，Agent 的"刹车"能力明显下降。

### 任务三：Relational Data（关系数据）

这个任务最接近真实业务场景。Agent 有 3 张关系表（用户、位置、食物）和 17 个查询工具，需要回答复合问题。

```
示例工具:
  find_users_by_name(name)        -> 按名字搜用户
  get_user_location(user_id)      -> 获取用户所在位置
  get_weather_at_location(loc_id) -> 获取某位置的天气

示例问题: "Alice 现在需要带伞吗?"

需要的推理链:
  1. find_users_by_name("Alice") -> 得到 user_id
  2. get_user_location(user_id)  -> 得到 location_id
  3. get_weather_at_location(location_id) -> 得到天气信息
  4. 根据天气判断是否需要伞
```

这个任务考察的是 Agent 能否把多个工具串联起来做多步推理，以及能否正确区分"名字"和"ID"（说明书明确提醒了这一点）。

### 任务四：Multiverse Math（平行宇宙数学）

这是最邪恶的任务。数学规则被改了：在这个宇宙里，2 + 2 = 5.2，5.2 - 2 = 0.2。Agent 必须**完全忽略自己知道的数学知识**，只通过工具来计算。

```
系统提示（节选）:
  "你在一个替代数学宇宙中。运算规则与你所知的不同。
   不要猜答案，不要用你内在的数学知识。
   必须使用工具来回答。
   交换律和结合律仍然成立，但分配律不成立。"

示例复合问题: 
  "5 个细胞，每 20 分钟分裂一次，120 分钟后有多少？"
  
  需要的推理:
  1. divide(120, 20) = d  (分裂次数)
  2. power(2, d) = c      (每个细胞产生的数量)
  3. multiply(5, c) = f   (最终总数)

  注意: 每一步的结果都不是你"以为"的那个数!
```

这个任务考察两个关键能力：
- **能否抵抗预训练知识**: 模型会不会"忍不住"用自己知道的数学来算
- **组合推理能力**: 能否把多步工具调用的结果正确串联

## 核心发现

### 模型表现概览

```
                    Typewriter   Typewriter   Relational   Multiverse
模型                 (1 tool)     (26 tools)   Data         Math
----------------------------------------------------------------------
GPT-4 (Tool Call)     高           中高         中高         中
GPT-3.5 (Tool Call)   中           中           中           低
GPT-4 (OpenAI Fn)     高           中高         中高         中
GPT-3.5 (OpenAI Fn)   中           中           中           低
开源模型              低-中         低           低           很低
----------------------------------------------------------------------
```

### 关键发现

| 发现 | 说明 |
|------|------|
| 简单任务也会失败 | GPT-4 在单工具 Typewriter 上不是 100%，会出现拒绝执行或不识别单词的情况 |
| 工具数量影响大 | 从 1 个工具变成 26 个，所有模型的表现都下降 |
| "停不下来"是通病 | 多个模型在完成任务后继续调用工具，不知道该停了 |
| 开源模型差距明显 | 在工具调用场景下，开源模型与闭源模型的差距比纯文本任务大得多 |
| 安全过滤的副作用 | Google 的 Gemini-pro 把"2 的 3 次方是多少"标记为"不安全"，误报率过高影响可用性 |

## 类比理解

把 Agent 的工具使用能力想象成**考驾照**：

- **Typewriter 单工具** = 直线行驶：最基本的操作，油门、刹车、方向盘。你以为人人都会，但有人就是会忘踩刹车（停不下来）。

- **Typewriter 26 工具** = 在停车场找车位：你要在 26 个车位中选对自己的位置，而且要按正确的路线开过去。工具多了，选择困难症就来了。

- **Relational Data** = 在陌生城市导航：你要查地图（用户表）、找路线（位置表）、看天气（天气表），多个信息源串联在一起才能做出正确决策。

- **Multiverse Math** = 在英国开车：所有交通规则都和你习惯的相反（靠左行驶、右舵车）。你必须完全抛弃肌肉记忆，严格按新规则来。这考验的是"能否克制住本能"。

## 为什么重要

1. **选模型有了数据支撑**: 不再是"GPT-4 最强就用 GPT-4"，而是"我的应用需要用 17 个工具做关系查询，哪个模型在这个场景下最好"。

2. **暴露了工具调用的真实困难**: "支持 Function Calling"和"能可靠地使用工具"是两回事。基准测试让你看到模型在压力下的真实表现。

3. **指导 Agent 架构设计**: 如果模型在 26 个工具时表现下降，也许你应该做工具分组或工具路由，而不是把所有工具一股脑扔给模型。

4. **开源模型的发展方向**: 测试清楚暴露了开源模型在工具调用上的差距，为社区指明了最需要改进的方向。

## 延伸思考

1. **工具描述的质量影响有多大？** 这些基准测试中的工具描述都很清晰。但在现实中，工具文档往往模糊不清。工具描述质量对 Agent 表现的影响可能比模型选择更大。

2. **"停不下来"的问题怎么解？** 多个模型都有过度调用工具的倾向。这是模型本身的问题，还是 Prompt 设计的问题？加上明确的"完成条件"指令能否改善？

3. **工具数量的临界点在哪？** 从 1 到 26 工具，表现下降了。那从 26 到 100 呢？是线性下降还是存在断崖？这对设计真实 Agent 应用至关重要。

4. **这些基准测试还缺什么？** 所有任务都是单轮的（给一个问题，完成后结束）。但真实 Agent 需要在多轮对话中持续使用工具，中间可能有上下文切换、错误恢复等复杂情况。

5. **模型迭代后表现变了吗？** 这篇文章发布于 2023 年底。到 2024-2025 年，GPT-4o、Claude 3.5/4、Gemini 2 等新模型在这些任务上的表现理应有大幅改善。定期重跑基准测试才能跟上模型进化的速度。
