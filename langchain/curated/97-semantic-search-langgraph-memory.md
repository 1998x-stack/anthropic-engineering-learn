# LangGraph Memory 的语义搜索：让 Agent 按"意思"找记忆

> 一句话总结：LangGraph 的内存存储（Memory Store）新增了语义搜索（Semantic Search）能力，让 Agent 不再只能按关键词精确匹配，而是能根据"意思相近"来检索过往记忆，大幅提升个性化和上下文利用率。

---

## 核心要点

### 1. 为什么需要语义搜索？

传统的内存过滤只能做精确匹配——你存了"用户喜欢咖啡"，搜索"咖啡"才找得到。但 Agent 经常需要根据"意思"来找信息，比如用户问"推荐一杯热饮"，精确匹配就无能为力了。语义搜索通过向量嵌入（Embedding）把文本转换成数学表示，然后比较"距离"来衡量语义相似度。

想象一下：你的大脑不会按"关键词索引"来回忆事情。你想起"上次吃的好吃的"时，大脑是按"好吃"这个意思去搜索的，而不是按具体菜名。语义搜索就是让 Agent 拥有这种"按意思找"的能力。

### 2. Agent 需要语义搜索的三种典型场景

| 场景 | 说明 | 举例 |
|------|------|------|
| 用户偏好回忆 | 根据当前对话找到相关的历史偏好 | 用户说"帮我订机票"，Agent 记起他偏好靠窗座位 |
| 从失败中学习 | 检索过去类似的失败尝试 | 上次用方案 A 解决类似问题失败了，这次换方案 B |
| 知识一致性 | 回忆之前学到的重要事实 | 上周用户说自己是素食主义者，现在推荐餐厅时要记住 |

### 3. 怎么用？

`BaseStore` 的 `search` 方法现在支持传入自然语言 `query` 参数。文档会按语义相似度评分并返回。目前支持两种存储后端：

- `InMemoryStore`：用于开发测试
- `PostgresStore`：用于生产环境

```
用户最新消息 ──> store.search(query=消息内容) ──> 返回相似度最高的记忆
```

### 4. 配置方式

在 `langgraph.json` 中添加索引配置即可：

| 配置项 | 含义 | 示例值 |
|--------|------|--------|
| `embed` | 嵌入模型提供方 | `"openai:text-embedding-3-small"` |
| `dims` | 嵌入向量维度 | `1536` |
| `fields` | 要索引的字段列表 | `["text", "summary"]` 或 `["$"]` 表示全部 |

你也可以自定义嵌入函数，不依赖 LangChain 的内置提供方。还可以在 `store.put` 时用 `index` 参数控制单条数据是否参与索引、索引哪些字段。

### 5. 迁移成本几乎为零

如果你已经在用 LangGraph 的 Memory Store，加上语义搜索是完全向后兼容的（Non-breaking）。原有的 `put`、`get` 操作一切照旧，只需要加一个 `index` 配置，新存入的文档就会自动建立语义索引。

```
+------------------+     自然语言查询      +-------------------+
|                  | ──────────────────> |                   |
|   Agent 节点      |                     |   BaseStore       |
|                  | <────────────────── |   (search 方法)    |
+------------------+   按相似度排序返回     +-------------------+
                                                |
                                          +-----+------+
                                          |            |
                                   InMemoryStore  PostgresStore
                                    (开发用)       (生产用)
                                          |            |
                                     嵌入向量索引   嵌入向量索引
                                     (内存中)     (PostgreSQL)
```

```
存储流程:
  store.put(namespace, key, value)
       |
       v
  是否配置了 index?
       |
    是 / 否
   /       \
  v         v
提取 fields  直接存储
  |          (不索引)
  v
调用 embed 模型
  |
  v
生成向量并存储

检索流程:
  store.search(namespace, query="...")
       |
       v
  query 文本 -> embed -> 向量
       |
       v
  与存储的向量做相似度计算
       |
       v
  按分数排序，返回 top-k 结果
```

## 类比理解

把 Agent 的记忆存储想象成一个图书馆。以前你只能通过"书名精确查找"来找书——你必须记得书的确切标题。现在有了语义搜索，就像图书馆请了一位理解你需求的管理员：你说"我想找一本关于太空探索的科幻小说"，管理员能帮你在整个书架上找到《三体》《银河帝国》这些意思相关的书，即使你从没提过这些具体书名。

---

## 为什么重要

1. **Agent 个性化的基石**：没有语义搜索，Agent 很难真正"记住"用户。用户换个说法描述同一件事，Agent 就可能找不到之前的记忆。
2. **从"关键词匹配"到"意思理解"的跨越**：这是让 Agent 从"工具"进化为"助手"的关键能力。人类的记忆是按语义组织的，Agent 的记忆也应该如此。
3. **零迁移成本降低了采用门槛**：已有用户不需要重构代码，加几行配置就能获得语义搜索能力，这让整个 LangGraph 生态的 Agent 质量都能快速提升。

---

## 延伸思考

1. 语义搜索依赖嵌入模型的质量——如果嵌入模型对你的领域术语理解不好（比如医学、法律专有名词），搜索质量会下降。你需要考虑是否要用领域微调过的嵌入模型。
2. 语义搜索和精确过滤（Filter）可以组合使用。实际场景中，你往往先按命名空间（Namespace）和元数据过滤缩小范围，再在结果中做语义排序。
3. 随着记忆量增长，向量索引的性能和成本都会成为问题。什么时候该清理旧记忆？什么时候该合并相似记忆？这些是语义搜索之上需要考虑的"记忆管理"问题。
