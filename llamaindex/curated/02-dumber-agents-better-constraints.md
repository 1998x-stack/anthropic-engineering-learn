# 越笨的 Agent 越需要约束：复杂度该放在哪一层？

> **一句话总结：** 能力弱的 LLM 做 Agent 时，与其让它自由推理，不如把复杂逻辑下沉到工具层，让 Agent 只做简单的路由选择——约束越多，结果反而越好。

---

## 核心要点

1. **复杂 Agent + 简单工具 vs. 简单 Agent + 复杂工具。** 这是 Agent 系统设计的核心权衡：推理复杂度应该放在 Agent 层还是工具层？
2. **GPT-3 级别的 LLM 驾驭不了 ReAct 循环。** 实验表明，GPT-3 在 ReAct 模式下选错工具、漏选工具、推理链出错，表现很不稳定。
3. **GPT-4 可以自由发挥，GPT-3 需要"导轨"。** 更强的模型能在开放推理中表现良好，更弱的模型则需要更强的结构化约束。
4. **路由模式是弱模型的最佳策略。** 把 Agent 简化为"选择器"，把比较/对比等复杂逻辑封装进专门的工具，GPT-3 也能给出高质量答案。

---

## 实验设置与结果对比

| 配置 | Agent 类型 | LLM | 工具集 | 表现 |
|------|-----------|-----|-------|------|
| 配置 A | ReAct（自由推理） | GPT-3 | 3 个简单向量索引 | 差 -- 选错工具、遗漏数据源、推理链混乱 |
| 配置 B | ReAct（自由推理） | GPT-4 | 3 个简单向量索引 | 好 -- 遍历所有数据源，答案详实 |
| 配置 C | Router（单步路由） | GPT-3 | 3 个简单索引 + 1 个对比查询引擎 | 好 -- 正确选择对比工具，答案质量接近 GPT-4 |

## 两种架构对比

```
方案 A：复杂 Agent + 简单工具（ReAct 模式）
+------------------------------------------+
|           Agent (ReAct 推理循环)           |
|  Thought -> Action -> Observation -> ...  |
|  需要 LLM 自行决定：                       |
|  - 查哪些文档？                            |
|  - 查几次？                               |
|  - 如何合并结果？                          |
+----+----------+-----------+--------------+
     |          |           |
     v          v           v
  +------+  +------+  +------+
  |3月索引|  |6月索引|  |9月索引|
  |简单检索|  |简单检索|  |简单检索|
  +------+  +------+  +------+


方案 B：简单 Agent + 复杂工具（Router 模式）
+------------------------------------------+
|        Agent (单步路由选择器)               |
|  只做一件事：选择最合适的工具               |
+----+-------+--------+----------+---------+
     |       |        |          |
     v       v        v          v
  +------+ +------+ +------+ +----------+
  |3月索引| |6月索引| |9月索引| |对比查询引擎|
  |简单检索| |简单检索| |简单检索| |内置分解逻辑|
  +------+ +------+ +------+ |内置合并逻辑|
                              +----------+
```

## GPT-3 ReAct 的四大失败模式

```
失败模式 1: 工具选择不完整
  问题: "分析 Uber 过去几个季度的收入增长"
  期望: 查询 3月、6月、9月三份报告
  实际: 只查了 9月 --> 答案片面

失败模式 2: 推理链混乱
  问题: "Uber 在 2022 年 9 月有多少现金？"
  实际: 无法给工具提供正确输入 + 查了无关的 6月和 3月文件

失败模式 3: 微小措辞变化导致完全不同的结果
  "...over time"  --> 选了 Tool A，输入 "financials"
  "...over quarters" --> 选了 Tool B，输入 "revenue growth"
  同一个问题，两种说法，两种完全不同的回答

失败模式 4: 工具输入与问题脱节
  问题关于 "revenue growth and risk factors"
  Agent 给工具的输入却是 "financials"
  --> 答案空泛无用
```

## 复杂度分配原则

```
           LLM 能力强                    LLM 能力弱
     +------------------+         +------------------+
     |   Agent 层       |         |   Agent 层       |
     |   可以复杂       |         |   必须简单       |
     |   (ReAct 循环)   |         |   (单步路由)     |
     |   ████████████   |         |   ██             |
     +------------------+         +------------------+
     |   Tool 层        |         |   Tool 层        |
     |   可以简单       |         |   必须复杂       |
     |   ██             |         |   ████████████   |
     +------------------+         +------------------+

     总复杂度 = Agent 复杂度 + Tool 复杂度
     关键: 总复杂度不变，但分配方式取决于 LLM 能力
```

## 类比理解

想象你在经营一家餐厅：

- **ReAct Agent** 就像让一个新手厨师（GPT-3）拿着食材自己想怎么做就怎么做。他可能忘了加盐、漏掉某道配菜、或者把鱼香肉丝做成了糖醋排骨。
- **Router Agent** 则像是给这个新手厨师提供了**预制菜包**——每个包上写清楚了"这是红烧排骨套餐"。他只需要做一件事：根据客人点的菜选对应的预制包，然后按说明加热就行。
- **GPT-4** 则像是一个大厨，给他原材料他也能发挥出色。但就算是大厨，如果你给他预制菜包，出品会更稳定。

核心洞察：**不是所有 Agent 都需要自由推理。对于能力有限的模型，约束就是最好的赋能。**

---

## 为什么重要

- **成本与质量的平衡。** GPT-4 强但贵，GPT-3 弱但便宜。通过合理设计工具层，你可以用便宜的模型达到接近昂贵模型的效果。
- **可靠性是生产环境的底线。** ReAct 的不确定性在 demo 里可以接受，但在金融分析等严肃场景中是灾难性的。路由模式的可预测性是巨大优势。
- **Agent 设计的通用原则。** "把复杂度放在最可控的地方"不仅适用于 LLM Agent，也是所有系统设计的黄金法则。

---

## 延伸思考

1. **开源模型适用吗？** 文中只测试了 GPT-3 和 GPT-4。对于 Llama、Mistral 等开源模型，"约束换可靠性"的策略是否同样有效？大概率是的，甚至更需要。
2. **能否动态切换？** 简单问题用路由模式省钱，复杂问题切换到 ReAct 模式追求质量——这种"自适应 Agent"是不是更好的方案？
3. **Prompt 工程的上限在哪？** 文中承认没有尝试优化 ReAct 的提示词。也许通过精心设计的提示词，GPT-3 的 ReAct 表现能大幅提升？这是一个值得探索的方向。
