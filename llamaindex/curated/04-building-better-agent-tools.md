# 如何为 LLM Agent 打造好用的工具

> **一句话总结：** 给 Agent 写工具，不是写普通函数——你需要站在"一个会犯错的新手同事"的角度，把提示写清楚、把输入做容错、把错误变成引导。

---

## 核心要点

1. **工具提示（Tool Prompt）是 Agent 唯一的说明书。** Agent 不会看你的源码，它只读函数签名和文档字符串（docstring）。写得模糊，Agent 就猜；写得太长，又挤占上下文窗口（Context Window）。
2. **容错设计（Tolerance）比严格校验更实用。** 如果某个参数能从已有数据推断出来，就别强制 Agent 传。少传一个参数，工具自己补上，比报错再来一轮要高效得多。
3. **错误信息就是下一轮提示。** 不要把底层库的报错原样抛给 Agent，而是告诉它"你哪里做错了、怎么改"。Agent 大概率能自我纠正。
4. **提供辅助函数。** Agent 不知道今天几号、不会算时区。把这些确定性小工具暴露出来，比让 Agent 猜或幻觉（Hallucination）好得多。
5. **变更操作要返回确认提示。** 创建、更新、删除这类操作成功后，返回一句"完成了，可以继续下一步"，比返回空值更能推动 Agent 往前走。
6. **大响应存索引。** 返回数据超过上下文窗口时，先存进索引（Index），让 Agent 用检索的方式按需读取。

## 六大实践速查表

| 实践 | 问题场景 | 解决思路 | 效果 |
|------|---------|---------|------|
| 写好工具提示 | Agent 传错参数格式 | docstring 写清参数类型、用途、示例值 | 减少调用错误 |
| 容错部分输入 | Agent 漏传非关键参数 | 用已有数据填充缺失字段 | 提高任务成功率 |
| 友好错误引导 | Agent 传了空的 draft_id | 返回"你漏了 draft_id，可以从上文获取" | Agent 自我纠正 |
| 暴露辅助函数 | Agent 不知道当前日期 | 提供 `get_date()` 工具 | 消除幻觉 |
| 变更操作返回确认 | Agent 创建事件后不知下一步 | 返回"Event created! Move on." | 流程不卡顿 |
| 大响应存索引 | API 返回数据超过上下文窗口 | 包装成 Document，用 LoadAndSearchTool | 避免溢出报错 |

## 类比理解

把 Agent 想象成一个新来的实习生，你给他一本操作手册（工具提示）和一套工具箱。

- **工具提示**就是手册里的操作说明。如果你写"拧那个螺丝"，实习生会问"哪个螺丝？用什么扳手？"。但如果你写"用十字螺丝刀，拧面板左上角的 M3 银色螺丝，顺时针两圈"，他一次就能做对。
- **容错设计**就像工具箱里附带了默认配件。实习生说"我要拧螺丝但忘了带垫片"，你不用让他跑回仓库，因为工具箱里已经备好了标准垫片。
- **错误引导**就像师傅在旁边指点。实习生拿错了工具，你不是把错误代码甩给他，而是说"你拿的是一字螺丝刀，这里需要十字的，在第二个抽屉"。

---

## 为什么重要

当前 Agent 系统的瓶颈往往不在模型智力，而在工具设计。一个设计粗糙的工具会让 Agent 反复出错、浪费 Token（令牌）、拖慢用户体验。反过来，一个设计精良的工具能让 Agent 在更少的交互轮次中完成任务，直接降低成本、提升可靠性。

工具设计本质上是一种"人机接口设计"——只不过用户换成了 LLM。你在写 docstring 时投入的每一分钟思考，都能在生产环境中节省成百上千次错误调用。

---

## 延伸思考

1. **工具数量的上限在哪里？** 当 Agent 面对几十个工具时，选择本身就变成了挑战。你可能需要工具分组、动态加载，或者用一个"工具路由 Agent"来先筛选候选工具。
2. **提示与代码的边界。** 有些逻辑放在提示里（"如果不知道日期就先调 get_date"），有些放在代码里（自动填充缺失字段）。怎么划分？经验法则：确定性逻辑写代码，模糊判断留给提示。
3. **测试工具的方式。** 文中提到一个巧妙的调试技巧：直接问 Agent"你有哪些工具？参数是什么？"来验证 Agent 对工具的理解是否正确。这其实是一种"可解释性测试"，值得纳入开发流程。
