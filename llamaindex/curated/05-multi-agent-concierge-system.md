# 多 Agent 礼宾系统：如何让一群 Agent 协作服务用户

> **一句话总结：** 当一个 Agent 管不了几十个任务时，把职责拆给多个专职 Agent，再用一个"调度员"决定谁来接客、一个"接力员"自动串联依赖任务——这就是多 Agent 礼宾系统（Multi-Agent Concierge System）的核心思路。

---

## 核心要点

1. **单 Agent 有天花板。** 当任务多达几十种、工具多达上百个时，单个 Agent 的系统提示（System Prompt）会膨胀到不可控，工具选择准确率也会下降。拆分成多个专职 Agent 是自然的扩展方式。
2. **三种"元 Agent"是架构关键。** 礼宾 Agent（Concierge）负责迎客和反馈；编排 Agent（Orchestrator）负责路由决策；接续 Agent（Continuation）负责自动串联有依赖关系的任务链。
3. **全局状态（Global State）是 Agent 间的共享记忆。** 用户是否已认证、当前选中的账户是什么——这些信息不存在任何单个 Agent 里，而是存在一个所有 Agent 都能读写的全局字典中。
4. **任务依赖用自然语言描述。** 编排 Agent 的提示里写着"如果用户要查余额但没认证，先路由到认证 Agent"，而不是用代码写死依赖图。这让系统灵活且易扩展。

---

## 系统角色一览

| 角色 | 类型 | 职责 | 是否直接面向用户 |
|------|------|------|-----------------|
| 股票查询 Agent | 任务 Agent | 查股票代码、查价格 | 是 |
| 认证 Agent | 任务 Agent | 验证用户名和密码 | 是 |
| 账户余额 Agent | 任务 Agent | 选账户、查余额 | 是 |
| 转账 Agent | 任务 Agent | 选目标账户、输入金额、执行转账 | 是 |
| 礼宾 Agent（Concierge） | 元 Agent | 迎接用户、展示可用服务、反馈结果 | 是 |
| 编排 Agent（Orchestrator） | 元 Agent | 根据用户意图和当前状态路由到合适的 Agent | 否（仅输出 Agent 名称） |
| 接续 Agent（Continuation） | 元 Agent | 任务完成后检查是否有后续步骤，自动发起下一个请求 | 否（仅触发路由） |

## 系统运行流程

```
用户输入
  |
  v
+--------------------+
| 编排 Agent         |  <-- 读取全局状态 + 聊天历史
| (Orchestrator)     |      输出：应该由哪个 Agent 接手
+--------------------+
  |
  |  路由到对应 Agent
  v
+--------------------+       +--------------------+
| 礼宾 Agent        |       | 认证 Agent         |
| (初次/无明确意图)  |       | (需要登录时)       |
+--------------------+       +--------------------+
                                    |
                                    | 认证完成
                                    v
                             +--------------------+
                             | 接续 Agent         |  <-- 检查聊天历史
                             | (Continuation)     |      发现原始意图是"查余额"
                             +--------------------+
                                    |
                                    | 自动路由
                                    v
                             +--------------------+
                             | 账户余额 Agent     |
                             | (完成原始任务)     |
                             +--------------------+
                                    |
                                    v
                              返回结果给用户
```

## 关键设计：任务依赖链

一个用户说"我要转账"，系统的处理链路是：

```
转账 --> 需要先查余额 --> 需要先认证

实际执行顺序：
认证 Agent --> 接续 Agent --> 账户余额 Agent --> 接续 Agent --> 转账 Agent
              (自动串联)                       (自动串联)
```

这里的精妙之处在于：每个任务 Agent 不知道自己是"链"的一环。认证 Agent 只管认证，不关心用户最终想做什么。是接续 Agent 在任务完成后回溯聊天历史，发现"原来用户的真正目的是转账"，然后自动把请求重新丢给编排 Agent。

## 类比理解

想象你走进一家高端酒店。

- **礼宾 Agent** 就是大堂的礼宾员（Concierge），微笑着问你"需要什么服务？"并列出酒店能提供的服务清单。
- **编排 Agent** 就是后台的调度中心。你说"我想订餐厅"，调度中心不会亲自去订，而是在对讲机里说"把客人转给餐饮部"。
- **任务 Agent** 就是各个部门的专员：餐饮部、客房部、健身中心、机场接送……每个人只精通自己的领域。
- **接续 Agent** 就是那个特别细心的协调员。你说"我要办入住然后去健身房"，当前台办完入住后，协调员记得你还想去健身房，主动帮你联系健身中心，而不是让你再跑一趟大堂。
- **全局状态** 就是酒店的客户管理系统——无论你跟哪个部门打交道，他们都能看到你的房间号、会员等级、偏好记录。

## 为什么重要

多 Agent 系统解决的核心问题是**复杂度管理**。当你的聊天机器人需要处理 50 种任务、200 个工具时，单 Agent 方案会变成一团乱麻：系统提示写不完、工具选择不准确、调试无从下手。

拆分成多个 Agent 后，每个 Agent 的职责清晰、提示简短、工具数量可控。编排 Agent 只做路由决策，不执行具体任务；任务 Agent 只关注自己的领域，不操心全局流程。这种"关注点分离"（Separation of Concerns）是软件工程的经典原则，在 Agent 架构中同样适用。

---

## 延伸思考

1. **编排 Agent 的可靠性。** 整个系统的正确性高度依赖编排 Agent 的路由判断。如果它把"转账"路由到了"股票查询"，后果不堪设想。在生产环境中，你可能需要对编排 Agent 的输出做白名单校验，甚至加一层人工确认。
2. **状态管理的一致性。** 全局状态被多个 Agent 读写，存在并发冲突的风险。当前的简单字典方案适合单用户、单会话场景，但多用户场景下你需要更严谨的状态管理机制。
3. **Agent 之间的解耦程度。** 接续 Agent 需要回溯聊天历史来推断用户原始意图，这依赖于聊天记录的质量和上下文窗口的大小。如果对话很长，接续 Agent 可能"忘记"最初的目标。可以考虑在全局状态中显式记录"当前任务链"来增强健壮性。
