# 马斯克式决策审问：Harness Engineering——在 Agent 优先的世界中使用 Codex

> **分析对象**: [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)
> **分析框架**: Musk-Style Decision Interrogation
> **角色**: OpenAI 工程团队（三人核心团队 + Codex agents）

---

## 问题一：你的故事——你做了什么决策，为什么？

我们用零行手写代码构建并发布了一个软件产品。100 万行代码。1500 个 PR。5 个月。3 个人类工程师驱动 Codex agents。这大约是手写代码所需时间的 1/10。

但这不是"AI 替人类写代码所以很快"的故事。这是"人类的角色从写代码变成了构建 agent 能工作的环境"的故事。而且早期进展比我们预期的**更慢**——不是因为 Codex 不够好，而是因为环境还不够好。

### 决策一：零行手写代码——不是噱头，是强迫函数

**直觉的质疑：**

"零行手写代码"听起来像营销噱头。为什么不手写一些关键部分？为什么不让人类在最复杂的模块上直接写代码？

**我的回答：**

因为**约束会驱动正确的行为。** 如果我们允许自己在 agent 卡住时手写代码——我们永远学不会如何让 agent 不卡住。我们会走捷径。我们会写一些代码，然后忘记把让 agent 也能写这些代码所需的环境改进编码回系统。

零手写代码意味着：**当 agent 失败时，唯一的修复路径是改进 agent 的环境。** 你

不能"自己写"。你必须问："agent 缺少什么能力？如何让这种能力对 agent 既可理解又可执行？"

这种约束改变了整个工程范式：

- 不是"这段代码太难了，我手写吧" → 是"agent 为什么写不了这段代码？环境缺什么？"
- 不是"我改一下 prompt 让 agent 试试" → 是"把所需的知识/工具/约束编码进仓库，让 agent 每次都能做对"
- 人类的角色从"编码者"变成了"环境设计师"

**最深层的转变：**

早期进展比预期更慢。不是因为 Codex 不行——而是因为**环境是未充分规定的。** Agent 缺少工具、抽象、内部结构来完成高层次目标。工程团队的主要工作变成了**让 agent 能做有用的工作。**

"当某些事情失败了，修复几乎从来不是'再试一次'。因为取得进展的唯一方式是让 Codex 完成工作，人类工程师总是介入任务并问：'缺少什么能力，我们如何让它对 agent 既清晰又可执行？'"

### 决策二：AGENTS.md 作为目录而非百科全书——渐进式信息披露的极端版本

**失败的做法：**

我们尝试了"一个大 AGENTS.md"的方法。它以可预测的方式失败了：

1. **上下文是稀缺资源。** 巨大的指令文件挤走了任务、代码、相关文档——agent 要么漏掉关键约束，要么开始优化错误的约束。

2. **太多指导变成没有指导。** 当所有东西都"重要"时——没有东西是重要的。Agent 最终是局部模式匹配而不是有意图地导航。

3. **它瞬间腐烂。** 单体手册变成了过时规则的墓地。Agent 无法分辨什么仍然有效。人类停止维护它。文件静悄悄地变成了一个诱人的麻烦。

4. **无法验证。** 一个单体 blob 不适合机械检查（覆盖率、新鲜度、ownership、交叉链接）——所以漂移是不可避免的。

**正确的做法——渐进式信息披露：**

AGENTS.md 大约 100 行——被注入上下文，**主要是作为地图**，带指针指向更深层的真值来源。

仓库的知识库存在于结构化的 `docs/` 目录中——作为系统记录：

- 设计文档被编目和索引，包括验证状态和定义 agent 优先操作原则的核心信念集
- 架构文档提供领域和包分层的顶层地图
- 质量文档对每个产品领域和架构层进行评分，随时间追踪差距
- 计划被当作一等制品——轻量计划用于小变更，执行计划（带进度和决策日志）用于复杂工作

**机械执行：**

我们用专用 linters 和 CI 作业来验证知识库是最新的、交叉链接的、结构正确的。一个定期的"文档园艺"agent 扫描陈旧或过时的文档，打开修复 PR。

**这个设计的物理本质：**

不是"给 agent 一本百科全书"——是给 agent **一张地图 + 知道如何查找更深层信息的能力。** Agent 从一个小的、稳定的入口点开始，被教会下一步去哪里找，而不是一开始就被淹没。

这与人类入职完全一致。你不会给新员工 1000 页手册让他们背——你给他们一张组织架构图、一份关键文档的目录、和"当你遇到 X 时去看 Y"的指导。

### 决策三：仓库知识作为系统记录——一切必须在仓库内

**根本原则：**

从 agent 的视角——任何它不能在上下文中访问的东西，实际上就不存在。Google Docs 里的知识、Slack 讨论、人脑中的信息——对 agent 都是不可见

的。**仓库本地的、版本化的制品（代码、markdown、schemas、可执行计划）是 agent 能看到的一切。**

这意味着：

- 那个让团队在架构模式上达成一致的 Slack 讨论？如果它不能在仓库中被发现——它对 agent 就是不可见的——就像一个三个月后入职的新员工一样不知道它的存在。
- 我们倾向于**可以被 agent 完全内部化和在仓库内推理的依赖和抽象。** "无聊"的技术（可组合性、API 稳定性、训练数据中的良好覆盖）对 agent 更容易建模。
- 在某些情况下，**让 agent 重新实现功能的子集比绕过公共库的不透明上游行为更便宜。** 我们实现了自己的 `map-with-concurrency` 辅助函数——与我们的 OpenTelemetry instrumentation 紧密集成，100% 测试覆盖率，行为精确符合我们的运行时预期。

**这个决策的深层含义：**

传统工程中，知识存在于人的脑子里、Slack 里、Google Docs 里、代码里。Agent 优先工程中——**知识只存在于代码仓库里。** 任何不在仓库的信息，agent 就无法利用。

这迫使团队把对话、决策、架构模式全部编码为仓库内的制品。不是文档作为次要产物——**文档作为开发过程中平等的、必要的产物。**

### 决策四：刚性架构模型 + 机械执行——不是专制，是倍增器

**直觉反感：**

一个严格的架构模型——每个业务领域划分为固定的层次（Types → Config → Repo → Service → Runtime → UI），依赖方向被严格验证——这在人类优先的工程文化中会被视为过度约束。"为什么不能自由选择架构？""这太死板了。"

**为什么在 agent 优先的世界中这是必需的：**

因为 agent 没有架构直觉。它会复制已有的模式——包括不均匀的、次优的模式。如果不强制执行边界——agent 会向四面八方蔓延。

**机械执行是关键：**

- 自定义 linters 和结构测试强制执行层次依赖
- 跨领域关注点（auth、connectors、telemetry）只能通过单一的显式接口进入：Providers
- 文件大小限制、命名约定、结构化日志——全部通过自定义 lint 强制执行
- **Lint 的错误消息被编写为向 agent 上下文注入修复指令**

这不是"人类写规则约束 agent"——是"规则一旦编码，它们到处同时生效"。在人类优先的工作流中，这些规则可能感觉像说教或束缚。在 agent 优先的工作流中——**它们变成倍增器。**

**架构作为早期先决条件：**

这种架构通常是你有几百个工程师时才推迟实施的。有了 coding agents——它是早期的先决条件：**约束是允许速度而不衰减或架构漂移的东西。**

### 决策五：最小阻塞合并门——吞吐量 > 完美

**传统智慧：**

每个 PR 必须在合并前通过所有测试。测试不稳定？修复测试。代码审查未完成？别合并。

**我们的反直觉做法：**

仓库以最小阻塞合并门运行。PR 是短命的。测试 flake 通常通过后续运行处理，而不是无限期阻塞进度。**在一个 agent 吞吐量远超人类注意力的系统中——修正便宜，等待昂贵。**

这在低吞吐量环境中是不负责任的。在这个系统中——通常是对的。

**为什么：**

因为 agent 的吞吐量 = 每天 3.5 个 PR/工程师（而且随着团队增长这个数字还在上升）。如果每个 PR 被一个人类审查者阻塞 2 小时——那么人类不是瓶颈，他们是**整个系统的锁。**

解决之道不是更多人类审查者——是**将审查推给 agent。**

我们推动几乎所有审查工作由 agent 到 agent 处理。人类可以审查 PR——但不是必需的。Codex 被指示：在本地审查自己的变更 → 请求额外的特定 agent 审查（本地和云端）→ 响应任何 agent 或人类反馈 → 在循环中迭代直到所有 agent 审查者满意。

### 决策六：垃圾回收——用"黄金原则"对抗熵增

**不可避免的问题：**

Agent 会复制仓库中已有的模式——包括不均匀的、次优的模式。随时间推移——这是熵增的必然。

**最初的人类应对——手动清理：**

团队每周五花 20% 的时间清理"AI slop"。这不可扩展。

**正确的方案——编码清理规则，让 agent 自己清理：**

我们把"黄金原则"直接编码进仓库。这些是有意见的、机械的规则：

1. 偏好共享工具包而不是手写的辅助函数——保持不变量集中
2. 不要"YOLO 式"探测数据——验证边界或依赖有类型的 SDK——这样 agent 不会意外地基于猜测的形状构建

在固定的节律上，一组后台 Codex 任务扫描偏离、更新质量评分、打开定向重构 PR。**大多数可以在不到一分钟内审查并自动合并。**

**这像垃圾回收：** 技术债务是高利贷——持续小额偿还几乎总是比让它复利后再做痛苦的爆发式清理更好。人类的品味被捕获一次——然后在每一行代码上持续强制执行。

## 问题二：你解决过最难的问题是什么？

### 情境与任务

一个完全由 agent 生成的 100 万行代码库。3 个人类工程师。1500 个 PR。零行手写代码。

问题不是"写代码"——agent 能写。问题是**在 agent 以人类不可能达到的吞吐量生成代码时，如何保持代码库的连贯性、可维护性和架构完整性？**

人类审查跟不上。人类 QA 跟不上。人类对"这段代码应该长什么样"的直觉跟不上。

### 行动

**失败的直觉——人类作为质量闸门：**

最初我们假设人类审查是质量保证的最终防线。人类读 PR、找问题、给反馈。但随着 agent 吞吐量增长——人类变成了瓶颈。每个 PR 都在等人类。人类在审查 50 个 PR 后注意力衰减。Agent 等待人类反馈的延迟开始吞噬整个系统的吞吐量。

**第二个失败直觉——大 AGENTS.md：**

我们尝试把所有规则编码成一个大文件。Agent 读它——然后要么忽略它（因为太多内容），要么过度优化某些规则而忽视其他，要么基于过时的信息做出错误决策。当文件腐烂时——agent 既遵循了过时的规则，又忽视了最新的规则。

**亲手解剖——我们如何理解瓶颈：**

我们追踪了 agent 失败的根本原因。不是"agent 不够聪明"——而是：

1. **Agent 缺乏足够的上下文来做决策。** 它能看到代码，但看不到为什么代码长这样——架构决策在 Slack 里、在 Google Docs 里、在人脑里。

2. **Agent 缺乏边界感。** 它不知道"这里的依赖方向必须是从左到右"——因为这条规则没有被编码。它在没有地图的情况下穿越代码库——每次 PR 都可能意外地跨越了不应该跨越的边界。

3. **Agent 复制了它看到的——包括坏的。** 仓库里已有的不均匀模式被 agent 识别为"这就是这里做事情的方式"——然后复制、扩散。

4. **人类无法以 agent 的速度 QA。** 当 agent 每小时产生多个 PR 时——人类 QA 不可能验证每一个 PR 的 UI 行为、API 正确性、架构符合性。

**洞察时刻——"让 agent 自己审查自己，但给它们审查所需的全部信息"：**

两个同时发生的洞察改变了方向：

**洞察一**：人类审查不是唯一的审查。Agent 可以审查 agent——**如果它们被给定了明确的审查标准和工具。**

我们把 Chrome DevTools Protocol 接入 agent 运行时，创建了操作 DOM 快照、截图和导航的技能。Codex 可以启动应用的独立实例（每个 git worktree 一个），直接操作 UI，复现 bug，验证修复。Agent 可以查询日志（LogQL）和指标（PromQL）——不需要人类在中间。

**洞察二**：代码库的连贯性不是来自人类审查每一行——是来自**机械地强制执行的架构约束。** 自定义 linters + 结构测试 = agent 每次提交时都在被自动检查。不需要人类判断"这个依赖方向对吗"——lint 自动报错。

### 破坏性解决方案——四层防线：

**第一层——架构即代码：** 每个业务领域被划分为固定的层次。依赖方向被机械验证。"Taste invariants"（品味不变量）被编码为 lint 规则。错误消息向 agent 注入修复指令。

**第二层——仓库即真值：** 所有知识必须在仓库内。文档、设计决策、架构地图、质量评分、执行计划——全部在仓库中，版本化，交叉链接，被 linter 验证新鲜度。

**第三层——Agent 自审查：** Codex 在本地审查自己的变更。请求额外的 agent 审查。在循环中迭代直到所有 agent 审查者满意。人类可以审查——但不是必需的。

**第四层——垃圾回收：** 定期的后台 Codex 任务扫描偏离"黄金原则"的地方，打开定向重构 PR。人类的品味捕获一次——在所有代码上持续强制执行。

### Case Study：让应用对 agent 可读

我们做了几件反直觉的事：

- 让应用按 git worktree 独立启动——每个 PR 一个实例，agent 可以直接操作。
- 把 Chrome DevTools Protocol 接入 agent 运行时——agent 可以截图、导航、操作 DOM、复现 bug。
- 把可观测性工具暴露给 agent——LogQL 查询日志，PromQL 查询指标。Agent 不需要人类帮它看"发生了什么"。
- 观察栈是临时的——每个 worktree 有独立的日志和指标，任务完成时拆除。

结果是：**Codex 单次运行可以在一个任务上连续工作超过六小时（经常在人类睡觉的时候）。**

Prompt 如"确保服务启动在 800ms 内完成"或"这四个关键用户旅程中的任何 span 不超过两秒"——变得可处理。不是因为 agent 更聪明了——是因为 agent 终于有了**可见性**。

### 结果

| 指标 | 数字 |
|------|------|
| 代码库规模 | ~100 万行 |
| 时间跨度 | 5 个月 |
| 人类工程师 | 3 → 7 人 |
| 手写代码 | 0 行 |
| 总 PR 数 | ~1500 |
| 吞吐量 | 3.5 PRs/工程师/天（且增长中） |
| 构建速度 | 约手写的 1/10 |
| 用户 | 数百内部用户 + 外部 alpha |

**最近的突破——端到端自主 feature 开发：**

系统最近跨越了一个有意义的门槛：给定一个 prompt——agent 可以验证代码库状态 → 复现 bug → 录制失败视频 → 实现修复 → 验证修复 → 录制成功视频 → 开 PR → 响应 agent 和人类反馈 → 检测和修复构建失败 → 仅在需要判断时升级给人类 → **合并变更。**

**我必须承认的局限：**

- 这在很大程度上依赖于这个仓库的特定结构和工具。不要假设它能在没有类似投资的情况下泛化——至少现在不能。
- 我们还不知道在完全 agent 生成的系统中，架构连贯性在数年中如何演变。
- 人类判断在哪些地方增加最多杠杆——这仍然在探索中。
- 系统如何随着模型持续变得更强大而演变——未知。

**最核心的教训：**

**构建软件仍然需要纪律——但纪律更多地体现在脚手架中，而不是代码中。** 让代码库保持连贯的工具、抽象和反馈循环变得越来越重要。人类的工作不是写代码——是设计环境、指定意图、构建反馈循环——让 agent 做可靠的工作。

我们最困难的挑战现在集中在：**设计环境、反馈循环和控制系统，帮助 agent 实现我们的目标——大规模构建和维护复杂、可靠的软件。**

---

*这个分析用第一性原理拆解了 OpenAI 的 Agent 优先工程范式。核心洞察：零手写代码不是噱头——是强迫函数，强制团队在 agent 失败时改进环境而不是手写绕过。人类的角色从"编码者"变成"环境设计师"——而环境设计的核心是把知识、约束、反馈全部编码进仓库中 agent 可以访问的形式。架构约束不是束缚——是倍增器：规则一旦编码，在每一行代码上同时生效。最小阻塞合并门的社会契约是"修正便宜，等待昂贵"——在一个 agent 吞吐量远超人类注意力的系统中，这是唯一可持续的策略。*
