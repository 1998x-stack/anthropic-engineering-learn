# Phase 3 — Safe local content pipeline

\`python -m ael\` is the single **supported maintenance entrypoint**. No network crawler is invoked here. Historical scraping scripts remain untouched archives until their extraction quality, output paths, and legal/source checks have been reviewed. Python >=3.11; standard library only.

## Commands

\`\`\`bash
PYTHONPATH=src python -m ael plan               # full read-only preview
PYTHONPATH=src python -m ael ingest             # discover unregistered local source files
PYTHONPATH=src python -m ael ingest --write     # append discovered files + reconcile (explicit)
PYTHONPATH=src python -m ael normalize          # preview canonical metadata extraction
PYTHONPATH=src python -m ael validate           # schema/path/ref checks from Registry
PYTHONPATH=src python -m ael reconcile          # preview metadata and audit changes
PYTHONPATH=src python -m ael reconcile --write  # explicitly regenerate Registry + audit
PYTHONPATH=src python -m ael publish            # preview static catalog generation
PYTHONPATH=src python -m ael publish --write    # generate ONLY docs/catalog.json
PYTHONPATH=src python -m ael publish --check    # check output catalog reproducibility
PYTHONPATH=src python -m ael check              # full read-only CI integrity check
\`\`\`

The build pipeline is:

**Local inventory (Ingest) → field extraction (Normalize) → integrity checks (Validate) → provenance reconciliation (Reconcile) → JSON catalog (Publish).**

New remote article *fetching* and automatic HTML content reconstruction are deliberately excluded from this first safe pipeline. Ingest here means registering existing reviewed local files, not downloading unknown website pages.

## Write boundaries

Only these paths are written, and **only** on an explicit \`--write\`:

- \`registry/records.jsonl\`: authoritative content records
- \`registry/audit-report.json\`: all field conflicts / legacy integrity findings
- \`docs/catalog.json\`: machine-readable site catalog generated by Pages CI

Original Markdown, PDFs, \`_meta/\`, \`index.json\`, and existing HTML are **read-only**. Write operations use temporary files and atomic-per-file replacement; an interruption between the two Registry outputs may require re-running reconciliation. CI detects drift.

The GitHub Pages job regenerates \`docs/catalog.json\` inside the build workspace before uploading the static site; it does not commit generated site data into Git. Existing HTML design remains unchanged. The catalog includes only registered \`publication_status=published\` pages and may intentionally omit historical unmapped pages.

## Legacy scripts: migration status

Historical scripts are *not* part of the supported pipeline or CI:

- \`_scripts/*.py\` — old fetch/refetch, cleanup/dedup, index rebuilds; some can delete or overwrite content and use outdated relative roots
- \`langchain/fetch_blog.py\`, \`llamaindex/fetch_blog.py\` — old crawlers, rely on /tmp URL lists and can overwrite content
- \`langchain/classify_and_index.py\`, \`llamaindex/build_index.py\` — legacy categorization and index writers
- \`scripts/gen_langchain_html_batch3.py\`, \`scripts/rebuild_index_pages.py\` — historical static-HTML generators, not used for deploy

Do **not** run these against the main content tree without a snapshot/diff review. This stage fixes two known portability defects but does not certify legacy scrapers safe; migration to source-specific adapters is future work.
